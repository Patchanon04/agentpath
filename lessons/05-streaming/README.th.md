## 1. ปัญหาที่ค้างมาจากบทที่ 04

บทที่ 04 ให้ agent ที่ทำงานได้จริงกับคุณ มันถามโมเดล รัน tool ที่โมเดลขอ ส่งผล
ลัพธ์กลับไป แล้วถามอีกจนกว่าโมเดลจะตอบเป็นถ้อยคำ มันถูกต้อง แต่ในฐานะสิ่งที่
คุณต้องนั่งจ้อง มันก็ชวนอึดอัดอยู่นิด ๆ

ลองรันแล้วดูว่า terminal ของคุณทำอะไร

```text
$ python agent.py
                                      <- nothing
                                      <- still nothing
                                      <- still nothing
[calling add with {'a': 2, 'b': 3}]
[add returned 5]
                                      <- nothing again
The answer is 5.
```

ถ้าเจอกับโมเดลที่โฮสต์ไว้และเร็ว ช่วงเงียบนั้นแค่วินาทีสองวินาที คุณแทบไม่
สังเกต แต่ถ้าเป็นโมเดลที่รันบนแล็ปท็อปของคุณเอง มันอาจนานยี่สิบหรือสามสิบ
วินาที และสามสิบวินาทีที่เคอร์เซอร์ไม่ขยับไม่ได้ให้ความรู้สึกเหมือนกำลังรอ
มันให้ความรู้สึกเหมือนโปรแกรมพัง คุณจะเริ่มสงสัยว่าพิมพ์ URL ผิดหรือเปล่า
process ค้างหรือเปล่า ควรกด control C ดีไหม และหลายครั้งคุณจะกด control C ใส่
โปรแกรมที่กำลังจะสำเร็จอยู่แล้ว

ต้นเหตุอยู่ในบรรทัดเดียวของ `llm.py` ในบทที่ 04

```python
response = httpx.post(
    f"{base_url}/chat/completions", json=payload, headers=headers, timeout=120
)
```

`httpx.post` จะไม่คืนค่าจนกว่าเซิร์ฟเวอร์จะเขียน response body จบทั้งก้อน โมเดล
สร้างคำตอบทีละ token ใช้เวลาหลายวินาที และเซิร์ฟเวอร์ก็เก็บ token ทุกตัวไว้จนกว่า
ตัวสุดท้ายจะเกิดขึ้น แล้วค่อยส่งมาทั้งกอง โปรแกรมของคุณถูกบล็อกอยู่ที่บรรทัด
เดียวตลอดการ generate และไม่มีอะไรให้แสดงเลยจริง ๆ เพราะยังไม่ได้รับอะไรเลย

นี่ไม่ใช่ปัญหาด้าน performance streaming ไม่ได้ทำให้โมเดลเร็วขึ้น เวลารวมตั้งแต่
คุณกดปุ่มจนถึงคำสุดท้ายเท่าเดิมทั้งสองแบบ สิ่งที่เปลี่ยนคือคำแรกโผล่มาเกือบจะ
ทันทีแทนที่จะโผล่ตอนจบ และโปรแกรมที่แสดงความคืบหน้าให้ความรู้สึกว่ามีชีวิต ส่วน
โปรแกรมที่ไม่แสดงอะไรเลยให้ความรู้สึกว่าพัง ความต่างด้านความรู้สึกนี้แหละคือ
เหตุผลทั้งหมดที่ chat product ทุกตัวที่คุณเคยใช้พิมพ์คำตอบออกมาให้คุณดูทีละนิด

ยังมีเหตุผลที่สอง ซึ่งเห็นได้ยากกว่าแต่ใช้งานได้จริงมากกว่า เมื่อ output มาถึง
ทีละส่วน คุณก็จัดการมันทีละส่วนได้ คุณ print มันได้ log มันได้ สแกนหาวลีที่ใช้
หยุดได้ หรือตัดการเชื่อมต่อทิ้งเมื่อโมเดลเริ่มออกทะเล ทั้งหมดนี้ทำไม่ได้เลยถ้า
สิ่งแรกที่คุณรู้เกี่ยวกับคำตอบคือมันเสร็จแล้ว

## 2. server sent events คืออะไร และอ่านด้วยตาเปล่าอย่างไร

server sent events หรือที่มักย่อว่า SSE คือรูปแบบที่ provider ใช้ส่ง response
ให้คุณเป็นชิ้น ๆ มันเป็นรูปแบบข้อความที่ส่งผ่าน HTTP response body ธรรมดา และ
เล็กพอที่จะอธิบายได้ครบในหัวข้อเดียว

### กฎของรูปแบบนี้

stream คือลำดับของ event หนึ่ง event คือหนึ่งบรรทัดหรือมากกว่า และบรรทัดว่าง
คือจุดจบของ event บรรทัดที่ขึ้นต้นด้วย `data: ` คือบรรทัดที่พา payload มา และ
ทุกอย่างหลังจาก prefix หกตัวอักษรนั้นคือเนื้อ payload บรรทัดที่ขึ้นต้นด้วย
prefix อื่นก็มีอยู่ในมาตรฐานฉบับเต็ม เช่น `event: ` และ `id: ` แต่ provider ที่
เราสนใจไม่ได้ใช้มันตรงนี้ อะไรที่คุณไม่รู้จักก็ข้ามไป

นั่นคือ specification ทั้งหมดที่คุณต้องรู้ นี่คือชิ้นส่วนจริง ตรงตามที่ fake
server ของโปรเจกต์นี้เขียนออกมาเมื่อคุณขอให้โมเดลทักทาย

```text
data: {"choices": [{"index": 0, "delta": {"content": "Hello "}}]}

data: {"choices": [{"index": 0, "delta": {"content": "from t"}}]}

data: {"choices": [{"index": 0, "delta": {"content": "he moc"}}]}

data: {"choices": [{"index": 0, "delta": {"content": "k serv"}}]}

data: {"choices": [{"index": 0, "delta": {"content": "er."}}]}

data: {"choices": [{"index": 0, "delta": {}, "finish_reason": "stop"}]}

data: [DONE]

```

ดูบรรทัดว่างพวกนั้นให้ดี มันไม่ใช่การจัดหน้าให้คุณอ่านสบายตา มันคือตัวคั่นที่
บอกว่า event หนึ่งจบแล้วและอีก event หนึ่งอาจเริ่มได้ เซิร์ฟเวอร์เขียนมันลงไป
โดยตั้งใจ คุณเห็นมันทำแบบนั้นได้ใน `mock_server.py`

```python
for event in events:
    self.wfile.write(f"data: {json.dumps(event)}\n\n".encode())
    self.wfile.flush()
self.wfile.write(b"data: [DONE]\n\n")
```

`\n\n` คือจุดจบบรรทัดของบรรทัด data ตามด้วยบรรทัดว่างที่ใช้คั่น ส่วน `flush`
คือสิ่งที่ทำให้มันเป็น streaming แทนที่จะเป็นการ buffer เพราะถ้าไม่มีมัน
ระบบปฏิบัติการจะเก็บ byte ไว้อย่างสบายใจจนกว่าจะมีปริมาณมากพอที่จะส่ง

### ชิ้นส่วนภายใน payload

ทีนี้ดูว่าข้างใน event หนึ่ง ๆ มีอะไร

```json
{"choices": [{"index": 0, "delta": {"content": "Hello "}}]}
```

เทียบกับ body แบบไม่ stream ที่คุณ parse ในบทที่ 03

```json
{"choices": [{"index": 0, "message": {"role": "assistant", "content": "Hello from the mock server."}}]}
```

ต่างกันสองจุด และมีแค่สองจุด key คือ `delta` แทนที่จะเป็น `message` และค่าของมัน
คือชิ้นส่วน ไม่ใช่ของทั้งก้อน เปลือกนอกเหมือนกันเป๊ะ ซึ่ง provider ตั้งใจทำแบบ
นั้นและสะดวกกับเรา เพราะ `json.loads(data)["choices"][0]` หมายถึงสิ่งเดียวกันใน
ทั้งสองโลก

สังเกตว่าชิ้นส่วนพวกนี้ไม่ใช่คำ `"from t"` ตัดคำว่า "the" ขาดครึ่ง streaming พา
อะไรก็ตามที่ tokeniser ผลิตออกมา และขอบเขตของ token ไม่เกี่ยวอะไรกับขอบเขตของคำ
ถ้าคุณเขียนโค้ดที่สมมติว่าชิ้นส่วนหนึ่งคือหนึ่งคำ หรือชิ้นส่วนจบที่ช่องว่าง
มันจะทำงานได้ราวหนึ่งสัปดาห์แล้วก็ทำคุณขายหน้า

### สอง event สุดท้าย

event รองสุดท้ายคือตัวที่ delta ว่างเปล่า

```text
data: {"choices": [{"index": 0, "delta": {}, "finish_reason": "stop"}]}
```

ไม่มีอะไรใหม่มาถึง provider กำลังบอกคุณว่าทำไมการ generate ถึงหยุด `stop`
หมายความว่าโมเดลจบประโยคและเลือกที่จะหยุดเอง `tool_calls` หมายความว่ามันหยุด
เพราะต้องการให้รัน tool `length` หมายความว่ามันชนขีดจำกัด output token และถูกตัด
ซึ่งจะสำคัญมากในหัวข้อ 6

event สุดท้ายคือ sentinel

```text
data: [DONE]
```

payload นั้นไม่ใช่ JSON มันคืออักขระสี่ตัว `[DONE]` เท่านั้น ถ้าคุณโยนมันให้
`json.loads` คุณจะได้ exception ซึ่งเป็นพิธีกรรมที่ทุกคนที่เขียน streaming
client ตัวแรกต้องผ่าน มันมีอยู่เพราะ stream ต้องมีเครื่องหมายจบที่ชัดเจนและ
แยกออกจากการที่การเชื่อมต่อหลุด ถ้าไม่มีมัน client ที่หยุดได้รับ byte จะแยกไม่
ออกระหว่าง "โมเดลทำงานเสร็จแล้ว" กับ "wifi ของคุณตาย" และสองสถานการณ์นั้น
ต้องการพฤติกรรมที่ต่างกันมาก

### ทำไมต้องรูปแบบนี้ ไม่ใช่ websockets

คำถามที่ผุดขึ้นทันทีคือทำไม provider ไม่ใช้ websockets ไปเลย ซึ่งใคร ๆ ก็เคย
ได้ยินและถูกสร้างมาเพื่อผลักข้อมูลไปหา client มีสามเหตุผล และทั้งสามชี้ไป
ทางเดียวกัน

หนึ่ง traffic นี้ไปทางเดียว คุณส่ง request เซิร์ฟเวอร์ส่งคำตอบเป็นชิ้น ๆ จบ
websockets ให้ช่องทางแบบ full duplex ที่ทั้งสองฝั่งพูดได้ตลอดเวลา คุณจะจ่ายค่า
ความสามารถที่ไม่มีวันได้ใช้

สอง นี่คือ HTTP response ธรรมดา status line, header, bearer token และ body
ทำงานเหมือน request อื่น ๆ ทุกประการ นั่นแปลว่า proxy, load balancer,
firewall ขององค์กร, CDN และ HTTP library ทุกตัวบนโลกรองรับมันอยู่แล้ว ส่วน
websockets ต้องการ upgrade handshake ที่โครงสร้างพื้นฐานเครือข่ายจำนวนน่า
ตกใจบล็อกหรือทำพัง และต้องการการรองรับจาก library ที่ภาษาของคุณอาจมีหรือไม่มี

สาม มันไม่ต้องการ protocol เพิ่มซ้อนทับ ลองดูอีกทีว่าคุณต้องทำอะไรบ้างเพื่อ
บริโภคมัน แยกบรรทัดตาม newline เก็บบรรทัดที่ขึ้นต้นด้วย prefix หยุดเมื่อเจอ
sentinel นั่นคือโค้ดสิบกว่าบรรทัดโดยไม่ต้องพึ่ง dependency ส่วน websocket
client คือ dependency หนึ่งตัว บวก handshake บวกชั้น framing บวก ping และ pong
keepalive บวกเรื่องราวของการ reconnect

สิ่งที่ต้องแลกคือคุณส่งอะไรไปหาเซิร์ฟเวอร์ไม่ได้อีกเมื่อ request ออกไปแล้ว
และเนื่องจากคุณไม่มีอะไรจะส่งอยู่แล้ว การแลกนี้จึงไม่มีต้นทุนอะไรเลย

## 3. ภาคหนึ่ง การ stream ข้อความ

ทีนี้เปิด `llm.py` แล้วอ่านครึ่งแรกของฟังก์ชัน signature เปลี่ยนไปแล้ว

```python
def complete_stream(messages, tools=None, on_text=None):
    """Stream one reply. Returns (text, tool_calls).

    on_text is called with every piece of text as it arrives.
    """
```

มันเป็นชื่อใหม่แทนที่จะไปแก้ `complete` เพื่อให้คุณวางบทที่ 04 กับบทที่ 05
เทียบกันแล้ว diff ได้ มีพารามิเตอร์ใหม่หนึ่งตัวคือ `on_text` และเราจะกลับมาที่
มันในอีกสักครู่

environment variables, header และ bearer token เหมือนบทที่ 03 และบทที่ 04
ทุกไบต์ มีแค่บรรทัดเดียวของ request ที่เปลี่ยน

```python
payload = {"model": model, "messages": messages, "stream": True}
```

key ตัวเดียวนั้นคือสิ่งที่เปลี่ยน response จาก JSON หนึ่งชุดให้กลายเป็น SSE
stream มันคือการร้องขอรูปแบบ response ที่ต่างออกไป แค่นั้นเอง โมเดล prompt และ
tool ทั้งหมดไม่เปลี่ยน และคำตอบที่คุณประกอบขึ้นในที่สุดก็เป็นคำตอบเดียวกัน

### stream context manager

นี่คือรูปร่างของโค้ดส่วนอ่าน

```python
with httpx.Client(timeout=120) as client:
    with client.stream(
        "POST", f"{base_url}/chat/completions", json=payload, headers=headers
    ) as response:
        response.raise_for_status()
        for line in response.iter_lines():
            ...
```

มีสามเรื่องเกิดขึ้น และแต่ละเรื่องควรได้คำอธิบายสักประโยค

`httpx.Client` คือ connection pool ที่มีอายุขัย ฟังก์ชันอำนวยความสะดวก
`httpx.post` ที่คุณใช้ในบทที่ 04 สร้างตัวนี้ขึ้นมาภายในสำหรับ request เดียวแล้ว
ทิ้งไป เมื่อคุณจะถือ connection เปิดค้างไว้ระหว่างอ่านจากมัน คุณอยากให้ object
อยู่ใน scope เราจึงสร้างมันขึ้นมาตรง ๆ แล้วให้บล็อก `with` ปิดมัน

`client.stream` คือการเปลี่ยนแปลงสำคัญ ในขณะที่ `httpx.post` คืนค่าหลังจาก
ดาวน์โหลด body ครบแล้ว `client.stream` คืนค่าทันทีที่ status line และ header มา
ถึง โดยที่ body ยังเปิดอยู่และยังทยอยมา มันต้องถูกใช้เป็น context manager
เพราะตอนนี้มี socket ที่เปิดอยู่และต้องมีใครสักคนปิดมัน ไม่ว่า loop ของคุณจะจบ
ตามปกติ break ออกก่อน หรือ raise บล็อก `with` คือใครคนนั้น ถ้าคุณลองใช้
response หลังจากบล็อกจบแล้ว httpx จะบอกคุณว่า stream ปิดแล้ว และมันก็ถูกที่ทำ
แบบนั้น

`response.raise_for_status()` ยังใช้ได้ตรงนี้เพราะ status code มาพร้อม header
ก่อน body ใด ๆ 401 หรือ 500 จะถูกจับได้ก่อนที่คุณจะเสียเวลา parse ชิ้นส่วนของ
หน้า error

`response.iter_lines()` คือ generator ทุกครั้งที่ loop ขอค่าจากมัน มันจะยื่น
บรรทัดสมบูรณ์บรรทัดถัดไปที่มาถึง โดยถอดรหัสจาก byte เป็น `str` และตัด newline
ท้ายออกแล้ว เมื่อยังไม่มีอะไรมาถึง มันจะบล็อกและรอ เมื่อ body จบ มันก็หยุด
บรรทัดว่างที่ใช้คั่นจะมาเป็น string ว่าง ซึ่งสะดวกดี เพราะ string ว่างไม่ได้
ขึ้นต้นด้วย `data: ` ตัวกรองของเราจึงทิ้งมันไปได้โดยไม่ต้องมีเคสพิเศษ

### เนื้อในของ loop

```python
for line in response.iter_lines():
    if not line.startswith("data: "):
        continue
    data = line[len("data: ") :]
    if data == "[DONE]":
        break
    delta = json.loads(data)["choices"][0].get("delta", {})
```

ไล่ทีละบรรทัด

ตัวป้องกัน `startswith` โยนบรรทัดว่างที่ใช้คั่นทิ้ง รวมถึงบรรทัด comment หรือ
keepalive ที่ provider อาจส่งมา และอะไรก็ตามที่เราไม่เข้าใจ การใจกว้างเรื่อง
สิ่งที่คุณข้ามคือสิ่งที่ทำให้โค้ดนี้ยังทำงานได้ข้าม provider ที่ต่างคนต่างเติม
ของประดับของตัวเอง

การ slice `line[len("data: ") :]` ตัด prefix หกตัวอักษรออก การเขียน
`len("data: ")` แทนเลข 6 แปลว่าไม่มีใครต้องนับตัวอักษรเพื่อตรวจโค้ด และไม่มีใคร
เผลอทิ้งช่องว่างนำหน้าไว้ใน payload

การเช็ก `[DONE]` มาก่อนการ parse ไม่ใช่หลัง นี่คือแนวป้องกันทั้งหมดต่อ
exception ที่พูดถึงในหัวข้อ 2 และตำแหน่งของมันในฟังก์ชันคือเคล็ดลับทั้งหมด

ใช้ `.get("delta", {})` แทน `["delta"]` เพราะ event สุดท้ายก่อน `[DONE]` พา
`finish_reason` มา และอาจไม่มี delta เลย หรือมีแบบว่างเปล่า การไปหยิบ key ที่
ไม่มีอยู่จะ raise ตอน event รองสุดท้ายของ stream ที่สำเร็จโดยสมบูรณ์ ซึ่งเป็น
บั๊กที่ตามหาแล้วชวนคลั่ง

### สะสมและเรียก callback ไปพร้อมกัน

```python
if delta.get("content"):
    text_parts.append(delta["content"])
    if on_text:
        on_text(delta["content"])
```

ชิ้นส่วนข้อความทุกชิ้นทำงานสองอย่าง และเรื่องนี้ควรพูดให้ชัดเพราะมันดูซ้ำซ้อน
ตอนอ่านครั้งแรก

`text_parts.append` คือการสะสม ตอนจบฟังก์ชัน `"".join(text_parts)` จะสร้าง
คำตอบฉบับสมบูรณ์ขึ้นมาใหม่ เราต้องการมันเพราะคำตอบต้องกลับเข้าไปใน `messages`
ในฐานะเนื้อหาของ assistant turn ประวัติบทสนทนาไม่ใช่ stream มันคือ list ของ
message ทั้งก้อน และโมเดลใน turn ถัดไปต้องเห็นข้อความเต็มของสิ่งที่มันพูดไปครั้ง
ก่อน การเก็บชิ้นส่วนสามสิบชิ้นคือการเก็บเรื่องของชั้นขนส่งราวกับว่ามันเป็นเรื่อง
ของบทสนทนา

การเรียก `on_text` คือการส่งมอบ มันยื่นแต่ละชิ้นให้กับใครก็ตามที่ขอไว้ ณ วินาที
ที่ชิ้นนั้นเกิดขึ้น ใน `agent.py` ผู้เรียกคนนั้นคือ lambda บรรทัดเดียว

```python
text, calls = complete_stream(
    messages, tools.SCHEMAS, on_text=lambda piece: print(piece, end="", flush=True)
)
```

`end=""` เพราะชิ้นส่วนมี newline ที่ควรอยู่ในคำตอบมาอยู่แล้ว และ `flush=True`
เพราะ Python buffer standard output ไว้ ไม่อย่างนั้นมันจะนั่งทับข้อความที่คุณ
อุตส่าห์ stream มาสวย ๆ จนกว่าบรรทัดจะจบ ซึ่งจะล้มบทเรียนนี้ทั้งบท

ทีนี้ ทำไมต้องเป็น callback แทนที่จะทำให้ `complete_stream` เป็น generator ที่
yield ชิ้นส่วนออกมา ทั้งสองแบบใช้ได้ และ library จริงก็มีทั้งสองแบบ แต่ callback
ชนะตรงนี้ด้วยเหตุผลเฉพาะเจาะจง generator จะต้อง yield ของสองชนิดที่ต่างกัน คือ
ชิ้นส่วนข้อความระหว่าง stream และ list ของ tool call ตอนจบ แล้วผู้เรียกก็ต้องมา
คัดแยกเอง นั่นคือการดันความรู้เรื่อง protocol ขึ้นไปอยู่ใน `agent.py` ซึ่งเป็น
ที่ที่เราไม่อยากให้มันอยู่เลย ด้วย callback `complete_stream` ยังคง return type
แบบบทที่ 04 คือ `(text, calls)` agent loop ยังคงรูปร่างเดิม และ streaming
กลายเป็นช่องทางเสริมที่คุณเมินได้ทั้งหมดด้วยการไม่ส่งอะไรเข้าไป ดู `check.py`
เป็นหลักฐานว่าการเมินมันไม่มีปัญหา

```python
_, calls = complete_stream([{"role": "user", "content": PROMPT}], tools.SCHEMAS)
```

ไม่มี `on_text` ไม่มีการพิมพ์ ค่าที่คืนเหมือนเดิม ผู้เรียกสองรายที่ต้องการต่างกัน
ฟังก์ชันเดียว ไม่มีการแตกกิ่ง

### พิสูจน์ว่าชิ้นส่วนรวมกันแล้วถูกต้อง

ครึ่งแรกของ `check.py` ทดสอบคุณสมบัติที่สำคัญพอดีเป๊ะ

```python
pieces = []
text, _ = complete_stream(
    [{"role": "user", "content": "Say hello."}], None, on_text=pieces.append
)
if len(pieces) < 2:
    print(f"FAIL the reply did not arrive in pieces. Got {len(pieces)} piece(s)")
    sys.exit(1)
if "".join(pieces) != text:
    print("FAIL the streamed pieces do not add up to the final text")
    sys.exit(1)
print(f"OK text arrived in {len(pieces)} pieces")
```

การส่ง `pieces.append` เป็น callback เป็นลูกเล่นเนียน ๆ ที่ควรขโมยไปใช้ bound
method ของ list เองก็เป็นฟังก์ชันที่รับหนึ่ง argument และบันทึกสิ่งที่ได้รับอยู่
แล้ว คุณจึงได้ตัวบันทึกมาโดยไม่ต้องเขียนเอง

การยืนยันสองข้อนั้นคือสองทางที่ streaming จะทรยศคุณได้ ถ้าได้ชิ้นส่วนน้อยกว่า
สองชิ้นแปลว่าคุณไม่ได้ stream จริง คุณแค่ได้คำตอบทั้งก้อนมาใน event เดียวและไม่
เคยได้ทดสอบการสะสมเลย ส่วนชิ้นส่วนที่ต่อกลับแล้วไม่ตรงกับข้อความที่คืนมาแปลว่า
คุณทำหล่นหรือทำซ้ำบางอย่าง ซึ่งเป็นความล้มเหลวที่ผลิตคำตอบที่หายไปหนึ่งคำตรง
กลาง


## 4. ภาคสอง การ stream tool calls

นี่คือครึ่งที่ยาก ทุกอย่างจนถึงตรงนี้เป็นแค่งานจดบัญชี สิ่งที่ตามมาคือส่วนที่วิธี
ที่ดูชัดเจนนั้นผิด และเหตุผลก็ไม่ชัดเจน

### สิ่งที่ทำให้วิธีที่ดูชัดเจนพัง

ในบทที่ 03 tool call มาถึงเป็น object หนึ่งตัวพร้อม string ของ arguments ที่
สมบูรณ์

```json
{
  "id": "call_mock_1",
  "type": "function",
  "function": {"name": "add", "arguments": "{\"a\": 2, \"b\": 3}"}
}
```

ตรงนั้นคุณได้เรียนว่า `arguments` คือ string ที่บรรจุ JSON ไม่ใช่ object และ
`json.loads` เปลี่ยนมันเป็น dictionary ก็ดี

streaming เอา string นั้นมาหั่นเป็นชิ้น ๆ เพราะโมเดลผลิตมันทีละ token เหมือนกับ
ที่ผลิตร้อยแก้ว นี่คือ stream จริงของ `add` โดยที่ `a` เท่ากับ 2 และ `b` เท่ากับ
3 คัดลอกมาจาก fake server ของโปรเจกต์นี้ ซึ่งหั่น arguments ของ tool เป็นก้อนละ
ห้าตัวอักษร

```text
data: {"choices": [{"index": 0, "delta": {"tool_calls": [{"index": 0, "id": "call_mock_1", "type": "function", "function": {"name": "add", "arguments": ""}}]}}]}

data: {"choices": [{"index": 0, "delta": {"tool_calls": [{"index": 0, "function": {"arguments": "{\"a\":"}}]}}]}

data: {"choices": [{"index": 0, "delta": {"tool_calls": [{"index": 0, "function": {"arguments": " 2, \""}}]}}]}

data: {"choices": [{"index": 0, "delta": {"tool_calls": [{"index": 0, "function": {"arguments": "b\": 3"}}]}}]}

data: {"choices": [{"index": 0, "delta": {"tool_calls": [{"index": 0, "function": {"arguments": "}"}}]}}]}

data: {"choices": [{"index": 0, "delta": {}, "finish_reason": "tool_calls"}]}

data: [DONE]

```

จ้อง event แรกให้ดี มันพา `id`, `type`, `name` และค่า `arguments` ที่เป็น string
ว่างมาด้วย นั่นคือการประกาศตัว provider กำลังบอกคุณว่า tool call กำลังจะเริ่ม
นี่คือใคร เนื้อจะตามมา

ทีนี้จ้องสี่ event ถัดจากนั้น มันไม่มี `id` และไม่มี `name` มีแต่ชิ้นส่วนถัดไป
ของ `arguments` ถ้าลอกเปลือก JSON ออก ข้อความ argument จริง ๆ จะมาถึงแบบนี้

```text
piece 1   {"a":
piece 2    2, "
piece 3   b": 3
piece 4   }
```

นั่นคือชิ้นส่วนจริง โดยเอาการ escape ของรูปแบบสายส่งออกไปแล้ว ทีนี้ลองทำสิ่งที่ดู
สมเหตุสมผลกับมันดู

```python
arguments = json.loads(piece)   # do not do this
```

พังทุกชิ้นไม่มีเหลือ

```text
json.loads('{"a":')   -> JSONDecodeError: Expecting value: line 1 column 6 (char 5)
json.loads(' 2, "')   -> JSONDecodeError: Extra data: line 1 column 3 (char 2)
json.loads('b": 3')   -> JSONDecodeError: Expecting value: line 1 column 1 (char 0)
json.loads('}')       -> JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

ดูชิ้นที่ 2 กับชิ้นที่ 3 เป็นพิเศษ เพราะชิ้นที่ 2 แสดงความล้มเหลวเวอร์ชันที่
อันตรายที่สุด ชิ้นส่วน ` 2, "` ขึ้นต้นด้วยตัวเลข JSON ที่ถูกต้องสมบูรณ์ parser
จึงอ่าน `2` ตัดสินว่ามันได้เอกสารครบแล้ว แล้วค่อยบ่นเรื่อง `, "` ที่ตามมา
ชิ้นส่วนที่ต่างออกไปเล็กน้อยอาจ parse ผ่านฉลุยและยื่นเลข 2 ให้คุณราวกับว่านั่น
คือคำตอบ ซึ่งเป็นผลลัพธ์ที่ผิดแบบเงียบ ๆ แทนที่จะเป็น error ที่ส่งเสียงดัง ส่วน
ชิ้นที่ 3 คือภาพสะท้อนกลับด้าน มันเริ่มด้วยตัวอักษร `b` ซึ่งไม่ใช่ key `b` แต่
เป็นอักขระที่อยู่ข้างใน string ที่เปิดไว้ใน event ก่อนหน้า ไม่มี parser ตัวไหนใน
โลกที่ทำอะไรถูกต้องกับ `b": 3` เพียงลำพังได้

นี่คือแบบจำลองความคิดที่ปลดล็อกหัวข้อนี้ **stream ไม่ได้พาค่า JSON มา มันพา
อักขระของ string มา และ string นั้นบังเอิญบรรจุ JSON เมื่อมันสมบูรณ์แล้ว**
การต่อสตริงคือ operation เดียวที่นิยามไว้กับมัน ส่วนการ parse คือสิ่งที่คุณทำได้
ครั้งเดียว ตอนจบ

### รูปแบบสะสมก่อนแล้วค่อย parse

นี่คือครึ่ง tool call ของ loop ใน `llm.py`

```python
for chunk in delta.get("tool_calls", []):
    index = chunk.get("index", 0)
    slot = partial.setdefault(index, {"id": "", "name": "", "arguments": ""})
    if chunk.get("id"):
        slot["id"] = chunk["id"]
    function = chunk.get("function", {})
    if function.get("name"):
        slot["name"] = function["name"]
    if function.get("arguments"):
        slot["arguments"] += function["arguments"]
```

อ่านมันเป็นสามความคิดที่แยกจากกัน

**buffer ที่มีอยู่ก่อนข้อมูลจะมา** `partial` คือ dictionary ที่ประกาศไว้ข้าง ๆ
`text_parts` ที่ต้นฟังก์ชัน `setdefault` จะคืนรายการที่มีอยู่แล้วของ index นี้
หรือไม่ก็สร้างรายการใหม่ที่มี string ว่างสามตัวแล้วคืนมันมา นั่นแปลว่า event
ประกาศตัวและ event ชิ้นส่วนวิ่งผ่านโค้ดชุดเดียวกันเป๊ะ โดยไม่ต้องมีกิ่ง "นี่ตัว
แรกหรือเปล่า" string ว่างคือค่าศูนย์ที่ถูกต้องตรงนี้ เพราะ string ว่างคือสิ่งที่
คุณได้เมื่อต่ออะไรก็ตามที่ไม่มี

**field ที่เขียนทับ กับ field ที่ต่อท้าย** `id` และ `name` ถูกกำหนดค่าด้วย `=`
ส่วน arguments ถูกต่อท้ายด้วย `+=` ความไม่สมมาตรนั้นคือการออกแบบทั้งหมด อัตลักษณ์
ของ call มาถึงครั้งเดียวและครบถ้วน ส่วน arguments ของมันมาถึงหลายครั้งและมาไม่
ครบ ตัวป้องกัน `if chunk.get("id")` มีอยู่เพราะ event ต่อ ๆ มาไม่มี `id` เลย และ
การกำหนดค่าไปดื้อ ๆ จะเขียนทับตัวระบุที่ดีด้วย `None`

**ไม่มีการ parse ที่ไหนเลยใน loop** ไม่มี `json.loads` แม้แต่ตัวเดียวที่แตะ
`slot["arguments"]` ขณะที่ stream กำลังทำงาน เพราะอย่างที่คุณเพิ่งพิสูจน์ไป มัน
ไม่มีอะไรที่ถูกต้องให้ parse

ทีนี้ถึงการ parse ซึ่งเกิดขึ้นหลังบล็อก `with` ปิดลงและ stream จบแล้ว

```python
calls = []
for _, slot in sorted(partial.items()):
    try:
        arguments = json.loads(slot["arguments"] or "{}")
        error = ""
    except json.JSONDecodeError as problem:
        arguments = {}
        error = f"arguments were not valid JSON ({problem})"
    calls.append(
        {
            "id": slot["id"],
            "name": slot["name"],
            "arguments": arguments,
            "error": error,
        }
    )
return "".join(text_parts), calls
```

ใช้ `sorted(partial.items())` เพราะ dictionary รักษาลำดับการใส่ แต่เราต้องการ
ลำดับตาม index และสองอย่างนั้นตรงกันเฉพาะตอนที่ provider เรียบร้อยเท่านั้น
การเรียงตาม index ที่ provider ให้มาไม่มีต้นทุนอะไร และกำจัดบั๊กทั้งตระกูลที่จะ
โผล่มาเฉพาะกับ endpoint บางตัวเท่านั้น

`or "{}"` สืบทอดมาจากบทที่ 03 และรองรับ tool ที่ไม่รับ argument เลย ซึ่ง

## 5. ทำไม buffer ถึงใช้ index เป็น key

คุณอาจตั้งคำถามที่สมเหตุสมผลกับโค้ดข้างบนได้ ในตัวอย่างมี tool call เดียว แล้ว
ทำไม `partial` ต้องเป็น dictionary ด้วย ทำไมไม่ใช้ตัวแปร string ตัวเดียวที่คุณ
ต่อเข้าไปเรื่อย ๆ

เพราะโมเดลได้รับอนุญาตให้ขอ tool หลายตัวใน turn เดียว และมันก็ทำแบบนั้นจริง
"ทอยลูกเต๋าแล้วบวก 10 เข้าไปในผลลัพธ์" คือหนึ่ง turn ที่มีหนึ่ง tool ส่วน
"ทอยลูกเต๋าและบอกด้วยว่า 2 บวก 3 เท่ากับเท่าไร" คือหนึ่ง turn ที่มีสอง tool และ
โมเดลที่มีเหตุผลจะขอทั้งสองพร้อมกันแทนที่จะเปลือง round trip บทที่ 04 วน loop
บน `calls` อยู่แล้วด้วยเหตุผลนี้เป๊ะ

เมื่อมีสอง call ทุก event ชิ้นส่วนจะพา `index` มาบอกว่ามันเป็นของ call ไหน นี่

ชิ้นส่วนนั้นเป็นของ tool call ตัวไหนใน turn นี้

fake server ของเราสุภาพและจบ call 0 ก่อนจะเริ่ม call 1 provider จริงไม่มีพันธะ
ต้องทำแบบนั้น และบางเจ้าก็ไม่ทำ ชิ้นส่วนของสอง call สลับกันมาได้ เพราะโมเดล
ผลิต token stream เส้นเดียวและ provider แค่ส่งต่อ ลำดับที่คุณได้รับก็คือลำดับที่
โมเดลบังเอิญผลิตออกมา

ทีนี้ลองนึกภาพว่าคุณใช้ตัวแปร string ตัวเดียวแล้วต่อทุกอย่างเข้าไปในนั้น

สับปนกันเหมือนไพ่สองครึ่งสำรับ ข้อมูลว่าอักขระตัวไหนเป็นของ call ไหนถูกโยนทิ้งไป

กลับมาได้

การใช้ index เป็น key ของ buffer คือสิ่งที่แยกสอง stream นี้ออกจากกัน

```python

```

index 0 สะสมลง slot ของตัวเอง index 1 ลง slot ของตัวเอง และไม่มีตัวไหนได้เห็น
อักขระของอีกตัว ตอนจบคุณจะได้ string ที่สมบูรณ์สองเส้นซึ่ง parse ผ่านฉลุยทั้งคู่

มีบทเรียนที่กว้างกว่านี้ซึ่งอยู่ยืนยาวกว่าไฟล์นี้ เมื่อ protocol ยื่นตัวระบุมา
พร้อมกับชิ้นส่วน ตัวระบุนั้นไม่ใช่ของประดับ มันอยู่ตรงนั้นเพราะชิ้นส่วนมาถึงแบบ
ผิดลำดับได้ และคนออกแบบ protocol รู้เรื่องนี้ ถึงแม้ตัวอย่างที่คุณอ่านอยู่จะไม่
ได้แสดงมันก็ตาม โค้ดที่เมินตัวระบุแบบนี้จะทำงานได้เรื่อยไปจนถึงวันที่ลำดับ
เปลี่ยน แล้วก็พังในแบบที่ดูเหมือนโมเดลเสียสติ มากกว่าจะดูเหมือน buffer ของคุณถูก
สับปนกัน

และเหตุผลที่ fake server ของเราไม่สลับลำดับก็ควรพูดให้ตรง ๆ เซิร์ฟเวอร์ทดสอบที่
ให้ผลเหมือนเดิมทุกครั้งควรจำลองรูปร่างของ traffic จริง ไม่ใช่จำลองวันที่แย่ที่สุด
ของมัน การจัดการ index ก็ถูกต้องอยู่แล้ว มันจึงพร้อมเมื่อ provider จริงสลับลำดับ
และคุณจะไม่ต้องมานั่ง debug มันตอนนั้น

## 6. เมื่อ JSON ไม่มีวันจบ

ทุกอย่างในหัวข้อ 4 ตั้งสมมติฐานว่าชิ้นส่วนสุดท้ายจะมาถึงในที่สุด ทีนี้ลองคิดว่า
จะเกิดอะไรขึ้นเมื่อมันไม่มา

ทุกโมเดลมีขีดจำกัด output token บางครั้งมันคือค่าปริยายของ provider บางครั้งคือ
ค่า `max_tokens` ที่คุณตั้งเอง บางครั้งคือโมเดลไปถึงปลาย context window ของมัน
เมื่อการ generate ชนเพดานนั้น provider จะหยุดโมเดลกลางคำแล้วปิด stream มันไม่ใช่
error สถานะ HTTP คือ 200 SSE stream ถูกต้องตามรูปแบบ sentinel `[DONE]` มาถึง
ตรงตามที่ควรเป็น field `finish_reason` บน event รองสุดท้ายบอกว่า `length` แทน
`stop` หรือ `tool_calls` ซึ่งเป็นเบาะแสเดียวที่คุณมี

ถ้าเรื่องนี้เกิดระหว่างร้อยแก้ว คุณจะได้ประโยคที่หยุดกลางคำและมนุษย์จะสังเกตเห็น
แต่ถ้ามันเกิดระหว่าง tool call คุณจะได้สิ่งนี้ใน buffer ของคุณ

```text
{"a": 2, "b
```

อักขระหยุดไปเฉย ๆ ไม่มีเครื่องหมายคำพูดปิด ไม่มีค่าให้ `b` ไม่มีปีกกาปิด และ
`json.loads` ก็บอกแบบนั้น

```text
json.JSONDecodeError: Unterminated string starting at: line 1 column 10 (char 9)
```

ขึ้นอยู่กับว่ารอยตัดไปลงตรงไหน คุณจะได้คำบ่นที่ต่างกัน และทั้งสามแบบนี้เป็นเรื่อง
ธรรมดา

```text
'{"a": 2, "b'    -> Unterminated string starting at: line 1 column 10 (char 9)
'{"a": 2, '      -> Expecting property name enclosed in double quotes: line 1 column 10 (char 9)
'{"a": 2, "b": ' -> Expecting value: line 1 column 15 (char 14)
```

ณ ตอนนี้

มันหยุดการ crash ได้ และมันคือพฤติกรรมที่แย่ที่สุดเท่าที่มีให้เลือก ควรเรียกชื่อ
โหมดความล้มเหลวทั้งสามของมันออกมา เพราะแต่ละอันร้ายกาจกว่าอันก่อนหน้า

**tool ถูกรันโดยไม่มี argument** `tools.run("add", {})` กลายเป็น `add()` ซึ่ง
raise `TypeError: add() missing 2 required positional arguments` ตรงนี้มันถูกจับ

จริงมาวางแทน `delete_files()` โดยไม่มี argument โดยที่พารามิเตอร์ที่ไม่เคยมาถึง

และคำสั่งกว้าง ๆ ที่ยิงใส่ tool ที่ทำลายล้างได้คือหน้าตาของหายนะในรายงาน
incident

**โมเดลไม่มีวันรู้ว่ามันทำผิด** ข้อนี้ละเอียดกว่า และในทางปฏิบัติแย่กว่า โมเดลขอ
`add` พร้อมสอง argument แต่มีบางอย่างปลายทางแอบเขียน request ใหม่เป็น `add` ที่
มีศูนย์ argument ไม่ว่าอะไรจะกลับมา โมเดลก็เห็นผลลัพธ์ของคำถามที่มันไม่ได้ถาม
มันแก้ error ที่ไม่เคยมีใครบอกมันไม่ได้ คุณสมบัติที่มีค่าที่สุดของ agent loop ที่
คุณสร้างในบทที่ 04 คือโมเดลได้อ่านผลของการกระทำของตัวเองแล้วปรับตัว การกลืน

ทำตัวโง่โดยไม่มีเหตุผล

มันขอ `add` โดยไม่มี argument แล้วได้ผลลัพธ์แปลก ๆ และการเดินเรื่องต่อที่มีโอกาส
มากที่สุดจากประวัติแบบนั้นก็คือทำแบบเดิมอีก คุณได้เขียนตัวอย่างที่ไม่ดีลงไปใน
context ของโมเดลเองแล้วขอให้มันเดินตามรูปแบบนั้นต่อ นี่คือวิธีที่ agent ติดอยู่ใน
loop ที่เผา `max_turns` และเงินจริงไปโดยไม่ได้ทำอะไรเลย

### บทเรียนนี้ทำอะไรแทน

`llm.py` บันทึกความล้มเหลวไว้แทนที่จะซ่อนมัน

```python
except json.JSONDecodeError as problem:
    arguments = {}
    error = f"arguments were not valid JSON ({problem})"
```

dictionary ว่างคือตัวยึดที่ทำให้รูปร่างของ record ที่คืนกลับมาคงเส้นคงวา มันไม่
เคยเป็นสิ่งที่ถูกนำไปรัน เพราะ string `error` เดินทางไปกับมันด้วย และ `agent.py`
ตรวจ string นั้นก่อน

```python
for call in calls:
    if call["error"]:
        result = f"Error: {call['error']}. Send the tool call again."
        print(f"\n[{call['name']} was not run because {call['error']}]")
    else:
        print(f"\n[calling {call['name']} with {call['arguments']}]")
        result = tools.run(call["name"], call["arguments"])
        print(f"[{call['name']} returned {result}]")
    messages.append({"role": "tool", "tool_call_id": call["id"], "content": result})
```

คุณสมบัติสามข้อหล่นออกมาจากเจ็ดบรรทัดนั้น

tool ไม่ถูกรัน ไม่มี side effect ใดเกิดขึ้นบนพื้นฐานของ argument ที่เรารู้อยู่
แล้วว่าไม่ครบ

message แบบ `tool` ยังถูกเพิ่มเข้าไป พร้อม `tool_call_id` ที่ตรงกัน นี่ไม่ใช่
มารยาทที่จะข้ามก็ได้ provider กำหนดว่าทุก tool call ใน assistant turn ต้องถูก
ตอบด้วย tool message ที่มี id เดียวกัน และการขาดไปหนึ่งอันคือ 400 ใน request
ถัดไปของคุณ error คือคำตอบที่ใช้ได้ดีอย่างสมบูรณ์

เนื้อหาของ message นั้นเป็นภาษาอังกฤษที่อ่านรู้เรื่อง อธิบายว่าเกิดอะไรผิดพลาด
ตามด้วยคำสั่งว่าต่อไปควรทำอะไร โมเดลอ่านมันใน turn ถัดไปเหมือนที่อ่านผลลัพธ์
tool อื่น ๆ ทุกประการ และผลลัพธ์ตามปกติคือความพยายามครั้งที่สองที่แก้ไขแล้ว
มันได้ผลเพราะโมเดลที่ได้รับ "arguments were not valid JSON" บวกกับคำสั่งให้ลอง
ใหม่ มีข้อมูลมากพอที่จะลงมือ ในขณะที่โมเดลที่ได้รับความเงียบไม่มีอะไรเลย

นี่คือหลักการเดียวกับที่ `tools.run` จับทุก exception แล้วคืนเป็น string ซึ่งคุณ
เจอในบทที่ 03 ความล้มเหลวกลายเป็นข้อความ ข้อความเข้าไปในบทสนทนา และโมเดลได้
ตอบสนองต่อความเป็นจริง agent ที่อ่าน error message ของตัวเองได้มีความสามารถ
มากกว่า agent ที่อ่านไม่ได้อย่างมหาศาล และโค้ดชิ้นเล็ก ๆ ทั้งสองนี้มีอยู่เพื่อ
เปิดช่องทางนั้นค้างไว้

```python
"arguments": json.loads(raw["function"]["arguments"] or "{}"),
```

ไม่มี `try` ไม่มี `except` ไม่มีอะไรเลย ถ้าโมเดลผลิต argument ที่ผิดรูป บรรทัด
นั้นจะโยน `JSONDecodeError` พุ่งขึ้นผ่าน `complete` แล้วออกจากโปรแกรมพร้อม
traceback

นั่นเป็นความตั้งใจ และควรพูดกับคุณตรง ๆ ว่าทำไม เพราะมันเป็นการตัดสินใจเชิงการ
สอนที่คุณจะเจออีกในคอร์สนี้

ตอนนั้นไม่มีเหตุผลที่จะทำให้บรรทัดนั้นซับซ้อน argument มาถึงเป็น string เดียวที่
สมบูรณ์ใน response เดียว และทางเดียวที่ string นั้นจะพังคือโมเดลอ่อนแอที่ผลิต
เรื่องเหลวไหลออกมาจริง ๆ ซึ่งหายากพอที่ traceback เป็นผลลัพธ์ที่ยอมรับได้ การ
เพิ่มบล็อก `try` เข้าไปคงเป็นการกันปัญหาที่ยังไม่ปรากฏ โดยไปนั่งอยู่กลางสาม
บรรทัดที่ผู้อ่านควรกำลังศึกษาอยู่พอดี README ของบทที่ 03 ก็พูดไว้ตอนท้ายหัวข้อ
นั้นแล้ว โดยสัญญาว่า agent จริงจะจับมันแล้วป้อน error กลับไป นี่คือสัญญานั้นถึง
กำหนดชำระ

สิ่งที่เปลี่ยนไปในบทที่ 05 ไม่ใช่สไตล์การเขียนโค้ด แต่คือโลก การถูกตัดกลางคันไม่
ใช่เรื่องหายากเมื่อ argument ถูก stream เพราะ stream ถูกตัดได้ที่อักขระใดก็ได้
และรอยตัดไปลงกลาง argument บ่อยพอที่คุณจะได้เห็นมันกับโมเดลจริงภายในหนึ่งวันหลัง
เริ่มรัน agent ด้วยงบ token ที่ต่ำ การจัดการ error มาถึงในวินาทีที่ error กลาย
เป็นเรื่องที่มีโอกาสเกิด

และมีเหตุผลที่จะทำตามลำดับนี้แทนที่จะป้องกันทุกอย่างตั้งแต่ต้น ตอนนี้คุณรู้แล้วว่า
`JSONDecodeError` จาก tool call ที่ถูกตัดหน้าตาเป็นอย่างไรจริง ๆ ข้อความของมัน
พูดว่าอะไร และมันมาจากไหน ถ้าบทที่ 03 ห่อบรรทัดนั้นด้วย `try` ก่อนที่คุณจะเคย
เจอ exception นั้น `try` ก็จะเป็นแค่เสียงรบกวนที่คุณคัดลอกมา การเห็นบางอย่างพัง
แล้วค่อยซ่อมมันสอนได้ดีกว่าการถูกยื่นเกราะกันปัญหาที่คุณไม่เคยมี โค้ดเชิง

ข้อโต้แย้งที่ฟังขึ้นต่อบทนี้ทั้งบทคือ streaming เป็นแค่เรื่องผิวสวย agent ก็ทำงาน
ได้แล้วตั้งแต่จบบทที่ 04 streaming แค่ทำให้มันรู้สึกดีขึ้น มันน่าจะเป็นงานขัดเงา
ที่ทำหลังจากสร้างฟีเจอร์ที่น่าสนใจเสร็จแล้วสิ

เหตุผลนั้นผิด และวิธีที่มันผิดโดยเฉพาะเจาะจงนั้นควรค่าแก่การเข้าใจ เพราะมันใช้

## 8. การแก้ปัญหา

### stream ทำงานได้ แต่ tool calls กลับมาว่างเปล่า

endpoint บางตัว โดยเฉพาะตัวที่รันในเครื่อง รองรับ streaming และรองรับ tool
calling แต่ไม่รองรับพร้อมกัน request สำเร็จ ร้อยแก้ว stream ออกมาสวยงาม และ
`tool_calls` ไม่เคยโผล่ใน delta ใดเลย ขึ้นอยู่กับเซิร์ฟเวอร์ คุณอาจได้ 400 แทน
ทันทีที่ `stream` และ `tools` อยู่ใน payload พร้อมกัน หรือได้ tool call ที่ส่งมา
เป็นข้อความล้วนอยู่ใน `content`

ยืนยันได้ในขั้นตอนเดียว รัน `check.py` แล้วอ่านว่าการยืนยันข้อไหนล้มเหลว

```text
OK text arrived in 5 pieces
FAIL streamed tool arguments were not reassembled. Got []
```

การ stream ข้อความผ่าน แต่ tool call กลับมาเป็น list ว่าง ถ้านั่นคือสิ่งที่คุณ
เห็น ทางแก้คือเลิกขอ stream ทุกครั้งที่มี tool อยู่ด้วย

```python
    want_stream = not tools
    payload = {"model": model, "messages": messages, "stream": want_stream}
    if tools:
        payload["tools"] = tools
```

จากนั้นก็จัดการกับคำตอบแบบไม่ stream เพราะตอนนี้ body คือ JSON หนึ่งชุด ไม่ใช่
ลำดับของ event

```python
    if not want_stream:
        response = httpx.post(
            f"{base_url}/chat/completions", json=payload, headers=headers, timeout=120
        )
        response.raise_for_status()
        message = response.json()["choices"][0]["message"]
        text = message.get("content") or ""
        if text and on_text:
            on_text(text)
        calls = []
        for raw in message.get("tool_calls") or []:
            try:
                arguments = json.loads(raw["function"]["arguments"] or "{}")
                error = ""
            except json.JSONDecodeError as problem:
                arguments = {}
                error = f"arguments were not valid JSON ({problem})"
            calls.append(
                {
                    "id": raw["id"],
                    "name": raw["function"]["name"],
                    "arguments": arguments,
                    "error": error,
                }
            )
        return text, calls
```

บล็อกนั้นวางไว้ก่อนบรรทัด `with httpx.Client(...)` ทันที และเส้นทาง streaming ที่
อยู่ใต้มันไม่ถูกแตะเลย

สังเกตว่า `on_text` ยังถูกเรียกอยู่ หนึ่งครั้ง พร้อมข้อความทั้งก้อน สัญญาของ
callback ไม่ได้รับปากว่าจะให้ชิ้นเล็ก ๆ มันรับปากแค่ว่าคุณจะได้รับข้อความเมื่อมัน
พร้อมใช้งาน ตรงนี้มันพร้อมใช้งานทีเดียวทั้งก้อน `agent.py` ไม่ต้องแก้อะไร การ
ยืนยันเรื่อง tool ของ `check.py` ยังผ่าน และมีแต่การยืนยันเรื่อง "arrived in 5
pieces" เท่านั้นที่ได้รับผลกระทบ ซึ่งมันก็จะไม่ได้รับผลกระทบ เพราะการเรียกครั้ง
นั้นไม่ได้ส่ง tool ไปด้วย

นี่คือการแลกที่มีจริงและคุณควรตัดสินใจโดยรู้ตัว คุณเสียความรู้สึกสด ๆ ไปใน turn
ที่โมเดลกำลังเลือก tool ซึ่งมักเป็น turn ที่ช้าที่สุด แต่คุณยังเก็บมันไว้ได้ใน
turn สุดท้ายที่โมเดลเขียนคำตอบให้ผู้ใช้ ซึ่งเป็น turn ที่การรอเห็นชัดที่สุด ถ้า
endpoint ของคุณบังคับให้เลือก นั่นคือครึ่งที่ควรเก็บไว้

### JSONDecodeError ที่ event สุดท้ายพอดี

```text
json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```

คุณ parse `[DONE]` เข้าไป การเช็ก sentinel ต้องมาก่อน `json.loads` ไม่ใช่หลังมัน
และไม่ใช่ข้างใน `try` ตรวจลำดับได้ในหัวข้อ 3

### ข้อความโผล่มาทีเดียวทั้งก้อนตอนจบ

มีผู้ต้องสงสัยสองราย ไม่คุณทำ `flush=True` หล่นไปจาก print ซึ่งกรณีนั้น Python
กำลัง buffer output ของคุณแล้วปล่อยออกมาตอน process จบ ก็มีอะไรบางอย่างระหว่างคุณ
กับ provider ที่ buffer response ไว้ proxy ขององค์กรที่ก้าวร้าวจะเก็บ SSE body
ทั้งก้อนไว้อย่างสบายใจแล้วส่งมาทีเดียว ซึ่งเป็นปัญหาเครือข่ายไม่ใช่ปัญหาโค้ด
ทดสอบกับ fake server ก่อนเพื่อดูว่าปัญหาอยู่ฝั่งไหน

```bash
python ci/run_lessons.py
```

### มีชิ้นส่วนมาแค่ชิ้นเดียว

```text
FAIL the reply did not arrive in pieces. Got 1 piece(s)
```

คำตอบสั้นพอที่จะยัดลงใน event เดียว หรือ endpoint เมิน `stream` แล้วส่ง JSON body
ธรรมดาที่บังเอิญขึ้นต้นด้วย `data: ` ซึ่งไม่มีทางเกิดขึ้น ยืนยันได้ด้วยการพิมพ์
ทุกบรรทัดที่ loop เห็น

```python
for line in response.iter_lines():
    print(repr(line))
```

ถ้าคุณเห็น JSON บรรทัดยาวบรรทัดเดียวที่มี key ชื่อ `message` แทนที่จะเป็นบรรทัด
สั้นหลายบรรทัดที่มี key ชื่อ `delta` แปลว่า endpoint ของคุณเมินธง `stream`

### ผลลัพธ์ของ tool ไม่เคยจับคู่กับ call ของมัน


มี `id` หายไป สาเหตุที่พบบ่อยคือการตัดตัวป้องกัน `if chunk.get("id")` ทิ้ง ทำให้
ชิ้นส่วนที่มาทีหลังซึ่งไม่มี id เขียนทับตัวที่ดีด้วย `None` หัวข้อ 4 อธิบายว่า
ทำไมตัวป้องกันนั้นถึงอยู่ตรงนั้น

ทุกอย่างในนั้นคือการตัดสินใจเรื่องรูปร่างที่ OpenAI เป็นคนทำ คำว่า `choices`
คำว่า `delta` การที่ arguments เป็น string ไม่ใช่ object และตำแหน่งที่ index ไป
อยู่ ไม่มีอะไรเกี่ยวกับ streaming ที่บังคับให้ต้องเป็นแบบนั้นเลย มันคือคำตอบของ
บริษัทหนึ่งต่อชุดคำถามหนึ่ง ที่ทุกคนซึ่งอยากให้ endpoint ของตัวเองใช้งานได้กับ
client library ที่มีอยู่แล้วลอกตามไป

Anthropic ตอบคำถามชุดเดียวกันด้วยวิธีที่ต่างออกไป และ fake server ของโปรเจกต์นี้
ก็พูดภาษาถิ่นนั้นได้ด้วย ซึ่งทำให้คุณเทียบทั้งสองแบบเคียงข้างกันได้ นี่คือ call
`add` ตัวเดียวกันในรูปแบบ streaming ของ Anthropic

```text
data: {"type": "message_start", "message": {"id": "mock-1", "role": "assistant", "content": []}}

data: {"type": "content_block_stop", "index": 0}

data: {"type": "message_delta", "delta": {"stop_reason": "tool_use"}}

data: {"type": "message_stop"}

```

ดูว่าอะไรรอดจากการแปลงและอะไรไม่รอด ชั้นขนส่งเหมือนเดิมทุกประการ ยังเป็นบรรทัด
`data: ` พร้อมตัวคั่นบรรทัดว่าง ชิ้นส่วน argument เหมือนกันทุกตัวอักษร ยังเป็น
การหั่นห้าตัวอักษรจาก string เดียวกัน ยัง parse แยกทีละชิ้นไม่ได้ ยังต้องสะสม
ก่อนแล้วค่อย parse และ index ก็ยังเป็นสิ่งที่แยก call ที่เกิดพร้อมกันออกจากกัน

ทุกอย่างที่เหลือต่างกันหมด event พา field `type` มาด้วย และมันมีเจ็ดชนิด ไม่มี
list ชื่อ `choices` tool call คือ content block ที่เริ่มและหยุด ไม่ใช่รายการใน
array ชื่อ `tool_calls` ชิ้นส่วนอยู่ใต้ `partial_json` ข้างใน `delta` ที่มี
`type` ของตัวเอง stream จบด้วย `message_stop` ไม่ใช่ `[DONE]` ดังนั้น client ที่
`break` เมื่อเจอ sentinel จะค้างรอสิ่งที่ไม่มีวันมา

`llm.py` ไม่เข้าใจอะไรในนั้นเลยแม้แต่นิดเดียว เปลี่ยน `AGENTPATH_BASE_URL` ไป
เป็น endpoint ของ Anthropic แล้วมันจะพังทันทีตั้งแต่ event แรก ด้วย `KeyError`
ของ `choices`

ในไฟล์ที่ยังต้องอ่าน environment เรียก HTTP กรองบรรทัด ทำ buffer และ parse ไป
พร้อมกันด้วย การจะรองรับ provider ตัวที่สองคุณต้องสอดการตัดสินใจเรื่องรูปร่างอีก
ชุดหนึ่งแทรกไปทั่วทั้งหมดนั้น และความคิดที่คุณสนใจจริง ๆ คือสะสมก่อนแล้วค่อย
parse และการแยกด้วย index ก็จะถูกฝังอยู่ใต้กิ่ง `if provider ==`

ทางแก้คือสังเกตว่าความคิดพวกนั้นไม่ได้ผูกกับ provider เลยแม้แต่น้อย ทุก provider
stream ทุกเจ้าส่ง argument ของ tool มาเป็นชิ้นส่วน ทุกเจ้าต้องการให้ชิ้นส่วนถูก
แยกออกจากกันด้วยตัวระบุบางอย่าง สิ่งที่ต่างกันมีแค่ว่าแต่ละ field ไปนั่งอยู่ตรง
ไหนใน JSON ดึงความรู้เรื่องรูปร่างมารวมไว้ที่เดียวต่อหนึ่ง provider เก็บตัวแทน
