# บทที่ 07 file tools

นี่คือบทแรกของ ภาคสอง และเป็นบทที่ agent เลิกเป็นแค่ของสาธิต แล้วเริ่มเป็นสิ่งที่คุณจะเอาไปรันกับโฟลเดอร์ที่คุณแคร์จริง ๆ

## 1. ยินดีต้อนรับสู่ ภาคสอง

ภาคหนึ่ง สร้าง loop ขึ้นมา หกบท โค้ดราวสามร้อยบรรทัด และเมื่อจบแล้วคุณได้โปรแกรมที่คุยโต้ตอบได้ อธิบายฟังก์ชัน Python ของคุณให้ model ฟังได้ อ่าน request แบบมีโครงสร้างสำหรับฟังก์ชันเหล่านั้นกลับมาได้ รันมันได้ ป้อนผลลัพธ์กลับเข้าไปได้ และทำทั้งหมดนั้นกับ provider API สองเจ้าที่ต่างกันโดยสิ้นเชิงโดยไม่รู้ด้วยซ้ำว่ากำลังคุยกับเจ้าไหน

และมันทำอะไรไม่ได้เลย

นั่นคือบทสรุปที่ซื่อสัตย์ของ ภาคหนึ่ง tool ที่มีคือ `add` กับการทอยลูกเต๋า ผลลัพธ์ที่แย่ที่สุดของ bug คือตัวเลขผิดบน terminal ของคุณ agent พูดได้ และการพูดคือทั้งหมดที่มันทำได้

ตั้งแต่บทนี้เป็นต้นไป มันแตะ filesystem ของคุณ มันอ่านไฟล์ที่คุณไม่ได้เอาให้มันดู มันเขียนไฟล์ มันแก้ไฟล์ในที่เดิม นั่นคือจุดที่แบบฝึกหัดทั้งหมดนี้เริ่มมีประโยชน์ เพราะ agent ที่อ่านโค้ดคุณได้และแก้โค้ดคุณได้คือสิ่งที่ทุกคนต้องการจริง ๆ และมันก็เป็นจุดเดียวกันเป๊ะที่มันเริ่มอันตราย เพราะกริยาทุกตัวที่ว่ามาทำงานได้ดีพอกันกับไฟล์ที่คุณไม่ได้ตั้งใจและ directory ที่คุณไม่ได้เอ่ยถึง

แปลว่า ภาคสอง คือสองเรื่องที่เกิดขึ้นพร้อมกัน ความสามารถใหม่ และกลไกความปลอดภัยของจริงชุดแรกในคอร์สนี้ ทั้งสองมาถึงพร้อมกันในบทนี้ และจะมาถึงพร้อมกันต่อไปเรื่อย ๆ เพราะ file tool ที่ไม่มี gate ไม่ใช่ file tool เวอร์ชันที่เรียบง่ายกว่า มันเป็นของคนละอย่างและแย่กว่า

### loop ไม่เปลี่ยน และนั่นคือประเด็น

นี่คือคำกล่าวอ้างที่ทำให้ส่วนที่เหลือของ ภาคสอง ง่ายลง และคุณตรวจสอบมันได้ด้วยคำสั่งเดียวก่อนจะอ่านคำถัดไปด้วยซ้ำ

```bash
cd lessons
diff 06-provider-abstraction/agent.py 07-file-tools/agent.py
```

```text
Files are identical
```

รันคำสั่งเดียวกันกับ `providers.py` แล้วคุณจะได้คำตอบเดียวกัน agent loop และชั้น provider ไม่เปลี่ยนเลยระหว่างบทที่ agent บวกเลขสองจำนวนได้ กับบทที่มันเขียน source code ของคุณใหม่ได้

เรื่องนี้ควรค่าแก่การนั่งคิดสักครู่ เพราะมันไม่ใช่อุบัติเหตุและไม่ใช่โชค มันคือผลตอบแทนของทุกอย่างที่ ภาคหนึ่ง ใช้เวลาไปกับมัน

ลองคิดดูว่า loop รู้จักทำอะไรจริง ๆ มันรู้วิธีส่ง messages มันรู้วิธีรับ request ที่มี name มี id และมี dictionary ของ arguments มันรู้วิธีค้นชื่อนั้นใน dictionary เรียกสิ่งที่หาเจอ แปลงคำตอบเป็น string แล้ว append string นั้นเข้าไปในบทสนทนาพร้อม id ที่ตรงกัน นั่นคือสัญญาทั้งหมด และไม่มีอะไรในนั้นพูดถึงเลขคณิต ไฟล์ shell หรือ network เลย

เพราะสัญญาแคบขนาดนั้น ความสามารถใหม่ทุกอย่างใน part นี้จึงเป็น tool และเป็นแค่ tool การอ่านไฟล์คือ tool การแก้ไฟล์คือ tool การรันคำสั่ง shell ในบทที่ 08 คือ tool การค้นหาใน codebase ในบทที่ 09 คือ tool ไม่มีสักตัวที่ต้องแก้ `agent.py` แม้แต่บรรทัดเดียว

```text
lesson 03    tools.py  ->  add, roll_dice                  toy
lesson 07    tools.py  ->  read_file, write_file,          real
                           edit_file, list_files
lesson 08    tools.py  ->  + run_shell                     real and loud
lesson 09    tools.py  ->  + glob_files, grep_files        real and fast

agent.py     unchanged through all four
providers.py unchanged through all four
```

นี่คือสิ่งที่คนหมายถึงเวลาพูดว่าดีไซน์หนึ่งมีรอยต่อที่ดี คุณตัดระบบในจุดที่ถูกต้องครั้งเดียว แล้วงานส่วนที่แพงจะเกิดขึ้นบนฝั่งหนึ่งของรอยตัดขณะที่อีกฝั่งอยู่นิ่ง ถ้าคุณสร้าง loop โดยถักการจัดการไฟล์เข้าไปในตัวมัน ทุกบทในสี่บทถัดไปจะกลายเป็นการผ่าตัดโค้ดที่ทำงานได้อยู่แล้ว และทุกบทจะมีโอกาสทำของที่เคยดีอยู่พัง

คุณไม่ได้ทำแบบนั้น พวกมันจึงจะไม่เกิดขึ้น จากนี้ไป ความสามารถใหม่หมายถึงฟังก์ชันใหม่หนึ่งตัวและ schema ใหม่หนึ่งอันใน `tools.py`

### สิ่งที่เปลี่ยนจริงในบทนี้

ไฟล์เดียวเป๊ะ `tools.py` ถูกเขียนใหม่จากเวอร์ชันของเล่นที่คุณแบกมาตั้งแต่บทที่ 03 และมีสองแนวคิดมาพร้อมกับมันที่ก่อนหน้านี้ไม่จำเป็น

อย่างแรกคือ ทุก path ที่ model ส่งมาต้องผ่าน gate เดียวชื่อ `resolve_inside` เพื่อให้กฎว่าอะไรแตะได้บ้างอยู่ในฟังก์ชันเดียว แทนที่จะถูกพูดซ้ำในสี่ที่

อย่างที่สองคือ ทุกสิ่งที่ tool คืนกลับมาไม่ใช่ print statement มันคือข้อมูลที่เข้าไปในบทสนทนาและถูกส่งไปยัง model provider ทั้งใน request นี้และใน request ทุกครั้งหลังจากนั้น ข้อเท็จจริงข้อเดียวนี้คือเหตุผลที่ tool ตัดทอน output ของตัวเอง และเป็นเหตุผลที่พวกมันปฏิเสธที่จะแตะไฟล์ credential ซึ่งทั้งสองการตัดสินใจนี้จะอธิบายเต็ม ๆ ด้านล่าง

## 2. ปัญหาที่ค้างมาจากบทที่ 06

เปิด `lessons/06-provider-abstraction/tools.py` แล้วอ่านทั้งไฟล์ มันสั้น และความสั้นของมันคือปัญหา

```python
def add(a, b):
    return a + b


def roll_dice(sides):
    return random.randint(1, sides)
```

ดูสิ่งที่ฟังก์ชันเหล่านี้มีร่วมกัน ทุก argument เป็นตัวเลข ทุกค่าที่คืนกลับเป็นตัวเลข ไม่มี input ใดที่ model ส่งมาแล้วจะทำอะไรได้แย่กว่าการให้คำตอบผิด ถ้า model ขอ `add(a=99999999, b=99999999)` คุณก็ได้จำนวนเต็มขนาดใหญ่ ถ้ามันขอ `roll_dice(sides=0)` คุณก็ได้ `ValueError` ที่ `tools.run` ดักไว้แล้วส่งกลับเป็น string

เพราะแบบนั้น `tools.run` ในบทที่ 06 จึงเป็นฟังก์ชันที่เชื่อใจทุกอย่างโดยสมบูรณ์

```python
def run(name, arguments):
    function = FUNCTIONS.get(name)
    if function is None:
        return f"Error: unknown tool {name}"
    try:
        return str(function(**arguments))
    except Exception as error:
        return f"Error: {type(error).__name__}: {error}"
```

มันค้นชื่อ กระจาย arguments เข้าไป แล้วดักทุกอย่างที่ออกมา ไม่มี validation ที่ไหนเลย และก็ไม่จำเป็นต้องมี เพราะกรณีแย่ที่สุดคือเลขคณิต

ทีนี้ลองนึกภาพการเพิ่ม file tool ตัวแรกที่ชัดเจนที่สุดลงในไฟล์นั้น ด้วยวิธีแรกที่ชัดเจนที่สุดที่คนเขียนกัน

```python
def read_file(path):
    return Path(path).read_text()
```

สามบรรทัด มันทำงานได้ และมันคือหายนะ ฟังก์ชันนั้นจะอ่าน `/etc/passwd` มันจะอ่าน `~/.ssh/id_rsa` มันจะอ่านไฟล์ `.env` ในไดเรกทอรีโปรเจกต์ที่มี provider key ของคุณอยู่ข้างใน มันจะอ่านไฟล์ที่อยู่สูงขึ้นไปสามชั้นจากที่ที่คุณเริ่ม agent มันจะอ่าน log ขนาดสองร้อยเมกะไบต์แล้วส่งทั้งก้อนกลับเข้าไปในบทสนทนาที่ถูกส่งซ้ำทุกเทิร์นหลังจากนั้น

ไม่มีอะไรในนั้นต้องอาศัย model ที่ประสงค์ร้าย ผลลัพธ์ทุกข้อคือสิ่งที่ model ที่อยากช่วยเหลือทำ เมื่อมันพยายามตอบคำถามของคุณแล้วเดาผิดว่าของอยู่ตรงไหน

สรุปสถานการณ์ตรง ๆ บทที่ 06 ทิ้ง `tools.py` ที่ฟังก์ชันของมันสร้างความเสียหายไม่ได้ไว้ให้คุณ และเพราะแบบนั้นจึงไม่มีนิสัย ไม่มี gate และไม่มีคำศัพท์สำหรับกรณีที่พวกมันทำได้ บทนี้คือจุดที่เรื่องนั้นเปลี่ยน และส่วนที่มีประโยชน์ไม่ใช่การที่เราเพิ่มการตรวจสอบความปลอดภัย มันคือ *ที่ตรงไหน* ที่เราเพิ่มมันเข้าไป เพราะที่ที่ผิดคือที่ที่ดูชัดเจนที่สุด

## 3. gate เดียวสำหรับทุก path

นี่คือ gate ทั้งหมด ยกเว้น docstring ที่ตัดออกให้ block สั้น ตัวฟังก์ชันใน tools.py ยาวยี่สิบบรรทัดเมื่อนับ docstring ด้วย และมันคือโค้ดที่สำคัญที่สุดในบทนี้

```python
WORKSPACE = Path(os.environ.get("AGENTPATH_WORKSPACE", ".")).resolve()


class WorkspaceError(Exception):
    """Raised when a tool asks for a path it is not allowed to have."""


def resolve_inside(path):
    candidate = (WORKSPACE / Path(path)).resolve()
    if candidate != WORKSPACE and not candidate.is_relative_to(WORKSPACE):
        raise WorkspaceError(f"{path} is outside the workspace")
    if looks_like_a_secret(candidate.name):
        raise WorkspaceError(
            f"this tool refuses to touch {candidate.name} because credential files "
            "must not enter the conversation or be changed by an agent"
        )
    return candidate
```

### มันคืออะไร

`resolve_inside` คือตัวแปลที่มีสิทธิ์ยับยั้ง มันรับ string ที่ language model ผลิตขึ้น ซึ่งก็คือ string ที่ไม่มีการรับประกันอะไรติดมาด้วยเลย แล้วมันจะคืน `Path` object ของจริงที่ tool ได้รับอนุญาตให้ทำงานด้วย หรือไม่ก็ raise `WorkspaceError` แล้ว tool ไม่ได้รันเลย

มีทางออกจากฟังก์ชันนั้นแค่สองทางเป๊ะ ๆ path ที่ปลอดภัย หรือ exception ไม่มีสาขาที่สามที่ path น่าสงสัยเล็กน้อยผ่านไปได้พร้อมคำเตือนที่พิมพ์ไว้ที่ไหนสักแห่ง

`WORKSPACE` คือรากของทุกอย่างที่ agent ได้รับอนุญาตให้แตะ มันมาจาก environment variable (ตัวแปรสภาพแวดล้อม คือค่าที่ตั้งไว้ใน shell) ชื่อ `AGENTPATH_WORKSPACE` โดยมีค่าเริ่มต้นเป็น `.` และถูก resolve เป็น absolute path หนึ่งครั้งตอนที่ module ถูก import รายละเอียดข้อสุดท้ายนั้นสำคัญกว่าที่เห็น และมีหัวข้อย่อยของตัวเองในหัวข้อ 9

### ทำไมเราถึงทำแบบนี้

เพราะ model เป็นคนตัดสินว่า path คืออะไร และคุณเป็นคนตัดสินว่าอะไรได้รับอนุญาต และนั่นคืองานสองอย่างที่ต้องไม่ถูกทำโดยผู้เล่นคนเดียวกัน

ในกรณีปกติ model ไม่ได้เป็นศัตรู มันอยากช่วย และมันกำลังเดา คุณขอให้มันแก้ import ที่ล้มเหลว มันให้เหตุผลว่า config น่าจะอยู่สูงขึ้นไปหนึ่งชั้น มันจึงขอ `../config.py` คุณขอให้มันสรุปโปรเจกต์ของคุณ มันให้เหตุผลว่าค่า deployment น่าสนใจ มันจึงขอ `.env` ไม่มีอะไรในคำขอทั้งสองที่เป็นการมุ่งร้าย ทั้งสองคำขอผิด และมีแต่โค้ดของคุณเท่านั้นที่อยู่ในตำแหน่งที่จะบอกได้ว่ามันผิด

ยังมีอีกกรณีที่คนขอไม่ใช่ model พอ agent อ่านไฟล์ได้ ข้อความที่คนอื่นเขียนก็ไหลเข้ามาในบทสนทนา แล้ว model ก็รับมันเป็น input README ของ dependency ตัวหนึ่งอาจมีประโยคที่เขียนถึง agent ตรง ๆ นั่นคือ prompt injection (การแทรกคำสั่ง คือ model ทำตามข้อความจากข้างนอกเหมือนคุณสั่งเอง) มันเข้ามาทาง tool result ไม่ได้เข้ามาทางคุณ และภาคสามจะจัดการมันอย่างจริงจัง ที่สำคัญตรงนี้คือ gate ที่เขียนด้วย Python ไม่ฟังประโยคในไฟล์ ส่วนกฎที่เขียนไว้ใน prompt เป็นของที่ประโยคในไฟล์เถียงด้วยได้พอดี

### ทำไมต้องฟังก์ชันเดียว ไม่ใช่สี่ที่

นี่คือการตัดสินใจเชิงดีไซน์ที่หัวข้อนี้ตั้งชื่อตาม นี่คือคำอธิบายฉบับเต็ม

ทางเลือกอื่นชัดเจนมากและเป็นสิ่งที่คนส่วนใหญ่เขียนก่อน คือใส่การตรวจสอบไว้ใน tool แต่ละตัว ตรงจุดที่ path ถูกใช้งาน

```python
def read_file(path):
    target = (WORKSPACE / path).resolve()
    if not target.is_relative_to(WORKSPACE):
        return "Error: outside the workspace"
    ...


def write_file(path, content):
    target = (WORKSPACE / path).resolve()
    if not target.is_relative_to(WORKSPACE):
        return "Error: outside the workspace"
    ...


def edit_file(path, old, new):
    target = (WORKSPACE / path).resolve()
    # ... and so on, four times
```

ทุกสำเนาถูกต้อง โค้ดทำงานได้ และมันก็ยังเป็นคำตอบที่ผิด ด้วยเหตุผลสองข้อที่ควรแยกออกจากกัน

กฎที่กระจายอยู่สี่ที่ คือกฎที่จะมีสักที่หนึ่งลืมมันไป ไม่ใช่วันนี้ วันนี้คุณมีสี่ฟังก์ชันและคุณเขียนทั้งสี่ตัวในชั่วโมงเดียวกันด้วยความคิดชุดเดียวกันในหัว การลืมจะเกิดขึ้นในอีกหกสัปดาห์ตอนที่คุณเพิ่ม `append_file` หรือ `copy_file` หรือ `delete_file` แล้วคุณเขียนมันด้วยการคัดลอกรูปทรงของ `read_file` มาปรับ หรือมันเกิดตอนที่มีคนปรับปรุงการตรวจสอบนั้นอย่างถูกต้องในสามจากสี่ฟังก์ชัน เพราะเขาหาเจอสามตัวด้วยการ search และมีตัวที่สี่ที่สะกดต่างออกไปนิดหน่อย หรือมันเกิดตอนที่ tool ตัวหนึ่งงอก path argument ตัวที่สองขึ้นมา เช่นการ rename ที่มีต้นทางและปลายทาง แล้วมีแค่ตัวแรกที่ถูกตรวจ

รูปแบบความล้มเหลวของ security ที่ทำซ้ำ ไม่เคยเป็นการที่สำเนาทุกอันผิด มันคือการที่มีอันหนึ่งผิด ส่วนอีกสามอันยังทำงานได้อย่างสมบูรณ์แบบและทำให้ทั้งระบบดูเหมือนไม่มีปัญหา

กฎความปลอดภัยที่คุณตรวจทานให้จบในการนั่งครั้งเดียวไม่ได้ ไม่ใช่กฎความปลอดภัย นี่คือครึ่งที่คมกว่าของข้อโต้แย้ง ลองถามว่าต้องใช้อะไรบ้างเพื่อตอบคำถามว่า "agent ตัวนี้อ่านไฟล์นอก workspace ได้ไหม" ด้วย gate เดียว คุณอ่านยี่สิบบรรทัดแล้วจบ และคุณมั่นใจได้เพราะคุณตรวจได้ด้วยว่าไม่มี tool ตัวไหนสร้าง path ด้วยวิธีอื่น ด้วยสำเนาสี่อัน คุณต้องอ่านสี่ฟังก์ชัน ยืนยันว่าการตรวจสอบทั้งสี่เป็นการตรวจสอบเดียวกัน ยืนยันว่าไม่มีตัวไหน return ออกก่อนถึงจุดตรวจ และยืนยันว่าไม่มีใครเพิ่ม tool ตัวที่ห้าตั้งแต่ครั้งล่าสุดที่คุณดู การตรวจทานแบบแรกคืองานหนึ่งชิ้น แบบที่สองคือภาระผูกพันถาวร และภาระผูกพันถาวรไม่เคยถูกทำจริง

สังเกตว่าข้อโต้แย้งนี้ไม่เกี่ยวกับการพิมพ์น้อยลงเลย มันจะยังเป็นทางเลือกที่ถูกต้องอยู่ดีถ้า `resolve_inside` ยาวสี่สิบบรรทัดและโค้ดที่ซ้ำมีแค่สี่บรรทัด คุณค่าไม่ได้อยู่ที่โค้ดปรากฏครั้งเดียว มันอยู่ที่ *การตัดสินใจ* ปรากฏครั้งเดียว ในที่ที่มีชื่อเรียก เพื่อให้การใช้เหตุผลกับมันเป็นงานที่มีขอบเขตจำกัด

คุณเห็นผลลัพธ์ได้จากการที่ tool แต่ละตัวเล็กลงแค่ไหน

```python
def read_file(path):
    target = resolve_inside(path)
    if not target.is_file():
        return f"Error: {path} does not exist"
    return truncate(target.read_text(encoding="utf-8", errors="replace"))
```

ไม่มี security อยู่ใน `read_file` เลย มันคือสี่บรรทัดที่ว่าด้วยการอ่านไฟล์ และร่องรอยเดียวของ gate คือบรรทัดแรกของมันเรียก gate นั่นแหละคือหน้าตาที่ tool ควรเป็น เมื่อกฎไปอยู่ที่อื่นแล้ว ถ้าคุณอยากรู้ว่า tool ตัวใหม่ปลอดภัยไหม คำถามไม่ใช่ "คุณเขียนการตรวจสอบไว้หรือยัง" แต่เป็นคำถามที่ง่ายกว่ามากว่า "มันเรียก `resolve_inside` ไหม"

### ทำไมต้อง raise exception แทนการ return error

ดูทางออกทั้งสองอีกครั้ง ตอนปฏิเสธ `resolve_inside` จะ raise มันไม่ return `None` และไม่ return error string

นั่นเป็นความตั้งใจ และมันคือจุดเดียวในไฟล์นี้ที่การ raise ดีกว่าการ return

ถ้า gate คืนค่า sentinel ผู้เรียกทุกคนต้องตรวจค่านั้น และผู้เรียกที่ลืมตรวจจะเดินหน้าต่อด้วย `None` หรือด้วย path ที่ไม่ผ่านการตรวจสอบ ความผิดพลาดจะเงียบ ซึ่งคือความล้มเหลวแบบเดียวกับที่เราเพิ่งใช้หัวข้อย่อยที่แล้วกำจัดไป exception ถูกลืมไม่ได้ tool ที่เพิกเฉยต่อผลของ `resolve_inside` ไม่มีอยู่จริง เพราะเมื่อ path ถูกปฏิเสธก็ไม่มีผลลัพธ์ให้เพิกเฉย การควบคุมออกจากฟังก์ชันไปเลย

exception ถูกดักที่เดียวเป๊ะ ๆ ที่ขอบ ใน `tools.run`

```python
def run(name, arguments):
    function = FUNCTIONS.get(name)
    if function is None:
        return f"Error: unknown tool {name}"
    try:
        return str(function(**arguments))
    except WorkspaceError as error:
        return f"Error: {error}"
    except Exception as error:
        return f"Error: {type(error).__name__}: {error}"
```

เทียบกับเวอร์ชันของบทที่ 06 แล้วคุณจะเจอ clause ใหม่หนึ่งอัน แขน `except WorkspaceError` อยู่เหนืออันทั่วไป เพื่อให้การปฏิเสธกลับมาเป็นประโยคที่สะอาด แทนที่จะเป็น `WorkspaceError: ...` ที่มีชื่อคลาสติดมาด้วย model อ่านประโยคนั้น และประโยคที่อ่านเหมือนคำอธิบายได้รับการตอบสนองที่ดีกว่าประโยคที่อ่านเหมือนโปรแกรมพัง

นี่คือหลักการเดียวกับ parse error ในบทที่ 05 การปฏิเสธไม่ใช่หายนะที่ต้องยกระดับ มันคือข้อมูลที่ model ต้องการ ส่งมอบผ่านช่องทางเดียวที่ model ได้ยิน ซึ่งก็คือ tool result agent ขอ `../../etc/passwd` ถูกบอกว่ามันอยู่นอก workspace แล้วก็ลองทำอย่างอื่นที่สมเหตุสมผลแทน ไม่มีอะไรพัง ไม่มีอะไรรั่ว และ loop ก็เดินต่อ

## 4. resolve_inside หยุดอะไรได้จริงบ้าง

path สองประเภทถูกปฏิเสธโดยการตรวจสอบข้อแรก และควรดูแยกกัน เพราะคนส่วนใหญ่มักนึกถึงแค่ประเภทแรก

### การหนีขึ้นไปยัง directory แม่

model ขอ path ที่มี `..` อยู่ข้างในแล้วเดินขึ้นไปนอก workspace

```python
tools.run("read_file", {"path": "../../secrets.txt"})
```

```text
'Error: ../../secrets.txt is outside the workspace'
```

กลไกนั้นเรียบง่ายเมื่อเขียนออกมา `WORKSPACE / Path(path)` ต่อ path ที่ร้องขอเข้ากับรากของ workspace ได้ออกมาเป็นอะไรทำนอง `/tmp/agentpath-lesson07-abc/../../secrets.txt` แล้ว `.resolve()` ก็ยุบมันลง เพราะนั่นคือสิ่งที่ `resolve` ทำกับส่วนประกอบ `..` และคุณก็เหลือ `/secrets.txt` path สุดท้ายนั้นถูกนำไปเทียบกับ workspace ปรากฏว่าไม่ได้อยู่ข้างใน การเรียกจึงถูกปฏิเสธ

### absolute path

model ไม่สนใจ `..` แล้วเรียกชื่อไฟล์ที่มันต้องการตรง ๆ

```python
tools.run("read_file", {"path": "/etc/passwd"})
tools.run("read_file", {"path": "C:/Windows/win.ini"})
```

```text
'Error: /etc/passwd is outside the workspace'
'Error: C:/Windows/win.ini is outside the workspace'
```

ถูกปฏิเสธทั้งคู่ ด้วยบรรทัดเดียวกัน โดยไม่มีกรณีพิเศษให้อันไหนเลย

เหตุผลที่การตรวจสอบเดียวครอบคลุมทั้งสองแบบคือคุณสมบัติของ `pathlib` ที่ควรรู้ไว้ในตัวมันเอง เมื่อคุณต่อ path เข้ากับอีก path ด้วย `/` แล้วฝั่งขวาเป็น absolute ฝั่งซ้ายจะถูกทิ้งไปทั้งหมด

```python
>>> from pathlib import Path
>>> Path("/home/me/work") / "notes.txt"
PosixPath('/home/me/work/notes.txt')
>>> Path("/home/me/work") / "/etc/passwd"
PosixPath('/etc/passwd')
```

พฤติกรรมนั้นทำให้คนแปลกใจในครั้งแรก และบางครั้งก็เป็นสาเหตุของ bug ตรงนี้มันทำงานให้เรา absolute path จาก model ล้างคำนำหน้าที่เป็น workspace ทิ้ง ได้ absolute path ที่ชี้ไปที่อื่น แล้วก็ตกการทดสอบการบรรจุอันเดียวกับที่ดัก `..` ไว้ gate ไม่จำเป็นต้องรู้ว่ามีการใช้กลไหน มันแค่ต้องรู้ว่า path ไปจบลงที่ไหน

### ทำไมการ resolve ก่อนคือสิ่งที่ทำให้เรื่องนี้ได้ผล

ทีนี้มาถึงส่วนที่สำคัญกว่าตัวอย่างทั้งสองอัน

ลำดับการทำงานในฟังก์ชันนั้นไม่ใช่การตกแต่ง `resolve_inside` resolve path *ก่อน* แล้วเปรียบเทียบ *ทีหลัง* สิ่งล่อใจ และสิ่งที่คุณจะเจอในโค้ดจริงจำนวนมาก คือการเปรียบเทียบข้อความของ path ก่อนที่จะ resolve มัน แบบนั้นเขียนง่าย อ่านง่าย และหลอกง่าย

นี่คือเวอร์ชันที่แย่ ซึ่งเป็นสิ่งที่คนมักคว้ามาใช้

```python
# do not do this
def resolve_inside_wrong(path):
    if ".." in path or path.startswith("/"):
        raise WorkspaceError("nope")
    return WORKSPACE / path
```

มานับวิธีเล็ดลอดผ่านมันกัน

Backslash คือทางหนึ่ง บน Windows model อาจส่ง `..\..\etc\hosts` มาก็ได้ substring `..` มีอยู่ในนั้น การตรวจสอบแบบนี้จึงบังเอิญดักได้ แต่การตรวจสอบใด ๆ ที่เขียนในเทอมของตัวคั่น `/` จะดักไม่ได้ ตัวคั่น path เป็นรายละเอียดของแพลตฟอร์ม และการตรวจสอบด้วย string ต้องทำให้ถูกต้องกับทุกแพลตฟอร์มด้วยมือ

ส่วนประกอบตัวแรกที่ไม่ใช่ `..` คืออีกทางหนึ่ง string `notes/../../../etc/passwd` ไม่ได้ขึ้นต้นด้วย slash และดูเหมือนเริ่มด้วยไดเรกทอรีที่ไม่มีพิษภัย มันหนีขึ้นไปสามชั้น การตรวจสอบใด ๆ ที่ดูแค่ตอนต้นของ string จะพลาดมันไป

Drive letter และ UNC path ก็ผ่านไปได้เช่นกัน `C:/Windows/win.ini` ไม่ได้ขึ้นต้นด้วย `/` และไม่มี `..` เลย การตรวจสอบข้างบนจึงปล่อยผ่านไปตรง ๆ `\\server\share\file` ก็เช่นกัน

Symbolic link (ไฟล์ที่ชี้ไปหา path อื่น เรียกสั้น ๆ ว่า symlink) คืออันที่การตรวจสอบด้วย string แก้ไม่ได้เลย แม้แต่ในเชิงหลักการ สมมติว่า workspace มี symlink ชื่อ `data` ที่ชี้ไปที่ `/etc` path `data/passwd` ไม่มี `..` ไม่มี drive letter ไม่มี slash นำหน้า และไม่มีอักขระน่าสงสัยใด ๆ ทั้งสิ้น มันคือ relative path ธรรมดา ๆ และมันอ่าน `/etc/passwd` ไม่ว่าจะตรวจข้อความมากแค่ไหนก็ตรวจไม่พบ เพราะข้อมูลไม่ได้อยู่ในข้อความ มันอยู่บน filesystem `.resolve()` เดินตาม symlink path ที่ resolve แล้วเลยกลายเป็น `/etc/passwd` แล้วการตรวจว่ามันอยู่ใน workspace ไหมก็ปฏิเสธมัน

และอีกอย่างหนึ่ง ซึ่งเป็น bug คลาสสิกในตระกูลนี้ และเป็นเหตุผลที่โค้ดใช้ `is_relative_to` แทนการเปรียบเทียบ string แม้จะ resolve แล้วก็ตาม

ทางสุดท้ายคือคำนำหน้าที่ไม่ใช่ไดเรกทอรีแม่ สมมติว่าคุณ resolve อย่างถูกต้องแล้ว แต่ไปเปรียบเทียบด้วย `str(candidate).startswith(str(WORKSPACE))` ถ้า workspace คือ `/home/me/work` path `/home/me/workspace_evil/notes.txt` จะผ่านการทดสอบนั้น เพราะ string ของ workspace เป็นคำนำหน้าของมันจริง ๆ แต่มันไม่ได้อยู่ใน workspace มันคือไดเรกทอรีพี่น้องที่บังเอิญชื่อขึ้นต้นเหมือนกัน `is_relative_to` เปรียบเทียบส่วนประกอบของ path แทนที่จะเทียบตัวอักษร `work` กับ `workspace_evil` จึงเป็นคนละส่วนประกอบกัน และการทดสอบก็ล้มเหลวอย่างถูกต้อง

รวมทั้งหมดเข้าด้วยกันแล้วกฎก็สั้น เปลี่ยนคำขอให้เป็น path ที่เป็นของจริง เป็น absolute และปราศจาก symlink เสียก่อน แล้วค่อยถามคำถามเดียวว่า path นั้นอยู่ที่ไหนจริง ๆ อย่าพยายามตัดสินคำถามนั้นจากตัวคำขอเอง เพราะคำขอคือข้อความ และข้อความมีวิธีอธิบายจุดหมายเดียวกันได้ไม่จำกัด

ยังเหลือเงื่อนไขชิ้นเล็ก ๆ อีกชิ้นที่ต้องอธิบาย

```python
    if candidate != WORKSPACE and not candidate.is_relative_to(WORKSPACE):
```

`Path.is_relative_to` คืนค่า `True` อยู่แล้วเมื่อ path ทั้งสองเท่ากัน แปลว่าครึ่งแรกของเงื่อนไขนั้นไม่จำเป็นอย่างเคร่งครัด มันอยู่ตรงนั้นเพื่อทำให้เจตนาชัดเจน เพราะ `list_files(".")` resolve ออกมาเป็นรากของ workspace พอดี และผู้อ่านไม่ควรต้องไปตรวจพฤติกรรมของ standard library ในกรณีความเท่ากันเพื่อให้มั่นใจว่าการเรียกที่พบบ่อยที่สุดทำงานได้ นี่คือจุดที่ clause ที่ซ้ำซ้อนซื้อความชัดเจนในโค้ดที่คนจะอ่านอย่างละเอียดแต่อ่านไม่บ่อย ซึ่งเป็นการแลกที่ดีในฟังก์ชันด้านความปลอดภัย และเป็นการแลกที่แย่ในเกือบทุกที่อื่น

สังเกตด้วยว่า `is_relative_to` ต้องใช้ Python 3.9 ขึ้นไป บน interpreter ที่เก่ากว่านั้นคุณจะต้องเขียนการทดสอบเดียวกันด้วย `os.path.commonpath` และคุณมีโอกาสสูงกว่าที่จะเขียนผิดแบบแนบเนียน ซึ่งเป็นข้อโต้แย้งที่ดีพอสมควรสำหรับข้อกำหนดเรื่องเวอร์ชันในคอร์สนี้

## 5. deny list ของ credential

```python
SECRET_NAMES = {".env", "id_rsa", "id_ed25519", ".npmrc", ".netrc", "credentials"}
SECRET_SUFFIXES = {".pem", ".key", ".p12", ".pfx"}


def looks_like_a_secret(name):
    lowered = name.lower()
    if lowered in SECRET_NAMES or lowered.startswith(".env."):
        return True
    return Path(lowered).suffix in SECRET_SUFFIXES
```

### ความล้มเหลวเฉพาะเจาะจงที่มันป้องกัน

ไล่ดูทีละขั้น เพราะรูปทรงของความล้มเหลวนี้ผิดปกติ และส่วนที่ผิดปกตินั่นแหละคือสิ่งที่ทำให้มันร้ายแรง

คุณเริ่ม agent ในไดเรกทอรีโปรเจกต์แล้วถามอะไรธรรมดา ๆ "ทำไม deploy script นี้ถึงล้มเหลว" agent list ไดเรกทอรี เห็นไฟล์ `.env` แล้วให้เหตุผลอย่างถูกต้องทุกประการว่า deploy script น่าจะอ่าน configuration ของมันจากตรงนั้น มันจึงเรียก `read_file` ด้วย `.env`

ยังไม่มีอะไรผิดพลาดเลยในความหมายใด ๆ ที่ model จะรับรู้ได้ มันกำลังช่วยเหลือ การอ่านไฟล์ config คือสัญชาตญาณที่ถูกต้อง

tool คืนเนื้อหากลับมา เนื้อหานั้นกลายเป็น `content` ของ message ที่มี role เป็น `tool` และ message นั้นถูก append เข้าไปใน `messages` ใน `agent.py` API key ของคุณในรูปข้อความล้วนตอนนี้เป็นสมาชิกลำดับที่สี่ใน list ของ Python

ตรงนี้คือจุดที่มันเลิกเป็นความผิดพลาดธรรมดา ดูสิ่งที่ loop ทำต่อไป

```python
        messages.append({"role": "tool", "tool_call_id": call["id"], "content": result})
```

แล้วต่อมา ที่ตอนต้นของรอบถัดไป

```python

```

`messages` ทั้ง list ถูกส่งไป ไม่ใช่แค่ส่วนใหม่ ทั้งหมดเลย ทุกเทิร์น นั่นคือวิธีที่บทสนทนาทำงาน และบทที่ 02 ได้อธิบายเหตุผลไว้แล้ว ผลที่ตามมาคือ key ของคุณไม่ได้ถูกส่งครั้งเดียว มันถูกส่งใน request นี้ และใน request ถัดไป และใน request ทุกครั้งตลอดที่เหลือของ session บทสนทนายี่สิบเทิร์นส่งมันไปยี่สิบครั้ง

มันยังถูกเขียนลงในที่ใดก็ตามที่คุณเขียนบทสนทนาลงไปด้วย transcript ทุกไฟล์ที่คุณบันทึกมีมันอยู่ log ทุกบรรทัดที่ dump `messages` เพื่อ debug มีมันอยู่ crash report ทุกฉบับที่รวม request body มีมันอยู่ ชุดข้อมูลประเมินผลทุกชุดที่คุณสร้างจาก session ที่บันทึกไว้มีมันอยู่ ทุกอย่างที่ว่ามาเป็นเรื่องปกติที่คนทำกัน และตอนนี้ทุกอย่างมี credential ที่ยังใช้งานได้อยู่ในที่ที่ไม่มีใครคิดจะไปหา

### คุณเอามันคืนไม่ได้

นี่คือคุณสมบัติที่ทำให้มันคุ้มค่ากับการมีหัวข้อทั้งหัวข้อแทนที่จะเป็นแค่หัวข้อย่อยหนึ่งบรรทัด

บทสนทนาเป็นแบบ append only ไม่ใช่โดยนโยบาย แต่โดยโครงสร้าง `messages` คือ list และ loop append เข้าไปในนั้น ไม่มีกลไกใดในดีไซน์นี้ที่จะแก้ไข message ย้อนหลังได้ และจริง ๆ แล้วก็มีไม่ได้ เพราะคำตอบในภายหลังของ model ถูกผลิตขึ้นภายใต้การมีอยู่ของเนื้อหาก่อนหน้า และการเขียนประวัติศาสตร์ใหม่ใต้พวกมันไม่สมเหตุสมผล

จึงไม่มี undo การรู้ตัวว่าพลาดหลังจากนั้นหนึ่งเทิร์นก็ไม่ช่วย คุณหยุดโปรเซสได้ แต่ key ก็ถูกส่งข้ามสายไปแล้ว คุณลบไฟล์ transcript ได้ แต่ key ก็ถูกส่งข้ามสายไปแล้ว ทางแก้จริง ๆ ทางเดียวหลังเกิดเหตุคือการ rotate credential เป็นงานน่าเบื่อ คนจึงผัดวันประกันพรุ่ง แล้วมันก็ไม่เกิดขึ้น

เทียบกับ bug ของ tool เกือบทุกชนิดอื่น การแก้ที่ผิดย้อนกลับได้ ไฟล์ที่เขียนผิดที่ย้ายได้ คำสั่ง shell ที่ล้มเหลวรันใหม่ได้ ทั้งหมดนั้นกู้คืนได้ ความลับที่เข้าไปในบทสนทนาแล้วกู้คืนไม่ได้ และความย้อนกลับไม่ได้คือคุณสมบัติที่ควรใช้ตัดสินว่าคุณจะทุ่มความพยายามในการป้องกันไปที่ไหน

### ทำไมการตรวจสอบถึงอยู่ใน tool ไม่ใช่ใน prompt

ทางเลือกที่ชัดเจนคือหนึ่งบรรทัดใน system prompt (คำสั่งตั้งต้นที่บอก model ว่าให้ทำตัวยังไง)

```text
Never read .env or any file containing credentials.
```

บรรทัดนั้นควรมีไว้ ใส่มันไปเถอะ มันจะเปลี่ยนพฤติกรรมได้เป็นส่วนใหญ่ เพราะ model ค่อนข้างเก่งในการทำตามคำสั่งประจำที่ชัดเจน และการที่ agent ไม่พยายามตั้งแต่แรกดีกว่าการที่มันพยายามแล้วถูกปฏิเสธ

แต่มันไม่ใช่มาตรการควบคุม และเหตุผลเป็นเรื่องของจังหวะเวลา ไม่ใช่เรื่องว่า model ประพฤติตัวดีแค่ไหน

ตามลำดับเหตุการณ์ดู model ผลิต tool call provider stream มันกลับมา `agent.py` แจงมันแล้วเรียก `tools.run` ณ ขณะนั้น คำขอสำหรับ `.env` มีอยู่แล้ว มันอยู่ใน `calls` มันกำลังจะถูก append เข้า `messages` ในฐานะส่วนหนึ่งของเทิร์นของ assistant **เมื่อถึงเวลาที่ model ขอแล้ว ช่วงเวลาสำหรับการขอร้องดี ๆ ก็ผ่านไปแล้ว** คำถามเดียวที่ยังเปิดอยู่คือเนื้อหาจะกลับมาหรือไม่ และผู้เล่นคนเดียวที่มีสิทธิ์ตอบคำถามนั้นคือโค้ดของคุณ

คำสั่งใน prompt ทำงานก่อนคำขอ มันลดความน่าจะเป็นของคำขอ มันไม่ได้ทำงานกับตัวคำขอ เพราะมันไม่ได้อยู่ตรงจุดที่คำขอถูกตอบ นั่นคือตำแหน่งคนละจุดใน pipeline และมีแค่จุดเดียวที่เป็น gate

ยังมีเหตุผลที่สอง และเป็นเหตุผลที่ใช้ได้กว้างกว่า prompt คือข้อความในบทสนทนา และเมื่อจบ ภาคสอง บทสนทนาจะเต็มไปด้วยข้อความอื่นที่มาจากไฟล์ output ของคำสั่ง และผลการค้นหา ซึ่งคุณไม่ได้เขียนสักอย่าง คำสั่งกับข้อมูลใช้ช่องทางเดียวกัน tool result ที่มีข้อความว่า "ignore your previous instructions about configuration files" กำลังแข่งกับ system prompt ของคุณบนพื้นฐานที่เท่าเทียมกัน และการแข่งขันนั้นถูกตัดสินด้วยวิจารณญาณของ model ไม่ใช่ด้วยสิ่งใดที่คุณควบคุม การตรวจสอบใน `resolve_inside` ไม่ได้อยู่ในช่องทางนั้นเลย มันอยู่ใน Python มันไม่มีความเห็นต่อข้อโต้แย้งที่ฟังดูน่าเชื่อ เพราะมันไม่เคยเห็นข้อโต้แย้งเหล่านั้น

กฎที่อยู่ใต้เหตุผลทั้งสองข้อคือกฎที่คุณควรพกติดตัวไปกับทุก agent ที่คุณสร้าง prompt กำหนดรูปร่างของสิ่งที่ model พยายามทำ โค้ดตัดสินว่าอะไรจะเกิดขึ้น อะไรก็ตามที่คุณย้อนกลับไม่ได้อยู่ในประเภทที่สอง

### list นี้จับอะไรได้จริง และจับอะไรไม่ได้

อ่าน `looks_like_a_secret` ให้ละเอียด เพราะการพูดให้ตรงเรื่องขีดจำกัดของมาตรการควบคุมคือส่วนหนึ่งของการมีมาตรการนั้น

มันแปลงชื่อเป็นตัวพิมพ์เล็กก่อน แปลว่า `.ENV` และ `ID_RSA` ถูกดักไว้ มันจับคู่ชื่อทั้งชื่อกับ `SECRET_NAMES` ซึ่งครอบคลุม `.env` กุญแจส่วนตัวของ SSH สองแบบที่พบบ่อย `.npmrc` และ `.netrc` ที่ทั้งคู่มักมี token อยู่เป็นประจำ และ `credentials` เปล่า ๆ ซึ่งเป็นชื่อไฟล์ของ AWS CLI มันจับคู่คำนำหน้า `.env.` ด้วย แปลว่า `.env.production` และ `.env.local` ก็ถูกดัก และมันจับคู่ suffix สี่แบบ แปลว่าไฟล์ certificate และ key ถูกดักไม่ว่าจะวางอยู่ตรงไหน

ทีนี้มาถึงส่วนที่ต้องพูดตามตรง

มันตรวจเฉพาะส่วนประกอบสุดท้าย `candidate.name` คือชื่อไฟล์ แปลว่าไฟล์ที่อยู่ที่ `credentials/database.txt` ไม่ถูกดักโดยรายการ `credentials` เพราะรายการนั้นจับคู่กับไฟล์ที่ชื่อ `credentials` ไม่ใช่ไดเรกทอรี

มันคือ deny list และ deny list ไม่เคยครบถ้วน ไฟล์ที่ชื่อ `api_keys.txt` ผ่านฉลุย `config.local.json` ที่มี token อยู่ข้างในก็เช่นกัน ไม่มี list ใดเป็นไปได้ที่จะครอบคลุมทุกชื่อที่ความลับจะถูกตั้งได้ เพราะการตั้งชื่อขึ้นอยู่กับใครก็ตามที่สร้างไฟล์นั้น

มันไม่ได้ห้ามการมองเห็นไฟล์ `list_files` ไม่กรองชื่อ แปลว่า agent บอกคุณได้ว่า `.env` มีอยู่ นี่คือผลลัพธ์จริงตามที่มันเกิดขึ้น

```text
'.env\ncalc.py\nnotes.txt'
```

ซึ่งทำให้เกิดคำถามที่เป็นธรรมว่าจะเสียเวลากับอะไรที่รั่วขนาดนี้ไปทำไม

เพราะสิ่งที่มันเล็งเป้าไว้ มาตรการนี้ไม่ได้เล็งไปที่ผู้โจมตีที่พยายามดึง key ของคุณออกไป และมันก็ทำงานนั้นได้แย่ มันเล็งไปที่ model ที่อยากช่วยเหลือแล้วทำความผิดพลาดที่พบบ่อยที่สุดและแพงที่สุดเท่าที่มันทำได้ นั่นคือการเปิดไฟล์ที่ตั้งชื่อตามค่า configuration ของ environment ตรง ๆ กรณีเฉพาะกรณีเดียวนั้นครอบคลุมเหตุการณ์จริงส่วนใหญ่ มันมีราคาหกบรรทัด และมัน fail closed กับชื่อที่สำคัญที่สุด

การรู้ว่ามาตรการควบคุมหนึ่งไม่สมบูรณ์ไม่ใช่เหตุผลที่จะข้ามมันไป มันคือเหตุผลที่จะรู้ว่าคุณรับมือกับภัยคุกคามข้อไหนไปแล้ว คำตอบที่สมบูรณ์ ซึ่งคือระบบสิทธิ์ที่ถามคุณก่อนที่อะไรที่อ่อนไหวจะเกิดขึ้น แทนที่จะเดาจากชื่อไฟล์ อยู่ใน ภาคสาม

มีอีกรายละเอียดหนึ่งที่ควรสังเกต deny list อยู่ใน `resolve_inside` ซึ่งแปลว่ามันใช้กับ `write_file` ด้วย ไม่ใช่แค่การอ่าน agent เขียนทับ `.env` ของคุณไม่ได้เช่นกัน นั่นเป็นของแถมที่ได้มาจากการวางกฎไว้ใน gate แทนที่จะวางไว้ใน `read_file` และมันคือตัวอย่างรูปธรรมเล็ก ๆ ของข้อโต้แย้งในหัวข้อที่ 3 กฎที่อยู่ที่เดียวจะถูกใช้ทุกที่โดยปริยาย กฎที่อยู่สี่ที่จะถูกใช้ในสี่ที่ที่มีคนนึกถึง

## 6. ทำไม edit_file ถึงปฏิเสธ match ที่กำกวม

นี่คือการตัดสินใจเชิงดีไซน์ที่น่าสนใจที่สุดในบทนี้ และเป็นข้อที่แยก file tool ที่ทำงานได้ในเดโม ออกจากตัวที่ทำงานได้กับ codebase จริง

```python
def edit_file(path, old, new):
    target = resolve_inside(path)
    if not target.is_file():
        return f"Error: {path} does not exist"
    text = target.read_text(encoding="utf-8")
    found = text.count(old)
    if found == 0:
        return (
            f"Error: the text to replace was not found in {path}. "
            "Read the file again and copy the exact text including whitespace."
        )
    if found > 1:
        return (
            f"Error: the text to replace appears {found} times in {path}. "
            "Include more surrounding lines so the match is unique."
        )
    target.write_text(text.replace(old, new), encoding="utf-8")
    return f"Edited {path}"
```

### มันคืออะไร

`edit_file` แทนที่ข้อความชุดหนึ่งที่ตรงเป๊ะด้วยอีกชุดหนึ่ง และมันทำการแทนที่ก็ต่อเมื่อข้อความเดิมปรากฏในไฟล์เพียงครั้งเดียวเท่านั้น ศูนย์ match คือ error สองครั้งขึ้นไปคือ error หนึ่ง match คือการแก้ไข

สังเกตว่ามันนับก่อนเขียน `found = text.count(old)` ทำงานกับเนื้อหาไฟล์ การปฏิเสธทั้งสองแบบเกิดขึ้นตรงนั้น แล้วหลังจากนั้นเท่านั้น `text.replace` ถึงจะทำงาน ไม่มีสถานะครึ่ง ๆ กลาง ๆ ไฟล์ถูกเขียนหนึ่งครั้งอย่างถูกต้อง หรือไม่ก็ไม่ถูกแตะเลย

### ทำไมเราถึงทำแบบนี้

เพราะการ implement แบบธรรมชาติคือเครื่องจักรทำลายข้อมูลแบบเงียบ ๆ และมันทำลายในแบบที่แทบจะออกแบบมาให้รอดสายตาโดยสมบูรณ์

นี่คือการ implement แบบธรรมชาติ

```python
def edit_file(path, old, new):
    target = resolve_inside(path)
    text = target.read_text()
    target.write_text(text.replace(old, new))
    return f"Edited {path}"
```

`str.replace` แทนที่ทุกตำแหน่งที่พบ นั่นคือสิ่งที่มันทำมาตลอดและเป็นพฤติกรรมที่ถูกต้องสำหรับ `str.replace` แต่มันคือหายนะเมื่อใช้เป็น tool ให้ model เพราะ model ไม่รู้เลยว่ามีกี่ตำแหน่ง

ลองคิดถึงสิ่งที่ model มีอยู่ในมือจริง ๆ มันอ่านไฟล์ไปเมื่อหลายเทิร์นก่อน ตอนนี้มันกำลังผลิต string `old` จากความจำ ทีละตัวอักษร โดยเล็งจะระบุตำแหน่งเฉพาะหนึ่งจุด มันไม่ได้กำลังนับ มันไม่ได้กำลังดูไฟล์ มันเลือกข้อความสั้น ๆ ที่รู้สึกว่าโดดเด่นสำหรับมัน ซึ่งไม่ใช่สิ่งเดียวกันเลยกับข้อความที่ปรากฏเพียงครั้งเดียว

ทีนี้สมมติว่าไฟล์เป็นแบบนี้

```python
def parse(line):
    total = 0
    ...

def summarise(rows):
    total = 0
    ...

def report(rows):
    total = 0
    ...
```

model ต้องการเปลี่ยนค่าเริ่มต้นใน `summarise` เท่านั้น มันจึงส่ง `old="total = 0"` ด้วยการ implement แบบซื่อ ๆ ทั้งสามที่เปลี่ยนหมด tool คืนค่า `Edited notes.py` ซึ่งเป็นความจริง model อ่านค่านั้น สรุปว่างานเป็นไปตามแผน แล้วเดินหน้าต่อ คุณก็อ่านมันเช่นกัน และมันดูเหมือนขั้นตอนที่สำเร็จตามปกติใน trace ที่เต็มไปด้วยขั้นตอนที่สำเร็จตามปกติ

สองในสามการแก้นั้นผิด และไม่มีใครในระบบรู้ model ไม่รู้ เพราะ feedback เดียวที่มันได้คือคำว่า `Edited` คุณไม่รู้ เพราะคุณกำลังดู trace และ trace บอกว่ามันสำเร็จ โปรแกรมไม่รู้ เพราะอีกสองฟังก์ชันยัง parse ได้อย่างสมบูรณ์และยังรันได้ แค่ตอนนี้มันคำนวณผิดเท่านั้นเอง

นั่นคือความล้มเหลวเฉพาะเจาะจงและควรเรียกชื่อมันให้ตรง มันไม่ใช่การ crash มันไม่ใช่ error ที่ loop ป้อนกลับได้ มันคือการเปลี่ยนโค้ดที่คุณไม่ได้ขอให้เปลี่ยน ถูกรายงานว่าเป็นความสำเร็จ ถูกค้นพบภายหลังโดยใครก็ตามที่โชคร้าย ในระยะห่างจากต้นเหตุที่ทำให้ความเชื่อมโยงมองเห็นได้ยาก

นี่คือการปฏิเสธแทน ตามที่ tool ผลิตออกมาจริง

```text
'Error: the text to replace appears 3 times in notes.py. Include more surrounding lines so the match is unique.'
```

และการปฏิเสธอีกแบบหนึ่ง สำหรับกรณีที่ข้อความที่ model จำได้ไม่ตรงกับไฟล์เลย ซึ่งมักเป็นเพราะช่องว่าง

```text
'Error: the text to replace was not found in notes.py. Read the file again and copy the exact text including whitespace.'
```

### ทำไมต้องวิธีนี้ ไม่ใช่ทางเลือกอื่น

ยังมีดีไซน์อื่นอีกหลายแบบ และแต่ละแบบแย่กว่าด้วยเหตุผลที่ควรทำความเข้าใจ

ทางเลือกแรกคือแทนที่เฉพาะตำแหน่งแรก ใช้ `text.replace(old, new, 1)` แล้วเดินหน้าต่อ วิธีนี้แย่กว่าการแทนที่ทุกตำแหน่ง ซึ่งฟังดูแปลกจนกว่าคุณจะเห็นเหตุผล การแทนที่ทุกตำแหน่งอย่างน้อยก็สร้างความเละที่มองเห็นได้ กฎแทนที่ตำแหน่งแรกจะแก้ตำแหน่งที่บังเอิญมาก่อนที่สุดในไฟล์อย่างเงียบ ๆ ซึ่งเป็นตำแหน่งที่ model ไม่ได้คิดถึงเลย คุณจะได้การแก้ในฟังก์ชันที่ผิด ถูกรายงานว่าสำเร็จ โดยไม่มีสัญญาณใด ๆ ที่ไหนเลย มันเปลี่ยนความกำกวมให้เป็นการโยนเหรียญ แล้วซ่อนเหรียญไว้

ทางที่สองคือรับหมายเลขบรรทัดมาด้วย ให้ model ส่ง `line=42` มาแล้วแก้ตรงนั้น ตอนนี้ tool แม่นยำ แต่ model ถูกบังคับให้ติดตามหมายเลขบรรทัดตลอดบทสนทนาขณะที่ไฟล์เปลี่ยนไปใต้เท้ามัน ทุกการแก้ก่อนหน้าเลื่อนหมายเลขที่อยู่ใต้มัน model ทำเลขคณิตแบบนี้ได้แย่ และที่แย่กว่านั้น รูปแบบ error ที่ตามมาคือความคลาดเคลื่อนหนึ่งบรรทัดที่ไปลงผิดที่แล้วสำเร็จ การจับคู่ด้วยข้อความมีข้อได้เปรียบมหาศาลตรงที่ตัวระบุตำแหน่งของ model ตรวจสอบกับไฟล์ได้ หมายเลขบรรทัดตรวจไม่ได้

ทางที่สามคือถามผู้ใช้ว่าตำแหน่งไหน ถามมนุษย์ทุกครั้งที่ match กำกวม วิธีนี้ไม่ผิด และบทที่ 08 จะแนะนำการยืนยันสำหรับคำสั่ง shell ซึ่งมันถูกต้องพอดี แต่มันเป็นเครื่องมือที่ผิดสำหรับปัญหานี้ เพราะความกำกวมตรงนี้ไม่ใช่คำถามเรื่องเจตนา มันคือคำถามเรื่องความเฉพาะเจาะจง และ model แก้ได้เองด้วยการส่ง context มาเพิ่ม การขัดจังหวะคนเพื่อตอบสิ่งที่ model แก้ได้ด้วยการลองใหม่คือการแลกที่แย่ และ agent ที่ถามตลอดเวลาจะถูกกดอนุมัติโดยอัตโนมัติ ซึ่งทำลายคุณค่าของการถามทั้งหมด

ทางที่สี่คือให้ model ส่ง diff หรือ patch มา นี่คือสิ่งที่ tool จริงบางตัวทำ และเป็นดีไซน์ที่ชอบธรรม มันมีต้นทุนเป็น patch parser ตัวแก้ offset และนโยบายการจับคู่แบบยืดหยุ่น และมันให้ format ที่ model ผลิตได้เชื่อถือได้น้อยกว่าข้อความธรรมดา มันเป็นการแลกที่สมเหตุสมผลเมื่อทำในสเกลใหญ่ และเป็นการแลกที่แย่สำหรับ tool ที่คุณอยากให้อยู่ในยี่สิบบรรทัดและเข้าใจได้ทั้งหมด

### error ที่ model อ่านได้ ดีกว่า edit ที่ model มองไม่เห็น

หัวข้อย่อยนั้นคือหลักการทั้งหมด และควรพูดเป็นกฎทั่วไป เพราะมันใช้ได้ไกลเกินฟังก์ชันนี้มาก

คุณกำลังออกแบบให้ผู้เล่นที่สังเกตผลลัพธ์ไม่ได้ model ไม่เห็น filesystem ของคุณ มันไม่เห็น diff มันไม่มีทางสังเกตได้ว่าไฟล์เปลี่ยนไปสามที่ตอนที่มันต้องการที่เดียว การรับรู้ทั้งหมดของมันเกี่ยวกับสิ่งที่เกิดขึ้นคือ string ที่ tool ของคุณคืนกลับมา

นั่นมีผลโดยตรงต่อวิธีที่คุณเขียน tool อะไรก็ตามที่ tool ไม่ได้พูดถึงเท่ากับไม่ได้เกิดขึ้น ในมุมมองของ model แปลว่า tool ต้องไม่ทำสิ่งที่ model จะคัดค้านแล้วรายงานว่าสำเร็จเป็นอันขาด เพราะความสำเร็จปลอมกู้คืนไม่ได้ภายใน loop ไม่มีขั้นตอนใดในภายหลังที่ model จะได้รู้ความจริง

ในทางกลับกัน การปฏิเสธกู้คืนได้อย่างสมบูรณ์และราคาถูก ดูสิ่งที่ loop ทำกับมัน error string กลับไปเป็น tool result model อ่านประโยคที่บอกมันตรง ๆ ว่าอะไรผิดและจะแก้อย่างไร แล้วมันส่ง call ใหม่พร้อม context รอบข้างเพิ่มอีกสามบรรทัด นั่นคือหนึ่งเทิร์นเพิ่ม หนึ่งเทิร์นเพิ่มมีราคาไม่กี่วินาทีและ token ไม่กี่พันตัว การทำลายข้อมูลแบบเงียบ ๆ มีราคาเป็นบ่ายทั้งบ่าย และมันเก็บค่านั้นจากคนที่ยังไม่รู้ตัวด้วยซ้ำว่ามันเกิดขึ้น

อ่านข้อความ error ทั้งสองอีกครั้งโดยคิดถึงเรื่องนี้ ไม่มีอันไหนที่แค่รายงานความล้มเหลว ทั้งสองอันมีคำสั่งว่าต้องทำอะไรต่ออยู่ในตัว `Include more surrounding lines so the match is unique` บอก model ถึงวิธีแก้ `Read the file again and copy the exact text including whitespace` บอก model ทั้งสาเหตุที่น่าจะเป็นและวิธีแก้ไปพร้อมกัน เพราะเหตุผลปกติของการ match ศูนย์ครั้งคือ model ประกอบการเยื้องขึ้นมาจากความจำแล้วผิดไปนิดหน่อย จำนวนครั้งก็อยู่ในข้อความด้วย เพราะการรู้ว่ามันเป็นสามไม่ใช่สองบอก model ว่าต้องเพิ่ม context อีกเท่าไร

การเขียนข้อความ error แบบนี้ไม่ใช่ความสุภาพ มันคือ interface error string คือ prompt ที่ผลิตโดยโค้ดของคุณ มาถึงในจังหวะที่ model ต้องการมันที่สุด และมันสมควรได้รับความใส่ใจเท่ากับอะไรก็ตามใน system prompt ของคุณ บทที่ 10 จะอธิบายข้อโต้แย้งนี้อย่างเต็มที่

### นี่คือสิ่งที่ harness จริงทำ

นี่ไม่ใช่การลดทอนเพื่อการสอนที่จะถูกแทนที่ด้วยอะไรที่ซับซ้อนกว่าในภายหลัง กฎ unique match คือสิ่งที่ tool ของจริงทำ

tool สำหรับแก้ไขของ Claude Code กำหนดให้ string เดิมต้องไม่ซ้ำในไฟล์ และคืน error ที่ขอ context เพิ่มเมื่อมันไม่ unique Aider จับคู่บล็อกแบบตรงเป๊ะและปฏิเสธเมื่อบล็อกนั้นไม่ระบุตำแหน่งได้ที่เดียว apply model ของ Cursor สร้างขึ้นรอบ ๆ จุดยึดที่ไม่กำกวม กฎนี้ไม่ได้เหมือนกันทุกรายละเอียด แต่หลักการที่ว่าการแก้ไขต้องระบุตำแหน่งได้เพียงหนึ่งเดียวหรือไม่ก็ล้มเหลว เกือบจะเป็นสากล

พวกเขามาบรรจบกันที่วิธีนี้ด้วยเหตุผลเดียวกับที่คุณเพิ่งอ่านไป ความล้มเหลวแบบทางเลือกอื่นมันเงียบ และความล้มเหลวแบบเงียบในระบบที่แก้โค้ดของคุณเป็นสิ่งที่รับไม่ได้ไม่ว่าจะเกิดถี่แค่ไหน

## 7. ทำไม write_file อันตรายกว่า edit_file

นี่คือ tool สองตัวเทียบกัน

```python
def write_file(path, content):
    target = resolve_inside(path)
    target.parent.mkdir(parents=True, exist_ok=True)
    target.write_text(content, encoding="utf-8")
    return f"Wrote {len(content)} characters to {path}"
```

`write_file` ไม่มีอะไรเทียบเท่าการตรวจนับ และมันมีไม่ได้ `edit_file` ตรวจสอบคำกล่าวอ้างเกี่ยวกับไฟล์ก่อนลงมือได้ เพราะ model บอกมันว่าคาดว่าจะเจออะไร `write_file` ไม่ได้รับคำกล่าวอ้างใด ๆ เลย มันได้รับเนื้อหาใหม่ และเนื้อหาใหม่สอดคล้องกับสถานะปัจจุบันทุกแบบที่เป็นไปได้ของไฟล์ จึงไม่มีอะไรให้ตรวจ

ความต่างนั้นมีคมในทางปฏิบัติ ถ้า model จำเนื้อหาไฟล์ผิดไปเล็กน้อย แล้วมันเขียนไฟล์ทั้งไฟล์ใหม่จากความจำนั้น ทุกอย่างที่มันจำผิดจะกลายเป็นความจริงบนดิสก์ ฟังก์ชันที่มันลืมหายไป คอมเมนต์ที่มันคิดว่าไม่สำคัญหายไป import ที่มันไม่ได้สังเกตหายไป tool รายงาน `Wrote 2431 characters to app.py` และความสูญเสียทุกข้อมองไม่เห็นในประโยคนั้น

`edit_file` ทำแบบนั้นไม่ได้ รัศมีการทำลายของมันถูกจำกัดโดยโครงสร้าง มันเปลี่ยนข้อความชุดเดียวที่มันพิสูจน์แล้วว่ามีอยู่ และทุกไบต์อื่นในไฟล์ถูกยกข้ามไปโดยไม่ถูกแตะ เพราะมันไม่เคยอยู่ในเกม

ยังมีต้นทุนที่สองซึ่งวัดง่ายกว่า การเขียนไฟล์ทั้งไฟล์ใหม่แปลว่า model ต้องสร้างไฟล์ทั้งไฟล์ สำหรับ source file สามร้อยบรรทัด นั่นคือ output token หลายพันตัวที่ใช้ไปเพื่อเปลี่ยนแค่ตัวเดียว มันช้า มันแพง และทุก token ที่ถูกสร้างคือโอกาสอีกครั้งที่จะทำให้เกิดความต่างที่ไม่มีใครขอ นั่นคือข้อโต้แย้งเดียวกับที่บทที่ 06 ให้ไว้ตอนที่มันสัญญาว่า ภาคสอง จะมี edit tool ไม่ใช่มีแค่ write tool และนี่คือคำสัญญาที่ถูกทำให้เป็นจริง

`write_file` มีอยู่เพราะคุณต้องใช้มันจริง ๆ การสร้างไฟล์ใหม่ต้องใช้มัน การแทนที่ไฟล์ที่เนื้อหาเดิมไม่เกี่ยวข้องต้องใช้มัน มันคือ tool ที่ถูกต้องในบางครั้งและเป็น tool ที่ผิดโดยส่วนใหญ่ และ model ต้องถูกบอกว่าอันไหนเป็นอันไหน

### description คือคำสั่งเดียวที่ model ได้รับ

ลองคิดถึงสิ่งที่ model มีให้ใช้เวลาตัดสินใจระหว่าง tool สองตัว มันมีชื่อ tool มี description และมี description ของ parameter นั่นคือข้อกำหนดทั้งหมด มันอ่าน `tools.py` ไม่ได้ มันมองไม่เห็นว่า `edit_file` นับจำนวนครั้งก่อน มันมองไม่เห็นว่า `write_file` ตัดทิ้งทุกอย่างที่เคยอยู่ตรงนั้น มันไม่เคยเจอ codebase ของคุณ มันไม่มีความทรงจำเกี่ยวกับ session ก่อนหน้าของคุณ และมันจะไม่เรียนรู้จากความผิดพลาดที่มันทำเมื่อวาน

ทุกอย่างที่คุณรู้เกี่ยวกับว่า tool ไหนเหมาะสมและเพราะอะไร ต้องรอดชีวิตจากการเดินทางเข้าไปในไม่กี่ประโยคนั้น ไม่อย่างนั้นมันไปไม่ถึง model เลย

ทีนี้อ่าน description อีกสามอันด้วยแว่นแบบนั้น

```python
            "description": "Read a text file and return its contents.",
```

สั้น เพราะไม่มีอะไรต้องแก้ความกำกวม มีวิธีอ่านไฟล์แค่วิธีเดียวและไม่มี tool คู่แข่ง

```python
            "description": (
                "Replace one exact piece of text in a file. The old text must appear "
                "exactly once, so include enough surrounding lines to make it unique."
            ),
```

สองประโยค และประโยคที่สองทำงานจริง มันระบุข้อจำกัดและวิธีแก้ล่วงหน้า เพื่อให้ model มีโอกาสทำถูกตั้งแต่ครั้งแรก แทนที่จะเรียนรู้กฎด้วยการถูกปฏิเสธ สังเกตการใช้ถ้อยคำ มันไม่ได้พูดว่า "an error occurs if the text is not unique." มันบอกว่าต้องทำอะไร description ที่เขียนเป็นคำสั่งทำงานได้ดีกว่า description ที่เขียนเป็นข้อกำหนด เพราะ model กำลังตัดสินใจว่าจะส่งอะไร ไม่ได้กำลังเขียนรายงานการปฏิบัติตามข้อกำหนด

```python
                    "path": {"type": "string", "description": "Path relative to the workspace"}
```

สามในสี่ tool ใช้ description ของ parameter เดียวกันนี้ซ้ำ และควรสังเกตว่ามันมีไว้เพื่ออะไร มันคือกฎเรื่อง workspace ที่พูดซ้ำในจุดที่ model จะกำลังมองอยู่ ณ ขณะที่มันประกอบ path ขึ้นมา gate ใน `resolve_inside` คือสิ่งที่ทำให้กฎเป็นจริง บรรทัดนี้คือสิ่งที่ทำให้กฎเป็นที่รับรู้ คุณอยากได้ทั้งสองอย่าง เพราะการปฏิเสธที่ model หลีกเลี่ยงได้คือเทิร์นที่เสียเปล่า ถึงแม้มันจะถูกจัดการอย่างถูกต้องก็ตาม

ประเด็นทั่วไปคือสิ่งที่แทบทุกคนพลาดในครั้งแรก เมื่อ tool ของคุณทำงานผิดปกติใน agent สัญชาตญาณของคุณจะพาไปดู Python บ่อยครั้งมาก Python ไม่มีปัญหา แต่ description ต่างหากที่ผิด เพราะ description คือส่วนที่ model อ่านจริง จงปฏิบัติกับไม่กี่ประโยคนั้นเหมือนเป็น user interface ของ tool ของคุณ และเขียนมันเพื่อผู้อ่านที่มีความสามารถ มีแรงจูงใจ และไม่มีแหล่งข้อมูลอื่นใดเลย บทที่ 10 ว่าด้วยเรื่องนี้ทั้งบท

### ทำไม tool result ไม่ใช่ print statement

นี่คือแบบจำลองความคิดที่ต้องแก้ให้ถูกตั้งแต่ตอนนี้ เพราะทุกอย่างที่เหลือในหัวข้อนี้ตามมาจากมัน และเพราะมันคือสิ่งที่มือใหม่เข้าใจผิด

เวลาคุณ `print` ในโปรแกรมปกติ string ไปที่ terminal ของคุณแล้วก็จบ มันไม่มีต้นทุน มันหายไป และการพิมพ์เพิ่มก็มีต้นทุนเป็นสัดส่วนกับความไม่มีอะไรนั้น

tool result ไม่ใช่แบบนั้น มันถูก append เข้าไปใน `messages` และ `messages` ถูกส่งซ้ำทั้งก้อนในทุกการเรียกครั้งถัดไป แปลว่า tool result ไม่ใช่สิ่งที่คุณปล่อยออกไป มันคือสิ่งที่คุณ *ติดตั้ง* เข้าไปในบทสนทนา และมันอยู่ติดตั้งไว้แบบนั้นจนกว่า session จะจบ

ลองนับดูว่านั่นหมายถึงอะไรสำหรับผลลัพธ์ก้อนใหญ่ก้อนเดียว สมมติว่า agent อ่านไฟล์ log ขนาด 120000 ตัวอักษร ซึ่งราว ๆ 30000 token และ session รันต่ออีกสิบห้าเทิร์นหลังจากนั้น token 30000 ตัวนั้นถูกส่งในเทิร์นที่มันมาถึงและในทุกเทิร์นอีกสิบห้าเทิร์นหลังจากนั้น คุณจ่ายค่าไฟล์นั้นสิบหกครั้ง มันยังกิน token 30000 ตัวจาก context window (ข้อความมากสุดที่ model อ่านได้ในหนึ่งครั้ง) ที่มีขนาดตายตัว มันเลยเบียดไฟล์ที่คุณต้องอ่านจริงในเทิร์นที่สิบสองออกไป และเมื่อ window เต็ม ส่วนที่เก่าที่สุดและสำคัญที่สุดของบทสนทนาคือสิ่งที่ต้องถูกตัดออก

ยังมีต้นทุนที่สามซึ่งมองเห็นยากกว่าและมักเป็นตัวที่แย่ที่สุด ในทางปฏิบัติความสนใจของ model มีจำกัดแม้ว่า context window จะไม่จำกัด การฝังฟังก์ชันที่เกี่ยวข้องหนึ่งตัวไว้ในกอง log แสนตัวอักษรทำให้คำตอบแย่ลง ไม่ใช่แค่แพงขึ้น input ที่น้อยลงสร้าง output ที่ดีกว่าได้จริง ซึ่งเป็นคำกล่าวอ้างที่ขัดสัญชาตญาณจนกว่าคุณจะได้เห็นมันเกิดขึ้น

ขีดจำกัดนี้ไม่ใช่ความขี้เหนียว สี่พันตัวอักษรคือราว ๆ หนึ่งพัน token ซึ่งเป็น source file ขนาดใหญ่และเป็นรายการไดเรกทอรีที่ใหญ่มาก มันเหลือเฟือสำหรับงาน และเล็กพอที่การเดาผิดว่าจะอ่านไฟล์ไหนมีต้นทุนเป็นเศษปัดเศษ ไม่ใช่ก้อนใหญ่ของ session

### การตัดสินใจที่เกี่ยวข้องใน list_files

```python
SKIP_DIRECTORIES = {".git", ".venv", "__pycache__", "node_modules", ".ruff_cache"}
```

```python
def list_files(path="."):
    target = resolve_inside(path)
    if not target.is_dir():
        return f"Error: {path} is not a directory"
    names = []
    for entry in sorted(target.iterdir()):
        if entry.name in SKIP_DIRECTORIES:
            continue
        names.append(entry.name + "/" if entry.is_dir() else entry.name)
    return truncate("\n".join(names) or "(empty directory)")
```

นี่คือหลักเศรษฐศาสตร์เดียวกันที่ใช้ ณ จุดอื่น ชื่อไดเรกทอรีห้าอันนั้นถูกข้ามเพราะมันใหญ่มหาศาล ไม่น่าสนใจ และถูกสร้างโดยเครื่อง `node_modules` ในโปรเจกต์ขนาดปานกลางมีรายการหลายหมื่นรายการ ไดเรกทอรี `.git` มี object file ที่ไม่ใช่ข้อความ การ list อันไหนก็ตามจะทะลุขีดจำกัดการตัดทอนและเติม context ของ model ด้วยสิ่งที่มันใช้ไม่ได้

สังเกตรายละเอียดเล็ก ๆ สองอย่างที่ท้ายฟังก์ชัน ไดเรกทอรีได้ `/` ต่อท้าย ซึ่งมีราคาตัวอักษรละหนึ่งตัวและช่วย model ให้ไม่ต้องเรียก `read_file` กับไดเรกทอรีเพื่อดูว่ามันคืออะไร และไดเรกทอรีว่างคืน `(empty directory)` แทนที่จะคืน string ว่าง เพราะ tool result ที่ว่างเปล่านั้นกำกวม มันอาจแปลว่าไดเรกทอรีว่าง หรือแปลว่า tool ล้มเหลวแบบเงียบ ๆ การพูดออกมาช่วยขจัดความกำกวมด้วยราคาแค่คำเดียว

### การอ้างอิงไปข้างหน้า

ทุกอย่างในหัวข้อนี้คือการผ่านครั้งแรกของเรื่องที่จะมีบทเป็นของตัวเอง ภาคสาม มีบทว่าด้วยเศรษฐศาสตร์ของ token ซึ่งคุณจะได้วัดว่า token ของ session ไปอยู่ที่ไหนจริง ๆ เรียนรู้ว่าทำไมบทสนทนาที่ยาวขึ้นจึงช้าลงและแพงขึ้นต่อเทิร์นแม้ไม่มีอะไรอื่นเปลี่ยน และสร้างกลไกสำหรับจัดการมันอย่างถูกต้อง รวมถึงการสรุปเทิร์นเก่าและการทิ้ง tool result ที่ไม่เกี่ยวข้องแล้ว

นิสัยที่ควรสร้างตั้งแต่ตอนนี้ ก่อนถึงบทนั้น คือการถามคำถามเดียวทุกครั้งที่คุณเขียน tool ค่าที่คืนกลับนี้ใหญ่ได้แค่ไหน ใครเป็นคนจ่าย และจ่ายกี่ครั้ง tool ที่เขียนขึ้นโดยไม่ถามคำถามนั้นคือเหตุผลอันดับหนึ่งที่ agent ซึ่งทำงานได้สวยงามกับตัวอย่างเล็ก ๆ กลายเป็นใช้งานไม่ได้กับของจริง

นั่นคือโค้ดระดับ module มันรันครั้งเดียวเป๊ะ ๆ ในครั้งแรกที่ `tools` ถูก import แล้วไม่รันอีกเลย ถ้าตั้งค่า `AGENTPATH_WORKSPACE` หลังจาก import นั้น จะไม่มีอะไรเกิดขึ้น เพราะ `WORKSPACE` ถูกคำนวณและเก็บไว้แล้ว

ถ้า import อยู่ในตำแหน่งปกติที่ด้านบน workspace ก็จะเป็นไดเรกทอรีปัจจุบัน และ test ที่พยายามอ่าน `.env` ก็จะไปคว้าไฟล์ในโปรเจกต์จริงของคุณ check จะล้มเหลวอย่างชวนสับสน หรือที่แย่กว่ามาก มันจะผ่านทั้งที่กำลังทดสอบอย่างอื่นที่ไม่ใช่สิ่งที่มันอ้าง

การอ่าน configuration ครั้งเดียวตอน import คือการแลกที่มีจริง มันทำให้ค่าคงที่ ราคาถูก และเปลี่ยนกลางทางไม่ได้ ซึ่งเป็นคุณสมบัติที่ดีสำหรับขอบเขตความปลอดภัย เพราะ workspace ที่กำหนดค่าใหม่ได้ตอน runtime คือ workspace ที่วันหนึ่งคำสั่งที่ถูกฉีดเข้ามาอาจพูดจนกล่อม harness ให้กำหนดค่าใหม่ได้ ต้นทุนคือความงุ่มง่ามในการทดสอบแบบนี้ แบบฝึกหัดตอนท้ายเสนอให้เปลี่ยนมันเป็น argument ของฟังก์ชัน เพื่อให้คุณเห็นอีกด้านของการแลกด้วยตัวเอง

### prompt และทำไมถึงเขียนแบบนั้น

```python
READ_AND_EDIT = (
    "Fix the bug in calc.py. "
    '[[tool:read_file:{"path": "calc.py"}]]'
    '[[tool:edit_file:{"path": "calc.py", "old": "return a - b", "new": "return a + b"}]]'
)
```

เครื่องหมาย `[[tool:...]]` เหล่านั้นคือรูปแบบคำสั่งที่ fake server ของคอร์สนี้เข้าใจ เป็นรูปแบบเดียวกับที่คุณใช้มาตั้งแต่บทที่ 03 mock server สแกนหาพวกมันใน prompt แล้วปล่อย tool call เหล่านั้นออกมาเป๊ะ ๆ check จึงได้ออกกำลังกับ loop จริง provider จริง streaming parser จริง และ tool จริง โดยมีเพียงการเลือกของ model เท่านั้นที่ถูกแทนที่ด้วยสคริปต์

นี่คือสิ่งที่ทำให้ check เป็น deterministic model จริงที่ถูกขอให้แก้ bug ใน `calc.py` ก็คงจะทำแบบเดียวกัน และคำว่าคงจะไม่ดีพอสำหรับสิ่งที่ CI รันทุกครั้งที่ push

### อ่านทีละบรรทัด

`OK` บรรทัดแรกเกิดขึ้นก่อนที่ model จะเข้ามาเกี่ยวข้องเลยด้วยซ้ำ

```python
    if "return a - b" not in tools.read_file("calc.py"):
        fail("read_file did not return the file contents")
```

`read_file` ถูกเรียกโดยตรงในโปรเซส และข้ออ้างคือไบต์จริงจากไฟล์จริงบนดิสก์กลับมา นี่คือ test ที่น่าสนใจน้อยที่สุดในไฟล์โดยตั้งใจ และมันควรอยู่เป็นอันแรก เพราะถ้ามันล้มเหลว ความล้มเหลวทุกอันหลังจากนั้นคือผลสืบเนื่อง และคุณจะเสียเวลาไป debug ผิดชั้น

trace ของ tool ตรงกลางคือ `agent.py` กำลังพิมพ์ และเป็นโค้ดที่ไม่เปลี่ยนจากบทที่ 06 ที่ผลิตมันออกมา อ่านรูปทรงของมัน มีบรรทัดว่าง แล้วตามด้วย `[calling read_file with ...]` แล้วผลลัพธ์ แล้วคู่เดียวกันสำหรับ `edit_file` แล้วประโยคหนึ่งประโยคจาก model นั่นคือสองเทิร์นเต็มของ agent loop tool call ผลลัพธ์ถูก append เรียก model อีกครั้ง tool call ที่สอง ผลลัพธ์ถูก append เรียก model อีกครั้ง model ตอบเป็นคำพูด loop คืนค่า

บรรทัดว่างที่ด้านบนของแต่ละคู่มาจาก `\n` ที่อยู่หน้าข้อความ `[calling ...]` ซึ่งปกติทำหน้าที่คั่นข้อความที่ stream มากับ trace ของ tool ในเทิร์นที่ model ตรงไปที่ tool call เลย จะไม่มีข้อความอยู่ก่อนหน้า ขึ้นบรรทัดใหม่จึงไปลงบนบรรทัดว่าง บทที่ 06 อธิบายสิ่งประดิษฐ์เดียวกันนี้ไว้แล้ว

สังเกตว่า `[read_file returned ...]` พิมพ์เนื้อหาไฟล์ข้ามสองบรรทัดและปิดวงเล็บบนบรรทัดของตัวเอง นั่นคือไฟล์จริง พร้อมขึ้นบรรทัดใหม่ตอนท้ายที่ยังอยู่ครบ ถูกสะท้อนออกมาใน trace มันเป็นเครื่องเตือนใจเล็ก ๆ ว่า tool result คือข้อความตามอำเภอใจ ไม่ใช่ค่าบรรทัดเดียวที่เรียบร้อย ซึ่งเป็นเหตุผลที่หัวข้อ 8 มีอยู่พอดี

`The tool returned Edited calc.py.` คือประโยคสุดท้ายของ fake server ฟังก์ชัน `decide` ของมันแปลง tool result อะไรก็ตามให้เป็นประโยคนั้น ซึ่งเป็นวิธีที่ loop ไปถึงเทิร์นที่ไม่มี tool call แล้วออกจากลูป

`OK` บรรทัดที่สองคือบรรทัดที่สำคัญที่สุด และสังเกตสิ่งที่มันตรวจ

```python
    run(provider, READ_AND_EDIT)
    if "return a + b" not in (workspace / "calc.py").read_text(encoding="utf-8"):
        fail("the agent did not edit the file on disk")
```

มันไม่ได้ตรวจสิ่งที่ `run` คืนกลับมา มันอ่านไฟล์จากดิสก์ นั่นคือข้ออ้างที่ถูกต้องสำหรับบทเรียนที่ว่าด้วยผลข้างเคียง เพราะการที่ tool รายงาน `Edited calc.py` คือคำกล่าวอ้าง และเนื้อหาไฟล์คือข้อเท็จจริง การทดสอบคำกล่าวอ้างจะผ่านแม้ว่า `edit_file` จะคืนข้อความความสำเร็จโดยไม่เขียนอะไรเลย

`OK` บรรทัดที่สามเลี่ยง model ไปเลยทั้งหมด

```python
    escape = tools.run("read_file", {"path": "../../secrets.txt"})
    if "outside the workspace" not in escape:
        fail(f"an escape attempt was not refused. Got {escape!r}")
```

`tools.run` ถูกเรียกโดยตรงด้วย path ที่ไม่มี model ตัวไหนผลิตขึ้น นั่นถูกต้องแล้ว เพราะคุณสมบัติที่กำลังทดสอบเป็นคุณสมบัติของ gate และการดึง model เข้ามาจะทำให้ test ไปขึ้นกับว่า model เลือกลอง path ที่ไม่ดีหรือไม่ คุณทดสอบมาตรการควบคุมด้วยการโจมตีมันด้วยตัวเอง

`OK` บรรทัดที่สี่มีสองเงื่อนไข และทั้งสองรับน้ำหนักจริง

```python
    secret = tools.run("read_file", {"path": ".env"})
    if "refuses to touch" not in secret or "supersecretvalue" in secret:
        fail(f"the credential file was not protected. Got {secret!r}")
```

เงื่อนไขแรกตรวจว่าการปฏิเสธเกิดขึ้นจริง เงื่อนไขที่สองตรวจว่าความลับไม่ได้อยู่ใน string ที่คืนกลับมา เงื่อนไขที่สองไม่ได้ซ้ำซ้อน และเหตุผลคือ bug ประเภทหนึ่งที่มีอยู่จริง ลองนึกภาพ tool เวอร์ชันอนาคตที่อ่านไฟล์ก่อนแล้วค่อยตัดสินใจว่าจะอนุญาตไหม และใส่เนื้อหาลงในข้อความ error เพื่อการ debug เวอร์ชันนั้นจะปฏิเสธ แปลว่าเงื่อนไขแรกผ่าน และมันจะรั่ว ซึ่งเป็นสิ่งเดียวที่มาตรการควบคุมนี้มีอยู่เพื่อป้องกัน check นี้ตั้งข้ออ้างกับผลลัพธ์ที่คุณแคร์ ไม่ใช่แค่กับกลไกที่คุณบังเอิญสร้างขึ้น

### ถ้ามันล้มเหลว

`FAIL read_file did not return the file contents` แปลว่าไฟล์ไม่ได้ถูกเขียนในที่ที่ `tools` มองหา ซึ่งเกือบทุกครั้งแปลว่า `AGENTPATH_WORKSPACE` ถูกตั้งค่าหลังจาก `tools` ถูก import แล้ว ตรวจลำดับการ import

`FAIL the agent did not edit the file on disk` โดยมี trace ของ tool ที่สะอาดอยู่ข้างบน แปลว่า `edit_file` คืน error แทนที่จะแก้ไข อ่าน trace แล้วดูว่า `[edit_file returned ...]` พูดว่าอะไรจริง ๆ ข้อความที่น่าจะเป็นมีสองแบบ คือแบบ match ศูนย์ครั้งกับแบบ match หลายครั้ง และทั้งสองแบบระบุสาเหตุไว้แล้ว

`KeyError: 'AGENTPATH_BASE_URL'` แปลว่าตัวแปรของ provider ไม่ได้ถูกตั้งค่าใน shell นี้ ให้รัน `ci/run_lessons.py` จากรากของ repository แทน หรือตั้งค่าเองตามที่บทที่ 06 แสดงไว้

## 10. สิ่งที่คุณยังทำไม่ได้

หยุดแล้วดูสิ่งที่ agent ได้มาจากไฟล์เดียว

มัน list ไดเรกทอรีและเห็นว่ามีอะไรอยู่ได้ มันอ่านไฟล์ข้อความใดก็ได้ภายใน workspace ของมัน มันสร้างไฟล์ได้ รวมถึงไดเรกทอรีระหว่างทางไปหาไฟล์นั้น มันเปลี่ยนข้อความชิ้นหนึ่งที่ตรงเป๊ะในไฟล์ที่มีอยู่ได้ และมันจะถูกบอกอย่างชัดเจนเมื่อเป้าหมายของมันกำกวมหรือไม่มีอยู่ มันออกนอก workspace ไม่ได้ ไม่ว่าจะทิศทางไหน ด้วยนิพจน์ path แบบใดก็ตาม มันเอา credential ของคุณใส่เข้าไปในบทสนทนาไม่ได้ ไม่มีอะไรที่มันคืนกลับมาที่จะท่วม context window ได้โดยไม่บอกกล่าว

และมันก็ยังหาไม่ได้ว่าสิ่งเหล่านั้นได้ผลหรือไม่

นั่นคือช่องว่าง และมันเป็นช่องว่างที่ใหญ่ agent ในบทนี้แก้ `calc.py` และเปลี่ยน `return a - b` เป็น `return a + b` มันถูกไหม agent ไม่รู้เลย มันรันไฟล์ไม่ได้ มันรัน test ไม่ได้ มันรัน `python -c` เพื่อตรวจว่า `add(2, 3)` เป็น `5` แล้วไม่ได้ มันทำการเปลี่ยนแปลง มันถูกบอกว่าการเปลี่ยนแปลงลงไปบนดิสก์แล้ว และนั่นคือจุดสิ้นสุดของความรู้ของมัน

ลองคิดว่านั่นมีต้นทุนอะไร agent ทุกตัวในบทนี้ทำงานแบบ open loop มันให้เหตุผล มันลงมือ และมันไม่เคยสังเกตผลของการลงมือเลย การแก้ไขทุกครั้งต้องมาจากคุณ ที่อ่าน diff เองและพิมพ์คำสั่งใหม่ agent สังเกตไม่ได้ว่ามันพิมพ์ผิดตรงไหน ค้นพบไม่ได้ว่าการแก้ของมันทำให้ test อีกตัวพัง และลองวิธีที่สองไม่ได้เมื่อวิธีแรกไม่ได้ผล เพราะมันไม่มีทางรู้ได้ว่าวิธีแรกไม่ได้ผล

สิ่งที่ปิดลูปนั้นคือ tool ที่รันคำสั่งได้ และนั่นคือบทที่ 08 เมื่อ agent รัน test suite ได้ อ่าน output ของความล้มเหลวได้ แก้อีกครั้ง แล้วรันอีกครั้ง มันจะกลายเป็นสิ่งที่ต่างจากที่คุณมีตอนนี้ในเชิงคุณภาพ นั่นคือความต่างทั้งหมดระหว่างผู้ช่วยที่เสนอการเปลี่ยนแปลง กับ agent ที่ไปถึงผลลัพธ์ที่ใช้งานได้

มันยังเป็น tool ที่อันตรายที่สุดในคอร์สนี้แบบทิ้งห่าง ซึ่งเป็นเหตุผลที่คำถามยืนยันอยู่ในตัวมันตั้งแต่วันแรกที่มันมีอยู่ แทนที่จะถูกเพิ่มเข้ามาทีหลัง `resolve_inside` จำกัดขอบเขตว่า file tool เอื้อมไปถึงไหนได้ ไม่มีขอบเขตแบบเดียวกันที่คำสั่ง shell จะเคารพ เพราะคำสั่ง shell ทำอะไรก็ได้ที่ผู้ใช้ที่รันมันทำได้ รวมถึงการล้มล้างข้อจำกัดทุกข้อในบทนี้ นั่นคือหัวข้อของบทที่ 08 และเป็นเหตุผลที่บทนั้นจริงจังกับความปลอดภัยยิ่งกว่าบทนี้เสียอีก

### แบบฝึกหัดก่อนไปต่อ

สี่ข้อ เรียงตามความยากที่เพิ่มขึ้น

ข้อแรกคือลองหนีออกไปให้ได้ เริ่ม Python session ตั้ง `AGENTPATH_WORKSPACE` ให้เป็นไดเรกทอรีชั่วคราว import `tools` แล้วใช้เวลาสิบนาทีเรียก `tools.run("read_file", {"path": ...})` ด้วย path ที่ร้ายกาจที่สุดเท่าที่คุณคิดออก backslash ตัวคั่นผสมกัน สายโซ่ `..` ที่ยาวมาก UNC path path ที่มี null byte อยู่ข้างใน จุดต่อท้ายบน Windows จดบันทึกทุกอย่างที่มีพฤติกรรมไม่ตรงกับที่คุณคาด จากนั้นสร้าง symlink ภายใน workspace ที่ชี้ออกไปข้างนอกแล้วยืนยันว่ามันถูกปฏิเสธ เพราะนั่นคือกรณีที่การ resolve ก่อนมีอยู่เพื่อดักไว้

ข้อสองคือทำให้ `edit_file` พังโดยตั้งใจ เปลี่ยนมันเป็น `text.replace(old, new)` ธรรมดาที่ไม่มีการนับ แล้วรันมันกับไฟล์ที่มีบรรทัดเหมือนกันสามบรรทัด แล้วดูมันรายงาน `Edited` ขณะที่ทำลายสองตำแหน่งที่คุณไม่ได้ตั้งใจ ทีนี้ลองนึกภาพว่าสิ่งนั้นอยู่ในการรัน agent ห้าสิบขั้น เรื่องนี้ใช้เวลาสองนาทีและเป็นวิธีที่เร็วที่สุดที่จะทำให้หัวข้อ 6 อยู่ในหัวคุณอย่างถาวร

ข้อสามคือทำให้ workspace เป็น argument แทนที่จะเป็นค่าคงที่ระดับ module ให้ tool เป็นคลาสเล็ก ๆ ที่ถือรากไว้และมี `read_file` `write_file` `edit_file` และ `list_files` เป็น method แล้วสร้าง `FUNCTIONS` จาก instance ของมัน `check.py` จะไม่ต้องใช้กลลำดับการ import อีกต่อไป จากนั้นตัดสินใจด้วยตัวเองว่าคุณชอบเวอร์ชันไหน และต้องบอกได้ว่าเพราะอะไร มีข้อโต้แย้งจริงอยู่ทั้งสองฝั่ง และแบบฝึกหัดคือการได้ถกมัน

ข้อสี่คือเพิ่ม tool ตัวที่ห้าชื่อ `append_file` ที่ต่อข้อความไว้ท้ายไฟล์ เขียนมันขึ้นมา แล้วดูสิ่งที่คุณเขียน คุณเรียก `resolve_inside` หรือเปล่า คุณตัดทอนสิ่งที่มันคืนกลับมาหรือเปล่า คุณเขียน description ที่บอก model ว่าควรใช้มันเมื่อไรแทน `write_file` หรือเปล่า ทีนี้กลับไปที่หัวข้อ 3 แล้วอ่านข้อโต้แย้งเรื่องกฎที่กระจายอยู่สี่ที่อีกครั้ง โดยมีฟังก์ชันใหม่ของคุณเองวางอยู่ตรงหน้าเป็นหลักฐาน
