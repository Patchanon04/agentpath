## 2. ทำไมถึงใช้ thread ไม่ใช่ async

ก่อนจะดูโค้ด นี่คือการตัดสินใจที่กำหนดรูปร่างของทุกอย่าง

**ตัวเลือกคืออะไร** Python มีอย่างน้อยสองวิธีในการทำหลายอย่างพร้อมกัน
thread ซึ่ง operating system จัดคิวหลาย stack แล้วสลับไปมา
และ `asyncio` ซึ่งมี stack เดียวรัน event loop และฟังก์ชันที่ทำเครื่องหมาย `async`
จะคืนการควบคุมกลับมาที่ทุก `await` ยังมี multiprocessing อีกอย่างหนึ่ง
ซึ่งเป็นคนละเรื่องและไม่ใช่ตัวเลือกที่นี่ด้วยเหตุผลที่จะบอกข้างล่าง

**ทำไมโปรเจกต์นี้ใช้ thread** ลองดูว่า agent run ใช้เวลาไปกับอะไรจริง ๆ
มันสร้าง request ส่งออกไป แล้วรอ มันรอไบต์แรกของ response
มันรอทุก chunk ของ stream ระหว่างเทิร์นมันรัน tool ซึ่งมักเป็นการอ่านไฟล์หรือ subprocess
แล้วก็รออีก แทบทั้งชีวิตตามเวลานาฬิกาของ agent run คือเวลาที่ถูก block อยู่บน socket
โดยไม่มีอะไรต้องคำนวณเลย

นั่นคือกรณีที่ thread จัดการได้ดี thread ที่ถูก block ทำให้คุณเสีย stack หนึ่งอัน
กับ entry ใน scheduler หนึ่งรายการ ไม่มีอะไรมากกว่านั้น
global interpreter lock ซึ่งเป็นสิ่งที่คนเตือนคุณอย่างถูกต้อง จะถูกปล่อยขณะ thread รอ I/O
ดังนั้น thread สี่ตัวที่รอบน socket สี่ตัวจึงรอพร้อมกันได้จริง
lock จะบังคับให้เรียงคิวเฉพาะ thread ที่กำลังรัน Python bytecode
และ agent run แทบไม่ทำสิ่งนั้นเลย

นี่ก็เป็นเหตุผลว่าทำไม multiprocessing ไม่ใช่คำตอบ process มีไว้เพื่อเลี่ยง interpreter lock
สำหรับงานที่ติด CPU จริง ๆ การจ่ายค่า interpreter สี่ตัว สำเนาของทุก import สี่ชุด
และการ pickle ทุกข้อความข้าม pipe เพื่อเร่งงานสี่อย่างที่ทั้งหมดกำลังหลับอยู่บน socket
คือการซื้อทางแก้ราคาแพงให้กับปัญหาที่คุณไม่ได้มี

**ทำไมไม่ใช้ async ทั้งที่ async มีไว้เพื่อเรื่องนี้โดยตรง**
เพราะราคาที่ผู้อ่านต้องจ่าย ไม่ใช่ราคาที่เครื่องต้องจ่าย

ทุก module ในโปรเจกต์นี้เป็นแบบ synchronous `providers.py` เรียก `httpx` แล้ว block
`tools.py` เรียก `subprocess.run` แล้ว block `agent.py` คือ `for` loop ธรรมดา
ที่เรียกฟังก์ชันธรรมดา การเอา `asyncio` เข้ามาที่นี่ไม่ได้แค่เพิ่ม keyword
มันเปลี่ยนสีของทุกฟังก์ชันที่มันแตะ และการเปลี่ยนนั้นแผ่ออกไป
`run_in_parallel` กลายเป็น `async def` เพื่อจะ await ข้างในได้ agent run ต้อง awaitable
ดังนั้น `run` ก็กลายเป็น `async def` เพื่อจะ await ข้างในนั้นได้ `provider.stream`
ก็กลายเป็น `async def` ซึ่งแปลว่า `httpx.Client` กลายเป็น `httpx.AsyncClient`
ซึ่งแปลว่า generator ที่ yield ข้อความแบบ streaming กลายเป็น async generator
ซึ่งแปลว่าทุก `for` ที่วนบนมันกลายเป็น `async for` ส่วน tool ยัง block อยู่
มันจึงต้องใช้ `run_in_executor` ซึ่งก็คือการยัด thread pool กลับเข้ามาในโปรแกรมอยู่ดี
และ `check.py` ทุกไฟล์ใน repository ก็ต้องมี event loop เพื่อจะเรียกอะไรก็ตาม

ผู้อ่านมาที่นี่เพื่อเรียนว่า agent ทำงานอย่างไร การบังคับให้เขาเรียนกฎเรื่องสีของฟังก์ชันก่อน
และให้ไป debug อาการค้างที่เกิดจาก `await` ที่ลืมไปตัวเดียว คือต้นทุนจริงที่จ่ายผิดสกุลเงิน
thread ทำให้บทนี้ได้พูดเรื่อง fan out ลำดับ ความล้มเหลว และ shared state
ซึ่งเป็นแนวคิดที่ถ่ายทอดไปใช้ที่อื่นได้ แทนที่จะพูดเรื่อง syntax ของ concurrency ใน Python
ซึ่งถ่ายทอดไปไหนไม่ได้เลย

**เวอร์ชันที่ซื่อสัตย์ของข้ออ้างนี้** thread ไม่ได้ดีกว่า async
service ที่รัน agent พร้อมกันเป็นพัน ๆ ตัวจะใช้ async และก็ถูกต้องที่จะใช้
ที่ขนาดนั้น ต้นทุน stack ต่อ thread และ context switching หยุดเป็นเรื่องเล็ก
และ event loop ที่ถือ socket ว่างอยู่หมื่นตัวก็ถูกกว่า thread หมื่นตัวที่ถือ socket ชุดเดียวกันอย่างชัดเจน
ตัวเลขที่จุดตัดนั้นเกิดขึ้นอยู่แถวหลักร้อยปลาย ๆ ส่วนบทนี้รัน worker สี่ตัว

นี่จึงเป็นการตัดสินใจเชิงการสอน และขอระบุไว้ตรง ๆ แบบนั้น
ถ้าคุณเอาโค้ดนี้ไปใส่ใน service ที่ fan out ไปยัง agent หลายร้อยตัวต่อ process
ให้เขียนใหม่ด้วย `asyncio` queue, sentinel, การติดป้าย
และทุกปัญหาในหัวข้อ 4 ถึง 8 รอดจากการเขียนใหม่นั้นโดยไม่เปลี่ยน
เพราะไม่มีอันไหนเลยที่เป็นเรื่องของ thread มันเป็นเรื่องของหลายอย่างเกิดขึ้นพร้อมกัน
ซึ่งเป็นจริงในทั้งสองโมเดล

docstring ของ module พูดเรื่องเดียวกันนี้ในห้าบรรทัด

```python
"""Running several agents at once and merging what they say.

Threads rather than async, for the same reason the rest of the project is
synchronous. An agent run spends nearly all of its life waiting on a socket,
which is the case threads handle well, and async would put a second mental
model in front of a reader who came here to learn about agents.
"""
```

## 3. queue เดียวเป็นจุดนัดพบ

นี่คือ `run_in_parallel` ทั้งหมด

```python
def run_in_parallel(jobs, workers=4):
    jobs = list(jobs)
    if not jobs:
        return

    results = queue.Queue()
    pending = queue.Queue()
    for job in jobs:
        pending.put(job)

    def work():
        while True:
            try:
                label, produce = pending.get_nowait()
            except queue.Empty:
                return
            try:
                for event in produce():
                    results.put((label, event))
            except Exception as error:
                results.put((label, FanoutError(label, error)))
            finally:
                results.put((label, DONE))

    threads = [
        threading.Thread(target=work, daemon=True) for _ in range(min(workers, len(jobs)))
    ]
    for thread in threads:
        thread.start()

    finished = 0
    while finished < len(jobs):
        label, event = results.get()
        if event is DONE:
            finished += 1
            continue
        yield label, event

    for thread in threads:
        thread.join()
```

สามสิบบรรทัด ไล่ดูตามลำดับความสำคัญ

### job คืออะไร

```python
    jobs = list(jobs)
```

job คือคู่ของ label กับ callable ที่คืน iterator ของ event
label คือ string ที่คุณเลือกเอง เช่น `"auth"` หรือ `"parser"`
ส่วน callable ไม่รับอาร์กิวเมนต์ และเมื่อถูกเรียก มันจะผลิต event ออกมาทีละตัว

ทำไมต้องเป็น callable ไม่ใช่ iterator เพราะ iterator ต้องถูกสร้างข้างใน worker thread
ไม่ใช่ในฝั่งผู้เรียก ถ้าคุณส่ง generator ที่เริ่มไปแล้วเข้ามา
ผู้เรียกจะได้รันส่วนแรกของมันบน main thread ไปแล้วก่อนจะส่งต่อ
ซึ่งทำลายจุดประสงค์อย่างเงียบ ๆ และทำให้ไล่เรื่อง timing ไม่ได้
การส่งฟังก์ชันเข้าไปแปลว่าไม่มีอะไรเกี่ยวกับ job นั้นเกิดขึ้นเลยจนกว่า worker จะหยิบมันไป

ทำไมต้อง `list(jobs)` ในบรรทัดแรก เพราะฟังก์ชันนี้ต้องใช้ `len(jobs)` สองครั้ง
ครั้งหนึ่งเพื่อกำหนดขนาด thread pool อีกครั้งเพื่อใช้เป็นขอบเขตของ loop
และผู้เรียกมีสิทธิ์ส่ง generator เข้ามา การเรียก `len` บน generator จะ raise
และการวนซ้ำสองรอบจะไม่ได้อะไรเลยในรอบที่สอง บรรทัดเดียวกำจัดความล้มเหลวทั้งสองแบบ

และกรณีว่างเปล่าจะ return ทันที เพราะการเริ่ม thread ศูนย์ตัวแล้วรอ sentinel ศูนย์ตัว
จะทำงานได้ก็จริง แต่อ่านแล้วเหมือนว่ามันอาจจะไม่ทำงาน

### pending queue ซึ่งก็คือตัวงาน

```python
    pending = queue.Queue()
    for job in jobs:
        pending.put(job)
```

ทุก job ถูกใส่ลงใน queue ก่อนที่ thread ใดจะเริ่ม
แล้ว worker แต่ละตัวก็ดึงจากมันวนไปจนกว่า queue จะว่าง

ทำไมต้องใช้ queue แทนที่จะใช้หนึ่ง thread ต่อหนึ่ง job มีสองเหตุผล และข้อที่สองคือข้อจริง
สิบ job จะแปลว่าสิบ thread ร้อย job ก็ร้อย thread และพารามิเตอร์ `workers` ก็จะกลายเป็นคำโกหก
ที่สำคัญกว่านั้น จำนวน agent ที่คุณรันพร้อมกันเป็นคำถามเรื่อง rate limit
provider จำกัดที่จำนวน request ต่อนาที และ fan out ที่เริ่ม agent หกสิบตัว
เพียงเพราะคุณบังเอิญมีไฟล์หกสิบไฟล์ จะเก็บ 429 กลับมาหกสิบตัว
`workers=4` คือวาล์ว และ queue ที่ใช้ร่วมกันคือสิ่งที่ทำให้วาล์วนั้นเป็นจริง

ทำไมต้อง `get_nowait` ไม่ใช่ `get` เพราะ pending queue ที่ว่างแปลว่างานจบแล้ว
และ worker ตัวนี้ควร return `get` แบบ block จะรอตลอดกาลสำหรับ job ที่ไม่มีวันมา
และ thread ก็จะไม่มีวันจบ ทางเลือกอื่นคือใส่ sentinel ต่อ worker ลงบน `pending`
ซึ่งใช้ได้ และเขียนยาวกว่าเพื่อผลลัพธ์เดียวกัน
`get_nowait` บวกกับการจับ `queue.Empty` พูดเรื่องเดียวกันได้ในสามบรรทัด

การออกแบบนี้มีคุณสมบัติหนึ่งที่ควรเรียกชื่อ job ไม่ได้ถูกจ่ายให้ worker ล่วงหน้า
worker ที่ทำ job เร็วเสร็จจะหยิบ job ถัดไปทันที
ดังนั้นสาม job ที่เร็วกับหนึ่ง job ที่ช้าจะไม่ทำให้ thread สามตัวว่างอยู่ระหว่างที่ตัวช้ากำลังรัน
การจ่ายงานแบบตายตัว ที่ worker หนึ่งได้ job หนึ่งกับสอง และ worker สองได้สามกับสี่
เขียนง่ายกว่าและแย่กว่าด้วยเหตุผลข้อนี้เป๊ะ ๆ

### results queue ซึ่งก็คือคำตอบ

```python
                for event in produce():
                    results.put((label, event))
```

ทุก event ไปลงบน queue เดียว และมันไปพร้อมกับ label ของตัวเอง
มี results queue หนึ่งอันสำหรับ fan out ทั้งชุด ไม่ใช่หนึ่งอันต่อหนึ่ง job

ทำไมต้อง queue เดียว เพราะผู้เรียกอยากได้ event ตามที่มันมาถึง
และการ merge queue สี่อันแปลว่าต้อง poll queue สี่อัน
ซึ่งแปลว่าต้องมี spin loop หรือ thread เพิ่มอีกสี่ตัวมาทำ merge
queue เดียวทำ merge ให้ฟรี และ `queue.Queue` คือกลไกส่งต่อแบบ thread safe
ของ standard library ดังนั้นไม่มีอะไรในไฟล์นี้ที่ต้องจับ lock แบบชัดแจ้ง

ทำไม label ต้องเดินทางไปกับทุก event แทนที่จะประกาศครั้งเดียวตอนต้น job
เพราะฝั่งผู้รับไม่มีสิ่งที่เรียกว่าจุดเริ่มของ job
event จาก job สี่ตัวมาถึงแบบปนกัน ดังนั้นเครื่องหมายที่บอกว่า event ถัดไปเป็นของ `auth`
ก็จะถูกตามมาทันทีด้วย event สามตัวที่ไม่ใช่ หัวข้อ 4 ว่าด้วยผลของเรื่องนี้ทั้งหัวข้อ
และการติดป้ายคือสิ่งที่ทำให้ผลนั้นพออยู่ได้

### sentinel ที่บอกว่า worker ทำงานเสร็จแล้ว

```python
DONE = object()
```

หนึ่งบรรทัดที่หัว module `object()` เปล่า ๆ ที่ใช้เพียงเพื่อ identity ของมัน
และเทียบด้วย `is` ไม่ใช่ `==`

ทำไมต้องมี sentinel เลย ผู้บริโภคต้องรู้ว่าจะหยุดอ่านจาก results queue เมื่อไร
มันรู้จาก queue เองไม่ได้ เพราะ queue ที่ว่างไม่ได้แปลว่าอะไร
มันอาจแปลว่า worker อยู่ระหว่าง event สองตัว
ดังนั้นการจบต้องถูกประกาศ in band ในรูปของค่า และค่านั้นคือ `DONE`

ทำไมต้อง `object()` ไม่ใช่ `None` หรือ string `"done"` หรือ `StopIteration`
เพราะ sentinel ต้องไม่ใช่ค่าที่ job ใด ๆ ผลิตออกมาได้อย่างชอบธรรม
job ที่ yield `None` เป็นไปได้เต็มที่ job ที่ yield string `"done"`
ก็เป็นไปได้ในบทที่พูดเรื่อง agent รายงานผลงานของตัวเอง
`object()` ที่เพิ่งสร้างใหม่ไม่มี reference อื่นใดในโปรแกรมทั้งโปรแกรม
ดังนั้น `event is DONE` จะเป็นจริงกับสิ่งเดียวในจักรวาล และปลอมด้วย payload ไม่ได้

ทีนี้มาถึงตำแหน่งวาง ซึ่งเป็นส่วนที่แบกน้ำหนักไว้

```python
            finally:
                results.put((label, DONE))
```

มันอยู่ใน `finally` job ที่จบปกติจะใส่ `DONE` job ที่ raise จะใส่ `FanoutError`
แล้วตามด้วย `DONE` ไม่มีเส้นทางไหนในตัว worker ที่กิน job จาก `pending`
โดยไม่ลงเอยด้วยการใส่ `DONE` ลงบน `results`
invariant นั้นคือสิ่งเดียวที่กั้นระหว่างผู้เรียกกับการค้างถาวร
มันจึงถูกบังคับด้วยตัวภาษา ไม่ใช่ด้วยการจำว่าต้องทำมันในสองที่

สังเกตด้วยว่า `DONE` เป็นรายต่อ job ไม่ใช่ต่อ worker มันอยู่ข้างใน `while` loop
ดังนั้น worker ที่จัดการสาม job จะปล่อย sentinel สามตัว
นั่นคือสิ่งที่ทำให้การนับในส่วนถัดไปถูกต้อง

### ทำไม main loop ถึงนับ sentinel

```python
    finished = 0
    while finished < len(jobs):
        label, event = results.get()
        if event is DONE:
            finished += 1
            continue
        yield label, event
```

เงื่อนไขการจบคือจำนวน sentinel ที่เห็นเท่ากับจำนวน job ที่ส่งเข้าไป
ไม่ใช่ว่า thread หยุดแล้ว

ทางเลือกที่นึกออกง่ายคือถาม thread เอา

```python
    while any(thread.is_alive() for thread in threads):
        ...
```

นั่นผิดทั้งสองทาง และทั้งสองทางควรค่าแก่การเข้าใจ
เพราะนี่คือความผิดพลาดคลาสสิกในโค้ดแบบ producer และ consumer

**มันหยุดเร็วเกินไปได้** thread ทำ job สุดท้ายจบ ใส่ event ชุดสุดท้ายลงบน `results` แล้วออก
ตอนนี้ `is_alive` เป็นเท็จสำหรับทุก thread ทั้งที่ยังมี event นั่งอยู่ใน queue โดยไม่มีใครอ่าน
loop ออก และผู้เรียกก็ได้ event น้อยกว่าที่ job ผลิตออกมาแบบเงียบ ๆ
คำว่าเงียบ ๆ คือคำสำคัญ ไม่มีอะไร raise
คุณได้คำตอบที่หายไปหนึ่งย่อหน้าโดยไม่มีสัญญาณใดบอกว่ามีอะไรผิดพลาด

**และมันก็หยุดในจังหวะที่ถูกต้องไม่ได้เช่นกัน** `results.get()` block
การผสมการอ่านแบบ block กับเงื่อนไขความมีชีวิตแปลว่าคุณเช็คเงื่อนไขระหว่างที่ถูก block ไม่ได้
คุณจึงต้องใช้ `get(timeout=...)` กับ loop ที่ตื่นขึ้นมาซ้ำ ๆ เพื่อถามคำถาม
ที่คำตอบแทบจะเหมือนเดิมทุกครั้ง นั่นคือ spin loop ที่มีขั้นตอนเพิ่ม
มันเผา CPU ทั้งที่ไม่ได้ทำอะไร และมันเพิ่มพารามิเตอร์ที่ต้องจูนโดยไม่มีค่าที่ถูกต้อง

การนับ sentinel ไม่มีปัญหาทั้งสองข้อ `results.get()` block โดยไม่มี timeout
ซึ่งไม่มีต้นทุนขณะรอ และตื่นทันทีที่มีอะไรมาถึง
และเพราะทุก job ถูกรับประกันว่ามี sentinel หนึ่งตัวพอดีด้วย `finally`
การที่ตัวนับถึง `len(jobs)` จึงแปลว่าทุก event ที่จะถูกผลิตขึ้นได้ถูกใส่ลง queue ไปแล้ว
และทุกตัวถูกอ่านก่อน sentinel ของมัน
เพราะ worker แต่ละตัวใส่ event ของ job ลง queue ก่อนที่จะใส่ sentinel ของ job นั้น
และ queue คืนของตามลำดับที่ใส่เข้าไป

มีประเด็นที่ลึกกว่านั้นอยู่ตรงนี้ `is_alive` ตอบคำถามเกี่ยวกับ worker
คำถามของผู้เรียกเป็นเรื่องของ job สองอย่างนี้เป็นคนละอย่างกัน
จำนวนก็ยังไม่เท่ากันด้วยซ้ำ และการสร้าง loop บนอย่างที่ผิดคือสิ่งที่ทำให้บั๊กนี้เกิดขึ้นได้ตั้งแต่ต้น

`join` ตอนท้ายเป็นงานเก็บกวาดมากกว่าการ synchronise
เมื่อถึงตอนที่ตัวนับครบแล้ว งานก็เสร็จแล้ว และ join แค่เก็บ thread
เพื่อไม่ให้มันอยู่นานกว่าการเรียกครั้งนี้

### ข้อจำกัดสองข้อของฟังก์ชันนี้ที่พูดกันตรง ๆ

ทั้งสองข้อไม่ใช่ข้อบกพร่อง แต่คุณควรรู้ทั้งคู่

`run_in_parallel` เป็น generator ดังนั้น thread จะไม่เริ่มจนกว่าผู้เรียกจะเริ่มวนซ้ำ
เรียกมันแล้วทิ้งผลลัพธ์ไป จะไม่มีอะไรรันเลย
ปกติแล้วนั่นคือสิ่งที่คุณต้องการ และเป็นเรื่องน่าประหลาดใจอยู่บ้างเป็นครั้งคราว

และถ้าผู้เรียกทิ้ง generator กลางคัน ด้วยการ break ออกจาก `for` thread จะยังทำงานต่อ
มันเป็น `daemon=True` ดังนั้นมันจะไม่ขวางไม่ให้โปรแกรมจบ
และ event ที่มันผลิตก็จะกองอยู่ใน queue ที่ไม่มีใครอ่าน
`join` ข้างล่างจะไม่ถูกรันเลย สำหรับ fan out สี่ job เรื่องนี้ไม่มีพิษภัย
สำหรับ service ที่รันยาว มันคือ leak และทางแก้คือ cancellation token
แบบที่บทที่ 17 สร้างไว้ โดยให้ worker เช็คมันระหว่าง event

## 4. streaming กับ concurrency ดึงกันไปคนละทาง

หัวข้อนี้ไม่ใช่เรื่องแทรก มันคือเหตุผลที่ `run_in_parallel` yield `(label, event)`
แทนที่จะเป็น `event` และเป็นปัญหาการออกแบบที่ทุก agent interface จริง ๆ ต้องแก้

**streaming มีไว้ทำอะไร** บทที่ 05 สร้างมันขึ้นมา และเหตุผลคือเรื่องของคนที่นั่งดู
model ใช้เวลายี่สิบวินาทีกว่าจะผลิตคำตอบออกมา
การพิมพ์ทั้งก้อนตอนจบแปลว่าจอว่างเปล่ายี่สิบวินาที และจอว่างเปล่าก็แยกไม่ออกจากอาการค้าง
การพิมพ์แต่ละ token ตามที่มันมาถึงแปลว่าคนเห็นความคืบหน้าทันที
และบอกได้ภายในสองวินาทีว่า agent เข้าใจคำถามหรือไม่

**concurrency ทำอะไรกับเรื่องนั้น** streaming ทำงานได้เพราะมีผู้เขียนหนึ่งคนต่อจอหนึ่งจอ
agent สี่ตัว streaming พร้อมกันคือผู้เขียนสี่คนต่อจอเดียว
และพวกมันผลัดกันในระดับตัวอักษร

นี่ไม่ใช่การทดลองในความคิด สอง job แต่ละตัว yield ทีละตัวอักษร
เขียนตรงไปที่ stdout โดยไม่มี label

```python
jobs = [
    ("one", chars("the auth module looks fine", 0.004)),
    ("two", chars("THE PARSER DROPS A TOKEN", 0.004)),
]
for label, event in run_in_parallel(jobs, workers=2):
    sys.stdout.write(event)
```

```text
tTHhEe  PauAtRSh EmRo dDRulOPeS l Ao oTkOsK EfNine
```

ทั้งสองประโยคอยู่ในนั้น แต่อ่านไม่ออกสักประโยค
และสังเกตว่าคุณเสียประโยคไหนไป เพราะมันสำคัญ
หนึ่งในสอง job นั้นกำลังรายงานบั๊กใน parser
และตอนนี้มันกลายเป็นลำดับตัวอักษรพิมพ์ใหญ่ที่ถูกยัดอยู่ในประโยคที่บอกว่าทุกอย่างเรียบร้อยดี

agent สองตัวก็อ่านไม่ออกแล้ว สี่ตัวยิ่งแย่กว่า และความล้มเหลวนี้ไม่ค่อยสง่างาม
มันไม่ได้แค่อ่านยากขึ้น มันเลิกเป็นข้อความไปเลย

**ทำไมทุก event ถึงต้องพก label ไปด้วย** เพราะการ merge ต้องย้อนกลับได้
เมื่อ stream สี่สายถูกต่อรวมเป็นลำดับตัวอักษรเดียวแล้ว
ไม่มีความฉลาดใดปลายทางที่จะแยกมันออกจากกันได้อีก
ข้อมูลว่า job ไหนพูดอะไรต้องรอดจากการ merge
และที่เดียวที่จะใส่มันได้คือบนแต่ละ event ณ ขณะที่ event ถูกผลิต
ข้างใน worker ที่รู้คำตอบ

```python
                for event in produce():
                    results.put((label, event))
```

นั่นคือกลไกทั้งหมด `label` ถูกจับมาจาก job ที่ worker ดึงจาก `pending`
มันจึงหลุดจังหวะกับ event ไม่ได้

เมื่อมี label การรันแบบเดียวกันก็อ่านออกอย่างสมบูรณ์
และนี่คือ output จริงจาก fan out สาม job ชุดเดิม โดยมีการหน่วงเล็กน้อยระหว่าง event

```text
   c | c-0
   b | b-0
   a | a-0
   b | b-1
   a | a-1
   c | c-1
   c | c-2
   a | a-2
   b | b-2
```

เก้า event ปนกันอย่างทั่วถึง และทุกตัวระบุที่มาได้

**ทำไม interface จริง ๆ ถึงหยุด streaming อยู่ดี** การติด label ทำให้ output กู้คืนได้
มันไม่ได้ทำให้ข้อความแบบทีละ token อ่านง่ายขึ้น
การใส่ชื่อ job นำหน้าทุก token เปลี่ยนข้อความยี่สิบห้าตัวอักษรให้เป็นยี่สิบห้าบรรทัด
ซึ่งแย่กว่าการปนกันที่มันแก้ไปเสียอีก

คำตอบที่ใช้ได้จริง และเป็นสิ่งที่ harness ที่จริงจังทุกตัวทำ
คือเปลี่ยนสิ่งที่แสดงผลทันทีที่มี job มากกว่าหนึ่งตัวกำลังรัน
job เดียว ก็ stream ข้อความไป มากกว่าหนึ่ง job ก็หยุด stream ข้อความ
แล้วแสดงความคืบหน้ารายตัวแทน

```text
  auth      running   3 tool calls   12s
  parser    running   5 tool calls   14s
  storage   done      2 tool calls    9s   found 1 issue
  config    queued
```

การแสดงผลนั้นสร้างจาก stream ของ event ที่ติด label ชุดเดียวกันเป๊ะ
ไม่มีอะไรใน `fanout.py` เปลี่ยนเลย ผู้เรียกเป็นคนตัดสินใจว่าจะ render หนึ่งบรรทัดต่อหนึ่ง label
อัปเดตทับที่เดิม แทนที่จะต่อข้อความกัน
นี่คือเหตุผลที่ `run_in_parallel` ไม่มีความเห็นเรื่องการนำเสนอ และแค่ yield คู่ออกมา
หน้าที่ของ module นี้คือทำให้ข้อมูลใช้ได้พร้อมกับที่มาของมัน
ส่วนจะทำอะไรกับมันเป็นคำถามเรื่องหน้าจอ
และ module ที่พิมพ์เองก็จะฝังคำตอบเดียวของคำถามนั้นลงในไฟล์ที่ thread สี่ตัว import

นั่นคือข้อโต้แย้งเดียวกับที่บทที่ 18 พูดเรื่อง `on_message` เป็น callback
และเหมือนกับที่บทที่ 17 พูดเรื่องตัวช่วย retry ที่ไม่พิมพ์อะไร
มันมาถึงที่นี่ในฐานะผลที่ตามมา ไม่ใช่ความชอบส่วนตัว
module ที่พิมพ์เองไม่สามารถถูกใช้โดย thread สี่ตัวพร้อมกันได้
เพราะสี่ module ที่พิมพ์ลง stream เดียวกันจะได้ผลเป็นเรื่องไร้สาระข้างบนนั้นเป๊ะ ๆ

## 5. อะไรที่รับปาก และอะไรที่ไม่

สองประโยค และประโยคที่สองคือข้อจำกัดที่ยกเลิกไม่ได้

**ลำดับภายใน job หนึ่งตัวถูกรักษาไว้** ถ้า job `auth` ผลิต event สามตัว
ผู้เรียกจะได้รับ event สามตัวนั้นตามลำดับสัมพัทธ์กันเอง เสมอ

**ลำดับข้าม job ไม่มีนิยาม** ไม่มีการรับประกันว่า event ของ `auth`
จะตกอยู่ตรงไหนเทียบกับของ `parser` และรับประกันไม่ได้ด้วย
เพราะการรันพร้อมกันคือความหมายของการที่สองลำดับไม่สัมพันธ์กันพอดี
fan out ที่รับปากลำดับตายตัวข้าม job จะต้องรัน job ทีละตัวเพื่อรักษาสัญญา
ซึ่งเป็นสิ่งที่ module นี้มีอยู่เพื่อหยุดทำ

ทำไมการรับประกันข้อแรกถึงเป็นจริงก็ควรพูดสักประโยค เพราะมันไม่ใช่เรื่องบังเอิญของ timing
worker รัน `for event in produce()` และใส่ event แต่ละตัวลง queue
ตามลำดับที่มันออกมาจาก iterator `queue.Queue` เป็นแบบ first in first out
ดังนั้นสอง event จาก job เดียวกันสลับที่กันไม่ได้ เพราะมันถูกใส่ลง queue เดียวกัน
โดย thread เดียวกัน ตามลำดับ ไม่มีอะไรอื่นเกี่ยวกับ scheduling ที่มีผล

docstring ผูกมัดกับทั้งสองข้อ รวมถึงส่วนที่บอกว่าข้อไหนสำคัญ

```python
    jobs is a list of (label, callable) where the callable returns an
    iterator of events. Order across jobs is not defined and cannot be,
    because that is what running at the same time means. Order within one
    job is preserved, which is the part that actually matters.
```

ประโยคย่อยสุดท้ายนั้นคือข้ออ้างเชิงการออกแบบ event ของ job หนึ่งตัวคือลำดับที่มีความหมาย
อ่านไฟล์ แล้วแก้ไฟล์ แล้วรัน test การกลับลำดับนั้นเป็นคนละเรื่องกันเลย
ส่วน `auth` จบก่อน `parser` หรือไม่ แทบไม่เคยเป็นข้อมูลที่ใครต้องการ
และราคาของการรับประกันมันคือ speedup ทั้งหมด

### check ที่พิสูจน์เรื่องนี้

`check.py` รันสาม job ที่มี event ตัวละสามตัว แล้ว assert บน subsequence ราย label

```python
    jobs = [("a", steps("a", 3)), ("b", steps("b", 3)), ("c", steps("c", 3))]
    seen = list(run_in_parallel(jobs, workers=3))
    if len(seen) != 9:
        fail(f"expected nine events, got {len(seen)}")
    print("OK three jobs ran at once and every event arrived")

    for label in ["a", "b", "c"]:
        ordered = [event for name, event in seen if name == label]
        if ordered != [f"{label}-0", f"{label}-1", f"{label}-2"]:
            fail(f"job {label} came back out of order. Got {ordered}")
    print("OK each job kept its own order even though the output was interleaved")
```

อ่านดูว่าตัวกรองนั้นทำอะไร มันเอาลำดับการมาถึงทั้งหมด ซึ่งปนกัน
แล้วเก็บเฉพาะ event ที่มี label เดียว subsequence นั้นต้องเป็น
`a-0`, `a-1`, `a-2` เป๊ะ ๆ check ไม่ได้ assert อะไรเลยเกี่ยวกับว่าสามตัวนั้นอยู่ตรงไหนใน list รวม

นั่นเป็นรูปแบบเดียวของ assertion ที่ทำได้ที่นี่ check ที่ assert บน list ทั้งก้อน
จะเท่ากับ assert บน scheduler และมันจะผ่านบนเครื่องคุณ ผ่านร้อยครั้งติดกัน
แล้วก็ไปพังใน CI บน runner ที่โหลดหนัก ด้วยเหตุผลที่ไม่เกี่ยวกับโค้ดของคุณเลย
check ที่ผลลัพธ์ไม่แน่นอนแย่กว่าไม่มี check เลย เพราะมันฝึกให้ทุกคนรันซ้ำแทนที่จะอ่านมัน

ข้ออ้างแรก `len(seen) != 9` คือคู่ตรงข้าม มันบอกว่าไม่มีอะไรหายไป
นั่นคือ assertion ที่จับบั๊ก `is_alive` จากหัวข้อ 3
ที่ผู้บริโภคหยุดขณะยังมี event ค้างอยู่ใน queue เก้า event เข้าไป เก้า event ออกมา
และ assertion เรื่องลำดับก็ครอบคลุมส่วนที่เหลือ

ทั้งสองบรรทัดจากการรันจริง

```text
OK three jobs ran at once and every event arrived
OK each job kept its own order even though the output was interleaved
```

มีอีกอย่างที่คุณลองดูเองได้ รันสาม job ชุดเดิมโดยไม่มีการหน่วงระหว่าง event
แล้ว output มักจะไม่ปนกันเลย

```text
   a | a-0
   a | a-1
   a | a-2
   b | b-0
   b | b-1
   b | b-2
```

ไม่มีอะไรผิด job สั้นมากจน worker ตัวแรกระบาย job ทั้งตัวของมันจนหมด
ก่อนที่ operating system จะเริ่ม thread ตัวที่สามเสร็จด้วยซ้ำ
นี่คือเหตุผลเชิงปฏิบัติที่ check กรองด้วย label แทนที่จะคาดหวังว่าจะเห็นการปนกัน
concurrency ไม่ได้รับปากว่าจะมี interleaving ให้คุณ มันแค่ปฏิเสธที่จะรับปากเรื่องลำดับ

## 6. job หนึ่งตัวล้มเหลวต้องไม่ล้มทั้งชุด

**เกิดอะไรขึ้นเมื่อ job หนึ่ง raise** worker จับมันไว้ แปลงเป็นค่าหนึ่งค่า
แล้วใส่ค่านั้นลง results queue เหมือน event อื่น ๆ

```python
            try:
                for event in produce():
                    results.put((label, event))
            except Exception as error:
                results.put((label, FanoutError(label, error)))
            finally:
                results.put((label, DONE))
```

มีสามเรื่องที่ตามมาจากเจ็ดบรรทัดนั้น และแต่ละเรื่องเป็นความตั้งใจ

อีกสาม job ไม่ถูกแตะต้อง มันรันอยู่บน thread อื่นและไม่รู้เรื่องนี้เลย
event ของมันยังมาถึงเรื่อย ๆ และ sentinel ของมันก็ยังทำให้ตัวนับเดินหน้าต่อ

event ที่ job นี้ผลิตออกมาก่อนที่มันจะพังถูกส่งมอบไปแล้ว
มันไปลง queue ตอนที่ถูกผลิต ดังนั้น job ที่อ่านสองไฟล์แล้วพังที่ไฟล์ที่สาม
ได้ให้ผลลัพธ์จริงกับคุณสองชิ้นบวกกับรายงานความล้มเหลว แทนที่จะไม่ให้อะไรเลย

และ `finally` ยังทำงานอยู่ ดังนั้น sentinel ก็ยังมาถึง
ถ้าไม่มีมัน job ที่ raise ตัวเดียวจะทำให้ main loop รอตลอดกาลสำหรับตัวนับที่ไม่มีวันครบ
ชุดงานที่ค้างเพราะ job เสียตัวเดียวเป็นผลลัพธ์ที่แย่กว่าชุดงานที่ล้มเหลวไปเลย
เพราะอย่างน้อยความล้มเหลวก็บอกอะไรคุณบ้าง

**ทำไมความล้มเหลวถึงเป็น event ไม่ใช่ exception**
นี่คือการตัดสินใจที่ควรค่าแก่การปกป้อง เพราะการ raise มันดูเป็นธรรมชาติกว่า
และเป็นสิ่งที่คนส่วนใหญ่เขียนเป็นอย่างแรก

exception ใน worker thread ไม่สามารถถูก raise ในฝั่งผู้เรียกได้ ไม่มีกลไกสำหรับเรื่องนั้น
สิ่งที่ดีที่สุดที่คุณทำได้คือเก็บมันไว้แล้ว re raise จาก main loop
แล้วก็ต้องตอบคำถามว่าอีกสาม job จะเป็นอย่างไร

ถ้าคุณ re raise ทันที คุณก็ได้สร้าง fan out ที่ความล้มเหลวหนึ่งอันทิ้งผลลัพธ์ที่ดีสามอัน
agent สี่ตัว review สี่ module ตัวหนึ่งเจอ network error ที่ request สุดท้าย
แล้วตอนนี้คุณไม่เหลืออะไรเลย สามตัวที่สำเร็จก็สำเร็จจริง คำตอบของมันถูกต้องและครบถ้วน
และคุณโยนมันทิ้งไปเพราะมีอะไรที่ไม่เกี่ยวกันเกิดผิดพลาดขึ้น

ถ้าคุณเก็บ exception ไว้แล้ว raise ตอนจบ คุณต้องคิดค้นวิธี raise สี่อย่างพร้อมกัน
และผู้เรียกก็เสีย interleaving ซึ่งเป็นจุดประสงค์ของการ stream ผลลัพธ์ตามที่มันมาถึง

ถ้าคุณกลืนมันเงียบ ๆ คุณจะได้ผลลัพธ์ที่แย่ที่สุดในบทนี้ทั้งบท
สี่ job เข้าไป สามคำตอบออกมา ไม่มีอะไรที่ไหนบอกว่าเคยมี job ที่สี่อยู่
ผู้เรียกเขียนรายงานเรื่องสาม module แล้วไม่มีวันรู้ว่าตัวที่สี่ไม่เคยถูก review เลย
docstring ระบุเรื่องนี้ไว้ตรง ๆ

```python
    A job that raises does not stop the others. It yields one final event of
    its own describing the failure, because a batch where one item silently
    vanished is worse than one that reports a problem.
```

การรายงานความล้มเหลวในรูป event เลี่ยงปัญหาทั้งสามข้อ
ผู้เรียกเห็นมันใน stream ตามลำดับ พร้อม label ติดมาด้วย
แล้วตัดสินใจเองว่าชุดงานที่ได้ไม่ครบใช้ได้หรือไม่
การตัดสินใจนั้นเป็นของผู้เรียก เพราะมีแต่ผู้เรียกที่รู้ว่าชุดงานนี้มีไว้ทำอะไร

**ทำไม `FanoutError` ถึงไม่ใช่ exception class**

```python
class FanoutError:
    """One job failed. Reported as an event so the caller sees it in order."""

    def __init__(self, label, error):
        self.label = label
        self.error = error

    def __repr__(self):
        return f"FanoutError({self.label!r}, {self.error!r})"
```

มันไม่ได้สืบทอดจาก `Exception` นั่นไม่ใช่ความหลงลืม
มันแปลว่าไม่มีใครปลายทางที่จะ `raise` มันโดยบังเอิญได้
เพราะ Python ปฏิเสธที่จะ raise สิ่งที่ไม่ใช่ `BaseException`
ระบบ type บังคับว่าสิ่งนี้เป็นค่าที่บรรยายความล้มเหลว ไม่ใช่ความล้มเหลวที่กำลังลอยอยู่
ซึ่งเป็นความแตกต่างที่การออกแบบนี้พึ่งพาอยู่พอดี

มันเก็บ exception ต้นฉบับไว้ใน `self.error` ดังนั้นไม่มีอะไรสูญหาย
ทั้ง type และข้อความของ traceback อยู่ครบสำหรับผู้เรียกที่อยาก log มัน
และ `__repr__` พิมพ์ทั้งคู่เมื่อ check ล้มเหลว
ซึ่งเป็นความต่างระหว่างข้อความความล้มเหลวที่ใช้ได้กับ `<FanoutError object at 0x7f...>`

**ตัว check** หนึ่ง job ที่ปกติดี กับอีกหนึ่งที่พังกลางคัน

```python
    def explode():
        yield "before"
        raise RuntimeError("this job broke")

    mixed = list(run_in_parallel([("good", steps("good", 2)), ("bad", explode)], workers=2))
    good = [event for label, event in mixed if label == "good"]
    bad = [event for label, event in mixed if label == "bad"]
    if good != ["good-0", "good-1"]:
        fail(f"a failing job disturbed a healthy one. Got {good}")
    if not isinstance(bad[-1], FanoutError):
        fail(f"a failing job was not reported. Got {bad}")
```

`explode` yield หนึ่ง event ก่อนจะ raise ซึ่งเป็นความตั้งใจ
job ที่ล้มเหลวก่อนจะผลิตอะไรเลยจะไม่ได้ทดสอบว่าผลลัพธ์บางส่วนรอดหรือไม่

สอง assertion ครอบคลุมสองทางที่เรื่องนี้จะพลาด
job ที่ปกติดีต้องส่งมอบ event ทั้งสองตัวของมันตามลำดับ
ซึ่งตัดความเป็นไปได้ที่ความล้มเหลวไปรบกวนมันออกไป
และ event สุดท้ายจาก job ที่ล้มเหลวต้องเป็น `FanoutError`
ซึ่งตัดความเป็นไปได้ที่มันหายไปเงียบ ๆ ออกไป
สังเกตว่ามันเช็ค `bad[-1]` ไม่ใช่ `bad` เพราะ `before` อยู่ในนั้นอย่างชอบธรรมและต้องอยู่

```text
OK one job failing did not take the batch with it, and the failure was reported
```

## 7. พิสูจน์ว่างานซ้อนทับกันจริง

ทุกอย่างข้างบนคือกลไก ไม่มีอะไรคุ้มค่าสักบรรทัดถ้า job ไม่ได้รันพร้อมกันจริง
และเป็นไปได้อย่างสิ้นเชิงที่จะเขียนทั้งหมดนี้แล้วมันยังรันแบบเรียงลำดับอยู่ดี
เช่นด้วยการเผลอบริโภค iterator แต่ละตัวบน main thread

ดังนั้น check จึงวัด

```python
    slow = [("x", steps("x", 1, pause=0.3)), ("y", steps("y", 1, pause=0.3))]
    started = time.monotonic()
    list(run_in_parallel(slow, workers=2))
    elapsed = time.monotonic() - started
    if elapsed > 0.55:
        fail(f"the jobs ran one after another, taking {elapsed:.2f} seconds")
    print(f"OK two jobs that each wait 0.3 seconds finished in {elapsed:.2f}, so they overlapped")
```

สอง job แต่ละตัวหลับสามในสิบวินาทีแล้ว yield หนึ่ง event
รันทีละตัวจะได้หกในสิบ รันพร้อมกันจะได้สามในสิบบวกต้นทุนการเริ่ม thread

output จริง

```text
OK two jobs that each wait 0.3 seconds finished in 0.30, so they overlapped
```

สามในสิบ ไม่ใช่หกในสิบ การซ้อนทับถูกวัด ไม่ใช่ถูก assert
และนี่คือข้ออ้างเดียวใน `check.py` ที่ไม่สามารถทำได้ด้วยการอ่านโค้ด

รายละเอียดสามข้อในเจ็ดบรรทัดนั้นควรค่าแก่การคัดลอกไปใส่ใน test ของคุณเอง

**`time.monotonic` ไม่ใช่ `time.time`** `time.time` เป็นนาฬิกาแขวนผนัง
มันถูกปรับโดย NTP ได้ มันกระโดดเมื่อนาฬิการะบบถูกแก้ และมันเดินถอยหลังได้
ซึ่งจะได้ระยะเวลาติดลบและ check ที่ล้มเหลวด้วยเหตุผลที่ไม่เกี่ยวกับโค้ดเลย
`time.monotonic` เดินไปข้างหน้าเสมอและมีอยู่เพื่อการวัดแบบนี้พอดี
แบบฝึกหัดข้อที่สองของบทที่ 18 พูดเรื่องความต่างเดียวกันนี้จากอีกทางหนึ่ง

**`sleep` ไม่ใช่การคำนวณ** `time.sleep` ปล่อย interpreter lock
ซึ่งทำให้มันเป็นตัวแทนที่ซื่อสัตย์ของการรอบน socket
thread สองตัวที่ทำเลขคณิตสามในสิบวินาทีจะไม่จบใน 0.3 วินาที
เพราะ lock บังคับให้ bytecode เรียงคิว การใช้ busy loop ตรงนี้จะได้ check
ที่ล้มเหลวทั้งที่โค้ดถูกต้อง และจะเป็นการจำลองสิ่งที่ผิด
เพราะ agent run รอมากกว่าคำนวณอยู่มาก

**เกณฑ์คือ 0.55 ไม่ใช่ 0.31** ขอบเขตต้องแยกสองผลลัพธ์ออกจากกัน
ซึ่งคือสามในสิบกับหกในสิบ และมันควรอยู่ตรงกลางระหว่างสองค่านั้น
มากกว่าจะไปเบียดชิดค่าที่ดี การเริ่ม thread ความสั่นไหวของ scheduler
และเครื่อง CI ที่โหลดหนัก ล้วนเพิ่มมิลลิวินาทีที่ไม่เกี่ยวกับความถูกต้อง
การ assert `elapsed < 0.31` ให้ check ที่ล้มเหลวในบ่ายที่เครื่องยุ่ง
และสอนให้ทุกคนเมินมัน การ assert `elapsed > 0.55`
จะล้มเหลวก็ต่อเมื่อ job รันทีละตัวจริง ๆ ซึ่งเป็นสิ่งที่กำลังถูกทดสอบ

ประเด็นสุดท้ายนั้นใช้ได้ทั่วไป เวลาคุณจับเวลา concurrency
ให้เลือกเกณฑ์ด้วยการถามว่าคุณกำลังแยกสองผลลัพธ์ไหนออกจากกัน แล้ววางเส้นไว้ตรงช่องว่าง

## 8. อันตรายที่ไม่มีใครเตือนคุณ

ทุกอย่างที่ผ่านมาเป็นเรื่องการ merge output หัวข้อนี้เป็นเรื่อง shared state
มันคือเหตุผลที่ agent แบบขนานยากกว่า HTTP request แบบขนาน
และเป็นส่วนที่งานเขียนส่วนใหญ่ในเรื่องนี้ละไว้

**ความล้มเหลวที่เป็นรูปธรรม** agent สองตัวรันพร้อมกัน ทั้งคู่มี `edit_file`
ทั้งคู่ตัดสินใจแก้ `settings.py`

1. worker one อ่าน `settings.py` ตอนนี้มันถือข้อความนั้นไว้ใน context ของตัวเอง
2. worker two อ่าน `settings.py` มันถือข้อความชุดเดียวกัน
3. worker one คิดออกว่าจะแก้อะไรแล้วเขียนไฟล์ ตอนนี้ `DEBUG = True` อยู่บนดิสก์แล้ว
4. worker two คิดออกว่าจะแก้อะไรแล้วเขียนไฟล์ แต่ worker two กำลังเขียนเวอร์ชัน
   ที่มันอ่านมาในขั้นที่ 2 ซึ่งไม่มีการแก้ของ worker one อยู่ บวกกับการแก้ของตัวเองทับลงไป

การแก้ของ worker one หายไป ไม่ใช่ conflict ไม่ใช่ถูกรายงาน ไม่ใช่ถูกปฏิเสธ
หายไป ถูกเขียนทับด้วยการเขียนที่สำเร็จ

นี่คือปัญหา lost update มันเก่าเป็นสิบ ๆ ปีแล้ว และควรค่าแก่การดูมันเกิดขึ้น
สอง job แต่ละตัวอ่านไฟล์ คิดสักครู่ แล้วเขียน

```python
def editor(label, old, new, pause):
    def produce():
        text = target.read_text(encoding="utf-8")   # read
        yield f"{label} read the file"
        time.sleep(pause)                            # think
        text = text.replace(old, new)
        target.write_text(text, encoding="utf-8")    # write
        yield f"{label} wrote the file"
    return produce

jobs = [
    ("worker-1", editor("worker-1", "DEBUG = False", "DEBUG = True", 0.05)),
    ("worker-2", editor("worker-2", "TIMEOUT = 30", "TIMEOUT = 60", 0.10)),
]
```

ไฟล์เริ่มต้นด้วย `DEBUG = False` และ `TIMEOUT = 30`
worker สองตัวแก้คนละบรรทัด ซึ่งเป็นกรณีที่ทุกคนคิดว่าปลอดภัย output จริง

```text
 worker-2 | worker-2 read the file
 worker-1 | worker-1 read the file
 worker-1 | worker-1 wrote the file
 worker-2 | worker-2 wrote the file
---- settings.py afterwards ----
DEBUG = False
TIMEOUT = 60
```

อ่านสองบรรทัดสุดท้าย `TIMEOUT` ถูกเปลี่ยน `DEBUG` ไม่ถูกเปลี่ยน
worker one รายงานว่าสำเร็จ `edit_file` คืนค่าตามปกติ และการแก้ของมันไม่อยู่บนดิสก์

ลองนั่งพิจารณาดูว่าการวินิจฉัยนี้แย่แค่ไหน ไม่มี exception ไม่มี warning
agent ทั้งคู่จะบอกคุณอย่างซื่อสัตย์ว่ามันแก้ไปแล้ว
เพราะจากมุมมองข้างใน agent แต่ละตัว นั่นคือสิ่งที่เกิดขึ้นจริง
ไฟล์ session บันทึกการแก้ที่สำเร็จสองครั้ง
ทางเดียวที่จะรู้คือไปอ่านไฟล์ทีหลังแล้วสังเกตว่ามีอะไรหายไป
และถ้าสิ่งที่หายไปเป็นบรรทัดที่คุณเพิ่ม ไม่ใช่บรรทัดที่คุณลบ
คุณอาจไม่สังเกตไปอีกทั้งสัปดาห์

**ทำไมการแก้คนละบรรทัดถึงไม่ช่วยคุณ** เพราะ `edit_file` ไม่ได้แก้ทีละบรรทัด
มันอ่านไฟล์ทั้งไฟล์ แทนที่ string แล้วเขียนไฟล์ทั้งไฟล์กลับไป
หน่วยของการเขียนคือไฟล์ ดังนั้นการเขียนสองครั้งลงไฟล์เดียวกันจะชนกันเสมอ
ไม่ว่าจุดที่แก้จะห่างกันแค่ไหน ตัวอย่างข้างบนคือเวอร์ชันที่เป็นมิตรที่สุดของเรื่องนี้
สองการแก้บรรทัดเดียวที่เป็นอิสระต่อกัน และมันยังเสียไปหนึ่งอัน

**มันไม่ใช่เรื่องทฤษฎี และไม่ใช่เรื่องหายาก** มันต้องการสองเงื่อนไข
agent สองตัวรันพร้อมกัน และมีการทับซ้อนใด ๆ ในไฟล์ที่มันแตะ
fan out ไปสี่ module ใน package เดียว แล้วทั้งหมดก็จะอยากแตะ config ที่ใช้ร่วมกัน
แตะ import แตะ test helper ยิ่ง fan out ของคุณมีประโยชน์มากเท่าไร
job ก็ยิ่งเกี่ยวข้องกันมากเท่านั้น และยิ่งเกี่ยวข้องกันก็ยิ่งทับซ้อนกันมาก

**harness จริง ๆ ทำอะไรกับเรื่องนี้** มีคำตอบสองตระกูล
และทั้งสองเป็นงานวิศวกรรมจริง ไม่ใช่แค่ flag

ตระกูลแรกคือทำให้การเขียนเรียงคิว การอ่านรันแบบขนานได้
เพราะการอ่านพร้อมกันชนกันไม่ได้ และทุก tool ที่เปลี่ยนแปลงโลกต้องผ่าน lock
หรือผ่าน writer thread ตัวเดียว ดังนั้นจะมีการเขียนแค่ครั้งเดียวที่กำลังดำเนินอยู่
วิธีนี้ทำง่ายและมันไม่ได้แก้ปัญหาจริง ๆ มันทำให้การเขียนเป็น atomic
คุณจึงไม่มีวันได้ไฟล์ที่เขียนไม่จบ แต่ลำดับเหตุการณ์ข้างบนมีการเขียนเป็น atomic ทั้งคู่อยู่แล้ว
และ update ก็ยังหายอยู่ดี การจะทำให้ถูกต้องต้องให้ผู้เขียนตรวจว่าไฟล์ไม่ได้เปลี่ยนไป
ตั้งแต่ตอนที่ agent อ่าน และปฏิเสธการเขียนถ้ามันเปลี่ยน
ซึ่งคือ optimistic concurrency control จากนั้นคุณต้องตัดสินใจว่า agent จะทำอะไรเมื่อถูกปฏิเสธ
และคำตอบคือมันต้องอ่านใหม่และทำงานใหม่

ตระกูลที่สองคือให้ worker แต่ละตัวมีสำเนา workspace ของตัวเอง
git worktree หรือไดเรกทอรีที่ copy มาต่อ agent หนึ่งตัว
เพื่อจะได้ไม่มีไฟล์ร่วมให้เสีย agent ทุกตัวเขียนได้อย่างอิสระ ไม่มีใครเขียนทับใคร
และ conflict จะโผล่ตอนจบในรูปของ merge ซึ่งเป็นปัญหาที่มีเครื่องมือรองรับมาสี่สิบปี
นี่คือสิ่งที่ harness ที่จริงจังทำ และเป็นเหตุผลที่เครื่องมือ agent เริ่มรองรับ worktree
ต้นทุนก็มีจริง การ copy workspace ไม่ฟรี ไดเรกทอรี build ต่อ agent หนึ่งตัว
ทวีคูณทั้งพื้นที่ดิสก์และเวลา build และบาง job ก็ต้องเห็นการแก้ของกันและกันจึงจะถูกต้อง

**บทเรียนนี้ทำอะไรกับเรื่องนี้** ไม่ทำอะไรเลย

`fanout.py` ไม่มี lock ไม่มีการตรวจ version และไม่มีการแยกพื้นที่
`tools.py` เหมือนกันทุกไบต์กับในบทที่ 20 ซึ่งแปลว่า `edit_file`
จะทำสิ่งที่คุณเพิ่งดูมันทำอย่างเต็มใจ ที่ระบุไว้ตรง ๆ แบบนี้
เพราะทางเลือกอีกทางคือบทที่แสดง fan out ให้คุณดูแล้วปล่อยให้คุณไปค้นพบเรื่องนี้บนโค้ดของคุณเอง

ทางแก้ที่ซื่อสัตย์ และเป็นทางที่ควรใช้จริง คือ **ทำแบบขนานเฉพาะ job ที่อ่านอย่างเดียว**
review สี่ module แบบขนาน ค้นสี่ไดเรกทอรีแบบขนาน สรุปสี่เอกสารแบบขนาน
แล้วเก็บสี่คำตอบมา จากนั้นค่อยลงมือแก้ทีละอย่าง แบบเรียงลำดับ จากตัวแม่
ซึ่งเป็นสิ่งที่ `for call in calls` ของบทที่ 20 ทำอยู่แล้วพอดี

กฎข้อนั้นแทบไม่มีต้นทุนในทางปฏิบัติ เพราะเวลาส่วนใหญ่หมดไปกับการอ่าน
agent สี่ตัวในหัวข้อ 1 ใช้เวลาตัวละสี่สิบวินาที และเกือบทั้งหมดคือการค้นและการอ่าน
ส่วนการแก้ตอนท้ายใช้เวลาไม่กี่วินาที
การทำส่วนที่ช้าและปลอดภัยแบบขนาน และทำส่วนที่เร็วและอันตรายแบบเรียงลำดับ
ให้ speedup กับคุณโดยไม่มี race และเป็นกฎที่คุณจำไว้ในหัวได้
ซึ่งกลไก locking ทำแบบนั้นไม่ได้

ถ้าคุณอยากได้เวอร์ชันทั่วไป แบบฝึกหัดคือคำตอบตระกูลที่สองข้างบน
ให้ job แต่ละตัวมีสำเนา workspace ของตัวเอง รัน fan out แล้ว merge
จากนั้นค่อยไปหาคำตอบว่าคุณจะบอกตัวแม่อย่างไรว่าให้เชื่อสำเนาไหน

## 9. รูปแบบที่ควรรู้

สามรูปแบบ อันแรกคือสิ่งที่บทนี้สร้าง อีกสองอันคือกลไกเดียวกันที่จัดวางต่างกัน

**Fan out และ gather** แบ่งงานเป็น job ที่เป็นอิสระต่อกัน รันพร้อมกัน แล้ว merge ผลลัพธ์
`run_in_parallel` คือสิ่งนี้พอดี ใช้มันเมื่อ job ไม่ต้องการกันและกัน
ซึ่งคุณตรวจได้ด้วยการถามว่า job ที่สามจะเปลี่ยนไปหรือไม่ถ้า job ที่หนึ่งไม่เคยรัน
review สี่ module ค้นสี่ repository สรุปยี่สิบเอกสาร
มันเป็นรูปแบบเดียวที่นี่ที่ให้ speedup กับคุณ เพราะเป็นรูปแบบเดียวที่งานเป็นอิสระต่อกันจริง

**Orchestrator ที่วางแผนแล้วมอบหมาย** agent ตัวหนึ่งอ่านงานแล้วตัดสินใจว่า job มีอะไรบ้าง
แล้วแจกออกไป ความต่างจาก fan out คือรายการ job ถูกผลิตโดย model
แทนที่จะถูกเขียนโดยคุณ ซึ่งทำให้มันปรับตัวได้และทำให้มันเป็นจุดที่เรื่องผิดพลาดได้
planner ที่ปล่อยแปด job ทั้งที่สามก็พอ ทำให้คุณเสีย agent run ไปแปดครั้ง
และ planner ที่ปล่อย job ที่แอบขึ้นต่อกัน จะเอา race ในหัวข้อ 8 กลับมา
โดยไม่มีใครตัดสินใจให้เป็นแบบนั้น ใน codebase นี้ orchestrator คือตัวแม่จากบทที่ 20
ที่ปล่อย `run_subagent` หลาย call ในเทิร์นเดียว
และการเปลี่ยนแปลงคือการ dispatch call เหล่านั้นผ่าน `run_in_parallel`
แทน `for call in calls` แบบเรียงลำดับ

**Reviewer ที่ตรวจงานของ agent อีกตัว** agent ตัวหนึ่งทำงาน
แล้ว agent ตัวที่สองที่มี context ใหม่เอี่ยมได้รับผลลัพธ์และถูกถามว่ามีอะไรผิด
นี่ไม่ใช่ speedup และไม่ได้ใช้ `fanout.py` เลย มันเรียงลำดับโดยธรรมชาติ
เพราะ reviewer ต้องการสิ่งที่จะถูก review สิ่งที่ได้คือ reviewer
ยังไม่ได้ใช้เวลาสี่สิบเทิร์นโน้มน้าวตัวเองว่าแนวทางนั้นถูกต้อง
มันจึงมีโอกาสสูงกว่ามากที่จะสังเกตว่า test ไม่เคยถูกรันเลย
ต้นทุนคือ agent run เต็มรูปแบบเพิ่มอีกหนึ่งครั้งต่อหนึ่ง job
และความเสี่ยงคือ reviewer ที่ไม่มีความสามารถตรวจอะไรได้เชิงกลไก
จะผลิตการอนุมัติที่ฟังดูน่าเชื่อ ซึ่งเป็นเหตุผลว่าทำไม reviewer ควรได้ `run_shell`
และถูกขอหลักฐานแทนที่จะถูกขอความเห็น
บทที่ 22 คือสิ่งที่เปลี่ยนเรื่องนั้นจากความหวังให้เป็นการวัด

สังเกตสิ่งที่ไม่อยู่ใน output นั้น ไม่มี provider ไม่มี model และไม่มี network
`check.py` ไม่เคย import `agent.py` เลย job คือ `steps`
ซึ่งเป็นฟังก์ชันที่ yield string สามตัว

```python
def steps(label, count, pause=0.0):
    def produce():
        for index in range(count):
            if pause:
                time.sleep(pause)
            yield f"{label}-{index}"

    return produce
```

นั่นเป็นความตั้งใจ และเป็นข้อโต้แย้งเดียวกับที่บทที่ 14 พูดเรื่อง `fit_to_budget`
`run_in_parallel` ไม่รู้ว่า agent คืออะไร สัญญาของมันคือคุณส่ง callable
ที่คืน iterator เข้ามา ดังนั้นวิธีทดสอบที่ซื่อสัตย์ที่สุดคือใช้ callable
ที่คืน iterator ที่ง่ายที่สุดเท่าที่มี การเอา agent จริงมาใส่ใน check นี้
จะเพิ่ม provider เพิ่ม socket และเพิ่ม mock server เข้าไปใน test
ที่ว่าด้วยกลไกของ queue และเมื่อมันล้มเหลว คุณจะไม่รู้ว่าสี่อย่างนั้นอันไหนพัง

ถ้าบรรทัดแรกล้มเหลว แปลว่า event กำลังหายไป และจุดที่ต้องไปดูคือเงื่อนไขการจบใน main loop
ถ้าบรรทัดที่สองล้มเหลว แปลว่ามีอะไรบางอย่างบริโภค iterator อยู่นอก worker
หรือ event ถูกสลับลำดับระหว่างทางไป queue
ถ้าบรรทัดที่สามล้มเหลว แปลว่า `except` ไม่ได้จับ หรือ `finally` ไม่ได้ทำงาน
และถ้ามันค้างแทนที่จะล้มเหลว ก็เป็นเรื่องของ `finally` แน่นอน
ถ้าบรรทัดที่สี่ล้มเหลวและรายงานประมาณหกในสิบวินาที แปลว่า job รันทีละตัว
และสาเหตุที่น่าจะเป็นคือการเรียก `produce()` บน main thread แทนที่จะเรียกข้างใน `work`

## 11. สิ่งที่คุณยังทำไม่ได้

ตอนนี้คุณมี harness ที่ต่อกับ tool ที่มันไม่ได้เขียนเอง เริ่ม agent ตัวอื่นได้
และรันหลายตัวพร้อมกันได้ หยุดสักครู่แล้วถามคำถามหนึ่งข้อกับทั้งหมดนี้

มีอะไรในนั้นดีขึ้นบ้างไหม

ไม่ใช่เร็วขึ้น หัวข้อ 7 วัดความเร็วแล้วและความเร็วก็ถูกพิสูจน์แล้ว
ดีขึ้นในความหมายที่ว่า agent ผลิตงานที่ถูกต้องมากขึ้นที่ต้นทุนที่ยอมรับได้
มากกว่าเมื่อสี่บทที่แล้วหรือไม่

คุณตอบไม่ได้ ไม่มีอะไรที่คุณสร้างมาที่ตอบได้

ลองพิจารณาสิ่งที่คุณเพิ่งเปลี่ยนไปจริง ๆ บทที่ 19 ต่อกับ MCP server
ซึ่งเพิ่ม tool และเพิ่ม schema ของมันลงในทุก request ด้วย
และบทที่ 19 เองก็เตือนว่า tool ยิ่งเยอะ model ยิ่งเลือกได้แย่ลง
บทที่ 20 เพิ่ม subagent ซึ่งทำให้ context ของตัวแม่สะอาด
และก็แปลว่าตัวแม่กำลังใช้เหตุผลจากคำตอบที่ model เขียน
แทนที่จะใช้จากผลลัพธ์ของ tool โดยตรง บทนี้ให้กลไกสำหรับรันสี่ตัวพร้อมกัน ซึ่งเร็วขึ้น
และก็แปลว่ามี agent สี่ตัวก่อร่างมุมมองสี่ชุดที่แยกจากกันต่อ codebase
ที่พวกมันกำลังแก้ร่วมกัน

ทุกข้อนั้นเป็นการแลก ไม่มีข้อไหนถูกวัดเลย
คุณมีการปรับปรุงที่ฟังดูสมเหตุสมผลสี่บท กับเครื่องมือวัดศูนย์ชิ้น
และรูปแบบความล้มเหลวของสถานการณ์นั้นชัดเจน คุณจะไม่สังเกตเห็นการถดถอย
คุณจะสะสมมันไว้หลายอย่าง แต่ละอย่างก็ปกป้องได้ในตัวเอง
แล้วสามสัปดาห์ต่อมา agent ก็แย่ลงกว่าเดิม
และไม่มีทางหาได้ว่าการเปลี่ยนอันไหนทำให้เป็นแบบนั้น

เวอร์ชันแบบขนานทำให้เรื่องนี้ชัดกว่าตอนบทที่ 18
agent run เดียวที่ผลลัพธ์ออกมาไม่ดี อย่างน้อยก็ยังอ่านได้จากไฟล์ session ตั้งแต่ต้นจนจบ
agent สี่ตัวผลิต event stream สี่สายที่ปนกัน และอย่างที่หัวข้อ 8 ได้แสดงไว้
ยังผลิต workspace ที่สถานะสุดท้ายขึ้นอยู่กับ scheduling ด้วย
การดูการรันครั้งหนึ่งแล้วเกิดความรู้สึกก็เป็นหลักฐานที่อ่อนอยู่แล้ว
การดูการรันที่จะทำซ้ำให้เหมือนเดิมไม่ได้แม้จะไม่เปลี่ยนอะไรเลย ไม่ใช่หลักฐาน

สิ่งที่คุณต้องการคือชุดงานที่ตายตัวพร้อมผลลัพธ์ที่ตรวจได้ รันด้วยวิธีเดียวกันทุกครั้ง
เพื่อให้การเปลี่ยน prompt หรือ model หรือความกว้างของ fan out
กลายเป็นการทดลองที่มีตัวเลขตอนจบ แทนที่จะเป็นความรู้สึก
สำหรับผลลัพธ์ที่ตรวจเชิงกลไกไม่ได้ เพราะคำตอบเป็นข้อความบรรยาย คุณต้องมี judge
และเมื่อคุณมีสิ่งนั้นแล้ว การเลือกระหว่าง model ก็เลิกเป็นความเห็น
และกลายเป็นการทดลองแบบเดียวกันที่เปลี่ยนตัวแปรเดียว
