# บทที่ 01 การเรียก LLM ครั้งแรกของคุณ

จบบทที่ 00 คุณมี Python environment ที่ใช้งานได้ และมี endpoint (URL ที่เรายิง request ไปหา) ที่ตอบกลับมาเมื่อ setup script ไปเคาะประตูถามหา แต่คุณยังไม่ได้เขียนโค้ดของตัวเองสักบรรทัดที่คุยกับ model เลย บทนี้คือบทที่แก้เรื่องนั้น

พอจบบทนี้คุณจะมีไฟล์ชื่อ `llm.py` ที่มีฟังก์ชันเดียวอยู่ข้างใน คุณส่ง string เข้าไป มันคืนคำตอบของ model กลับมาเป็น string ฟังก์ชันนั้นยาวสิบเก้าบรรทัด และ agent ทุกตัวที่คุณจะสร้างในอีกยี่สิบสองบทที่เหลือล้วนวางอยู่บนมัน

## 1. ปัญหา เรายังไม่มีทางคุยกับ model เลยสักทาง

ตอนนี้โปรแกรมของคุณยังถามอะไร model ไม่ได้เลย ถ้าอยากได้ประโยคสักประโยค คุณต้องเปิดเว็บแชทในเบราว์เซอร์ พิมพ์ลงกล่อง แล้วอ่านคำตอบด้วยตาตัวเอง โค้ด Python ของคุณไม่ได้มีส่วนร่วมอะไรเลย

agent คือโปรแกรมที่ตัดสินใจว่าจะทำอะไรต่อโดยการถาม model แล้วลงมือทำ แล้วถามอีก ทั้งหมดนี้เป็นไปไม่ได้เลยตราบใดที่ทางเดียวที่จะเข้าถึง model คือให้คนพิมพ์ลงเว็บ สิ่งแรกสุดที่เราต้องมีคือฟังก์ชัน Python ที่โปรแกรมเรียกใช้ได้

เป้าหมายของบทนี้จึงเล็กและชัดเจน เราอยากให้โค้ดนี้ทำงานได้

```python
from llm import ask

print(ask("What is the capital of France?"))
```

ก่อนจะสร้างมันได้ เราต้องตอบคำถามหนึ่งข้อก่อน เวลาคุณพิมพ์ลงเว็บแชท จริง ๆ แล้วเกิดอะไรขึ้นระหว่างเบราว์เซอร์ของคุณกับบริษัทที่รัน model อยู่ พอรู้คำตอบแล้ว การเขียนฟังก์ชันจะกลายเป็นเรื่องง่าย เพราะฟังก์ชันก็แค่ทำสิ่งเดียวกับที่เบราว์เซอร์ของคุณทำอยู่

### จากมุมมองภายนอก language model คืออะไรกันแน่

language model คือโปรแกรมที่รับข้อความเข้าไปแล้วทำนายว่าข้อความถัดไปคืออะไร เท่านั้นเองคือกลไกทั้งหมด เมื่อคุณเขียนว่า "The capital of France is" มันจะผลิตคำว่า "Paris" ออกมา เพราะนั่นคือส่วนต่อที่มีความน่าจะเป็นสูงที่สุดจากทุกอย่างที่มันถูกเทรนมา

model สมัยใหม่ใหญ่เกินกว่าจะรันบนแล็ปท็อปธรรมดา บริษัทต่าง ๆ จึงรันมันบนเครื่องของตัวเองและเปิดให้คุณส่งข้อความไปหาผ่านอินเทอร์เน็ต สิ่งที่คุณคุยด้วยจริง ๆ คือ **API** ซึ่งย่อมาจาก application programming interface ในทางปฏิบัติ API คือ URL ที่คุณส่งข้อมูลไปหาได้ แล้วมันส่งข้อมูลกลับมา

URL นั้นเรียกว่า **endpoint** endpoint ที่เราสนใจในคอร์สนี้คือ `/chat/completions` และควรพูดให้ชัดว่ามันหมายถึงอะไร ในมุมมองของโปรแกรมคุณ language model ไม่ใช่สมองลึกลับอะไร มันคือ URL ที่รับ list ของ message เข้าไปแล้วคืน message กลับมาอีกหนึ่งอัน แค่นั้น ไม่มีอะไรมากกว่านั้น

ประโยคนั้นคือแนวคิดที่มีประโยชน์ที่สุดในบทนี้ ทุกอย่างที่เหลือในคอร์สสร้างขึ้นจากการทำสิ่งเดียวกันนี้ซ้ำ ๆ โดยมีโครงสร้างห่อหุ้มมากขึ้นเรื่อย ๆ

### ทำไมทุก provider ในคอร์สนี้จึงพูดด้วยรูปแบบเดียวกัน

OpenAI เผยแพร่รูปแบบ request นี้สำหรับ chat model ของตัวเอง แล้วมันกลายเป็นมาตรฐานโดยพฤตินัย ทุกวันนี้ provider ส่วนใหญ่พูดภาษานี้ ทั้ง Groq Together Fireworks OpenRouter vLLM LM Studio และ Ollama ต่างเปิด endpoint `/chat/completions` ที่รับ JSON หน้าตาเดียวกัน นี่คือเหตุผลที่บทที่ 00 ให้คุณกรอก base URL เอง แทนที่จะเลือกบริษัทให้คุณ

provider บางเจ้า โดยเฉพาะ Anthropic และ Google มีรูปแบบ native ของตัวเองที่หน้าตาต่างออกไป เราจะจัดการเรื่องนี้อย่างเป็นระบบในบทที่ 06 ตอนที่เราสร้าง provider abstraction สำหรับบทที่ 01 ถึง 05 เราจะใช้รูปแบบ chat completions เพราะการเรียนรู้ wire format เดียวให้แตกฉานดีกว่าการรู้สามแบบแบบงู ๆ ปลา ๆ มาก

## 2. HTTP request ที่ส่งไปหา language model หน้าตาเป็นอย่างไร

มาดูไบต์จริง ๆ กัน นี่คือส่วนที่ tutorial ส่วนใหญ่ข้าม และการข้ามมันคือเหตุผลที่ทำให้คนคิดว่า model เป็นเวทมนตร์

### request

การคุยกับ endpoint คือการส่ง **HTTP POST request** HTTP คือ protocol ที่เบราว์เซอร์ของคุณใช้ทำทุกอย่าง POST request คือแบบที่ใช้เมื่อคุณส่งข้อมูลไปให้ server ไม่ใช่แค่ขอหน้าเว็บมาอ่าน ข้อมูลที่คุณส่งเรียกว่า **body** และสำหรับ endpoint นี้ body คือ **JSON** ซึ่งเป็นรูปแบบข้อความสำหรับเก็บข้อมูลแบบ key และ value ที่ซ้อนกันได้

นี่คือ request เต็ม ๆ พร้อม header ทั้งหมด ที่ส่งไปหา OpenAI

```http
POST /v1/chat/completions HTTP/1.1
Host: api.openai.com
Content-Type: application/json
Authorization: Bearer sk-proj-h2Kd8vQ1mZ4rT7xN0pLbW3sYcF6gJa9E
Content-Length: 101

{
  "model": "gpt-4o-mini",
  "messages": [
    {"role": "user", "content": "Say hello in one short sentence."}
  ]
}
```

ทีนี้มาดูทีละชิ้น

`POST /v1/chat/completions HTTP/1.1` คือ request line มันบอกว่าเรากำลังส่งข้อมูลไปที่ path `/v1/chat/completions` โดยใช้ HTTP เวอร์ชัน 1.1 ส่วน `/v1` คือคำนำหน้าบอกเวอร์ชันที่ provider เลือกใช้ เพื่อให้เขาเปลี่ยน API ในอนาคตได้โดยไม่ทำให้โปรแกรมเก่าพัง

`Host` ระบุชื่อ server เมื่อรวมกับ path จะได้ URL เต็มคือ `https://api.openai.com/v1/chat/completions`

`Content-Type: application/json` บอก server ว่าต้องอ่าน body อย่างไร ถ้าไม่มีบรรทัดนี้ server จะไม่รู้ว่าไบต์พวกนั้นคือ JSON เป็นฟอร์มเว็บ หรือเป็นไฟล์อัปโหลด และมันมักจะปฏิเสธ request ไปเลย **header** คือบรรทัดรูปแบบ `Name: value` พวกนี้ ซึ่งพกข้อมูลเกี่ยวกับตัว request มากกว่าจะเป็นเนื้อหาจริงของ request

`Authorization: Bearer sk-proj-...` คือวิธีที่ server รู้ว่าคุณเป็นใคร คำว่า `Bearer` เป็นชื่อ scheme จากมาตรฐาน HTTP แปลว่า "ใครถือ token นี้ คนนั้นได้สิทธิ์เข้าถึง" สตริงยาว ๆ ที่ตามมาคือ **API key** ของคุณ ซึ่งเป็นรหัสลับที่ provider ให้มา ใครก็ตามที่ได้มันไปสามารถใช้เงินของคุณได้ นี่คือเหตุผลที่มันต้องอยู่ใน environment variable และห้ามอยู่ใน source code เด็ดขาด หัวข้อ 4 จะลงรายละเอียดเรื่องนี้อย่างจริงจัง

`Content-Length` คือจำนวนไบต์ของ body ไลบรารี HTTP ของคุณจะเติมค่านี้ให้เอง และคุณจะไม่มีวันต้องตั้งเองด้วยมือ

จากนั้นเว้นบรรทัดว่างหนึ่งบรรทัด แล้วตามด้วย body body ตรงนี้มีสอง key

`model` ระบุว่าจะให้ model ไหนตอบ endpoint เดียวให้บริการ model หลายตัว server จึงเดาเองไม่ได้ provider หนึ่งอาจให้บริการ `gpt-4o-mini` `gpt-4o` และอีกเป็นสิบตัวอยู่หลัง URL เดียวกันเป๊ะ ๆ ซึ่งแต่ละตัวต่างกันมหาศาลทั้งราคาและคุณภาพ key นี้คือวิธีที่คุณเลือก

`messages` เป็น list และเป็นตัวสำคัญ มันคือบทสนทนาทั้งหมดที่ผ่านมา เรียงตามลำดับ เก่าสุดอยู่ก่อน model อ่านทั้งหมดแล้วเขียน message ถัดไป

แต่ละรายการใน `messages` เป็น object ที่มี key บังคับสองตัว

`role` บอกว่าใครเป็นคนเขียน message นั้น มีสาม role ในบทนี้ และ role ที่สี่คือ `tool` จะมาถึงในบทที่ 02 `user` คือคุณ ไม่ว่าจะเป็นมนุษย์หรือโปรแกรมที่ทำหน้าที่แทนมนุษย์ `assistant` คือ model `system` คือบล็อกคำสั่งพิเศษที่กำหนดพฤติกรรมและกฎ และมันจะอยู่ตัวแรกเสมอเมื่อมีการใช้งาน เราจะไม่ส่ง system message ในบทนี้ เพราะเราอยากได้ request ที่เล็กที่สุดเท่าที่จะเป็นไปได้ บทที่ 02 จะอธิบาย role นี้ และปล่อยให้คุณเพิ่มมันเองในแบบฝึกหัดข้อแรก

role สำคัญกว่าที่หน้าตามันดูมาก model ถูกเทรนด้วยบทสนทนาในรูปแบบนี้ มันจึงเรียนรู้ว่าข้อความที่ติดป้าย `user` คือคำขอที่ต้องตอบ และข้อความที่ติดป้าย `assistant` คือคำพูดของตัวมันเองก่อนหน้านี้ ถ้าคุณยัดทุกอย่างไว้ใต้ role เดียว คุณภาพจะตกลงอย่างเห็นได้ชัด

`content` คือตัวข้อความของ message นั้น ในบทหลัง ๆ content สามารถเป็น list ของชิ้นส่วนได้ด้วย เพื่อให้คุณส่งรูปภาพได้ แต่ string ธรรมดาคือกรณีที่พบบ่อยที่สุด และเป็นสิ่งที่เราใช้ตรงนี้

นั่นคือ request ทั้งหมด สอง key ซึ่ง key หนึ่งเป็น list ของ object ที่มีสอง key ไม่มีอะไรซ่อนอยู่ในนั้นอีกแล้ว

### response

นี่คือ JSON เต็ม ๆ ที่ server ส่งกลับมา

```json
{
  "id": "chatcmpl-BgY4kR2mQ1sVn8pTt3Lw9dXqZ0aBc",
  "object": "chat.completion",
  "created": 1756684800,
  "model": "gpt-4o-mini-2024-07-18",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "Hello, it is nice to meet you.",
        "refusal": null
      },
      "logprobs": null,
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 14,
    "completion_tokens": 9,
    "total_tokens": 23
  },
  "system_fingerprint": "fp_9c2ea6d1f4"
}
```

มาดูทีละ field

`id` คือตัวระบุเฉพาะของการเรียกครั้งนี้ คุณไม่จำเป็นต้องใช้มันเพื่อให้ได้คำตอบ แต่มันคือสิ่งที่คุณอ้างอิงตอนแจ้งทีมซัพพอร์ตของ provider เวลามีปัญหา และเป็นสิ่งที่คุณเก็บ log ไว้ถ้าอยากตามรอยคำตอบที่ผิดพลาดย้อนหลัง

`object` บอกรูปร่างของ JSON ก้อนนี้ ค่าจะเป็น `chat.completion` สำหรับคำตอบปกติ และเป็น `chat.completion.chunk` สำหรับชิ้นส่วนของ streaming ที่เราจะเจอในบทที่ 05 มันมีอยู่เพื่อให้โปรแกรมรู้ได้ว่าได้รับรูปร่างแบบไหนมาโดยไม่ต้องเดา

`created` คือเวลาที่คำตอบถูกสร้างขึ้น ในรูปแบบ Unix timestamp หมายถึงจำนวนวินาทีนับจากวันที่หนึ่งมกราคม ปี 1970 ค่า `1756684800` คือช่วงเวลาหนึ่งในเดือนกันยายน ปี 2025

`model` คือ model ตัวจริงที่ตอบ สังเกตว่ามันเจาะจงกว่าที่เราขอไป เราส่ง `gpt-4o-mini` ไปแต่ได้ `gpt-4o-mini-2024-07-18` กลับมา ชื่อ alias ของ provider ชี้ไปยัง snapshot ที่มีวันที่กำกับ และ field นี้บอกคุณว่าจริง ๆ แล้วคุณได้ snapshot ไหน เวลาคำตอบเปลี่ยนคุณภาพข้ามคืนทั้งที่คุณไม่ได้แก้โค้ดเลย field นี้คือที่ที่คุณต้องไปดู

`choices` เป็น list และความจริงที่ว่ามันเป็น list ทำให้ทุกคนแปลกใจในครั้งแรก ทำไมคำถามเดียวถึงมีหลายคำตอบ เพราะ API เปิดให้คุณขอ completion อิสระหลายชุดจาก prompt เดียวกันได้ โดยส่ง key เพิ่มชื่อ `n` ถ้าคุณส่ง `"n": 3` คุณจะได้สามรายการกลับมา และ workflow บางแบบใช้วิธีนี้สร้างตัวเลือกแล้วคัดอันที่ดีที่สุด

เราไม่เคยส่ง `n` ค่าเริ่มต้นคือหนึ่งจึงถูกใช้ list จึงมีรายการเดียวเสมอ โค้ดของเราจึงอ่าน `choices[0]` มันคุ้มค่าที่จะรู้ว่าทำไม index นั้นถึงอยู่ตรงนั้น แทนที่จะมองมันเป็นสิ่งรกตาที่ต้องพิมพ์

`index` คือตำแหน่งของ choice นั้นใน list เมื่อมี choice เดียวมันจะเป็น `0` เสมอ

`message` คือคำตอบจริง ๆ และให้ดูรูปร่างของมันดี ๆ มันมี `role` และ `content` ซึ่งเป็นสอง key เดียวกันเป๊ะกับ message ที่เราส่งไป ความสมมาตรนี้ไม่ใช่เรื่องบังเอิญ และเป็นเหตุผลที่รูปแบบการสนทนาทั้งหมดใช้งานได้ คำตอบที่คุณได้กลับมาสามารถต่อท้ายเข้าไปใน list `messages` ที่คุณจะส่งครั้งถัดไปได้เลยโดยไม่ต้องแก้อะไร บทที่ 02 สร้างขึ้นบนข้อเท็จจริงนี้ล้วน ๆ

ตรงนี้ `role` คือ `assistant` เพราะ model เป็นคนเขียน และ `content` คือข้อความที่เราต้องการ

`refusal` เป็น `null` เมื่อเป็นคำตอบปกติ และจะเก็บสตริงคำอธิบายไว้เมื่อ model ปฏิเสธที่จะตอบ `null` คือคำใน JSON ที่แปลว่าไม่มีอะไร และ Python จะแปลงมันเป็น `None`

`logprobs` เป็น `null` เว้นแต่คุณจะขอข้อมูลความน่าจะเป็นของแต่ละ token ที่ถูกเลือก ซึ่งเราไม่เคยทำในคอร์สนี้

`finish_reason` บอกว่าทำไม model ถึงหยุดเขียน และมันสำคัญกว่าที่หน้าตาดูมาก ค่าที่พบบ่อยมีดังนี้

- `stop` แปลว่า model เขียนความคิดของมันจบตามธรรมชาติ นี่คือกรณีที่ดี
- `length` แปลว่ามันชนเพดานจำนวน token สูงสุดที่อนุญาต แล้วถูกตัดกลางประโยค ถ้าคุณเจอคำตอบที่ขาดกลางคัน field นี้คือหลักฐานยืนยันว่าโดนตัด ไม่ใช่ model ตอบสั้นเอง
- `tool_calls` แปลว่า model ต้องการเรียกฟังก์ชันแทนที่จะเขียนข้อความ ค่านี้คือหัวข้อทั้งหมดของบทที่ 03 และเป็นจังหวะที่ chatbot กลายเป็น agent
- `content_filter` แปลว่าระบบความปลอดภัยของ provider หยุดคำตอบนั้นไว้

ฟังก์ชันของเราในบทนี้ไม่สนใจ `finish_reason` ซึ่งไม่เป็นไรสำหรับการทักทายครั้งเดียว แต่จะเริ่มเป็นปัญหาทันทีที่เราสร้าง agent loop จำไว้ว่ามันมีอยู่

`usage` นับปริมาณงานที่ทำไป **token** คือหน่วยที่ model อ่านและเขียน คร่าว ๆ ประมาณสามในสี่ของคำภาษาอังกฤษหนึ่งคำ แปลว่า "hello" คือหนึ่ง token ส่วน "unbelievable" อาจเป็นสาม `prompt_tokens` นับสิ่งที่คุณส่งไป `completion_tokens` นับสิ่งที่ได้กลับมา และ `total_tokens` คือผลรวม คุณถูกคิดเงินตาม token และ model มีเพดานตายตัวว่า token กี่ตัวใส่ได้ใน request เดียว field นี้จึงเป็นทั้งบิลค่าใช้จ่ายและงบประมาณของคุณ บทที่ 14 และ 15 ว่าด้วยการจัดการเรื่องนี้

`system_fingerprint` ระบุการตั้งค่า backend ที่ให้บริการคุณ มันจะเปลี่ยนเมื่อ provider อัปเดตระบบให้บริการของเขา คนส่วนใหญ่ไม่เคยดูมันเลย

ทีนี้ลองเทียบเอกสารสองชุดดู คุณส่ง list ของ message ไป คุณได้ message กลับมาหนึ่งอันในรูปแบบเดียวกัน บวกกับข้อมูลบัญชีจิปาถะ นั่นคือ protocol ทั้งหมด

## 3. ทำไมเราใช้ httpx ตรง ๆ แทนที่จะใช้ SDK อย่างเป็นทางการ

provider ทุกเจ้ามี **SDK** ซึ่งย่อมาจาก software development kit เป็นไลบรารีที่ห่อ API ของเขาไว้ในฟังก์ชันสำเร็จรูป ของ OpenAI ชื่อ `openai` และถ้าใช้มัน โค้ดของบทนี้จะเหลือประมาณสี่บรรทัด

เราจะไม่ใช้มัน และเหตุผลคือแก่นของบทนี้

หน้าที่ของ SDK คือซ่อน HTTP request นั่นเป็นเรื่องดีจริง ๆ เวลาคุณกำลังส่งมอบผลิตภัณฑ์ และเป็นเรื่องแย่เวลาคุณกำลังพยายามเข้าใจว่า language model คืออะไร ถ้าคุณเรียนรู้แค่ `client.chat.completions.create(...)` โดยไม่เคยเห็น JSON ที่อยู่ข้างใต้ model จะยังเป็นกล่องเวทมนตร์ต่อไป และทุกปัญหาที่คุณเจอทีหลังจะกลายเป็นเรื่องอธิบายไม่ได้ ทำไม model ถึงลืม system prompt จริง ๆ แล้วคืออะไร tool call มาถึงได้อย่างไร ทุกคำถามเหล่านี้มีคำตอบที่ชัดเจนทันทีเมื่อคุณเคยเห็น wire format และไม่มีคำตอบเลยถ้าคุณไม่เคยเห็น

คอร์สนี้มีกฎอยู่ข้อหนึ่ง ห้ามมีเวทมนตร์ คุณต้องมองเห็นทุกชั้นได้ ลงไปจนถึงชั้นล่างสุด และต้องสร้างมันขึ้นใหม่เองได้ บทหลัง ๆ จะเพิ่ม streaming tool call การ retry และการรองรับหลาย provider และแต่ละอย่างคือการเปลี่ยนแปลงบน request เดียวกันนี้ที่คุณจะมองเห็นและอธิบายเหตุผลได้

เราจึงใช้ `httpx` ซึ่งเป็นไลบรารี HTTP อเนกประสงค์สำหรับ Python มันไม่รู้จัก language model เลยสักนิด มันส่ง request ที่คุณยื่นให้ แล้วคืน response ให้คุณ ความเป็นกลางแบบนี้คือสิ่งที่เราต้องการพอดี เพราะมันแปลว่าไม่มีอะไรระหว่างคุณกับ API ที่ทำสิ่งที่คุณไม่ได้เขียนเอง

ขอพูดให้ชัดมาก ๆ เพราะเรื่องนี้เป็นคำถามที่คนกังวลกันจริง ๆ การใช้ SDK อย่างเป็นทางการในโปรเจกต์ของคุณเองหลังจากนี้เป็นทางเลือกที่สมเหตุสมผลอย่างยิ่ง และมักจะเป็นทางเลือกที่ถูกต้องด้วย SDK จัดการเรื่อง retry connection pooling timeout และกรณีขอบแปลก ๆ ในรูปแบบ response ที่ไม่อย่างนั้นคุณต้องจัดการเอง ข้อโต้แย้งตรงนี้เป็นเรื่องของลำดับการเรียนรู้เท่านั้น เข้าใจ request ดิบก่อน แล้วค่อยปล่อยให้ไลบรารีทำแทนถ้าคุณต้องการ วิธีนี้เวลาไลบรารีทำตัวแปลก คุณยังอ่าน traffic ได้และเห็นว่าเพราะอะไร

เราเลือก `httpx` แทนไลบรารี `requests` ที่เก่ากว่าด้วยเหตุผลมองไปข้างหน้าหนึ่งข้อ `httpx` รองรับทั้งการเรียกแบบ blocking ปกติและการเรียกแบบ `async` ด้วยโค้ดที่แทบจะเหมือนกัน และจัดการ streaming response ได้อย่างสะอาด ซึ่งเป็นสิ่งที่เราต้องใช้ในบทที่ 05 การเริ่มด้วยมันแปลว่าเราไม่ต้องเปลี่ยนไลบรารีกลางคอร์ส

## 5. เขียน llm.py ทีละบรรทัด

นี่คือไฟล์ฉบับเต็ม อ่านมันรวดเดียวก่อน แล้วเราจะไล่ดูทุกบรรทัดว่ามันมาจากไหน

```python
"""One function that sends text to a model and returns the text it sends back.

Everything else in this course is built on top of this. There is no library
between you and the API here on purpose. You should be able to see that a
language model is an HTTP endpoint that takes a list of messages and returns
one more message.
"""
import os

import httpx


def ask(prompt):
    """Send one message and return the assistant reply as a string."""
    base_url = os.environ["AGENTPATH_BASE_URL"].rstrip("/")
    api_key = os.environ.get("AGENTPATH_API_KEY", "")
    model = os.environ["AGENTPATH_MODEL"]

    headers = {"Content-Type": "application/json"}
    if api_key:
        headers["Authorization"] = f"Bearer {api_key}"

    response = httpx.post(
        f"{base_url}/chat/completions",
        json={"model": model, "messages": [{"role": "user", "content": prompt}]},
        headers=headers,
        timeout=120,
    )
    response.raise_for_status()
    body = response.json()
    return body["choices"][0]["message"]["content"]


if __name__ == "__main__":
    print(ask("Say hello in one short sentence."))
```

สามสิบกว่าบรรทัด และหนึ่งในสามของมันคือคำอธิบาย ทีนี้มาไล่ดูกัน

### ส่วน import

```python
import os

import httpx
```

`os` อยู่ใน standard library ของ Python และให้ `os.environ` กับเรา `httpx` คือไลบรารีของบุคคลที่สามที่คุณติดตั้งไปในบทที่ 00 บรรทัดว่างระหว่างทั้งสองเป็นไปตามธรรมเนียมปกติของ Python ที่แยก import จาก standard library ออกจาก import ของบุคคลที่สาม ซึ่งทำให้เห็นได้ในพริบตาว่าโปรเจกต์ของคุณพึ่งพาอะไรจากภายนอกบ้าง

### signature ของฟังก์ชัน

```python
def ask(prompt):
    """Send one message and return the assistant reply as a string."""
```

หนึ่ง argument เป็น string และคืนค่าเป็น string ไม่มี class ไม่มี client object ให้สร้าง ไม่มี configuration ให้ส่งต่อไปมา นั่นเป็นความตั้งใจ ฟังก์ชันที่เรียบง่ายขนาดนี้อ่านจบทั้งอันได้ในสิบวินาที และทุกบทถัดไปจะขยายมันในแบบที่คุณเอามา diff กับเวอร์ชันนี้ได้

### การอ่าน configuration

```python
    base_url = os.environ["AGENTPATH_BASE_URL"].rstrip("/")
    api_key = os.environ.get("AGENTPATH_API_KEY", "")
    model = os.environ["AGENTPATH_MODEL"]
```

สังเกตว่าสองบรรทัดใช้วงเล็บเหลี่ยม ส่วนอีกบรรทัดใช้ `.get` ความต่างนั้นตั้งใจและมีความหมาย

`os.environ["AGENTPATH_BASE_URL"]` จะโยน `KeyError` ถ้าตัวแปรหายไป นั่นคือสิ่งที่เราต้องการ เพราะไม่มีค่าเริ่มต้นที่สมเหตุสมผลสำหรับ URL และโปรแกรมที่ไม่มี endpoint ก็ทำอะไรที่มีประโยชน์ไม่ได้อยู่ดี การล้มเหลวทันทีพร้อมชื่อตัวแปรในข้อความ error ใจดีกว่าการล้มเหลวทีหลังด้วยอะไรที่คลุมเครือมาก เรื่องเดียวกันนี้ใช้กับ `AGENTPATH_MODEL`

`os.environ.get("AGENTPATH_API_KEY", "")` คืนสตริงว่างเมื่อตัวแปรหายไป แทนที่จะโยน error นั่นก็คือสิ่งที่เราต้องการเช่นกัน เพราะการไม่มี key เป็นสถานการณ์ปกติที่เรารองรับอย่างเต็มที่ model ที่รันในเครื่องไม่ต้องใช้มัน

### rstrip ทำอะไร และทำไม base url ถึงต้องใช้มัน

```python
    base_url = os.environ["AGENTPATH_BASE_URL"].rstrip("/")
```

`rstrip("/")` ลบอักขระ slash ที่ต่อท้ายอยู่ทางขวาสุดของสตริงออก มันเปลี่ยน `"https://api.openai.com/v1/"` เป็น `"https://api.openai.com/v1"` และปล่อย `"https://api.openai.com/v1"` ไว้เหมือนเดิม

ทำไมต้องเสียเวลาทำ เพราะถัดลงไปเราประกอบ URL แบบนี้

```python
f"{base_url}/chat/completions"
```

ถ้ามีใครตั้งค่าตัวแปรโดยมี slash ต่อท้าย ซึ่งคนทำกันตลอดเพราะเอกสารของ provider แต่ละเจ้าไม่สอดคล้องกันเรื่องนี้ ผลลัพธ์จะเป็นแบบนี้

```text
https://api.openai.com/v1//chat/completions
```

slash คู่นั้นเป็นคนละ path ในสายตาของ server บาง server ปรับให้เป็นปกติแล้วให้อภัยคุณ แต่หลายเจ้าคืน 404 not found และบางเจ้าคืน 401 ที่ชวนสับสน ผู้เรียนก็จะนั่งจ้อง URL ที่ดูถูกต้องใน shell ของตัวเองแล้วมองไม่เห็นปัญหา เพราะ slash ที่เกินมามองไม่เห็นเวลากวาดตาอ่านผ่าน ๆ

การเรียกเมธอดครั้งเดียวกำจัดคำถามซัพพอร์ตไปได้ทั้งหมวด นี่คือรูปแบบทั่วไปของการจัดการ input ที่ดี รับทั้งสองรูปแบบที่คนปกติจะพิมพ์ แล้วปรับให้เป็นมาตรฐานครั้งเดียวที่ขอบ ทันทีหลังจากอ่านค่าเข้ามา

### การประกอบ header และบรรทัดที่ทำให้ model ในเครื่องใช้งานได้

```python
    headers = {"Content-Type": "application/json"}
    if api_key:
        headers["Authorization"] = f"Bearer {api_key}"
```

เราเริ่มด้วย header ตัวเดียวที่ต้องมีเสมอ `Content-Type` ที่ตั้งเป็น `application/json` บอก server ให้แปลง body เป็น JSON ถ้าไม่ใส่ server ส่วนใหญ่จะปฏิเสธ request ไปเลย

จากนั้นคือส่วนที่มีเงื่อนไข ใน Python สตริงว่างมีค่าเป็นเท็จ แปลว่า `if api_key` จะเป็นเท็จก็ต่อเมื่อตัวแปรหายไปหรือถูกตั้งเป็นค่าว่าง ในกรณีนั้นเราจะไม่เพิ่ม header `Authorization` เลย

เงื่อนไข `if` เล็ก ๆ นี้คือสิ่งที่ทำให้ไฟล์เดียวใช้ได้ทั้งกับ cloud API ที่เสียเงินและ model ที่รันบนแล็ปท็อปของคุณเอง จึงคุ้มค่าที่จะอธิบายให้แม่นยำว่าเพราะอะไร

Ollama และ server ในเครื่องลักษณะเดียวกันยอมรับ request ที่ไม่มีการยืนยันตัวตน เพราะ server รันอยู่บนเครื่องของคุณเองและไม่มีใครให้ต้องยืนยันตัวตน แต่ส่วนสำคัญคือสิ่งที่จะเกิดขึ้นถ้าคุณส่ง header `Authorization` ไปทั้งอย่างนั้น server ในเครื่องและ server ที่โฮสต์เองหลายตัวไม่ได้แค่เพิกเฉยต่อ header ที่ไม่คาดคิด บางตัวตรวจสอบรูปแบบของ bearer token และปฏิเสธตัวที่ผิดรูปแบบ และการส่งข้อความ `Bearer ` ตามด้วย token ว่างเปล่าถือว่าผิดรูปแบบ คุณจะได้ 401 unauthorized ที่ชวนงงจาก server ที่ไม่มีระบบบัญชีผู้ใช้ด้วยซ้ำ

การเพิ่ม header เฉพาะตอนที่มีของจะใส่จริง ๆ ช่วยเลี่ยงคำถามทั้งหมดนี้ บทเรียนที่ควรจำไปคือ header ที่ไม่มีอยู่กับ header ที่ว่างเปล่าไม่ใช่สิ่งเดียวกัน และเมื่อค่าใดเป็นตัวเลือก คุณควรละ header นั้นไปเลยแทนที่จะส่งไปแบบว่าง ๆ

### การส่ง request

```python
    response = httpx.post(
        f"{base_url}/chat/completions",
        json={"model": model, "messages": [{"role": "user", "content": prompt}]},
        headers=headers,
        timeout=120,
    )
```

การเรียกครั้งเดียวนี้สร้าง HTTP request แบบเดียวกันเป๊ะกับที่พิมพ์ไว้ในหัวข้อ 2 ถ้ายังสงสัยลองเทียบดูทั้งสองอัน

argument แรกคือ URL เต็ม `httpx.post` แปลว่า HTTP method คือ POST

argument `json=` คือตัวที่น่าสนใจ คุณยื่น dictionary ของ Python ธรรมดาให้ `httpx` แล้วมันทำงานสองอย่างให้คุณ มันแปลง dictionary เป็นสตริง JSON และมันตั้ง `Content-Type` เป็น `application/json` ให้อัตโนมัติ เราตั้ง header นั้นเองอยู่ดี ทั้งเพราะการเขียนให้ชัดเจนช่วยสอนผู้อ่านว่าอะไรจำเป็น และเพราะไม่อย่างนั้น dictionary `headers` ของเราจะเป็น header ตัวเดียวที่ request พกไปในกรณีของ model ในเครื่อง

ภายใน `json=` คุณจะเห็น request body จากหัวข้อ 2 ถูกประกอบขึ้นใหม่ในภาษา Python `model` มาจาก environment `messages` เป็น list ที่มี dictionary อยู่หนึ่งอันพอดี โดย `role` ตั้งเป็น `user` เพราะมนุษย์เป็นคนพูด และ `content` ตั้งเป็นสตริงอะไรก็ตามที่ผู้เรียกส่งเข้ามา

สังเกตว่า list นี้มีสมาชิกหนึ่งตัวเสมอ ข้อเท็จจริงเดียวนั้นคือข้อจำกัดที่บทเรียนทั้งบทนี้จบลง และเป็นสิ่งที่บทที่ 02 จะกำจัดออกไป

`headers=headers` ส่ง dictionary ที่เราเพิ่งสร้างเข้าไป

### timeout และทำไมมันถึงไม่ใช่ของที่จะมีก็ได้ไม่มีก็ได้

```python
        timeout=120,
```

timeout คือจำนวนวินาทีที่ `httpx` จะรอก่อนยอมแพ้แล้วโยน error

`httpx` มี timeout ค่าเริ่มต้นห้าวินาที นั่นเป็นค่าเริ่มต้นที่เหมาะสมสำหรับ web API ทั่วไป แต่แย่สำหรับ language model model ที่กำลังสร้างคำตอบยาว ๆ ใช้เวลายี่สิบ สี่สิบ บางทีเก้าสิบวินาทีเป็นเรื่องปกติ เพราะมันผลิตคำตอบทีละ token แล้วส่งกลับมาก็ต่อเมื่อเสร็จทั้งก้อน ถ้าใช้ค่าเริ่มต้น คุณจะเจอความล้มเหลวแบบสุ่มบน request ที่กำลังทำงานหนักที่สุดพอดี

เราจึงเพิ่มมันเป็น 120 วินาที และเหตุผลที่เราตั้งตัวเลขไว้เลย แทนที่จะปิด timeout ไปเลย คือความล้มเหลวอีกด้านหนึ่ง ถ้าเครือข่ายหลุดหรือ server ค้าง request ที่ไม่มี timeout จะรอตลอดกาล และโปรแกรมของคุณก็หยุดนิ่งไปเฉย ๆ ไม่มี error ไม่มี output นั่นดีบั๊กยากกว่า error timeout ที่ชัดเจนหลังผ่านไปสองนาทีมาก เพดานที่ใจกว้างแต่ยังมีอยู่จริงคือคำตอบที่ถูกต้องสำหรับปัญหาทั้งสองแบบ

### การตรวจสอบสถานะ


หัวข้อ 7 ว่าด้วยบรรทัดนี้ทั้งหัวข้อ เพราะมันคู่ควรกับพื้นที่ขนาดนั้น

### การดึงคำตอบออกจาก response

```python
    body = response.json()
    return body["choices"][0]["message"]["content"]
```

`response.json()` แปลงข้อความ JSON ที่ server ส่งมาให้เป็น object ของ Python object ใน JSON กลายเป็น dictionary array ใน JSON กลายเป็น list และ `null` กลายเป็น `None` หลังบรรทัดนี้ `body` คือโครงสร้างเดียวกันเป๊ะกับที่พิมพ์ไว้ในหัวข้อ 2 เพียงแต่ตอนนี้ประกอบขึ้นจากค่าของ Python

บรรทัดสุดท้ายไล่เดินลงไปในโครงสร้างนั้น และทุกก้าวตอนนี้มีเหตุผลที่คุณรู้อยู่แล้ว

- `body["choices"]` คือ list ของ completion มันเป็น list เพราะ API รองรับการขอหลายอันด้วย `n`
- `[0]` หยิบอันแรก เราไม่เคยส่ง `n` จึงมีอันเดียวพอดี และ index ศูนย์คืออันนั้น
- `["message"]` คือ object คำตอบที่มี `role` และ `content` รูปร่างเดียวกับ message ที่เราส่งไป
- `["content"]` คือตัวข้อความ

เราทิ้งทุกอย่างที่เหลือ ทั้งจำนวน token finish reason และ model snapshot ถูกโยนทิ้งหมด เพราะฟังก์ชันของบทนี้สัญญาว่าจะให้ string และไม่ให้อะไรมากกว่านั้น ทุก field ที่ทิ้งไปจะกลับมาในบทหลัง ๆ ตอนที่เราต้องใช้มันจริง ๆ และ `finish_reason` โดยเฉพาะจะกลับมาในบทที่ 03

```python
if __name__ == "__main__":
```

มันเรียก `ask` ด้วย prompt ตายตัว แล้วยืนยันสองอย่างเกี่ยวกับผลลัพธ์ `isinstance(reply, str)` ตรวจว่าคุณได้ string กลับมา ไม่ใช่ dictionary เพราะมีคนเผลอ return `body["choices"][0]["message"]` `reply.strip()` ตัดช่องว่างรอบ ๆ ออก และผลลัพธ์ที่ว่างเปล่าหลังตัดช่องว่างแปลว่า model ไม่ได้คืนอะไรที่มีประโยชน์ ซึ่งการตรวจแบบง่าย ๆ ว่าค่ามีความจริงหรือไม่จะมองข้ามไป เพราะสตริงที่มีแต่ช่องว่างถือว่าเป็นจริงใน Python

เมื่อล้มเหลว มันพิมพ์ค่าออกมาด้วย `!r` ซึ่งคือรูปแบบ `repr` แบบนั้นจะแสดงเครื่องหมายคำพูดและอักขระ escape แปลว่าสตริงว่างจะพิมพ์ออกมาเป็น `''` แทนที่จะเป็นช่องว่างเปล่า ๆ ที่ชวนสับสนใน terminal ของคุณ จากนั้น `sys.exit(1)` จบโปรแกรมด้วย exit code ที่ไม่ใช่ศูนย์ ซึ่งเป็นวิธีที่ระบบ continuous integration รู้ว่ามีอะไรพัง

### เมื่อมันไม่ทำงาน

มีความล้มเหลวไม่กี่แบบที่พบบ่อยพอจะเอ่ยถึง

ถ้าคุณเห็น `KeyError: 'AGENTPATH_BASE_URL'` แปลว่า environment variable ไม่ได้ถูกตั้งใน shell ที่คุณกำลังรันอยู่จริง ๆ environment variable ที่ตั้งด้วย `export` มีผลเฉพาะกับหน้าต่าง terminal นั้นเท่านั้น แท็บใหม่จึงเริ่มต้นจากศูนย์

หัวข้อ 7 อธิบายว่าทำไมคุณถึงได้เห็นข้อความชัด ๆ พวกนี้ตั้งแต่แรก

## 7. raise_for_status ทำอะไร และทำไมฟังก์ชันนี้จะอันตรายถ้าไม่มีมัน

```python
    response.raise_for_status()
```

HTTP response ทุกอันพก **status code** มาด้วย ซึ่งเป็นตัวเลขสามหลักที่บอกว่าผลเป็นอย่างไร รหัสในช่วง 200 แปลว่าสำเร็จ รหัสในช่วง 400 แปลว่า request ของคุณผิดอะไรสักอย่าง โดย 401 แปลว่าไม่ได้รับอนุญาต 404 แปลว่าไม่พบ และ 429 แปลว่าคุณส่ง request ถี่เกินไป รหัสในช่วง 500 แปลว่าตัว server เองพัง

นี่คือจุดสำคัญที่ต้องเข้าใจ ในมุมมองของ `httpx` 401 คือธุรกรรม HTTP ที่สำเร็จอย่างสมบูรณ์ คุณถาม server ตอบ ไบต์เดินทางมาถึง ไลบรารีจะไม่โยน exception เพราะในมุมมองของเครือข่ายไม่มีอะไรล้มเหลว `httpx.post` คืน response object ให้คุณเหมือนกับตอนได้ 200 ทุกประการ และเป็นหน้าที่ของคุณเองที่ต้องไปดูรหัส

`raise_for_status()` คือการไปดูนั้น มันตรวจ status code ไม่ทำอะไรเลยถ้ารหัสบอกว่าสำเร็จ และโยน `httpx.HTTPStatusError` ถ้าไม่ใช่

### อะไรจะพังจริง ๆ ถ้าไม่มีมัน

ลองคิดดูว่า request ที่ล้มเหลวมีอะไรอยู่ข้างใน เมื่อ key ของคุณผิด OpenAI จะคืน 401 พร้อม body แบบนี้

```json
{
  "error": {
    "message": "Incorrect API key provided: sk-proj-h2K***9E. You can find your API key at https://platform.openai.com/account/api-keys.",
    "type": "invalid_request_error",
    "param": null,
    "code": "invalid_api_key"
  }
}
```

นั่นเป็นข้อความที่ช่วยเหลือได้จริง มันบอกคุณอย่างแม่นยำว่าอะไรผิดและต้องไปแก้ที่ไหน

ทีนี้ลองลบ `raise_for_status()` ออกจากไฟล์แล้วจินตนาการถึงการรัน ฟังก์ชันไม่ตรวจรหัส มันจึงวิ่งตรงไปที่ `response.json()` ซึ่งทำงานสำเร็จ เพราะ body ของ error นั้นเป็น JSON ที่ถูกต้องทุกประการ จากนั้นมันประเมิน `body["choices"]` และไม่มี key ชื่อ `choices` อยู่ใน dictionary นั้น เพราะนี่เป็นเอกสาร error ไม่ใช่ completion Python จึงโยนสิ่งนี้ออกมา

```text
Traceback (most recent call last):
  File "llm.py", line 34, in <module>
    print(ask("Say hello in one short sentence."))
          ~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "llm.py", line 30, in ask
    return body["choices"][0]["message"]["content"]
           ~~~~^^^^^^^^^^^
KeyError: 'choices'
```

ดูสิว่าสิ่งนั้นบอกอะไรกับผู้เริ่มต้น ไม่มีอะไรที่เป็นความจริงเลย มันชี้ไปที่บรรทัดสุดท้ายของฟังก์ชัน ซึ่งเป็นโค้ดที่ถูกต้อง มันบอกว่ามี key หายไป ซึ่งชวนให้คิดว่ารูปแบบของ response ต่างจากที่คุณคาดไว้ แล้วส่งคุณไปนั่งอ่านเอกสาร API ที่ไม่ได้ผิดอะไรเลย มันไม่เคยพูดถึงการยืนยันตัวตน หรือ status code หรือข้อความ error ชั้นเยี่ยมที่ server ส่งมา ซึ่งโปรแกรมของคุณรับมาแล้วโยนทิ้งไป

ต้นตอที่แท้จริง คือ API key ที่ผิด มองไม่เห็นเลย นั่นคือสิ่งที่ทำให้เวอร์ชันที่ไม่มีบรรทัดนี้อันตราย ไม่ใช่แค่ไม่สมบูรณ์ มันไม่ได้ล้มเหลวแบบเงียบ ๆ แต่ล้มเหลวเสียงดังพร้อมเรื่องเล่าที่ชวนให้เข้าใจผิด และ error ที่ชวนเข้าใจผิดกินเวลามากกว่า error ที่ตรงไปตรงมาหลายเท่า

ทีนี้นี่คือการรันเดียวกันเมื่อมีบรรทัดนั้นอยู่

```text
Traceback (most recent call last):
  File "llm.py", line 35, in <module>
    print(ask("Say hello in one short sentence."))
          ~~~^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "llm.py", line 29, in ask
    response.raise_for_status()
    ~~~~~~~~~~~~~~~~~~~~~~~~~^^
httpx.HTTPStatusError: Client error '401 Unauthorized' for url 'https://api.openai.com/v1/chat/completions'
For more information check: https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/401
```

status code ถูกระบุชื่อ คำว่า Unauthorized ปรากฏขึ้น URL ที่ล้มเหลวถูกพิมพ์ออกมา คุณรู้ภายในหนึ่งวินาทีว่านี่เป็นปัญหาเรื่อง credential ไม่ใช่ปัญหาเรื่องโค้ด

### หลักการทั่วไป

ล้มเหลวที่ขอบ ไม่ใช่หลังจากนั้นอีกสามก้าว `raise_for_status()` วางอยู่ตรงจุดที่โลกภายนอกเข้าสู่โปรแกรมของคุณพอดี และหยุดทุกสิ่งที่ไม่คาดคิดไม่ให้เดินทางลึกเข้าไปกว่านั้น ทุกบรรทัดหลังจากมันได้รับอนุญาตให้สมมติว่ากำลังถือ completion ของจริงอยู่ ซึ่งเป็นเหตุผลที่บรรทัดสุดท้ายเป็นโซ่ของการ subscript เปล่า ๆ ได้โดยไม่ต้องมีการตรวจสอบป้องกันใด ๆ ล้อมรอบ

นั่นคือการแลกเปลี่ยนที่เกิดขึ้น การตรวจสอบหนึ่งบรรทัดที่ขอบซื้อความเรียบง่ายให้ทุกอย่างที่อยู่ถัดไป เมื่อคุณไปถึงบทที่ 04 และ agent loop เรียกฟังก์ชันนี้หลายสิบครั้งใน `while` loop ข้อความ error ที่ผิดจะถูกฝังอยู่ใต้การวนซ้ำจำนวนมาก และบรรทัดนี้คือสิ่งที่ทำให้มันยังค้นหาเจอ

500 จาก server ก็ทำงานแบบเดียวกัน และ 429 ตอนที่คุณโดนจำกัดอัตราก็เช่นกัน ทั้งหมดหยุดตรงนี้พร้อมชื่อจริงของมันติดมาด้วย แทนที่จะกลายเป็น `KeyError` เรื่อง `choices` ในบทที่ 17 เราจะกลับมาเปลี่ยนกรณี 429 ให้เป็นการ retry อัตโนมัติ ซึ่งทำได้ก็เพราะเราแยก 429 ออกจากความล้มเหลวแบบอื่น ๆ ได้

## 8. สิ่งที่คุณยังทำไม่ได้

คุณมีสายสื่อสารที่ใช้งานได้ไปยัง language model แล้ว ทีนี้มาหาขีดจำกัดของมันกัน เพราะขีดจำกัดนั้นคือเหตุผลที่ต้องมีบทที่ 02

ลองอันนี้

```python
from llm import ask

print(ask("My name is Ada."))
print(ask("What is my name?"))
```

output จะออกมาประมาณนี้

```text
Nice to meet you, Ada. How can I help you today?
I do not have access to your name. If you tell me, I will use it.
```

มันลืม และมันลืมทันที ระหว่างสองบรรทัดในโปรแกรมของคุณเอง

นี่ไม่ใช่เรื่องของ model ตัวเล็กที่อ่อนแอ และไม่ใช่บั๊กในโค้ดของคุณ มันเป็นผลโดยตรงจากรูปแบบ request ที่คุณอ่านไปในหัวข้อ 2 ดูสิว่าการเรียกครั้งที่สองส่งอะไรไปจริง ๆ

```json
{
  "model": "gpt-4o-mini",
  "messages": [
    {"role": "user", "content": "What is my name?"}
  ]
}
```

ไม่มีร่องรอยของ Ada อยู่ที่ไหนเลยในเอกสารนั้น server ไม่มีอะไรให้จดจำเลยสักอย่าง

แนวคิดสำคัญ และเป็นแนวคิดที่ทำให้เกือบทุกคนที่เรียนเรื่องนี้สะดุด คือ **API นั้น stateless** stateless แปลว่า server ไม่เก็บอะไรไว้เลยระหว่างการเรียกแต่ละครั้ง มันไม่รู้ว่าคุณเพิ่งเรียกมันไปเมื่อครู่ มันอ่าน list `messages` ที่คุณส่งไป ผลิตคำตอบหนึ่งอัน แล้วลืมทุกอย่าง ไม่มี session อยู่ที่ปลายทาง ไม่มีบทสนทนาที่ถูกเก็บไว้ใต้บัญชีของคุณ ไม่มีอะไรทั้งนั้น

ซึ่งนำไปสู่คำถามที่ชัดเจน เว็บแชทจำสิ่งที่คุณพูดได้อย่างชัดเจน แล้วมันทำได้อย่างไร

มันทำสิ่งเดียวกับที่คุณกำลังจะทำ ทุกครั้งที่คุณกด enter แอปพลิเคชันจะส่งบทสนทนาทั้งหมดตั้งแต่ต้น บวกกับข้อความใหม่ของคุณ ไปเป็น list `messages` ก้อนใหญ่ก้อนเดียว ความทรงจำไม่ได้อยู่ที่ server ความทรงจำคือ list ของ Python ที่อยู่ฝั่ง client และ client ส่งมันไปใหม่ทั้งหมดทุกครั้งไม่มีเว้น

นี่คือเหตุผลที่ `message` ใน response มีรูปร่าง `role` และ `content` เหมือนกับ message ที่คุณส่งไป มันถูกออกแบบมาให้ต่อท้ายเข้า list ของคุณได้ตรง ๆ แล้วส่งกลับไปพร้อมคำถามถัดไป

รูปร่างของบทที่ 02 จึงมองเห็นได้แล้วจากตรงนี้ แทนที่จะเป็นฟังก์ชันที่สร้าง list สมาชิกเดียวแล้วโยนทิ้ง เราจะเก็บ list ที่อยู่รอดข้ามการเรียกแต่ละครั้ง เอา message ของ user ต่อท้ายเข้าไป เอาคำตอบของ model ต่อท้ายเข้าไป แล้วส่งทั้งก้อนไปทุกครั้ง การเปลี่ยนแปลงเพียงข้อเดียวนั้นเปลี่ยน `ask` ให้กลายเป็นบทสนทนา และเป็นสิ่งที่ทำให้ทุกอย่างหลังจากนั้นเป็นไปได้ เพราะโดยพื้นฐานแล้ว agent คือบทสนทนาที่บางเทิร์นเป็นผลลัพธ์จาก tool แทนที่จะเป็นคำพูดของมนุษย์

### สิ่งที่คุณสร้างขึ้นในบทนี้

- คุณรู้แล้วว่า language model ในมุมมองของโปรแกรม คือ HTTP endpoint ที่รับ list ของ message แล้วคืน message กลับมาอีกหนึ่งอัน
- คุณอ่าน request แบบ chat completions ได้ และเรียกชื่อทุก field ในนั้นได้
- คุณอ่าน response ได้ และหาคำตอบเจอใน `choices` และคุณรู้ว่าทำไม `choices` ถึงเป็น list
- คุณมีฟังก์ชัน `ask` ที่ใช้งานได้จริง โดยไม่มี SDK คั่นระหว่างคุณกับ API
- คุณรู้ว่าทำไมโค้ดถึงอ่าน environment variable สามตัว ทำไม base URL ถึงต้องถูกตัดท้าย ทำไม header `Authorization` ถึงมีเงื่อนไข และทำไม timeout ถึงเป็น 120 วินาที แทนที่จะไม่มีหรือใช้ค่าเริ่มต้น
- คุณรู้ว่า `raise_for_status` ปกป้องคุณจากอะไร และจดจำ `KeyError` ที่ชวนเข้าใจผิดซึ่งคุณจะเจอถ้าไม่มีมันได้

ไปต่อที่บทที่ 02 ที่ซึ่ง model จะจดจำสิ่งที่คุณพูดได้เสียที
