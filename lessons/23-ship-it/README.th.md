## 1. สิ่งที่คุณมีอยู่ในมือ

พูดกันตรง ๆ เพราะสิ่งยั่วใจตอนจบคอร์สคือการพองตัวเอง และตอนจบที่พองเกินจริงจะสอนให้คุณ
ประเมินสิ่งต่อไปที่คุณจะสร้างผิดพลาด

คุณมี Python 1872 บรรทัดกระจายอยู่ในสิบหกไฟล์ ถ้ารวมไฟล์ตรวจสอบของบทนี้เข้าไปด้วยก็เป็น
1989 บรรทัด นั่นเล็กกว่าไฟล์ซอร์สไฟล์เดียวส่วนใหญ่ใน framework ที่คนติดตั้งกันเพื่อจะได้ไม่ต้อง
เขียนสิ่งนี้ และมันเล็กพอที่คุณจะอ่านทั้งหมดได้ในบ่ายเดียว ซึ่งเป็นคุณสมบัติเดียวที่ทำให้มันคุ้ม
ค่าแก่การสอน

dependency เดียวที่อยู่นอก Python standard library คือ `httpx` ไม่มีอะไรสักอย่างในโฟลเดอร์นี้ที่
import agent framework, SDK ของ model provider, ไลบรารี embedding, vector database, ชุด
เครื่องมือ CLI, ไลบรารี retry หรือ tokeniser การตรวจสอบบังคับข้อนี้แทนที่จะเชื่อใจไปเฉย ๆ

```python
ALLOWED_OUTSIDE_THE_STANDARD_LIBRARY = {"httpx"}
```

มันได้ข้อสรุปนั้นด้วยการเดินไล่ทุกไฟล์ `.py` ในโฟลเดอร์ เก็บชื่อระดับบนสุดของทุกคำสั่ง `import`
และ `from` ลบทุกอย่างที่อยู่ใน `sys.stdlib_module_names` และทุกอย่างที่เป็น module ของคอร์สเอง
ออก แล้วเทียบสิ่งที่เหลือกับเซ็ตนั้น

```python
    third_party = {
        name
        for name in imported
        if name not in sys.stdlib_module_names
        and name not in {m for m in MODULES}
        and name not in {"__future__"}
    }
    if not third_party <= ALLOWED_OUTSIDE_THE_STANDARD_LIBRARY:
        fail(f"something reaches for an unexpected dependency, {third_party}")
```

นั่นเป็นข้ออ้างที่เข้มงวดกว่า `requirements.txt` ที่มีบรรทัดเดียว เพราะไฟล์ requirements บันทึก
สิ่งที่คุณตั้งใจ ส่วนสิ่งนี้บันทึกสิ่งที่โค้ดทำจริง ถ้ามีใครใส่ `import tiktoken` ลงในไฟล์ช่วยเหลือ
เมื่อสามบทก่อน สิ่งนี้จะล้มเหลวตอน push ครั้งถัดไป

## 2. สี่ส่วน เล่าเป็นเรื่องเดียว

สี่ส่วน หนึ่งเส้นของการให้เหตุผล อ่านไปตามลำดับแล้วรูปร่างของคอร์สคือข้ออ้างเดียวที่ถูกขยายออกไป
เรื่อย ๆ

**ส่วนที่ 1 บทที่ 00 ถึง 06 บอกว่า model คือ HTTP endpoint** บทที่ 01 ส่ง POST request หนึ่งครั้ง
พร้อมรายการข้อความใน body แล้วได้รายการข้อความกลับมาโดยมีเพิ่มมาอีกหนึ่งอันท้ายสุด ไม่มีไลบรารี
มาขวางอยู่ตรงกลาง จึงไม่มีที่ให้เวทมนตร์ซ่อนตัว บทที่ 02 ค้นพบว่า model ไม่จำอะไรเลย และบทสนทนา
ทั้งหมดถูกส่งใหม่ในทุก request ซึ่งเป็นข้อเท็จจริงที่ต้นทุนและข้อจำกัดเกือบทั้งหมดในคอร์สนี้สืบทอด
มาจากมัน บทที่ 03 แสดงให้เห็นว่า tool call ไม่ใช่ความสามารถพิเศษ มันคือ model ที่ปล่อยชื่อกับ
object ของ argument แบบ JSON ออกมาแล้วรอให้คุณส่งสตริงกลับไป บทที่ 04 ห่อสิ่งนั้นไว้ในลูป `for`
ลูปนั้นคือ agent ตัวแรก และมันคือลูปเดียวกับที่คุณมีอยู่ทุกวันนี้

**ส่วนที่ 2 บทที่ 07 ถึง 11 ให้มือกับมัน และแนะนำอันตรายจริงอันแรก** การอ่านและแก้ไขไฟล์ การรัน
คำสั่ง shell การทำ glob และ grep ความสามารถมาพร้อมกับปัญหาที่ติดมาด้วย เพราะทันทีที่ agent เขียน
ลงดิสก์ของคุณและรันคำสั่งใน shell ของคุณได้ ข้อความที่มันอ่านก็กลายเป็นขอบเขตด้านความปลอดภัย
บทที่ 08 วางคนไว้หน้า shell tool ตั้งแต่วันแรก แทนที่จะทำเป็นการเสริมความแข็งแกร่งทีหลัง บทที่ 09
ให้เหตุผลว่า grep ชนะ vector index สำหรับโค้ด และทำให้คุณรู้สึกได้ว่าทำไม บทที่ 10 ชี้ให้เห็นว่า
คำอธิบายของ tool คือ prompt engineering ที่คนส่วนใหญ่ไม่เคยแก้ไข บทที่ 11 เล็งทั้งหมดนี้ไปที่
โฟลเดอร์ที่มี bug จริง แล้วมันก็แก้ได้

**ส่วนที่ 3 บทที่ 12 ถึง 18 เปลี่ยน agent ให้เป็นสิ่งที่อยู่รอดได้** ไม่ใช่เก่งขึ้น แต่อยู่รอดได้
ประตูตรวจสอบสิทธิ์ที่จำคำตอบของคุณได้ เพื่อให้มันยังถูกอ่านอยู่ตอน prompt ที่สี่สิบ session ในรูปแบบ
JSONL ธรรมดา ซึ่งกลายเป็นเครื่องมือ debug ที่ดีที่สุดในโปรเจกต์ การจัดการ context รวมถึงกับดักที่
การตัดทอนระหว่าง tool call กับผลลัพธ์ของมันทำให้ request ถัดไปถูกปฏิเสธทันที การบริหาร token ที่
บอกว่าเงินหายไปไหนจริง ๆ การทำ retrieval และสี่คำถามที่คุณต้องถามก่อนเอื้อมไปหามัน ข้อผิดพลาด
การ retry และการขัดจังหวะที่หยุดงานแทนที่จะหยุดหน้าจอ บทที่ 18 รันทั้งหมดพร้อมกันกับไดเรกทอรี
จริงแล้วไปตรวจดูดิสก์

**ส่วนที่ 4 บทที่ 19 ถึง 23 เชื่อมมันออกไปข้างนอกและให้คุณวัดผลมันได้** บทที่ 19 เขียน MCP client
ด้วยมือ ทำให้ tool กลายเป็นสิ่งที่คุณเชื่อมต่อไปหาแทนที่จะเป็นสิ่งที่คุณเขียน แล้วตีราคามันอย่างซื่อสัตย์
เพราะ schema ของ tool ถูกส่งใหม่ในทุก request และ server สี่ตัวกินพื้นที่ context ของคุณหมดได้ก่อน
งานจะเริ่มด้วยซ้ำ บทที่ 20 เปลี่ยน agent ทั้งตัวให้เป็น tool หนึ่งตัว เพื่อให้การสืบสวนที่ยาวนานเลิก
ถมบทสนทนาของตัวแม่ และเรียกชื่อกับดักที่ติดมาฟรี ๆ กับมัน นั่นคือตัวแม่กับตัวลูกตอนนี้ถือมุมมองต่อ
โลกที่ต่างกัน บทที่ 21 รันหลายตัวพร้อมกันด้วย thread และ queue แล้วทำให้คุณค้นพบว่าส่วนไหนของ
harness ของคุณแอบสมมติเงียบ ๆ ว่าจะมีแค่ตัวเดียวเสมอ บทที่ 22 มอบเครื่องมือวัดให้คุณ ทำให้การ
เปลี่ยน system prompt กลายเป็นสิ่งที่คุณทดสอบได้ แทนที่จะเป็นสิ่งที่คุณรู้สึกเอา

## 3. แนวคิดเดียวที่ควรเก็บติดตัวไป

ถ้าคุณจะเก็บประโยคเดียวจากยี่สิบสี่บท เก็บประโยคนี้

**ตลอดสิบเก้าบทของความสามารถใหม่ agent loop เปลี่ยนแปลงก็ต่อเมื่อมีการเพิ่ม subsystem เท่านั้น
และไม่เคยเปลี่ยนเลยเมื่อมีการเพิ่ม tool**

นั่นไม่ใช่คำขวัญ มันคือการวัดผล มันถูกวัดสองครั้ง และครั้งที่สองอยู่ในโฟลเดอร์นี้

### การวัดผล

บทที่ 18 แจกแจงทุกความแตกต่างระหว่างลูปในบทที่ 04 กับลูปตอนจบส่วนที่ 3 สิบสี่ความแตกต่าง สอง
อย่างมาจาก streaming สองอย่างจาก provider abstraction สองอย่างจาก system prompt หนึ่งอย่างจาก
permissions สามอย่างจาก session หนึ่งอย่างจากการจัดการ context สองอย่างจากการบริหาร token หนึ่ง
อย่างจากข้อผิดพลาดและการขัดจังหวะ ศูนย์อย่างมาจากการเพิ่ม tool และนั่นรวมถึงบทที่ 16 ซึ่งสร้าง
vector index ตัว embedder และตัวให้คะแนน แล้วปล่อย `agent.py` ไว้เหมือนเดิมทุกไบต์

ส่วนที่ 4 คือครึ่งหลังของการวัดผลนี้ และมันเป็นการทดสอบที่หินกว่า เพราะส่วนที่ 4 เพิ่มสี่สิ่งที่มีแนวโน้ม
มากที่สุดที่จะเรียกร้องการเปลี่ยนแปลงที่ใจกลาง tool ที่อยู่ในโปรเซสอื่น agent ที่เริ่ม agent ตัวอื่น
agent หลายตัวรันพร้อมกัน และ harness สำหรับทดสอบที่รัน agent ซ้ำหลายรอบ

```bash
cd lessons
for d in 19-mcp-client 20-subagents 21-multi-agent 22-evals 23-ship-it; do
  diff -q 18-the-harness/agent.py $d/agent.py > /dev/null 2>&1 \
    && echo "agent.py in $d is identical to 18-the-harness" \
    || echo "agent.py in $d DIFFERS"
done
```

```text
agent.py in 19-mcp-client is identical to 18-the-harness
agent.py in 20-subagents is identical to 18-the-harness
agent.py in 21-multi-agent is identical to 18-the-harness
agent.py in 22-evals is identical to 18-the-harness
agent.py in 23-ship-it is identical to 18-the-harness
```

ห้าบท สี่ฟีเจอร์ใหญ่ และฟังก์ชันที่สำคัญที่สุดในโปรแกรมไม่ถูกเปิดขึ้นมาเลยสักครั้ง ไฟล์เดียวที่ขยับคือ
`tools.py` จาก 405 บรรทัดเป็น 422 ตอนที่บทที่ 19 สอนให้มันรับ tool ที่ implementation อยู่หลังท่อ

ดูว่าฟีเจอร์ของส่วนที่ 4 แต่ละอย่างลงจอดอย่างไร เพราะรูปแบบมันเหมือนกันทั้งสี่ครั้ง

| ฟีเจอร์ | มันมาถึงอย่างไร | ลูปเห็นอะไร |
| --- | --- | --- |
| MCP server | schema และรายการ dispatch ถูกเพิ่มเข้าไปใน `tools.py` | tool เพิ่มขึ้น |
| Subagent | `run_subagent` ซึ่งเป็น tool ที่ body ของมันเรียก `run` | tool เพิ่มอีกหนึ่งตัว |
| agent ที่รันขนาน | `fanout.py` ซึ่งเรียก `run` จาก thread | ไม่เห็นอะไรเลย มันอยู่เหนือลูป |
| Eval | `evals.py` ซึ่งเรียก `run` หลายครั้ง | ไม่เห็นอะไรเลย มันอยู่เหนือลูป |

`subagent.py` พูดเรื่องนี้ไว้ในย่อหน้าแรกของตัวเอง

```text
There is no new machinery here. A subagent is a tool whose implementation
happens to run another agent. The parent sees a tool with a name and a
description, exactly like read_file, and the loop does not change at all.
That is the point worth noticing rather than the code.
```

### ทำไมนี่ถึงเป็นกฎ ไม่ใช่ความบังเอิญ

มันง่ายมากที่จะอ่านตารางนั้นแล้วคิดว่าเป็นโชค หรือเป็นเพราะผู้เขียนเลือกตัวอย่างที่เข้าทาง มันไม่ใช่ทั้ง
สองอย่าง และเหตุผลอยู่ที่โครงสร้าง สองหมวดหมู่นี้ต่างกันที่คุณสมบัติเดียวเท่านั้น นั่นคือสิ่งใหม่นั้นต้อง
มองเห็นอะไรบ้าง

**tool ต้องการแค่ argument ของตัวเอง และคืนค่าออกมา** `read_file` ได้ path มา `grep_files` ได้
pattern กับ glob มา `run_shell` ได้คำสั่งมา ไม่มีตัวไหนต้องรู้ว่ามีบทสนทนาอยู่ ผ่านมากี่เทิร์นแล้ว
งบประมาณเท่าไร หรือ model พูดอะไรไปล่าสุด พวกมันรับ input แล้วผลิตสตริงออกมา สัญญานั้นมีอยู่แล้ว
ตั้งแต่หลังบทที่ 03 ดังนั้น tool ใหม่จึงเป็นแค่แถวใหม่ใน dictionary และรายการใหม่ในลิสต์ของ schema
ไม่มีที่ให้มันไปแตะลูป เพราะมันไม่เคยรู้ด้วยซ้ำว่าลูปมีอยู่

นั่นคือเหตุผลที่ MCP tool และ subagent ต่างก็แทรกเข้ามาได้โดยไม่ต้องต่อสู้ MCP tool คือฟังก์ชันที่
เขียน JSON ลงท่อแล้วอ่าน JSON กลับมา subagent คือฟังก์ชันที่รัน agent อีกตัว ทั้งคู่คือ Python
อะไรก็ได้ที่อยู่หลังสัญญาเดียวกัน และสัญญานั้นไม่เคยเกี่ยวกับว่าฟังก์ชันทำอะไร

**subsystem ต้องสังเกตหรือดักจับบางอย่างที่ลูปเป็นเจ้าของ ในจังหวะที่มีแต่ลูปเท่านั้นที่ควบคุมได้**
permissions ต้องทำงานในช่องว่างระหว่างตอนที่ model ขอให้เรียกกับตอนที่การเรียกเกิดขึ้นจริง และไม่มี
อะไรนอกลูปที่ยืนอยู่ในช่องว่างนั้นได้ session ต้องเห็นข้อความแต่ละอันในวินาทีที่มันถูกสร้าง ซึ่งเป็น
เหตุผลว่าทำไมการเขียนไฟล์ตอนจบจึงเป็นโปรแกรมคนละแบบและแย่กว่า การจัดการ context ต้องแก้ไข
payload หลังจากรายการข้อความมีอยู่แล้วและก่อนที่มันจะถูกส่ง การยกเลิกต้องถูกอ่านระหว่างเทิร์น การ
นับการใช้งานต้องถูกบวกเพิ่มหลังจาก provider รายงานมัน

ห้าสิ่งนั้นทำจากข้างนอกไม่ได้ ดังนั้นแต่ละอย่างจึงต้องการรอยต่อใน `run` นั่นคือความแตกต่างทั้งหมด
ไม่ใช่ความสำคัญ ไม่ใช่ขนาด ไม่ใช่ว่าโค้ดยากแค่ไหน แค่ว่าสิ่งใหม่นั้นต้องเข้าถึงจังหวะส่วนตัวของ
เครื่องยนต์หรือไม่

### กฎสำหรับใช้จำแนกมันในที่อื่น

ถามคำถามเดียวกับทุกสิ่งที่คุณกำลังจะเพิ่มเข้าไปในระบบที่มีลูป ตัวกระจายงาน หรือตัวจัดคิวอยู่ตรงกลาง

**สิ่งนี้ต้องมองเห็นสถานะที่เครื่องยนต์เป็นเจ้าของ ในจังหวะที่เครื่องยนต์เป็นคนเลือก หรือไม่**

ถ้าคำตอบคือไม่ มันคือใบไม้ปลายกิ่ง มันไปอยู่หลังสัญญาที่มีอยู่แล้ว และเครื่องยนต์ต้องไม่รู้จักชื่อของมัน
ถ้าคุณพบว่าตัวเองกำลังเพิ่มเงื่อนไขที่เอ่ยชื่อสิ่งใหม่นั้นตรง ๆ แสดงว่าคุณจำแนกใบไม้ผิด และบทที่ 12
คือตัวอย่าง การยืนยัน shell เริ่มต้นอยู่ข้างใน `run_shell` ซึ่งทำให้ tool นั้นทดสอบไม่ได้และใช้ไม่ได้ถ้า
ไม่มี terminal และการย้ายมันออกไปที่ `permissions.py` คือสิ่งที่ทำให้บทที่ 20 รัน tool ได้โดยไม่มีคน
นั่งอยู่หน้าคีย์บอร์ด

ถ้าคำตอบคือใช่ มันคือ subsystem และมันต้องการรอยต่อ ออกแบบรอยต่อให้เป็นแบบทั่วไปแทนที่จะเฉพาะ
เจาะจงกับฟีเจอร์ที่เป็นแรงจูงใจให้สร้างมัน เพราะนั่นคือสิ่งที่หยุดไม่ให้จำนวนรอยต่อโตตามจำนวนฟีเจอร์
`on_message` เป็นฟังก์ชันที่รับหนึ่ง argument มันจึงรับใช้ไฟล์ session การทดสอบที่ append เข้า list
และ socket ได้เหมือนกันหมด `permissions.check` คืนค่า boolean การทดสอบจึงสร้างตัวที่ปฏิเสธทุกอย่าง
แล้วส่งเข้าไปในการรันจริงได้ `fit_to_budget` คืน list ใหม่ การตัดทอนจึงทำให้บันทึกเสียหายไม่ได้เลย

ขอบเขตเดียวกันนี้อยู่ทุกที่ เมื่อคุณมีชื่อเรียกให้มันแล้ว

- **web framework** การเพิ่ม route ไม่เคยเปลี่ยนตัวกระจายงาน เพราะ handler รับ request แล้วคืน
  response การเพิ่ม authentication การ log request การจำกัดอัตรา หรือการทำ tracing เปลี่ยน เพราะ
  แต่ละอย่างต้องนั่งอยู่ระหว่างตัวกระจายงานกับ handler ทุก framework ที่โตแล้วตอบด้วย middleware
  ซึ่งก็คือ `on_message` และ `permissions.check` ในชื่ออื่น
- **build tool** การเพิ่ม task คือข้อมูล การเพิ่มการทำแคช การรันขนาน หรือแถบแสดงความคืบหน้าไปแตะ
  ตัวจัดคิว เพราะแต่ละอย่างต้องรู้ว่า task เริ่มและจบเมื่อไร
- **database client** การเพิ่ม query คือข้อมูล การเพิ่ม connection pooling การ retry หรือการจับเวลา
  query คือ subsystem เพราะแต่ละอย่างต้องการจังหวะก่อนและหลังการเรียกผ่านสาย
- **game engine** การเพิ่ม entity คือข้อมูล การเพิ่มการหยุดชั่วคราว การเล่นซ้ำ หรือ seed แบบกำหนดผล
  ได้แน่นอน ไปแตะลูปเฟรม

รูปแบบความล้มเหลวไม่เคยเป็นว่าคุณเพิ่ม subsystem ไม่ได้ มันคือคุณเพิ่มมันเป็นเงื่อนไขแทนที่จะเป็น
รอยต่อ เงื่อนไขแรกดูสมเหตุสมผล อันที่สองก็ด้วย พอถึงอันที่ห้า เครื่องยนต์กลายเป็นไฟล์ที่ทุกฟีเจอร์ต้อง
ผ่าน มันยาวสี่ร้อยบรรทัด ไม่มีใครกล้าแก้ และการเพิ่มฟีเจอร์ที่หกทำให้ห้าอย่างที่ทำงานได้อยู่แล้วเสี่ยง
ไปด้วย ทั้งสองการออกแบบรันโปรแกรมเดียวกันในวันที่คุณเขียนมันเสร็จ พวกมันแยกทางกันในวันที่สามสิบ
และคอร์สนี้คือการทดลองนั้นเวอร์ชันสามสิบวัน ที่รันในที่สาธารณะ พร้อมกับเก็บ hash ไว้

## 4. การทำให้เป็น package

โฟลเดอร์ lessons เป็นกองไฟล์แบน ๆ อย่างจงใจ เพราะคอร์สที่บทสี่แอบไปขึ้นอยู่กับการแก้ไขที่คุณทำใน
บทสอง คือคอร์สที่คนเลิกเรียนกลางคัน แต่กองไฟล์แบน ๆ ไม่ใช่สิ่งที่คุณเอาไปให้ใครได้
`src/agentpath/` คือแนวคิดเดียวกันที่เขียนไว้ครั้งเดียวอย่างเรียบร้อย และนี่คือไฟล์ที่เปลี่ยนมันให้เป็น
package ที่ติดตั้งได้

นี่คือทั้งไฟล์

```toml
[project]
name = "agentpath"
version = "0.3.0"
description = "Learn how AI agents actually work by building a real one, from a single LLM call to a full agent harness."
readme = "README.md"
requires-python = ">=3.10"
license = { text = "MIT" }
dependencies = ["httpx>=0.27"]

[project.scripts]
agentpath = "agentpath.cli:main"

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.6"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/agentpath"]

[tool.ruff]
line-length = 100
exclude = ["lessons"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.pytest.ini_options]
testpaths = ["tests"]
```

สามสิบเอ็ดบรรทัด ห้าตาราง และทุกบรรทัดทำงานอยู่ ไล่ดูทีละอัน

### ตาราง project

นี่คือตารางข้อมูลกำกับที่เป็นมาตรฐาน เหตุผลที่มันคุ้มค่าแก่การเรียนรู้แทนที่จะลอกไปเฉย ๆ คือมันเป็นการ
ประกาศและไม่ผูกกับเครื่องมือใด สิบปีก่อนข้อมูลนี้อยู่ใน `setup.py` ซึ่งเป็นสคริปต์ Python ที่รันตอน
ติดตั้งและทำอะไรก็ได้ รวมถึงตรวจดูเครื่องของคุณแล้วตัดสินใจว่า package ของคุณคืออะไร การย้ายมันไป
เป็นข้อมูลนิ่งใน `pyproject.toml` หมายความว่าเครื่องมือหนึ่งอ่านได้ว่า package ของคุณคืออะไรโดยไม่
ต้องรันโค้ดของคุณ และนั่นคือเหตุผลที่ตัวติดตั้งทุกวันนี้แก้ปัญหา dependency ได้โดยไม่ต้องดาวน์โหลด
และรันซอร์สที่ไม่รู้ที่มา

**`name`** คือตัวตน มันคือสิ่งที่คนพิมพ์ต่อจาก `pip install` และมันต้องไม่ซ้ำกับใครทั้ง Python
Package Index หัวข้อ 5 พูดถึงเรื่องที่ว่ามันยากกว่าที่ฟังดู

**`version`** คือ `0.3.0` และตัวเลขเดินตามคอร์สแทนที่จะเดินตามปฏิทิน เอกสารออกแบบกำหนดให้หนึ่ง
ส่วนเท่ากับหนึ่ง release ดังนั้นส่วนที่ 1 จึงออกเป็น `0.1.0` ส่วนที่ 2 เป็น `0.2.0` ส่วนที่ 3 เป็น
`0.3.0` เหตุผลที่ผูก release กับส่วนแทนที่จะผูกกับบทคือ หนึ่งส่วนเป็นหน่วยที่เล็กที่สุดของคอร์สที่มี
ประโยชน์ได้ด้วยตัวเอง การออกเวอร์ชันที่คุณค่าของมันเพิ่งโผล่มาอีกสามบทถัดไปคือการส่งของที่สร้างเสร็จ
แค่ครึ่งเดียว

หมายเลขเวอร์ชันยังปรากฏใน `src/agentpath/__init__.py` ในชื่อ `__version__` ด้วย และการรักษาสอง
สำเนาให้ตรงกันด้วยมือคือวิธีที่รู้กันดีว่าจะทำให้เผยแพร่ package ที่รายงานเลขผิด hatchling อ่าน
เวอร์ชันออกจากไฟล์ซอร์สแทนได้ และเหตุผลที่โปรเจกต์นี้ยังไม่ทำแบบนั้นคือมันเป็นเวทมนตร์การ build อีก
ชิ้นที่มาคั่นระหว่างผู้อ่านกับไฟล์ ซึ่งเป็นการแลกที่หลักการข้อสองของโปรเจกต์มักจะแพ้

**`description`** คือหนึ่งบรรทัด และมันคือคำโปรย มันกลายเป็นประโยคใต้ชื่อในผลการค้นหา ดังนั้นมันจึง
เป็นงานเขียนชิ้นเดียวที่คนส่วนใหญ่จะได้อ่านเกี่ยวกับโปรเจกต์นี้

**`readme`** ชี้ไปที่ `README.md` ซึ่งเนื้อหาทั้งหมดของมันจะถูกคัดลอกเข้าไปในข้อมูลกำกับของ package
ตอน build แล้วถูกเรนเดอร์เป็นหน้าโปรเจกต์ นั่นคุ้มค่าแก่การรู้เพราะมันหมายความว่า README ถูกส่งไป
อยู่ข้างใน wheel ไม่ใช่ถูกลิงก์จากมัน นี่คือส่วนบนของข้อมูลกำกับจาก wheel ที่บทนี้ build ขึ้นมา

```text
Metadata-Version: 2.5
Name: agentpath
Version: 0.3.0
Summary: Learn how AI agents actually work by building a real one, from a single LLM call to a full agent harness.
License: MIT
License-File: LICENSE
Requires-Python: >=3.10
Requires-Dist: httpx>=0.27
Provides-Extra: dev
Requires-Dist: pytest>=8.0; extra == 'dev'
Requires-Dist: ruff>=0.6; extra == 'dev'
Description-Content-Type: text/markdown
```

ทุกบรรทัดในนั้นมาจากแปดบรรทัดของตาราง project

**`requires-python`** คือคำสัญญาที่ถูกบังคับใช้โดยตัวติดตั้งแทนที่จะถูกผู้ใช้ค้นพบเอง ถ้าไม่มีมัน คนที่
ใช้ Python 3.8 จะติดตั้ง package ได้สำเร็จ แล้วเจอ `SyntaxError` หรือ `AttributeError` จากกลางโค้ด
ของคุณ ซึ่งอ่านออกมาเหมือน package ของคุณพัง ถ้ามีมัน `pip` จะปฏิเสธการติดตั้งและบอกเหตุผล

ขอบเขตล่างคือ `>=3.10` ด้วยเหตุผลที่เป็นรูปธรรมมากกว่าเป็นแฟชั่น `check.py` ในโฟลเดอร์นี้ใช้
`sys.stdlib_module_names` ซึ่งมาถึงใน 3.10 และเป็นสิ่งที่ทำให้ตรวจสอบข้ออ้างเรื่อง dependency
ข้างต้นได้เลย การจำกัด path ใน `tools.py` ใช้ `Path.is_relative_to` ซึ่งมาถึงใน 3.9 การตั้งขอบล่าง
ด้วยการหาสิ่งที่ใหม่ที่สุดที่คุณใช้จริงคือวิธีที่ถูกต้อง การตั้งมันตามที่คุณบังเอิญรันอยู่คือวิธีที่จะกันผู้ใช้
ของคุณออกไปครึ่งหนึ่งโดยไม่ได้อะไรเลย

**`license`** สำคัญกว่าที่เห็นในโปรเจกต์เพื่อการสอน MIT หมายความว่ามีคนเอาโค้ดนี้ไปใส่ในผลิตภัณฑ์
เชิงพาณิชย์ได้โดยไม่ต้องขอ โปรเจกต์ที่ไม่มีสัญญาอนุญาตเลยไม่ใช่สมบัติสาธารณะ มันคือของที่มีลิขสิทธิ์

### Dependencies

```toml
dependencies = ["httpx>=0.27"]
```

หนึ่งบรรทัด และการไปถึงจุดนั้นคือประเด็นของทั้งคอร์ส ทุกบทที่อาจจะเพิ่ม dependency ได้เลือกที่จะสร้าง
สิ่งนั้นแล้วอธิบายมันแทน `argparse` แทน CLI framework เพราะ standard library เพียงพอแล้ว
`fnmatch` และ `re` แทนไลบรารีค้นหา embedder ที่ทำมือในบทที่ 16 แทน vector database MCP client
ที่เขียนด้วยมือในบทที่ 19 แทน SDK ทางการ แต่ละอย่างคือจุดที่ผู้อ่านอาจติดหล่มกับสิ่งที่ไม่ใช่หัวข้อ

ตัวระบุเวอร์ชันเป็นขอบล่าง ไม่ใช่การตรึง และความต่างนั้นสำคัญ ถ้าคุณตรึงมันด้วย `==0.27.2` ใครก็ตาม
ที่ติดตั้ง package ของคุณควบคู่กับอย่างอื่นที่ต้องการ `httpx` ใหม่กว่าจะเจอความขัดแย้งที่แก้ไม่ได้ และ
ทางแก้เดียวคือให้คุณเผยแพร่เวอร์ชันใหม่ ไลบรารีควรบอกเวอร์ชันที่เก่าที่สุดที่รู้ว่ามันทำงานด้วยได้ แล้ว
ปล่อยให้แอปพลิเคชันตัดสินใจส่วนที่เหลือ การตรึงแบบเป๊ะ ๆ ถูกต้องสำหรับแอปพลิเคชันที่คุณ deploy และ
ผิดสำหรับ package ที่คนอื่นติดตั้ง

ทีนี้มาถึงส่วนที่ซื่อสัตย์ dependency หนึ่งบรรทัดไม่ได้แปลว่า package หนึ่งตัว นี่คือสิ่งที่ environment

### console script entry point

```toml
[project.scripts]
agentpath = "agentpath.cli:main"
```

สองคำกับเครื่องหมายทวิภาคหนึ่งตัวทางฝั่งขวา ฝั่งซ้ายคือชื่อคำสั่งที่จะมีอยู่ใน `PATH` ของผู้ใช้ ฝั่งขวา
คือ import path กับ callable คั่นด้วยเครื่องหมายทวิภาค หมายความว่าให้ import module `agentpath.cli`
แล้วเรียกฟังก์ชัน `main` ในนั้นโดยไม่ส่ง argument

สิ่งที่ตัวติดตั้งทำกับข้อมูลนั้นคือสร้างไฟล์ปฏิบัติการเล็ก ๆ ตอนติดตั้งแล้ววางไว้ในไดเรกทอรี scripts ของ
environment นั่นคือเหตุผลที่มันใช้ได้ทันทีโดยไม่ต้องตั้งค่า shell และไม่ต้อง `chmod` และเป็นเหตุผลที่
มันชี้ไปยัง Python ตัวที่ถูกต้องแม้จะมีสามเวอร์ชันติดตั้งอยู่ มันถูกบันทึกไว้ใน wheel เป็นไฟล์ข้อความ
ธรรมดา

```text
[console_scripts]
agentpath = agentpath.cli:main
```

ทางเลือกที่ชัดเจนสองทางแพ้ การส่ง shell script ไปด้วยหมายถึงต้องเขียนสองรอบ รอบหนึ่งสำหรับ `sh`
และอีกรอบสำหรับ Windows แล้วยังต้องฝังพาธของ interpreter ซึ่งผิดในทุกเครื่องยกเว้นเครื่องคุณ การ
บอกให้คนรัน `python -m agentpath` ฟรีและใช้ได้ แต่มันทำให้เครื่องมือรู้สึกเหมือนสคริปต์มากกว่า
โปรแกรม และมันใส่ interpreter ลงไปในทุกคำสั่งที่ผู้ใช้พิมพ์หรือเขียนลงใน makefile entry point จ่าย
แค่หนึ่งบรรทัดและกำจัดปัญหาทั้งสองอย่าง

สิ่งเดียวที่ต้องระวังคือ `main` ต้องเรียกได้โดยไม่ส่ง argument และควรคืนรหัสออกแทนที่จะเรียก
`sys.exit` นั่นคือเหตุผลที่ `cli.py` และ `main.py` ต่างจบด้วยวิธีเดียวกัน

```python
if __name__ == "__main__":
    raise SystemExit(main())
```

ความห่างนั้นจะถูกค้นพบในวันที่ pull request ของใครสักคนล้มเหลวด้วยเหตุผลที่เขาทำซ้ำไม่ได้

### ตาราง build system

```toml
[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

นี่คือตารางที่คนลอกไปโดยไม่อ่าน จึงคุ้มค่าที่จะพูดให้ชัดว่ามันหมายถึงอะไร มันบอกว่าเพื่อจะเปลี่ยน
ไดเรกทอรีนี้ให้เป็น package ที่แจกจ่ายได้ เครื่องมือควรสร้าง environment แยกขึ้นมาก่อน ติดตั้ง
`hatchling` ลงไป แล้วเรียก build interface มาตรฐานที่ `hatchling.build`

เหตุผลที่สิ่งนี้มีอยู่ในฐานะการประกาศแทนที่จะเป็นข้อสมมติคือประวัติศาสตร์ หลายปีที่ผ่านมาเครื่องมือ
build คือ `setuptools` แบบสากล แบบโดยปริยาย และโปรเจกต์ไหนที่อยากใช้ตัวอื่นก็เจอปัญหาไก่กับไข่
เพราะคำสั่งวิธี build มันถูกเขียนไว้ในสิ่งที่คุณต้อง build ก่อน มาตรฐานแก้เรื่องนี้ด้วยการทำให้ build
backend เป็นข้อมูลนิ่งที่ frontend ตัวไหนก็อ่านก่อนได้ `pip`, `build` และ `uv` เข้าใจตารางนี้ทั้งหมด
package จึง build ออกมาเหมือนกันไม่ว่าคุณจะใช้ตัวไหน

ใช้ `hatchling` แทน `setuptools` ด้วยเหตุผลสองข้อที่เกี่ยวกับผู้อ่านทั้งคู่ มันไม่ต้องมี `setup.py` และ
ไม่ต้องมี `MANIFEST.in` ไฟล์นี้จึงเป็นการตั้งค่า build เพียงอย่างเดียวในโปรเจกต์ และค่าเริ่มต้นของมัน
สำหรับโครงสร้างแบบ `src` ก็ใกล้เคียงถูกต้องพอที่จะต้องเขียนทับแค่บรรทัดเดียว

บรรทัดเดียวนั้นคือตารางถัดไป

```toml
[tool.hatch.build.targets.wheel]
packages = ["src/agentpath"]
```

สิ่งนี้จำเป็นเพราะโครงสร้างแบบ `src` package ที่ import ได้คือ `agentpath` แต่บนดิสก์มันอยู่ที่
`src/agentpath` และถ้าไม่มีบรรทัดนี้ backend จะต้องเดาว่าจะส่งไดเรกทอรีระดับบนสุดชื่อ `src` หรือ
ไดเรกทอรีระดับบนสุดชื่อ `agentpath` บรรทัดนี้บอกว่าให้ส่งเนื้อหาของ `src/agentpath` ในฐานะ package
ชื่อ `agentpath`

โครงสร้างแบบ `src` คุ้มค่ากับบรรทัดที่เพิ่มมาด้วยเหตุผลที่โผล่ในสถานการณ์เดียวเท่านั้น นั่นคือการ
ทดสอบ ถ้า package อยู่ที่รากของ repository การ `import agentpath` จากไดเรกทอรีรากจะเจอ source
tree ไม่ว่า package จะถูกติดตั้งไว้หรือไม่ เพราะไดเรกทอรีปัจจุบันอยู่บน `sys.path` ดังนั้นเทสต์ของคุณ
จึงผ่านกับสำเนางานของคุณและไม่บอกอะไรคุณเลยว่าสิ่งที่คุณกำลังจะเผยแพร่ครบถ้วนหรือไม่ ด้วย
โครงสร้างแบบ `src` ซอร์สจะ import ไม่ได้โดยบังเอิญ เทสต์จึงรันกับ package ที่ติดตั้งแล้ว และ module
ที่คุณลืมใส่จะล้มเหลวทันทีแทนที่จะล้มหลังเผยแพร่ไปแล้ว

### การตั้งค่าเครื่องมือ

```toml
[tool.ruff]
line-length = 100
exclude = ["lessons"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.pytest.ini_options]
testpaths = ["tests"]
```

ทุกตาราง `[tool.*]` ถูกจัดอยู่ในเนมสเปซของเครื่องมือหนึ่งตัว ซึ่งเป็นกลไกที่ทำให้ไฟล์เดียวเก็บการ
ตั้งค่าของทุกอย่างได้ แทนที่จะเป็นรากของ repository ที่เต็มไปด้วยไฟล์จุด

`exclude = ["lessons"]` คือรายการที่น่าสนใจ และมันเข้ารหัสการตัดสินใจจากเอกสารออกแบบมากกว่าจะ
เป็นความชอบส่วนตัว โค้ดของบทเรียนถูกทำซ้ำในยี่สิบสี่โฟลเดอร์อย่างจงใจ linter ที่ถูกเล็งไปที่มันจึงจะ
รายงานสิ่งเดียวกันยี่สิบสี่ครั้ง และกฎการเรียงลำดับ import ก็จะตีกับการ import ที่ก้นฟังก์ชันซึ่งเป็น
ความจงใจที่บทที่ 18 ใช้ทั้งหัวข้ออธิบาย framework ใน `src/` ถูกบังคับด้วย linter ส่วนภาพนิ่งเพื่อการ
สอนถูกบังคับด้วยการตรวจสอบแทน

`testpaths = ["tests"]` หยุดไม่ให้ `pytest` ไปเก็บโฟลเดอร์ lessons ซึ่งจะเจอไฟล์ชื่อ `check.py`
ยี่สิบสี่ไฟล์ แล้ว import เข้ามา แล้วมันก็จะเริ่มคุยกับ model ทันที

## 5. การเผยแพร่ แบบตรงไปตรงมา

ข้อมูลกำกับของ package คือคำบรรยาย การเผยแพร่คือการลงมือ มีสี่ขั้นตอน และลำดับของสองขั้นตอนใน
นั้นคือจุดที่คนเจ็บตัว

### สร้าง artifact

```bash
python -m build
```

```text
* Creating isolated environment: venv+pip...
* Installing packages in isolated environment:
  - hatchling
* Getting build dependencies for sdist...
* Building sdist...
* Building wheel from sdist
* Creating isolated environment: venv+pip...
* Installing packages in isolated environment:
  - hatchling
* Getting build dependencies for wheel...
* Building wheel...
Successfully built agentpath-0.3.0.tar.gz and agentpath-0.3.0-py3-none-any.whl
```

อ่านดูว่ามันทำอะไร เพราะมันอธิบายตาราง `[build-system]` จากหัวข้อที่แล้ว มันสร้าง environment ใหม่
ติดตั้ง `hatchling` ลงไป build source distribution แล้ว build wheel จาก source distribution นั้น
แทนที่จะ build จากไดเรกทอรีงานของคุณ รายละเอียดสุดท้ายนั้นเป็นความจงใจของเครื่องมือ การ build
wheel จาก sdist พิสูจน์ว่า sdist ครบถ้วน เพราะถ้ามีไฟล์หายไปจากมัน การ build wheel จะล้มเหลวตรง
นั้นเลย แทนที่จะล้มอีกหกเดือนต่อมาตอนที่มีใครพยายาม build package ของคุณจากซอร์ส

artifact สองชิ้นออกมา และมันเป็นคนละอย่างกัน

**wheel** ที่ลงท้ายด้วย `.whl` คือไฟล์ zip ของโครงสร้างต้นไม้แบบที่ควรจะปรากฏหลังติดตั้งพอดี การ
ติดตั้งมันคือการแตก zip กับการเขียนข้อมูลกำกับ ไม่มีขั้นตอน build บนเครื่องผู้ใช้ ซึ่งเป็นเหตุผลที่
wheel ทำให้การติดตั้ง Python เร็วและเชื่อถือได้

**sdist** ที่ลงท้ายด้วย `.tar.gz` คือซอร์ส มันมีอยู่เพื่อคนและระบบที่ต้อง build package เอง เช่นผู้ทำ
แพ็กเกจของดิสทริบิวชัน การ build ในเครือข่ายที่ถูกตัดขาด หรือสถาปัตยกรรมที่คุณไม่ได้เผยแพร่ wheel
ให้

### ทดสอบการติดตั้งใน environment ที่สะอาด ก่อนเผยแพร่ ไม่ใช่หลังเผยแพร่

นี่คือขั้นตอนที่ถูกข้าม และการข้ามมันคือเหตุผลที่ release แรกจำนวนมากตามมาด้วย release ที่สองภายใน
ชั่วโมงเดียว

เหตุผลที่มันต้องเป็น environment ที่สะอาดนั้นเฉพาะเจาะจง package ของคุณ build จาก working tree
ของคุณ แต่มันถูก import จาก `sys.path` และบนเครื่องของคุณสองอย่างนี้ทับซ้อนกัน module ที่คุณลืม
ระบุ ไฟล์ข้อมูลที่ไม่เคยเข้าไปอยู่ใน wheel dependency ที่คุณใช้แต่ไม่เคยประกาศเพราะมันถูกติดตั้งไว้
อยู่แล้วเพื่ออย่างอื่น ทั้งหมดนี้ทำงานได้อย่างสมบูรณ์บนเครื่องที่ build มัน และล้มเหลวบนเครื่องแรกที่
ไม่ได้ build environment สำหรับพัฒนาของคุณคือที่เดียวในโลกที่ตรวจจับ bug ประเภทนี้ไม่ได้

ดังนั้นให้สร้าง venv ที่ไม่มีอะไรอยู่ในนั้น ติดตั้ง wheel ด้วยพาธของมัน แล้วลองขับดู

```bash

./fresh/bin/pip install dist/agentpath-0.3.0-py3-none-any.whl
./fresh/bin/agentpath --help
```

บน Windows สคริปต์จะอยู่ใน `fresh/Scripts/` แทน `fresh/bin/` ซึ่งเป็นที่ที่การรันของบทนี้ถูกเก็บมา

```text
usage: agentpath [-h] {chat,run,eval,resume} ...

positional arguments:
  {chat,run,eval,resume}
    chat                Talk to an agent in the terminal
    run                 Do one task and exit
    eval                Run a file of tasks and report which ones passed
    resume              Continue a saved session, or list sessions when given
                        no name

options:
  -h, --help            show this help message and exit
```

สี่อย่างถูกพิสูจน์ด้วยคำสั่งเดียวนั้น และไม่มีอย่างไหนถูกพิสูจน์โดยการ build wheel ติดตั้งได้ entry

แก้ไขได้จากสิ่งที่อยู่ใน wheel บวกกับ dependency ที่ประกาศไว้หนึ่งตัว เพราะไม่มีอะไรอย่างอื่นใน
environment นั้นให้พวกมันไปหา

ไปไกลอีกขั้นแล้วรันมันจริง ๆ กับ model ของคุณ หรือกับ mock server ของโปรเจกต์ `--help` พิสูจน์ว่า
package import ได้ มันไม่ได้พิสูจน์ว่า package ทำงานได้

ลำดับคือประเด็นทั้งหมด การเผยแพร่เป็นทางเดียว หมายเลขเวอร์ชันบน package index นำกลับมาใช้ซ้ำไม่ได้

`0.3.0` ที่พังจึงไม่ใช่สิ่งที่คุณแก้ มันคือสิ่งที่คุณแทนที่ด้วย `0.3.1` ในขณะที่ตัวที่พังยังมองเห็นได้ตลอด
ไป สิบนาทีใน virtual environment ใหม่ ๆ ซื้อความสามารถที่จะไม่ต้องทำแบบนั้นเลยให้คุณ

### การเผยแพร่ต้องมีบัญชีและ token

ตัวการอัปโหลดเองเป็นส่วนที่สั้น

```bash
python -m twine upload dist/*
```

สามอย่างต้องเป็นจริงก่อน

คุณต้องมีบัญชีบน package index และคุณควรมีบัญชีบน TestPyPI ด้วย ซึ่งเป็นบริการแยกต่างหากที่มีบัญชี
แยกต่างหาก และมีอยู่เพื่อให้การอัปโหลดครั้งแรกในชีวิตของคุณผิดพลาดได้พอดี อัปโหลดที่นั่น ติดตั้งจาก
ที่นั่นลง environment ใหม่ แล้วค่อยทำของจริง

คุณต้องมี API token แทนรหัสผ่าน สร้างมันในหน้าตั้งค่าบัญชีของคุณ จำกัดขอบเขตให้อยู่แค่โปรเจกต์เดียว
ถ้าโปรเจกต์นั้นมีอยู่แล้ว แล้วใช้ `__token__` เป็นชื่อผู้ใช้โดยมี token เป็นรหัสผ่าน เหตุผลที่ควรเลือก
token คือมันถูกเพิกถอนได้ด้วยตัวมันเองโดยไม่ต้องเปลี่ยนรหัสผ่านของคุณ และ token ที่จำกัดขอบเขตไว้ที่
โปรเจกต์เดียวถ้าหลุดออกไปก็แตะอย่างอื่นที่คุณเป็นเจ้าของไม่ได้ เก็บมันไว้ใน `~/.pypirc` โดยตั้งสิทธิ์ให้
เข้มงวด หรือใน environment variable หรือในที่เก็บความลับของ continuous integration ของคุณ อย่าใส่
มันไว้ใน repository token ที่ถูก commit ไปครั้งหนึ่งคือ token ที่ต้องถูกเพิกถอน เพราะการลบ commit
นั้นไม่ได้ลบมันออกจาก clone ของใครเลย

และคุณต้องมี two factor authentication บนบัญชี ซึ่งตอนนี้ index บังคับสำหรับทุกคนที่เผยแพร่

### MCP over HTTP

บทที่ 19 สร้าง client ที่พูดได้แค่ stdio client เริ่ม server เป็นโปรเซสลูกแล้วคุย JSON-RPC ผ่านท่อของ
มัน ดังนั้นทุก server ที่คุณใช้ได้คือโปรแกรมบนเครื่องของคุณเองที่คุณเป็นคนเปิดขึ้นมา

**มันให้อะไร** server ที่คุณไม่ได้เปิดและไม่ได้โฮสต์ ทีมหนึ่งรัน server ตัวเดียวสำหรับระบบภายในของ
ตัวเอง แล้ว agent ทุกตัวในบริษัทเชื่อมต่อไปยัง URL เดียวกันได้ มันยังยกเลิกข้อกำหนดที่ว่า server ต้อง
ติดตั้งได้บนเครื่องของคุณด้วย ซึ่งสำคัญทันทีที่ server ต้องการข้อมูลรับรองหรือการเชื่อมต่อฐานข้อมูลที่
คุณไม่มีในเครื่อง

**มันมีต้นทุนอะไร** ทุกอย่างที่เคยฟรีตอนเป็นโปรเซสลูกจะเลิกฟรี ท่อไปยังโปรเซสที่คุณเปิดเองไม่ต้องมี
authentication เพราะระบบปฏิบัติการตัดสินไปแล้วว่าคุณรันมันได้ HTTP endpoint ต้องมี authentication
ซึ่งหมายถึง token ซึ่งหมายถึงการเก็บและการหมุน token โปรเซสลูกตายพร้อมคุณ จึงไม่มีอายุ session ให้
จัดการ server ระยะไกลไม่ตาย ดังนั้น transport จึงต้องจัดการการเชื่อมต่อใหม่และ event ที่ server ส่ง
แบบสตรีม และเรื่องความไว้วางใจก็เปลี่ยนรูปร่างไปทั้งหมด server ในเครื่องรันในฐานะคุณ กับไฟล์ของคุณ
server ระยะไกลคือโค้ดของคนอื่นที่ถือ request ของคุณไว้ และทุกคำอธิบาย tool ที่มันส่งมาให้คุณจะเข้าไป
ใน context ของ model ของคุณตรง ๆ ซึ่งเป็นพื้นผิวสำหรับ prompt injection ที่บุคคลที่สามเป็นเจ้าของ

### Async

ทั้งโปรเจกต์เป็นแบบ synchronous อย่างจงใจ `fanout.py` บอกเหตุผลไว้ในย่อหน้าเปิดของมัน

```text
Threads rather than async, for the same reason the rest of the project is
synchronous. An agent run spends nearly all of its life waiting on a socket,
which is the case threads handle well, and async would put a second mental
model in front of a reader who came here to learn about agents.
```

**มันให้อะไร** การรัน agent พร้อมกันหลักพันในโปรเซสเดียวแทนที่จะเป็นหลักสิบ ถ้าคุณกำลังสร้างบริการ
ที่ผู้ใช้จำนวนมากใช้เครื่องเดียวร่วมกัน นี่ไม่ใช่ความชอบ มันคือการออกแบบเดียวที่ใช้ได้ เพราะ thread
หนึ่งตัวกินสแตกเป็นเมกะไบต์ ส่วน coroutine ที่รออยู่กินแค่กิโลไบต์

**มันมีต้นทุนอะไร** มันติดต่อกันได้ `async def` ที่ก้นหมายถึง `await` ไล่ขึ้นไปตลอดทาง ดังนั้น
provider ลูป ทุก tool ตัว MCP client และ CLI ก็เปลี่ยนหมด คุณทำครึ่ง ๆ กลาง ๆ ไม่ได้ และการเรียก
แบบ synchronous ที่หลงเหลืออยู่ตรงกลางจะบล็อก event loop ทั้งตัวและสร้าง bug ด้านประสิทธิภาพที่ดู
เหมือนปัญหาเครือข่าย บันทึกในไฟล์ไอเดียเพิ่มเงื่อนไขที่สำคัญสำหรับโปรเจกต์นี้ไว้ ถ้าจะทำมันสักวัน มัน
ต้องถูกให้เหตุผลด้วยสิ่งที่มันสอน ไม่ใช่ด้วยความเร็ว เพราะผู้อ่านมาเพื่อเรียนว่า agent ทำงานอย่างไร
และ event loop เป็นอีกหัวข้อหนึ่ง

## 7. สิ่งที่คอร์สนี้ไม่ได้ครอบคลุม และเพราะอะไร

สี่หัวข้อที่คนคาดว่าจะเจอในสิ่งที่เรียกว่าคอร์สเรื่อง AI agent และไม่มีอยู่ที่นี่ ไม่มีข้อไหนถูกตัดออกเพราะ
มันไม่สำคัญ พวกมันถูกตัดออกเพราะ harness เป็นสิ่งที่เฉพาะเจาะจง และสิ่งเหล่านี้ไม่ใช่มัน และคอร์สที่
ครอบคลุมทุกอย่างที่อยู่ข้างเคียงหัวข้อของตัวเองจะครอบคลุมหัวข้อของตัวเองได้ไม่ดี

**Fine tuning** การเอา base model มาแล้วฝึกต่อด้วยตัวอย่างของคุณเอง เพื่อให้มันทำตัวต่างออกไปโดย
ค่าเริ่มต้น มันเป็นเทคนิคจริงที่มีการใช้งานจริง ส่วนใหญ่คือการบีบ model ให้แคบลงมาที่รูปแบบหรือโดเมน
ที่เฉพาะเจาะจง มันไม่อยู่ที่นี่เพราะมันเปลี่ยนสิ่งที่อยู่หลัง endpoint และทุกอย่างในคอร์สนี้อยู่หน้ามัน ทุก
การตัดสินใจด้านการออกแบบตรงนี้ยังคงเป็นจริงไม่ว่า model ตัวไหนจะเป็นคนตอบ ซึ่งเป็นสิ่งที่ provider
abstraction ในบทที่ 06 มีไว้เพื่อการนั้น อีกอย่าง และในทางปฏิบัติมากกว่า มันคือเครื่องมือแรกที่ผิด แทบ
ทุกปัญหาที่คนเอื้อมไปหา fine tuning เพื่อแก้ กลายเป็นปัญหาของ prompt ปัญหาของคำอธิบาย tool หรือ
ปัญหาของ context และบทที่ 22 มีอยู่เพื่อให้คุณบอกได้ว่าคุณมีปัญหาแบบไหนก่อนจะเสียเงินไปค้นหา
คำตอบ

**Training** การสร้าง model นี่เป็นสาขาที่ต่างออกไปพร้อมข้อกำหนดเบื้องต้นที่ต่างกัน คณิตศาสตร์ที่
ต่างกัน และฮาร์ดแวร์ที่ต่างกัน และมันแทบไม่มีงานวิศวกรรมร่วมกับหัวข้อของคอร์สนี้เลย เอกสารออกแบบ
บอกไว้ในหัวข้อเปิดว่าที่นี่ไม่มีคณิตศาสตร์ และนั่นเป็นคำสัญญาว่าคอร์สนี้เขียนเพื่อใคร มากกว่าจะเป็นคำ
กล่าวว่าอะไรคุ้มค่าแก่การรู้

**การปรับ prompt ให้เหมาะที่สุดในระดับใหญ่** การค้นหาแบบอัตโนมัติเหนือ prompt หลายรูปแบบ ที่
โปรแกรมสร้างตัวเลือกขึ้นมา ให้คะแนนกับชุดข้อมูล แล้วเก็บตัวที่ชนะไว้ บทที่ 22 สร้างรากฐานที่สิ่งนี้ต้อง

ค้นหาที่วางอยู่บนนั้น มันอยู่นอกขอบเขตเพราะมันเป็นหัวข้อวิจัยที่พรมแดนยังขยับอยู่ และเพราะมันต้องใช้

จะรู้พอดีว่าคุณต้องการอะไรจากมัน

## 8. จะเรียนรู้ต่อจากนี้อย่างไร

สามอย่าง ตามลำดับ พวกมันเป็นรูปธรรมอย่างจงใจ เพราะคำแนะนำกว้าง ๆ ว่าให้สร้างต่อไปเรื่อย ๆ นั้นไม่มี
ค่าอะไรเลย

### อ่านซอร์สของ harness ที่คุณใช้งานจริง

เลือกเครื่องมือ agent ที่คุณใช้อยู่ทุกวันแล้วอ่านซอร์สของมัน หรืออ่าน protocol ของมันถ้าซอร์สปิดอยู่
ไม่ใช่บทเรียนเกี่ยวกับมัน แต่เป็นตัวโค้ด

ตอนนี้คุณอยู่ในตำแหน่งที่ไม่ธรรมดาที่ทำแบบนั้นได้อย่างมีประโยชน์ ซึ่งเมื่อยี่สิบสามบทก่อนคุณทำไม่ได้
คุณรู้ว่าต้องมองหาอะไร เพราะคุณรู้ว่าชิ้นส่วนต่าง ๆ เรียกว่าอะไรและการตัดสินใจที่ยากคืออะไร หาลูปให้
เจอ หาว่า permissions อยู่ที่ไหนและมันตัดสินใจหรือลงมือรัน หาว่า session ถูกเขียนตอนที่มันเกิดขึ้นหรือ
ถูกพักไว้ในบัฟเฟอร์ หาว่ามันทำอะไรเมื่อ context window เต็ม หาว่าการ retry ของมันล้อมการเรียกผ่าน
เครือข่ายหรือล้อมอะไรที่กว้างกว่านั้น

ทุกข้อในนั้นคือคำถามที่คุณตอบไปแล้วครั้งหนึ่ง ส่วนที่น่าสนใจจึงเป็นตรงที่คำตอบของพวกเขาต่างจากของ
คุณ บางครั้งเป็นเพราะพวกเขาผิด บ่อยกว่านั้นเป็นเพราะพวกเขามีข้อจำกัดที่คุณไม่มี และการหาให้เจอว่า
ข้อจำกัดนั้นคืออะไรคือทางที่เร็วที่สุดที่จะเรียนรู้สิ่งที่คุณคิดเองไม่ได้

เริ่มจาก schema ของ tool เพราะมันเป็นสิ่งที่ดึงออกมาง่ายที่สุดและเปิดเผยมากที่สุด harness ทุกตัวส่ง
คำอธิบาย tool ของมันไปให้ model ในทุก request พวกมันจึงมองเห็นได้จากข้างนอก และการอ่านคำ
อธิบาย tool ของใครสักคนคือการอ่านทฤษฎีทั้งหมดของเขาว่า model ควรทำตัวอย่างไร

### เขียน eval suite สำหรับงานที่คุณใส่ใจ

บทที่ 22 มอบเครื่องจักรให้คุณแล้ว เอามันไปใช้กับอะไรที่เป็นจริง และเริ่มให้เล็กกว่าที่รู้สึกว่าจริงจัง งาน
สิบงานจากงานของคุณเอง แต่ละงานมีการตรวจสอบเชิงกลไกที่คืนค่าจริงหรือเท็จ

จากนั้นใช้มันตอบคำถามหนึ่งข้อที่ตอนนี้คุณมีความเห็นอยู่แล้ว model ที่ถูกกว่าทำงานนี้ได้จริงหรือเปล่า
ประโยคที่คุณเพิ่มลงใน system prompt ช่วยหรือเปล่า การเพิ่มงบประมาณเปลี่ยนอะไรบ้างหรือเปล่า

นิสัยที่สิ่งนี้สร้างขึ้นมีค่ามากกว่าคำตอบข้อไหน ๆ และมันถ่ายโอนไปยังทุกอย่างที่คุณจะสร้างต่อไปที่มี
model อยู่ในนั้น `evals.py` พูดไว้ตรง ๆ ใน docstring ของมันเอง

```text
Everything before this chapter was built on the assumption that you can tell
a good change from a bad one by looking at it. You cannot. A wording change
in a system prompt can fix one task and quietly break three others, and the
only way to know is to run a set of tasks before and after.
```

คาดหวังได้เลยว่าผลลัพธ์แรกจะทำให้อึดอัด ผลลัพธ์ที่พบบ่อยที่สุดของ eval suite ชุดแรกคือการค้นพบว่า
การเปลี่ยนแปลงที่คุณมั่นใจสุด ๆ นั้นไม่ได้ทำอะไรเลย และนั่นคือชุดทดสอบที่ทำงานได้

### สร้าง tool หนึ่งตัวสำหรับสิ่งที่คุณทำด้วยมือทุกสัปดาห์

ไม่ใช่โปรเจกต์ tool ตัวเดียว ฟังก์ชันหนึ่งตัวพร้อม JSON schema และรายการ dispatch ในรูปแบบที่คุณ
เขียนมาแล้วแปดครั้ง

เลือกมันด้วยเกณฑ์ที่น่าเบื่อแทนที่จะเป็นเกณฑ์ที่น่าสนใจ อะไรที่คุณทำทุกสัปดาห์จริง ๆ ที่คุณเบื่อมันแล้ว
และที่ส่วนใหญ่เป็นการอ่านและแปลงข้อมูลมากกว่าการตัดสินใจ การ query ฐานข้อมูลของคุณเอง การดึง
สถานะปัจจุบันของ ticket ของคุณ การตรวจว่าบริการตัวไหนของคุณยังใช้เวอร์ชันเก่า อันที่น่าเบื่อคืออันที่ถูก
ต้อง เพราะคุณจะสังเกตได้ทันทีว่าเวอร์ชันที่เป็น agent ดีกว่าจริงหรือไม่ และไม่มีครูที่ดีไปกว่าการใช้
เครื่องมือของคุณเองในบ่ายวันอังคารตอนที่คุณกำลังยุ่ง

สามอย่างจะเกิดขึ้น และทั้งสามอย่างคือประเด็น

คุณจะพบว่าการเขียน tool นั้นง่ายและการเขียนคำอธิบายนั้นยาก ซึ่งคือบทที่ 10 ที่มาถึงในฐานะประสบการณ์
แทนที่จะเป็นข้ออ้าง คุณจะพบว่าเวอร์ชันแรกคืนค่ากลับมามากเกินไป และการตัดทอนสิ่งที่ tool คืนกลับมา
คืองานส่วนใหญ่ ซึ่งคือบทที่ 15 และคุณจะได้รู้ว่ารอยต่อนั้นอยู่ได้หรือไม่ในโค้ดเบสที่คุณไม่ได้ออกแบบมา
เป็นตัวอย่างเพื่อการสอน ซึ่งคือหัวข้อ 3 ที่ได้รับการทดสอบอย่างซื่อสัตย์ครั้งแรก

ถ้าปรากฏว่ามีคนเผยแพร่ MCP server สำหรับระบบนั้นไว้แล้ว ก็เชื่อมต่อมันด้วยบทที่ 19 แทนแล้วไม่ต้อง
เขียนอะไรเลย การรู้ว่าคุณอยู่ในสถานการณ์ไหนใน 2 อย่างนี้ก็เป็นสิ่งที่ตอนนี้คุณทำได้แล้ว

## 9. บันทึกปิดท้าย

ยี่สิบสี่บทที่แล้ว คุณส่ง HTTP request หนึ่งครั้งที่มีรายการข้อความอยู่ในนั้น

ตอนนี้คุณสร้างสิ่งที่ยืนล้อมรอบ model และทำให้มันมีประโยชน์ได้แล้ว ลูปที่เรียก tool จนกว่างานจะเสร็จ
ประตูที่ตัดสินว่าอะไรรันได้ บันทึกบนดิสก์ที่คุณอ่านย้อนหลังได้ การตัดทอนที่ไม่ทำให้บันทึกนั้นเสียหาย
การนับว่ามันมีค่าใช้จ่ายเท่าไร การ retry ที่ไม่ทำซ้ำสิ่งที่ต้องไม่ถูกทำซ้ำ การขัดจังหวะที่หยุดงาน
protocol สำหรับ tool ที่คุณไม่ได้เขียน agent ที่เริ่ม agent ตัวอื่น หลายตัวที่รันพร้อมกัน และวิธีวัดว่า
การเปลี่ยนแปลงใด ๆ ที่คุณทำเป็นการปรับปรุงให้ดีขึ้นหรือไม่

ไม่มีอะไรในนั้นมาจาก model เลย ทุกส่วนของมันคืองานวิศวกรรมธรรมดา และลูปที่อยู่ตรงกลางของมันคือ
ห้าสิบบรรทัดที่ไม่ได้เปลี่ยนรูปร่างเลยตั้งแต่บทที่ 04 model เป็นส่วนที่คนอื่นสร้างมาให้เสมอ

ส่วนที่น่าสนใจไม่เคยเป็น model มันคือทุกอย่างที่คุณต้องเอาไปวางล้อมรอบมันต่างหาก
