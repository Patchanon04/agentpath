## 1. คำถามที่ทุกคนถาม

agent ของผมควรใช้ RAG ไหม

คำตอบที่ตรงไปตรงมา ในกรณีส่วนใหญ่ คือไม่ ไม่ใช่เพราะ retrieval augmented
generation เป็นเทคนิคที่แย่ และไม่ใช่เพราะคนที่สร้างมันคิดผิด
มันเป็นเทคนิคที่ดีที่แก้ปัญหาจริง และหัวข้อ 7 ก็พูดแบบนั้นชัดเจน
คำตอบคือไม่ในกรณีส่วนใหญ่เพราะส่วนใหญ่แล้วมีทางเลือกที่ง่ายกว่าสามอย่างที่เหมาะกว่า
และคนที่ถามยังไม่ได้ตรวจสอบมันเลย

นั่นคือความล้มเหลวที่แท้จริง ไม่มีใครนั่งลง ประเมิน vector database
เทียบกับการค้นหาข้อความธรรมดา แล้วเลือก vector database ผิดพลาด
สิ่งที่เกิดขึ้นจริงคือคำว่า retrieval และ vector database
กลายเป็นคำเดียวกันในหัวคนส่วนใหญ่ ทางเลือกสามอย่างแรกจึงไม่เคยถูกพิจารณาเลย
คำถามที่ว่า ผมจะเอาเอกสารของผมไปวางต่อหน้า model ได้อย่างไร มาถึงพร้อมคำตอบสำเร็จรูปแล้ว

บทนี้จึงทำสองอย่าง

อย่างแรกคือขั้นตอนการตัดสินใจ สี่คำถาม ถามตามลำดับ และหยุดที่คำว่าใช่ครั้งแรก
ใช้เวลาประมาณสองนาที และเป็นส่วนที่มีค่าที่สุดของบทนี้ หัวข้อ 2 คือส่วนนั้น

อย่างที่สองคือ retrieval tool ที่ใช้งานได้จริง สร้างให้เล็ก
เพื่อให้คุณเห็นว่าไม่มีเวทมนตร์อะไรในนั้น หัวข้อ 3 ถึง 8 สร้างและปกป้อง `search_notes`
ซึ่งอ่านโฟลเดอร์ของเอกสาร ให้คะแนนทุกย่อหน้าเทียบกับคำถาม
และคืนย่อหน้าที่ดีที่สุดไม่กี่อันพร้อมไฟล์และบรรทัดที่มันมา มันทำงานได้จริง
มันมีประโยชน์จริง และการให้คะแนนข้างในเป็นเลขคณิตประมาณยี่สิบบรรทัด
ที่คุณจะเข้าใจทั้งหมดเมื่อจบหัวข้อ 4

ครึ่งหลังนั้นสำคัญกว่าที่เห็น เทคนิคที่คุณยังไม่เคยลงมือทำคือเทคนิคที่คุณตัดสินไม่ได้
และการที่ retrieval เป็นกล่องที่ไม่เคยถูกเปิด คือเหตุผลตรง ๆ ที่สี่คำถามถูกข้ามไป
เมื่อคุณเขียนการให้คะแนนด้วยตัวเอง เห็นมันทำงาน และเห็นชัดว่ามันพังตรงไหน
คำนี้จะสูญเสียอำนาจของมันและกลายเป็นสิ่งที่มันเป็นมาตลอด
นั่นคือวิธีหนึ่งในการหยิบบางย่อหน้าออกมาจากบางไฟล์

บทนี้ไม่ใช่การโจมตี embeddings หัวข้อ 7
เป็นการเล่าอย่างซื่อสัตย์ถึงสิ่งเดียวที่เวอร์ชันของเราทำไม่ได้และ embeddings ทำได้ดี
และมันเป็นช่องว่างจริง ไม่ใช่การยอมรับพอเป็นพิธี
สิ่งที่บทนี้คัดค้านคือการคว้าอะไรก็ตามมาใช้ก่อนที่คุณจะถามว่าคุณต้องการมันจริงไหม

## 2. สี่คำถามตามลำดับ และหยุดที่คำว่าใช่ครั้งแรก

นี่คือขั้นตอน อ่านหนึ่งรอบตอนนี้ แล้วค่อยอ่านสี่หัวข้อย่อยที่อธิบายแต่ละคำตอบ

| คำถาม | ถ้าใช่ |
| --- | --- |
| ข้อมูลเล็กพอจะใส่ลงใน context window ได้ไหม | ใส่ลงไปเลย ไม่ต้องสร้างอะไร |
| ข้อมูลมีโครงสร้างไหม และคุณรู้ไหมว่ากำลังถามอะไร | เขียน query ใช้ SQL หรือเรียก API |
| เป็นข้อความที่ agent เดินสำรวจเองได้ไหม | ให้ glob และ grep กับมัน นั่นคือบทที่ 09 |
| ไม่ใช่ทั้งหมดข้างต้น | ตอนนี้ vector search จึงคุ้มค่ากับที่ทางของมัน |

ลำดับไม่ได้มีไว้ประดับ แต่ละคำถามตอบว่าใช่แล้วถูกกว่าคำถามที่อยู่ถัดลงไป
ทั้งในแง่เวลาสร้าง ต้นทุนการรัน และจำนวนวิธีที่มันจะพังตอนตีสาม
และในทางปฏิบัติคำถามเหล่านี้แยกขาดจากกัน
นั่นคือเหตุผลที่คุณหยุดที่คำว่าใช่ครั้งแรกแทนที่จะไปเก็บความเห็นจากทั้งสี่ข้อ

ความผิดพลาดที่พบบ่อยที่สุดในเรื่องทั้งหมดนี้คือการกระโดดไปที่คำตอบที่สี่
ทั้งที่หนึ่งในสามคำตอบแรกใช้ได้ ผลของความผิดพลาดนั้นถูกจ่ายทีหลังและโดยคนอื่น
พูดประโยคนี้กับตัวเองอีกครั้งก่อนอ่านต่อ
เพราะที่เหลือของหัวข้อนี้เป็นเพียงการขยายความสี่แบบของประโยคนั้น

### คำถามที่หนึ่ง ข้อมูลเล็กพอจะใส่ลงใน context window ได้ไหม

ถ้าใช่ ใส่มันลงใน context window แล้วไม่ต้องสร้างอะไรเลย

ฟังดูชัดเจนเกินกว่าจะควรมีหัวข้อของตัวเอง และมันคือขั้นตอนที่ถูกข้ามบ่อยที่สุดในรายการ
เหตุผลคือคำตอบเปลี่ยนไปแล้วแต่สัญชาตญาณของคนยังไม่เปลี่ยน retrieval augmented
generation ถูกออกแบบตอนที่ context window ขนาดใหญ่คือสี่พัน token
สี่พัน token คือประมาณสามพันคำ ซึ่งเท่ากับหกหน้า ภายใต้ข้อจำกัดนั้นแทบไม่มีอะไรใส่ได้
retrieval จึงไม่ใช่การปรับให้ดีขึ้น มันคือทางเดียว

model ทุกวันนี้รับได้แสน token หรือมากกว่าเป็นเรื่องปกติ และหลายตัวรับได้ถึงล้าน
แสน token คือประมาณเจ็ดหมื่นห้าพันคำ ซึ่งเท่ากับหนังสือสามร้อยหน้า
เอกสารผลิตภัณฑ์ของคุณน่าจะเล็กกว่านั้น API reference ของคุณน่าจะเล็กกว่านั้น
คู่มือพนักงาน style guide คลัง support macro ทั้งหมด
และ schema ของฐานข้อมูลพร้อมคอมเมนต์ แทบจะแน่นอนว่าเล็กกว่า

วัดของคุณเองก่อนจะสมมติ นี่คือการวัดทั้งหมด

```bash
cat docs/*.md | wc -c
```

```text
  138204
```

หารด้วยสี่เพื่อประมาณจำนวน token คร่าว ๆ จะได้ราวสามหมื่นห้าพัน
ซึ่งใส่ได้สบายและยังเหลือที่ในทุก model ที่คุณน่าจะใช้อยู่
สถาปัตยกรรมที่ถูกต้องจึงคืออ่านไฟล์แล้วใส่ลงใน system prompt

ทีนี้ลองนับดูว่านั่นช่วยคุณประหยัดอะไรบ้าง ไม่มีกลยุทธ์การทำ chunking
และไม่มีการถกเถียงเรื่องขนาด chunk ไม่มี embedding model และไม่มี provider
ที่สองที่ต้องเก็บ API key ไว้ ไม่มี vector store ที่ต้องรัน สำรอง หรืออัปเกรด
ไม่มีขั้นตอนสร้าง index ตอน deploy ไม่มีปัญหาข้อมูลเก่าค้าง
เพราะไม่มีอะไรที่จะเก่าได้ ไม่มีปัญหาคุณภาพของ retrieval เพราะไม่มีอะไรถูกคัดเลือก
จึงไม่มีอะไรถูกทิ้งไปโดยพลาด และไม่มี bug ประเภทที่คำตอบอยู่ในเอกสารของคุณ
แต่ระบบไม่ได้ดึงมันมา ซึ่งเป็นโหมดความล้มเหลวที่น่าหงุดหงิดที่สุดของระบบ retrieval
พอดีเพราะว่ามันเงียบ

บทที่ 15 ให้เหตุผลเพิ่มว่าทำไมควรเลือกทางนี้
เนื้อหาที่ไม่เปลี่ยนระหว่าง request สามารถ cache ได้ และ prompt cache
ทำให้การส่งบล็อกใหญ่ที่นิ่งซ้ำ ๆ ถูกมาก เอกสารคือบล็อกที่เหมาะกับการ cache ที่สุด
เนื้อหาที่นิ่งมาก่อน เนื้อหาที่เปลี่ยนมาทีหลัง
และคู่มือสามหมื่นห้าพัน token ที่นั่งอยู่หน้าสุดของทุก request
มีต้นทุนเพียงเศษเสี้ยวของราคาหน้าตั๋ว

ข้อควรระวังที่ตรงไปตรงมาคือวิธีนี้จะเลิกใช้ได้ผล และมันเลิกได้ผลสองแบบไม่ใช่แบบเดียว
แบบที่ชัดเจนคือข้อมูลโตเกิน window แบบที่ไม่ชัดเจนคือ model
แย่ลงอย่างวัดได้ในการใช้ context ที่ยาวมาก ก่อนที่มันจะปฏิเสธเสียอีก
ข้อเท็จจริงที่ฝังอยู่กลางแปดหมื่น token ถูกค้นเจอได้น่าเชื่อถือน้อยกว่าข้อเท็จจริงเดียวกัน
ในแปดพัน token ดังนั้นคำว่า มันใส่ได้ ยังไม่ใช่บททดสอบที่ถูก
บททดสอบคือ มันใส่ได้และยังเหลือที่ และ model ยังหาของเจอในนั้น
และคุณตรวจครึ่งหลังด้วยการลองจริง

แต่ลองเถอะ มันเสียเวลาแค่บ่ายเดียว มันไม่ได้ผลก็ได้ผล และถ้าได้ผล คุณก็เสร็จแล้ว

### คำถามที่สอง ข้อมูลมีโครงสร้างไหม และคุณรู้ไหมว่ากำลังถามอะไร

ถ้าคำตอบคือใช่ ให้เขียน query นี่คือคำถามที่พลาดแล้วแพงที่สุด มันจึงได้พื้นที่มากที่สุด

โครงสร้างหมายความว่าข้อมูลรู้อยู่แล้วว่าส่วนต่าง ๆ ของตัวเองคืออะไร ตารางฐานข้อมูล
รู้ว่าคอลัมน์ไหนคือลูกค้าและคอลัมน์ไหนคือจำนวนเงิน JSON API รู้ว่า field ไหนคือวันที่
สเปรดชีตรู้จักคอลัมน์ของมัน โครงสร้างนั้นถูกใส่ไว้โดยคนที่เข้าใจโดเมน
และมันคือ index ที่ใช้งานได้ซึ่งมีคนอื่นจ่ายค่าทำไว้ให้แล้ว

ทีนี้นี่คือตัวอย่างที่ควรจำ

```text
Which customers spent more than five hundred pounds last month
```

นั่นคือ query มันไม่ใช่ similarity search และความต่างไม่ใช่เรื่องสำนวน

ดูว่ามันขออะไรจริง ๆ การเปรียบเทียบ ซึ่งคือจำนวนเงินมากกว่าห้าร้อย การรวมยอด
ซึ่งคือผลรวมคำสั่งซื้อของลูกค้าคนหนึ่งไม่ใช่คำสั่งซื้อเดียว และการกรองช่วงวันที่
ซึ่งต้องรู้ว่าวันนี้คือวันอะไรและขอบเขตของเดือนที่แล้วอยู่ตรงไหน
ไม่มีสักอย่างในสามอย่างนั้นที่เป็น operation กับข้อความ
ไม่มีการเรียบเรียงคำถามแบบไหนที่ทำให้มันกลายเป็นเรื่องว่าประโยคไหนคล้ายประโยคไหน

มันคือ SQL สิบสี่คำ

```sql
SELECT customer_id, SUM(amount) AS total
FROM orders
WHERE created_at >= '2026-08-01' AND created_at < '2026-09-01'
GROUP BY customer_id
HAVING SUM(amount) > 500;
```

นั่นคืนคำตอบที่ถูก ถูกเป๊ะ ทุกแถวที่เข้าเกณฑ์และไม่มีแถวที่ไม่เข้าเกณฑ์
คำนวณจากข้อมูลตามที่มันเป็นอยู่ ณ ขณะนี้ มันตรวจสอบได้
ในแง่ที่ใครสักคนอ่าน query แล้วยืนยันได้ว่ามันหมายถึงสิ่งที่คำถามหมายถึง มันทดสอบได้
มันใช้เวลาไม่กี่มิลลิวินาที และมันพิสูจน์ได้ว่าครบถ้วน
ซึ่งเป็นคุณสมบัติที่ similarity search ไม่เคยมี

ทีนี้ดูว่า vector search ทำอะไรกับคำถามเดียวกัน เพราะนี่คือส่วนที่ควรเข้าใจให้ดี

คุณ embed ประโยค which customers spent more than five hundred pounds last month
คุณได้ chunk ที่ embedding ของมันอยู่ใกล้ประโยคนั้นที่สุดกลับมา chunk เหล่านั้นจะเกี่ยวกับลูกค้า
เกี่ยวกับการใช้จ่าย เกี่ยวกับจำนวนเงิน เป็นไปได้มากว่าเกี่ยวกับเกณฑ์และเกี่ยวกับเดือน
มันจะดีเยี่ยมในเชิงหัวข้อ และมันจะเป็นแถวที่ผิด
เพราะความใกล้ใน embedding space คือการวัดว่าข้อความชิ้นหนึ่งเกี่ยวกับอะไร
และคำถามนี้ไม่ได้เกี่ยวกับหัวข้อ ห้าร้อยกับสี่ร้อยแปดสิบใกล้กันในเชิงความหมาย
และห่างกันมากในเชิงข้อเท็จจริง vector index ไม่มีเลขคณิตอยู่ในนั้น
มันบวกเลขสองตัวไม่ได้ มันจึงรวมยอดไม่ได้ มันไม่รู้เลยว่าเดือนไหนมีวันนี้อยู่

และนี่คือเหตุผลว่าทำไมสิ่งนี้แย่กว่าความล้มเหลวธรรมดา มันไม่ได้คืนค่าว่าง
มันคืนห้าย่อหน้าเกี่ยวกับการใช้จ่ายของลูกค้า model อ่านมัน
แล้ว model ก็เขียนย่อหน้าที่มั่นใจซึ่งระบุชื่อลูกค้าสามราย บางรายอาจถูกด้วยซ้ำ
ไม่มีอะไรในผลลัพธ์ถูกทำเครื่องหมายว่าเป็นการเดา

และวิธีเดียวที่จะจับได้คือคุณต้องรู้คำตอบอยู่แล้ว

บททดสอบของคำถามที่สองจึงมีสองอนุประโยคและคุณต้องได้ทั้งคู่ ข้อมูลมีโครงสร้างไหม

การถามมันตรง ๆ ย่อมดีกว่าการถามอะไรที่คล้องจองกับมันเสมอ

มีเวอร์ชันหนึ่งของเรื่องนี้ที่มีประโยชน์จริงและควรเรียกชื่อมันไว้เพื่อไม่ให้สับสน

model แปลงประโยคเป็น argument และฐานข้อมูลทำส่วนที่ฐานข้อมูลถนัด
นั่นเป็นสถาปัตยกรรมคนละแบบกับ retrieval และมักเป็นแบบที่ถูกต้องสำหรับอะไรก็ตามที่มี schema
สิ่งที่ไม่ถูกคือการดึงข้อความเกี่ยวกับข้อมูลมาแล้วหวังว่า model จะคำนวณจากมันได้

### คำถามที่สาม เป็นข้อความที่ agent เดินสำรวจเองได้ไหม

ถ้า corpus คือ code หรืออะไรก็ตามที่คำในคำถามเป็นคำเดียวกับที่ปรากฏในเป้าหมาย

`parse_arguments` ถูกเรียกว่า `parse_arguments` ทั้งในที่นิยามและทุกจุดที่เรียกใช้
การค้นหาสตริงนั้นจึงเจอทั้งหมดและไม่เจออย่างอื่น ภาษาโปรแกรมไม่มีคำพ้องความหมาย
และ compiler บังคับเรื่องนั้นเข้มงวดกว่าที่ embedding model ใด ๆ จะประมาณได้มาก

มีสองอย่างจากบทที่ 09 ที่ควรยกมาใช้ในบทนี้เป็นพิเศษ

และจุดประสงค์ทั้งหมดของ agent คือการแก้ไฟล์ grep ไม่มี index มันจึงเก่าไม่ได้
มันอ่านไฟล์ที่ agent เพิ่งเขียนเมื่อมิลลิวินาทีที่แล้ว

อย่างที่สองคืออย่างที่ใช้ได้กว้างที่สุด similarity search คือการยิงครั้งเดียว
คุณ embed คุณได้สิบ chunk นั่นคือคำตอบของคุณ agent loop ไม่ใช่การยิงครั้งเดียว
มันค้น อ่านสิ่งที่ได้กลับมา แล้วค้นใหม่ด้วยสิ่งที่มันเพิ่งเรียนรู้
และแต่ละก้าวถูกเลือกเพราะผลของก้าวก่อนหน้า tool หยาบ ๆ สองตัวใน loop
ที่กลับมาปรับปรุงได้ชนะ tool ฉลาดตัวเดียวที่มีโอกาสลองครั้งเดียว จำความคิดนี้ไว้
เพราะหัวข้อ 8 พูดถึงความหมายของมันต่อสิ่งที่เรากำลังสร้างอยู่นี่

คำถามที่สามกว้างกว่า code และนี่คือจุดที่คนหยุดเร็วเกินไป ไฟล์ configuration, logs,
Markdown ที่มีโครงสร้างพร้อมหัวข้อที่คาดเดาได้, CSV export,
อะไรก็ตามที่มีตัวระบุหรือรหัสข้อผิดพลาดหรือชื่อ field อยู่ในนั้น
ถ้าคนที่ตอบคำถามนี้จะคว้า control F มาใช้ agent ก็ควรคว้า grep

## 3. retrieval คืออะไรกันแน่ เมื่อถอดเวทมนตร์ออกไป

ลอกคำศัพท์ออก แล้ว retrieval คือประโยคเดียว

คุณมีข้อความหลายชิ้นและคำถามหนึ่งข้อ
คุณให้คะแนนทุกชิ้นตามความน่าจะเป็นที่มันจะตอบคำถามได้ คุณคืนไม่กี่ชิ้นที่คะแนนสูงสุด

แค่นั้นเอง chunking คือส่วนที่คุณตัดสินใจว่าชิ้นหนึ่งคืออะไร embedding
คือวิธีหนึ่งในการคำนวณคะแนน vector database
คือวิธีคำนวณคะแนนนั้นให้เร็วเมื่อมีสิบล้านชิ้น ทั้งสามอย่างเป็นการลงมือทำรายละเอียด
รูปร่างของมันคือให้คะแนนแล้วเรียง

นี่คือ `search_notes` ฉบับเต็ม

```python
def search_notes(question, limit=TOP_RESULTS, root=None, pattern=DEFAULT_PATTERN):
    root = Path(root or os.environ.get("AGENTPATH_WORKSPACE", ".")).resolve()
    index = build_index(root, pattern)
    if not index:
        return f"there are no {pattern} documents to search"

    appearances = {}
    for entry in index:
        for word in entry["words"]:
            appearances[word] = appearances.get(word, 0) + 1
    rarity = {word: math.log(len(index) / count) for word, count in appearances.items()}

    question_words = set(words(question))
    ranked = sorted(index, key=lambda entry: score(question_words, entry, rarity), reverse=True)
    best = [entry for entry in ranked if score(question_words, entry, rarity) > 0]
    if not best:
        return f"nothing in the documents mentions any of the words in {question!r}"
    best = rerank(question, best[:RERANK_TOP]) + best[RERANK_TOP:]
    _, _, truncate = _from_tools()
    parts = [f"{entry['source']}\n{entry['text']}" for entry in best[: int(limit)]]
    return truncate("\n\n".join(parts))
```

บรรทัด `rerank` หลังตัวกรองคือการมองรอบที่สองที่ยี่สิบอันดับแรก และหัวข้อ 7 อธิบายมัน
ข้ามไปก่อนจนกว่าจะถึงตรงนั้น

อ่านสามคำสั่งตรงกลางแล้วคุณก็ได้อ่านเทคนิคนี้ครบแล้ว
นับว่าแต่ละคำปรากฏในกี่ passage แปลงจำนวนนั้นเป็นน้ำหนัก
เรียง passage ตามผลรวมของน้ำหนักของคำที่มันมีร่วมกับคำถาม

ตัวฟังก์ชันให้คะแนนเองมีบรรทัดเดียว

```python
def score(question_words, entry, rarity):
    return sum(rarity.get(word, 0.0) for word in question_words & entry["words"])
```

`question_words & entry["words"]` คือ set intersection ซึ่งคือคำที่คำถามกับ passage
มีร่วมกัน รวมน้ำหนักของมัน นั่นคือคะแนน

มีการตัดสินใจย่อยสองอย่างในฟังก์ชันนั้นที่ควรเรียกชื่อไว้ตอนนี้และปกป้องทีหลัง

ตัวกรอง `if score(...) > 0` ทิ้ง passage ทุกอันที่ไม่มีคำร่วมกับคำถามเลย
ถ้าไม่มีมัน การค้นหาจะคืนห้า passage เสมอ
เพราะการเรียงลิสต์ย่อมได้ห้าอันดับแรกเสมอแม้ทุกคะแนนจะเป็นศูนย์ การคืนห้าย่อหน้าแบบสุ่ม
ให้ model ที่ถามคำถามซึ่ง corpus ตอบไม่ได้ แย่กว่าการคืนประโยคที่บอกว่าตอบไม่ได้มาก
และหัวข้อ 9 มี check ที่พิสูจน์ว่าพฤติกรรมนี้อยู่ตรงนี้อย่างตั้งใจ

และ `truncate` คือเพดานจากบทที่ 07 ที่นำมาใช้ตรงนี้ด้วยเหตุผลของบทที่ 07 ผลของ tool
ทุกอันเข้าไปอยู่ในบทสนทนาและถูกส่งซ้ำทุก request ถัดไป ไม่มีทางเอามันคืน tool
ที่คืนข้อความได้ไม่จำกัดคือปัญหา context window ที่รอคำถามที่ใช่อยู่

ทีนี้ฟังก์ชันที่เหลืออีกสองตัว `words` คือ tokeniser

```python
WORD = re.compile(r"[A-Za-z0-9_]+")


def words(text):
    return WORD.findall(text.lower())
```

แปลงทุกอย่างเป็นตัวพิมพ์เล็กแล้วเอาลำดับของตัวอักษร ตัวเลข และ underscore `Refunds,`
กลายเป็น `refunds` เครื่องหมายวรรคตอนหายไป
คำท้ายประโยคจึงตรงกับคำเดียวกันที่อยู่กลางประโยค underscore ถูกเก็บไว้
เพราะตัวระบุอย่าง `issue_refund` ควรอยู่เป็น token เดียวมากกว่าจะกลายเป็นสองตัว

ชื่อที่ยืมมาสองตัวนั้นมาถึงผ่านฟังก์ชันเล็กๆ ตัวหนึ่ง ไม่ได้ import ตรงๆ ที่หัวไฟล์

```python
def _from_tools():
    import tools

    return tools.SKIP_DIRECTORIES, tools.looks_like_a_secret, tools.truncate
```

การวาง import ไว้ข้างในฟังก์ชันเป็นความตั้งใจ `tools.py` import `retrieval.py`
เพื่อลงทะเบียน tool และถ้า `retrieval.py` import `tools.py` กลับที่หัวไฟล์
แต่ละไฟล์จะต้องรอให้อีกไฟล์โหลดเสร็จก่อนถึงจะโหลดตัวเองเสร็จ Python จะพังที่ไฟล์ไหนก็ตามที่คุณเรียกก่อน
การย้าย import เข้าไปข้างในฟังก์ชันเลื่อนมันออกไปจนถึงตอนที่ถูกเรียกจริง
ซึ่งเป็นเวลาหลังจากทั้งสองไฟล์โหลดเสร็จไปนานแล้ว
การยืมแทนการคัดลอกคือข้อโต้แย้งทั้งหมดของหัวข้อนี้ การยืมจึงต้องรอดจากลำดับการโหลดไฟล์ด้วย

และ `build_index` อ่านไฟล์

```python
def build_index(root, pattern=DEFAULT_PATTERN):
    """Read the documents once and remember their words."""
    skip, is_secret, _ = _from_tools()
    index = []
    for path in sorted(root.rglob(pattern)):
        if any(part in skip for part in path.relative_to(root).parts):
            continue
        if is_secret(path.name):
            continue
        for line_number, text in passages_in(path):
            index.append(
                {
                    "source": f"{path.relative_to(root).as_posix()}:{line_number}",
                    "text": text,
                    "words": set(words(text)),
                }
            )
    return index
```

สามอย่างในนั้นถูกนำกลับมาใช้ ไม่ได้คิดขึ้นใหม่ และสองในสามมาถึงผ่าน `_from_tools`
ภายใต้ชื่อในเครื่องว่า `skip` และ `is_secret` `SKIP_DIRECTORIES` คือ set ของบทที่ 07
retrieval จึงไม่ทำ index บน virtual environment ของคุณ `looks_like_a_secret`
คือฟังก์ชันช่วยของบทที่ 07 และมันอยู่ตรงนี้เพราะบทที่ 09 เจอช่องโหว่ที่ search tool
เดินสำรวจ tree เองและเลี่ยงการปฏิเสธเรื่อง credential ที่ `read_file` บังคับไว้
กฎที่บังคับที่จุดเข้าเพียงจุดเดียวคือกฎที่ไม่ได้ถูกบังคับ `as_posix()` คือบรรทัดของบทที่ 09
source บน Windows จึงอ่านว่า `docs/refunds.md` แทนที่จะเป็น `docs\refunds.md`

สังเกตสิ่งที่ไม่มีอยู่ ไม่มี index ถาวร ไม่มีไฟล์ cache ไม่มีฐานข้อมูล `build_index`

ไม่มีวันเก่าเพราะไม่มี index

การแลกนั้นกลับด้านที่จุดใดจุดหนึ่ง เอกสารหนึ่งล้านฉบับจะอ่านไม่ทันในหนึ่งในห้าวินาที
และคุณจะต้องเก็บอะไรบางอย่างไว้ สังเกตว่านี่คือปัญหาข้อมูลเก่าค้างอันเดียวกับที่หัวข้อ 7
ระบุว่าเป็นต้นทุนของ embeddings ซึ่งมาถึงจากคนละทิศทางกันอย่างสิ้นเชิง
นั่นบอกคุณว่ามันเป็นคุณสมบัติของการเก็บสำเนาที่แปรมาจากข้อมูลของคุณ
ไม่ใช่คุณสมบัติของ vector

## 4. การให้คะแนนด้วย rarity

นี่คือแนวคิดเดียวในการให้คะแนน ในภาษาธรรมดา

คำที่ปรากฏในทุก passage แยกแยะ passage ไม่ได้ มันจึงควรนับเป็นศูนย์ คำที่ปรากฏใน
passage เดียวเป๊ะ ชี้ตรงไปที่ passage นั้น มันจึงควรนับเยอะ

แค่นั้นเอง มันมีชื่อว่า inverse document frequency และชื่อนั้นน่ากลัวกว่าแนวคิดมาก
สองบรรทัดคือการลงมือทำมัน

```python
    appearances = {}
    for entry in index:
        for word in entry["words"]:
            appearances[word] = appearances.get(word, 0) + 1
    rarity = {word: math.log(len(index) / count) for word, count in appearances.items()}
```

นับว่าแต่ละคำปรากฏในกี่ passage เอาจำนวน passage ทั้งหมดหารด้วยจำนวนนั้น
แล้วใส่ลอการิทึม คำที่อยู่ในทุก passage ให้อัตราส่วนเป็นหนึ่งและลอการิทึมเป็นศูนย์
มันจึงไม่มีส่วนร่วมเลย คำที่อยู่ใน passage เดียวจากพัน passage ให้อัตราส่วนเป็นพัน
และน้ำหนักที่มากกว่ามาก

ลองดู fixture ของ check ซึ่งเป็นไฟล์ Markdown เล็ก ๆ สามไฟล์ นี่คือ index ที่มันสร้าง
แปด passage

```text
refunds.md:1  | # Refunds
refunds.md:3  | Customers may request a refund within thirty days of purchase.
refunds.md:5  | Refunds are paid back to the original card.
shipping.md:1 | # Shipping
shipping.md:3 | Orders are dispatched within two working days.
shipping.md:5 | Delivery takes three to five days.
team.md:1     | # The team
team.md:3     | The team works remotely across three time zones.
```

และนี่คือน้ำหนักที่คำนวณจากแปด passage นั้น

```text
the          appears in 3 of 8  rarity 0.981
days         appears in 3 of 8  rarity 0.981
refunds      appears in 2 of 8  rarity 1.386
three        appears in 2 of 8  rarity 1.386
team         appears in 2 of 8  rarity 1.386
refund       appears in 1 of 8  rarity 2.079
dispatched   appears in 1 of 8  rarity 2.079
long         appears in 0 of 8  rarity 0.000
```

อ่านคอลัมน์ตัวเลข `the` มีค่าน้อยกว่าครึ่งหนึ่งของ `refund`
และไม่มีใครเขียนรายการ stopword เพื่อให้เกิดเรื่องนั้น มันหลุดออกมาจากการนับ
นั่นคือคุณสมบัติที่ควรชื่นชม น้ำหนักปรับตัวตาม corpus ที่คุณชี้ให้มัน corpus
ของเอกสารกฎหมายจึงจะลดค่าคำว่า `agreement` และ `party` โดยอัตโนมัติ
โดยไม่มีใครต้องตัดสินว่ามันเป็นคำสามัญ

แถวสุดท้ายคือกรณีคำที่ไม่มีอยู่ `rarity.get(word, 0.0)` คืนศูนย์สำหรับคำที่ไม่ปรากฏที่ไหนเลย
คำถามที่มีคำว่า `long` จึงไม่ถูกลงโทษหรือทำให้พัง คำนั้นแค่ไม่มีส่วนร่วมอะไรเลย

ทีนี้ดูการค้นหาจริง คำถามคือ `how long to ask for a refund`
ซึ่งไม่ได้ใช้ถ้อยคำตรงกับเอกสารไหนเลย

```text
question words: ['a', 'ask', 'for', 'how', 'long', 'refund', 'to']

4.159  refunds.md:3   overlap=['a', 'refund']
1.386  refunds.md:5   overlap=['to']
1.386  shipping.md:5  overlap=['to']
0.000  refunds.md:1   overlap=[]
0.000  shipping.md:3  overlap=[]
0.000  team.md:3      overlap=[]
```

และนี่คือสิ่งที่ tool คืนมา

```text
refunds.md:3
Customers may request a refund within thirty days of purchase.

refunds.md:5
Refunds are paid back to the original card.

shipping.md:5
Delivery takes three to five days.
```

สาม passage ไม่ใช่ห้า เพราะมีแค่สามอันที่ได้คะแนนเกินศูนย์และตัวกรองทิ้งที่เหลือไป
อันแรกคือคำตอบ สี่จากเจ็ดคำในคำถามเป็น noise คำว่า `how` และ `long` และ `ask` และ
`for` ไม่มีส่วนร่วมอะไรเลย และคำเดียวที่มีความหมายก็หาประโยคที่ถูกเจอจนได้

ทีนี้พูดตรง ๆ เรื่องผลลัพธ์ที่สองและสาม เพราะมันคือ noise ทั้งคู่ได้คะแนน 1.386 จากคำว่า
`to` ทั้งคู่ไม่เกี่ยวข้อง

เหตุผลนั้นให้บทเรียน ใน corpus ที่มีแปด passage คำว่า `to` ปรากฏสองครั้ง
ซึ่งทำให้มันดูหายาก ใน corpus จริงที่มีหมื่น passage คำว่า `to` ปรากฏเกือบทุกอัน
และน้ำหนักของมันยุบลงเกือบเป็นศูนย์ ซึ่งคือสิ่งที่คุณต้องการพอดี เช่นเดียวกับคำว่า `a`
ซึ่งมีส่วนร่วมครึ่งหนึ่งของคะแนนที่ชนะตรงนี้ เพราะบังเอิญมันปรากฏใน passage เดียวจากแปด
สถิติ rarity กำลังทำเลขคณิตที่ถูกต้องบนข้อมูลที่บางเกินกว่าจะรองรับมันได้

นั่นควรพูดออกมามากกว่าซ่อนไว้ ด้วยเหตุผลสองข้อ
มันคือพฤติกรรมจริงของ code ในโฟลเดอร์นี้ และคุณจะเจอมันภายในสิบนาที
และมันเป็นคุณสมบัติทั่วไปของทุกวิธี retrieval เชิงสถิติ รวมถึงวิธีที่แพงด้วย
ทั้งหมดเป็นการประมาณจาก corpus ทั้งหมดมี noise มากขึ้นบน corpus เล็ก
และไม่มีวิธีไหนบอกคุณว่าผลลัพธ์ตัวไหนของมันเองคือ noise หัวข้อ 6
พูดถึงสิ่งเดียวที่ทำให้เรื่องนี้อยู่รอดได้

แนวคิดเดียวนี้ การซ้อนทับของคำถ่วงด้วย rarity
คือสิ่งที่ search engine แบบคลาสสิกทำเป็นส่วนใหญ่ เพิ่มการแก้ตามความยาวของ passage
เพื่อไม่ให้ passage ยาวชนะเพียงเพราะมันมีคำมากกว่า และเพิ่มพจน์ saturation
เพื่อให้การปรากฏครั้งที่สิบของคำนับน้อยกว่าครั้งที่สอง แล้วคุณจะได้ BM25
ซึ่งเป็นอัลกอริทึมที่อยู่ใต้ Lucene, Elasticsearch
และช่องค้นหาส่วนใหญ่ที่คุณเคยพิมพ์ลงไป การปรับปรุงสองอย่างนั้นคุ้มค่าที่จะมี
และมันเป็นการปรับปรุง เครื่องยนต์คือสองบรรทัดข้างบน

## 5. ทำไมใช้ย่อหน้าแทน chunk ขนาดคงที่

`build_index` ได้ชิ้นส่วนของมันมาจากตรงนี้

```python
def passages_in(path):
    """Split a file into paragraphs, keeping the line each one starts on."""
    passages = []
    line_number = 1
    for block in path.read_text(encoding="utf-8", errors="replace").split("\n\n"):
        if block.strip():
            passages.append((line_number, block.strip()))
        line_number += block.count("\n") + 2
    return passages
```

แบ่งที่บรรทัดว่าง เก็บหมายเลขบรรทัดที่แต่ละบล็อกเริ่ม ซึ่งเป็นสิ่งที่ทำให้ source ในหัวข้อ
6 เป็นไปได้ ข้ามบล็อกที่ว่างเปล่าหลังตัดช่องว่าง ซึ่งเกิดขึ้นเมื่อไฟล์มีบรรทัดว่างสองบรรทัดติดกัน

ทางเลือกมาตรฐาน และเป็นทางที่แทบทุก tutorial คว้ามาใช้ คือตัดทุก N ตัวอักษร สี่ร้อย
ห้าร้อย หนึ่งพัน โดยปกติจะมีการซ้อนทับระหว่างชิ้นข้างเคียง
เพื่อไม่ให้ประโยคที่คร่อมรอยตัดหายไปทั้งหมด

เหตุผลที่สนับสนุนย่อหน้าคือประโยคเดียว ย่อหน้าคือหน่วยที่คนเขียนขึ้นอย่างตั้งใจ
มีคนตัดสินใจว่ามันเริ่มตรงไหนและจบตรงไหน และเขาตัดสินใจบนพื้นฐานว่ามันคือหนึ่งความคิด
คุณได้การแบ่งส่วนมาฟรี ๆ ซึ่งทำโดยมนุษย์ที่เข้าใจเนื้อหา
และมันดีกว่าอะไรก็ตามที่เครื่องนับตัวอักษรจะผลิตได้

เหตุผลที่คัดค้านการตัดขนาดคงที่ อธิบายได้ดีที่สุดด้วยการลงมือทำ นี่คือ docstring
ที่หัวไฟล์ `retrieval.py` ซึ่งเป็นร้อยแก้วธรรมดา 1066 ตัวอักษร ตัดทุกสี่ร้อยตัวอักษร


ดูสิ่งที่เกิดขึ้นที่รอยต่อสองจุด เพราะทั้งคู่แย่กว่าที่เห็นตอนแรก

chunk แรกจบด้วย `weighted by how ra` chunk ที่สองเริ่มด้วย `re each word is`
คำว่า `rare` ถูกตัดเป็น `ra` กับ `re` และประโยคที่อธิบายเทคนิคทั้งหมดตอนนี้ไม่มีอยู่ในทั้งสอง
chunk ถ้าคุณดึง chunk แรกมา คุณได้คำสัญญาที่ไม่มีคำอธิบาย ถ้าคุณดึงอันที่สอง
คุณได้คำอธิบายที่ประธานหายไป

รอยต่อที่สองคืออันที่น่าจะทำให้คุณหน้าเบ้ chunk ที่สองจบด้วย `A question about re`
และอันที่สามเริ่มด้วย `funds will not find a document` คำว่า `refunds`
ถูกตัดครึ่ง ซึ่งแปลว่า chunk ที่ว่าด้วยเรื่อง refunds ทั้งอัน ไม่มีคำว่า `refund`
อยู่ในนั้นเลย และไม่มีการค้นหาแบบ keyword ใดจะเจอมันได้ มันผลิต token สองตัวคือ `re`
และ `funds` ซึ่งไม่มีความหมายและไม่ตรงกับอะไรเลย

นั่นไม่ใช่โชคร้าย มันคือพฤติกรรมที่รับประกันได้ของกฎที่ไม่รู้อะไรเลยเกี่ยวกับข้อความที่มันกำลังตัด
เมื่อใช้ซ้ำไม่กี่พันครั้ง รอยต่อของคุณส่วนหนึ่งจะตกกลางคำ
มากกว่านั้นจะตกกลางประโยค และผลลัพธ์อ่านแล้วไม่เป็นภาษา

ทีนี้ว่ากันตามจริง เพราะย่อหน้าก็ไม่ได้มาฟรี

ย่อหน้าไม่ใช่ขนาดคงที่ passage จึงมีตั้งแต่หนึ่งบรรทัดไปจนถึงหลายร้อยคำ passage
ยาวได้เปรียบในการให้คะแนน เพราะคำมากกว่าแปลว่าโอกาสซ้อนทับกับคำถามมากกว่า
และเวอร์ชันนี้ไม่มีการแก้ตามความยาว
นั่นคือข้อแรกของสองการปรับปรุงที่หัวข้อ 4 บอกว่าจะเปลี่ยนสิ่งนี้เป็น BM25
และมันสำคัญกว่าอีกข้อ

เอกสารบางอย่างไม่มีโครงสร้างย่อหน้าเลย ไฟล์ที่ถูก minify, CSV,
บันทึกคำต่อคำที่ส่งออกมาเป็นบล็อกใหญ่ก้อนเดียว การแบ่งที่บรรทัดว่างจะให้ passage เดียว
ที่บรรจุทั้งไฟล์ ซึ่งไร้ประโยชน์ ในทางปฏิบัติคุณรับมือด้วยการถอยไปใช้การตัดตามขนาด
เมื่อย่อหน้ายาวเกินค่าหนึ่ง ซึ่งเป็นลูกผสมที่สมเหตุสมผลและถูกทิ้งไว้เป็นแบบฝึกหัด

และหัวข้อกลายเป็น passage ของตัวเอง ซึ่งเป็นผลที่ปนกันจริง ๆ ใน index ของหัวข้อ 4
`# Refunds` เป็น passage เดี่ยวที่มีคำเดียว ลองรัน query จริงกับคอร์สนี้แล้วอันดับหนึ่งคือหัวข้อ

```text
09-search-tools/README.md:778
## 7. Why we cap the number of results
```

นั่นคือตัวชี้ที่ยอดเยี่ยมและคำตอบที่แย่ และมันยอดเยี่ยมได้ก็เพราะหัวข้อถัดไปเท่านั้น

## 6. ทำไมทุกผลลัพธ์ต้องพก source มาด้วย

ทุก passage กลับมาพร้อมไฟล์และบรรทัดที่มันมา ซึ่งสร้างขึ้นใน `build_index`

```python
"source": f"{path.relative_to(root).as_posix()}:{line_number}",
```

และถูกแสดงไว้หน้าทุกผลลัพธ์

```python
    parts = [f"{entry['source']}\n{entry['text']}" for entry in best[: int(limit)]]
```

นี่คือ format string สี่คำ และมันคือความต่างระหว่าง tool ที่ใช้งานได้กับ tool ที่อันตราย

passage ที่ไม่มี source แทบไร้ประโยชน์ ด้วยเหตุผลสองข้อที่แยกกันและพังไปคนละทาง

**agent ไปอ่านเพิ่มไม่ได้** retrieval คืนชิ้นส่วนกลับมาโดยธรรมชาติของมัน
ชิ้นส่วนนั้นมักตอบคำถามได้ครึ่งเดียว หรือตอบพร้อมข้อแม้ที่อยู่ในย่อหน้าถัดไป เมื่อมี source
model มีที่ให้ไปต่อ และมันมี tool ที่จะไปที่นั่นอยู่แล้ว ดูผลลัพธ์ที่เป็นหัวข้ออีกครั้ง

```text
09-search-tools/README.md:778
## 7. Why we cap the number of results
```

ลำพังตัวมันเองนั่นคือหัวข้อที่ไม่มีเนื้อหา เมื่อแนบ source มาด้วย
การเรียก tool ครั้งถัดไปก็ชัดเจน และ agent ทำมันโดยไม่ต้องมีใครบอก อ่านไฟล์นั้น grep
ใกล้ ๆ มัน ผลของ retrieval ไม่ใช่คำตอบ มันคือตัวชี้ และตัวชี้ที่ไม่มีที่อยู่ก็ไม่ใช่ตัวชี้

## 7. สิ่งที่วิธีนี้ทำไม่ได้จริง ๆ และอะไรจะแก้มันได้

ทีนี้ถึงส่วนที่ต้องพูดตรง ๆ และมันเป็นข้อจำกัดจริงไม่ใช่ข้อจำกัดพอเป็นพิธี

### reranking ในรูปที่ถูกที่สุดที่ยังนับว่าเป็นของจริง

reranking (การจัดอันดับใหม่ คือการมองรอบที่สองที่ช้ากว่าเฉพาะผู้เข้ารอบไม่กี่ตัวบนสุด) คือ
สิ่งที่ระบบจริงจังทำหลังการรวมผล pass แรกให้คะแนนทุก passage ใน corpus มันจึงต้องถูก และ
ตัวให้คะแนนที่ถูกจะมองข้ามบางอย่าง ตัวนี้ให้คะแนนคำเดี่ยว ๆ และไม่เคยเห็นลำดับของคำ passage ที่พูดถึงทุกคำในคำถาม
กระจายอยู่ในประโยคที่ไม่เกี่ยวกัน จึงเสมอกับ passage ที่พูดวลีนั้นตรง ๆ บนรายชื่อสั้น ๆ จ่ายค่า
ตัวให้คะแนนที่แพงกว่าไหว เพราะมีไม่กี่ตัว ในระบบจริงมันมักเป็น model เล็ก ๆ ที่อ่านคำถามกับ
passage พร้อมกัน ที่นี่คือคู่คำ ซึ่งพอให้เห็นรูปร่าง

```python
def rerank(question, entries):
    """A second, slower look at the best few, using something the first pass ignored."""
    wanted = phrases(question)
    return sorted(entries, key=lambda entry: -len(wanted & phrases(entry["text"])))
```

สองเรื่องที่ควรสังเกต มันเรียงใหม่ได้เฉพาะสิ่งที่ pass แรกหาเจอ passage ที่การให้คะแนนด้วย
rarity พลาดไปก็ยังพลาดอยู่ และเรื่องนี้จริงกับ reranker ทุกตัว และคู่คำถูกนับ ไม่ได้ถูกถ่วง
น้ำหนัก `of the` ที่มีร่วมกันจึงนับเท่ากับ `annual leave` ที่มีร่วมกัน นั่นคือราคาของตัวให้
คะแนนที่ถูกขนาดนี้ และเป็นเหตุผลที่ลำดับของ rarity ถูกเก็บไว้ข้างใต้ เพราะการเรียงเป็น

### การวัดมัน ให้ความเห็นกลายเป็นตัวเลข

ทุกอย่างข้างบนเป็นความเห็นจนกว่าคุณจะใส่ตัวเลขให้มันได้ และตัวเลขแรกที่ใช้วัด retrieval
คือ recall at k (สัดส่วนของ passage ที่ถูกซึ่งอยู่ใน k อันดับแรก) เขียนคำถามสักหยิบมือ และสำหรับแต่ละข้อ passage ไหนที่ควรกลับมา รันการค้น
recall at k คือสัดส่วนของ passage ที่ถูกต้องซึ่งปรากฏใน k อันดับแรก

```python
def recall_at_k(ranked_sources, relevant, k):
    """What share of the passages that should have been found are in the top k."""
    if not relevant:
        raise ValueError("a question with no relevant passages cannot be scored, leave it out")
    found = set(ranked_sources[:k]) & set(relevant)
    return len(found) / len(relevant)
```

มันแคบโดยตั้งใจ มันไม่บอกอะไรเลยว่า model ตอบดีไหมหลังจากนั้น ซึ่งเป็นปัญหาของบทที่ 22
มันบอกว่า passage ที่ถูกอยู่บนหน้าที่ model ได้เห็นหรือเปล่า ซึ่งเป็นส่วนเดียวที่ retrieval
รับผิดชอบ และการแยกสองอย่างนี้ออกจากกันคือวิธีหาว่าคำตอบที่แย่ต้องแก้ครึ่งไหน ราคาคือชุด
ทดสอบ ต้องมีคนเขียนคำถามและทำเครื่องหมาย passage ที่ถูก ต้องคอยอัปเดตเมื่อเอกสาร

## 8. retrieval เป็น tool ไม่ใช่ system

นี่คือการต่อสายทั้งหมดที่เพิ่ม retrieval เข้าไปใน harness อยู่ท้ายไฟล์ `tools.py`

เก้าบรรทัดรวมบรรทัดว่าง และ `agent.py` ไม่เปลี่ยนเลย นั่นคือรอยต่อของบทที่ 11
ที่ยังทนอยู่กับ tool ตัวที่แปด ซึ่งควรสังเกต แต่ไม่ใช่ประเด็นของหัวข้อนี้

ประเด็นคือเก้าบรรทัดนั้นบอกอะไรเกี่ยวกับสถาปัตยกรรม
และมันคือสิ่งที่ระบบ retrieval ส่วนใหญ่ทำผิด

ในระบบ retrieval augmented generation แบบทั่วไป retrieval ไม่ใช่ tool
มันคือขั้นตอนหนึ่ง ทุกคำถามผ่าน pipeline เดียวกัน embed คำถามของผู้ใช้ ดึง chunk
อันดับต้นมา แปะลงใน prompt เรียก model การ retrieval เกิดขึ้นก่อนจะปรึกษา model
ในทุก request ไม่ว่าจะจำเป็นหรือไม่

ลองคิดดูว่านั่นทำให้เกิดอะไร ผู้ใช้พูดว่า thanks, that worked pipeline ก็ทำหน้าที่ embed มัน
ดึงเอกสารห้าย่อหน้าที่ใกล้กับคำขอบคุณที่สุดในเชิงสถิติ แล้วแปะลงใน prompt
ผู้ใช้ถามอะไรที่ต้องค้นสามรอบต่อเนื่องกัน โดยคำถามที่สองจะเห็นชัดก็ต่อเมื่อตอบคำถามแรกแล้ว
และ pipeline ดึงครั้งเดียวจากถ้อยคำเดิม และไม่มีกลไกสำหรับความพยายามครั้งที่สอง
นี่คือปัญหาการยิงครั้งเดียวของบทที่ 09
ที่โผล่มาในฐานะคุณสมบัติของสถาปัตยกรรมมากกว่าคุณสมบัติของ vector

ที่นี่ retrieval เป็น tool model ตัดสินใจว่าจะเรียกมันไหม ตัดสินใจว่าจะค้นหาอะไร
อ่านผลลัพธ์ และตัดสินใจว่าจะทำอะไรต่อ มันข้ามไปเลยก็ได้ มันเรียกมัน ได้ผลที่มี noise
แบบหัวข้อ 4 สังเกตว่าสองในสาม passage ไม่เกี่ยวข้อง แล้วเรียก `read_file` บน source
ของอันที่เกี่ยวข้องก็ได้ มันเรียกสองครั้งด้วยถ้อยคำต่างกันก็ได้ มันใช้ grep แทนก็ได้

นั่นคือ loop จากบทที่ 04 ที่ทำงานที่มันทำมาตลอด และมันแปลว่าคำถามที่ว่า passage
ไหนเกี่ยวข้อง ถูกตอบโดยสิ่งที่ให้เหตุผลกับคำตอบได้
แทนที่จะถูกตอบด้วยระยะ cosine ที่คำนวณไว้ก่อนที่ใครจะได้อ่านอะไรเลย

ต้นทุนของการออกแบบนั้นคือ model ต้องรู้ว่าเมื่อไรควรใช้มัน ซึ่งทำให้คำอธิบาย tool
มีน้ำหนักจริง นี่คือมัน แบบคำต่อคำ

```python
SCHEMA = {

```

สามประโยค และประโยคที่สามคือประโยคที่น่าสนใจ

```text
For code, grep_files is usually better because names are exact.
```

นั่นคือคำอธิบาย tool ที่บอก model ให้เลือกใช้ tool อื่น ควรนั่งคิดสักครู่ว่ามันผิดปกติแค่ไหน
คำอธิบาย tool แทบทุกอันที่เคยเขียนมาคือโฆษณาให้ tool ของตัวเอง และผลลัพธ์คือ agent
ที่ถือ tool แปดตัวซึ่งแต่ละตัวอ้างว่าตัวเองคือตัวที่ถูก

เหตุผลที่มันควรอยู่ตรงนี้คือตอนนี้ agent มีวิธีค้นข้อความสองวิธีที่ทับซ้อนกัน และ tool
ที่ทับซ้อนกันคือจุดที่ model สับสน `grep_files` กับ `search_notes`
ต่างรับอะไรที่คล้าย query และต่างคืนอะไรที่คล้ายข้อความที่ตรงกันพร้อมไฟล์และบรรทัด
ถ้าไม่มีคำแนะนำ model จะเลือกระหว่างสองอันตามความรู้สึก และความรู้สึกของคำว่า
search the project documents for passages related to a question
นั้นน่าดึงดูดมากตอนที่คุณกำลังหาฟังก์ชัน

คำอธิบายจึงทำสามอย่างในสามประโยค มันบอกว่า tool ทำอะไร มันบอกว่ามีไว้เพื่ออะไร
ซึ่งคือร้อยแก้ว และมันระบุชื่อทางเลือกที่เจาะจงพร้อมเหตุผลว่าทำไมควรเลือกทางนั้น
เพื่อให้ model นำกฎไปใช้กับกรณีที่ประโยคนั้นไม่ได้คาดไว้ได้

`because names are exact` ทำงานหนักกว่าประโยคว่า `use grep_files instead for
code` กฎที่มีเหตุผลติดมาด้วยจะขยายไปใช้ได้กว้าง model
ที่เข้าใจว่าทำไมความแม่นยำจึงสำคัญ จะคว้า grep มาใช้กับรหัสข้อผิดพลาด
คีย์ configuration หรือ SKU สินค้าด้วย ซึ่งไม่มีอันไหนเป็น code
และทุกอันมีการสะกดที่ถูกต้องเพียงแบบเดียว นี่คือข้อโต้แย้งของบทที่ 10 เรื่องคำอธิบาย tool
ที่มาถึงในที่ที่มันสำคัญที่สุด ซึ่งคือตอนที่ tool สองตัวต่างก็ตอบได้อย่างน่าเชื่อทั้งคู่

สังเกตท้ายสุดว่าสี่คำถามในหัวข้อ 2 ไม่ได้หายไปเพียงเพราะมี tool อยู่แล้ว
คำถามที่หนึ่งยังบอกให้ใส่เอกสารเล็ก ๆ ลงใน prompt และถ้าโน้ตของคุณใส่ได้
การเคลื่อนไหวที่ถูกต้องคือ `build_system_prompt` จากบทที่ 10 ไม่ใช่ tool นี้
คำถามที่สามยังบอกให้ grep สำหรับ code และตัวคำอธิบาย tool ก็บอกแบบนั้นเอง
การที่สร้าง retrieval แล้วไม่ได้ทำให้มันกลายเป็นคำตอบ มันทำให้มันเป็นคำตอบที่สี่
ที่มีให้ใช้เมื่อสามคำตอบแรกไม่เข้าที

ก่อน จากนั้นคำตอบเรื่อง refund จากข้อยืนยันแรก ให้คะแนนด้วย `recall_at_k` เทียบกับ
passage เดียวที่ควรอยู่ตรงนั้น ได้หนึ่งที่ k เท่ากับหนึ่ง และรายการที่ไม่มีมันได้ศูนย์

ถ้าบรรทัดแรกล้มเหลว ให้ดูว่าตัวแปรสภาพแวดล้อม workspace
ถูกตั้งค่าก่อนที่ `tools` จะถูก import หรือไม่ ซึ่งเป็นกับดักเรื่องลำดับของบทที่ 09
และมันยังอยู่ตรงนี้ ถ้าข้อที่สองล้มเหลว format string ของ source ทำหมายเลขบรรทัดหาย
ถ้าข้อที่สี่ล้มเหลวและ tool คืน passage มาจริง แสดงว่ามีคนเพิ่ม stemming หรือ fuzzy
matching เข้ามา และหัวข้อ 7 ต้องถูกเขียนใหม่ก่อนที่การเปลี่ยนแปลงนั้นจะเข้ามา ถ้าข้อที่หก
ล้มเหลว `phrases` น่าจะตัดคำต่างจาก `words` และสองตัวนี้ต้องตรงกัน

## 10. สิ่งที่คุณยังทำไม่ได้

ลองสำรวจดู agent มี permission ที่จำสิ่งที่คุณตัดสินใจไว้ มี session ที่เขียนลงดิสก์
มีการจัดการ context ที่ไม่ล้น มีบัญชี token ที่คุณอ่านได้
และตอนนี้มีวิธีค้นหาร้อยแก้วที่ไม่ใช่ code นั่นคือ harness

และทุกบรรทัดของมันสมมติว่าไม่มีอะไรผิดพลาด

ดูที่ `provider.stream` แล้วสังเกตว่าไม่มี `try` อยู่ใกล้ ๆ เลย rate limit
network สะดุดห้าวินาที gateway รีสตาร์ต `500` จาก endpoint ที่โหลดเกิน แล้ว `httpx`
จะ raise exception เดินทางขึ้นผ่าน `run` และออกจากโปรแกรมของคุณ และคุณได้ traceback
ทุกอย่างในบทสนทนานั้นหายไป รวมถึงหกไฟล์ที่มันอ่านไปแล้วและ retrieval ที่มันจ่ายไปแล้ว

retrieval เพิ่มปัญหาเดียวกันในเวอร์ชันของมันเอง `build_index`
อ่านทุกไฟล์ที่ตรงกับ pattern ใน workspace ไฟล์ที่หายไประหว่างการเดินสำรวจกับการอ่าน
ข้อผิดพลาดเรื่องสิทธิ์บนเอกสารหนึ่งฉบับ
ดิสก์ที่ใช้ไม่ได้ชั่วคราวบน mount ผ่านเครือข่าย แล้วการค้นหาทั้งหมดจะพัง
แทนที่จะข้ามไฟล์เดียวนั้น เทียบกับ `grep_files` จากบทที่ 09 ซึ่งจับ `OSError`
รายไฟล์แล้วเดินหน้าต่อ นั่นคือการป้องกันแบบเดียวกันที่ใช้ในระดับที่ละเอียดกว่า
และมันคุ้มที่จะถามสำหรับทุก loop ที่คุณเขียนเดินสำรวจ filesystem
ว่าองค์ประกอบที่เสียหนึ่งชิ้นควรจบทั้ง operation หรือไม่

`raise RuntimeError` ที่ก้นของ loop คือปัญหารูปแบบเดียวกันจากอีกด้าน
การชนขีดจำกัดจำนวนเทิร์นบ่อยครั้งไม่ใช่ความล้มเหลวเลย
มันมักแปลว่า agent กำลังคืบหน้าและต้องการอีกเทิร์นเดียว การพังคือคำตอบที่แย่
และการเดินหน้าต่อเงียบ ๆ ก็แย่เช่นกัน

นั่นคือบทที่ 17 ความล้มเหลวแบบไหนคุ้มที่จะ retry และแบบไหนไม่คุ้ม exponential backoff
พร้อม jitter และการเคารพ header `Retry-After` เมื่อ server ส่งมา
มันยังครอบคลุมสองเรื่องที่พลาดได้ง่ายและร้ายแรง การ retry tool ที่มีผลข้างเคียง
แปลว่าทำผลข้างเคียงนั้นสองครั้ง จึงต้องมี idempotency key และ retry loop
รอบการเรียก model อย่างเดียวไม่พอ และการขัดจังหวะ agent
ต้องหยุดทุกชั้นพร้อมกัน ทั้ง stream ที่เปิดอยู่ subprocess ใด ๆ ที่มันสร้าง
และคำถามขออนุญาตที่ค้างอยู่ เพราะ harness จริง ๆ
เคยส่ง bug ที่หน้าจอบอกว่าหยุดแล้วแต่ tool ยังทำงานอยู่มาแล้ว

จากนั้นบทที่ 18 คือหมุดหมายที่สอง ที่ทั้งหมดนี้กลายเป็น command line tool จริง พร้อม
`chat`, `run` และ `resume`

### แบบฝึกหัดก่อนไปต่อ

**ข้อหนึ่ง** เพิ่มการแก้ตามความยาวจากหัวข้อ 5
หารคะแนนแต่ละอันด้วยรากที่สองของจำนวนคำใน passage
หรือด้วยความยาวเทียบกับความยาวเฉลี่ยของ passage แล้วรัน check ใหม่
ส่วนที่น่าสนใจไม่ใช่สูตร แต่คือการดูว่าผลลัพธ์ไหนเปลี่ยน จากนั้นหา query
ที่การแก้นี้ทำให้คำตอบแย่ลง และตัดสินว่านั่นบอกอะไรคุณ

**ข้อสอง** จัดการกับเอกสารที่ไม่มีย่อหน้า หาหรือสร้างไฟล์ที่เป็นบล็อกใหญ่ก้อนเดียว
ยืนยันว่า `passages_in` คืน passage เดียวที่ครอบคลุมทั้งไฟล์ แล้วเพิ่มทางถอย
ที่แบ่งบล็อกที่ยาวเกินตามขอบเขตประโยคแทนที่จะตามจำนวนตัวอักษร
รักษาหมายเลขบรรทัดให้ถูกต้อง ซึ่งเป็นส่วนที่กินเวลาและเป็นเหตุผลว่าทำไม source
ในหัวข้อ 6 จึงคุ้มที่จะปกป้อง

**ข้อสาม** สร้าง hybrid จากหัวข้อ 7 โดยไม่ใช้ embeddings รัน `search_notes` กับ
`grep_files` บนคำถามเดียวกัน รวมสองลิสต์ที่จัดอันดับแล้ว
และคืนผลผสมพร้อมหมายเหตุว่า tool ตัวไหนเจอ passage ไหน จากนั้นถามคำถามที่ยากกว่า
ซึ่งคือคุณจะจัดอันดับผลจาก keyword เทียบกับ passage
ที่มีคะแนนอย่างไรเมื่อตัวเลขสองตัวหมายถึงคนละเรื่องกันโดยสิ้นเชิง ไม่มีคำตอบที่สะอาด
และวิธีมาตรฐานคือ reciprocal rank fusion
ซึ่งคุ้มที่จะไปค้นดูสักครั้งหลังจากที่คุณรู้สึกแล้วว่าทำไมวิธีที่ดูชัดเจนถึงใช้ไม่ได้

**ข้อสี่** รันสี่คำถามของหัวข้อ 2 กับของจริงที่คุณเป็นเจ้าของ เขียนลงไปว่า corpus คืออะไร
คำตอบของแต่ละคำถามคืออะไร และคุณหยุดที่ไหน ถ้าคุณหยุดที่คำถามที่หนึ่ง
ให้เอาเอกสารใส่ลงใน prompt ในบ่ายนี้แล้วดูว่ามันได้ผลไหม
แบบฝึกหัดข้อนั้นช่วยประหยัดเวลาวิศวกรรมได้มากกว่าย่อหน้าอื่นใดในบทนี้
