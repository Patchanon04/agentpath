# บทที่ 14 Context management

บทนี้มีกับดักที่สำคัญที่สุดของทั้งคอร์ส

ไม่ใช่แนวคิดที่ยากที่สุด แต่เป็นกับดัก ในบทนี้มีบั๊กที่เกือบทุกคนที่เขียน
agent harness ต้องเขียนพลาดอย่างน้อยหนึ่งครั้ง มันทำให้ provider ตอบกลับมาเป็น
`400` มันโผล่ขึ้นมาใน request คนละตัวกับตัวที่เป็นต้นเหตุ และด้วยเหตุนี้มันจึง
ดูเหมือนโผล่มาจากที่ไหนก็ไม่รู้ หลายคนเสียเวลาไปทั้งบ่าย ส่วนวิธีแก้ยาวแปดบรรทัด
ทั้งบทนี้คือการทำความเข้าใจเพื่อให้ได้แปดบรรทัดนั้นมา

หัวข้อของบทนี้คือจะทำอย่างไรเมื่อบทสนทนาใหญ่เกินกว่าจะใส่ลงไปได้ บทที่ 02
วางข้อเท็จจริงที่เป็นต้นเหตุของปัญหาไว้แล้ว นั่นคือ model เป็น stateless และ
บทสนทนาทั้งหมดถูกส่งซ้ำในทุก request บทที่ 13 ทำให้เรื่องแย่ลงในแบบที่มองข้ามได้ง่าย
เมื่อ session ถูกเก็บไว้ถาวรแล้ว บทสนทนาก็ไม่ได้ถูกจำกัดด้วยเวลาที่คุณยอมนั่งอยู่
หน้าคีย์บอร์ดอีกต่อไป คุณ resume session ของเมื่อวานแล้วทำต่อได้ และไฟล์ก็มีแต่จะโตขึ้น

ดังนั้นต้องมีอะไรบางอย่างถูกตัดทิ้ง บทนี้ว่าด้วยว่าอะไรคือสิ่งนั้น

## 1. ปัญหาที่บทที่ 13 ทิ้งไว้ให้คุณ

เอา agent ที่คุณทำเสร็จในบทที่ 13 มาสั่งงานจริงบน repository จริง มันอ่านไฟล์
มัน grep มันอ่านไฟล์อีกสองไฟล์ มันรัน test ของคุณ ได้ failure มา อ่าน test
ที่ fail แก้อะไรบางอย่าง แล้วรัน test ใหม่

ลองนับดูว่าตอนนั้นใน `messages` มีอะไรอยู่บ้าง tool result ทุกตัวยังอยู่ครบ
เต็มรูปแบบ และทุกตัวถูกส่งซ้ำอีกครั้งใน request ถัดไป `read_file` ใน `tools.py`
ตัดข้อความที่ `MAX_OUTPUT = 4000` ตัวอักษร ดังนั้นการอ่านไฟล์หนึ่งครั้งประมาณ
สี่พันตัวอักษร คิดคร่าว ๆ เป็นหนึ่งพัน token การอ่านหกครั้งคือเนื้อไฟล์หกพัน
token ที่ติดไปกับทุก request ตลอดที่เหลือของ session

บวกค่าใช้จ่ายคงที่ที่ไม่มีใครนึกถึงเข้าไปด้วย system prompt จากบทที่ 10 ยาว
ประมาณหกร้อยตัวอักษร tool schema ทั้งเจ็ดตัว serialise ออกมาได้ 2595 ตัวอักษร
ซึ่งประมาณหกร้อยห้าสิบ token และมันถูกส่งไปทุก request ไม่ว่า model จะใช้สักตัวหรือไม่

บน model ที่มี context window (ข้อความมากสุดที่ model อ่านได้ในหนึ่งครั้ง) แปดพัน token คุณจะชนกำแพงภายในประมาณสิบเทิร์นของงานปกติ
ไม่ใช่งานที่ผิดปกติ แต่เป็นงานธรรมดา

หน้าตาของการชนกำแพงเป็นแบบนี้ นี่คือ endpoint แบบ OpenAI compatible
ซึ่งเป็นสิ่งที่ `OpenAICompatProvider` คุยด้วย

```json
{
  "error": {
    "message": "This model's maximum context length is 8192 tokens. However, your messages resulted in 9317 tokens. Please reduce the length of the messages.",
    "type": "invalid_request_error",
    "param": "messages",
    "code": "context_length_exceeded"
  }
}
```

และ failure แบบเดียวกันจาก endpoint ของ Anthropic โดยตรง ซึ่งเป็นสิ่งที่
`AnthropicProvider` คุยด้วย

```json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "prompt is too long: 213558 tokens > 200000 maximum"
  }
}
```

มีสองเรื่องใน body เหล่านั้นที่ควรสังเกตก่อนจะไปต่อ

ตัวเลขในข้อความคือตัวเลขของ provider ไม่ใช่ของคุณ มันเป็น 9317 เพราะ
tokeniser (ตัวแบ่งข้อความออกเป็น token) ของ provider นั้นบอกว่า 9317 ไม่มีอะไรที่คุณคำนวณเองในเครื่องแล้วจะ
ได้ตัวเลขเดียวกันเป๊ะ หัวข้อ 6 ว่าด้วยผลที่ตามมาจากเรื่องนี้ทั้งหัวข้อ

status เป็น 400 ไม่ใช่ 413 หรือ 429 ในสายตาของ API มันคือ request ที่ผิดรูป
อยู่ในหมวดเดียวกับการส่ง field ที่มันไม่รู้จักเป๊ะ ๆ เรื่องนี้สำคัญกับบทที่ 17
เพราะ `400` ไม่คุ้มที่จะ retry การส่งบทสนทนาที่ใหญ่เกินตัวเดิมซ้ำก็ได้การปฏิเสธ
แบบเดิม และ retry loop แบบไร้เดียงสาจะทำแบบนั้นสามครั้งพร้อม exponential backoff
ก่อนจะยอมแพ้ ซึ่งเป็นการเสียเวลาแปดวินาทีไปกับการพิสูจน์สิ่งที่รู้ได้ทันที

สิ่งที่คุณเห็นจริง ๆ บน terminal ให้ข้อมูลน้อยกว่า JSON body ทั้งสองอัน
เพราะ `providers.py` ทำ streaming และเรียก `response.raise_for_status()` บน
response ที่ยังไม่ได้อ่าน body

```text
Traceback (most recent call last):
    File "main.py", line 58, in <module>
    run(provider, task, system=system)
  File "agent.py", line 48, in run
    text, calls = provider.stream(
  File "providers.py", line 46, in stream
    response.raise_for_status()
httpx.HTTPStatusError: Client error '400 Bad Request' for url 'http://localhost:11434/v1/chat/completions'
For more information check: https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/400
```

คำอธิบายอยู่ใน body แต่สิ่งที่คุณได้คือบรรทัด status จำเรื่องนี้ไว้
เพราะมันจะสำคัญมากในหัวข้อ 3

ยังมี failure mode แบบที่สามซึ่งแย่กว่า error ทั้งสองแบบ และคุณควรรู้ว่ามันมีอยู่
local runtime หลายตัวไม่ปฏิเสธ prompt ที่ใหญ่เกินเลย มันเงียบ ๆ ตัด prompt
ให้พอดีกับ context length ที่ตั้งค่าไว้ ปกติตัดจากด้านหน้า แล้วตอบกลับมา
ไม่มี error ไม่มีคำเตือน ไม่มีบรรทัดใน log ใด ๆ agent ก็แค่สับสนว่าคุณสั่งอะไรไป
และคุณเสียเวลาครึ่งชั่วโมงงงว่าทำไมมันลืมงาน error ถือเป็นของขวัญเมื่อเทียบกับแบบนั้น

## 2. วิธีที่คิดออกทันที และเหตุผลที่มันคือหายนะ

สัญชาตญาณมาทันทีและรูปร่างของมันก็ถูกต้อง บทสนทนาใหญ่เกินไป ข้อความใหม่สุดสำคัญที่สุด
ดังนั้นตัดข้อความออกจากด้านหน้าไปเรื่อย ๆ จนกว่ายอดรวมจะพอดี

เขียนออกมาแล้วประมาณสิบบรรทัด และดูสมเหตุสมผลทุกประการ

```python
def fit_to_budget_the_wrong_way(messages, budget):
    """Do not do this."""
    system = [m for m in messages if m["role"] == "system"]
    rest = [m for m in messages if m["role"] != "system"]

    kept = []
    used = estimate_tokens(system)
    for message in reversed(rest):
        cost = estimate_tokens([message])
        if kept and used + cost > budget:
            break
        kept.insert(0, message)
        used += cost
    return system + kept
```

ลองอ่านเทียบกับ `fit_to_budget` ตัวจริงใน `context.py` แล้วสังเกตว่ามันใกล้กันแค่ไหน
โครงสร้างเดียวกัน guard เดียวกัน ตัวสะสมเดียวกัน การกลับลำดับเหมือนกัน
ความต่างอยู่ที่คำเดียว เวอร์ชันนี้เดินบน `rest` ส่วนตัวจริงเดินบน
`split_into_blocks(rest)`

ทีนี้ลองรันมันบนบทสนทนาจาก `check.py` ซึ่งจงใจให้เป็นบทสนทนาที่เล็กที่สุด
ที่สาธิตบั๊กนี้ได้

```python
CONVERSATION = [
    {"role": "system", "content": "be terse"},
    {"role": "user", "content": "first question"},
    {
        "role": "assistant",
        "content": "",
        "tool_calls": [
            {"id": "c1", "type": "function", "function": {"name": "add", "arguments": "{}"}}
        ],
    },
    {"role": "tool", "tool_call_id": "c1", "content": "result"},
    {"role": "assistant", "content": "first answer"},
    {"role": "user", "content": "second question"},
    {"role": "assistant", "content": "second answer"},
]
```

เจ็ดข้อความ ภายใต้ `estimate_tokens` พวกมันมีราคา 6 7 24 5 7 7 และ 7 token
รวมหกสิบสาม ข้อความของ assistant ที่มี tool call เป็นตัวแพงที่ 24
เพราะ object ของ call ที่ถูก serialise ถูกนับรวมไปกับ content ด้วย

ให้ budget (เพดาน token ที่ request หนึ่งใช้ได้) เป็น 40 กับเวอร์ชันที่ผิด แล้วนี่คือสิ่งที่ได้กลับมา

```json
[
  {
    "role": "system",
    "content": "be terse"
  },
  {
    "role": "tool",
    "tool_call_id": "c1",
    "content": "result"
  },
  {
    "role": "assistant",
    "content": "first answer"
  },
  {
    "role": "user",
    "content": "second question"
  },
  {
    "role": "assistant",
    "content": "second answer"
  }
]
```

ดูข้อความที่สอง

มีข้อความที่ role เป็น `tool` และมี `tool_call_id` เป็น `c1` แต่ไม่มีข้อความไหน
ในลิสต์นั้นที่มี tool call ซึ่งมี id เป็น `c1` อีกแล้ว ข้อความ assistant ราคาแพง
ที่เป็นคนเรียกนั้นมีราคา 24 token และเป็นตัวแรกที่เกินเส้น มันจึงถูกตัดทิ้ง
ส่วนผลลัพธ์ของมันซึ่งมีราคา 5 token นั้นถูก จึงรอด

นั่นคือ orphaned tool result และมันไม่ใช่ปัญหาเชิงความสวยงาม

## 3. tool result ที่ถูกทิ้งให้ลอย

นี่คือหัวใจของบทนี้ อ่านช้า ๆ เพราะทุกอย่างเกี่ยวกับวิธีที่บั๊กนี้แสดงตัวออกมา
ถูกออกแบบมาเพื่อส่งคุณไปหาผิดที่

### กฎที่ API บังคับใช้จริง

ทุก provider ที่รองรับ tool calling บังคับใช้กฎเชิงโครงสร้างข้อเดียวกัน
ไม่ว่ารูปแบบภายนอกจะต่างกันอย่างไร tool result ต้องมี tool call ที่มันตอบอยู่ข้างหน้า
การจับคู่ทำผ่าน id มันไม่ใช่ธรรมเนียม ไม่ใช่ข้อแนะนำ และไม่ใช่สิ่งที่ model แค่ชอบมากกว่า
มันถูก validate บนเซิร์ฟเวอร์ก่อนที่จะมี token สักตัวถูกสร้างขึ้น

เหตุผลไม่ได้ตั้งขึ้นมาลอย ๆ tool result ไม่ใช่ข้อเท็จจริงที่ยืนอยู่ได้ด้วยตัวเอง
ลำพังตัวมันเอง `{"role": "tool", "tool_call_id": "c1", "content": "result"}`
คือ string ชื่อ `result` ที่ไม่มีชื่อ ไม่มี argument และไม่มี context
ไม่มีอะไรใน object นั้นบอกว่า tool ตัวไหนทำงานหรือถูกถามอะไร ทั้งหมดนั้นอยู่ใน
ข้อความ assistant ที่เป็นคนเรียก เอา call ออกไปแล้วสิ่งที่เหลือก็ไร้ความหมายจริง ๆ
และ API ก็ปฏิเสธที่จะแกล้งทำเป็นว่ามันมีความหมาย

### API ทำอะไรกับ result ที่ลอยอยู่

นี่คือส่วนที่คนคิดผิดเวลาคิดแบบนามธรรม tool result ที่ลอยอยู่ไม่ได้ถูกเมิน
ไม่ได้ถูกข้าม มันไม่ได้ทำให้เกิดคำเตือนหรือคำตอบที่คุณภาพต่ำลง แต่ request
ทั้งตัวถูกปฏิเสธ

จาก endpoint แบบ OpenAI compatible

```json
{
  "error": {
    "message": "Invalid parameter: messages with role 'tool' must be a response to a preceeding message with 'tool_calls'.",
    "type": "invalid_request_error",
    "param": "messages.[1].role",
    "code": null
  }
}
```

คำสะกดผิด `preceeding` เป็นของเขาเอง และมันอยู่ตรงนั้นมาหลายปีแล้ว
ถ้าคุณจะค้นหา error นี้บนเว็บ ให้ค้นด้วยคำที่สะกดผิดนั่นแหละ

จาก endpoint ของ Anthropic โดยตรง ซึ่ง result เป็น content block ไม่ใช่ข้อความ
ถ้อยคำจึงต่างกันแต่กฎไม่ต่าง

```json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "messages.0: unexpected `tool_use_id` found in `tool_result` blocks: toolu_01A09q90qw90lq917835lq9. Each `tool_result` block must have a corresponding `tool_use` block in the previous message."
  }
}
```

และภาพสะท้อนของบั๊กเดียวกัน ซึ่งเป็นสิ่งที่คุณได้เมื่อทิ้ง result แล้วเก็บ call ไว้
การตัดจากด้านหน้ามักไม่ก่อให้เกิดแบบนี้ แต่การตัดจากด้านหลังก่อให้เกิด
และการ crash ระหว่างการ append สองครั้งก็เช่นกัน

```json
{
  "type": "error",
  "error": {
    "type": "invalid_request_error",
    "message": "messages.1: `tool_use` ids were found without `tool_result` blocks immediately after: toolu_01A09q90qw90lq917835lq9. Each `tool_use` block must have a corresponding `tool_result` block in the next message."
  }
}
```

สังเกต `param` ใน body แรก และคำนำหน้า `messages.N` ในอีกสองอัน
provider กำลังบอก index ของข้อความที่เป็นปัญหา นั่นคือ field ที่มีประโยชน์ที่สุด
ใน response และในหัวข้อ 1 คุณได้เห็นแล้วว่าทำไมคุณอาจไม่มีวันได้เห็นมัน
เพราะ `raise_for_status()` บน streaming response ที่ยังไม่ได้อ่านจะให้แค่บรรทัด
status และไม่มีอะไรอีก

### ทำไมมันดูเหมือนโผล่มาจากที่ไหนก็ไม่รู้

ทีนี้มาถึงส่วนที่ทำให้เรื่องนี้แพง ไม่ใช่แค่น่ารำคาญ

ตามไทม์ไลน์ผ่าน loop ใน `agent.py`

```text
turn 6   messages is 5,800 tokens. Under budget. Sent whole. Fine.
         The model calls read_file. The call and its result are appended.
turn 7   messages is now 6,900 tokens. Over budget.
         to_send() trims. The assistant message holding the turn 3 tool call
         goes over the line and is dropped. Its result, being small, is kept.
         The request is sent. It is accepted. The model answers normally.
         Nothing appears on your screen. You notice nothing at all.
turn 8   messages is trimmed again, the same way, and sent.
         400 Bad Request
```

อ่าน turn 7 อีกครั้ง การตัดที่สร้างลิสต์ที่พังไม่ได้ล้มเหลว
request ที่พา orphan (ข้อความ tool ที่คู่ของมันหายไป) ไปด้วยจะถูกปฏิเสธหรือไม่นั้นขึ้นอยู่กับว่าข้อความไหนบังเอิญ
ตกอยู่ฝั่งไหนของ budget ในเทิร์นนั้น ๆ และการจัดเรียงเฉพาะที่ทำให้ validator สะดุด
อาจไม่ปรากฏจนกว่าจะผ่านไปอีกหนึ่งหรือสองเทิร์น

ความเสียหายเกิดขึ้นเมื่อเทิร์นก่อน โดย function ที่ไม่ error ไม่พิมพ์อะไร และทิ้ง
บทสนทนาที่คุณเห็นใน `messages` ไว้ครบถ้วนสมบูรณ์ เพราะลิสต์ที่ถูกตัดเป็นสำเนา
ที่ถูกโยนทิ้งทันทีที่สร้าง request เสร็จ หัวข้อ 7 อธิบายว่าทำไมสำเนานั้นถึงควรเป็นสำเนา
และนั่นก็เป็นเหตุผลด้วยว่าทำไมคุณหาลิสต์ที่พังไม่เจอจากการเปิดไฟล์ session ทีหลัง

เพื่อจะหาบั๊กนี้เจอ คุณต้องสงสัย function ที่ไม่สร้าง error ในเทิร์นก่อนหน้าเทิร์น
ที่ล้มเหลว และผลลัพธ์ของมันไม่เคยถูกบันทึกไว้ที่ไหนเลย นั่นเป็นส่วนผสมที่โหดร้ายจริง ๆ

## 4. Block แทนข้อความ

ซึ่งนั่นคือวิธีแก้ อย่ามองข้อความทีละตัว ให้มองเป็น exchange

exchange เริ่มที่ข้อความของ user และวิ่งไปจนถึงก่อนข้อความ user ตัวถัดไป
ทุกอย่างที่ assistant พูดระหว่างนั้น ทุก tool ที่มันเรียก และทุก result ที่กลับมา
ล้วนเป็นของคำถามที่จุดชนวนมัน โค้ดสิบห้าบรรทัดใน `context.py` ทำสิ่งนี้

```python
def split_into_blocks(messages):
    """Group messages into exchanges that each begin with a user message.

    Everything the assistant said and every tool it ran belongs to the
    question that prompted it, so the question and its consequences travel
    together or not at all.
    """
    blocks = []
    for message in messages:
        if message["role"] == "user" or not blocks:
            blocks.append([message])
        else:
            blocks[-1].append(message)
    return blocks
```

ลองเดินตามมันบนข้อความที่ไม่ใช่ system ทั้งหกตัวของ fixture

| ข้อความ | Role | `blocks` หลังข้อความนี้ |
| --- | --- | --- |
| `first question` | user | หนึ่ง block ที่เก็บมันไว้ |
| tool call ของ `c1` | assistant | block เดิม ตอนนี้มีสองข้อความ |
| result ของ `c1` | tool | block เดิม ตอนนี้มีสามข้อความ |
| `first answer` | assistant | block เดิม ตอนนี้มีสี่ข้อความ |
| `second question` | user | block ที่สองเริ่มขึ้น |
| `second answer` | assistant | block ที่สอง ตอนนี้มีสองข้อความ |

สอง block ตัวแรกคือ `["user", "assistant", "tool", "assistant"]` และมีราคา
43 token ตัวที่สองคือ `["user", "assistant"]` และมีราคา 14 ข้อความ system
ถูกจัดการแยกต่างหาก มันจึงไม่อยู่ใน block ไหนเลย

รายละเอียดสามข้อในสิบห้าบรรทัดนั้นควรได้รับคำอธิบายอย่างละหนึ่งประโยค

`or not blocks` ไม่ใช่พิธีกรรม มันคือสิ่งที่เกิดขึ้นเมื่อข้อความแรกที่ส่งมาให้คุณ
ไม่ใช่ข้อความของ user นั่นเป็นกรณีจริง ไม่ใช่กรณีสมมติ เพราะ session ที่ถูก resume
อาจเริ่มที่จุดไหนก็ได้ และบทที่ 13 ก็ให้คุณ resume ได้ ถ้าไม่มีเงื่อนไขนั้น
`blocks[-1]` บนลิสต์ว่างจะโยน `IndexError` เมื่อมีมัน อะไรก็ตามที่มาถึงก่อน
จะเปิด block ใหม่ กฎคือ function นี้ต้องไม่ crash บนบทสนทนาที่มันไม่ได้คาดไว้
เพราะทางเลือกอีกทางคือการ resume session กลายเป็นการโยนหัวก้อย

เส้นแบ่งคือข้อความของ user เท่านั้น ไม่ใช่อย่างอื่น ไม่ใช่ข้อความ assistant
ไม่ใช่ tool result ไม่ใช่ตัวนับเทิร์น เหตุผลคือข้อความของ user เป็น role เดียว
ที่ไม่เคยมีคู่ ข้อความ assistant อาจมี result ที่ชี้กลับมาหามัน ข้อความ tool
ชี้กลับไปหาข้อความ assistant เสมอ ข้อความ user ไม่ชี้ไปหาอะไรและไม่มีอะไรชี้มาหามัน
มันจึงเป็นจุดเดียวที่ตัดได้อย่างปลอดภัย

block ใหญ่แค่ไหนก็ได้ ถามคำถามเดียวที่ทำให้ agent วิ่งผ่าน tool call สิบห้าครั้ง
นั่นก็คือหนึ่ง block นี่ไม่ใช่ข้อบกพร่องและไม่ใช่สิ่งที่ควรแก้ด้วยการซอย block ใหญ่
การสืบสวนที่ใช้สิบห้า call คือหน่วยความหมายหนึ่งหน่วย และครึ่งหนึ่งของมันก็ไม่ค่อย
มีประโยชน์อยู่แล้ว หัวข้อ 5 จัดการกับสิ่งที่เกิดขึ้นเมื่อ block ใหม่สุดตัวเดียว
ก็ใหญ่เกิน budget แล้ว

ตอนนี้ `fit_to_budget` อ่านแล้วแทบเหมือนหายนะในหัวข้อ 2

```python
def fit_to_budget(messages, budget: int):
    system = [m for m in messages if m["role"] == "system"]
    rest = [m for m in messages if m["role"] != "system"]
    blocks = split_into_blocks(rest)

    kept = []
    used = estimate_tokens(system)
    for block in reversed(blocks):
        cost = estimate_tokens(block)
        if kept and used + cost > budget:
            break
        kept.insert(0, block)
        used += cost
    return system + [message for block in kept for message in block]
```

ใหม่สุดก่อน เพราะอดีตที่เพิ่งผ่านมาคือสิ่งที่ model ต้องใช้ทำงานต่อ หยุดที่ block แรก
ที่ใส่ไม่ลง แทนที่จะข้ามมันไปลอง block ที่เก่ากว่า เพราะบทสนทนาที่มีรูตรงกลาง
แย่กว่าบทสนทนาที่สั้นกว่าแต่ต่อเนื่อง และบรรทัดสุดท้ายแบนมันกลับมาเป็นลิสต์ของ
ข้อความที่ provider ต้องการ ซึ่งเป็นที่เดียวที่รูปแบบแบนราบได้รับอนุญาตให้มีอยู่

คุณสมบัติที่สำคัญตอนนี้เป็นเรื่องเชิงโครงสร้าง ไม่ใช่สิ่งที่คุณต้องจำ tool call
กับ result ของมันอยู่ใน block เดียวกันโดยการก่อสร้าง block ถูกเก็บทั้งก้อนหรือ
ถูกทิ้งทั้งก้อน ดังนั้นไม่มีลำดับการตัดใด ๆ ที่จะแยกมันออกจากกันได้ คุณไม่ได้กำลัง
ระวัง invariant คุณทำให้มันถูกละเมิดไม่ได้เลย

## 5. สิ่งที่ต้องไม่ถูกตัดทิ้งเด็ดขาด

มีสองอย่างที่ได้รับการยกเว้น และแต่ละอย่างมีเหตุผลที่จะเผยตัวก็ต่อเมื่อคุณ
พิจารณาว่าจะเกิดอะไรขึ้นถ้าไม่มีมัน

### ข้อความ system

```python
    system = [m for m in messages if m["role"] == "system"]
    rest = [m for m in messages if m["role"] != "system"]
```

มันถูกดึงออกมาก่อนที่จะมีการวัดอะไรทั้งสิ้น และถูกใส่กลับเข้าไปโดยไม่มีเงื่อนไข
ในตอนท้าย มันถูกตัดทิ้งไม่ได้เพราะมันไม่เคยเป็นตัวเลือกให้ตัดเลย

ในโปรแกรมนี้ ข้อความ system ยังเป็นหนึ่งในข้อความที่เก่าที่สุดในบทสนทนาด้วย
`run` append มันเป็นตัวแรก ภายใต้นโยบายใดก็ตามที่ตัดของเก่าที่สุดทิ้ง มันจะไปเป็นตัวแรก
และมันคือสิ่งสุดท้ายที่คุณอยากเสียไป

ลองคิดดูว่าคุณอยาก debug failure แบบไหนมากกว่ากัน agent ที่ลืมจุดเริ่มต้นของบทสนทนา
ยังรู้ว่าต้องประพฤติตัวอย่างไร ยังรู้ว่าตัวเองถูกจำกัดอยู่ใน directory ไหน
ยังรู้ข้อเท็จจริงเกี่ยวกับ workspace ที่ `build_system_prompt` ให้ไว้ มันเสียประวัติไป
มันจะขอให้คุณเตือนว่าคุณต้องการอะไร ซึ่งน่ารำคาญแต่กู้คืนได้

agent ที่ลืมคำสั่งของตัวเองกลางทางของงานเป็นสัตว์คนละชนิด มันคือ model ดิบ
พร้อมชุด tool ที่แก้ไฟล์และรันคำสั่ง shell ได้ โดยไม่มีข้อความใดบอกว่ามันควรทำอะไร
หรือควรประพฤติตัวอย่างไร มันไม่ประกาศว่ามันทำคำสั่งหาย เพราะมันไม่มีความทรงจำว่า
เคยมีคำสั่งเหล่านั้น มันแค่เริ่มประพฤติตัวต่างไป กลางงาน ทั้งที่ไฟล์ของคุณอยู่ในมือมัน

failure สองแบบนี้เทียบกันไม่ได้ เราจึงเลือกแบบที่ราคาถูกทุกครั้ง

`check.py` ทำให้มันเป็นกฎ

```python
    if fit_to_budget(CONVERSATION, budget=1)[0]["role"] != "system":
        fail("the system message was dropped, so the agent forgot its instructions")
```

budget หนึ่ง token ไม่มีอะไรอื่นใส่ลงไปได้เลย ข้อความ system ต้องยังอยู่เป็นตัวแรก

### Block ใหม่สุด แม้ตัวมันเดียวจะเกิน budget

นี่คือ `kept and` ในเงื่อนไข และมันอ่านผ่านไปได้ง่ายมาก

```python
        if kept and used + cost > budget:
            break
```

ในรอบแรก `kept` ว่าง เงื่อนไขทั้งหมดจึงเป็นเท็จไม่ว่าราคาจะเท่าไร และ block ใหม่สุด
ถูก append เข้าไปไม่ว่ามันจะใหญ่แค่ไหน budget เริ่มมีอำนาจตั้งแต่รอบที่สองเป็นต้นไปเท่านั้น

ลบสองคำนั้นออกแล้ว function จะถูกต้องในเชิงเลขคณิตและไร้ประโยชน์ในทางปฏิบัติ
บน fixture นี้ ที่ข้อความ system ราคา 6 และ block ใหม่สุดราคา 14 ทุก budget
ตั้งแต่ 1 ถึง 19 จะคืนแค่ข้อความ system เท่านั้น คุณจะส่ง system prompt
พร้อม tool schema เจ็ดตัว โดยไม่มีบทสนทนาเลย

เปรียบเทียบ failure สองแบบอีกครั้ง เพราะเหตุผลมีรูปร่างเดียวกับก่อนหน้านี้

ส่ง request ที่ใหญ่เกินแล้วคุณจะได้ `400` จากหัวข้อ 1 ซึ่งบอกทั้งขีดจำกัดและขนาด
ที่คุณเกินมา มันชัดเจน มันชี้ไปที่ปัญหาที่ถูกต้อง และวิธีแก้ก็เห็นได้ชัด

ส่งบทสนทนาที่ไม่มีข้อความ user เลยแล้วคุณจะได้ `200` model ตอบกลับมา
มันมี system prompt ที่บอกว่ามันคือ coding agent ใน directory หนึ่งพร้อม tool เจ็ดตัว
และไม่มีอะไรให้ทำ มันจึงคิดอะไรขึ้นมาเอง มันทักทายคุณ มันถามว่าคุณต้องการอะไร
มันเลือกไฟล์มาไฟล์หนึ่งแล้วเริ่มบรรยาย ไม่ว่ามันจะทำอะไร มันก็ลื่นไหลและลอยเคว้ง
และไม่มีอะไรใน response ที่บ่งชี้ว่ามีอะไรผิดพลาด รายงานของผู้ใช้จะบอกว่า agent
เพี้ยนไปแล้ว ซึ่งถูกต้อง และเอาไปทำอะไรต่อไม่ได้

อย่าแลก error ที่ชัดเจนกับคำตอบผิดที่มั่นใจเด็ดขาด model ที่ได้รับความว่างเปล่า
ไม่ล้มเหลวแบบส่งเสียงดัง และนั่นแหละคือเหตุผลว่าทำไมบทสนทนาว่างเปล่าจึงเป็นผลลัพธ์

## 6. ทำไมค่าประมาณถึงหยาบโดยตั้งใจ

ทีนี้มาถึง `estimate_tokens` ซึ่งเป็นชิ้นส่วนที่มีแนวโน้มถูกเข้าใจผิดว่าเป็นจุดอ่อน
ของโมดูลนี้มากที่สุด

```python
CHARACTERS_PER_TOKEN = 4
PER_MESSAGE_OVERHEAD = 4


def estimate_tokens(messages):
    total = 0
    for message in messages:
        total += len(message.get("content") or "") // CHARACTERS_PER_TOKEN
        for call in message.get("tool_calls") or []:
            total += len(str(call)) // CHARACTERS_PER_TOKEN
        total += PER_MESSAGE_OVERHEAD
    return total
```

หารจำนวนตัวอักษรด้วยสี่ บวกสี่ต่อหนึ่งข้อความสำหรับ role และกรอบที่ provider
เติมรอบ ๆ แต่ละข้อความ นับ tool call ที่ถูก serialise ด้วยเพราะมันใหญ่และมันถูกส่งไป
ทั้งหมดมีแค่นั้น

มันผิด มันผิดโดยตั้งใจ และไม่มีเวอร์ชันไหนของมันที่ถูก

ทุก provider นับต่างกัน token คือสิ่งที่ tokeniser ตัวหนึ่งบอกว่ามันเป็น
OpenAI ใช้ tokeniser ต่างกันใน model แต่ละรุ่น string เดียวกันจึงมีจำนวน token
ต่างกันบนสอง model จากบริษัทเดียวกัน tokeniser ของ Anthropic ก็ต่างออกไปอีก
และไม่ได้เผยแพร่ model open weight ก็มาพร้อม tokeniser ของตัวเอง ไม่มีจำนวน token
สากลของ string ใด ๆ มีแต่จำนวนที่สัมพันธ์กับ tokeniser ตัวหนึ่ง

tokeniser ที่สร้างมาเพื่อบริษัทหนึ่งนับ token ของอีกบริษัทไม่ได้
นี่คือความผิดพลาดที่ควรเรียกชื่อออกมาให้ชัด เพราะมันเป็นความผิดพลาดที่ดูเหมือน
ความขยัน คุณติดตั้ง `tiktoken` ซึ่งเป็น tokeniser ของจริงที่ OpenAI เขียน
คุณรันมันบนข้อความของคุณ แล้วได้ตัวเลขที่แม่นยำ มันแม่นยำและมันเป็นของ model ผิดตัว
ชี้ agent นั้นไปที่ Claude หรือไปที่ Qwen ที่รันในเครื่อง แล้วคุณกำลังคำนวณ
คำตอบที่เป๊ะของคำถามที่ไม่มีใครถาม ความแม่นยำยิ่งทำให้แย่ลง เพราะตัวเลขหยาบ ๆ
ชวนให้คุณเผื่อที่ไว้ ส่วนตัวเลขเป๊ะ ๆ ชวนให้คุณเชื่อมัน

สี่ตัวอักษรต่อหนึ่ง token จริงเฉพาะกับร้อยแก้วภาษาอังกฤษ โค้ดถูก tokenise
ได้แย่กว่า เพราะ identifier เครื่องหมายวรรคตอน และการย่อหน้าถูกแตกออกเป็นชิ้น
JSON ยิ่งแย่กว่านั้นอีก ภาษาไทย ญี่ปุ่น และจีนแย่กว่ามาก บ่อยครั้งเข้าใกล้
หนึ่ง token ต่อหนึ่งตัวอักษร ค่าประมาณที่ใกล้เคียงถูกสำหรับบทสนทนาภาษาอังกฤษ
จึงอาจคลาดเคลื่อนถึงสามเท่าสำหรับบทสนทนาภาษาไทย และเนื่องจาก tool result ใน agent
ตัวนี้ส่วนใหญ่เป็นซอร์สโค้ดกับ JSON ค่าประมาณตรงนี้จึงเอนไปทางนับต่ำกว่าความจริง

และมันไม่ได้นับทุกอย่างที่ถูกส่งไป นี่คือช่องว่างที่ใหญ่ที่สุดและมันไม่ได้อยู่
ใน function เลย `estimate_tokens` วัดข้อความ แต่ request ยังพา tool schema เจ็ดตัว
ไปด้วย ซึ่ง serialise ออกมาได้ 2595 ตัวอักษรในบทนี้ ประมาณหกร้อยห้าสิบ token
ในทุก request ไม่มีอะไรใน `context.py` รู้ว่ามันมีอยู่

กฎการใช้งานจึงเป็นอย่างที่เขียนไว้ใน docstring

```python
    """A rough count, deliberately not exact.

    Every provider counts differently and none of them count the way a
    character estimate does. Use this to decide when to start trimming, then
    use the number the provider reports afterwards to know what actually
    happened. Trusting a local estimate to be exact is how people end up
    trimming to ninety percent of a window and still getting rejected.
    """
```

ใช้มันเพื่อตัดสินใจว่าจะเริ่มตัดเมื่อไรนั้นไม่มีปัญหา การตัดไม่ใช่ปฏิบัติการที่แม่นยำ
คุณแค่ต้องรู้คร่าว ๆ ว่าบทสนทนากำลังใหญ่ขึ้นเมื่อไร และการผิดพลาดยี่สิบเปอร์เซ็นต์
หมายถึงคุณตัดเร็วไปนิดหรือช้าไปนิด ซึ่งทั้งสองแบบก็รอดได้

การใช้มันเป็นตัวเลขที่เป๊ะคือวิธีที่ทำให้คนถูกปฏิเสธที่เก้าสิบเปอร์เซ็นต์ของ window
ตรรกะคือ window เท่ากับ 8192 ก็ตัดให้เหลือ 7372 ซึ่งเผื่อไว้สิบเปอร์เซ็นต์
และนั่นน่าจะเหลือเฟือ จากนั้นค่าประมาณนับต่ำไปสิบห้าเปอร์เซ็นต์เพราะบทสนทนา
เต็มไปด้วย JSON และ schema เพิ่มอีกหกร้อยห้าสิบ token ที่ไม่เคยอยู่ในผลรวม
แล้ว request ก็กลายเป็น 9317 token และคุณก็ได้ error จากหัวข้อ 1 ขณะที่มอง
บรรทัด log ที่เขียนว่า 7372 ซึ่งส่งคุณไปตามล่าบั๊กในเลขคณิตที่ไม่มีอยู่จริง
เพราะเลขคณิตนั้นไม่เคยเป็นสิ่งที่ถูกต้องได้ตั้งแต่แรก

ดังนั้นให้เลือก budget ที่เผื่อไว้จริง ๆ มองตัวเลขเป็นสัญญาณไม่ใช่การวัด
แล้วไปเอาความจริงจาก provider ทีหลัง ทุก response พา usage block ที่มีจำนวน
ที่ถูกคิดเงินจริงมาด้วย การอ่านมัน การลงมือทำตามมัน และการทำให้ต้นทุนมองเห็นได้
คือบทที่ 15

## 7. สิ่งที่เดินทางไม่ใช่สิ่งที่ถูกจดจำ

การเปลี่ยนแปลงใน `agent.py` มีสี่บรรทัด และการตัดสินใจเชิงออกแบบหนึ่งข้อ

```python
    def to_send():
        """What travels is not what is remembered.

        The whole conversation stays in messages because the session file
        and anyone debugging later need all of it. Only the copy handed to
        the provider is trimmed.
        """
        return messages if budget is None else fit_to_budget(messages, budget)
```

และที่จุดเรียกใช้

```python
        text, calls = provider.stream(
            to_send(), schemas, on_text=lambda piece: print(piece, end="", flush=True)
        )
```

`messages` ไม่เคยถูกตัด มันโตขึ้นตลอดการรันและเก็บทุกอย่าง `fit_to_budget`
คืนลิสต์ใหม่ `provider.stream` ได้ลิสต์นั้น และมันถูกทิ้งเมื่อ request เสร็จ

ทางเลือกอีกทางคือตัดในที่เดิม ซึ่งสั้นกว่าหนึ่งบรรทัดและทำลายสิ่งที่คุณต้องการ

ไฟล์ session จะสูญเสียข้อความ `remember` เรียก `on_message` ซึ่งในบทที่ 13
คือ `session.append` ถ้าการตัดไปเปลี่ยนค่า `messages` ไฟล์ session ก็จะยังมี
บรรทัดที่ถูกตัดอยู่ เพราะมันถูกเขียนไปตอนที่มันเกิดขึ้น แต่บทสนทนาในหน่วยความจำ
กับไฟล์จะเริ่มแยกจากกัน และการ resume จะโหลดข้อความที่ agent ที่กำลังรันตัดสินใจ
ลืมไปแล้วกลับมา แหล่งความจริงสองแหล่งเกี่ยวกับบทสนทนาเดียวกันคือเครื่องผลิตบั๊ก

การ debug จะเป็นไปไม่ได้ บทที่ 13 ให้เหตุผลว่าคุณค่าสูงสุดของไฟล์ session
ไม่ใช่การ resume แต่คือเมื่อ agent ทำอะไรที่อธิบายไม่ได้ คุณเปิดไฟล์แล้วอ่านได้เป๊ะ ๆ
ว่ามันเห็นอะไร เหตุผลนั้นจะยืนอยู่ได้ก็ต่อเมื่อไฟล์ครบถ้วน agent ที่ทิ้งการอ่านไฟล์
ในเทิร์น 7 แล้วไปขัดแย้งกับไฟล์นั้นในเทิร์น 9 กำลังทำตัวสมเหตุสมผลอย่างสมบูรณ์
และคุณจะเข้าใจเรื่องนี้ได้ก็ต่อเมื่อเทิร์น 7 ยังอยู่บนดิสก์

การตัดเป็นคุณสมบัติของ request ไม่ใช่ของบทสนทนา นี่คือวิธีมองที่สะอาดที่สุด
budget เป็นของ model ที่คุณกำลังคุยด้วยตอนนี้ สลับจาก model local ขนาดแปดพัน token
ไปเป็น model hosted ขนาดสองแสน token กลางคัน แล้วประวัติเดิมควรใส่ลงไปได้ทันที
และมันทำได้ เพราะประวัติไม่เคยเสียหาย มีแต่สำเนาที่เล็กลง

และการตัดถูกคำนวณใหม่ทุกเทิร์น `to_send` เป็น function ไม่ใช่ค่าที่คำนวณครั้งเดียว
ก่อนเข้า loop ในแต่ละเทิร์นมันดู `messages` ปัจจุบันแล้วตัดสินใจใหม่ block ที่ถูกตัด
ในเทิร์น 7 กลับมาได้ในเทิร์น 8 ถ้า budget อนุญาต ซึ่งจะอนุญาตถ้า block ใหม่สุดเล็ก
การตัดไม่มีความทรงจำและก็ไม่จำเป็นต้องมี

มีต้นทุนหนึ่งอย่างที่ต้องพูดตรง ๆ และหัวข้อ 3 บอกไว้แล้ว ลิสต์ที่ถูกส่งไปจริง
มีอยู่แค่ภายในการเรียก `stream` ถ้าคุณต้องการเห็นมัน และตอน debug บั๊กเรื่องการตัด
คุณต้องการแน่ ๆ คุณต้องพิมพ์มันตรงนั้น นั่นคือราคาของการรักษาบันทึกให้ครบถ้วน
และมันเป็นฝั่งที่ถูกต้องของการแลกเปลี่ยน

ค่าเริ่มต้นคือ `budget=None` ซึ่งหมายถึงไม่ตัดอะไรเลย พฤติกรรมของทุกบทก่อนหน้า
ไม่เปลี่ยนแปลงจนกว่าคุณจะขอพฤติกรรมใหม่

## 8. การสรุปแทนการตัดทิ้ง และทำไมไม่ใช้ที่นี่

มีคำตอบที่ดีกว่าการตัดทิ้ง และมันสมควรได้รับการพิจารณาอย่างเป็นธรรมมากกว่าการ
ปัดตก เพราะคุณจะเอื้อมไปหามันแน่นอน

แนวคิดคือแทนที่จะทิ้ง block เก่าที่สุด คุณส่งมันไปให้ model พร้อมคำขอให้สรุป
แล้วแทนที่มันด้วยบทสรุป การสำรวจหนึ่งหมื่นสองพัน token กลายเป็นสี่ร้อย token
ที่บอกว่าอ่านไฟล์ไหนบ้าง ในนั้นมีอะไร ลองอะไรไปแล้ว และอะไรล้มเหลว harness
ของจริงทุกตัวทำเวอร์ชันใดเวอร์ชันหนึ่งของสิ่งนี้ และเหตุผลก็สมเหตุสมผล

สรุปแล้วได้อะไรกลับมาจริง ๆ การตัดทิ้งทำให้ข้อมูลหายไปถาวร ถ้า agent อ่านไฟล์ config
ในเทิร์น 2 แล้วต้องการค่าจากมันในเทิร์น 20 การตัดทิ้งหมายความว่ามันต้องอ่านไฟล์
ใหม่ ซึ่งเสียหนึ่งเทิร์นและ token เท่าเดิม การสรุปเก็บร่องรอยที่ถูกบีบอัดของทุกอย่างไว้
agent จึงยังรู้ว่าไฟล์นั้นมีอยู่และในนั้นมีอะไรคร่าว ๆ ในงานยาว ๆ ความต่างนั้นใหญ่มาก

ที่มันไม่อยู่ในบทนี้ก็เพราะต้นทุน

มันเสียการเรียก model เพิ่มอีกหนึ่งครั้ง โดยมีช่วงทั้งหมดที่กำลังสรุปเป็น input
การเรียกนั้นไม่ฟรีทั้งในแง่เงินและในแง่เวลา มันเกิดขึ้นกลางงาน ขณะที่คุณกำลังดูอยู่
และ agent หยุดไปหลายวินาทีเพื่อคิดเรื่องประวัติของตัวเองแทนที่จะคิดเรื่องปัญหาของคุณ

มันอาจทำให้รายละเอียดที่สำคัญหายไป บทสรุปคือการบีบอัดแบบสูญเสียที่ถูกเลือกโดย model
ที่ไม่รู้ว่าคุณจะต้องการรายละเอียดไหนในเทิร์น 20 failure มีลักษณะเฉพาะและน่ารำคาญ
บทสรุปบอกว่า test ถูกรันแล้วและสองตัว fail ส่วนข้อความ assertion ที่เป๊ะ ๆ
ซึ่งมีตัวเลขที่อธิบายทุกอย่างนั้นหายไป การตัดทิ้งทำให้เสียเยอะแบบเห็นได้ชัด
การสรุปทำให้เสียนิดหน่อยแบบมองไม่เห็น และการสูญเสียที่มองไม่เห็นนั้นคิดตามได้ยากกว่า
เพราะตอนนี้ agent เชื่ออย่างมั่นใจในเวอร์ชันของอดีตตัวเองที่ผิดไปนิดหน่อย

และมันทำให้บทสนทนาทำซ้ำไม่ได้ รัน session เดิมสองครั้งด้วย input เดิมแล้วคุณจะได้
บทสรุปสองแบบ เพราะตัวสรุปคือ language model จากจุดนั้นการรันสองครั้งจะมีประวัติ
ต่างกันและแยกทางกัน สำหรับคอร์สที่ `check.py` ทุกตัวต้องให้คำตอบเดิมทุกครั้ง
แค่นั้นก็ตัดออกไปได้แล้ว สำหรับระบบจริงมันหมายความว่าไฟล์ session ไม่อธิบายการรัน
อีกต่อไป เพราะการเล่นซ้ำจะให้ผลอย่างอื่น

มีประเด็นที่สี่ที่ควรรู้และแทบไม่มีใครพูดถึง บทสรุปเข้าสู่บทสนทนาในฐานะข้อความ
และถ้าช่วงที่ถูกสรุปมี tool result ที่มีคำสั่งแฝงอยู่ ตัวสรุปอาจนำคำสั่งเหล่านั้น
เข้าไปในบทสรุปอย่างซื่อสัตย์ ซึ่งตอนนี้มันดูเหมือนเป็นบันทึกของ agent เอง
มากกว่าจะเป็นเนื้อหาของไฟล์ ข้อโต้แย้งของบทที่ 12 เรื่องความยากในการแยกคำสั่ง
ออกจากข้อมูลใช้ได้แรงยิ่งขึ้นกับอะไรก็ตามที่เขียนบทสนทนาใหม่

ค่าเริ่มต้นจึงเป็นการตัด exchange ทั้งก้อนทิ้ง มันเป็น deterministic
มันไม่มีต้นทุน มันยาวประมาณแปดสิบบรรทัดโดยไม่มีการเรียก model เลย มันทดสอบได้ง่ายมาก
ซึ่งเป็นสิ่งที่หัวข้อ 9 ฝึกฝน และข้อมูลที่มันทำหายก็หายไปในแบบที่เห็นได้ชัด
ซึ่ง agent กู้คืนได้ด้วยการอ่านไฟล์ใหม่

การสรุปเป็นสิ่งที่เพิ่มเข้ามาได้อย่างสมเหตุสมผล และการเพิ่มมันบนดีไซน์นี้ก็ตรงไปตรงมา
เพราะ `split_into_blocks` ให้หน่วยสำหรับสรุปกับคุณแล้ว แทนที่ block เก่าชุดหนึ่ง
ด้วย block ที่สังเคราะห์ขึ้นหนึ่งอันแทนที่จะลบมันทิ้ง เก็บ block ใหม่สุดไว้แบบคำต่อคำ
และยกเว้นข้อความ system ต่อไปเหมือนที่เป็นอยู่ ขอบเขตของ block คือรอยต่อที่ถูกต้อง
สำหรับทั้งสองนโยบาย ซึ่งเป็นสัญญาณที่ดีว่ารอยต่ออยู่ถูกที่แล้ว

ทำสิ่งที่ง่ายก่อน แล้ววัดว่าคุณต้องการสิ่งที่ซับซ้อนจริงหรือไม่

## 9. การรัน check.py

จากโฟลเดอร์ของบทนี้ ไม่ต้องมี endpoint และไม่ต้องมี API key เพราะไม่มีอะไร
ในนี้เรียก model

```bash
cd lessons/14-context-management
python check.py
```

```text
OK a tool call and its result stay together in one block
OK the system message is never dropped
OK the newest exchange is the one that is kept
OK no budget produces an orphaned tool result, which is the bug this prevents
OK a full conversation of about 63 tokens is left alone
```

ห้าบรรทัด สามบรรทัดแรกว่าด้วยชิ้นส่วน บรรทัดที่ห้าเป็นการตรวจสอบความสมเหตุสมผลว่า
budget ขนาดใหญ่แล้วไม่มีอะไรเกิดขึ้น และบรรทัดที่สี่คือเหตุผลที่โมดูลนี้มีอยู่

การตรวจข้อแรกพิสูจน์ว่า block ยึดคู่ไว้ด้วยกัน

```python
    blocks = split_into_blocks(CONVERSATION[1:])
    if len(blocks) != 2:
        fail(f"expected two exchanges, got {len(blocks)}")
    if [m["role"] for m in blocks[0]] != ["user", "assistant", "tool", "assistant"]:
        fail("a tool call and its result did not stay in the same block")
```

การ slice ตัดข้อความ system ออก ซึ่ง `fit_to_budget` จัดการแยกอยู่แล้ว
สอง block และ block แรกมี tool call กับ result ของมันติดกัน ซึ่งเป็นคุณสมบัติ
ที่ทุกอย่างที่เหลือตั้งอยู่บนมัน

ข้อสองและข้อสามคือข้อยกเว้นจากหัวข้อ 5 budget เท่ากับหนึ่งยังคืนข้อความ system
เป็นตัวแรก budget เท่ากับ 20 ยังจบด้วย `second answer` ซึ่งพิสูจน์ว่า exchange
ใหม่สุดคือสิ่งที่รอด ไม่ใช่ตัวเก่าสุด ยี่สิบถูกเลือกเพราะมันคือข้อความ system
บวก block ใหม่สุดพอดี มันจึงเป็น budget ที่คับที่สุดที่มีการเลือกอย่างแท้จริงเกิดขึ้น

ข้อสี่คือการกวาด

```python
    for budget in range(1, 60):
        kept = fit_to_budget(CONVERSATION, budget=budget)
        if not result_ids(kept) <= call_ids(kept):
            fail(f"a tool result was left with no tool call at budget {budget}")
        if not any(m["role"] == "user" for m in kept):
            fail(f"nothing was left to answer at budget {budget}")
```

`result_ids(kept) <= call_ids(kept)` คือการทดสอบ subset บนเซตของ id สองเซต
ทุก `tool_call_id` ที่ปรากฏใน result ต้องปรากฏเป็น id ของ call ที่ยังอยู่
นั่นคือกฎของ API จากหัวข้อ 3 เขียนใหม่เป็น Python หนึ่งบรรทัดที่รันใน check
แทนที่จะรันบนเซิร์ฟเวอร์

คำถามที่ควรตอบคือทำไมนี่จึงเป็น loop จาก 1 ถึง 59 แทนที่จะเป็น budget ที่เลือกมาดี ๆ
ค่าเดียว ในเมื่อตัวเลขเดียวสั้นกว่าและดูเหมือนทดสอบสิ่งเดียวกัน

มันไม่ได้ทดสอบสิ่งเดียวกัน และการ implement แบบไร้เดียงสาจากหัวข้อ 2 แสดงให้เห็น
ชัดเจนว่าทำไม รันมันกับ fixture นี้ที่ทุก budget แล้วบันทึกว่าค่าไหนสร้าง orphan บ้าง

```text
budgets 1 to 31    no orphan. the newest block alone, or nothing much
budgets 32 to 55   ORPHAN. the tool result survives, its call does not
budgets 56 to 63   no orphan. both survive
```

ยี่สิบสี่ budget จากหกสิบสามค่าเปิดเผยมัน และสามสิบเก้าค่าซ่อนมันไว้ ถ้า check
เลือก 20 มันผ่าน ถ้าเลือก 60 มันก็ผ่าน ทั้งสองเป็นตัวเลขที่ดูสมเหตุสมผล
และทั้งสองรับรองว่าการ implement ที่พังนั้นถูกต้อง บั๊กไม่ได้มีหรือไม่มี
แต่มันมีอยู่ในช่วงหนึ่ง และ test ที่สุ่มตัวอย่างจุดเดียวนอกช่วงนั้นก็ไม่ได้เรียนรู้อะไรเลย

ช่วงนั้นกว้างเพราะเวอร์ชันไร้เดียงสาผิดอย่างรุนแรง เวอร์ชันที่ละเอียดอ่อนกว่า
จะแคบกว่ามาก เปลี่ยนการเปรียบเทียบใน `fit_to_budget` จาก `used + cost > budget`
เป็น `used + cost >= budget` แล้วสอง implementation จะไม่ตรงกันที่ budget เพียงค่าเดียว
จากทุกค่าที่คุณเลือกได้ ซึ่งสำหรับ fixture นี้คือ 63 จุดที่สอง block บวกข้อความ system
เท่ากับ budget พอดี ข้อผิดพลาดแบบ off by one อาศัยอยู่บนเส้นขอบ และเส้นขอบมี
ความกว้างหนึ่งค่า การเดาว่าค่าไหนไม่ใช่กลยุทธ์ การกวาดต่างหากที่ใช่

assertion ที่สองใน loop คือกฎอีกข้อของหัวข้อ 5 ในรูปของ check ที่ทุก budget
ไม่ว่าจะเล็กแค่ไหน ต้องมีบางอย่างเหลือให้ model ตอบ นั่นคือสิ่งที่จับการลบ `kept and`
ซึ่งบน fixture นี้จะทำให้บทสนทนาว่างเปล่าที่ทุก budget ตั้งแต่ 1 ถึง 19

ข้อห้าพิสูจน์ว่า budget ขนาดใหญ่ไม่เปลี่ยนอะไรเลย

```python
    if fit_to_budget(CONVERSATION, budget=100000) != CONVERSATION:
        fail("a large budget changed the conversation")
```

เทียบความเท่ากันกับลิสต์ต้นฉบับ ไม่ใช่เทียบความยาว มันพิสูจน์ว่าลำดับถูกรักษาไว้
ข้อความ system กลับเข้าไปในตำแหน่งที่ถูกต้อง และไม่มีอะไรถูกทำซ้ำจากการแบนราบ
ในตอนท้าย ตัวตัดที่เงียบ ๆ จัดลำดับบทสนทนาใหม่ทั้งที่ไม่มีงานให้ทำคือตัวตัดที่
คุณจะไม่ไว้ใจมันทีหลัง

ตัวเลข 63 token ที่ถูกพิมพ์ออกมาคือค่าประมาณจากหัวข้อ 6 สำหรับ fixture ทั้งก้อน
มันอยู่ใน output เพื่อเตือนว่าตัวเลขนั้นมีอยู่และเป็นค่าประมาณ ซึ่งเป็นวิธีอ่าน
ที่ถูกต้องพอดี

ถ้าบรรทัดที่สี่ล้มเหลวจากการเปลี่ยนแปลงที่คุณทำ ให้อ่าน budget ในข้อความนั้น
แล้วรัน `fit_to_budget` ที่ budget นั้นด้วยมือ ลิสต์ที่พังซึ่งมันคืนมาจะแสดงให้คุณ
เห็นในพริบตาเดียวว่าครึ่งไหนของคู่หายไป

## 10. สิ่งที่คุณยังทำไม่ได้

ตอนนี้คุณเก็บบทสนทนาให้อยู่ใน window ได้โดยไม่ทำให้มันพัง ยังมีสองอย่างที่ขาดอยู่
และมันคือเรื่องเดียวกันที่พูดสองครั้ง

คุณกำลังตัดโดยอ้างอิงการเดา `budget` คือตัวเลขที่คุณเลือกเอง ค่าประมาณที่ตัดสิน
ว่าจะลงมือเมื่อไรคือการหารด้วยสี่ ไม่มีอะไรในโปรแกรมเคยเปรียบเทียบตัวไหนกับความจริงเลย
คุณอาจกำลังตัดที่หกสิบเปอร์เซ็นต์ของ window แล้วโยน context ที่ไม่จำเป็นต้องเสียทิ้งไป
หรือตัดที่เก้าสิบห้าเปอร์เซ็นต์แล้วยังถูกปฏิเสธอยู่ดี และคุณไม่มีทางรู้ว่าเป็นแบบไหน
เพราะไม่เคยมีตัวเลขจริงเข้ามาในโปรแกรมเลย

คุณไม่รู้เลยว่าทั้งหมดนี้มีต้นทุนเท่าไร ไม่มีจำนวน token สักตัวเดียวถูกพิมพ์
ออกมาโดยอะไรก็ตามในสิบสี่บทที่ผ่านมา คุณบอกไม่ได้ว่างานที่คุณเพิ่งรันไปมีต้นทุน
หนึ่งในสิบเซนต์หรือสี่สิบเซนต์ คุณบอกไม่ได้ว่าส่วนไหนของมันแพง และถ้าไม่มีสิ่งนั้น
การ optimise ทุกอย่างก็เป็นเรื่องงมงาย คุณจะไปย่อ system prompt ซึ่งมีประมาณ
หนึ่งร้อยห้าสิบ token แล้วรู้สึกว่าได้ทำอะไรบางอย่าง ขณะที่ผลลัพธ์ของ `grep_files`
ยาวหนึ่งร้อยแปดสิบบรรทัดติดไปกับทุก request ตลอดที่เหลือของ session และทำให้คุณ
เสียเงินมากกว่าสามสิบเท่า

มีความย้อนแย้งเฉพาะเจาะจงที่ควรนั่งพิจารณา บทนี้เพิ่มกลไกเพื่อจัดการทรัพยากรหนึ่งอย่าง
