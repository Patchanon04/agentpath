# บทที่ 10 กายวิภาคของ prompt

นี่คือบทสุดท้ายก่อนถึง milestone และเป็นบทที่มีอัตราส่วนระหว่างแรงที่ลงกับผลที่ได้
แย่ที่สุดในคอร์สทั้งหมด คุณจะเขียนไฟล์หนึ่งไฟล์ที่มีชื่ออยู่สองชื่อ แล้วเพิ่มโค้ด
สามบรรทัดเข้าไปใน agent loop รวมแล้วอาจราวยี่สิบบรรทัด agent จะไม่ได้ความสามารถ
ใหม่เพิ่มขึ้นแม้แต่อย่างเดียว

แล้ว agent จะใช้ความสามารถเจ็ดอย่างที่มีอยู่แล้วได้ดีขึ้นอย่างเห็นได้ชัด

ฟังดูเหมือนเวทมนตร์ และบทนี้มีอยู่เพื่อไม่ให้มันเป็นเวทมนตร์ต่อไป ทุกอย่างในบทนี้
มีกลไกรองรับ และกลไกนั้นคือกลไกเดียวกับในบทที่ 02 โมเดลเห็นแค่บทสนทนา ไม่เห็นอย่างอื่นเลย
ทุกข้อเท็จจริงที่มันใช้ ทุกกฎที่มันทำตาม ทุกความชอบที่มันเคารพ ล้วนอยู่ในบทสนทนานั้น
ไม่อย่างนั้นมันก็ไม่มีให้ใช้ การทำ prompt ไม่ใช่วิธีโน้มน้าวโมเดล แต่เป็นการตัดสินใจว่า
อะไรจะอยู่ในบทสนทนา

ไฟล์ในโฟลเดอร์นี้

```text
lessons/10-anatomy-of-a-prompt/
  prompt.py      new, builds the system prompt
  agent.py       lesson 09's loop, plus a system message at the front
  tools.py       unchanged from lesson 09, byte for byte
  providers.py   unchanged from lesson 06
  check.py       proves the system prompt exists and arrives first
  README.md      this file
```

สังเกต `tools.py` ในรายการนั้น มันไม่ได้เปลี่ยนเลย และหัวข้อ 6 ส่วนใหญ่พูดถึงส่วนหนึ่ง
ของไฟล์นี้ที่คุณเขียนมาตั้งแต่บทที่ 07 โดยที่ยังไม่มีใครบอกว่ามันคืออะไร

## 1. ปัญหาที่ค้างมาจากบทที่ 09

ตอนจบบทที่ 09 agent มี tool เจ็ดตัว

```text
read_file    write_file    edit_file    list_files
run_shell    glob_files    grep_files
```

นั่นคือชุดที่ครบถ้วน อะไรก็ตามที่นักพัฒนาทำกับ code base ได้ สามารถแสดงออกมาเป็น
ลำดับของ tool เจ็ดตัวนี้ได้ ไม่มีอะไรขาด

ทีนี้ลองเริ่มบทสนทนาจริงแล้วดูว่าโมเดลรู้อะไรบ้าง ในบทที่ 09 บทสนทนาทั้งหมด
ในคำขอแรกมีแค่ข้อความเดียว

```python
messages = [{"role": "user", "content": user_input}]
```

ประโยคเดียวที่คุณพิมพ์เอง นั่นคือโลกทั้งใบ โมเดลไม่รู้ว่ามันยืนอยู่ใน directory ไหน
ไม่รู้ว่าอยู่บน Windows หรือ Linux ไม่รู้ว่า `read_file` หยุดที่ 4000 ตัวอักษร ไม่รู้ว่า
การค้นหานั้นถูกและการอ่านทุกอย่างนั้นแพง ไม่รู้ว่าเมื่อคุณพูดว่า "the config" คุณหมายถึง
ไฟล์ใน repository นี้ ไม่ใช่ไฟล์ใน training data ของมัน

มันจึงเดา ไม่ใช่เพราะมันสะเพร่า แต่เพราะการเดาคือสิ่งเดียวที่มีให้ใช้ และการเดาผิด
ไม่ได้ล้มเหลวแบบเงียบ ๆ มันเสียไปทั้ง turn ซึ่งก็คือ HTTP request เต็มหนึ่งครั้ง
ที่แบกบทสนทนาทั้งหมดไปด้วย บวกกับ token ของความพยายามที่ล้มเหลว ซึ่งจะค้างอยู่
ในบทสนทนาตลอดไป

หน้าตาในทางปฏิบัติเป็นแบบนี้ ร่องรอยสามชุด ทุกชุดเป็นเรื่องธรรมดา

### การเดาที่หนึ่ง path ที่แต่งขึ้นเอง

คุณพิมพ์แบบนี้

```text
You: add a docstring to the start function
```

โมเดลต้องเรียก tool มันไม่รู้เลยว่าอะไรอยู่ตรงไหน และมันอ่าน Python มาเยอะมาก
ใน training data มันจึงผลิต path ที่ธรรมดาที่สุดในเชิงสถิติเท่าที่มันจะนึกออก

```text
[calling read_file with {'path': '/home/user/project/src/main.py'}]
[read_file returned Error: /home/user/project/src/main.py is outside the workspace]
```

นั่นคือหนึ่ง turn ที่เสียไป ไม่ได้เรียนรู้อะไรเกี่ยวกับโปรเจกต์ของคุณเลย โมเดลลองอีกครั้ง
ด้วยการเดาที่สั้นลง

```text
[calling read_file with {'path': 'src/main.py'}]
[read_file returned Error: src/main.py does not exist]
```

เสียไปสอง turn พอถึงครั้งที่สามมันถึงเรียก `list_files` ซึ่งคือสิ่งที่ควรทำตั้งแต่แรก
และคือสิ่งที่มันจะทำตั้งแต่แรกถ้ามีใครบอกว่ามันกำลังยืนอยู่ใน directory ที่ไม่คุ้นเคย
ไม่ใช่ยืนอยู่ในค่าเฉลี่ยจินตนาการของทุกโปรเจกต์ Python ที่เคยถูกเขียนมา

### การเดาที่สอง คำสั่ง Unix บน Windows

คุณอยู่บน Windows คุณขอให้ agent ตรวจ test suite

```text
[calling run_shell with {'command': 'ls -la && cat pytest.ini'}]
```

ตอนนี้ผู้ใช้กำลังมองหน้าจอยืนยันสำหรับคำสั่งที่ทำงานไม่ได้ ถ้าเขาอนุมัติ ผลลัพธ์ที่ได้กลับมา
จะเป็นแบบนี้

```text
'ls' is not recognized as an internal or external command,
operable program or batch file.
[exit code 1]
```

หนึ่ง turn ที่เสียไป และแย่กว่านั้นคือเป็น turn ที่เสียความสนใจของมนุษย์ไปด้วย บทที่ 08
ทำให้ผู้ใช้เป็นด่านสุดท้ายก่อนที่อะไรจะถูกรัน ทุกคำสั่งที่โมเดลเสนอแล้วไม่มีทางทำงานได้
คือการถอนเงินออกจากความอดทนของคนคนนั้น และความอดทนคือทรัพยากรที่ทำให้ด่านยืนยัน
เป็นไปได้ตั้งแต่แรก ผู้ใช้ที่กด no ไปสี่ครั้งจะเริ่มกด yes โดยไม่อ่าน

โมเดลไม่ได้ชอบ Unix เป็นพิเศษ มันไม่มีข้อมูล และเมื่อไม่มีข้อมูล มันจึงผลิตรูปแบบที่พบบ่อยที่สุด
ใน training data ซึ่งก็คือ Linux shell เพราะ shell script ส่วนใหญ่ในโลกเขียนแบบนั้น

### การเดาที่สาม เลือก tool ผิดงาน

อันนี้แพงที่สุด และมันเงียบ

```text
You: change the timeout in config.py from 30 to 60
```

```text
[calling read_file with {'path': 'config.py'}]
[read_file returned TIMEOUT = 30
RETRIES = 3
LOG_LEVEL = "info"
...]
[calling write_file with {'path': 'config.py', 'content': 'TIMEOUT = 60\nRETRIES = 3\n...'}]
[write_file returned Wrote 61 characters to config.py]
```

มันสำเร็จ นั่นแหละคือปัญหา ไม่มี error ไม่มีการปฏิเสธ และ agent รายงานว่าสำเร็จ แต่
`write_file` แทนที่ไฟล์ทั้งไฟล์ด้วยสิ่งที่โมเดลพิมพ์ออกมา และโมเดลกำลังประกอบ 61 ตัวอักษร
ขึ้นใหม่จากการอ่านที่อาจถูกตัดที่ 4000 ตัวอักษร คอมเมนต์ใดที่มันไม่ได้พิมพ์ซ้ำ บรรทัดใด
ที่อยู่ต่ำกว่าจุดตัด บรรทัดว่างใดที่มันปรับให้เป็นมาตรฐาน หายไปหมด diff ที่คุณจะรีวิว
ไม่ใช่การเปลี่ยนหนึ่งบรรทัด แต่เป็นการเขียนไฟล์ใหม่ทั้งไฟล์ที่บังเอิญดูคล้ายของเดิม

`edit_file` มีอยู่เพื่อกรณีนี้โดยเฉพาะ มันแทนที่ข้อความชิ้นเดียวแบบตรงเป๊ะ และไม่แตะอะไรอย่างอื่น
โมเดลมีมันให้ใช้แต่เลือกอีกตัวหนึ่ง เพราะไม่มีอะไรในบทสนทนาบอกว่าควรเลือกตัวไหน

### สิ่งที่ทั้งสามกรณีมีร่วมกัน

ไม่มีกรณีไหนเลยที่เกิดจากความสามารถที่ขาดหายไป ทั้งสามกรณี tool ที่ถูกต้องนั่งอยู่ใน
รายการ schema อยู่แล้ว สิ่งที่ขาดคือข้อมูล

| การเดา | สิ่งที่จะป้องกันมันได้ |
| --- | --- |
| absolute path ที่แต่งขึ้นมา | ประโยคหนึ่งที่ระบุ workspace directory |
| `ls -la` บน Windows | ประโยคหนึ่งที่ระบุ platform |
| เลือก `write_file` แทน `edit_file` | ประโยคหนึ่งที่ระบุความชอบ |

สามประโยค นั่นคือเนื้อหาทั้งหมดของบทนี้ และส่วนที่เหลือของบทพูดถึงว่าแต่ละประโยคควรอยู่ตรงไหน
และทำไมตำแหน่งจึงสำคัญกว่าถ้อยคำ

## 2. สามช่องทางที่คำของคุณไปถึงโมเดล

นี่คือแนวคิดหลักของบทนี้ และควรพูดออกมาตรง ๆ ก่อนที่จะมีโค้ดปรากฏ

มีสามช่องทางพอดีที่คำของคุณจะไปถึงโมเดล

**system prompt** ข้อความที่อยู่หน้าสุดของบทสนทนา ถูกส่งก่อนทุกอย่างที่ผู้ใช้พูด
เป็นที่ที่คุณใส่คำสั่งประจำและข้อเท็จจริงประจำ คุณซึ่งเป็นนักพัฒนาเขียนมันครั้งเดียว
และมันจะอยู่ในทุก request ตลอดอายุของ session

**user message** คืองาน เขียนโดยใครก็ตามที่ใช้ agent ของคุณ ใหม่ทุก turn และต่างกันทุกครั้ง

**คำอธิบายของแต่ละ tool** สตริงที่ผูกอยู่กับทุกฟังก์ชันในรายการ schema ของคุณ
มันถูกส่งไปในทุก request พร้อมกับ messages และมันคือสิ่งเดียวที่โมเดลจะได้รู้ว่า
ฟังก์ชันของคุณทำอะไร

คนส่วนใหญ่ที่พูดเรื่อง prompt engineering รู้จักสองอย่างแรก พวกเขาเถียงกันเรื่องถ้อยคำ
ของ system prompt เก็บเทมเพลต ถกกันว่าจะเขียน "you are an expert" ไว้ข้างบนดีไหม
แทบไม่มีใครคิดถึงอย่างที่สามเลย และอย่างที่สามคือจุดที่มี leverage อยู่มากมาย

ลองดูว่า provider ส่งอะไรใน request เดียว แล้วเหตุผลจะชัดขึ้นทันที นี่คือรูปร่างของ payload
จาก `providers.py` โดยทำเครื่องหมายส่วนที่มาจากคุณ

```json
{
  "model": "...",
  "stream": true,
  "messages": [
    {"role": "system",    "content": "<- channel one, written by you"},
    {"role": "user",      "content": "<- channel two, written by your user"},
    {"role": "assistant", "content": "..."},
    {"role": "tool",      "content": "..."}
  ],
  "tools": [
    {"name": "read_file", "description": "<- channel three, written by you",
     "parameters": {"...": "..."}}
  ]
}
```

สามในสี่จุดที่ทำเครื่องหมายไว้เป็นของคุณ อาร์เรย์ `tools` ไม่ใช่ configuration ที่นั่งเงียบ ๆ
อยู่ข้างสนาม มันคือข้อความ มันอยู่ใน prompt และโมเดลอ่านมันแบบเดียวกับที่อ่าน system message
ไม่มีความแตกต่างเชิงสถาปัตยกรรมระหว่างประโยคใน system prompt กับประโยคใน tool description
ทั้งคู่มาถึงใน request เดียวกัน ถูกประมวลผลโดยโมเดลเดียวกัน และแย่งความสนใจก้อนเดียวกัน

ความต่างอยู่ที่ว่ามันอยู่ตรงไหนเมื่อเทียบกับการตัดสินใจที่กำลังเกิดขึ้น และหัวข้อ 6 จะเถียงว่า
ความต่างนี้เข้าข้าง tool description บ่อยกว่าที่คนคาดไว้

ยังมีช่องทางที่สี่ที่ควรเอ่ยชื่อไว้เพื่อไม่ให้สับสนกับสามช่องทางนี้ tool result ตั้งแต่บทที่ 07
เป็นต้นมาก็เป็นข้อความที่คุณควบคุมเช่นกัน และคุณก็ได้ทำ engineering กับมันมาแล้ว เวลาที่
`edit_file` ตอบกลับว่า "Include more surrounding lines so the match is unique" นั่นคือ
ประโยคที่คุณเขียน จ่าหน้าถึงโมเดล ตั้งใจให้เปลี่ยนการกระทำถัดไปของมัน มันคือกิจกรรมเดียวกัน
ภายใต้ชื่ออื่น เหตุผลเดียวที่ไม่ถูกนับรวมตรงนี้คือมันเป็นเชิงตอบสนอง ส่งหลังจากเกิดอะไรขึ้นแล้ว
ในขณะที่สามช่องทางนี้ปรากฏก่อนที่โมเดลจะทำอะไรเลย

## 3. อะไรควรอยู่ใน system prompt

เปิด `prompt.py` มันสั้น และทำงานสองอย่างที่สับสนกันง่าย บวกอีกหนึ่งอย่างที่หัวข้อนี้จะ
วกกลับมา สองอย่างแรกคืองานสองอย่างที่สับสนกันได้ง่าย

**งานที่หนึ่งคือพฤติกรรม** ทำงานอย่างไร ชอบอะไร ทำอย่างไรเมื่อมีอะไรผิดพลาด
ส่วนนี้คุณเขียนครั้งเดียวและไม่เปลี่ยนระหว่างการรันแต่ละครั้ง

**งานที่สองคือข้อเท็จจริง** สิ่งที่เป็นจริงสำหรับการรันครั้งนี้โดยเฉพาะ ซึ่งโมเดลไม่มีทางค้นพบ
ได้เลยหากไม่ยอมเสีย turn ไปกับมัน มันยืนอยู่ตรงไหน ระบบปฏิบัติการอะไร Python เวอร์ชันไหน
ที่ใช้ได้ ส่วนนี้ถูกคำนวณใหม่ทุกครั้งที่โปรแกรมเริ่มทำงาน

การแยกทั้งสองออกจากกันสำคัญ เพราะมันมีอายุขัยต่างกันและมีผู้เขียนต่างกัน พฤติกรรมคือ
การตัดสินใจด้านการออกแบบที่คุณทำตอนเขียน agent ข้อเท็จจริงคือการวัดค่าตอนเริ่มโปรแกรม
การผสมทั้งสองเข้าไปในสตริงที่เขียนด้วยมือก้อนเดียวหมายความว่าสุดท้ายจะมีใครสักคน hardcode
directory เข้าไป แล้ว agent ก็จะโกหกโมเดลอย่างเงียบ ๆ บนเครื่องอื่นทุกเครื่อง

### บล็อกพฤติกรรม

นี่คือข้อความจริงตามที่ปรากฏในไฟล์

```python
BEHAVIOUR = """You are a careful software assistant working inside one directory.

Work in small steps. Look before you change anything. When you need to know
what a file contains, read it rather than guessing. When you change a file,
change the smallest amount of text that does the job.

Prefer edit_file over write_file for existing files, because write_file
replaces the whole file and loses anything you did not include.

When you are done, say what you changed in one or two sentences."""
```

สี่ย่อหน้า ค่อย ๆ ดูทีละอัน เพราะแต่ละอันทำงานเฉพาะอย่าง และไม่มีอันไหนเป็นไส้ถ่วง

**"You are a careful software assistant working inside one directory."**

นี่คือประโยคเดียวใน prompt ที่คล้ายการเปิดแบบ "you are an expert X" ที่ใคร ๆ ก็เขียนกัน
และมันอยู่ตรงนี้ด้วยเหตุผลที่แคบกว่าที่คนมักใช้กัน คำที่แบกน้ำหนักคือ `careful` กับ
`one directory`

`careful` กำหนดท่าทีที่ย่อหน้าถัด ๆ ไปจะทำให้เป็นรูปธรรม ถ้าอยู่ตัวเดียวมันแทบไร้ค่า
เพราะคำสั่งกว้าง ๆ ว่าให้ระวังไม่ได้บอกโมเดลว่าต้องทำอะไรต่างไป มันได้ที่ยืนเพราะเป็นหัวข้อ
ที่กฎเฉพาะด้านล่างห้อยอยู่

`one directory` คือครึ่งที่สำคัญ มันบอกโมเดลว่าโลกของมันมีขอบเขต ซึ่งเตรียมมันไว้สำหรับ
การปฏิเสธที่จะได้รับจาก `resolve_inside` เมื่อมันเอื้อมออกไปข้างนอก โมเดลที่ถูกบอกว่า
ทำงานอยู่ใน directory เดียว จะอ่าน "outside the workspace" ว่าเป็นกฎที่มันเข้าใจล่วงหน้าแล้ว
ไม่ใช่เรื่องน่าประหลาดใจที่ต้องมานั่งคิด

**"Work in small steps. Look before you change anything. When you need to know
what a file contains, read it rather than guessing. When you change a file,
change the smallest amount of text that does the job."**

นี่คือวิธีทำงาน และทุกประโยคในนั้นจับคู่กับความล้มเหลวเฉพาะอย่างที่คุณเห็นในหัวข้อ 1

"Look before you change anything" คือทางแก้ของการเดาที่หนึ่ง มันผลักโมเดลไปหา `list_files`
และ `glob_files` และ `grep_files` ก่อนที่จะเริ่มเปิดไฟล์ตามชื่อ tool เหล่านั้นราคาถูก
การเดา path ไม่ถูก เพราะเดาผิดหนึ่งครั้งเสียการเดินทางไปกลับเต็มรอบ

"Read it rather than guessing" มุ่งไปที่ความล้มเหลวเฉพาะที่โมเดลเขียน edit จากสิ่งที่มัน
สมมติว่าไฟล์มีอยู่ โมเดลเก่งมากในการผลิตเนื้อไฟล์ที่ดูน่าเชื่อ ซึ่งนั่นแหละคืออันตราย
`edit_file` จะปฏิเสธ edit ที่ข้อความเดิมไม่ปรากฏ ดังนั้นการเดาจึงไม่ทำให้ข้อมูลเสียหาย
แต่มันเผา turn ทิ้งและมันใส่เวอร์ชันผิดของไฟล์เข้าไปในบทสนทนาซึ่งจะค้างอยู่ตรงนั้น

"Change the smallest amount of text that does the job" เป็นเรื่องของ diff ที่มนุษย์จะอ่าน
ทีหลัง agent ที่เขียนไฟล์ใหม่ทั้งไฟล์เพื่อเปลี่ยนหนึ่งบรรทัดสร้างความเปลี่ยนแปลงที่ไม่มีใคร
รีวิวได้ และความเปลี่ยนแปลงที่รีวิวไม่ได้คือสิ่งที่คุณต้องยอมรับแบบหลับตาหรือไม่ก็ทิ้งไป
ทั้งสองทางล้วนเป็นผลลัพธ์ที่แย่

**"Prefer edit_file over write_file for existing files, because write_file
replaces the whole file and loses anything you did not include."**

นี่คือทางแก้ของการเดาที่สาม และเป็นบรรทัดที่ควรศึกษาที่สุดในบล็อกนี้ เพราะคำว่า `because`

คำสั่งนี้ยังอ่านรู้เรื่องแม้ไม่มีอนุประโยคตามหลัง "Prefer edit_file over write_file for
existing files" เป็นกฎที่สมบูรณ์อยู่แล้ว การให้เหตุผลเพิ่มทำอีกสองอย่าง

มันทำให้กฎขยายผลได้ โมเดลที่รู้ว่ากฎมีอยู่ทำไม สามารถนำไปใช้กับกรณีที่กฎไม่ได้พูดถึง
ถ้าบอกแค่กฎ โมเดลจะไม่มีอะไรให้ใช้คิดเมื่อเจอสถานการณ์ที่กฎไม่ครอบคลุม เช่นไฟล์ที่มัน
เพิ่งสร้างเมื่อสาม turn ก่อน ถ้าบอกเหตุผล มันจะคิดออกว่าความเสี่ยงคือการสูญเสียเนื้อหา
ที่มันไม่ได้ใส่ไว้ แล้วทำตามนั้น

มันอยู่รอดเมื่อเกิดความขัดแย้ง ต่อมาในบทสนทนายาว ๆ โมเดลจะเจอสถานการณ์ที่ดึงไปอีกทาง
เช่นผู้ใช้ขอตรง ๆ ให้สร้างไฟล์ใหม่ตั้งแต่ต้น กฎเปล่า ๆ กับคำขอที่ชัดเจนคือคำสั่งสองอันที่
ตึงกันโดยไม่มีอะไรมาตัดสิน กฎที่มีเหตุผลติดมาด้วยทำให้โมเดลเห็นว่าเหตุผลนั้นใช้ไม่ได้ที่นี่
เพราะไม่มีอะไรจะเสีย แล้วทำตามผู้ใช้

สังเกตด้วยว่าประโยคนี้เรียกชื่อ tool ของคุณด้วยชื่อจริงเป๊ะ ๆ `edit_file` และ `write_file`
คือสตริงที่อยู่ใน schema ไม่ใช่ "the edit tool" ไม่ใช่ "editing" โมเดลจับคู่สิ่งที่อ่านใน prompt
กับสิ่งที่เห็นในรายการ tool และชื่อที่ตรงเป๊ะทำให้การจับคู่นั้นง่ายแทนที่จะต้องอนุมาน

**"When you are done, say what you changed in one or two sentences."**

กฎรูปแบบผลลัพธ์ และเป็นกฎที่เล็กที่สุดที่ใช้ได้จริง ถ้าไม่มีมัน โมเดลจะจบ session ในสองแบบ
ที่ไม่ช่วยอะไร แบบแรกคือหยุดหลัง tool call สุดท้ายโดยไม่มีข้อความเลย ทิ้งให้ผู้ใช้จ้อง trace
แล้วสงสัยว่ามันเสร็จหรือยัง แบบที่สองคือผลิตหกย่อหน้าเล่าซ้ำทุกอย่างที่ทำ ซึ่งผู้ใช้ไม่อ่านอยู่ดี

เพดานหนึ่งถึงสองประโยคทำงานจริง "Summarise your changes" ตัวเดียวโดด ๆ ผลิตเรียงความ
ออกมาแน่นอน ตัวเลขคือคำสั่งที่โมเดลทำตามได้จริง

### บล็อกข้อเท็จจริง

ทีนี้มาถึงงานที่สอง และมันเป็นโค้ดมากกว่าร้อยแก้ว เพราะค่าต่าง ๆ ยังไม่รู้จนกว่าโปรแกรมจะรัน

```python
def build_system_prompt(root, extra=""):
    """Assemble the system prompt for a run inside root."""
    facts = [
        f"Workspace directory {Path(root).resolve()}",
        f"Platform {platform.system()}",
        f"Python {sys.version_info.major}.{sys.version_info.minor}",
    ]
    prompt = BEHAVIOUR + "\n\nFacts about this environment\n" + "\n".join(facts)
    if extra:
        prompt += "\n\n" + extra
    return prompt
```

ข้อเท็จจริงสามข้อ เรียกฟังก์ชันข้อละครั้ง ทั้งหมดมาจาก standard library

`Path(root).resolve()` ให้ absolute path ที่ symlink และส่วน `..` ถูกยุบเรียบร้อยแล้ว
การ resolve สำคัญเพราะ `.` ไม่ใช่ข้อเท็จจริง ถ้า prompt บอกว่า workspace คือ `.` โมเดล
จะไม่ได้เรียนรู้อะไรที่มันไม่ได้สมมติไว้อยู่แล้ว และสตริงนั้นจะหมายถึง directory คนละอัน
ขึ้นกับว่าโปรเซสถูกเริ่มจากที่ไหน path ที่ resolve แล้วคือ path เดียวกับที่ `resolve_inside`
ใน `tools.py` ใช้เปรียบเทียบ ดังนั้นโมเดลจึงถูกบอกความจริงตามที่ tool เข้าใจ ไม่ใช่ค่าประมาณ

`platform.system()` คืนคำเดียว `Windows` `Linux` หรือ `Darwin` หัวข้อ 4 ทั้งหัวข้อพูดถึง
ว่าทำไมคำเดียวนั้นคุ้มค่าตัวเอง

`sys.version_info` ให้เวอร์ชันของ interpreter ที่กำลังรัน อันนี้แคบกว่าอีกสองอันแต่มันป้องกัน
ความสูญเปล่าประเภทที่เห็นได้ชัด โมเดลที่ไม่รู้เวอร์ชันจะเลี่ยง syntax ใหม่ ๆ เพื่อความปลอดภัย
ทำให้ได้โค้ดเก่าและเทอะทะกว่าที่จำเป็น หรือไม่ก็ใช้อะไรบางอย่างจากเวอร์ชันที่คุณไม่มีแล้วรู้ตัว
ตอนที่รันเทสต์แล้วพัง ทั้งสองอย่างไม่แพงเท่า path ผิด แต่ทั้งคู่ป้องกันได้ฟรี

บรรทัดหัวข้อ `Facts about this environment` ไม่ใช่ของประดับ มันขีดเส้นแบ่งเนื้อหาสองประเภท
ที่โมเดลควรปฏิบัติต่างกัน เหนือเส้นคือคำสั่ง สิ่งที่ต้องทำ ใต้เส้นคือการสังเกต สิ่งที่เป็นจริง
การติดป้ายเส้นแบ่งนั้นทำให้โอกาสที่ข้อเท็จจริงจะถูกอ่านเป็นข้อเสนอแนะลดลงมาก

`extra` คือจุดขยาย มันต่อข้อความที่ผู้เรียกส่งเข้ามาไว้ท้ายสุด ซึ่งเป็นที่ที่คำสั่งเฉพาะโปรเจกต์
ควรอยู่ ถ้าคุณเคยใช้ coding agent ที่อ่านไฟล์กฎเฉพาะโปรเจกต์จาก root ของ repository
พารามิเตอร์นี้คือจุดที่ไฟล์แบบนั้นจะถูกวางลงไป บทที่ 11 ใช้มัน

นี่คือของทั้งหมดที่ประกอบแล้ว พิมพ์ออกมาจากการรันจริงบนเครื่องที่ใช้เขียนบทนี้

```text
You are a careful software assistant working inside one directory.

Work in small steps. Look before you change anything. When you need to know
what a file contains, read it rather than guessing. When you change a file,
change the smallest amount of text that does the job.

Prefer edit_file over write_file for existing files, because write_file
replaces the whole file and loses anything you did not include.

When you are done, say what you changed in one or two sentences.

Facts about this environment
Workspace directory C:\Users\usEr\Desktop\agentpath\lessons\10-anatomy-of-a-prompt

Python 3.11
```

### บล็อกตัวอย่าง และเทคนิคอีกสองอย่างที่มีชื่อเรียก

การให้โมเดลดูตัวอย่างคำตอบที่คุณต้องการสองสามตัวอย่างเรียกว่า few shot prompting (การ
ให้ตัวอย่างไม่กี่ตัวใน prompt) และมันได้ผลด้วยเหตุผลที่ภาคพื้นฐานให้ไว้ในประโยคเดียว โมเดล
ทาย token ถัดไป มันจึงต่อรูปแบบที่มันมองเห็น
ได้ซื่อตรงกว่าการทำตามคำอธิบายของรูปแบบนั้นมาก บอกให้ตอบในบรรทัดเดียว มันอาจจะทำ
ให้มันดูคำตอบบรรทัดเดียวสามตัวอย่าง มันแทบจะทำเสมอ

`prompt.py` มี helper เล็ก ๆ สำหรับเรื่องนี้ เพราะตัวอย่างมีรูปร่าง และรูปร่างสำคัญ

```python
def examples_block(pairs):
    """Turn a few question and answer pairs into text the prompt can carry."""
    shown = []
    for question, answer in pairs:
        shown.append(f"Request\n{question}\n\nGood answer\n{answer}")
    return "Examples of the kind of answer wanted\n\n" + "\n\n".join(shown)
```

มันเข้าไปทาง `extra` ซึ่งคือสิ่งที่ `extra` มีไว้ทำ สามเรื่องที่ควรรู้ก่อนใช้ ตัวอย่างถูกจ่าย
ในทุก request เหมือนทุกบรรทัดอื่น ตัวอย่างดี ๆ สองตัวจึงชนะหกตัว ลำดับเป็นส่วนหนึ่งของ
รูปแบบ และโมเดลจะเอนไปทางตัวสุดท้าย จึงควรวางกรณีที่ปกติที่สุดไว้ท้ายสุด และตัวอย่างที่ไม่
ตรงกับงานแย่กว่าไม่มีเลย เพราะโมเดลจะเลียนแบบมันอยู่ดี `check.py` ยึดรูปร่างนี้ไว้ ว่าบล็อก
ไปลงท้าย prompt และแต่ละคำตอบตามหลังคำถามของตัวเอง

เทคนิคที่สองที่มีชื่ออยู่ใน `BEHAVIOUR` แล้ว ในประโยคที่บอกให้ดูก่อนเปลี่ยนอะไร การขอให้
โมเดลไล่ขั้นตอนก่อนให้คำตอบเรียกว่า chain of thought (การให้โมเดลเขียนขั้นตอนคิดก่อนตอบ)
และในงานที่มีมากกว่าหนึ่งขั้น มันเพิ่มความแม่นด้วยเหตุผลเดียวกับที่คนแสดงวิธีทำแล้วคำนวณ
ผิดน้อยลง ทุก token ที่โมเดลเขียนคือ context ของ token ถัดไป โมเดลที่เขียนเหตุผลก่อนจึงทายคำตอบจากเหตุผล ไม่ใช่จากคำถาม
เปล่า ๆ สำหรับ agent เรื่องนี้ดูแลตัวเองเป็นส่วนใหญ่ เพราะ tool call คือขั้นตอน และ loop ที่
อ่านไฟล์ก่อนแก้คือ chain of thought ที่ทำจากการกระทำ โมเดลที่คุณจะเรียกในวันนี้ก็ทำเรื่องนี้
ในแบบของตัวเองด้วย และบทที่ 06 แสดงบล็อกที่มันส่งกลับมาให้ดูแล้ว

เทคนิคที่สามคือตัวที่แพง ถามคำถามเดิมหลายครั้งที่ temperature (ค่าความสุ่มตอนเลือก token)
สูงกว่าศูนย์ แล้วเอาคำตอบที่กลับมาบ่อยที่สุด เรียกว่า self consistency (การสุ่มหลายคำตอบแล้ว
เลือกเสียงข้างมาก) มันชนะคำตอบเดี่ยวอย่างวัดได้ในคำถามที่มีคำตอบถูกหนึ่งแบบ และมันมีราคา
เท่ากับจำนวนครั้งที่คุณสุ่ม มันคือการซื้อความแม่นด้วยจำนวนครั้งที่เรียก ไม่ใช่ด้วยถ้อยคำ และ
บิลคือประเด็น คอร์สนี้ไม่ได้สร้างมัน ถ้าคุณต้องการ มันอยู่ข้าง judge ของบทที่ 22 ได้อย่าง
เป็นธรรมชาติ และมีราคาเท่ากับ judge คูณจำนวนครั้ง

## 4. ทำไมโมเดลต้องถูกบอกว่ามันอยู่ที่ไหนและอยู่บน platform อะไร

หัวข้อนี้มีอยู่เพราะบล็อกข้อเท็จจริงดูเหมือนส่วนที่น่าสนใจน้อยที่สุดในไฟล์ แต่จริง ๆ แล้ว
เป็นส่วนที่เปลี่ยนพฤติกรรมได้มากที่สุดต่อทุกตัวอักษรที่จ่ายไป

เริ่มจากหลักการทั่วไป language model ไม่มีประสาทสัมผัส มันรัน `pwd` ไม่ได้ มันมองแถบงาน
ของคุณไม่ได้ มันไม่มีการรับรู้แวดล้อมใด ๆ เลยแม้แต่น้อย ความรู้ของมันเกี่ยวกับปัจจุบันขณะ
คือข้อความในบทสนทนาเป๊ะ ๆ และถ้าข้อเท็จจริงไม่อยู่ในข้อความนั้น ในมุมของโมเดลข้อเท็จจริงนั้น
ก็ไม่มีอยู่จริง

แต่มันก็ยังต้องผลิตคำตอบออกมา และนี่คือส่วนที่คนประเมินต่ำไป โมเดลที่ถูกถามหา file path
จะไม่ตอบว่า "I do not know" มันจะคืน path ที่น่าจะเป็นที่สุด ความน่าจะเป็นนั้นเรียนมาจาก
โค้ดสาธารณะจำนวนมหาศาล ซึ่งแปลว่าการเดาโดยปริยายของโมเดลไม่ใช่การสุ่ม มันคือการเดา
ที่มั่นใจ เฉพาะเจาะจง และรูปแบบดี ดึงมาจากค่าเฉลี่ยของทุกอย่างที่มันเคยอ่าน

ค่าเฉลี่ยนั้นคือเครื่อง Linux อยู่ใน directory ที่ชื่อประมาณ `/home/user/project` หรือ `/app`
รัน shell ที่มี `ls` และ `grep` และ `cat` การเดานั้นไม่ได้โง่ มันถูกต้องสำหรับโค้ดส่วนใหญ่
ที่โมเดลถูกเทรนมา มันแค่ไม่ถูกต้องสำหรับเครื่องของคุณ และโมเดลไม่มีทางรู้ได้เลย

### ต้นทุนของการเดา platform

ใส่ตัวเลขให้มัน ถ้า agent ของคุณอยู่บน Windows และ system prompt ไม่พูดอะไรเลย
ทุกคำสั่ง shell ที่โมเดลเสนอก็คือการโยนเหรียญที่ถ่วงน้ำหนักไปทาง Unix นี่คือคู่ที่โผล่มาตลอด

| สิ่งที่โมเดลเขียน | สิ่งที่ Windows ต้องการ |
| --- | --- |
| `ls -la` | `dir` or `Get-ChildItem` |
| `cat file.txt` | `type file.txt` or `Get-Content` |
| `rm -rf build` | `Remove-Item -Recurse build` |
| `export VAR=1` | `$env:VAR = "1"` |
| `grep -r x .` | `Select-String -Path *.* -Pattern x` |
| `./venv/bin/python` | `venv\Scripts\python.exe` |

การเดาผิดแต่ละครั้งคือหน้าจอยืนยันที่แสดงให้มนุษย์ดู เป็นการปฏิเสธหรือคำสั่งที่ล้มเหลว
เป็นข้อความ error ที่ถูกเพิ่มเข้าไปในบทสนทนาอย่างถาวร และเป็นการเดินทางไปกลับเต็มรอบอีกครั้ง
เกิดสามครั้งใน session เดียวคุณก็เสีย token ไปกับสำเนียง shell มากกว่างานจริงแล้ว

ด้วยคำเดียวใน prompt โมเดลทำถูกตั้งแต่ครั้งแรก `Platform Windows` ราคาสอง token
ความล้มเหลวที่มันป้องกันได้ราคาหลายร้อย token ต่อครั้ง บวกกับสิ่งที่มีค่ากว่า token
ซึ่งก็คือความเต็มใจของผู้ใช้ที่จะอ่านหน้าจอยืนยันอย่างตั้งใจต่อไป

### ต้นทุนของการเดา directory

path ของ workspace ทำอะไรที่ต่างออกไปเล็กน้อย และควรแยกออกมาพูด

ประโยชน์ที่ชัดเจนคือโมเดลเลิกแต่ง absolute path ขึ้นมาเอง ซึ่ง `resolve_inside` ก็ปฏิเสธ
อยู่แล้ว ความพยายามเหล่านั้นจึงเป็นความสูญเปล่าล้วน ๆ

ประโยชน์ที่ละเอียดกว่าคือ absolute path บอกโมเดลว่ามันอยู่ในสถานที่แบบไหน ลองดูความต่าง
ระหว่างข้อเท็จจริงสองอันนี้

```text
Workspace directory C:\Users\usEr\Desktop\agentpath\lessons\10-anatomy-of-a-prompt
```

```text
Workspace directory /srv/deploy/customer-data-import
```

อันแรกบอกว่านี่คือโฟลเดอร์บทเรียนใน repository ของคอร์ส บนเดสก์ท็อปของใครสักคน
ซึ่งเป็นที่ที่ทดลองอะไรก็ได้ อันที่สองบอกว่า production โมเดลที่เห็นสตริงใดสตริงหนึ่งจะคิด
ต่างกันว่าควรตรวจสอบมากแค่ไหนก่อนลงมือ และมันไม่ต้องถูกบอกเรื่องพวกนั้นตรง ๆ เลย
path พาข้อมูลนั้นมาให้แล้ว

มีประโยชน์อย่างที่สามที่โผล่มาเฉพาะตอนเกิด error เมื่อ `resolve_inside` ปฏิเสธ path
โมเดลต้องคิดเองว่า path ที่ถูกกฎหน้าตาเป็นอย่างไร ถ้า workspace อยู่ใน prompt การคิดนั้น
เกิดขึ้นทันที ถ้าไม่มี โมเดลก็เดาอีกครั้ง และการเดาครั้งที่สองหลังถูกปฏิเสธมักแย่กว่าครั้งแรก
เพราะโมเดลจะเริ่มลองหาทางเลี่ยงแบบซับซ้อน

### ข้อเท็จจริง ไม่ใช่คำสั่ง

ประเด็นสุดท้ายเกี่ยวกับรูปร่างของบล็อกนี้ เพราะเป็นนิสัยที่ควรสร้าง

สังเกตว่าไม่มีข้อเท็จจริงข้อไหนในสามข้อที่เขียนเป็นคำสั่ง มันไม่ได้บอกว่า "always use Windows
commands" หรือ "never use absolute paths" มันบอกว่าอะไรเป็นจริงแล้วปล่อยให้โมเดลสรุปเอง

นี่จงใจและมันขยายผลได้ดีกว่า การอยู่บน Windows มีผลตามมาหลายสิบอย่างและคุณไล่นับไม่หมด
ตัวคั่น path การขึ้นบรรทัดใหม่ การไม่มี `chmod` ตัวเรียก Python ที่ต่างออกไป ชื่อไฟล์
ที่ไม่แยกตัวพิมพ์ใหญ่เล็ก `%APPDATA%` แทน `$HOME` ถ้าเขียนทั้งหมดเป็นกฎคุณก็จะได้กฎ
สามสิบข้อที่แย่งกันเอง ซึ่งหัวข้อ 7 บอกว่าเป็นวิธีทำให้ prompt แย่ลง ระบุข้อเท็จจริงข้อเดียว
แล้วโมเดลก็รู้ผลที่ตามมาอยู่แล้ว เพราะความรู้ชุดนั้นมีอยู่จริงใน training data ของมัน
สิ่งที่มันขาดไม่ใช่ความรู้เรื่อง Windows แต่คือการรู้ว่าตรงนี้คือ Windows

ระบุข้อเท็จจริงที่โมเดลไม่มีทางรู้ แล้วปล่อยให้มันใช้ความรู้ที่มีอยู่แล้ว

## 5. อะไรควรอยู่ใน user message

หัวข้อนี้สั้น เพราะ user message คือช่องทางเดียวที่คำตอบที่ถูกต้องคือทำให้น้อยลง

user message คืองาน แค่นั้น

```python
messages.append({"role": "user", "content": user_input})
```

อะไรก็ตามที่คนพิมพ์เข้ามาใส่ลงไปโดยไม่แก้ ไม่มีคำนำหน้า ไม่มีเทมเพลต ไม่มีคำเตือนต่อท้าย
ให้ระวังตัว ไม่มีการพูดกฎซ้ำ

สามเหตุผล เรียงตามความสำคัญจากน้อยไปมาก

**มันถูกครอบคลุมไปแล้ว** อะไรก็ตามที่คุณจะเติมไว้หน้าทุก user message ควรอยู่ใน
system prompt ที่เขียนครั้งเดียวและระบุครั้งเดียว การเติมตรงนี้แปลว่าคำสั่งเดียวกัน
ปรากฏสองครั้งในบทสนทนา และเมื่อคำสั่งเดียวกันปรากฏสองครั้ง โมเดลต้องตัดสินใจว่า
ครั้งที่สองคือการเน้นย้ำหรือการแก้ไขครั้งแรก การตีความทั้งสองแบบไม่ช่วยอะไร

**มันโต** คำเตือนที่ต่อท้ายทุก user message จะถูกส่งซ้ำสำหรับทุกข้อความในประวัติ
สิบ turn เข้าไปใน session คำเตือนนั้นอยู่ในบทสนทนาสิบครั้ง ถูกจ่ายเงินสิบครั้ง
และเจือจางบทสนทนาสิบครั้ง

**มันซ่อนงาน** อันนี้คือของจริง หน้าที่ของโมเดลในแต่ละ turn คือหาให้ได้ว่าผู้ใช้ต้องการอะไร
การยัดข้อความด้วยข้อความสำเร็จรูปฝังกลบประโยคเดียวที่สำคัญจริง และโมเดลก็เหมือนคน
คือให้น้ำหนักจุดเริ่มและจุดจบของข้อความมากกว่าตรงกลาง การห่องานด้วยคำนำและคำท้าย
คือการวางส่วนสำคัญไว้ในตำแหน่งที่ได้รับความสนใจน้อยที่สุด

มีกรณีหนึ่งที่เนื้อหาเพิ่มเติมใน turn ของผู้ใช้เป็นสิ่งที่ถูกต้อง และควรเอ่ยไว้เพื่อให้คุณ
แยกออกว่ามันต่างกัน context ที่ผู้ใช้ตั้งใจแนบมากับงานชิ้นนี้โดยเฉพาะ เช่นข้อความ error
ที่เขาเจอ หรือเนื้อหาไฟล์ที่เขาวางมา ควรอยู่ใน user message เพราะมันเป็นส่วนหนึ่งของงาน
และมันไม่เป็นจริงสำหรับงานถัดไป นั่นไม่ใช่เทมเพลต นั่นคือผู้ใช้กำลังพูด

## 6. tool description คือ prompt engineering และนี่คือส่วนที่คนมองข้าม

ทีนี้มาถึงหัวข้อยาว และเหตุผลที่มันยาวคือนี่คือช่องทางที่ไม่มีใครนับ

เปิด `tools.py` มันไม่ได้เปลี่ยนตั้งแต่บทที่ 09 ดูสิ่งที่นั่งอยู่ใน schema ของ `read_file`

```python
"description": "Read a text file and return its contents.",
```

นี่คือข้ออ้างของหัวข้อนี้ ประโยคนั้นคือ prompt ไม่ใช่อะไรที่คล้าย prompt ไม่ใช่ metadata
เกี่ยวกับ prompt มันคือข้อความที่คุณเขียน ที่ถูกส่งไปหาโมเดลภายใน HTTP request เดียวกับ
system message ของคุณ ที่โมเดลอ่านก่อนตัดสินใจว่าจะทำอะไร และที่มีอิทธิพลต่อพฤติกรรม
ของมันด้วยกลไกเดียวกับข้อความอื่นใน request คุณเขียน prompt มาตั้งแต่บทที่ 07 แล้ว
และบทนี้คือที่ที่คุณเพิ่งรู้ตัว

### คำอธิบายคือทั้งหมดที่โมเดลจะได้รู้

รับข้อนี้ไปอย่างจริงจัง เพราะมันเด็ดขาดกว่าที่ฟังดู

โมเดลมองไม่เห็น Python ของคุณ มันไม่รู้ว่า `read_file` เรียก `resolve_inside` มันไม่รู้ว่า
ค่าที่คืนกลับถูกตัดที่ 4000 ตัวอักษร มันตรวจสอบฟังก์ชันไม่ได้ อ่าน docstring ของคุณไม่ได้
รันเพื่อดูว่ามันทำอะไรก็ไม่ได้ มันมีแค่ชื่อ คำอธิบาย และ schema ของพารามิเตอร์
นั่นคือ interface ทั้งหมด

ทุกคุณสมบัติของฟังก์ชันคุณที่โมเดลต้องมีเพื่อใช้มันได้ดีต้องอยู่ในสตริงนั้น ไม่อย่างนั้นโมเดล
ก็ไม่มีมัน

นี่กลับหัวกลับหางกับวิธีที่คุณเขียน docstring ตามปกติ docstring เขียนให้คนที่อ่านโค้ดข้างล่าง
ได้ด้วย มันจึงห้วนและปล่อยให้บางอย่างเป็นนัยได้ tool description เขียนให้ผู้เรียกที่จะไม่มีวัน
เห็นโค้ด จะไม่มีวันเห็นมันอีกหลังการเรียกครั้งนี้ และถามคำถามต่อไม่ได้ ห้ามปล่อยอะไรเป็นนัยเลย
ถ้าข้อจำกัดไม่ถูกเขียนลงไป มันก็ไม่มีอยู่ในมุมมองของผู้เรียก

### มันถูกอ่านในทุก request

นี่คือคุณสมบัติที่สอง และเป็นคุณสมบัติที่ทำให้คำอธิบายทรงพลังผิดปกติ

รายการ tool ถูกส่งไปในทุก request ของบทสนทนา ไม่ใช่ครั้งเดียวตอนต้น ทุกครั้ง
turn ที่หนึ่ง turn ที่ห้า turn ที่ยี่สิบ

เทียบกับ system prompt ซึ่งก็อยู่ทุกครั้งเหมือนกัน แต่ถูกวางไว้หน้าสุดของบทสนทนา
ที่โตขึ้นเรื่อย ๆ พอถึง turn ที่สิบห้า system prompt ของคุณก็ถูกฝังอยู่ใต้สิบห้า turn
ของเนื้อไฟล์ ผลการค้นหา และผลลัพธ์จาก shell มันยังอยู่ตรงนั้นและโมเดลก็ยังใส่ใจมัน
แต่มันต้องแข่งกับวัตถุดิบใหม่กว่าจำนวนมาก

tool description ไม่ได้อยู่ในกระแสนั้น มันนั่งอยู่ในอาร์เรย์ `tools` ข้าง ๆ ฟังก์ชันที่โมเดล
กำลังจะเรียก ซึ่งแปลว่ามันอยู่ติดกับการตัดสินใจ ไม่ใช่อยู่เหนือน้ำขึ้นไปสิบห้า turn

ความติดกันนั้นคือเหตุผลที่กฎเชิงปฏิบัติข้างล่างนี้เป็นจริงอย่างสม่ำเสมอ

**ถ้าคุณอยากเปลี่ยนวิธีที่ tool ถูกใช้ ให้เปลี่ยนคำอธิบายของมันก่อนที่จะเพิ่มย่อหน้าเข้าไปใน
system prompt**

คำอธิบายถูกอ่าน ณ ขณะที่กำลังเลือก มันใช้กับการตัดสินใจที่คุณสนใจพอดี และมันไม่ต้องแข่ง
กับอะไรเลยนอกจากคำอธิบายอีกหกอัน กฎใน system prompt ที่พูดถึง tool ตัวหนึ่งคือคำสั่งทั่วไป
ที่ต้องถูกนึกออกในจังหวะที่ถูกต้อง ส่วนคำอธิบายคือข้อมูลที่ส่งถึงที่จุดที่ใช้งาน

ทีนี้มาดูว่า tool description ในโปรเจกต์นี้ใช้ตำแหน่งนั้นทำอะไรบ้าง

### ตัวอย่างที่หนึ่ง write_file ที่ผลักไปหา edit_file

```python
"description": (
    "Write a whole file, creating it if needed. Use edit_file instead when "
    "you only want to change part of an existing file."
),
```

อ่านประโยคที่สองอีกครั้ง มันคือคำอธิบายของ `write_file` ที่ใช้ความยาวครึ่งหนึ่งบอกโมเดล
ให้ไปเรียก tool ตัวอื่น

ครั้งแรกที่เห็นมันดูผิด เอกสารของฟังก์ชันควรอธิบายฟังก์ชันนั้น แต่ให้จำไว้ว่าผู้อ่านคือใคร
และเขาอ่านตอนไหน โมเดลอ่านสิ่งนี้ระหว่างตัดสินใจว่าจะเรียกอะไร ช่วงเวลาก่อนที่มันจะเรียก
`write_file` กับไฟล์ที่มีอยู่แล้วคือช่วงเวลาที่คำเตือนนี้มีประโยชน์ที่สุด วางไว้ที่อื่นแปลว่า
มันมาถึงเร็วเกินไปหรือช้าเกินไป

และมันก็ได้ผลด้วย นี่คือกฎเดียวกับที่อยู่ใน system prompt แล้ว ในย่อหน้า
`Prefer edit_file over write_file` และการมีมันในสองที่ไม่ใช่อุบัติเหตุ มันคือกฎเดียวที่ถูกระบุ
ในที่ที่มันถูกจำได้ และระบุอีกครั้งในที่ที่มันถูกใช้ ถ้าเลือกได้แค่ที่เดียว คำอธิบายคืออันที่โดน
เพราะมันติดอยู่กับการตัดสินใจ แทนที่จะเป็นนโยบายที่โมเดลต้องนึกออกเอง

สังเกตความแม่นยำของเงื่อนไข มันบอกว่า `part of an existing file` ไม่ใช่ "prefer edit_file"
ทั้งสองครึ่งของวลีนั้นสำคัญ `existing` ตัดกรณีที่ไฟล์ยังไม่มีอยู่ออก ซึ่งเป็นกรณีที่ `write_file`
ถูกต้องและ `edit_file` จะล้มเหลว `part of` ตัดกรณีที่ไฟล์ทั้งไฟล์ถูกแทนที่จริง ๆ ออก
คำสั่งแบบเหมารวมจะผลักโมเดลไปหา `edit_file` ในสถานการณ์ที่ `edit_file` ทำงานไม่ได้
แล้วมันก็ล้มเหลว ลองใหม่ และคุณก็ทำให้เรื่องแย่ลงด้วยคำสั่งที่แรงเกินไป

เทียบกับคำอธิบายที่คนมักเขียนกัน

```python
"description": "Writes a file."
```

ทุกอย่างที่โมเดลต้องการหายไปหมด มันไม่รู้ว่ามี tool พี่น้องอยู่ ไม่รู้ว่าการเขียนนี้ทำลายของเดิม
ไม่รู้ว่าเมื่อไรตัวพี่น้องคือตัวเลือกที่ดีกว่า ฟังก์ชันทำงานเหมือนเดิมทุกประการ แต่ agent
ทำงานแย่ลงมาก และมันแย่ลงในแบบเงียบ ๆ ตามหัวข้อ 1 ที่ไม่มี error อะไรเลยแล้วไฟล์ก็เสีย
เนื้อหาไปเงียบ ๆ

### ตัวอย่างที่สอง edit_file ที่อธิบายวิธีทำให้สำเร็จ

นี่คือคำอธิบายที่ดีที่สุดในไฟล์ และแพตเทิร์นนี้ควรจำไปทั้งอัน

```python
"description": (
    "Replace one exact piece of text in a file. The old text must appear "
    "exactly once, so include enough surrounding lines to make it unique."
),
```

สามอย่างถูกอัดอยู่ในสองประโยค

**มันทำอะไร** แทนที่ข้อความชิ้นเดียวแบบตรงเป๊ะ

**ข้อจำกัด** ข้อความเดิมต้องปรากฏเพียงครั้งเดียว

**วิธีทำให้เข้าเงื่อนไข** ใส่บรรทัดรอบข้างให้พอที่จะทำให้มันไม่ซ้ำ

อันที่สามคือส่วนที่ tool description ส่วนใหญ่ตกหล่น และการตกหล่นมันคือความต่างระหว่างโมเดล
ที่สำเร็จตั้งแต่การเรียกครั้งแรก กับโมเดลที่สำเร็จในครั้งที่สอง

ไล่ดูทั้งสองเวอร์ชัน สมมติว่าโมเดลอยากเปลี่ยน `return None` ในฟังก์ชันหนึ่ง และในไฟล์มีอยู่
สี่จุด

ถ้าไม่มีประโยคที่สาม โมเดลจะส่ง edit ที่เล็กที่สุดเท่าที่ทำได้ เพราะ edit เล็ก ๆ คือสิ่งที่มันถูกบอก
ให้ชอบ

```text
[calling edit_file with {'path': 'app.py', 'old': '    return None', 'new': '    return []'}]
[edit_file returned Error: the text to replace appears 4 times in app.py.
 Include more surrounding lines so the match is unique.]
```

เสียไปหนึ่ง turn ข้อความ error ที่คุณเขียนไว้ตั้งแต่บทที่ 07 ช่วยกู้สถานการณ์ โมเดลอ่านมัน
เพิ่ม context และการเรียกครั้งที่สองก็สำเร็จ ระบบฟื้นตัวได้ ซึ่งเป็นสิ่งที่ข้อความ error นั้น
ถูกออกแบบมาเพื่อทำพอดี

ถ้ามีประโยคที่สามอยู่ในคำอธิบาย โมเดลจะรู้กฎเรื่องความไม่ซ้ำก่อนที่จะประกอบการเรียก
และมันจะส่งแบบนี้แทน

```text
[calling edit_file with {'path': 'app.py', 'old': 'def parse(raw):\n    if not raw:\n        return None', 'new': 'def parse(raw):\n    if not raw:\n        return []'}]
[edit_file returned Edited app.py]
```

ไม่มี turn ที่เสียเปล่า ฟังก์ชันเดียวกัน โค้ดเดียวกัน การจัดการ error เดียวกันก็ยังอยู่ตรงนั้น
สำหรับกรณีที่จำเป็นจริง ๆ ความต่างเดียวคือข้อกำหนดถูกระบุล่วงหน้าแทนที่จะระบุตอนที่ถูกละเมิด

พูดรูปแบบทั่วไปออกมาดัง ๆ เพราะมันใช้กับทุก tool ที่คุณจะเขียนต่อจากนี้

**ข้อความ error ที่ดีบอกโมเดลว่าอะไรผิดพลาด คำอธิบายที่ดีหยุดมันไม่ให้ผิดพลาด**

คุณต้องการทั้งคู่ error คือตาข่ายนิรภัยและคุณสร้างตาข่ายที่ดีไว้แล้วในบทที่ 07 คำอธิบายคือ
ส่วนที่ทำให้แทบไม่ต้องใช้ตาข่ายนั้น ระบบที่มีแค่ข้อความ error ก็ทำงานได้ และจ่ายไปหนึ่ง turn
ทุกครั้ง ระบบที่มีแค่คำอธิบายก็ทำงานได้จนกว่าจะเกิดเรื่องที่ไม่คาดคิด แล้วก็ไม่มีทางฟื้นตัว
การมีทั้งคู่คือเหตุผลที่ agent รู้สึกลื่นไหลแทนที่จะแค่ใช้งานได้

### ตัวอย่างที่สาม สอน syntax ด้วยตัวอย่าง

```python
"description": (
    "Find files by name pattern, for example **/*.py or test_*.py. "
    "Use this when you know roughly what a file is called."
),
```

มีสองเทคนิคตรงนี้ที่ควรแยกออกมาพูด

อันแรกคือ `for example **/*.py or test_*.py` ห้าคำนั้นทำได้มากกว่าย่อหน้าที่อธิบาย syntax
ของ `fnmatch` ตัวอย่างที่เป็นรูปธรรมสองอันสร้างความเข้าใจเรื่องภาษาถิ่นทันที และมันถูกเลือก
มาอย่างระมัดระวัง `**/*.py` คือรูปแบบเรียกซ้ำลงไปในโฟลเดอร์ย่อย และ `test_*.py` คือรูปแบบ
ชื่อเปล่า ซึ่งเป็นสองกรณีพอดีที่หัวข้อ 4 ของบทที่ 09 ต้องเขียนโค้ดจับคู่เพิ่มเพื่อรองรับ
ตัวอย่างในคำอธิบายกับการจับคู่สองแบบในโค้ดคือการตัดสินใจออกแบบเดียวกันมองจากสองด้าน

อันที่สองคือ `Use this when you know roughly what a file is called` ประโยคนั้นไม่ได้พูดถึง
`glob_files` เลย มันพูดถึงการเลือกระหว่าง `glob_files` กับ `grep_files` ซึ่งเป็นการตัดสินใจ
จริง ๆ ที่โมเดลเผชิญตอนอ่านรายการ tool เทียบกับคำอธิบายข้างเคียง

```python
"description": (
    "Search the text inside files using a regular expression and return "
    "matching lines with their file name and line number."
),
```

tool ตัวหนึ่งบอกว่ามันค้นชื่อและบอกว่าควรใช้เมื่อไร อีกตัวบอกว่ามันค้นเนื้อหาและบอกว่า
มันคืนอะไรกลับมา ระหว่างสองอันนี้โมเดลเลือกได้ถูกโดยไม่ต้องลองอันหนึ่งแล้วถอยกลับ
และการลองอันหนึ่งแล้วถอยกลับคือหนึ่ง turn

สังเกตด้วยว่า `grep_files` โฆษณารูปแบบผลลัพธ์ของตัวเอง การบอกว่ามันคืนชื่อไฟล์และเลขบรรทัด
บอกโมเดลล่วงหน้าว่าผลลัพธ์นั้นป้อนเข้า `read_file` ได้ ซึ่งคือข้อโต้แย้งเรื่องการต่อกันทั้งหมด
จากบทที่ 09 ที่ถูกส่งมอบในอนุประโยคเดียว

### ตัวอย่างที่สี่ อธิบาย side effect

```python
"description": (
    "Run a shell command in the workspace directory and return its output. "
    "The user is asked to approve the command before it runs."
),
```

ประโยคที่สองอธิบายสิ่งที่เกิดขึ้นนอกโลกของโมเดล มนุษย์คนหนึ่งกำลังจะดูคำสั่งนั้นและตัดสินใจ

ทำไมต้องบอกโมเดลด้วย ในเมื่อมันมีอิทธิพลต่อผลลัพธ์ไม่ได้

เพราะมันเปลี่ยนสิ่งที่โมเดลทำทั้งก่อนและหลัง ก่อนหน้านั้น มันรู้ว่าคำสั่งจะถูกอ่านโดยคน
ซึ่งลดแรงจูงใจในการเขียน one liner ที่ต่อกันยาว ๆ และหันไปหาคำสั่งที่คนประเมินได้ในพริบตา
หลังจากนั้น เมื่อข้อความปฏิเสธกลับมา มันตีความได้ถูกว่าเป็นการตัดสินใจของมนุษย์ ไม่ใช่ tool
ที่พัง และไม่ลองสิ่งเดิมซ้ำด้วยเครื่องหมายคำพูดที่ต่างไปนิดหน่อย

มันยังบอกโมเดลด้วยว่า tool นี้มีต้นทุนที่ไม่ได้วัดเป็น token ทุกการเรียก `run_shell` ขัดจังหวะ
คนหนึ่งคน นั่นคือสิ่งที่ควรรู้เวลาเลือกระหว่าง `run_shell` กับ `grep_files` สำหรับคำถามเดียวกัน

สังเกตสิ่งที่คำอธิบายไม่ได้บอก มันไม่ได้บอกว่าคำสั่งรันด้วย `shell=True` หรือว่ามี timeout
60 วินาที หรือว่าผลลัพธ์ถูกตัดที่ 4000 ตัวอักษร นั่นคือรายละเอียดการทำงานภายในที่โมเดล
ทำอะไรกับมันไม่ได้ และข้อโต้แย้งเรื่องคำสั่งที่แข่งกันเองในหัวข้อ 7 ก็ใช้ได้ภายในคำอธิบายด้วย
เรื่อง timeout ถือว่าก้ำกึ่งและเถียงได้ว่าควรใส่ ที่เหลือคือสัญญาณรบกวน

### ชุดทั้งหมด และต้นทุนของมัน

นี่คือทุกคำอธิบายในโปรเจกต์ พร้อมตัวเลข

| Tool | ความยาวคำอธิบาย | schema เต็มในรูป JSON |
| --- | --- | --- |
| `read_file` | 41 | 230 |
| `write_file` | 119 | 395 |
| `edit_file` | 136 | 484 |
| `list_files` | 48 | 237 |
| `run_shell` | 126 | 314 |
| `glob_files` | 115 | 295 |
| `grep_files` | 119 | 388 |
| total | 704 | 2343 |

คำอธิบาย 704 ตัวอักษร ประมาณ 180 token ส่งไปทุก request ควบคู่กับ system prompt
ราว 150 token schema ของพารามิเตอร์เพิ่มขึ้นราวสามเท่า เพราะ JSON เยิ่นเย้อ และเรื่อง JSON
ก็ทำอะไรไม่ได้

ตัวคำอธิบายเองคือส่วนที่คุณควบคุมได้ และตารางนี้คือเหตุผลที่ควรปล่อยให้อันที่น่าเบื่อยังน่าเบื่อ
ต่อไป `read_file` ได้ 41 ตัวอักษรเพราะไม่มีอะไรน่าสนใจให้พูดเกี่ยวกับการอ่านไฟล์
`edit_file` ได้ 136 เพราะมีข้อจำกัดที่โมเดลต้องรู้ล่วงหน้า ความยาวตามมาจากว่าผู้เรียกต้องการ
มากแค่ไหนจริง ๆ ไม่ใช่จากความอยากจะละเอียด

### วิธีทำงานกับคำอธิบาย

วิธีปฏิบัติสั้น ๆ เพราะนี่คือสิ่งที่คุณจะทำซ้ำไปตลอดชีวิตการสร้าง agent

**ดู trace** ทุกการเรียก tool ที่ผิด ทุกอาร์กิวเมนต์ที่ผิดรูป ทุกการลองใหม่ คือข้อบกพร่อง
ในคำอธิบาย อย่าแก้ด้วยการเพิ่มกฎใน system prompt ให้อ่านคำอธิบายที่โมเดลใช้ทำงาน
แล้วถามว่าคนคนหนึ่งจะเข้าใจผิดอะไรถ้ามีแค่คำเหล่านั้น

**เปลี่ยนทีละคำอธิบาย** มันสั้นพอที่ผลของการเปลี่ยนครั้งเดียวจะมองเห็นได้ และการเปลี่ยน
สองอันพร้อมกันแปลว่าคุณไม่ได้เรียนรู้อะไรเลยเกี่ยวกับทั้งสองอัน

**เขียนข้อจำกัดก่อนที่โมเดลจะละเมิดมัน** นี่คือบทเรียน `edit_file` ที่ถูกขยายผล ถ้าฟังก์ชัน
ของคุณจะปฏิเสธ input บางแบบ กฎนั้นควรอยู่ในคำอธิบายด้วย ไม่ใช่แค่ในข้อความ error

**เอ่ยชื่อ tool พี่น้องเมื่อมีมัน** เมื่อใดที่ tool สองตัวทับซ้อนกัน คำอธิบายแต่ละอันควรบอกว่า
เมื่อไรอีกตัวถึงจะถูก นี่คือบทเรียน `write_file` และเป็นการแก้ไขที่ให้ค่ามากที่สุดอย่างเดียว
ที่คุณทำกับรายการ tool ได้

**ลบทุกอย่างที่โมเดลทำอะไรกับมันไม่ได้** รายละเอียดการทำงานภายในกิน token ทุก request
ตลอดไปและไม่เปลี่ยนอะไรเกี่ยวกับการเรียกเลย

## 7. ทำไม system prompt ที่ยาวกว่าจึงไม่ใช่ system prompt ที่ดีกว่า

หลังจบบทนี้มีก้าวถัดไปที่ชัดเจน และมันคือก้าวที่ผิด เมื่อเห็นว่าไม่กี่ประโยคทำให้ agent ดีขึ้น
ข้อสรุปตามธรรมชาติคืออีกไม่กี่ประโยคจะทำให้มันดีขึ้นอีก คนจึงลงเอยด้วย system prompt
ยาวสองพันคำ แล้ว agent ของพวกเขาก็ไม่ได้ดีขึ้นสองพันคำ

สามเหตุผล และเป็นอิสระต่อกัน ซึ่งแปลว่ามันซ้อนทับกันได้

### ทุก token ถูกส่งซ้ำในทุก request ตลอดไป

นี่คือกลไกจากบทที่ 02 ที่มาพร้อมใบเรียกเก็บเงิน

system prompt ไม่ได้ถูกส่งครั้งเดียวตอนต้น session มันเป็นส่วนหนึ่งของบทสนทนา และ
บทสนทนาทั้งหมดถูกส่งออกไปในทุก request session ที่มียี่สิบ turn ส่ง system prompt ยี่สิบครั้ง

prompt ในบทนี้ประมาณ 150 token prompt ที่บวมอย่างมีเจตนาดีก็ 1500 ได้ง่าย ๆ เอามาวางกับ
session แล้วความต่างเป็นเรื่องจริง

| | prompt 150 token | prompt 1500 token |
| --- | --- | --- |
| หนึ่ง request | 150 | 1500 |
| session ยี่สิบ turn | 3,000 | 30,000 |
| หนึ่งร้อย session | 300,000 | 3,000,000 |

นั่นคือ input token ที่คุณจ่ายเงิน ในทุก request ตราบเท่าที่ agent ยังอยู่ และ input token
ไม่ใช่ต้นทุนเดียว มันคือ latency เพราะโมเดลต้องประมวลผลมันก่อนจะผลิต output token แรก
และมันคือ context window เพราะทุกพื้นที่ที่ prompt ครองอยู่คือพื้นที่ที่งานจริงใช้ไม่ได้

ประเด็นไม่ใช่ว่า 1350 token ที่เกินมาจะทำให้คุณล้มละลาย แต่คือประโยคใน system prompt
เป็นต้นทุนประจำที่เกิดซ้ำถาวร มันจึงควรต้องพิสูจน์คุณค่าตัวเองแบบเดียวกับที่ต้นทุนประจำต้องทำ
ถามทุกบรรทัดว่ามันจะเปลี่ยนสิ่งที่โมเดลทำหรือไม่ ถ้าไม่ มันก็คือค่าสมาชิกรายเดือนที่ไม่ได้อะไรเลย

### คำสั่งแข่งกันเอง

นี่คือเหตุผลที่สำคัญกว่า และมันไม่ใช่เรื่องเงิน

โมเดลไม่ได้ถือรายการกฎแล้วเช็กทีละข้อ มันใส่ใจบทสนทนาทั้งหมดพร้อมกัน และความสนใจนั้น
มีจำกัดและถูกแบ่งกัน คำสั่งเพิ่มทุกอันดึงส่วนแบ่งความสนใจที่คำสั่งอื่นเคยได้ไป

ผลในทางปฏิบัติน่าอึดอัดและควรพูดตรง ๆ โมเดลที่ได้กฎห้าข้อทำตามได้น่าเชื่อถือกว่าโมเดล
ที่ได้กฎยี่สิบข้อ ไม่ใช่เพราะยี่สิบข้อมากเกินกว่าจะเก็บไว้ แต่เพราะกฎข้อที่ยี่สิบเจือจางกฎข้อแรก
การเพิ่มกฎที่คุณสนใจนิดหน่อยทำให้กฎที่คุณสนใจมากอ่อนลงเล็กน้อย

มันแย่ลงอีกเมื่อกฎมีปฏิสัมพันธ์กัน ซึ่งเกิดบ่อยกว่าที่คนคาดตอนเขียนทีละข้อ ลองพิจารณา prompt
ที่มีทั้งหมดนี้

```text
Always read a file before editing it.
Minimise the number of tool calls you make.
Never make an edit you have not verified.
Be efficient and avoid unnecessary work.
```

กฎข้อหนึ่งกับข้อสามเรียกร้อง tool call มากขึ้น กฎข้อสองกับข้อสี่เรียกร้องให้น้อยลง
ทุกข้อฟังดูสมเหตุสมผลเมื่ออยู่เดี่ยว ๆ และเมื่ออยู่ด้วยกันมันอธิบายความขัดแย้ง โมเดลจะแก้มัน
ด้วยวิธีใดวิธีหนึ่ง ต่างกันไปในแต่ละ turn และพฤติกรรมที่คุณเห็นจะดูเหมือนความสุ่ม มันไม่ใช่
ความสุ่ม มันคือคุณขอสองอย่างที่เข้ากันไม่ได้แล้วปล่อยให้โมเดลเลือกเอง

บล็อกพฤติกรรมใน `prompt.py` มีสี่ย่อหน้าสั้น ๆ และถูกตรวจทานกันเอง "Work in small steps"
กับ "change the smallest amount of text" ชี้ไปทางเดียวกัน "Look before you change anything"
กับ "read rather than guessing" ชี้ไปทางเดียวกัน ไม่มีอะไรในนั้นเถียงกับอะไรอื่นในนั้น
คุณสมบัตินี้รักษาไว้ได้ง่ายกว่ามากที่สี่ย่อหน้าเมื่อเทียบกับสี่สิบ ซึ่งเป็นเหตุผลที่ดีที่จะอยู่ที่สี่

### กฎในโค้ดชนะกฎใน prompt ทุกครั้ง

เหตุผลที่สามสำคัญที่สุดและเป็นเหตุผลที่เปลี่ยนวิธีที่คุณสร้างของ

prompt คือคำขอ แม้แต่คำสั่งที่เขียนดีคู่กับโมเดลที่ดีก็ยังเป็นแค่แนวโน้มที่แรง ไม่ใช่การรับประกัน
จะมี input บางอย่าง บทสนทนาบางอย่าง ถ้อยคำแปลก ๆ บางอย่างเสมอ ที่โมเดลทำอย่างอื่น

โค้ดไม่ใช่คำขอ โค้ดคือสิ่งที่เกิดขึ้น

คุณมีตัวอย่างที่ชัดเจนที่สุดอยู่แล้ว และมันคือบทที่ 08 ลองพิจารณาสองวิธีที่คุณอาจสร้าง
shell tool ได้

## 8. เขียน prompt.py และแก้ agent loop

ทีนี้มาถึงโค้ด ซึ่งหลังจากเถียงมาทั้งหมดแล้วกลับสั้นมาก

### prompt.py

ไฟล์ทั้งไฟล์ ตั้งแต่ต้นจนจบ

```python
import platform
import sys
from pathlib import Path

BEHAVIOUR = """You are a careful software assistant working inside one directory.

Work in small steps. Look before you change anything. When you need to know
what a file contains, read it rather than guessing. When you change a file,
change the smallest amount of text that does the job.

Prefer edit_file over write_file for existing files, because write_file
replaces the whole file and loses anything you did not include.

When you are done, say what you changed in one or two sentences."""


def build_system_prompt(root, extra=""):
    """Assemble the system prompt for a run inside root."""
    facts = [
        f"Workspace directory {Path(root).resolve()}",
        f"Platform {platform.system()}",
        f"Python {sys.version_info.major}.{sys.version_info.minor}",
    ]
    prompt = BEHAVIOUR + "\n\nFacts about this environment\n" + "\n".join(facts)
    if extra:
        prompt += "\n\n" + extra
    return prompt
```

มีการตัดสินใจเล็ก ๆ สามอย่างในนั้นที่ควรได้คำอธิบายอย่างละประโยค

prompt ถูกสร้างด้วย**ฟังก์ชัน** ไม่ใช่เก็บเป็นค่าคงที่ ค่าคงที่บรรจุ `platform.system()`
ไม่ได้ และทันทีที่คุณอยากได้ข้อเท็จจริงใน prompt คุณก็ต้องมีโค้ดมาผลิตมัน การสร้างมัน
ในฟังก์ชันยังแปลว่า prompt ถูกคำนวณตอนที่การรันเริ่มต้น ไม่ใช่ตอนที่ module ถูก import
ซึ่งคือความต่างระหว่าง prompt ที่อธิบายการรันปัจจุบัน กับ prompt ที่อธิบายสิ่งที่เป็นจริงตอน
ที่ Python แตะไฟล์นั้นครั้งแรก

`root` เป็น**พารามิเตอร์** แทนที่จะอ่านจาก `os.environ` ภายในฟังก์ชัน module ของ tool
อ่าน environment จริงตอน import และนั่นถูกต้องสำหรับ tool เพราะ workspace เป็นคุณสมบัติ
ของโปรเซส แต่ตรงนี้พารามิเตอร์ดีกว่าเพราะมันทำให้ฟังก์ชันทดสอบได้โดยไม่ต้องแตะ global state
ซึ่งเป็นสิ่งที่ `check.py` พึ่งพาพอดี

prompt อยู่ใน**ไฟล์ของตัวเอง** มันไม่ใช่สตริงข้างใน `agent.py` loop ไม่ควรมีความเห็นว่า
agent มีไว้ทำอะไร และการวางบุคลิกไว้ใน module แยกทำให้เส้นแบ่งนั้นสะอาด ในบทที่ 11
คุณจะมี loop หนึ่งอันกับ prompt ที่คุณแก้อยู่ตลอด และคุณไม่อยากเปิด loop เพื่อแก้ประโยคเดียว

### สิ่งที่เปลี่ยนใน agent.py

สามบรรทัด ที่ส่วนบนของ `run`

```python
def run(provider, user_input, system=None, max_turns=10):
    messages = []
    if system:
        messages.append({"role": "system", "content": system})
    messages.append({"role": "user", "content": user_input})
```

นั่นแทนที่บรรทัดเดียวจากบทที่ 09

```python
    messages = [{"role": "user", "content": user_input}]
```

`system=None` ที่มีค่าเริ่มต้นแปลว่าผู้เรียกเดิมทุกตัวยังทำงานได้ บทที่ 06 ถึง 09 เรียก
`run(provider, prompt)` ด้วยสองอาร์กิวเมนต์และไม่ได้รับผลกระทบ การทำให้พารามิเตอร์
เป็นทางเลือกแทนที่จะบังคับ คือสิ่งที่ทำให้การเปลี่ยนแบบนี้ลงจอดได้โดยไม่ต้องแตะอะไรต้นน้ำเลย

การ์ด `if system` ครอบคลุมทั้ง `None` และสตริงว่าง ดังนั้น prompt ว่างจึงไม่ผลิต
system message ที่ว่างเปล่า system message ว่างไม่ใช่ error แต่มันคือข้อความที่เสียเงิน
นิดหน่อยและไม่ได้บอกอะไร และบางครั้งโมเดลก็ตีความข้อความว่างที่ไม่คาดคิดว่ามีความหมาย

ยังมีการเปลี่ยนแปลงที่สองที่เล็กกว่าอยู่ด้านล่าง ตอนนี้ฟังก์ชันคืนทั้งข้อความและรายการ message

```python
        if not calls:
            print()
            return text, messages
```

บทที่ 09 คืนแค่ `text` การคืนบทสนทนามาด้วยทำให้ผู้เรียกตรวจสอบได้ว่าอะไรถูกส่งไปจริง
ซึ่งเป็นสิ่งที่ `check.py` ทำพอดีตอนที่มันยืนยันว่าข้อความแรกคือ system message
มันยังมีประโยชน์ในบทที่ 11 ที่ loop ถูกเรียกซ้ำ ๆ และบทสนทนาต้องอยู่รอดระหว่างการเรียก

### ทำไม system message ต้องมาก่อน

ไม่ใช่ "ใกล้ ๆ ข้างหน้า" แต่คือมาก่อน ตำแหน่งศูนย์ ก่อนทุกอย่างที่ผู้ใช้พูด

สามเหตุผล และไม่เกี่ยวข้องกันเลย ซึ่งเป็นสัญญาณดีว่าลำดับนี้ไม่ได้ตั้งขึ้นมาลอย ๆ

**API นิยามไว้แบบนั้น** สำหรับ endpoint ที่เข้ากันได้กับ OpenAI system prompt คือข้อความ
ที่ตั้ง `role` เป็น `system` และคาดว่าจะอยู่ต้นอาร์เรย์ provider ถูกเทรนและปรับจูนบนบทสนทนา
ที่มีรูปแบบนั้น การวาง system message ไว้กลางบทสนทนาไม่ใช่ error ที่คุณจะเห็นรายงาน
มันแค่เป็น request ที่โมเดลเคยเห็นน้อยกว่ามาก และรูปแบบที่คุ้นเคยน้อยกว่าย่อมได้พฤติกรรม
ที่น่าเชื่อถือน้อยกว่า

**คำสั่งต้องมาก่อนสิ่งที่มันควบคุม** อันนี้คือข้อที่สำคัญต่อพฤติกรรม กฎเรื่องการชอบ `edit_file`
ต้องอยู่ใน context ก่อนที่โมเดลจะอ่านคำขอที่อาจล่อมันไปหา `write_file` โมเดลอ่านบทสนทนา
ทั้งก้อน แต่ลำดับก็ยังมีความหมาย และคำสั่งที่ปรากฏหลังงานอ่านเหมือนความคิดที่นึกได้ทีหลัง
หรือการแก้ไข มากกว่าจะเป็นกฎประจำ

**มันนิ่ง และเนื้อหาที่นิ่งควรอยู่หน้าสุด** system prompt เหมือนกันเป๊ะในทุก request ของ
session ทุกอย่างหลังจากนั้นเปลี่ยน provider ที่ให้บริการ prompt caching ใช้ prefix ที่ใช้ร่วมกัน
เป็นคีย์ ดังนั้นบล็อกที่ไม่เปลี่ยนที่ตำแหน่งศูนย์คือรูปแบบที่แคชได้พอดี และ input ที่แคชแล้ว
ถูกกว่าและเร็วกว่ามาก ถ้าวาง system prompt ไว้หลังข้อความแรกของผู้ใช้ prefix ก็จะต่างกัน
ทุก session และไม่มีอะไรให้แคชเลย

มีประเด็นที่สี่ซึ่งจริง ๆ แล้วเป็นเรื่องของ `providers.py` และเป็นเหตุผลที่การออกแบบนี้อยู่รอด
เมื่อเจอ API ตัวที่สอง Anthropic API ไม่ได้รับ system prompt เป็น message เลย มันรับเป็น

ทุกส่วนของ coding agent มีอยู่ครบแล้ว loop ที่เดินต่อไปจนกว่าโมเดลจะหยุดขอ tool
การ stream เพื่อให้คุณดูมันทำงานได้ provider สองตัวเพื่อที่คุณจะไม่ถูกล็อกไว้กับบริษัทเดียว
tool เจ็ดตัวที่เป็นชุดครบสำหรับการเปลี่ยนโค้ด ขอบเขต workspace การปฏิเสธ credential
เพดานผลลัพธ์ และด่านมนุษย์บน shell และตอนนี้ก็มี prompt ที่บอกโมเดลว่ามันอยู่ที่ไหน
และควรทำตัวอย่างไร

และคุณใช้อะไรไม่ได้เลยสักอย่าง

ไม่มีโปรแกรม มีแค่ห้าโฟลเดอร์ แต่ละอันมีสำเนา `tools.py` ของตัวเองในระดับความสมบูรณ์
ที่ต่างกัน แต่ละอันมี `check.py` ที่พิสูจน์ข้ออ้างของบทหนึ่งแล้วจบการทำงาน ไม่มีอะไรรับงาน
จากคุณ ไม่มีอะไรรันเกินหนึ่ง request โดยไม่มีไฟล์ check มาขับเคลื่อน ถ้าคุณอยากชี้สิ่งนี้ไปที่
โฟลเดอร์จริงแล้วขอให้มันแก้บั๊กในบ่ายนี้ คุณต้องเขียนสายไฟเองทั้งหมด และคุณจะเจอคำถาม
ที่ยังไม่มีบทไหนตอบทันที

workspace มาจากไหนเวลาคนรันมันจริง ไม่ใช่เทสต์ ข้อความที่สองถูกเพิ่มเข้าไปในบทสนทนา
ที่มีอยู่แล้วอย่างไร เพื่อที่คุณจะพูดได้ว่า "no, the other file" โดยไม่ต้องเริ่มใหม่ เกิดอะไรขึ้น
เมื่อโมเดลอยากไปต่อเกินขีดจำกัดของ turn ผู้ใช้เห็นอะไรจริง ๆ ระหว่างที่มันทำงาน ในเมื่อ
trace ของ tool ที่พิมพ์ดิบ ๆ อ่านไม่รู้เรื่องหลังจากราวสามการเรียก คนต้องพิมพ์อะไรถึงจะเริ่มมันได้

ไม่มีข้อไหนยาก แต่ทุกข้อยังไม่ได้ถูกสร้าง

### แบบฝึกหัดก่อนไปต่อ

**ข้อหนึ่ง** ลบบล็อกข้อเท็จจริงออก รัน agent กับ directory จริงโดยมีแค่ `BEHAVIOUR`
