## 2. ความล้มเหลวแบบไหนที่คุ้มจะ retry

นี่คือการตัดสินใจทั้งหมด

```python
RETRYABLE_STATUS = {408, 409, 429, 500, 502, 503, 504, 529}
```

```python
def with_retries(call, attempts=4, sleep=time.sleep):
    """Run call, retrying only the failures that retrying can fix.

    A 400 means the request itself was wrong, so sending the same wrong
    request again produces the same wrong answer more slowly. Only statuses
    that mean try again later, and transport failures where nothing arrived
    at all, are worth a second attempt.
    """
    last_error = None
    for attempt in range(1, attempts + 1):
        try:
            return call()
        except httpx.HTTPStatusError as error:
            if error.response.status_code not in RETRYABLE_STATUS:
                raise
            last_error = error
            if attempt == attempts:
                break
            sleep(delay_for(attempt, error.response))
        except httpx.TransportError as error:
            last_error = error
            if attempt == attempts:
                break
            sleep(delay_for(attempt))
    raise last_error
```

**มันคืออะไร** ฟังก์ชันที่รันฟังก์ชันอีกตัวได้สูงสุดสี่ครั้ง รอระหว่างแต่ละครั้ง
และยอมแพ้ในแบบที่ยังรักษา error ต้นฉบับไว้

**ทำไมเราถึงทำ** เพราะความล้มเหลวส่วนใหญ่ที่ agent จริงเจอไม่ใช่ bug มันคือดินฟ้าอากาศ
provider ยุ่งอยู่หนึ่งวินาที socket ตาย ไม่มีอะไรผิดในโปรแกรมของคุณ
และไม่มีอะไรในนั้นที่ต้องเปลี่ยน

**ทำไมต้องทำแบบนี้ ไม่ใช่แบบอื่น** เวอร์ชันที่ชวนให้ทำคือ `except Exception`
เปล่า ๆ ที่มี sleep อยู่ในนั้น และเวอร์ชันนั้นคือหายนะ
เพราะมันเปลี่ยนความล้มเหลวถาวรทุกอันให้เป็นความล้มเหลวถาวรที่ช้า การแบ่งสำคัญกว่ากลไก

### การแบ่ง พูดกันตรง ๆ

คำถามไม่ใช่ว่า error นี้แย่แค่ไหน คำถามคือ request เดิม ที่ส่งไปอีกครั้ง
จะให้คำตอบที่ต่างออกไปได้หรือไม่

| Status | ความหมาย | Retry | ทำไม |
| --- | --- | --- | --- |
| `408` | request timeout | ใช่ | server เลิกรอ ไม่ได้เลิกเพราะเนื้อหา |
| `409` | conflict | ใช่ | การแย่งกันชั่วคราวฝั่ง provider |
| `429` | too many requests | ใช่ | คุณมาเร็วไป ไม่ได้ผิด |
| `500` | internal server error | ใช่ | มีอะไรพังฝั่งโน้น ไม่ใช่ฝั่งนี้ |
| `502` | bad gateway | ใช่ | proxy ติดต่อ backend ไม่ได้ในตอนนั้น |
| `503` | service unavailable | ใช่ | service บอกไว้ในชื่อแล้ว |
| `504` | gateway timeout | ใช่ | backend ช้าครั้งนี้ครั้งเดียว |
| `529` | overloaded | ใช่ | รหัสนอกมาตรฐานของ Anthropic สำหรับเรื่องนี้พอดี |
| `400` | bad request | **ไม่** | JSON ของคุณผิดรูป หรือ field ผิด |
| `401` | unauthorized | **ไม่** | key ของคุณผิด และจะยังผิดอยู่ |
| `403` | forbidden | **ไม่** | คุณไม่มีสิทธิ์เข้าถึง model นี้ |
| `404` | not found | **ไม่** | URL หรือชื่อ model นั้นไม่มีอยู่ |
| `413` | payload too large | **ไม่** | บทสนทนาใหญ่เกินไปและจะใหญ่เกินไปต่อไป |
| `422` | unprocessable | **ไม่** | request ถูก parse ได้และยังไม่ถูกต้องอยู่ดี |

อ่านสองครึ่งเป็นสองประโยค ทุกอย่างเหนือเส้นแปลว่าลองใหม่ทีหลัง
ทุกอย่างใต้เส้นแปลว่าสิ่งที่คุณส่งไปผิด

นั่นคือเหตุผลที่ `with_retries` จัดการสองกรณีด้วย `raise` กับ `sleep`
แทนที่จะใช้เส้นทาง code ร่วมกัน status ที่ retry ไม่ได้จะถูก re-raise ทันที
โดยไม่ห่อหุ้ม ตั้งแต่ความพยายามครั้งแรก มันจึงถึงมือคุณภายในไม่ถึงวินาที
พร้อม exception ของ `httpx` ต้นฉบับที่ยังครบถ้วน

### ทำไมการ retry 400 จึงแย่กว่าการไม่ retry มัน

ควรพูดให้ชัดว่าทำไมครึ่งที่แย่ถึงแย่ เพราะความล้มเหลวที่มันก่อนั้นแนบเนียนมากกว่าจะดังโครม

สมมติคุณ retry ทุกอย่าง คุณส่งบทสนทนาที่มี tool call ซึ่งขาดผลลัพธ์ไป
ซึ่งคือกับดักเรื่องการจับคู่จากบทที่ 14 provider ตอบ `400` คุณรอหนึ่งวินาทีแล้วส่งบทสนทนาเดิมเป๊ะ
`400` คุณรอสองวินาที `400` คุณรอสี่วินาที `400`

เจ็ดวินาทีต่อมาคุณ raise error ตัวเดียวกับที่คุณมีตั้งแต่วินาทีที่ศูนย์ ไม่ได้อะไรเพิ่ม
คุณเผาสี่ request จากโควตา rate limit ของคุณ ซึ่งทำให้ `429` ของจริงมีโอกาสเกิดมากขึ้น
สำหรับการเรียกจริงครั้งถัดไป และ error
ที่คุณแสดงให้ผู้ใช้เห็นในที่สุดก็มาถึงเจ็ดวินาทีหลังความผิดพลาด
ซึ่งตอนนั้นเขาเริ่มไปอ่านอย่างอื่นแล้ว

ตัวคูณคือสิ่งที่ทำให้เรื่องนี้ร้ายแรง retry สี่ครั้งต่อการเรียกหนึ่งครั้ง บน agent
ที่เรียกสิบครั้งต่องาน คือสี่สิบ request ไร้ประโยชน์ต่อหนึ่งงานที่พัง บน key
ที่แชร์กัน นั่นมากพอที่จะทำให้เพื่อนร่วมงานของคุณโดน rate limit
ออกจาก service ที่กำลังทำงานได้ดีอยู่

`400` คือ bug ใน code ของคุณหรือใน state ของบทสนทนา
การตอบสนองที่ถูกต้องต่อ bug คือการเห็นมันทันที

### ทำไม transport error ถึงนับว่า retry ได้

อนุประโยคนี้สมควรมีย่อหน้าของตัวเองเพราะการให้เหตุผลต่างจากกรณี status code

```python
        except httpx.TransportError as error:
            last_error = error
```

`httpx.TransportError` คือคลาสฐานของทุกความล้มเหลวที่การแลกเปลี่ยนไม่สมบูรณ์
`ConnectError`, `ConnectTimeout`, `ReadTimeout`, `ReadError`, `WriteError`,
`PoolTimeout`, `RemoteProtocolError` สิ่งที่มันมีร่วมกันคือสิ่งที่ทำให้มันปลอดภัย

**ไม่มีอะไรมาถึง จึงไม่มีอะไรเกิดขึ้น** ไม่มี HTTP status เพราะไม่มี HTTP response
request อาจไม่เคยไปถึง server หรือคำตอบของมันไม่เคยมาถึงคุณ ในทั้งสองกรณี model
ไม่ได้ผลิตอะไรที่คุณมีอยู่ และไม่มี state ฝั่งคุณที่เปลี่ยนไป การส่งใหม่ไม่ใช่การทำซ้ำ
มันคือการทำให้สิ่งนั้นเกิดขึ้นเป็นครั้งแรก

สังเกต argument ตัวที่สองในสาขา transport

```python
            sleep(delay_for(attempt))
```

ไม่มีการส่ง response เข้าไป เพราะไม่มี response `delay_for` จัดการกรณีนั้นด้วย
`if response is not None` แล้วตกลงไปที่สูตรทันที server
ที่ไม่เคยตอบย่อมไม่ได้ส่ง header `Retry-After` มา

พูดตรง ๆ เรื่องกรณีเดียวที่การให้เหตุผลนี้ไม่สมบูรณ์ `ReadTimeout`
ที่เกิดหลังจาก server รับ request ไปแล้วแปลว่างานอาจเกิดขึ้นแล้วและมีแค่คำตอบที่หายไป
สำหรับการเรียก model นั่นไม่มีอันตราย
เพราะต้นทุนมีแค่เงินและ state มีแค่บทสนทนาที่คุณควบคุมอยู่ สำหรับการเรียก tool
มันจะไม่ไร้อันตรายเลย ซึ่งคือหัวข้อ 5

### ทำไมสี่ครั้ง

`attempts=4` เป็นค่าตั้งต้นไม่ใช่กฎหมาย และเหตุผลคือเลขคณิต ด้วยหน่วงเวลาในหัวข้อถัดไป
สี่ครั้งกินเวลาราวเจ็ดวินาทีในกรณีแย่สุด นั่นนานพอจะข้ามการรีสตาร์ต gateway
หรือช่วง rate limit ที่พุ่งขึ้น และสั้นพอที่คนที่นั่งดู terminal
ยังไม่ทันตัดสินใจว่าโปรแกรมค้าง

สิบครั้งจะครอบคลุมการล่มที่ยาวกว่า และมันก็จะแปลว่า endpoint
ที่ตายจริงใช้เวลาหลายนาทีกว่าจะรายงานตัวเอง เมื่อ provider ล่ม
การรู้เร็วมีค่ามากกว่าโอกาสเล็ก ๆ ที่จะรอดจากมัน

## 3. ฟัง server

```python
def delay_for(attempt: int, response=None, base=1.0, cap=30.0) -> float:
    """How long to wait before the given attempt, counting from one.

    A Retry-After header wins outright. It is the server telling us when it
    will be ready, and guessing earlier than that just wastes a request and
    makes the overload worse.
    """
    if response is not None:
        header = response.headers.get("Retry-After")
        if header:
            try:
                return float(header)
            except ValueError:
                pass
    exponential = min(cap, base * (2 ** (attempt - 1)))
    return exponential * (0.5 + random.random() / 2)
```

อ่านลำดับของฟังก์ชัน header ถูกตรวจก่อน และถ้ามันมีอยู่และ parse ได้ ฟังก์ชันก็คืนค่า
สูตรที่อยู่ใต้มันไม่เคยได้รัน

**`Retry-After` คืออะไร** header ของ response ที่ถูกนิยามไว้ในสเปก HTTP
และถูกส่งโดยแทบทุก provider ที่จำกัดอัตราคุณ มันบรรจุจำนวนวินาที `Retry-After: 2`
แปลว่ากลับมาในอีกสองวินาที

**ทำไมเราถึงทำ** เพราะมันคือตัวเลขเดียวในบททั้งบทนี้ที่ไม่ใช่การเดา
สูตรของเราคือ heuristic ที่เราคิดขึ้นเองโดยไม่รู้อะไรเกี่ยวกับ service เลย header คือ
service ที่บอกเราจากข้างในว่ามันจะพร้อมเมื่อไร
เมื่อฝ่ายหนึ่งในบทสนทนารู้คำตอบและอีกฝ่ายกำลังคาดเดา การฟังไม่ใช่มารยาท มันคือความถูกต้อง

**ทำไมต้องทำแบบนี้ ไม่ใช่แบบอื่น** ทางเลือกที่เห็นชัดคือถือว่า header เป็นคำแนะนำ
แล้วเลือกตัวเลขที่น้อยกว่าในสองตัว บนทฤษฎีที่ว่ากลับมาเร็วอาจได้ผลและไม่เสียหาย
ทฤษฎีนั้นผิดทั้งสองครึ่ง

การกลับมาเร็วไม่ได้ผล เพราะ server บอกคุณแล้วว่ามันจะยังไม่พร้อม และมันหมายความอย่างนั้นจริง
request ที่มาเร็วจะได้ `429` อีก คุณจึงใช้ความพยายามไปหนึ่งครั้งจากงบสี่ครั้ง
เพื่อเรียนรู้สิ่งที่คุณถูกบอกไปแล้ว

และมันเสียหายด้วย service ที่กำลังจำกัดอัตราคุณกำลังแบกโหลดอยู่ ทุก request
ที่คุณส่งไปขณะที่มันกำลังปัดโหลดออก คืองานที่มันต้องทำเพื่อปฏิเสธคุณ
และมันทำแบบนั้นให้ทุก client พร้อมกัน header คือกลไกประสานงาน
การเพิกเฉยต่อมันคือการทรยศ และมันทำให้เหตุขัดข้องยาวขึ้นสำหรับทุกคนรวมทั้งคุณ

### สูตร เมื่อ server ไม่พูดอะไร

ความล้มเหลวส่วนใหญ่ไม่ได้พก `Retry-After` มาด้วย `500` จาก worker ที่ crash
ไม่มีความเห็นเรื่องอนาคต นั่นคือสิ่งที่สองบรรทัดสุดท้ายมีไว้เพื่อ

```python
    exponential = min(cap, base * (2 ** (attempt - 1)))
```

`attempt` นับจากหนึ่ง `2 ** (attempt - 1)` จึงให้หนึ่ง สอง สี่ แปด เวลารอเพิ่มเป็นสองเท่าทุกครั้ง

การเพิ่มเป็นสองเท่าแทนที่จะหน่วงคงที่คือความหมายของคำว่า backoff การ retry
ทุกหนึ่งวินาทีแบบคงที่คือการส่ง request เดิมด้วยอัตราเดิมไปเรื่อย ๆ ซึ่งเป็นพฤติกรรมของ
client ที่ไม่ได้เรียนรู้อะไรเลยจากการถูกปฏิเสธมาสามครั้ง
การเพิ่มเป็นสองเท่าแปลว่า service ที่ยุ่งชั่วคราวจะเห็นคุณอีกครั้งเร็ว
และ service ที่พังหนักจะเห็นคุณถอยออกไปให้พ้นทาง

`min(cap, ...)` หยุดการเพิ่มเป็นสองเท่าที่สามสิบวินาที ถ้าไม่มีมัน ความพยายามครั้งที่สิบ
จะรอเกินแปดนาที และการรอที่นานพอจนผู้ใช้คิดว่าโปรแกรมค้าง แย่กว่าความล้มเหลวที่เขาเห็นได้

| attempt | `2 ** (attempt - 1)` | exponential หลัง cap | เวลารอจริงหลัง jitter |
| --- | --- | --- | --- |
| 1 | 1 | 1.0 | 0.5 ถึง 1.0 วินาที |
| 2 | 2 | 2.0 | 1.0 ถึง 2.0 วินาที |
| 3 | 4 | 4.0 | 2.0 ถึง 4.0 วินาที |
| 4 | 8 | 8.0 | 4.0 ถึง 8.0 วินาที |
| 6 | 32 | 30.0 | 15.0 ถึง 30.0 วินาที |

ด้วยค่าตั้งต้นสี่ครั้ง คุณใช้แค่สามแถวแรกเท่านั้น
เวลารอรวมในกรณีแย่สุดจึงเป็นเจ็ดวินาที cap
มีไว้สำหรับผู้เรียกที่ขอจำนวนครั้งมากกว่าค่าตั้งต้น

### try รอบ float

```python
            try:
                return float(header)
            except ValueError:
                pass
```

`Retry-After` มีรูปแบบที่ถูกต้องสองแบบ แบบวินาที `Retry-After: 2` และแบบวันที่ HTTP
`Retry-After: Wed, 21 Oct 2015 07:28:00 GMT` ผู้ให้บริการ LLM ส่งแบบวินาที proxy
load balancer และ gateway ขององค์กรบางครั้งนั่งอยู่หน้าพวกเขาและส่งแบบวันที่

`float("Wed, 21 Oct 2015 07:28:00 GMT")` raise `ValueError` และถ้า exception
นั้นหลุดออกมา header ผิดปกติจาก middlebox ที่คุณไม่รู้ว่ามีอยู่
จะทำให้ฟังก์ชันที่มีหน้าที่ทั้งหมดคือการอยู่รอดเมื่อมีอะไรผิดพลาดนั้นพัง `pass` ตกลงไปที่สูตร
ซึ่งเป็นคำตอบที่แย่กว่าการ parse วันที่ และเป็นคำตอบที่ดีกว่า traceback มาก

## 4. ทำไม jitter ไม่ใช่ของประดับ

```python
    return exponential * (0.5 + random.random() / 2)
```

ตัวคูณนั้นดูเหมือนสัญญาณรบกวนที่ใส่มาเพื่อให้มีสัญญาณรบกวน
มันคือบรรทัดที่สำคัญที่สุดในไฟล์นี้ และควรเข้าใจให้ชัดว่ามันป้องกันอะไร

**jitter คืออะไร** การสุ่มเวลารอของแต่ละ client เพื่อให้ client
ที่ล้มเหลวพร้อมกันไม่กลับมาพร้อมกัน `random.random()` ให้ float ใน `[0.0, 1.0)`
`0.5 + random.random() / 2` จึงให้ตัวคูณใน `[0.5, 1.0)`
และเวลารอจริงอยู่ระหว่างครึ่งหนึ่งของหน่วงที่คำนวณได้กับเต็มจำนวน

**ทำไมเราถึงทำ** เพราะถ้าไม่มีมัน ปัญหาชั่วครู่จะกลายเป็นเหตุขัดข้องที่ยืดเยื้อ
และ client คือฝ่ายที่ยืดมันออกไป

### ความล้มเหลวที่มันป้องกัน ทีละขั้น

นึกภาพ service ที่มี client หนึ่งพันราย มีอะไรผิดพลาดหนึ่งวินาที
และทุก request ที่ค้างอยู่ได้ `503` กลับมา

ทีนี้รัน logic การ retry โดยไม่มี jitter ที่ซึ่งเวลารอคือหนึ่งวินาทีเป๊ะ แล้วสองวินาทีเป๊ะ
แล้วสี่วินาทีเป๊ะ

ที่เวลาศูนย์ client หนึ่งพันรายล้มเหลว แต่ละรายคำนวณหน่วงได้ 1.0 วินาทีเป๊ะ ที่เวลาหนึ่ง
request หนึ่งพันมาถึงในเสี้ยววินาทีเดียวกัน

service เพิ่งกลับมาและยังเย็นอยู่ cache ของมันว่างเปล่า connection pool ของมันว่างเปล่า
และตอนนี้มันได้รับโหลดสูงสุดของทั้งวันอัดรวมมาในชั่วขณะเดียว มันล้มอีกครั้ง
ซึ่งมันจะไม่ล้มถ้า request หนึ่งพันเดียวกันนั้นกระจายออกไปตลอดหนึ่งวินาที

ดังนั้นที่เวลาหนึ่ง client หนึ่งพันรายล้มเหลวอีกครั้ง แต่ละรายคำนวณหน่วงได้ 2.0 วินาทีเป๊ะ
ที่เวลาสาม request หนึ่งพันมาถึงในเสี้ยววินาทีเดียวกัน

ไม่มีอะไรตัดวงจรนี้ service ไม่ฟื้นเพราะมันถูกกำแพงทราฟฟิกที่ประสานกันซัดทุกครั้งที่มันลุกขึ้นยืน
และกำแพงนั้นประสานกันพอดีเพราะทุก client รัน code การ retry ที่ดูถูกต้องอันเดียวกัน
เหตุขัดข้องหนึ่งวินาทีตอนนี้ยาวหนึ่งนาที และไม่มี client
รายไหนทำอะไรผิดนอกจากเหมือนกับ client รายอื่นทุกราย

รูปแบบนั้นมีชื่อว่า thundering herd
และมันคือหนึ่งในวิธีคลาสสิกที่ระบบกระจายทำตัวเองล่มโดยไม่มีองค์ประกอบใดผิดสักอย่าง

### ตัวคูณทำอะไรกับเรื่องนั้น

ทีนี้ใส่ jitter กลับเข้าไป client แต่ละรายรอระหว่าง 0.5 กับ 1.0 วินาที client
หนึ่งพันรายมาถึงกระจายตลอดครึ่งวินาทีแทนที่จะอัดกันในชั่วขณะเดียว
อัตราการมาถึงสูงสุดจึงเป็นเศษเสี้ยวของเดิม service ดูดซับคลื่นแรกได้ อุ่นเครื่องขึ้น และ
client ที่ล้มเหลวในคลื่นแรกจะมาถึงช้าลงไปอีกเพราะหน่วงครั้งที่สองของพวกมันก็ถูก jitter ด้วย

ฝูงก็ยังเป็นฝูง แต่มันไม่ใช่กำแพงอีกต่อไป

รายละเอียดสองอย่างของตัวคูณนี้ควรตั้งข้อสังเกต

**มันทำได้แค่ย่นเวลารอ** ช่วงคือ `[0.5, 1.0)` ของหน่วงที่คำนวณได้ ไม่ใช่ `[0.5, 1.5)`
ไม่มีใครรอนานกว่าที่ตาราง backoff กำหนด การเพิ่ม jitter
จึงไม่เคยทำให้กรณีแย่สุดช้ากว่าตารางในหัวข้อ 3

**มันไม่มีวันถึงศูนย์** พื้นที่ 0.5 แปลว่า client ที่โชคร้ายก็ยัง retry ทันทีไม่ได้ ตัวคูณที่เป็น
`random.random()` เปล่า ๆ บางครั้งจะให้หน่วงแค่ไม่กี่มิลลิวินาที ซึ่งคือ client
ที่เพิกเฉยต่อ backoff ที่มันเพิ่งคำนวณเองไปแล้วโดยปริยาย

check พิสูจน์ว่า jitter อยู่จริง
และมันทำด้วยวิธีเดียวที่ใช้ได้กับความสุ่ม ซึ่งคือเรียกฟังก์ชันซ้ำ ๆ แล้วนับคำตอบที่ต่างกัน

```python
    spread = {delay_for(3) for _ in range(20)}
    if len(spread) < 2:
        fail("the delay has no jitter, so every client would retry at the same instant")
```

เรียกยี่สิบครั้ง เก็บลง set ถ้ามีคนลบตัวคูณทิ้งตอนเก็บกวาด code set
จะมีสมาชิกตัวเดียวและ check จะล้มเหลวด้วยข้อความที่บอกว่าทำไมมันถึงสำคัญ
แทนที่จะบอกว่ามีข้อยืนยันที่เป็นเท็จ

## 5. สิ่งที่ต้องไม่ถูก retry อัตโนมัติเด็ดขาด

ทุกอย่างจนถึงตรงนี้คือการทำให้ความล้มเหลวหายไป หัวข้อนี้คือเส้นแบ่ง
และเป็นส่วนของบทนี้ที่คนทำพลาดบน production มากกว่าใน tutorial

ดูว่า `with_retries` ถูกใช้กับอะไร และที่สำคัญกว่าคือดูว่ามันไม่ได้ถูกใช้กับอะไร
อ่าน docstring ของโมดูล

```python
Not everything may be retried. Asking the model again is safe because it
changes nothing outside the conversation. Running a tool that sent an email
is not, which is why nothing in this module wraps a tool call.
```

**การถาม model อีกครั้งปลอดภัย** การเรียก model อ่านบทสนทนาแล้วคืนข้อความกับคำขอเรียก tool
มันไม่แตะอะไรนอกกระบวนการ ถ้าคุณส่งสองครั้ง คุณได้สองคำตอบแล้วใช้อันเดียว
ต้นทุนคือเงินกับ latency และทั้งคู่มีขอบเขตและเล็ก

**การรัน tool อีกครั้งไม่ปลอดภัย** tool มีอยู่เพื่อเปลี่ยนอะไรบางอย่างนอกกระบวนการโดยเฉพาะ
`write_file` เขียนลงดิสก์ของคุณ `run_shell` เริ่ม subprocess บน harness จริง
รายการ tool จะโตขึ้นจนรวมสิ่งที่ส่งอีเมล เปิด pull request เรียก API การ deploy
และตัดบัตรเครดิต

ลองพิจารณา timeout เดียวกันในสองที่ การเรียก model timeout หลังจาก server รับมันไปแล้ว
คุณ retry และกรณีแย่สุดคือคุณจ่ายสองครั้ง การเรียก tool ที่ทำการชำระเงิน timeout
หลังจาก server รับมันไปแล้ว คุณ retry
และกรณีแย่สุดคือลูกค้าถูกตัดเงินสองครั้งและตอนนี้มันคือ ticket ของ support การคืนเงิน
และการสนทนาว่า agent ของคุณควรได้เข้าใกล้ API การชำระเงินหรือไม่

สองกรณีนั้นดูเหมือนกันเป๊ะจากภายในตัวช่วย retry แบบทั่วไป
นั่นคือเหตุผลพอดีว่าทำไมตัวช่วยนี้ต้องไม่เป็นแบบทั่วไป

### idempotency ในภาษาธรรมดา

operation หนึ่งเป็น idempotent เมื่อทำมันสองครั้งแล้วโลกอยู่ในสภาพเดียวกับทำครั้งเดียว

การอ่านไฟล์เป็น idempotent อ่านสิบครั้ง ไฟล์ไม่เปลี่ยนและคุณได้เนื้อหาเดิมสิบครั้ง
การตั้งค่าให้เป็นเจ็ดเป็น idempotent การบวกเจ็ดเข้ากับค่าหนึ่งไม่ใช่
เพราะทำสองครั้งแล้วคุณได้สิบสี่ การส่งอีเมลไม่ใช่ การตัดบัตรไม่ใช่

คำนี้สำคัญเพราะมันแปลงความกังวลคลุมเครือเรื่อง retry
ให้เป็นคุณสมบัติที่คุณตรวจได้ทีละ tool สำหรับแต่ละ tool ให้ถามว่าการรันมันสองครั้ง
เหมือนกับการรันครั้งเดียวหรือไม่ ถ้าใช่ การ retry มันปลอดภัย ถ้าไม่ การ retry
มันต้องมีอะไรเพิ่ม

### อะไรเพิ่มที่ว่านั้นคืออะไร

กลไกคือ idempotency key และทุก API ด้านการชำระเงินและการส่งข้อความที่จริงจังก็ทำมัน
ซึ่งบอกคุณว่าปัญหานี้เป็นสากลแค่ไหน

ผู้เรียกสร้างตัวระบุที่ไม่ซ้ำสำหรับ operation ก่อนจะส่ง และแนบมันไปกับ request
service ที่รับบันทึก key นั้นไว้คู่กับผลลัพธ์ เมื่อ request มาถึงพร้อม key ที่มันเคยเห็นแล้ว
มันไม่ทำงานนั้นซ้ำ มันคืนผลลัพธ์ที่บันทึกไว้ครั้งแรก

ในเชิงรูปร่าง โดยไม่มี API จริง

```python
def charge(amount, idempotency_key):
    if idempotency_key in already_done:
        return already_done[idempotency_key]      # the earlier result, no new charge
    result = payment_api.charge(amount, key=idempotency_key)
    already_done[idempotency_key] = result
    return result
```

มีสองอย่างในนั้นที่รับน้ำหนักไว้

**key ถูกสร้างโดยผู้เรียก ก่อนความพยายามครั้งแรก และถูกใช้ซ้ำในทุกการ retry** key
ที่ถูกสร้างภายใน retry loop จะต่างกันทุกครั้ง
ซึ่งทำให้ทุกความพยายามดูเหมือน operation ใหม่และทำลายกลไกทั้งหมด key
ระบุความตั้งใจที่จะตัดเงิน ไม่ใช่ระบุ HTTP request แต่ละครั้ง

**การเรียกซ้ำคืนผลลัพธ์เดิมแทนที่จะคืน error** นั่นคือสิ่งที่ทำให้การ retry โปร่งใส
ผู้เรียกที่ทำ response หายเพราะ timeout ถามใหม่ ได้คำตอบที่มันพลาดไป
และไม่มีวันรู้ว่าการเรียกครั้งที่สองทำงานหรือเล่นซ้ำ การคืน error จะปลอดภัยแต่ไร้ประโยชน์
เพราะผู้เรียกก็ยังไม่รู้อยู่ดีว่าการตัดเงินสำเร็จหรือไม่

ผลที่สำคัญคือ logic นั้นต้องอยู่ที่ไหน ตัวช่วย retry จัดหามันให้ไม่ได้
เพราะมีแต่ tool เท่านั้นที่รู้ว่า operation ของตัวเองคืออะไร
และอะไรนับว่าเป็น operation เดียวกัน ซึ่งคือเหตุผลของการตัดสินใจออกแบบที่หัวข้อนี้มีอยู่เพื่ออธิบาย

### ทำไมไม่มีอะไรใน retry.py ที่ห่อการเรียก tool

พูดออกมาตรง ๆ เพราะมันคือการไม่มีอยู่โดยตั้งใจ และการไม่มีอยู่นั้นมองข้ามได้ง่าย

`retry.py` มีสองฟังก์ชัน `delay_for` ซึ่งคำนวณตัวเลข และ `with_retries` ซึ่งห่อ callable
ทั้งคู่ไม่รู้อะไรเกี่ยวกับ tool เลย และ `agent.py` ไม่ได้ import `retry` เลยด้วยซ้ำ
บรรทัดที่ dispatch tool ยังเป็นแบบเดียวกับในบทที่ 04 เป๊ะ

```python
                result = tools.run(call["name"], call["arguments"])
```

ไม่มีตัวห่อ retry โดยตั้งใจ

การออกแบบทางเลือกนั้นชวนให้ทำมากและมันคือกับดัก คุณมีตัวช่วย retry ที่ดีอยู่แล้ว
การเรียก tool ก็ล้มเหลวบ้าง คุณจึงห่อบรรทัด dispatch และตอนนี้ทุก tool
ในโปรแกรมได้การ retry อัตโนมัติฟรี รวมถึงตัวที่ไม่ควรได้มันเลย bug
ที่เกิดจากเรื่องนี้ไม่โผล่ตอนทดสอบ เพราะ tool ที่คุณใช้ทดสอบเป็น idempotent ทั้งหมด
มันโผล่ครั้งแรกที่มีคนเพิ่ม tool ที่มีผลข้างเคียงจริง
และมันโผล่ในรูปการกระทำซ้ำที่ไม่มีข้อความ error ที่ไหนเลย
เพราะจากมุมมองของโปรแกรมไม่มีอะไรผิดพลาด

เมื่อ tool ต้องการการ retry จริง ๆ การ retry ควรอยู่ภายใน tool นั้น ข้าง ๆ idempotency
key ที่ทำให้มันถูกต้อง ตัวช่วยยังอยู่ที่เดิม
ห่อ operation เดียวของโปรแกรมนี้ที่ปลอดภัยจะทำซ้ำได้จริง

### with_retries ควรไปอยู่ที่ไหนจริง ๆ

มีที่ที่ถูกต้องเพียงที่เดียว และมันคือภายใน provider `providers.py`
ในโฟลเดอร์นี้วางมันไว้ตรงนั้นแล้ว ในฟังก์ชันเล็ก ๆ ที่ provider ทั้งสองตัวเรียกใช้

```python
from retry import with_retries


def open_stream(client, url, payload, headers, attempts=4):
    """Open a streaming request, retrying the failures worth retrying."""

    def once():
        request = client.build_request("POST", url, json=payload, headers=headers)
        response = client.send(request, stream=True)
        if response.status_code >= 400:
            response.read()
            response.close()
            response.raise_for_status()
        return response

    return with_retries(once, attempts=attempts)
```

provider คือ object เดียวในโปรแกรมที่รู้ว่ามันกำลังพูด HTTP มันคือที่ที่ `httpx`
ถูก import ที่ที่ `raise_for_status` ถูกเรียก และดังนั้นจึงเป็นที่เดียวที่
`httpx.HTTPStatusError` เป็นชนิดที่มีความหมายให้จับ การเอา retry ไปใส่ใน loop
แทนจะแปลว่า `agent.py` ต้อง import `httpx` เพื่อจะรู้ว่าความล้มเหลวแบบไหนสำคัญ
และการที่ loop ยังไม่รู้เรื่องสายสัญญาณคือคุณสมบัติที่บทที่ 06 ซื้อมาและบทที่ 11 วัดไว้

`check.py` ยังเรียก `with_retries` ตรง ๆ กับ mock server แทนที่จะผ่าน provider
และนั่นไม่ใช่การทำซ้ำ การทดสอบที่ถือตัวช่วยไว้เองสามารถบังคับให้เกิด `500` สองครั้ง
นับจำนวนครั้งที่ลอง และส่ง `sleep` ปลอมที่บันทึกเวลาหน่วงแทนที่จะรอจริงเข้าไปได้
ไม่มีอะไรในนั้นเข้าถึงได้ผ่าน `stream` check
จึงพิสูจน์ว่าตัวช่วยทำงานถูกต้อง ส่วนการต่อสายเป็นสิ่งที่คุณอ่านเอา
ไม่ใช่สิ่งที่ check ยืนยันให้

ทีนี้ความซับซ้อนที่ต้องพูดตรง ๆ และมันคือเหตุผลที่ retry อยู่ใน `open_stream`
แทนที่จะห่อ `stream` ทั้งก้อน stream ที่ถูก retry จะเริ่มใหม่ตั้งแต่ต้น
ข้อความที่ถูกพิมพ์ออกไปแล้วผ่าน `on_text` จึงจะถูกพิมพ์ซ้ำ และผู้อ่านจะเห็นคำตอบครึ่งเดียวสองรอบ
มีแค่การเปิด request เท่านั้นที่ทำซ้ำได้ จึงมีแค่การเปิด request เท่านั้นที่ถูกทำซ้ำ
คอมเมนต์ใน `providers.py` บอกไว้ตรงจุดที่เรียก

```python
            # Only opening the request is retried. Once bytes have arrived the
            # caller has already seen part of an answer, and replaying would
            # splice a second answer onto the first.
```

นั่นคือการตัดสินใจออกแบบจริงที่มีต้นทุนจริง การเชื่อมต่อที่ขาดกลางคันระหว่างคำตอบยาว ๆ
จะกู้คืนไม่ได้ และไม่มีทางกู้คืนได้เลยนอกจากจะ buffer response ทั้งก้อนก่อนพิมพ์อะไรออกมา
ซึ่งเท่ากับยอมทิ้งความรู้สึกของ streaming ที่บทที่ 05 สร้างไว้
หรือให้ provider ส่งเฉพาะส่วนท้ายที่ขาดไปกลับมาใหม่ ซึ่งไม่มี provider เจ้าไหนให้คุณขอแบบนั้นได้

## 6. การหยุด agent ที่กำลังทำงานให้หยุดจริง

อีกครึ่งหนึ่งของบทนี้ และเป็นครึ่งที่มีโหมดความล้มเหลวน่าอับอายกว่า

```python
"""One object that says stop, shared by everything that can be stopped.

An interrupt that only updates the screen is the bug this exists to prevent.
Harnesses people use every day have shipped versions where pressing the
interrupt key printed a cancellation message while the tool it was supposed
to stop kept running to completion.

The same token is checked by the agent loop between turns and by the shell
tool before it starts a process, so one press stops the actual work rather
than only the display.
"""
import threading


class Cancellation:
    def __init__(self):
        self._event = threading.Event()

    def cancel(self) -> None:
        self._event.set()

    @property
    def cancelled(self) -> bool:
        return self._event.is_set()

    def raise_if_cancelled(self) -> None:
        if self.cancelled:
            raise KeyboardInterrupt("cancelled")


NEVER = Cancellation()
```

สามสิบเอ็ดบรรทัด ซึ่งส่วนใหญ่เป็น docstring

**มันคืออะไร** object เดียวที่ถือ flag หนึ่งตัว ส่งต่อไปให้ทุกอย่างที่อาจต้องหยุด

**ทำไมเราถึงทำ** เพราะ interrupt ที่แค่พิมพ์ข้อความคือคำโกหก
และมันคือคำโกหกที่ถูกส่งออกไปในเครื่องมือที่คนใช้กันทุกวัน หน้าจอบอกว่าหยุดแล้ว
subprocess ยังทำงานอยู่ ไฟล์ยังถูกเขียนอยู่ คุณเชื่อว่า agent หยุดแล้ว
คุณจึงไปแก้ไฟล์ที่มันยังแก้อยู่

### การกดต้องไปถึงทุกชั้น

เมื่อคุณกด Ctrl+C agent อาจอยู่ในหนึ่งในสามที่ และการหยุดหมายถึงการหยุดในทั้งสามที่

**request ที่กำลังเดินทาง** model กำลัง stream และข้อความกำลังปรากฏบนหน้าจอคุณ
การหยุดแปลว่า loop จะไม่เริ่มเทิร์นใหม่เมื่อเทิร์นนี้จบ

**subprocess** `run_shell` เริ่ม `pytest` ไปแล้วและมันผ่านไปสามสิบวินาทีของการรันสองนาที
การหยุดแปลว่ากระบวนการนั้นจะไม่ถูกทิ้งไว้ให้รันต่อหลังจาก harness บอกคุณว่าหยุดแล้ว

**คำถามที่ค้างอยู่** `ask_in_terminal` พิมพ์คำถามขออนุญาตออกมาแล้วและถูกบล็อกอยู่ใน `input`
รอให้คุณพิมพ์ `y` การหยุดแปลว่าคำถามนั้นหายไปและการเรียกที่มันคุ้มกันอยู่จะไม่ถูกรัน

ความล้มเหลวที่ถูกส่งออกไปคือตอนที่ชั้นหนึ่งได้ยิน interrupt แต่ชั้นอื่นไม่ได้ยิน
ชั้นแสดงผลคือชั้นที่ต่อสายง่ายที่สุดและเป็นชั้นที่คุณสังเกตเห็นก่อน
ซึ่งเป็นเหตุผลพอดีว่าทำไมมันจึงเป็นชั้นที่ถูกต่อสายไว้ชั้นเดียว

### ทำไมต้องใช้ token ร่วมกันตัวเดียวแทน flag ต่อชั้น

นี่คือคำถามเชิงออกแบบ และมันมีคำตอบที่ชัดเจน

ทางเลือกคือให้แต่ละชั้นถือ state ของตัวเอง loop มี `self.stopping` shell tool มี
`_cancelled` ระดับโมดูล คำถามขออนุญาตมีอย่างที่สาม signal handler ตั้งค่าทั้งหมดนั้น

การออกแบบนั้นใช้ได้ในวันที่คุณเขียนมัน นี่คือเหตุผลที่มันเลิกใช้ได้

**ทุกสิ่งใหม่ที่หยุดได้คือ flag ใหม่ และการลืมสักตัวเป็นเรื่องเงียบ** เพิ่ม tool ที่ยิง HTTP
request ยาว ๆ มันต้องยกเลิกได้ ถ้าคุณลืมเพิ่ม flag ให้มันและลืมตั้งค่า flag นั้นใน handler
จะไม่มีอะไรพังให้เห็น มันแค่ยกเลิกไม่ได้ และคุณจะรู้ตอนเกิดเหตุการณ์จริง

**ไม่มีคำตอบเดียวว่าเรากำลังหยุดอยู่หรือไม่** ด้วย token ตัวเดียวคุณถามได้ ด้วยสี่ flag
จะมีสิบหก state ซึ่งส่วนใหญ่ไร้สาระ และครึ่งหนึ่งของ bug ที่เป็นไปได้คือ flag สองตัวขัดแย้งกัน

**ชั้นต่าง ๆ ไม่ได้อยู่บน thread เดียวกันทั้งหมด** `Cancellation` ห่อ `threading.Event`
ซึ่งเป็น flag แบบ one shot ที่ปลอดภัยกับ thread ของไลบรารีมาตรฐาน `set` และ `is_set`
ปลอดภัยจากทุก thread ดังนั้น signal handler, main loop และ worker
จึงอ่านค่าเดียวกันได้โดยคุณไม่ต้อง lock อะไรเลย boolean ธรรมดาจะเป็น data race
ที่ทำงานได้ในทุก test และล้มเหลวครั้งเดียวตอนมีโหลด

จริง ๆ แล้ว boolean ธรรมดาจะเพียงพอสำหรับ code แบบ single thread ในปัจจุบัน `Event`
ถูกเลือกเพราะทันทีที่ tool รันบน worker thread boolean จะผิดแบบเงียบ ๆ
และนี่คือวิธีถูก ๆ ที่จะไม่ต้องคิดเรื่องนี้อีกเลย

สังเกตสิ่งที่คลาสนี้ไม่มี ไม่มีเหตุผลของการยกเลิก ไม่มีรายการ callback
ไม่มีวิธียกเลิกการยกเลิก การยกเลิกเป็นทางเดียว เมื่อคุณบอกให้หยุดแล้ว
คำตอบของคำถามว่าเรากำลังหยุดอยู่หรือไม่คือใช่ตลอดไป และ token ที่รีเซ็ตได้
จะต้องมีกฎว่าใครรีเซ็ตได้และเมื่อไร command line ได้ผลแบบเดียวกันด้วยการสร้าง
`Cancellation` ตัวใหม่สำหรับเทิร์นถัดไป ซึ่งเป็นบรรทัดเดียวและไม่มีความกำกวมอยู่ในนั้น

### loop ตรวจมันตรงไหน

สองที่ใน `agent.py` และทั้งคู่ถูกเลือกมาไม่ใช่โปรยไว้

```python
    def stop_requested():
        return cancellation is not None and cancellation.cancelled
```

```python
    for _ in range(max_turns):
        if stop_requested():
            raise KeyboardInterrupt("cancelled")
```

```python
        for call in calls:
            if stop_requested():
                raise KeyboardInterrupt("cancelled")
```

ก่อนแต่ละเทิร์น และก่อนการเรียก tool แต่ละครั้ง
นั่นคือสองจังหวะที่โปรแกรมกำลังจะเริ่มอะไรที่แพงหรืออะไรที่มีผลข้างเคียง
การตรวจระหว่างตัวอักษรที่ถูก stream ในคำตอบจะหยุดได้เร็วขึ้นเสี้ยววินาที
และจะแปลว่าต้องร้อย token เข้าไปใน loop การ parse ของ provider
ซึ่งเป็นการผูกกันมากมายเพื่อประหยัดครึ่งวินาที

`cancellation=None` คือค่าตั้งต้นและ `stop_requested` จัดการมัน
ผู้เรียกทุกรายที่เขียนก่อนบทนี้จึงยังทำงานได้และเพียงแค่ไม่เคยหยุด
เวอร์ชันแบบ package ของ code เดียวกันใช้ sentinel `NEVER` ที่ก้นไฟล์ `cancel.py`
เพื่อจุดประสงค์เดียวกัน ซึ่งทำให้มันเรียก `raise_if_cancelled` ได้โดยไม่มีเงื่อนไข
แทนที่จะต้องตรวจ `None` ก่อน

### คำถามที่ค้างอยู่ และ subprocess

`ask_in_terminal` จัดการ interrupt อยู่แล้ว และทำมาตั้งแต่บทที่ 12

```python
    try:
        answer = input("Allow? [y]es once, [a]lways for this exact call, [N]o ")
    except (EOFError, KeyboardInterrupt):
        print()
        return DENY
```

Ctrl+C ขณะที่คำถามค้างอยู่จะคืน `DENY` การเรียกที่รอการอนุมัติจึงไม่ถูกรัน
จากนั้น loop จะไปถึงจุดตรวจที่หัวของการเรียกครั้งถัดไปแล้ว raise
ชั้นคำถามกับชั้น loop มาถึงผลลัพธ์เดียวกันจากสองทิศทาง
ซึ่งคือสิ่งที่คุณต้องการเมื่อสองชั้นถูกขัดจังหวะในจังหวะที่ต่างกันเล็กน้อย

ชั้น subprocess คือชั้นที่ต้องพูดตรง ๆ และความจริงไม่ใช่อย่างที่คุณน่าจะเดา
`tools.py` ในโฟลเดอร์นี้ปรึกษา token จริง ตรงจุดที่ docstring ของ `cancel.py` บอกว่าควรอยู่

```python
CANCELLATION = None


def run_shell(command):
    ...
    if CANCELLATION is not None and CANCELLATION.cancelled:
        return "Cancelled before the command started."
```

### interrupt handler และการกดครั้งที่สอง

token ต้องถูกตั้งค่าโดยอะไรสักอย่าง สิ่งนั้นอยู่ใน command line มากกว่าใน loop
เพราะ `agent.py` ไม่ควรรู้ว่าคีย์บอร์ดมีอยู่ นี่คือมันจาก harness แบบ package ใน
`src/agentpath/cli.py` ซึ่งเป็นสิ่งที่บทที่ 18 ประกอบขึ้น

```python
def install_interrupt_handler(agent):
    """Make Ctrl+C stop the work rather than only the display.

    The first press asks the agent to stop, which it notices between turns
    and before running a tool. A second press falls through to the normal
    Python behaviour, so a genuinely wedged process can still be killed.
    """

    def handle(signum, frame):
        if agent.cancellation.cancelled:
            raise KeyboardInterrupt
        print("\nStopping after the current step. Press Ctrl+C again to force it.")
        agent.cancellation.cancel()

    try:
        signal.signal(signal.SIGINT, handle)
    except ValueError:
        pass
```

การกดครั้งแรกเป็นแบบร่วมมือ มันตั้ง flag บอกคุณว่ากำลังเกิดอะไรขึ้น
และปล่อยให้ agent หยุดที่จุดปลอดภัยจุดถัดไป ซึ่งแปลว่าไฟล์ session ถูกเขียนอย่างถูกต้อง
ยอดรวมการใช้งานถูกพิมพ์ออกมา และบทสนทนายังครบถ้วนสำหรับ `resume`

**ทำไมการกดครั้งที่สองจึงตกไปสู่พฤติกรรมปกติ** เพราะการยกเลิกแบบร่วมมือ
ขึ้นอยู่กับการที่โปรแกรมเดินไปถึงจุดตรวจ และโปรแกรมที่ติดแหง็กจริงจะไม่มีวันไปถึงจุดตรวจ
`read` บน socket ที่ firewall ทิ้งไปเงียบ ๆ บล็อกได้นานมาก subprocess
ที่รอ input ที่ไม่มีใครพิมพ์จะบล็อกตลอดไป ในทั้งสองกรณี flag ถูกตั้งแล้ว
ข้อความถูกพิมพ์ไปแล้ว และไม่มีอะไรเกิดขึ้น

ถ้า handler กลืนทุกการกด ทางเลือกที่เหลือมีเพียง terminal อีกหน้าต่างกับ `kill`
และ harness ที่ปุ่มหยุดไม่หยุดนั้นแย่กว่า harness ที่ไม่มีปุ่มหยุดเลย เพราะคุณนั่งกดมันอยู่อย่างนั้น

การกดครั้งที่สองจึง raise `KeyboardInterrupt` จากภายใน handler ซึ่งเป็นพฤติกรรม
interrupt ปกติของ Python การรันตาย traceback อาจดูน่าเกลียด ไฟล์ session
อาจขาดข้อความสุดท้าย นั่นคือการแลกที่ถูกต้อง การกดครั้งแรกเสนอการหยุดที่สะอาด
การกดครั้งที่สองรับประกันว่าจะหยุด

ข้อความก็คุ้มค่ากับที่ทางของมันเช่นกัน ถ้าไม่มีมัน การกดครั้งแรกจะดูเหมือนไม่ทำอะไร
เพราะ agent ยังกำลังทำเทิร์นให้จบ และผู้ใช้ที่คิดว่าปุ่มเสียจะกดมันอีกสี่ครั้ง

`except ValueError` ครอบคลุมกรณีที่ `signal.signal` ปฏิเสธการติดตั้ง handler
เมื่อถูกเรียกจาก thread ที่ไม่ใช่ main thread ซึ่งเกิดขึ้นเมื่อ harness ถูกฝังในอะไรที่ใหญ่กว่า
การติดตั้ง handler ที่มีก็ดีไม่ได้ ไม่ควรทำให้โปรแกรมเริ่มทำงานไม่ได้

และคุณทดสอบพฤติกรรมภายใต้ความล้มเหลวไม่ได้ถ้าไม่มีความล้มเหลว
มีสองวิธีที่จะได้มันมาและมีเพียงวิธีเดียวที่เป็น test

วิธีที่ไม่ใช่ test คือชี้ไปที่ provider จริงแล้วรอ คุณขอ `429` จาก endpoint
จริงในจังหวะที่ต้องการไม่ได้ คุณจะต้องกระหน่ำมันจนมันจำกัดอัตราคุณ ซึ่งเสียมารยาท ช้า
ขึ้นกับ API key ขึ้นกับเครือข่าย
และผลิตชุดทดสอบที่ผ่านบนเครื่องคุณแล้วล้มเหลวใน CI ด้วยเหตุผลที่ไม่มีใครทำซ้ำได้ test
ที่ล้มเหลวแบบสุ่มไม่ใช่ test มันคือแหล่งสัญญาณรบกวนที่สอนให้ทีมรัน build ใหม่

วิธีที่เป็น test คือ server ที่ล้มเหลวเมื่อคุณสั่งพอดี นั่นคือสิ่งที่ mock server
จากบทที่ 06 ได้ฟีเจอร์เพิ่มมาเพื่อการนี้

```python
    def _maybe_fail(self):
        """Return True when this request should fail, per the caller's headers.

        The caller drives this rather than the server failing on its own,
        because a test that fails at random is not a test.

        The counter lives on the server rather than in a module global so
        that each server starts fresh. A shared global would make one test
        depend on how many tests ran before it, which is the kind of bug
        that only appears when the whole suite runs.
        """
        status = self.headers.get("X-Mock-Fail")
        if not status:
            return False
        times = self.headers.get("X-Mock-Fail-Times")
        if times is not None:
            counts = getattr(self.server, "fail_counts", None)
            if counts is None:
                counts = self.server.fail_counts = {}
            key = f"{status}:{times}:{self.path}"
            counts[key] = counts.get(key, 0) + 1
            if counts[key] > int(times):
                return False
        code = int(status)
        headers = {"Retry-After": "2"} if code == 429 else {}
        self._send_json(
            {"error": {"type": "mock_failure", "code": code}},
            status=code,
            extra_headers=headers,
        )
        return True
```

สอง header และเมื่อรวมกันมันแสดงทุกสถานการณ์ที่บทนี้ต้องการได้

**`X-Mock-Fail`** ระบุ status code ที่จะคืน ส่ง `X-Mock-Fail: 500` แล้ว request
นี้จะกลับมาเป็น `500` ไม่มี header แปลว่า response ปกติ check
ทุกอันที่เขียนก่อนบทนี้จึงไม่ได้รับผลกระทบ

**`X-Mock-Fail-Times`** บอกว่ากี่ครั้ง มันคือสิ่งที่เปลี่ยนความล้มเหลวถาวรให้เป็นความล้มเหลวชั่วคราว
ซึ่งคือกรณีที่น่าสนใจ เพราะความล้มเหลวถาวรพิสูจน์แค่ว่าคุณยอมแพ้
และความล้มเหลวชั่วคราวพิสูจน์ว่าคุณฟื้นได้ ด้วย `X-Mock-Fail-Times: 2`
ตัวนับจะเพิ่มขึ้นทุก request สอง request แรกล้มเหลว และตั้งแต่ครั้งที่สาม การตรวจ
`counts[key] > int(times)` จะส่ง request ต่อไปยัง handler จริง

**header `Retry-After` บน `429`** หนึ่งบรรทัด และมันคือเหตุผลทั้งหมดที่หัวข้อ 3 ทดสอบได้

```python
        headers = {"Retry-After": "2"} if code == 429 else {}
```

mock ทำตัวแบบเดียวกับ provider จริง ซึ่งคือแนบ header
ไปกับ status ที่แปลว่าช้าลงหน่อยและไม่แนบกับ status อื่น check จึงเรียกร้อง `429` ได้
รู้แน่นอนว่า `Retry-After: 2` จะกลับมา และยืนยันได้ว่า client รอสองวินาทีเป๊ะ
แทนที่จะรอหนึ่งถึงสองวินาทีตามที่สูตรของมันเองจะให้ ถ้า mock ไม่ส่ง header นั้น
ก็จะไม่มีทางแยกความต่างระหว่างการเชื่อฟัง server กับการทอย jitter ได้เลขที่โชคดี

```python

            if counts is None:

```

วิธีทำที่เห็นชัดคือ dictionary ระดับโมดูล มันใช้ได้เมื่อคุณรัน check เดียว แล้ว CI ก็รัน
check ของบทเรียนสิบเก้าบทติดกันในกระบวนการเดียว
และตัวนับถูกเพิ่มไปแล้วโดยบทก่อนหน้า งบความล้มเหลวจึงถูกใช้หมด
และความล้มเหลวสองครั้งของคุณกลายเป็นครั้งเดียว check ล้มเหลว และมันล้มเหลวเฉพาะใน CI
เฉพาะตอนรันชุดทดสอบทั้งชุด และเฉพาะในลำดับที่การไล่รายชื่อไดเรกทอรีบังเอิญให้มา

รวม status จำนวนครั้ง และ path เข้าไปด้วย
สองสถานการณ์ในการตรวจเดียวกันจึงรั่วใส่กันไม่ได้เช่นกัน

### check หน้าตาเป็นอย่างไรจากฝั่ง client

```python
def post(headers=None):
    base_url = os.environ["AGENTPATH_BASE_URL"].rstrip("/")
    response = httpx.post(
        f"{base_url}/chat/completions",
        json={"model": os.environ["AGENTPATH_MODEL"], "messages": [{"role": "user", "content": "hi"}]},
        headers=headers or {},
        timeout=60,
    )
    response.raise_for_status()
    return response.json()
```

ตัวช่วยหนึ่งตัว และความล้มเหลวถูกร้องขอเป็นรายครั้งด้วยการส่ง header เข้าไป
มีสามสถานการณ์ตามมาจากมัน

```python
    def flaky():
        attempts.append(1)
        return post({"X-Mock-Fail": "500", "X-Mock-Fail-Times": "2"})

    body = with_retries(flaky, sleep=lambda seconds: None)
```

ล้มสองครั้ง แล้วสำเร็จ ข้อยืนยันคือ `attempts` มีสมาชิกสามตัวเป๊ะ
ซึ่งคือล้มสองครั้งกับสำเร็จหนึ่งครั้ง สองตัวจะแปลว่ามันยอมแพ้เร็วเกินไป
สี่ตัวจะแปลว่ามัน retry หลังจากสำเร็จไปแล้ว

```python
    def broken():
        bad_attempts.append(1)
        return post({"X-Mock-Fail": "400"})
```

ล้มถาวรด้วย client error ข้อยืนยันคือ `bad_attempts` มีสมาชิกหนึ่งตัวเป๊ะ และ
`httpx.HTTPStatusError` หลุดออกมา นี่คือกฎของหัวข้อ 2 ที่แสดงออกมาเป็นจำนวนนับ
และมันจะล้มเหลวเสียงดังถ้ามีคนเพิ่ม `400` เข้าไปใน `RETRYABLE_STATUS` เพื่อความสงบสุข

```python
    waited = []
    try:
        with_retries(lambda: post({"X-Mock-Fail": "429"}), attempts=2, sleep=waited.append)
    except httpx.HTTPStatusError:
        pass
    if waited != [2.0]:
        fail(f"the Retry-After header of 2 seconds was not obeyed. Waited {waited}")
```

อันนี้ควรค่าแก่การชื่นชม `sleep=waited.append` คือกลเม็ดทั้งหมด parameter `sleep`
มีอยู่เพื่อให้ผู้เรียกใส่อย่างอื่นแทน `time.sleep` ได้
และตรงนี้ตัวแทนบันทึกตัวเลขไว้แทนที่จะรอมันจริง check
จึงรันเสร็จทันทีและยังยืนยันหน่วงเวลาที่แน่นอนซึ่งการรันจริงจะรอ

`attempts=2` แปลว่ามีช่องว่างระหว่างความพยายามเพียงหนึ่งช่อง `waited`
จึงต้องเป็นลิสต์ที่มีตัวเลขตัวเดียว และตัวเลขนั้นต้องเป็น `2.0` เป๊ะ สูตร jitter
สำหรับความพยายามครั้งที่หนึ่งให้ค่าใน `[0.5, 1.0)` client ที่เพิกเฉยต่อ header
จึงผลิต `2.0` โดยบังเอิญไม่ได้ ความเท่ากันคือหลักฐานว่า header ชนะ

ไม่ใช่สูตรของเรา

บรรทัดที่สี่คือหัวข้อ 4 การเรียก `delay_for(3)` ยี่สิบครั้งผลิต float ที่ต่างกันยี่สิบค่า
ตัวคูณจึงทำหน้าที่ของมัน ถ้าคุณเห็นตัวเลขน้อยกว่ายี่สิบตรงนี้ก็ไม่เป็นไร
เพราะ float ที่เท่ากันเป็นไปได้ในหลักการ แต่ค่า `1` แปลว่า jitter หายไปแล้ว

บรรทัดที่ห้าคือหัวข้อ 6 และมันคือเวอร์ชันที่เล็กที่สุดเท่าที่จะเป็นไปได้ของข้ออ้างนั้น
ยกเลิก token เรียก `raise_if_cancelled` แล้ว `KeyboardInterrupt` ต้องออกมา
check ยืนยันบน exception แทนที่จะยืนยันบนข้อความที่พิมพ์ออกมา
ซึ่งเป็นวินัยเดียวกับที่บทที่ 11 ให้เหตุผลไว้ยืดยาว interrupt ที่พิมพ์ข้อความคือ bug
มีแต่ exception ที่ถูก raise เท่านั้นที่พิสูจน์อะไรได้

บรรทัดที่หกคือหัวข้อ 7 provider ปลอมคืนการเรียก `read_file` เดิมซ้ำไปเรื่อย ๆ
และการรันต้องจบเพราะตัวตรวจจับการทำซ้ำสังเกตเห็น ไม่ใช่เพราะ `max_turns` หมด
`max_turns` เป็นยี่สิบตรงนี้อย่างจงใจ model ที่ติดวนแล้วถูกหยุดด้วยขีดจำกัดจำนวนรอบ
ไม่ได้พิสูจน์อะไรเกี่ยวกับตัวตรวจจับเลย check จึงให้ขีดจำกัดมีที่ว่างพอ
จนการไปถึงมันคือความล้มเหลว

สังเกตสิ่งที่ห้าข้อแรกไม่ได้ทำ มันไม่เคยเริ่มการรัน agent จริง ไม่เคยเรียก tool
และไม่เคยรอจริงแม้แต่วินาทีเดียว ทุกสถานการณ์เหล่านั้นถูกขับผ่าน `with_retries` และ
`Cancellation` โดยตรง ซึ่งเป็นเหตุผลที่ check เสร็จทันทีและให้คำตอบเดิมทุกครั้ง
มีแต่ข้อที่หกที่ต้องใช้ loop และมันได้ provider ปลอมแทนที่จะได้เครือข่ายจริง

ถ้าบรรทัดแรกล้มเหลว ให้ดูว่า mock server ถูกติดต่อถึงหรือเปล่า
เพราะ error ของการเชื่อมต่อจะถูกนับเป็นความล้มเหลวของ transport และถูก retry
สี่ครั้งก่อนจะโผล่ขึ้นมา ถ้าบรรทัดที่สามล้มเหลวและเวลารอที่ถูกบันทึกเป็นตัวเลขระหว่างหนึ่งกับสอง
แปลว่า `delay_for` คำนวณสูตรก่อนตรวจ header ซึ่งแปลว่าสองบล็อกถูกสลับที่กัน
ถ้าบรรทัดที่สี่ล้มเหลว แปลว่าตัวคูณ jitter ถูกลบไปแล้ว

กับการยกเลิกจากบทนี้มาบรรจบกันใน object เดียวกัน

**บทที่ 18 คือ harness** ไฟล์ใหม่หนึ่งไฟล์ชื่อ `main.py`
ที่ซึ่งทุกชิ้นส่วนเหล่านั้นมาบรรจบกันเสียที command line ที่สร้างด้วย `argparse`
รับงานเป็น positional argument และมี `--workspace`, `--session`, `--resume`,
`--budget` กับ `--yes` เป็น flag ชื่อ session ที่เลือกได้สามทาง และ `--resume`
ที่ชนะด้วยการส่งชื่อเดิมเข้าไปแทนที่จะคัดลอกไฟล์ signal handler ที่ตั้งค่า cancellation
token และบรรทัดข้าง ๆ มันที่ส่ง token ตัวเดียวกันให้ `tools.py`
ซึ่งเป็นสิ่งที่ทำให้การตรวจของ shell tool เลิกเป็นโค้ดที่ตาย
จากนั้นคือ check หมุดหมายที่รันโปรแกรมที่ประกอบเสร็จแล้วตั้งแต่ต้นจนจบ

พูดให้ชัดว่าบทที่ 18 ไม่ได้ทำอะไร เพราะมีสองอย่างที่ยังคงเดิม `run`
ยังเป็นฟังก์ชันที่พิมพ์ออกหน้าจอเหมือนที่มันเป็นมาตั้งแต่บทที่ 04
การวาดบน terminal จึงยังอยู่ใน loop และชิ้นส่วนต่าง ๆ ยังถูกส่งให้มันเป็น keyword
argument แทนที่จะถูกถือโดย object ตัวหนึ่ง package ที่ติดตั้งได้ใต้ `src/agentpath/`
ไปไกลกว่านั้นจริง ด้วยคลาส `Agent` loop ที่ yield event ที่มีชนิด และ command line
ที่มี `chat`, `run` กับ `resume` เป็น subcommand และบทที่ 18 ก็ชี้ไปที่มันทุกครั้งที่สองอย่างนี้ต่างกัน
โฟลเดอร์บทเรียนยังเป็นสคริปต์แบน ๆ อย่างจงใจ
เพราะประเด็นของบทนี้คือคุณอ่านการประกอบทั้งหมดได้ในไฟล์เดียว

ไม่มีอะไรในบทที่ 18 ที่เป็นแนวคิดใหม่ มันคือหมุดหมายที่สอง และเหมือนหมุดหมายแรก
หน้าที่ของมันคือแสดงว่าชิ้นส่วนต่าง ๆ เข้ากันได้ ย้อนกลับไปดูรอยต่อ
และพูดตรง ๆ ว่ายังขาดอะไรอยู่
