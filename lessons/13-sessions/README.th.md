## 1. ปัญหาที่ค้างมาจากบทที่ 12

บทที่ 12 จบในจุดที่ดี agent ไม่ถามคุณเรื่องคำสั่งไร้พิษภัยเดิมสี่สิบครั้งอีกแล้ว ตอบ `a` ครั้งเดียว
แล้ว `run_shell` ด้วย argument ชุดนั้นเป๊ะ ๆ ก็หยุดถาม ประตูยังอยู่และความเหนื่อยล้าหายไป

ทีนี้ปิดโปรแกรม

```python
class Permissions:
    def __init__(self, ask=None, auto_approve=False):
        self.ask = ask
        self.auto_approve = auto_approve
        self.remembered = set()
```

`self.remembered` คือ set ของ Python บนออบเจกต์ที่ถูกถือไว้โดยตัวแปรท้องถิ่นใน `run` เมื่อ `run`
คืนค่า ไม่มีอะไรอ้างถึง instance ของ `Permissions` อีกแล้ว และ set นั้นก็เป็นขยะ
การตัดสินใจทุกอย่างที่คุณทำหายไป เริ่ม agent ใหม่แล้วมันถามเรื่อง `python -m pytest -q`
ราวกับคุณไม่เคยเห็นมันมาก่อน

ประโยคเดียวกันนี้จริงกับสิ่งที่มีค่ามากกว่ามากใน function นั้นด้วย

```python
    messages = list(history or [])
```

`messages` คือบทสนทนา ทุกอย่างที่ agent เรียนรู้เกี่ยวกับโปรเจกต์ของคุณอยู่ในนั้น ว่ามีไฟล์อะไรบ้าง
ไฟล์ไหนมีบั๊ก ผลของเทสต์บอกอะไร มันลองวิธีไหนแล้วละทิ้งไป ทั้งหมดคือลิสต์บน stack และเมื่อ `run`
คืนค่า ลิสต์นั้นถูกเก็บกวาดไปพร้อมกับความรู้

นั่นสร้างปัญหาที่ต่างกันสามข้อ และควรแยกมันออกจากกัน เพราะมันมีต้นทุนต่างกัน

คุณจ่ายค่าการค้นพบเดิมสองครั้ง ขอให้ agent แก้บั๊กตัวที่สองในโปรเจกต์เดิม แล้วมัน grep
หาสิ่งเดิม อ่านไฟล์เดิม และส่งทั้งหมดนั้นไปหา model อีกครั้ง บทที่ 11 แสดงเลขคณิตไว้แล้ว
การอ่านไฟล์สิบเทิร์นคือห้าหมื่นห้าพัน token ที่ถูกเรียกเก็บเงิน สำหรับเนื้อหาที่ไม่ซ้ำกันหนึ่งหมื่น token
และการเริ่มจากศูนย์แปลว่าจ่ายเงินนั้นเป็นครั้งที่สองสำหรับโปรเจกต์ที่ agent อ่านไปแล้ว

คุณออกไปแล้วกลับมาไม่ได้ งานจริงถูกขัดจังหวะ คุณเริ่ม agent กับอะไรที่ใช้เวลายี่สิบนาที
แล้วแล็ปท็อปหลับ มีประชุมโผล่มา หรือคุณกด Ctrl+C เพราะอยากเปลี่ยนงานนิดหน่อย
ทุกอย่างที่ว่ามาตอนนี้ถึงตายทั้งหมด ไม่มีกลไกไหนในโปรแกรมสำหรับทำสิ่งที่เริ่มไปแล้วต่อ

คุณหาไม่ได้ว่าเกิดอะไรขึ้น ข้อนี้เจ็บที่สุดและเป็นข้อที่คนสังเกตเห็นช้าที่สุด เมื่อ agent
แก้ไฟล์ผิด หรืออ้างว่าเทสต์ผ่านทั้งที่ไม่ผ่าน หรืออ่านไฟล์แล้วทำตัวราวกับได้อ่านอย่างอื่น
คำถามเดียวที่มีประโยชน์คืออะไรอยู่ใน context ของมันจริง ๆ ในตอนที่มันตัดสินใจ
ตอนนี้คำตอบของคำถามนั้นถูกโยนทิ้งไปไมโครวินาทีหลังการตัดสินใจ
และร่องรอยเดียวที่เหลือคืออะไรก็ตามที่เลื่อนผ่าน terminal ของคุณ ซึ่งคุณก็เสียมันไปกับ scrollback buffer แล้ว

หัวข้อ 6 ว่าด้วยปัญหาข้อที่สาม สองข้อแรกคือสิ่งที่โค้ดในบทนี้มีไว้เพื่ออย่างเห็นได้ชัด
ข้อที่สามคือเหตุผลที่บทนี้สำคัญ

## 2. session คืออะไร

session คือบทสนทนาบนดิสก์

นั่นคือแนวคิดทั้งหมดและมันน่าเบื่อโดยตั้งใจ แต่มีข้อคิดจริงฝังอยู่ในความน่าเบื่อของมัน อย่าอ่านผ่าน

ย้อนกลับไปบทที่ 02 สิ่งที่ทำให้ loop ของบทสนทนาทำงานได้คือการค้นพบว่า model ไม่จำอะไรเลย
และสิ่งที่เราเรียกว่าบทสนทนาคือลิสต์ของ Python ที่คุณส่งใหม่ทั้งหมดในทุก request ตั้งแต่บทที่ 02
ทุกบทเก็บลิสต์นั้นไว้ในรูปทรงเดิม ลิสต์ของ dictionary แต่ละอันมี `role` และ `content` บวกกับ
`tool_calls` บนข้อความของ assistant ที่ขออะไรบางอย่าง และ `tool_call_id` บนผลลัพธ์ที่กลับมา

```python
[
    {"role": "system", "content": "You are a coding agent..."},
    {"role": "user", "content": "the average is wrong"},
    {"role": "assistant", "content": "", "tool_calls": [...]},
    {"role": "tool", "tool_call_id": "call_1", "content": "stats.py:8: ..."},
]
```

dictionary ทุกอันในนั้นเป็น JSON อยู่แล้ว มันต้องเป็น เพราะมันกำลังจะถูก serialise แล้ว post
ไปที่ HTTP endpoint ไม่มีออบเจกต์ Python ในนั้น ไม่มีคลาส ไม่มี function
ไม่มีการอ้างถึงอะไรที่มีอยู่แค่ในหน่วยความจำ มันเป็น string dictionary และ list ตลอดทั้งชั้น

ดังนั้นการบันทึกบทสนทนาจึงไม่ใช่แนวคิดใหม่ มันไม่ใช่ปัญหาเรื่อง serialisation
ไม่ใช่ปัญหาการออกแบบ schema (บอกรูปร่างของข้อมูลด้วย JSON) และไม่ใช่ปัญหาฐานข้อมูลอย่างเด็ดขาด
มันคือข้อมูลชุดเดิมที่คุณมีอยู่แล้ว เขียนลงที่อีกที่หนึ่ง การตัดสินใจที่เหลือคือที่ไหนและจัดวางแบบใด
ซึ่งคือหัวข้อ 3

เรื่องนี้ควรพูดตรง ๆ เพราะสัญชาตญาณตอนที่คุณอยากได้ความคงทนครั้งแรกคือคว้าอะไรสักอย่างมาใช้
ORM document store schema migration ทั้งหมดนั้นคือเครื่องจักรสำหรับเปลี่ยนออบเจกต์ที่อยู่ในหน่วยความจำ
ให้เป็นแถวที่อยู่บนดิสก์ และคุณไม่มีออบเจกต์ คุณมี JSON ระยะทางระหว่างสิ่งที่คุณมีกับสิ่งที่คุณต้องการ
คือการเรียก `json.dumps` หนึ่งครั้ง

ข้อความหนึ่งคือ dictionary ธรรมดา ไม่ใช่คลาส คุณห่อแต่ละข้อความในคลาส `Message` ที่มีฟิลด์และการตรวจสอบก็ได้
แล้วคุณก็จะต้องมีวิธีเปลี่ยน `Message` เป็น JSON ให้ provider และเปลี่ยนกลับมาจากดิสก์
นั่นคือการแปลงสองครั้งกับนิยามคลาสหนึ่งอันที่ซื้อมาแลกกับความว่างเปล่า
เพราะรูปแบบบนสายคือรูปแบบการเก็บอยู่แล้ว กฎที่คอร์สนี้กลับมาพูดถึงเรื่อย ๆ คือ
ยิ่งคุณมีตัวแทนของสิ่งเดียวกันน้อยเท่าไร ก็ยิ่งมีที่ให้มันขัดแย้งกันน้อยเท่านั้น

## 3. ทำไม JSONL แทนที่จะเป็นไฟล์ JSON ก้อนใหญ่ก้อนเดียว

JSONL แปลว่าหนึ่ง JSON object ต่อหนึ่งบรรทัด ไม่มี array ห่อ ไม่มีจุลภาคระหว่างรายการ
ไม่มีวงเล็บเปิดหรือปิด ไฟล์นั้นไม่ใช่เอกสาร JSON มันคือไฟล์ข้อความที่ทุกบรรทัดบังเอิญเป็นเอกสาร JSON

```text
{"role": "user", "content": "the average is wrong"}
{"role": "assistant", "content": "I will look."}
{"role": "tool", "tool_call_id": "call_1", "content": "stats.py:8: ..."}
```

ทางเลือกที่ชัดเจนคือถือบทสนทนาทั้งหมดไว้ในหน่วยความจำแล้วเทออกมาเป็น JSON array ก้อนเดียวตอนรันจบ

```python
# The alternative we are not choosing.
path.write_text(json.dumps(messages, indent=2))
```

มีเหตุผลอิสระสองข้อที่ไม่ทำแบบนั้น และทั้งสองข้อสำคัญพอที่จะพูดให้ครบแทนที่จะแค่กล่าวอ้าง

### เหตุผลที่หนึ่ง การล่มทำให้เสียแค่สิ่งที่กำลังบินอยู่

การ append คือการ `write` หนึ่งครั้งของหนึ่งบรรทัดที่ท้ายไฟล์ มันไม่แตะไบต์ใดที่อยู่ที่นั่นแล้วเลย
ถ้า process ตายระหว่างการเขียนนั้น คุณเสียอย่างมากที่สุดคือข้อความที่กำลังถูกเขียน
และทุกข้อความก่อนหน้ายังอยู่ที่เดิมเป๊ะ

เอกสาร JSON เดียวทำแบบนั้นไม่ได้ JSON array มีวงเล็บปิด ไบต์สุดท้ายของไฟล์จึงขึ้นกับจำนวนสมาชิก
การเพิ่มสมาชิกจึงเปลี่ยนท้ายไฟล์ และคุณจึงต้องเขียนเอกสารใหม่ทั้งอัน
และการเขียนใหม่มีช่วงเวลาหนึ่งที่ไฟล์บนดิสก์ไม่ใช่เอกสารเก่าและไม่ใช่เอกสารใหม่
ตายในช่วงนั้นแล้วคุณจะได้ไฟล์ที่ parse ไม่ได้เลย ไม่ใช่ไฟล์ที่ขาดข้อความสุดท้าย แต่เป็นไฟล์ที่
`json.load` โยน exception และคุณเสียบทสนทนาทั้งอัน รวมถึงสิบเก้านาทีที่ทำงานสำเร็จไปแล้ว

นั่นคือความแตกต่างที่ตัดสินเรื่องนี้ การออกแบบหนึ่งเสื่อมลงด้วยการเสียสิ่งล่าสุด
อีกอันเสื่อมลงด้วยการเสียทุกอย่าง

และช่วงเวลานั้นไม่ใช่เรื่องสมมติ สิ่งที่ทำให้ process ของ agent จบกลางคันเป็นเรื่องธรรมดา
คุณกด Ctrl+C เพราะมันกำลังมุ่งไปผิดทาง provider คืน `500` และอย่างที่บทที่ 11 ยอมรับ ไม่มี `try`
รอบ `provider.stream` exception จึงพุ่งออกจาก `main` ตรง ๆ แล็ปท็อปคุณแบตหมด
เทสต์ที่ agent รันลาก terminal ล่มไปด้วย การรัน agent คือ process ที่อยู่ยาวและทำสิ่งเสี่ยง
ซึ่งทำให้มันเป็นโปรแกรมประเภทที่ถูกฆ่าในจังหวะที่ไม่สะดวกพอดี

คุณทำให้การเขียนใหม่ปลอดภัยได้ เขียนลงไฟล์ชั่วคราวแล้ว rename ทับของเดิม เพราะ rename เป็น atomic
บนระบบไฟล์ที่สำคัญ นั่นคือเทคนิคจริงและโปรแกรมจริงใช้มัน มันมีต้นทุนเป็นการเขียนบทสนทนาทั้งอันใหม่
หลังทุกข้อความ ซึ่งใน session ยาว ๆ แปลว่าเขียนหนึ่งร้อยกิโลไบต์ใหม่เพื่อเพิ่มสองร้อยไบต์ ในทุกเทิร์น
การ append หนึ่งบรรทัดมีต้นทุนเท่าความยาวของบรรทัดนั้น atomic rename ไม่ได้ซื้ออะไรให้คุณตรงนี้
ที่การ append ไม่มีอยู่แล้ว

### เหตุผลที่สอง เครื่องมือธรรมดาอ่านมันได้

นี่คือเหตุผลที่กลับกลายเป็นสำคัญกว่าในการใช้งานประจำวัน และเป็นข้อที่ประเมินค่าต่ำเกินไปได้ง่าย
ตอนคุณกำลังเลือกรูปแบบไฟล์

ไฟล์แบบบรรทัดต่อบรรทัดเข้ากันได้กับเครื่องมือข้อความทุกตัวที่มีอยู่ตั้งแต่ยุค 1970
ไม่มีอะไรต้องเข้าใจรูปแบบของคุณ ไม่มีอะไรต้องโหลดไฟล์เข้าหน่วยความจำ ไม่มีอะไรต้องเขียนขึ้นมาเลย

นับจำนวนข้อความ

```bash
wc -l ~/.agentpath/sessions/fix-average.jsonl
```

นับว่ามี tool result กลับมากี่อัน

```bash
grep -c '"role": "tool"' ~/.agentpath/sessions/fix-average.jsonl
```


ดู session ขณะที่ agent ทำงาน ใน terminal ที่สอง แบบสด

```bash
tail -f ~/.agentpath/sessions/fix-average.jsonl
```

ดึงหนึ่งบรรทัดออกมาแล้วอ่านให้ดี


ทุกอย่างที่ว่ามาเป็น output จริงจากไฟล์ session ที่บทนี้ผลิตออกมา และไม่มีอันไหนต้องเขียนโค้ดสักบรรทัด
โดยเฉพาะ `tail -f` คืออันที่คุณจะได้ใช้โดยไม่ได้วางแผนไว้
มันทำงานได้เพราะบรรทัดใหม่ที่มาถึงท้ายไฟล์คือเหตุการณ์ทั้งหมด

## 4. ทำไมใช้ callback แทนที่จะให้ loop รู้จักไฟล์

นี่คือการเปลี่ยนแปลงทั้งหมดใน `agent.py`

```python
def run(
    provider,
    user_input,
    system=None,
    permissions=None,
    on_message=None,
    history=None,
    max_turns=10,
):
    permissions = permissions or Permissions(auto_approve=True)
    messages = list(history or [])

    def remember(message):
        """Add to the conversation and tell whoever is listening.

        The callback is how a session gets written without the loop knowing
        that files exist. It is the same trick as permissions, which the
        loop also does not implement, only consult.
        """
        messages.append(message)
        if on_message:
            on_message(message)
```

จากนั้น `messages.append(...)` ทุกอันในตัว function กลายเป็น `remember(...)` มีทั้งหมดห้าอัน
ข้อความ system ข้อความ user ข้อความ assistant ที่พก tool call มา ผลของ tool
และคำตอบสุดท้ายของ assistant ตอนออกจาก loop อันสุดท้ายนั้นพลาดง่ายที่สุด
เพราะมันนั่งอยู่ใน branch `if not calls` เหนือ `return` ขึ้นไปสองบรรทัด
และการพลาดมันทำให้คุณเสียคำตอบท้ายสุดของทุก session ที่คุณเคยบันทึกไว้
นั่นคือการแก้ไขทั้งหมด

สังเกตสิ่งที่ไม่อยู่ใน `agent.py` ไม่มี `import session` ไม่มี `open` ไม่มี path ไม่มีชื่อไฟล์
ไม่มีไดเรกทอรี ไม่มี `AGENTPATH_HOME` loop เขียนไฟล์ไม่ได้และไม่รู้ว่าไฟล์มีอยู่

นั่นสำคัญมากกว่าเรื่องความเรียบร้อย loop รายงานว่าเกิดอะไรขึ้น
และอย่างอื่นตัดสินใจว่าจะทำอะไรกับรายงานนั้น คุณเคยเห็นรูปทรงนี้เป๊ะ ๆ มาแล้วสองครั้ง

| ประเด็น | สิ่งที่ loop ทำ | สิ่งที่ตัดสินใจ |
| --- | --- | --- |
| Streaming บทที่ 05 | เรียก `on_text(piece)` | ผู้เรียก ซึ่งพิมพ์ออกมา |
| Permission บทที่ 12 | เรียก `permissions.check(...)` | ออบเจกต์ `Permissions` |
| Persistence บทที่ 13 | เรียก `on_message(message)` | อะไรก็ตามที่ผู้เรียกส่งเข้ามา |

สามบท สามประเด็นที่ loop ปฏิเสธที่จะเป็นเจ้าของ หนึ่งรูปทรง และเหตุผลก็เหมือนกันทุกครั้ง
วินาทีที่ loop รู้ว่าข้อความควรถูกเก็บอย่างไร ก็จะมีวิธีเก็บมันเพียงวิธีเดียว
และทุกอย่างที่อยากได้วิธีอื่นต้องไปแก้ loop

นับผู้เรียกที่อยากได้วิธีอื่นดู เพราะมีมากกว่าที่คุณคิด

session บน terminal ส่ง `on_message=session.append` แล้วได้ไฟล์ที่มันทำงานต่อได้

`check.py` ก็ส่งมันเหมือนกัน แล้วเทียบสิ่งที่ลงบนดิสก์กับสิ่งที่ `run` คืนมา
นั่นไม่เหมือนการเขียนไฟล์ มันคือข้อยืนยันเกี่ยวกับไฟล์ และ loop ไม่ควรต้องรู้ความต่าง

unit test ส่ง `on_message=recorded.append` ด้วยลิสต์ธรรมดา
และตอนนี้บทสนทนาตรวจสอบได้โดยไม่แตะระบบไฟล์เลย ไม่มีไดเรกทอรีชั่วคราว ไม่มีการทำความสะอาด
ไม่มีเทสต์ที่ล้มเหลวบนเครื่องที่ home directory เขียนไม่ได้

การรัน eval ที่ให้คะแนนงานร้อยงานส่งอะไรบางอย่างที่เขียนหนึ่งแถวต่อหนึ่งงานลงตารางผลลัพธ์
และไม่ต้องการไฟล์ session ร้อยไฟล์

user interface ส่งอะไรบางอย่างที่ผลักแต่ละข้อความเข้าคิวที่ thread สำหรับ render อ่านอยู่
ทำให้ transcript อัปเดตขณะที่ agent ทำงาน

ห้าผู้เรียก ห้าปลายทางที่ต่างกันโดยสิ้นเชิง และ loop เหมือนกันหมดสำหรับทุกอัน เพราะมันไม่มีปลายทาง
มันมีรายงาน

ลองดูทางเลือกอีกทางแล้วดูว่ามันเสื่อมอย่างไร สมมติ loop รับ `session_path` แล้วเขียนลงไป วันแรกมันโอเคและสั้นกว่า
แล้วเทสต์อยากรันโดยไม่แตะดิสก์ `session_path=None` จึงมีความหมายขึ้นมา แล้ว eval อยากได้รูปแบบอื่น
argument ชื่อ `session_format` จึงโผล่มา แล้ว user interface อยากได้ callback (function ที่คุณส่งไปให้โค้ดอื่นเรียกกลับ) แบบสดอยู่ดี
และคุณก็จบลงด้วยการเพิ่ม `on_message` เข้าไปอยู่ดี แต่ตอนนี้ loop มีทั้งสองอย่างและมันขัดแย้งกันได้
คุณมาถึง callback ในตอนท้ายและจ่ายค่าอ้อมทาง

นี่คือข้อโต้แย้งเดียวกับที่บทที่ 11 ทำไว้เรื่อง `tools.run` เป็นรอยต่อที่ถูกต้อง เมื่อฝั่งหนึ่งเปลี่ยน
อีกฝั่งต้องเปลี่ยนตามเท่าไร คำตอบตรงนี้คือไม่ต้องเลย สำหรับห้าฝั่งที่ต่างกัน

มีต้นทุนหนึ่งข้อที่ต้องพูดตามตรง `on_message` ถูกเรียกแบบ synchronous ข้างใน loop
ก่อนสิ่งถัดไปจะเกิด ถ้า callback ของคุณช้า agent ก็ช้า ถ้ามันโยน exception การรันก็ตาย

ไปหา model เรื่องนี้จึงไม่กัดตรงนี้ มันจะกัดถ้าคุณส่ง callback ที่ post ไปเว็บเซอร์วิสในทุกข้อความ

### การสร้างหนึ่งอัน

```python
class Session:
    def __init__(self, name, directory=None):
        self.name = name
        self.path = Path(directory or default_directory()) / f"{name}.jsonl"
        self.path.parent.mkdir(parents=True, exist_ok=True)
```

session คือชื่อกับ path ชื่อกลายเป็นชื่อไฟล์ ซึ่งคือสิ่งที่ทำให้ `Session("fix-average")`
สองครั้งในสอง process ต่างกันอ้างถึงบทสนทนาเดียวกัน นั่นคือกลไกการทำงานต่อทั้งหมด
และไม่มี registry ไม่มี index และไม่มีตัวระบุให้ต้องจำ

`mkdir(parents=True, exist_ok=True)` สร้างไดเรกทอรีใน constructor แทนที่จะสร้างตอนเขียนครั้งแรก
`parents=True` สร้าง `~/.agentpath` พร้อมกับ `~/.agentpath/sessions` และ `exist_ok=True`
แปลว่า `Session` อันที่สองของวันไม่โยน exception การทำตรงนี้แปลว่าถ้าสร้างไดเรกทอรีไม่ได้
คุณรู้ตั้งแต่ตอนสร้าง session แทนที่จะรู้ตอนรันไปสี่นาทีแล้ว

constructor ไม่เปิดไฟล์และไม่สร้างไฟล์ `Session` ที่คุณไม่เคยเขียนลงไปจะไม่ทิ้งอะไรไว้

### การเขียนหนึ่งข้อความ

```python
    def append(self, message):
        """Write one message immediately.

        ensure_ascii is off because the file is for a person to read, and a
        Thai sentence turned into escape codes is not readable.
        """
        with self.path.open("a", encoding="utf-8") as handle:
            handle.write(json.dumps(message, ensure_ascii=False) + "\n")
```

ห้าเรื่องในสามบรรทัด

`"a"` คือโหมด append การเขียนไปที่ท้ายไฟล์และไม่มีอะไรที่อยู่ที่นั่นแล้วถูกแตะ
ทุกอย่างในหัวข้อ 3 ขึ้นอยู่กับตัวอักษรตัวเดียวนี้

ไฟล์ถูกเปิดและปิดในทุกข้อความ การ optimise ที่ชัดเจนคือเปิด file handle ค้างไว้ตลอดอายุของ session
อย่าทำ และเหตุผลคือ buffering (พักข้อมูลไว้ในหน่วยความจำก่อนเขียนจริง) handle ที่เปิดค้างถือข้อมูลไว้ใน buffer ที่จะถูก flush
เมื่อ Python สะดวก ซึ่งแปลว่า `tail -f` ไม่แสดงอะไรให้คุณสักพักแล้วโผล่มาแปดบรรทัดพร้อมกัน
และ process ที่ถูกฆ่าตอน buffer เต็มจะเสียข้อความที่คุณเชื่อว่าถูกเขียนไปแล้ว การปิดคือการ flush
ต้นทุนคือหนึ่งการเปิดและหนึ่งการปิดต่อหนึ่งข้อความ ซึ่งในบทสนทนาสี่สิบข้อความคือสี่สิบ system call
เทียบกับสี่สิบ HTTP request ไปหา model ภาษา มันไม่ปรากฏบนตาชั่งเลย

`encoding="utf-8"` เขียนไว้ชัดเจน Python บน Linux และ macOS ใช้ UTF-8 เป็นค่าเริ่มต้นอยู่แล้ว
Python บน Windows ในอดีตใช้ code page ของระบบเป็นค่าเริ่มต้น ซึ่งสำหรับ Windows ภาษาไทยคือ cp874
และสำหรับภาษาญี่ปุ่นคือ cp932 และทั้งคู่แทนสิ่งที่บทสนทนาอาจมีส่วนใหญ่ไม่ได้ ถ้าไม่มี argument นี้
โค้ดชุดเดียวกันเขียนไฟล์ต่างกันบนเครื่องต่างกัน และความล้มเหลวคือ `UnicodeEncodeError`
กลางการรันบนแล็ปท็อปของคนอื่น พูดสิ่งที่คุณหมายถึงออกมา

`+ "\n"` คือรูปแบบ `json.dumps` ไม่เคยปล่อยขึ้นบรรทัดใหม่ของมันเอง และ `json.dumps`
ด้วย argument ค่าเริ่มต้นก็ไม่เคยปล่อยขึ้นบรรทัดใหม่ข้างในเช่นกัน
หนึ่งออบเจกต์จึงรับประกันว่าเป็นหนึ่งบรรทัดพอดี การรับประกันนั้นคือสิ่งที่ทำให้ `splitlines`
เป็น parser ที่ถูกต้อง สังเกตว่า `indent=2` จะทำลายมัน ซึ่งเป็นสิ่งที่อยากได้อย่างสมเหตุสมผล
และเข้ากันไม่ได้เลยกับรูปแบบนี้

**`ensure_ascii=False` คืออันที่คุ้มค่ากับหัวข้อของตัวเอง**

### ensure_ascii ทำอะไรจริง ๆ

`json.dumps` ใช้ค่าเริ่มต้น `ensure_ascii=True` ซึ่ง escape ทุกตัวอักษรนอก ASCII ให้เป็นลำดับ
`\uXXXX` นี่คือข้อความเดียวกันที่เขียนออกมาทั้งสองแบบ

```python
>>> import json
>>> m = {"role": "user", "content": "สวัสดี ช่วยแก้บั๊กหน่อย"}
>>> print(json.dumps(m))
{"role": "user", "content": "\u0e2a\u0e27\u0e31\u0e2a\u0e14\u0e35 \u0e0a\u0e48\u0e27\u0e22\u0e41\u0e01\u0e49\u0e1a\u0e31\u0e4a\u0e01\u0e2b\u0e19\u0e48\u0e2d\u0e22"}
>>> print(json.dumps(m, ensure_ascii=False))
{"role": "user", "content": "สวัสดี ช่วยแก้บั๊กหน่อย"}
```

บรรทัดแรกคือตัวอักษรไทยยี่สิบสองตัวที่ถูกเปลี่ยนเป็นตัวอักษรเลขฐานสิบหกหนึ่งร้อยสามสิบสองตัว

ทั้งสองบรรทัดเป็น JSON ที่ถูกต้อง ทั้งคู่ parse กลับเป็น string ของ Python อันเดียวกันเป๊ะ
ไม่มีข้อมูลสูญหายในทิศทางใด และถ้าผู้บริโภคไฟล์นี้มีแค่ `json.loads` ค่านี้จะไม่สำคัญเลย

ผู้บริโภคคือคน นั่นคือข้อโต้แย้งทั้งหมด

หัวข้อ 6 กำลังจะอ้างว่าไฟล์ session คือเครื่องมือ debug ที่ดีที่สุดของคุณ
และข้ออ้างนั้นตั้งอยู่บนความสามารถที่จะเปิดไฟล์แล้วอ่านมันได้ทั้งหมด สำหรับคนที่พูดภาษาอังกฤษ
`ensure_ascii=True` ไม่มีต้นทุนอะไร เพราะภาษาอังกฤษคือ ASCII และการ escape ไม่เคยถูกกระตุ้น
ซึ่งเป็นเหตุผลเป๊ะ ๆ ที่ค่าเริ่มต้นนี้ยังอยู่รอดในโปรแกรมมากมาย คนที่เขียนโค้ดนั้นไม่เคยเห็นปัญหา

สำหรับคนอื่นทั้งหมด มันคือความต่างระหว่างเครื่องมือ debug กับกำแพงเลขฐานสิบหก
ผู้ใช้ชาวไทยที่ถามคำถามภาษาไทยเกี่ยวกับ codebase ที่มีคอมเมนต์ภาษาไทยจะได้ไฟล์ session
ที่คำถามของเขา เนื้อหาไฟล์ที่ agent อ่าน และคำตอบของ agent อ่านไม่ออกทั้งหมด `grep`
หาคำภาษาไทยจะไม่เจออะไร เพราะคำนั้นไม่ได้อยู่ในไฟล์ การอ่านไฟล์ใน editor ไม่บอกอะไรคุณเลย
คุณสมบัติที่มีค่าที่สุดของรูปแบบนี้ถูกทำลายด้วยค่าเริ่มต้น สำหรับทุกภาษาที่ไม่ใช่ภาษาอังกฤษ

นี่ก็เป็นเหตุผลที่ `check.py` ยืนยันเรื่องนี้แทนที่จะเชื่อคอมเมนต์

```python
    session.append({"role": "user", "content": "สวัสดี"})
    if "สวัสดี" not in session.path.read_text(encoding="utf-8"):
        fail("non English text was escaped away, which makes the file unreadable")
```

เทสต์แบบ round trip (เขียนออกแล้วอ่านกลับได้ของเดิม) จะผ่านด้วยค่าใดก็ได้ เพราะทั้งคู่ round trip ได้อย่างสมบูรณ์
ข้อยืนยันจึงต้องเป็นเรื่องไบต์ในไฟล์ เพราะความอ่านออกเป็นคุณสมบัติของไบต์ ไม่ใช่ของผลลัพธ์ที่ parse แล้ว

### การอ่านกลับมา

```python
    def load(self):
        if not self.path.exists():
            return []
        lines = self.path.read_text(encoding="utf-8").splitlines()
        return [json.loads(line) for line in lines if line.strip()]
```

ไฟล์ที่ไม่มีอยู่คือบทสนทนาว่าง ไม่ใช่ error ซึ่งคือสิ่งที่ทำให้ `Session("new-name").load()`
เป็นวิธีเริ่มต้นอะไรบางอย่างที่สมเหตุสมผล คุณไม่จำเป็นต้องรู้ว่ามี session อยู่แล้วหรือยังก่อนจะขอมัน

`splitlines()` แล้ว `json.loads` บนแต่ละบรรทัดคือกฎเพิ่มหนึ่งข้อที่ JSONL คิดค่าจากคุณ
และนี่คือมันทั้งหมด ในสองบรรทัด

`if line.strip()` ข้ามบรรทัดว่าง ไฟล์ที่จบด้วยขึ้นบรรทัดใหม่ ซึ่งไฟล์ทุกไฟล์ที่โปรแกรมนี้เขียนเป็นแบบนั้น
จะไม่ผลิต string ว่างที่ท้ายจาก `splitlines` ดังนั้นข้อนี้ไม่ได้มีไว้เพื่อการนั้น
มันมีไว้สำหรับไฟล์ที่มีบรรทัดว่างโผล่เข้ามาโดยบังเอิญ จาก text editor จากการเขียนไม่ครบ จากการที่ใครแปะอะไรลงไป
string ว่างหนึ่งอันที่ไปถึง `json.loads` ทำให้เกิด
`JSONDecodeError: Expecting value: line 1 column 1 (char 0)` และ session
ที่โหลดไม่ได้เพราะบรรทัดว่างคือการแลกที่แย่สำหรับโค้ดสี่ตัวอักษร

เราอ่านทั้งไฟล์รวดเดียว `read_text` โหลดทุกอย่างเข้าหน่วยความจำ ซึ่งไม่เป็นไร
เพราะบทสนทนาที่ใส่ใน context window ไม่ได้ ยังไงก็ใส่ใน RAM ได้แน่นอน
การอ่านแบบ stream ทีละบรรทัดจะระมัดระวังกว่าและซื้ออะไรไม่ได้เลย เพราะผู้เรียกอยากได้ทั้งลิสต์อยู่ดี

### การลิสต์สิ่งที่มีอยู่

```python
    @staticmethod
    def list_all(directory=None):
        folder = Path(directory or default_directory())
        if not folder.is_dir():
            return []
        return sorted(path.stem for path in folder.glob("*.jsonl"))
```

การลิสต์ไดเรกทอรีคือ index ไม่มีไฟล์แยกที่บันทึกว่ามี session อะไรอยู่บ้าง
ซึ่งแปลว่าไม่มีอะไรที่ขัดแย้งกับความจริงได้ ลบ session ด้วย `rm` แล้วมันหายไปจากลิสต์
เพราะลิสต์ไม่เคยเป็นอะไรนอกจากไดเรกทอรี

`path.stem` คือชื่อไฟล์ที่ไม่มีนามสกุล ดังนั้น `~/.agentpath/sessions/fix-average.jsonl`
กลับมาเป็น `fix-average` ซึ่งคือ string ที่คุณส่งให้ `Session(...)` เพื่อเปิดมันอีกครั้งเป๊ะ ๆ
ชื่อที่คุณเห็นคือชื่อที่คุณใช้

```python
>>> Session.list_all()
['fix-average']
```

## 6. ไฟล์ session คือเครื่องมือ debug ที่ดีที่สุดของคุณ

การทำงานต่อคือฟีเจอร์ที่คนสร้าง session ขึ้นมาเพื่อมัน การ debug คือสิ่งที่มันกลายเป็นจริง ๆ
และมันไม่ได้ใกล้เคียงกันเลย

นี่คือเหตุผล เมื่อ agent ทำอะไรที่ชวนงง และมันจะทำ มีคำถามที่มีประโยชน์อยู่ข้อเดียว
มันเห็นอะไรจริง ๆ ไม่ใช่สิ่งที่คุณหมายถึง ไม่ใช่สิ่งที่ prompt บอก ไม่ใช่สิ่งที่คุณสมมติว่า tool คืนมา
แต่คืออะไรอยู่ในลิสต์ของข้อความในตอนที่ model ผลิตการตัดสินใจที่คุณกำลังจ้องอยู่

บั๊กของ agent ทุกตัวที่คุณจะได้ debug คือหนึ่งในห้าอย่าง และทั้งห้าอย่างตอบได้ด้วยการอ่านลิสต์นั้น

tool คืนอะไรที่ไม่ใช่สิ่งที่คุณสมมติ ผลของ tool ถูกตัดและส่วนสำคัญอยู่ในส่วนที่ถูกตัดออก
system prompt ไม่ได้พูดอย่างที่คุณคิดว่ามันพูด model ไม่เคยถูกบอกเรื่องสิ่งที่คุณหงุดหงิดว่ามันไม่ใช้
หรือ model เห็นทุกอย่างถูกต้องแล้วตอบแย่ ซึ่งเป็นคนละปัญหาที่มีวิธีแก้ต่างกัน
และคุณแยกมันจากอีกสี่ข้อไม่ได้ถ้าไม่ไปดู

ไฟล์ session คือลิสต์นั้น มันถูกเขียนขณะที่การรันเกิดขึ้น มันจึงมีอยู่แม้การรันจะล่ม
ไม่มีภาษา query ให้เรียน ไม่มี viewer ให้สร้าง ไม่มี instrumentation ให้เพิ่ม
และไม่ต้องทำให้ปัญหาเกิดซ้ำ ซึ่งก็ดีแล้ว เพราะปัญหาอาจไม่เกิดซ้ำ

### ไฟล์ session จริง

นี่คือ output จริง ผลิตโดยโค้ดในโฟลเดอร์นี้กับ mock server ของคอร์ส โดยใช้บั๊กใน `stats.py`
อันเดียวกับบทที่ 11

```text
{"role": "user", "content": "The average is wrong. Find it and fix it. [[tool:grep_files:{\"pattern\": \"def average\", \"glob\": \"*.py\"}]][[tool:read_file:{\"path\": \"stats.py\"}]]"}
{"role": "assistant", "content": "", "tool_calls": [{"id": "call_mock_1", "type": "function", "function": {"name": "grep_files", "arguments": "{\"pattern\": \"def average\", \"glob\": \"*.py\"}"}}]}
{"role": "tool", "tool_call_id": "call_mock_1", "content": "stats.py:8: def average(numbers):"}
{"role": "assistant", "content": "", "tool_calls": [{"id": "call_mock_2", "type": "function", "function": {"name": "read_file", "arguments": "{\"path\": \"stats.py\"}"}}]}
{"role": "tool", "tool_call_id": "call_mock_2", "content": "\"\"\"Small helpers for summarising a list of numbers.\"\"\"\n\n\ndef total(numbers):\n    return sum(numbers)\n\n\ndef average(numbers):\n    if not numbers:\n        return 0\n    return total(numbers) / (len(numbers) + 1)\n"}
{"role": "assistant", "content": "The tool returned \"\"\"Small helpers for summarising a list of numbers.\"\"\"\n\n\ndef total(numbers):\n    return sum(numbers)\n\n\ndef average(numbers):\n    if not numbers:\n        return 0\n    return total(numbers) / (len(numbers) + 1)\n."}
```

หกบรรทัด อ่านตามลำดับ

บรรทัดที่ 1 คือข้อความของ user และมันมีงานเป๊ะตามที่ถูกส่งไป สังเกตคำสั่ง `[[tool:...]]`
ซึ่งเป็นวิธีบังคับทิศทาง mock server อย่างที่บทที่ 06 อธิบายไว้
เมื่อเจอกับ model จริงบรรทัดนี้จะเป็นประโยคของคุณและไม่มีอะไรอื่น
นี่คือข้อเท็จจริงสำหรับ debug ข้อแรกที่ไฟล์นี้ให้คุณฟรี ๆ ซึ่งคือสิ่งที่ model ถูกถาม แบบคำต่อคำ
รวมถึงอะไรก็ตามที่ wrapper เติมเข้าไปโดยที่คุณไม่รู้

บรรทัดที่ 2 คือ assistant ขอ tool `"content": ""` แปลว่า model ไม่ได้ผลิตข้อความร้อยแก้วในเทิร์นนั้น
ซึ่งเป็นเรื่องปกติสำหรับ model เล็กและไม่ใช่สัญญาณว่ามีอะไรผิด ส่วนที่น่าสนใจคือ `"id": "call_mock_1"`
และ argument ซึ่งเป็น JSON string อยู่ข้างใน JSON object การเข้ารหัสซ้อนสองชั้นนั้นไม่ใช่ตัวเลือกของเรา
มันคือสิ่งที่รูปแบบสายของ OpenAI กำหนด และบทที่ 05 จัดการกับมันไปแล้วตอนที่มันสะสมชิ้นส่วนของ argument
จาก stream ไฟล์เก็บรูปแบบบนสายไว้เพราะรูปแบบบนสายคือสิ่งที่ model เห็น

บรรทัดที่ 3 คือผลของการเรียกนั้น และมันนั่งอยู่ใต้มันโดยตรง นี่คือคุณสมบัติที่ควรชี้ให้ดู
`"tool_call_id": "call_mock_1"` บนบรรทัดที่ 3 ตรงกับ `"id": "call_mock_1"` บนบรรทัดที่ 2
คำขอกับคำตอบอยู่ติดกัน ตามลำดับ ในไฟล์ที่คุณอ่านจากบนลงล่างได้ เมื่อคุณอยากรู้ว่า `grep_files`
เจอสิ่งที่คุณคิดว่ามันเจอหรือเปล่า คุณไม่ต้องรันอะไรใหม่ มันอยู่ตรงนั้น มันเจอ `stats.py:8`
และไม่เจออย่างอื่น

บรรทัดที่ 4 และ 5 คือรูปแบบเดิมอีกครั้ง ด้วย `call_mock_2` และบรรทัดที่ 5
คือจุดที่รูปแบบไฟล์นี้พิสูจน์คุณค่าของตัวเอง ดูฟิลด์ `content` มันคือไฟล์ `stats.py` ทั้งไฟล์
โดยขึ้นบรรทัดใหม่ทุกอันถูกเก็บเป็น `\n` ข้างใน JSON string อันเดียว ผลของ tool ที่มีหลายบรรทัด
ยังคงเป็นบรรทัดเดียวของไฟล์ session พอดี ซึ่งคือสิ่งที่ทำให้ "หนึ่งข้อความต่อหนึ่งบรรทัด"
ยังเป็นจริงสำหรับผลของ tool ที่เป็น source code สิบกิโลไบต์ มันแน่นเกินกว่าจะอ่านดิบ ๆ
ซึ่งคือสิ่งที่ `python -m json.tool` จากหัวข้อ 3 มีไว้เพื่อ

และบั๊กมองเห็นได้ในบรรทัดนั้น `return total(numbers) / (len(numbers) + 1)` อยู่ใน context
ของ model ดังนั้นถ้ามันบอกต่อไปว่าไฟล์ดูปกติดี ตอนนี้คุณรู้แล้วว่าความล้มเหลวอยู่ที่การให้เหตุผลของ model
ไม่ใช่ที่การดึงข้อมูล นั่นคือการแยกแยะที่มีค่าที่สุดเวลา debug agent
และหนึ่งบรรทัดของไฟล์ข้อความก็ตัดสินมันได้

บรรทัดที่ 6 คือข้อความสุดท้ายของ assistant ที่ไม่มี `tool_calls` ซึ่งคือ loop ที่กำลังคืนค่า
เมื่อเจอกับ model จริงตรงนี้คือที่ที่ข้อความร้อยแก้วจะอยู่ mock server สะท้อนผลของ tool อันสุดท้ายแทน
ซึ่งเป็นเหตุผลที่บรรทัดนี้พูดเนื้อไฟล์ซ้ำ

### ทำไมมันชนะการทำ logging

คุณเพิ่ม logging แทนก็ได้ และนั่นคือสัญชาตญาณที่ชัดเจนกว่า มันแย่กว่าตรงนี้ ด้วยเหตุผลเฉพาะข้อหนึ่ง

log บันทึกสิ่งที่โปรแกรมของคุณตัดสินใจจะบันทึก มีคนเลือก level เลือกข้อความ
เลือกว่าจะแทรกตัวแปรไหนเข้าไป วินาทีที่คุณต้องการอะไรที่ไม่ได้ถูกเลือก คุณต้องเพิ่มบรรทัด log
deploy ใหม่ และทำให้ปัญหาเกิดซ้ำ และปัญหาของ agent มักเกิดซ้ำไม่ได้เพราะ model ไม่เป็น deterministic
บั๊กที่คุณกำลังไล่ล่าเกิดขึ้นครั้งเดียว เมื่อวาน บนบทสนทนาที่ไม่มีอยู่แล้ว

ไฟล์ session บันทึก input ของการตัดสินใจ ครบถ้วน โดยไม่มีการคัดเลือกใด ๆ
ทุกอย่างอยู่ในนั้นเพราะทั้งหมดอยู่ในนั้น คุณไม่ต้องคาดเดาคำถามไว้ล่วงหน้า

ไม่ใช่เพราะ JSONL กำลังฮิต แต่เพราะสิ่งแรกที่ทุกคนถามเกี่ยวกับ agent ที่ทำตัวผิดคือมันเห็นอะไร
และรูปแบบเดียวที่ตอบคำถามนั้นได้คือรูปแบบที่เก็บทั้งหมดไว้

## 7. การทำงานต่อ

การทำงานต่อคือการโหลดลิสต์แล้วไปต่อ นั่นไม่ใช่การพูดให้ง่ายเกินจริง

```python
from session import Session

session = Session("fix-average")
answer, messages = run(
    provider,
    "Now add a test for it.",
    history=session.load(),
    on_message=session.append,
)
```

สี่บรรทัด และสามในนั้นคือการส่ง argument `session.load()` คืนบทสนทนาอย่างที่มันเป็น `run`
เริ่มจากมัน `on_message=session.append` แปลว่าข้อความใหม่ไปลงท้ายไฟล์เดิม
ดังนั้นการทำงานต่อของพรุ่งนี้จะได้ของวันนี้และของเมื่อวาน

รายละเอียดสองอย่างใน loop ทำให้สิ่งนี้ทำงานได้อย่างถูกต้อง

```python
    messages = list(history or [])
```

`list(...)` คัดลอก ดังนั้นการที่ `run` ต่อท้าย `messages` ไม่ไปเปลี่ยนสิ่งที่ผู้เรียกส่งเข้ามา
และ history ถูกกำหนดค่าโดยตรงแทนที่จะส่งผ่าน `remember`
ซึ่งแปลว่าข้อความที่โหลดมาไม่ถูกเขียนลงไฟล์เป็นครั้งที่สอง ทำงานต่อจาก session สิบครั้ง
แล้วไฟล์ยังมีแต่ละข้อความครั้งเดียว ถ้าตรงนี้เป็น loop ที่เรียก `remember` บนแต่ละรายการของ history
การทำงานต่อทุกครั้งจะทำสำเนาบทสนทนาทั้งอันบนดิสก์ และไฟล์จะโตเป็นสองเท่าทุกครั้งที่ทำงานต่อ
ขณะที่บทสนทนายาวเท่าเดิม

```python
    if system and not messages:
        remember({"role": "system", "content": system})
```

`and not messages` คือกรณีของการทำงานต่อ history ที่โหลดมามีข้อความ system ของมันอยู่ที่บรรทัด 1
อยู่แล้ว ดังนั้นการเพิ่มอีกอันจะทำให้ model ได้ system prompt สองอัน ซึ่งไม่ใช่ error ที่ provider
จะปฏิเสธ และเป็นสิ่งที่ debug ได้สับสนมาก เงื่อนไขนี้บอกว่า system prompt มีไว้สำหรับการเริ่มบทสนทนา
ไม่ใช่สำหรับการทำต่อ

### ทำไมมันถึงทำงานได้ตั้งแต่แรก

หยุดแล้วสังเกตว่าอะไรทำให้การทำงานต่อเป็นไปได้ เพราะมันไม่ชัดเจน
และมันคือผลตอบแทนของสิ่งที่คุณเรียนไปตั้งแต่สิบเอ็ดบทก่อน

ไม่มี state ฝั่งเซิร์ฟเวอร์ เมื่อคุณทำงานต่อ คุณไม่ได้เชื่อมต่อกลับไปหาอะไร
ไม่มีตัวระบุ session ที่ provider ถือไว้ ไม่มีบทสนทนาที่ถูกหยุดพักไว้ฝั่งเขา ไม่มีอะไรให้ต่อกลับ
model ไม่รู้ว่าผ่านไปหนึ่งสัปดาห์ระหว่างข้อความที่สี่กับข้อความที่ห้า และมันรู้ไม่ได้
เพราะ request ที่พาข้อความที่ห้าไปหน้าตาเหมือนกับ request ที่ส่งไปเมื่อสัปดาห์ก่อนด้วยลิสต์เดียวกัน

นั่นคือบทที่ 02 สิ่งที่น่าประหลาดใจอันแรกสุดที่คอร์สนี้สอนคือ model ไม่จำอะไรเลย
ทุก request พาบทสนทนาทั้งอันไป และภาพลวงตาของความจำถูกผลิตขึ้นโดย client ของคุณ
ตอนนั้นมันมาถึงในฐานะต้นทุน คุณส่งทุกอย่างใหม่ ทุกครั้ง และคุณจ่ายเงินให้มัน

นี่คือเงินคืน เพราะ model ไม่มี state บทสนทนาจึงเป็นของคุณทั้งหมด มันคือข้อมูลที่คุณเป็นเจ้าของ
ในไฟล์ที่คุณเป็นเจ้าของ ในรูปแบบที่คุณเลือก คุณบันทึกมัน ปิดแล็ปท็อป กลับมาสัปดาห์หน้า แล้วทำต่อได้
คุณคัดลอกไฟล์ไปอีกเครื่องแล้วทำต่อที่นั่นได้ คุณส่งมันให้ provider อื่นแล้วทำต่อได้ เพราะบทที่ 06
ทำให้รูปแบบบนสายเป็นคุณสมบัติของ provider ไม่ใช่ของบทสนทนา คุณเปิดมัน
ลบสี่ข้อความที่ agent เดินเข้าทางตัน แล้วทำต่อจากเวอร์ชันที่ถูกตัดแต่งแล้วได้
และ model จะไม่รู้เลยว่ามีอะไรถูกลบออกไป เพราะมันไม่เคยรู้ว่ามีอะไรอยู่ตรงนั้น

ไม่มีอะไรที่ว่ามาจะเป็นไปได้ถ้า model ถือบทสนทนาไว้ คุณจะต้องไปขอฟีเจอร์ export จากเจ้าของบริการ

ความไร้ state ดูเหมือนเป็นคุณสมบัติที่แพงในบทที่ 02 มันคือคุณสมบัติที่ทำให้ทุกบทของ part 3
เป็นไปได้ session ตรงนี้ และในบทที่ 14 คือการที่คุณเขียนประวัติใหม่ให้พอดี context window ได้
ซึ่งทำได้เพียงเพราะไม่มีเซิร์ฟเวอร์ที่จะสังเกตเห็น

## 8. ข้อจำกัดที่คุณควรรู้

มี process ที่เขียนไฟล์ได้ทีละหนึ่งเท่านั้น

`Session.append` เปิดไฟล์ในโหมด append เขียนหนึ่งบรรทัด แล้วปิด
สอง process ที่ทำแบบนั้นกับไฟล์เดียวกันในเวลาเดียวกันจะสลับกัน ไม่ใช่ข้อความของพวกมันซึ่งยังพอรอด
แต่เป็นไบต์ของพวกมัน การเขียนบรรทัดยาวหนึ่งครั้งไม่รับประกันว่าเป็น atomic
สิ่งที่คุณได้จึงเป็นบรรทัดหนึ่งที่เริ่มกลางอีกบรรทัดหนึ่ง และทั้งคู่ parse ไม่ได้

```text
{"role": "user", "content": "fix the te{"role": "user", "content": "add a test"}
sts"}
```

`json.loads` ล้มเหลวทั้งคู่ ตัวป้องกัน `if line.strip()` ไม่ช่วย เพราะบรรทัดพวกนี้ไม่ได้ว่าง
มันคือขยะ และความล้มเหลวเป็นแบบถาวร ไม่มีการซ่อม
เพราะข้อมูลว่าข้อความหนึ่งจบตรงไหนและอีกข้อความเริ่มตรงไหนไม่ได้อยู่ในไฟล์อีกแล้ว

ต้องพูดให้ชัดว่านี่เป็นข้อจำกัดจริงไม่ใช่ทฤษฎี มันไม่ต้องการให้คุณทำอะไรแปลก ๆ เลย
เปิดสอง terminal แล้วทำงานต่อจาก session เดียวกันในทั้งสอง
ซึ่งเป็นเรื่องปกติที่เกิดขึ้นโดยบังเอิญเมื่อคุณลืมว่าอันแรกกำลังรันอยู่ รัน agent ใน watch loop
ขณะที่คุณกำลังใช้มันอยู่ด้วย มีปลั๊กอินของ editor กับ command line ชี้ไปที่ชื่อ session เดียวกัน
อย่างใดอย่างหนึ่งทำให้ไฟล์เสียหาย และคุณจะรู้ทีหลัง ตอนที่คุณพยายามโหลดมัน

harness จริงทำอย่างอื่น พวกมันจับ lock ก่อนเขียน บน Unix นั่นคือ `fcntl.flock` บน file descriptor
บน Windows คือ `msvcrt.locking` และทั้งสองมี semantics ต่างกัน ซึ่งเป็นเหตุผลแรกที่มันไม่ใช่โค้ดบรรทัดเดียว
เหตุผลที่สองคือการตัดสินใจว่าจะเกิดอะไรขึ้นเมื่อ lock ถูกถืออยู่ การบล็อกแปลว่า agent
ของคุณหยุดจนกว่าอีก process จะเสร็จ ซึ่งผิดถ้าอีก process คือ session ที่ตายไปแล้วและ lock
ไม่เคยถูกปล่อย การล้มเหลวแปลว่าต้องบอกผู้ใช้ว่า session ของเขาไม่ว่าง
ซึ่งต้องมีวิธีบอกและวิธีกู้คืน harness บางตัวเลี่ยงปัญหาแทน โดยให้แต่ละ process มีไฟล์ session
ของตัวเองแล้วรวมกันตอนอ่าน ซึ่งเป็นการออกแบบที่ดีและใหญ่กว่า

ที่ไม่ทำมันตรงนี้เป็นความตั้งใจ การ lock ไม่ใช่บทเรียน การ lock ไฟล์ข้ามแพลตฟอร์มน่าจะราวสี่สิบบรรทัด
พร้อม branch สำหรับสองแพลตฟอร์ม บวกการตรวจจับ lock ค้าง บวกการตัดสินใจเรื่องการบล็อก
และทุกบรรทัดในนั้นเป็นเรื่อง lock ไม่ใช่เรื่อง session การใส่มันลงในไฟล์นี้จะทำให้ `session.py`
ใหญ่ขึ้นสามเท่า และคนอ่านจะจากไปโดยได้เรียนเรื่อง `fcntl`
แทนที่จะได้เรียนว่าทำไมบทสนทนาบนดิสก์จึงคุ้มค่าที่จะมี

ดังนั้นกฎสำหรับโค้ดในโฟลเดอร์นี้คือหนึ่ง process ต่อหนึ่งชื่อ session กฎนั้นไม่ถูกบังคับใช้ที่ไหนเลย
และการทำผิดกฎทำให้ไฟล์เสียหาย บทที่ 18 มีหนึ่ง process ที่เป็นเจ้าของ session ซึ่งเลี่ยงเรื่องนี้ไป
และถ้าคุณเอาโค้ดนี้ไปใช้กับอะไรจริงจัง lock คือสิ่งแรกที่ควรเพิ่ม

## 9. การรัน check.py

จากในโฟลเดอร์ของบทเรียน โดยตั้งค่า endpoint ไว้แล้ว

```bash
cd lessons/13-sessions

```

หรือรันทุกบทพร้อมกันกับ mock server ที่มีมาให้

```bash
python ci/run_lessons.py
```

การรันที่ผ่านหน้าตาแบบนี้

```text
OK a conversation survives being written and read back
OK the file is one JSON object per line and you can read it
OK text in any language stays readable in the file
Hello from the mock server.
OK a real run was saved as it happened, 2 messages
OK the saved conversation can be loaded again to carry on from
```

บรรทัด `Hello from the mock server.` ตรงกลางไม่ใช่ส่วนหนึ่งของการตรวจ
มันคือ loop ที่กำลัง stream คำตอบของ model ออกมาที่ terminal เป๊ะตามที่บทที่ 05 สร้างไว้
และมันปรากฏตรงนั้นเพราะข้ออ้างที่สี่ทำการรันจริง

ห้าข้ออ้าง และแต่ละข้อทดสอบคนละเรื่อง

บทสนทนารอดจากการถูกเขียนและอ่านกลับมา สามข้อความเข้าไป
รวมถึงข้อความของ assistant ที่มี `tool_calls` และผลของ tool ที่คู่กัน
และลิสต์ที่โหลดมาต้องเท่ากับลิสต์ที่เขียนไป tool call อยู่ใน fixture โดยตั้งใจ
เทสต์ round trip ที่มีข้อความตัวอักษรธรรมดาสามอันจะผ่านแม้ว่าโครงสร้างซ้อนจะถูกทำให้แบน
และข้อความที่สำคัญจริงคือข้อความที่ซ้อนกัน

ไฟล์คือหนึ่ง JSON object ต่อหนึ่งบรรทัด ข้อนี้ถูกยืนยันแยกจาก round trip และมันต้องแยก
เพราะไฟล์ `pickle` จะผ่านเทสต์ round trip ได้อย่างสมบูรณ์และอ่านไม่ออก
การตรวจนับสามบรรทัดสำหรับสามข้อความและ parse แต่ละอันแยกกัน

```python
    lines = session.path.read_text(encoding="utf-8").splitlines()
    if len(lines) != 3 or any(not json.loads(line) for line in lines):
        fail("the file is not one readable JSON object per line")
```

ข้อความในภาษาใดก็ยังอ่านออก ข้อยืนยันเรื่อง `ensure_ascii` จากหัวข้อ 5
ซึ่งตรวจไบต์แทนที่จะตรวจค่าที่ parse แล้ว

การรันจริงถูกบันทึกขณะที่มันเกิดขึ้น ข้อนี้คือข้อที่ผูกทั้งบทเข้าด้วยกัน มันสร้าง provider จริง
เรียก `run` ด้วย `on_message=live.append` แล้วยืนยันว่า `live.load()` เท่ากับ `messages`
ที่ `run` คืนมา

```python
    live = Session("live")
    _, messages = run(provider, "Say hello.", on_message=live.append)
    if live.load() != messages:
        fail("the session on disk does not match the conversation in memory")
```

ความเท่ากันนั้นคือข้ออ้างทั้งหมดของบทนี้ในบรรทัดเดียว สิ่งที่อยู่บนดิสก์คือสิ่งที่อยู่ในหน่วยความจำ
ไม่ใช่บทสรุปของมัน ไม่ใช่การเรนเดอร์ของมัน และไม่ใช่เวอร์ชันที่สูญเสียข้อมูลของมัน
จำนวนถูกพิมพ์ออกมาเพราะมันเป็นสิ่งที่มีประโยชน์ที่จะเห็น สองข้อความสำหรับการรันนี้
คือข้อความของ user กับคำตอบของ assistant โดยไม่มี system prompt และไม่มี tool call

บทสนทนาที่บันทึกไว้โหลดกลับมาเพื่อทำต่อได้ `Session("live")` อันใหม่
ที่สร้างขึ้นจากชื่อเพียงอย่างเดียว โหลดบทสนทนาที่มี role เป็น `user` แล้วตามด้วย `assistant`
รูปทรงนั้นคือข้อกำหนดของการทำงานต่อ บทสนทนาที่จบด้วย tool call ที่ไม่มีผลลัพธ์
หรือบทสนทนาที่ข้อความมาถึงผิดลำดับ จะถูก provider ปฏิเสธใน request ถัดไป

ไดเรกทอรีชั่วคราวที่ต้นไฟล์คือเทคนิคเดียวกับที่บทที่ 11 ใช้ ด้วยเหตุผลเดียวกัน

```python
home = Path(tempfile.mkdtemp(prefix="agentpath-lesson13-"))
workspace = Path(tempfile.mkdtemp(prefix="agentpath-lesson13-ws-"))
os.environ["AGENTPATH_HOME"] = str(home)
os.environ["AGENTPATH_WORKSPACE"] = str(workspace)
```

สองไดเรกทอรีแทนที่จะเป็นหนึ่ง เพราะมันเป็นคนละเรื่องกัน home คือที่ที่ session ถูกเขียน
workspace คือที่ที่ agent ได้รับอนุญาตให้แตะไฟล์ การแยกมันในการตรวจช่วยให้คุณแยกมันในหัวได้
และการรันการตรวจไม่ทิ้งอะไรไว้ใน `~/.agentpath` จริงของคุณ

ถ้าข้อที่สามล้มเหลว `ensure_ascii` ถูกทิ้งไว้ที่ค่าเริ่มต้น ถ้าข้อที่สี่ล้มเหลว `on_message`
ไม่ได้ถูกเรียกสำหรับทุกข้อความ และที่ที่ควรไปดูคือการเรียก `messages.append` ทั้งห้าจุดใน `agent.py`
กลายเป็น `remember` แล้วหรือยัง รวมถึงอันที่อยู่ใน branch `if not calls` ด้วย

## 10. สิ่งที่คุณยังทำไม่ได้

ตอนนี้ agent ของคุณจำข้ามการรันได้แล้ว มันยังไม่ได้จัดการสิ่งที่มันจำ และนั่นคือปัญหาถัดไป
ไม่ใช่ปัญหาที่อยู่ไกล

ไม่มีอะไรในโปรแกรมนี้นับขนาดของบทสนทนา `max_turns=10` จำกัดจำนวนเทิร์นไม่ใช่จำนวนไบต์
และบทที่ 02 ได้ยืนยันแล้วว่าลิสต์ทั้งอันถูกส่งใหม่ในทุก request ดังนั้น session
ที่คุณทำงานต่อพรุ่งนี้จะเริ่มด้วยการส่งทั้งหมดของวันนี้ และ session ที่คุณทำงานต่อครั้งที่ห้าจะส่งสี่ครั้งก่อนหน้า
session ทำให้เรื่องนั้นแย่ลงแทนที่จะดีขึ้น เพราะก่อนบทนี้ บทสนทนายาว ๆ จบลงเมื่อ process จบ

เลขคณิตจากบทที่ 11 ไม่ได้หายไปไหน `read_file` หนึ่งครั้งราว 4000 ตัวอักษร ประมาณหนึ่งพัน token
แปดไฟล์ที่อ่านตลอดหนึ่งงานคือแปดพัน token ของเนื้อหาไฟล์ที่นั่งอยู่ในลิสต์อย่างถาวร
ถูกส่งใหม่ในทุกเทิร์นตลอดที่เหลือของ session และตอนนี้ถูกส่งใหม่อีกครั้งในทุกการทำงานต่อ

ความล้มเหลวเมื่อมันมาถึงนั้นฉับพลัน ไม่มีคำเตือน ไม่มีคุณภาพที่ค่อย ๆ แย่ลง มันคือ HTTP error
จาก provider ที่บอกว่า request เกินความยาว context มาถึงกลางงาน โดยไม่มีทางไปต่อ
และไฟล์ session ทำให้มันแย่ลงในแง่หนึ่งโดยเฉพาะ เพราะบทสนทนาที่โตจนส่งไม่ได้แล้วตอนนี้ถูกบันทึกไว้
ดังนั้นการทำงานต่อจากมันจะล้มเหลวทันทีและถาวร คุณมีไฟล์ที่คุณใช้ไม่ได้

การแก้ที่ชัดเจนคือทิ้งข้อความที่เก่าที่สุด และมันผิดในแบบที่ควรรู้ก่อนคุณจะเขียนมัน
ดูข้อความที่ยกมาในหัวข้อ 6 อีกครั้ง บรรทัดที่ 2 คือข้อความของ assistant ที่มี `tool_calls`
บรรทัดที่ 3 คือผลของมัน ทุก provider กำหนดว่าคู่นั้นต้องอยู่ด้วยกัน ทิ้งบรรทัดที่ 2 แล้วเก็บบรรทัดที่ 3
แล้ว request จะถูกปฏิเสธด้วย `400` เพราะมีผลลัพธ์ของการเรียกที่ไม่เคยเกิดขึ้น ทิ้งบรรทัดที่ 3
แล้วเก็บบรรทัดที่ 2 ก็ถูกปฏิเสธเช่นกัน หน่วยที่คุณทิ้งได้ไม่ใช่ข้อความ
และข้อความที่เก่าที่สุดมักเป็นข้อความที่มีค่าที่สุด เพราะมันมีงานต้นฉบับอยู่

บทที่ 14 คือการจัดการ context การวัดบทสนทนาแทนที่จะเดามัน การตัดสินใจว่าจะทิ้งอะไร
โดยถือการจับคู่ tool call เป็นข้อจำกัดที่แข็งอย่างที่มันเป็นจริง การสรุปช่วงกลางของ session ยาว ๆ
และคำถามว่าใครเป็นคนเขียนบทสรุปและนั่นมีต้นทุนเท่าไร

มีอีกหนึ่งอย่างที่บทนี้ไม่ได้ทำ และมันเล็กกว่าแต่คุณจะสังเกตเห็นเร็วกว่า ไม่มีอะไรตั้งชื่อ session
ให้คุณ `Session("fix-average")` ต้องให้คุณคิด string ขึ้นมาเองและจำมัน
และวันที่คุณจำไม่ได้ว่าเมื่อวานคุณตั้งชื่อ session ว่าอะไร `Session.list_all()`
ให้ลิสต์ชื่อที่เรียงแล้วกับคุณและไม่มีอะไรอื่น ไม่มีวันที่ ไม่มีข้อความแรก ไม่มีสัญญาณว่าอันไหนที่คุณอยู่ในนั้นเมื่อชั่วโมงก่อน
นั่นเป็นปัญหาของ command line มากกว่าปัญหาของ session และบทที่ 18 ก้าวแรกไปกับมัน
`main.py` ของบทนั้นได้ flag `--resume` ที่รับชื่อ session แล้วโหลด history ของ session นั้น
ก่อน loop จะเริ่ม บวกกับ flag `--session` และ timestamp ไว้ใช้เป็นชื่อเมื่อคุณไม่ให้ทั้งสองอย่าง
แค่นั้นก็พอจะทำงานต่อจากเมื่อวานได้ แต่ยังไม่พอจะตอบคำถามว่า "อันไหนคือเมื่อวาน"
และคอร์สนี้ไม่เคยสร้างส่วนนั้น

ก่อนไปต่อ ทำหนึ่งอย่าง รัน agent กับอะไรจริงจัง ปล่อยให้มันทำงาน
แล้วเปิดไฟล์ session ที่มันเขียนแล้วอ่านจากบนลงล่าง หา tool call ที่ทำให้คุณประหลาดใจ
แล้วดูบรรทัดที่อยู่ใต้มัน นิสัยนั้นคือสิ่งที่ควรเอาออกไปจากบทนี้
และมันจะประหยัดเวลาให้คุณมากกว่าการทำงานต่อเสียอีก
