# บทที่ 2 agent loop คือแก่นเดียวที่เหลืออยู่

หลักสูตรนี้มี 24 บท เพิ่ม tool (เครื่องมือ คือฟังก์ชันที่ model ขอให้เรารันได้)
เจ็ดตัว และเพิ่ม subsystem (ระบบย่อย คือชิ้นส่วนที่ต้องเห็นหรือแทรกกลางการทำงาน
ของแกน) ห้าตัว ผ่านการเขียนที่กินเวลาหลายสัปดาห์

แต่ agent loop (วงรอบของเอเจนต์ คือลูปที่ถาม model แล้วรัน tool สลับกันไป
จนได้คำตอบ) ไม่เปลี่ยนเลย และคำว่าไม่เปลี่ยนในที่นี้ไม่ได้แปลว่าคล้ายเดิม
มันแปลว่าเป็นไฟล์เดียวกันทุก byte

บทนี้อธิบายว่าทำไม

## 1. สี่ขั้นตอนที่เป็นทั้งหมดของ agent

ลบทุกอย่างที่เป็นส่วนประกอบออก แล้วสิ่งที่เหลือคือสี่ขั้นตอนนี้

1. ส่งบทสนทนาทั้งหมดไปถาม model พร้อมรายการ tool ที่มีให้เลือก
2. ถ้าคำตอบเป็นข้อความล้วน จบ คืนข้อความนั้น
3. ถ้าคำตอบคือคำขอเรียก tool ให้รัน tool นั้น แล้วเอาผลลัพธ์ใส่กลับเข้าบทสนทนา
4. กลับไปข้อ 1

**มันคืออะไร** ลูปที่วนจนกว่า model จะเลิกขอ tool

**ทำไมต้องเป็นลูป ไม่ใช่การเรียกฟังก์ชันเพิ่มอีกครั้ง** เพราะ model ไม่มีทาง
รู้คำตอบจนกว่าเราจะรัน tool ให้ และเมื่อมันเห็นผลลัพธ์แล้ว มันอาจต้องการ tool
อีกตัว การอ่านไฟล์แล้วพบว่าต้องอ่านอีกไฟล์เป็นเรื่องปกติ จำนวนรอบไปกลับ
จึงไม่มีทางรู้ล่วงหน้า และการทำซ้ำที่ไม่รู้จำนวนรอบล่วงหน้าคือนิยามของลูป

**ทำไมไม่ใช่ recursion หรือ state machine หรือ graph** recursion ทำงานถูก
แต่ทำให้ stack ลึกขึ้นตามจำนวนรอบโดยไม่ได้อะไรกลับมา และทำให้การอ่าน
traceback ตอนพังยากขึ้น state machine กับ graph เหมาะเมื่อมีสถานะหลายแบบที่
เปลี่ยนไปมาตามเงื่อนไข แต่ที่นี่มีสองสถานะเท่านั้นคือยังไม่จบกับจบแล้ว
การใส่ machinery ที่รองรับสิบสถานะเพื่อจัดการสองสถานะคือการซ่อนความง่าย
ไว้หลังความซับซ้อน

นี่คือ loop ตัวจริงจาก `src/agentpath/agent.py` ตัดส่วนป้องกันออกเพื่อให้
เห็นโครง

```python
    def run(self, user_input: str) -> Iterator:
        self._remember(Message(role="user", content=user_input))

        for _ in range(self.max_turns):
            assistant = None
            for event in self.provider.stream(self._to_send(), self.tools.schemas() or None):
                if isinstance(event, TurnDone):
                    assistant = event.message
                else:
                    yield event
            self._remember(assistant)

            if not assistant.tool_calls:
                yield TurnDone(message=assistant)
                return

            for call in assistant.tool_calls:
                yield ToolCallRequest(tool_call=call)
                result = self._run_one(call, recent)
                yield result
                self._remember(
                    Message(role="tool", content=result.content, tool_call_id=call.id)
                )
```

ทุกบรรทัดตรงกับสี่ขั้นตอนข้างบนหนึ่งต่อหนึ่ง

## 2. ทำไม assistant message ที่มี tool_calls ต้องกลับเข้า history

จุดที่คนพลาดบ่อยคือลืมใส่ข้อความของ assistant ที่ขอเรียก tool กลับเข้าไปใน
history แล้วใส่แต่ผลลัพธ์ ผลคือ model เห็นผลลัพธ์ของบางอย่างที่มันไม่รู้ว่า
ตัวเองเคยขอ

```python
# คำขอของ model ในเสียงของ model เอง
{"role": "assistant", "content": "", "tool_calls": [{"id": "call_1", ...}]}
# คำตอบของเราต่อคำขอนั้น
{"role": "tool", "tool_call_id": "call_1", "content": "42"}
```

สองบรรทัดนี้เป็นคู่กัน ผลลัพธ์ของ tool ไม่มีความหมายในตัวเอง เลข 42 เฉยๆ
ไม่ได้บอกอะไรเลยว่าเป็นผลของอะไร ความหมายทั้งหมดอยู่ในคำขอที่มาก่อนมัน

**ทำไมถึงสำคัญกว่าที่คิด** เพราะข้อเท็จจริงจากบทที่ 1 ที่ว่า model ไม่มี
ความจำ แปลว่ามันไม่ได้ "จำ" ว่าเคยขอ tool ไป มันต้องอ่านเจอในบทสนทนา
ถ้าคุณตัดคำขอทิ้ง คำขอนั้นไม่เคยเกิดขึ้นในสายตาของมัน และ API เองก็จะปฏิเสธ
คำขอครั้งถัดไปด้วย เพราะทุก tool result ต้องมี tool call คู่กัน กฎนี้คือ
หัวใจของบทที่ 4

## 4. leaf กับ subsystem คือเส้นแบ่งที่อธิบายทุกอย่าง

ถ้า loop ไม่เคยเปลี่ยนตอนเพิ่ม tool แต่เคยเปลี่ยนตอนเพิ่ม permission
sessions context management usage และ cancellation แล้วอะไรคือความต่าง

ความต่างมีข้อเดียว คือของใหม่นั้นต้องเห็นอะไร

**leaf (ใบ คือของที่ต่ออยู่ปลายสุดและไม่ต้องรู้จักแกน) ต้องการแค่ argument
ของตัวเอง แล้วคืนค่ากลับ** `read_file` ต้องการพาธ `grep_files` ต้องการ
pattern และ glob `run_shell` ต้องการคำสั่ง ไม่มีตัวไหนต้องรู้ว่ามีบทสนทนา
อยู่ ผ่านมากี่รอบแล้ว งบเหลือเท่าไหร่ หรือ model พูดอะไรไปล่าสุด มันรับ
input แล้วคืน string สัญญาแบบนี้มีอยู่แล้วตั้งแต่บทที่ 03 tool ตัวใหม่จึงเป็น
แค่รายการใหม่ใน dictionary กับ schema ใหม่ใน list มันไม่มีที่ให้แตะ loop
เพราะมันไม่เคยรู้ด้วยซ้ำว่า loop มีอยู่

นี่คือเหตุผลที่ MCP tool กับ subagent เข้ามาได้โดยไม่ต้องสู้อะไรเลย MCP tool
คือฟังก์ชันที่เขียน JSON ลงท่อแล้วอ่าน JSON กลับมา subagent คือฟังก์ชันที่
รัน agent อีกตัว ทั้งสองอย่างคือโค้ด Python อะไรก็ได้ที่อยู่หลังสัญญาเดิม
และสัญญานั้นไม่เคยสนใจว่าฟังก์ชันข้างในทำอะไร

**subsystem ต้องสังเกตหรือแทรกสิ่งที่ loop เป็นเจ้าของ ในจังหวะที่มีแต่ loop
เท่านั้นที่ควบคุมได้** permission ต้องทำงานในช่องว่างระหว่างที่ model ขอ
กับที่การเรียกเกิดขึ้น และไม่มีอะไรนอก loop ที่ยืนอยู่ในช่องว่างนั้นได้
session ต้องเห็นทุกข้อความในวินาทีที่มันถูกสร้าง ซึ่งเป็นคนละโปรแกรมกับการ
เขียนไฟล์ตอนจบและแย่กว่า context management ต้องแก้สิ่งที่จะส่งหลังจาก list
ถูกประกอบแล้วแต่ก่อนที่มันจะออกไป cancellation ต้องถูกอ่านระหว่างรอบ
usage ต้องถูกบวกหลังผู้ให้บริการรายงาน

ห้าอย่างนั้นทำจากข้างนอกไม่ได้ แต่ละอย่างจึงต้องการ seam (ตะเข็บ คือจุดต่อ
ที่ออกแบบไว้ให้ของอื่นเสียบเข้ามาได้) ใน `run` นั่นคือความต่างทั้งหมด
ไม่ใช่ความสำคัญ ไม่ใช่ขนาด ไม่ใช่ความยากของโค้ด แค่ว่าของใหม่ต้องเข้าถึง
จังหวะส่วนตัวของเครื่องยนต์หรือไม่

### คำถามข้อเดียวที่ใช้แยกได้

**ของชิ้นนี้ต้องเห็น state ที่แกนเป็นเจ้าของ ในจังหวะที่แกนเป็นคนเลือก หรือไม่**

ถ้าไม่ มันคือ leaf ให้มันไปอยู่หลังสัญญาที่มีอยู่แล้ว และห้ามให้แกนรู้จัก
ชื่อของมัน ถ้าคุณพบว่าตัวเองกำลังเขียน `if` ที่เอ่ยชื่อของใหม่ในแกน แปลว่า
คุณจัดประเภท leaf ผิด

ถ้าใช่ มันคือ subsystem และต้องมี seam ให้มัน ออกแบบ seam ให้ทั่วไปไว้
อย่าออกแบบให้ตรงกับฟีเจอร์ที่เป็นต้นเหตุ เพราะนั่นคือสิ่งที่หยุดไม่ให้จำนวน
seam โตตามจำนวนฟีเจอร์ `on_message` เป็นฟังก์ชันรับหนึ่ง argument จึงรับใช้
ไฟล์ session เทสที่ append ลง list และ socket ได้เหมือนกันหมด
`permissions.check` คืน boolean จึงเขียนตัวปลอมที่ปฏิเสธทุกอย่างมาใส่ใน
การรันจริงได้ `fit_to_budget` คืน list ใหม่ การตัดจึงไม่มีทางทำลายบันทึกต้นฉบับ

### สิ่งที่เกิดขึ้นถ้าจัดประเภทผิด

มันเริ่มอย่างไร้พิษภัย tool ที่รัน shell ต้องถามผู้ใช้ก่อน คุณจึงตัดสินใจว่า
loop ควรจัดการ เพราะ loop เป็นเจ้าของ terminal ตอนนี้ loop มี
`if call["name"] == "run_shell"` อยู่ข้างใน แล้ว `read_file` ต้องตัด output
ซึ่งฟังดูเป็นเรื่องทั่วไป เลยเข้าไปอยู่ใน loop ด้วย แล้ว `edit_file` บางที
พังในแบบที่ model ควรลองใหม่ loop จึงงอกกิ่งที่รู้จักข้อความ error ของ tool
ตัวนั้นโดยเฉพาะ

สี่ tool ให้หลัง loop ยาวสองร้อยบรรทัด ทุก tool มีเคสพิเศษอยู่ในนั้น
และไฟล์ที่คุณไม่กล้าแตะคือไฟล์เดียวที่ทุกฟีเจอร์ต้องวิ่งผ่าน การเพิ่ม tool
ตัวที่ห้าแปลว่าต้องแก้โค้ดที่อันตรายที่สุดในโปรแกรม และการแก้ทุกครั้ง
เสี่ยงกับ tool สี่ตัวที่ทำงานอยู่แล้ว

ทั้งสองแบบรัน agent ตัวเดียวกันได้ในวันแรก มันแยกทางกันในวันที่สามสิบ

### เส้นแบ่งเดียวกันนี้อยู่ทุกที่

- **web framework** การเพิ่ม route ไม่เคยแก้ dispatcher เพราะ handler รับ
  request แล้วคืน response ส่วนการเพิ่ม authentication การ log request
  rate limiting หรือ tracing ต้องแก้ เพราะแต่ละอย่างต้องนั่งอยู่ระหว่าง
  dispatcher กับ handler คำตอบของทุก framework ที่โตแล้วคือ middleware
  ซึ่งก็คือ `on_message` และ `permissions.check` ในชื่ออื่น
- **build tool** การเพิ่ม task คือข้อมูล การเพิ่ม cache การรันขนาน
  หรือแถบแสดงความคืบหน้า แตะ scheduler เพราะต้องรู้ว่า task เริ่มและจบเมื่อไหร่
- **database client** การเพิ่ม query คือข้อมูล การเพิ่ม connection pool
  การ retry หรือการจับเวลา query คือ subsystem เพราะต้องการจังหวะก่อนและ
  หลังการยิงออกสาย
- **game engine** การเพิ่ม entity คือข้อมูล การเพิ่มการหยุดชั่วคราว การเล่นซ้ำ
  หรือ seed ที่ให้ผลเหมือนเดิมทุกครั้ง แตะลูปเฟรม

## 5. max_turns ไม่ได้แก้ปัญหาการวนไม่รู้จบ

`max_turns` (จำนวนรอบสูงสุด) คือเพดานที่ทำให้ agent หยุดแทนที่จะรันตลอดกาล

```python
        for _ in range(self.max_turns):
            ...
        raise RuntimeError(f"agent stopped after max turns ({self.max_turns})")
```

**มันคืออะไร** ตัวนับที่รับประกันว่าโปรแกรมจะจบ

**ทำไมต้องมี** เพราะไม่มีอะไรรับประกันว่า model จะเลิกขอ tool มันอาจขอไป
เรื่อยๆ และถ้าไม่มีเพดาน คุณจะรู้ตัวตอนเห็นบิล

**ทำไมมันไม่พอ** เพราะตัวนับนับเป็นแต่ไม่ได้คิด model ที่ติดอยู่ในลูป
สามารถใช้ทุกรอบที่มีไปกับการเรียก tool เดิมด้วย argument ที่ต่างกันนิดเดียว
เช่นเติมช่องว่างท้ายบรรทัด หรือเปลี่ยนตัวพิมพ์ใหญ่เป็นเล็ก ทุกรอบเสียเงิน
และเมื่อครบเพดานคุณได้ exception ที่บอกว่าหมดรอบ ไม่ได้บอกว่าเกิดอะไรขึ้น
สิ่งที่คุณจ่ายไปคือค่าไฟของการวนอยู่กับที่สิบรอบ

ทางแก้จริงคือดูว่ามีความคืบหน้าหรือไม่ วิธีของหลักสูตรนี้คือทำ fingerprint
(ลายนิ้วมือ คือสตริงที่ระบุการเรียกครั้งหนึ่งแบบไม่สนรายละเอียดที่ไม่สำคัญ)
ของทุกการเรียก แล้วดูว่าซ้ำหรือเปล่า

```python
def loose_signature(call: ToolCall) -> str:
    """The same idea, but blind to whitespace and letter case.

    This one is for spotting a model going in circles, not for deciding what
    is allowed. A model that retries with a trailing space added, or with a
    word capitalised, has not changed anything and should not get a fresh
    fingerprint for it. Permission decisions keep using the exact signature,
    because there the difference between two nearly identical commands can
    be the whole point.
    """
    flattened = {
        key: " ".join(str(value).split()).lower() for key, value in call.arguments.items()
    }
    return f"{call.name}({json.dumps(flattened, sort_keys=True)})"
```

## 6. ทำไม v1 รัน tool ทีละตัว

ความพังที่เกิดบ้างไม่เกิดบ้าง ซึ่งเป็นชนิดของบั๊กที่หาที่มายากที่สุด

## 7. loop คายแต่ event ไม่พิมพ์และไม่ถาม

สิ่งสุดท้ายที่ทำให้ loop เดียวรับใช้ทุกที่ได้ คือมันไม่ทำสองอย่าง มันไม่พิมพ์
อะไรลงหน้าจอ และมันไม่ถามอะไรใคร

มันคาย event (เหตุการณ์ คือข้อความบอกว่าเกิดอะไรขึ้น ณ ขณะนั้น) ออกมาอย่างเดียว
คือ `TextDelta` เมื่อมีข้อความมา `ToolCallRequest` ก่อนรัน tool `ToolResult`
เมื่อรันเสร็จ และ `TurnDone` เมื่อจบรอบ ใครอยากวาดหน้าจอก็ไปรับ event
ไปวาดเอง

**ทำไมต้องเป็นแบบนี้** เพราะถ้า loop พิมพ์เอง มันจะรับใช้ CLI ได้ที่เดียว
subagent ที่ไม่มีใครดูอยู่จะพ่นข้อความรกหน้าจอของแม่ และ eval ที่รัน agent
ร้อยรอบจะพ่นข้อความหนึ่งแสนบรรทัด การให้ loop คาย event แล้วให้คนเรียก
ตัดสินใจว่าจะทำอะไรกับมัน คือสิ่งที่ทำให้ CLI subagent และ eval ใช้ loop
ตัวเดียวกันได้โดยไม่แก้ไส้ใน

**ทำไม permission ถึงถูกฉีดเข้ามาแทนที่จะถามเอง** ด้วยเหตุผลเดียวกัน CLI
ฉีดฟังก์ชันที่ถามคนจริง eval ฉีดตัวที่อนุญาตทุกอย่าง test ฉีดตัวที่ปฏิเสธ
ทุกอย่าง loop ไม่เคยรู้ว่ามีคีย์บอร์ดอยู่ในโลก
