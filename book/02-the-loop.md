## 1. สี่ขั้นตอนที่เป็นทั้งหมดของ agent

ลบทุกอย่างที่เป็นส่วนประกอบออก แล้วสิ่งที่เหลือคือสี่ขั้นตอนนี้

1. ส่งบทสนทนาทั้งหมดไปถาม model พร้อมรายการ tool ที่มีให้เลือก
2. ถ้าคำตอบเป็นข้อความล้วน จบ คืนข้อความนั้น
3. ถ้าคำตอบคือคำขอเรียก tool ให้รัน tool นั้น แล้วเอาผลลัพธ์ใส่กลับเข้าบทสนทนา
4. กลับไปข้อ 1

มันคือ loop ที่วนจนกว่า model จะเลิกขอ tool และมันต้องเป็น loop เพราะ model ไม่มีทาง
รู้คำตอบจนกว่าเราจะรัน tool ให้ พอมันเห็นผลลัพธ์ มันอาจต้องการ tool อีกตัว การอ่าน
ไฟล์แล้วพบว่าต้องอ่านอีกไฟล์เป็นเรื่องปกติ จำนวนรอบไปกลับจึงไม่มีทางรู้ล่วงหน้า และ
การทำซ้ำที่ไม่รู้จำนวนรอบล่วงหน้าคือนิยามของ loop ภาคพื้นฐานบทที่ 3 มี loop รูปเดียว
กันนี้ในขนาดที่เล็กกว่า คือทายคำ ต่อท้าย แล้วทายอีก

ทำไมไม่ใช่ recursion หรือ state machine หรือ graph recursion ทำงานถูก แต่ทำให้ stack
ลึกขึ้นตามจำนวนรอบโดยไม่ได้อะไรกลับมา และทำให้ traceback ตอนพังอ่านยากขึ้น state
machine กับ graph เหมาะเมื่อมีสถานะหลายแบบที่เปลี่ยนไปมาตามเงื่อนไข แต่ที่นี่มีสอง
สถานะเท่านั้น ยังไม่จบกับจบแล้ว การใส่ machinery ที่รองรับสิบสถานะเพื่อจัดการสอง
สถานะคือการซ่อนความง่ายไว้หลังความซับซ้อน

นี่คือ loop ตัวจริงจาก `src/agentpath/agent.py` ตัดส่วนป้องกันออกเพื่อให้เห็นโครง

```python
    def run(self, user_input: str) -> Iterator:
        self._remember(Message(role="user", content=user_input))
        recent: list[str] = []

        for _ in range(self.max_turns):
            assistant = None
            for event in self.provider.stream(self._to_send(), self.tools.schemas() or None):
                if isinstance(event, TurnDone):
                    assistant = event.message
                else:
                    yield event
            self._remember(assistant)

            if not assistant.tool_calls:
                yield TurnDone(message=assistant)
                return

            for call in assistant.tool_calls:
                yield ToolCallRequest(tool_call=call)
                result = self._run_one(call, recent)
                yield result
                self._remember(
                    Message(role="tool", content=result.content, tool_call_id=call.id)
                )
```

ทุกบรรทัดตรงกับสี่ขั้นตอนข้างบนหนึ่งต่อหนึ่ง

## 2. ทำไม assistant message ที่มี tool_calls ต้องกลับเข้า history

จุดที่คนพลาดบ่อยคือลืมใส่ข้อความของ assistant ที่ขอเรียก tool กลับเข้าไปใน history
แล้วใส่แต่ผลลัพธ์ ผลคือ model เห็นผลลัพธ์ของบางอย่างที่มันไม่รู้ว่าตัวเองเคยขอ

```python
# คำขอของ model ในเสียงของ model เอง
{"role": "assistant", "content": "", "tool_calls": [{"id": "call_1", ...}]}
# คำตอบของเราต่อคำขอนั้น
{"role": "tool", "tool_call_id": "call_1", "content": "42"}
```

สองบรรทัดนี้เป็นคู่กัน ผลลัพธ์ของ tool ไม่มีความหมายในตัวเอง เลข 42 เฉยๆ ไม่ได้บอก
อะไรเลยว่าเป็นผลของอะไร ความหมายทั้งหมดอยู่ในคำขอที่มาก่อนมัน

เรื่องนี้สำคัญกว่าที่คิด เพราะบทที่ 1 บอกว่า model ไม่มีความจำ มันไม่ได้จำว่าเคยขอ
tool ไป มันต้องอ่านเจอในบทสนทนา ถ้าคุณตัดคำขอทิ้ง คำขอนั้นไม่เคยเกิดขึ้นในสายตาของ
มัน และ API เองก็จะปฏิเสธคำขอครั้งถัดไปด้วย เพราะทุก tool result ต้องมี tool call
คู่กัน กฎนี้คือหัวใจของบทที่ 4

## 3. หลักฐานว่า loop แทบไม่ขยับ

ข้อความว่า loop แทบไม่ขยับเป็นคำกล่าวอ้างที่ต้องมีหลักฐาน หลักฐานคือ hash และตัวเลข
รวมคือ `agent.py` ของยี่สิบบทเรียนมีเนื้อไฟล์ต่างกันเก้าแบบ สิ่งที่น่าสนใจไม่ใช่เลข
เก้า แต่คือช่วงที่มันนิ่ง

สี่ hash ตอนเปิดบทคือช่วงแรก ระหว่างบท 06 ถึงบท 09 หลักสูตรเพิ่ม `read_file`
`write_file` `edit_file` `list_files` `run_shell` `glob_files` `grep_files` พร้อมกับ

การถามยืนยันจากคน timeout ของ subprocess และเพดานผลลัพธ์อีกสามตัว hash ไม่ขยับ

## 4. leaf กับ subsystem คือเส้นแบ่งที่อธิบายทุกอย่าง

ถ้า loop ไม่เคยเปลี่ยนตอนเพิ่ม tool แต่เคยเปลี่ยนตอนเพิ่ม permission sessions
context management usage และ cancellation แล้วอะไรคือความต่าง

ความต่างมีข้อเดียว ของใหม่นั้นต้องเห็นอะไร

leaf (ใบ คือของที่ต่ออยู่ปลายสุดและไม่ต้องรู้จักแกน) ต้องการแค่ argument ของตัวเอง
แล้วคืนค่ากลับ `read_file` ต้องการพาธ `grep_files` ต้องการ pattern และ glob
`run_shell` ต้องการคำสั่ง ไม่มีตัวไหนต้องรู้ว่ามีบทสนทนาอยู่ ผ่านมากี่รอบแล้ว งบ
เหลือเท่าไหร่ หรือ model พูดอะไรไปล่าสุด มันรับ input แล้วคืน string

สัญญาแบบนั้นมีอยู่แล้วตั้งแต่บทที่ 03 tool ตัวใหม่จึงเป็นแค่รายการใหม่ใน dictionary
กับ schema ใหม่ใน list มันไม่มีที่ให้แตะ loop เพราะมันไม่เคยรู้ด้วยซ้ำว่า loop มีอยู่

นี่คือเหตุผลที่ MCP tool กับ subagent เข้ามาได้โดยไม่ต้องสู้อะไรเลย MCP tool คือ
ฟังก์ชันที่เขียน JSON ลงท่อแล้วอ่าน JSON กลับมา subagent คือฟังก์ชันที่รัน agent อีก
ตัว ทั้งสองอย่างคือโค้ด Python อะไรก็ได้ที่อยู่หลังสัญญาเดิม และสัญญานั้นไม่เคย
สนใจว่าฟังก์ชันข้างในทำอะไร

subsystem ต่างออกไป มันต้องสังเกตหรือแทรกสิ่งที่ loop เป็นเจ้าของ ในจังหวะที่มีแต่
loop เท่านั้นที่ควบคุมได้ permission ต้องทำงานในช่องว่างระหว่างที่ model ขอกับที่การ
เรียกเกิดขึ้น และไม่มีอะไรนอก loop ที่ยืนอยู่ในช่องว่างนั้นได้

อีกสี่ตัวต้องการจังหวะแบบเดียวกัน คนละจังหวะกันไป session ต้องเห็นทุกข้อความใน
วินาทีที่มันถูกสร้าง ซึ่งเป็นคนละโปรแกรมกับการเขียนไฟล์ตอนจบและแย่กว่า context
management ต้องแก้สิ่งที่จะส่งหลังจาก list ถูกประกอบแล้วแต่ก่อนที่มันจะออกไป
cancellation ต้องถูกอ่านระหว่างรอบ usage ต้องถูกบวกหลังผู้ให้บริการรายงาน

ห้าอย่างนั้นทำจากข้างนอกไม่ได้ แต่ละอย่างจึงต้องการ seam (ตะเข็บ คือจุดต่อที่ออกแบบ
ไว้ให้ของอื่นเสียบเข้ามาได้) ใน `run` นั่นคือความต่างทั้งหมด ไม่ใช่ความสำคัญ ไม่ใช่
ขนาด ไม่ใช่ความยากของโค้ด แค่ว่าของใหม่ต้องเข้าถึงจังหวะส่วนตัวของเครื่องยนต์หรือไม่

### คำถามข้อเดียวที่ใช้แยกได้

**ของชิ้นนี้ต้องเห็น state ที่แกนเป็นเจ้าของ ในจังหวะที่แกนเป็นคนเลือก หรือไม่**

ถ้าไม่ มันคือ leaf ให้มันไปอยู่หลังสัญญาที่มีอยู่แล้ว และห้ามให้แกนรู้จักชื่อของมัน
ถ้าคุณพบว่าตัวเองกำลังเขียน `if` ที่เอ่ยชื่อของใหม่ในแกน แปลว่าคุณจัดประเภท leaf ผิด

ถ้าใช่ มันคือ subsystem และต้องมี seam ให้มัน ออกแบบ seam ให้ทั่วไปไว้ อย่าออกแบบ
ให้ตรงกับฟีเจอร์ที่เป็นต้นเหตุ เพราะนั่นคือสิ่งที่หยุดไม่ให้จำนวน seam โตตามจำนวน
ฟีเจอร์

seam ที่ทั่วไปพอมีอยู่สามตัวในโปรเจกต์นี้ `on_message` เป็นฟังก์ชันรับหนึ่ง argument
จึงรับใช้ไฟล์ session test ที่ append ลง list และ socket ได้เหมือนกันหมด
`permissions.check` คืน boolean จึงเขียนตัวปลอมที่ปฏิเสธทุกอย่างมาใส่ในการรันจริงได้
`fit_to_budget` คืน list ใหม่ การตัดจึงไม่มีทางทำลายบันทึกต้นฉบับ

### สิ่งที่เกิดขึ้นถ้าจัดประเภทผิด

มันเริ่มอย่างไร้พิษภัย tool ที่รัน shell ต้องถามผู้ใช้ก่อน คุณจึงตัดสินใจว่า loop ควร
จัดการ เพราะ loop เป็นเจ้าของ terminal ตอนนี้ loop มี `if call["name"] == "run_shell"`
อยู่ข้างใน แล้ว `read_file` ต้องตัด output ซึ่งฟังดูเป็นเรื่องทั่วไป เลยเข้าไปอยู่ใน
loop ด้วย แล้ว `edit_file` บางทีพังในแบบที่ model ควรลองใหม่ loop จึงงอกกิ่งที่รู้จัก
ข้อความ error ของ tool ตัวนั้นโดยเฉพาะ

สี่ tool ให้หลัง loop ยาวสองร้อยบรรทัด ทุก tool มีเคสพิเศษอยู่ในนั้น และไฟล์ที่คุณไม่
กล้าแตะ คือไฟล์เดียวที่ทุกฟีเจอร์ต้องวิ่งผ่าน การเพิ่ม tool ตัวที่ห้าแปลว่าต้องแก้โค้ด
ที่อันตรายที่สุดในโปรแกรม และการแก้ทุกครั้งเสี่ยงกับ tool สี่ตัวที่ทำงานอยู่แล้ว

ทั้งสองแบบรัน agent ตัวเดียวกันได้ในวันแรก มันแยกทางกันในวันที่สามสิบ

### เส้นแบ่งเดียวกันนี้อยู่ทุกที่

เส้นแบ่งนี้ไม่ได้เป็นของ agent โดยเฉพาะ มันโผล่ในซอฟต์แวร์ที่คุณใช้อยู่แล้วทุกวัน
และโผล่ด้วยรูปเดิมทุกครั้ง

- ใน web framework การเพิ่ม route ไม่เคยแก้ dispatcher เพราะ handler รับ request แล้ว
  คืน response ส่วนการเพิ่ม authentication การ log request rate limiting หรือ tracing
  ต้องแก้ เพราะแต่ละอย่างต้องนั่งอยู่ระหว่าง dispatcher กับ handler คำตอบของทุก
  framework ที่โตแล้วคือ middleware ซึ่งก็คือ `on_message` และ `permissions.check`
  ในชื่ออื่น

- ใน build tool การเพิ่ม task คือข้อมูล การเพิ่ม cache การรันขนาน หรือแถบแสดงความ

```python
def loose_signature(call: ToolCall) -> str:
    """The same idea, but forgiving about the edges of a value.

    This one is for spotting a model going in circles, not for deciding
    what is allowed. A model that retries with a trailing space added has
    changed nothing and should not get a fresh fingerprint for it. A model
    that changes a letter's case has, because a case sensitive search for
    Error and a search for error are different searches. Permission
    decisions keep using the exact signature, because there the difference
    between two nearly identical commands can be the whole point.
    """
    # Trailing and leading space only. An earlier version also folded case
    # and collapsed interior spaces, which made three genuinely different
    # searches look identical. A model widening a case sensitive pattern from
    # Error to ERROR to error is doing the right thing, and it was being told
    # it was going in circles and then stopped.
    flattened = {key: str(value).strip() for key, value in call.arguments.items()}
    return f"{call.name}({json.dumps(flattened, sort_keys=True)})"
```

สังเกตว่า fingerprint มองข้ามแค่ช่องว่างหัวท้าย ไม่ได้มองข้ามตัวพิมพ์ เวอร์ชันแรกมอง
ข้ามตัวพิมพ์ด้วย และมันสร้าง bug จริง model ที่ค่อยๆ ขยายการค้นหาจาก Error เป็น
ERROR เป็น error กำลังทำสิ่งที่ถูกต้อง เพราะการค้นหาแบบ case sensitive สามครั้งนั้น
เป็นคนละการค้นหากันจริงๆ แต่ fingerprint ที่มองข้ามตัวพิมพ์เห็นทั้งสามเป็นการเรียก
เดียวกัน เตือนว่าวนอยู่กับที่ แล้วหยุดงานที่กำลังเดินหน้า บรรทัดที่ตัดสินว่าอะไรนับว่า
ซ้ำจึงต้องระวังทั้งสองทิศ หลวมไปก็ปล่อยการวนจริงหลุด แน่นไปก็หยุดงานจริง

## 7. loop คายแต่ event ไม่พิมพ์และไม่ถาม

สิ่งสุดท้ายที่ทำให้ loop เดียวรับใช้ทุกที่ได้ คือมันไม่ทำสองอย่าง มันไม่พิมพ์อะไรลง
หน้าจอ และมันไม่ถามอะไรใคร

มันคาย event (เหตุการณ์ คือข้อความบอกว่าเกิดอะไรขึ้น ณ ขณะนั้น) ออกมาอย่างเดียว คือ
`TextDelta` เมื่อมีข้อความมา `ToolCallRequest` ก่อนรัน tool `ToolResult` เมื่อรันเสร็จ
และ `TurnDone` เมื่อจบรอบ ใครอยากวาดหน้าจอก็ไปรับ event ไปวาดเอง

ถ้า loop พิมพ์เอง มันจะรับใช้ CLI ได้ที่เดียว subagent ที่ไม่มีใครดูอยู่จะพ่นข้อความรก
หน้าจอของแม่ และ eval ที่รัน agent ร้อยรอบจะพ่นข้อความหนึ่งแสนบรรทัด การให้ loop คาย
event แล้วให้คนเรียกตัดสินใจว่าจะทำอะไรกับมัน คือสิ่งที่ทำให้ CLI subagent และ eval
ใช้ loop ตัวเดียวกันได้โดยไม่แก้ไส้ใน

permission ถูกฉีดเข้ามาแทนที่จะถามเอง ด้วยเหตุผลเดียวกัน CLI ฉีดฟังก์ชันที่ถามคนจริง
eval ฉีดตัวที่อนุญาตทุกอย่าง test ฉีดตัวที่ปฏิเสธทุกอย่าง loop ไม่เคยรู้ว่ามีคีย์บอร์ด
