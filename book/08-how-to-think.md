# บทที่ 8 กรอบคิดเจ็ดคำถามก่อนเขียนโค้ดบรรทัดแรก

คนใช้เวลาสามสัปดาห์สร้าง vector database (ฐานข้อมูลเวกเตอร์ คือที่เก็บข้อความในรูป
ตัวเลขเพื่อค้นด้วยความหมาย) ให้ข้อมูลที่ใส่ context ได้หมดตั้งแต่แรก คนสร้าง agent loop
สำหรับงานที่มีห้าขั้นตอนตายตัว คนออกแบบระบบ permission (สิทธิ์ คือกลไกที่ตัดสินว่าการ
กระทำไหนทำได้) หลังจากที่ tool ที่ลบข้อมูลถูกเขียนไปแล้ว

สามเรื่องนี้เกิดกับคนที่เข้าใจกลไกครบทุกข้อ ปัญหาที่พบบ่อยที่สุดในโปรเจกต์ agent
(เอเจนต์ คือโปรแกรมที่ให้ model ตัดสินใจว่าจะเรียกเครื่องมืออะไรต่อ) ไม่ใช่โค้ดผิด แต่คือ
โค้ดที่ถูกต้องสำหรับปัญหาที่ไม่มีอยู่ เจ็ดบทที่ผ่านมาอธิบายว่ากลไกทำงานยังไง ภาคนี้
อธิบายว่าจะตัดสินใจยังไง และคนที่เข้าใจกลไกครบทุกข้อยังสร้างของผิดได้ ถ้าเขาไม่เคยถาม
ว่าควรสร้างอะไร

บทนี้เสนอคำถามเจ็ดข้อที่ต้องตอบก่อน คำตอบของแต่ละข้อไม่ใช่ความเห็น มันเป็นข้อจำกัดที่
บีบรูปร่างของระบบ และบางคำตอบแปลว่าให้เลิกทำ ผลของมันคือเอกสารหนึ่งหน้าที่หัวข้อ 9
แสดงให้ดู ในนั้นมีรูปร่างของระบบหนึ่งบรรทัด ความเสียหายสูงสุดที่แยกเป็นสามชั้น ตาราง
tool หกคอลัมน์ รายการ tool ที่คุณจงใจไม่ใส่พร้อมเหตุผล และ eval สามถึงห้าข้อที่อย่าง
น้อยหนึ่งข้อทดสอบว่าระบบปฏิเสธเป็น

คุณไม่จำเป็นต้องอ่านเจ็ดข้อนี้เรียงหน้าจนจบในรอบเดียว ข้อ 2 กับข้อ 5 ตอบคู่กันเสมอ
คุณจึงกระโดดจากข้อ 2 ไปข้อ 5 แล้วย้อนกลับมาได้ และหัวข้อ 8 ที่อธิบายว่าทำไมลำดับเป็น
แบบนี้ ข้ามไปก่อนได้เต็มที่ แล้วค่อยกลับมาอ่านตอนที่คุณตอบครบเจ็ดข้อแล้ว

## 0. เจ็ดข้อ และสิ่งที่แต่ละข้อตัดสิน

| ข้อ | คำถาม | สิ่งที่คำตอบตัดสิน |
| --- | --- | --- |
| 1 | งานนี้ต้องใช้ agent จริงหรือ | รูปร่างของโปรแกรมทั้งโปรแกรม |
| 2 | ถ้าทำผิดแล้วเสียหายแค่ไหน | อะไรเป็น tool ได้ และอะไรห้ามเป็น |
| 3 | ใครดูอยู่ตอนมันทำงาน | รูปแบบของ permission และการรายงานผล |
| 4 | ข้อมูลอยู่ที่ไหนและอยู่ในรูปแบบไหน | โครงสร้างพื้นฐานที่ต้องสร้าง |
| 5 | tool ที่ต้องมีคืออะไร อันไหนอันตราย | ขอบเขตความสามารถทั้งหมดของระบบ |
| 6 | จะรู้ได้ยังไงว่ามันทำงานถูก | สิ่งที่ทำให้ทุกข้อข้างบนตรวจสอบได้ |
| 7 | ถ้าพังกลางทางจะเกิดอะไรขึ้น | สิ่งที่ต้องเก็บลงดิสก์และเมื่อไหร่ |

ลำดับไม่ใช่เรื่องบังเอิญ และหัวข้อสุดท้ายของบทนี้อธิบายว่าทำไม

### 0.1 คำว่า agent เก่ากว่า LLM สี่สิบปี และกรอบเก่ายังใช้ได้

ตำรา AI ที่ใช้สอนกันมาตั้งแต่ปี 1995 นิยาม agent ว่าคือสิ่งที่รับรู้สภาพแวดล้อมผ่าน
sensor แล้วกระทำต่อมันผ่าน actuator ในภาษาของหนังสือเล่มนี้ sensor คือผลลัพธ์ของ tool
ที่กลับเข้ามาใน context และ actuator คือ tool ที่ถูกเรียก loop ในบทที่ 2 คือวงจรรับรู้แล้ว
กระทำของตำราเล่มนั้นเป๊ะๆ สิ่งที่ LLM เปลี่ยนคือส่วนตรงกลางที่ตัดสินใจ ไม่ใช่รูปร่างของวงจร

ตำราเล่มเดียวกันบอกให้ถามคุณสมบัติของสภาพแวดล้อมก่อนออกแบบ agent และคำถามพวกนั้น
คือคำถามเจ็ดข้อข้างบนในอีกภาษาหนึ่ง มองเห็นได้ทั้งหมดหรือบางส่วน คือข้อ 4 ว่าข้อมูลอยู่
ที่ไหน agent ที่เห็นทั้ง repo กับ agent ที่เห็นเฉพาะไฟล์ที่ค้นเจอคือคนละสัตว์ กระทำแล้วผล
แน่นอนหรือสุ่ม คือข้อ 7 ว่าพังกลางทางแล้วเกิดอะไร เพราะการเขียนไฟล์ทำซ้ำได้ ส่วนการส่ง
อีเมลไม่ได้ แต่ละครั้งจบในตัวหรือต่อเนื่อง คือข้อ 1 ว่าต้องใช้ loop จริงไหม งานที่จบในรอบ
เดียวไม่ต้องการ agent สภาพแวดล้อมนิ่งหรือเปลี่ยนระหว่างที่คิด คือกับดักในบทที่ 15 ที่แม่
ถือไฟล์เวอร์ชันเก่าขณะที่ลูกแก้มันไปแล้ว

และตำราเล่มนั้นมีคำเตือนหนึ่งข้อที่บทนี้ยืมมาทั้งข้อ agent ที่มีเหตุผลคือ agent ที่ทำสิ่งที่ดี
ที่สุดตามเป้าที่ได้รับ ปัญหาคือเป้าที่เขียนได้ครบไม่มีจริง agent ที่ถูกสั่งให้ทำ test ผ่านจะ
แก้ test ให้ผ่านแทนที่จะแก้โค้ด ไม่ใช่เพราะมันโง่ แต่เพราะนั่นคือทางที่สั้นที่สุดไปสู่เป้าที่
เขียนไว้ ตำราเรียกช่องว่างระหว่างสิ่งที่คุณต้องการกับสิ่งที่คุณเขียนว่า value alignment
(การจัดวางคุณค่าให้ตรง คือปัญหาที่เป้าซึ่งเขียนให้เครื่องไม่เท่ากับสิ่งที่คนต้องการจริง) และ
ข้อ 2 กับข้อ 6 ของบทนี้คือวิธีอยู่กับช่องว่างนั้นในทางปฏิบัติ จำกัดความเสียหายของการตี
ความผิด และวัดจากโลกแทนที่จะวัดจากคำพูดของ agent ว่ามันทำสำเร็จครับ

## 1. งานนี้ต้องใช้ agent จริงหรือ

ถามข้อนี้ก่อนเพราะ agent เป็นเครื่องมือที่แพงที่สุดในกล่อง และคนหยิบมันมาใช้เพราะมัน
น่าตื่นเต้น ไม่ใช่เพราะปัญหาเรียกร้อง

งานหนึ่งงานมีสามรูปร่างที่เป็นไปได้ และรูปร่างที่คนเลือกผิดบ่อยที่สุดคือรูปที่สาม

| รูปร่าง | เมื่อไหร่ | ราคาต่อการทำงานหนึ่งครั้ง |
| --- | --- | --- |
| โปรแกรมธรรมดา ไม่มี model | ขั้นตอนแน่นอน และตัดสินใจจากข้อมูลที่มีโครงสร้าง | ศูนย์ |
| โปรแกรมธรรมดาที่เรียก model หนึ่งครั้ง | ขั้นตอนแน่นอน แต่มีจุดหนึ่งที่ต้องเข้าใจภาษา | หนึ่งการเรียก |
| agent loop | ไม่รู้ล่วงหน้าว่าต้องทำกี่ขั้นตอนและขั้นไหนบ้าง | หลายการเรียก และโตแบบกำลังสองตามบทที่ 1 |

วิธีทดสอบที่ใช้ได้จริงคือวาด flowchart (ผังงาน คือแผนภาพที่แสดงลำดับขั้นตอนและจุด
แตกแขนง) ของงานนั้นบนกระดาษ ถ้าคุณวาดจบและทุกจุดแตกแขนงตัดสินด้วยเงื่อนไขที่เขียนเป็น
`if` ได้ คุณเพิ่งเขียนโปรแกรมเสร็จแล้ว ไม่ต้องมี agent ถ้าคุณวาดไม่จบ เพราะขั้นตอน
ถัดไปขึ้นกับสิ่งที่อ่านเจอในขั้นก่อนหน้า และคุณไม่รู้ล่วงหน้าว่าจะเจออะไร นั่นคือจุดที่
agent มีค่า จากบทที่ 2 การทำซ้ำที่ไม่รู้จำนวนรอบล่วงหน้าคือนิยามของ loop และนั่นคือสิ่ง
เดียวที่ agent ให้คุณ

ถ้าคุณเขียนขั้นตอนออกมาเป็นข้อๆ ได้ครบ และแต่ละข้อทำอย่างเดิมทุกครั้ง ให้หยุดแล้วเขียน
โปรแกรมธรรมดา เหตุผลไม่ใช่เรื่องความบริสุทธิ์ทางวิศวกรรม แต่เป็นสามข้อที่วัดได้

- โปรแกรมธรรมดาให้ผลเดิมทุกครั้งกับ input เดิม agent ไม่ให้ ซึ่งแปลว่าคุณทดสอบด้วย
  assertion ตรงๆ ไม่ได้ ต้องใช้ eval ตามบทที่ 7 ซึ่งแพงกว่ามาก
- โปรแกรมธรรมดาไม่มีพื้นผิวให้ prompt injection ตามบทที่ 5 เพราะไม่มี model ให้แทรก
  คำสั่งใส่
- โปรแกรมธรรมดาไม่ต้องมีระบบ permission เพราะรายการสิ่งที่มันทำได้ถูกเขียนไว้ในโค้ด
  แล้ว ไม่ได้ถูกเลือกตอนรัน

ถ้าคำตอบคือรูปที่สอง คือโปรแกรมธรรมดาที่เรียก model หนึ่งครั้ง คุณไม่ต้องมี loop ไม่
ต้องมี tool ไม่ต้องมี context management และไม่ต้องมี permission ทั้งระบบ สิ่งที่คุณต้อง
มีคือ prompt หนึ่งอัน การเรียกหนึ่งครั้ง และการตรวจว่าผลลัพธ์อยู่ในรูปที่คาดไว้ จากบทที่
3 การบังคับรูปร่างคำตอบใช้กลไกเดียวกับ tool calling คุณจึงนิยาม tool หนึ่งตัวแล้วไม่รัน
มัน เท่านั้นพอ

ระหว่างรูปที่สองกับรูปที่สาม มีทางกลางที่คนมองข้าม คือ pipeline ที่แต่ละขั้นเรียก model
หนึ่งครั้ง ลำดับขั้นถูกเขียนไว้ในโค้ด ไม่ใช่ให้ model เลือก วิธีนี้ได้ความสามารถทางภาษา
โดยไม่เสียความแน่นอนของลำดับ และมันเหมาะกับงานจำนวนมากที่คนเผลอสร้างเป็น agent

## 2. ถ้าทำผิดแล้วเสียหายแค่ไหน

คำตอบข้อนี้กำหนดว่าอะไรควรถามและอะไรควรห้ามไปเลย และสองอย่างนี้เป็นคนละเรื่องกัน
คนส่วนใหญ่ออกแบบ permission ด้วยการไล่ดู tool ที่เขียนไว้แล้วว่าอันไหนน่ากลัว ซึ่งเป็น
การถามช้าไปหนึ่งขั้น เพราะถึงตอนนั้น tool ที่ไม่ควรมีอยู่ก็มีอยู่แล้ว

ให้แบ่งผลของความผิดพลาดเป็นสามชั้น

| ชั้น | นิยาม | สิ่งที่ควรทำ |
| --- | --- | --- |
| กู้คืนได้เอง | โปรแกรมย้อนกลับได้โดยไม่ต้องมีคน | ให้เป็น tool ที่ `safe` ได้ |
| กู้คืนได้แต่ต้องมีคนทำ | ต้องมีคนกดปุ่ม กู้ backup หรือโทรหาใคร | ต้องถามก่อนทำ และต้องบันทึกว่าทำอะไรไป |
| กู้คืนไม่ได้ | เงินออกไปแล้ว ข้อความส่งไปแล้ว ข้อมูลหายถาวร | ห้ามเป็น tool ของ agent |

เส้นที่สามคือเส้นที่สำคัญที่สุด และเหตุผลมาจากบทที่ 5 โดยตรง กลไกป้องกันทุกชั้นที่เรามี
ตั้งอยู่บนช่องว่างระหว่างคำขอกับการรัน ช่องว่างนั้นทำงานได้ดีกับสิ่งที่ย้อนกลับได้ แต่
กับสิ่งที่ย้อนกลับไม่ได้ ความผิดพลาดครั้งเดียวในหมื่นครั้งก็ยังเป็นความผิดพลาดที่แก้ไม่ได้
และ agent จะทำงานเกินหมื่นครั้งในเวลาไม่นาน

วิธีที่ถูกกับการกระทำที่ย้อนกลับไม่ได้ คือให้ agent เตรียมของ แล้วให้คนเป็นคนกด ต่างกัน
ตรงที่ agent ผลิต artifact (ผลผลิต คือไฟล์หรือข้อมูลที่ตรวจดูได้ก่อนถูกใช้) แทนที่จะ
ผลิตผลลัพธ์ ตัวอย่างคือ agent ที่เขียนอีเมลลง draft แทนที่จะส่ง และ agent ที่เขียนไฟล์
migration แทนที่จะรันมัน ซึ่งเป็นกรณีที่บทที่ 10 จะเดินให้ดูทั้งกรณี

ถ้าคำตอบคือไม่รู้ แปลว่าคุณยังไม่รู้ว่า tool จะแตะอะไรบ้าง ให้ข้ามไปตอบข้อ 5 ก่อนแล้ว
กลับมา สองข้อนี้ตอบคู่กันเสมอ และถ้าคำตอบคือเสียหายมากแต่โอกาสเกิดน้อย ให้ระวัง เพราะ
ประโยคนั้นเป็นสูตรมาตรฐานของการยอมรับความเสี่ยงโดยไม่ได้คำนวณ สิ่งที่ต้องคำนวณคือ
ความเสียหายคูณจำนวนครั้งที่ระบบจะทำงานในหนึ่งปี ไม่ใช่ความเสียหายคูณความรู้สึก

คำตอบข้อนี้เขียนตัวเองลงไปในฟิลด์เดียวจากบทที่ 3

```python
    safe: bool = False
```

ค่าเริ่มต้นเป็น `False` เพราะการลืมต้องนำไปสู่คำถาม ไม่ใช่ความเงียบ และเหตุผลที่ฟิลด์นี้
อยู่บน `Tool` ไม่ใช่ในไฟล์ config กลาง คือคนที่เขียน tool คือคนเดียวที่รู้ว่ามันทำลาย
อะไรได้ คำตอบของข้อ 2 จึงไม่ได้ถูกเก็บไว้ในเอกสาร มันถูกเก็บไว้ข้างๆ โค้ดที่มันควบคุม

## 3. ใครเป็นคนดูอยู่ตอนมันทำงาน

ระบบ permission ทั้งระบบในบทที่ 5 ตั้งอยู่บนสมมติฐานเงียบๆ ว่ามีคนอยู่หน้าจอที่พิมพ์
ตอบได้

```python
    answer = self.ask(tool, call)
```

บรรทัดนี้หยุดรอ ถ้าไม่มีใครอยู่ตรงนั้น มันหยุดรอตลอดไป

มีสามสถานการณ์จริง และแต่ละอันเปลี่ยนของคนละอย่าง

| สถานการณ์ | permission | การรายงานผล |
| --- | --- | --- |
| มีคนจ้องหน้าจอ เช่น CLI | ถามได้ตอนนั้น จำคำตอบได้ | stream ทีละ token ตามบทที่ 1 |
| มีคนแต่ไม่ได้จ้อง เช่น chat หรือ LINE | ถามได้แต่คำตอบมาช้า ต้องพักงานไว้ | ส่งผลเป็นก้อนเดียวเมื่อเสร็จ |
| ไม่มีคนเลย เช่น cron หรือ CI | ถามไม่ได้ ต้องตัดสินใจล่วงหน้าทั้งหมด | เขียน log และแจ้งเตือนเมื่อผิดปกติ |

แถวที่สองคือแถวที่คนออกแบบพลาดมากที่สุด เพราะมันดูเหมือนแถวแรก มีคนอยู่จริง เขาตอบ
ได้จริง แต่เขาตอบในอีกสิบนาที และในสิบนาทีนั้น process ที่รัน agent อาจถูกฆ่าไปแล้ว
การถามในสถานการณ์นี้จึงไม่ใช่การเรียกฟังก์ชันที่บล็อก มันคือการหยุดงานไว้ เก็บสถานะ
ลงดิสก์ และเริ่มใหม่จากจุดนั้นเมื่อคำตอบมาถึง ซึ่งเป็นคนละโปรแกรมกันโดยสิ้นเชิง บทที่ 9
เดินเรื่องนี้ทีละขั้น

ถ้าคำตอบข้อนี้คือไม่มีคนดู และคำตอบข้อ 2 คือมีการกระทำที่กู้คืนไม่ได้ ให้หยุด นี่คือการ
ตรวจไขว้ที่สำคัญที่สุดในกรอบทั้งหมด เพราะมันคือสูตรของความเสียหายที่ไม่มีใครเห็นจนกว่า
จะสาย

ในเชิงสถาปัตยกรรม สังเกตว่าบทที่ 2 ออกแบบ loop ให้คายแต่ event และไม่ถามอะไรใคร นั่น
คือสิ่งที่ทำให้คำตอบข้อ 3 เปลี่ยนได้โดยไม่แตะแกน CLI ฉีดฟังก์ชันที่ถามคนจริง eval ฉีดตัว
ที่อนุญาตทุกอย่าง และ webhook ฉีดตัวที่คืนคำตอบจากฐานข้อมูล ถ้า loop ถามเองด้วย
`input()` คำตอบข้อ 3 จะกลายเป็นการเขียนใหม่ทั้งโปรแกรม

## 4. ข้อมูลที่มันต้องใช้อยู่ที่ไหนและอยู่ในรูปแบบไหน

นี่คือข้อที่คนสร้างโครงสร้างพื้นฐานเกินความจำเป็นมากที่สุด คำว่า retrieval (การค้นคืน
คือการหาส่วนของข้อความที่น่าจะตอบคำถามได้) กับคำว่า vector database กลายเป็นคำเดียว
กันในความเข้าใจของคนจำนวนมาก ทั้งที่อย่างแรกคือปัญหา ส่วนอย่างหลังคือหนึ่งในสี่คำตอบ

บทที่ 16 ของหลักสูตรมีขั้นตอนตัดสินใจสี่ข้อ ถามตามลำดับ และหยุดที่ข้อแรกที่ตอบว่าใช่

| คำถาม | ถ้าใช่ ให้ทำ |
| --- | --- |
| ข้อมูลเล็กพอที่จะใส่ context window ไหม | ใส่ไปเลย ไม่ต้องสร้างอะไร |
| ข้อมูลมีโครงสร้าง และคุณรู้ว่ากำลังถามอะไร ไหม | เขียน query เป็น SQL หรือเรียก API |
| มันเป็นข้อความที่ agent เดินหาเองได้ไหม | ให้ glob กับ grep ซึ่งคือบทที่ 09 |
| ไม่เข้าสามข้อแรก | ตอนนี้ vector search ถึงจะคุ้ม |

หยุดที่ข้อแรกที่ตอบว่าใช่ ไม่ใช่เก็บความเห็นทั้งสี่ข้อมาชั่ง เพราะสี่ข้อนี้เรียงตามต้นทุน
ของโครงสร้างที่ต้องสร้างและดูแล ข้อแรกไม่ต้องสร้างอะไรเลย ข้อสองต้องมี schema กับ tool
ที่ยิง query ส่วนข้อสามต้องมี tool สองตัวที่หลักสูตรนี้เขียนไว้แล้ว ข้อสี่คือข้อที่ราคา
อยู่คนละชั้นกับสามข้อแรก มันต้องมี model สำหรับแปลงข้อความเป็นเวกเตอร์ ที่เก็บเวกเตอร์
ขั้นตอน build index ใน pipeline การ deploy การตัดสินใจเรื่องขนาด chunk และแผนว่าจะทำ
ยังไงเมื่อเอกสารเปลี่ยนแล้วเวกเตอร์เก่าใช้ไม่ได้ การเลือกข้อสี่ทั้งที่ข้อสองตอบได้ คือการ
รับภาระทั้งหมดนั้นมาโดยไม่ได้อะไรตอบแทน ภาคพื้นฐานบทที่ 5 สร้างทั้งสองตระกูลของการ
ค้นให้ดูในขนาดเล็ก คือค้นด้วยคำแบบ TF-IDF และค้นด้วยทิศทางแบบ vector

สิ่งที่ต้องระวังคือถามถูกหน่วย คำถามนี้ถามต่อกองข้อมูลหนึ่งกอง ไม่ใช่ต่อโปรเจกต์หนึ่ง
โปรเจกต์ ระบบเดียวมีข้อมูลสามกองที่ตอบคนละข้อได้เป็นเรื่องปกติ และมันคือคำตอบที่ถูก
บทที่ 9 มีตัวอย่างที่ชัด คือบันทึกอาการเป็นตารางจึงใช้ SQL ส่วนบทความสุขภาพเป็นร้อยแก้ว
จึงใช้ retrieval สองกองนี้อยู่ในระบบเดียวกันและต้องไม่ถูกยัดเข้าเครื่องมือเดียวกัน

ถ้าคำตอบคือทุกอย่างเข้าข้อสี่ แปลว่ายังไม่ได้ถามสามข้อแรกจริง ให้กลับไปตอบข้อหนึ่งด้วย
ตัวเลข คือนับตัวอักษรของข้อมูลจริง หารสี่ตามบทที่ 1 แล้วเทียบกับหน้าต่างของ model ที่จะ
ใช้ คนส่วนใหญ่ประหลาดใจว่ามันเล็กกว่าที่คิด

คำตอบข้อนี้ตัดสินว่าครึ่งหนึ่งของงานวิศวกรรมในโปรเจกต์นี้จะอยู่ที่ไหน ถ้าคำตอบคือข้อสี่
งานส่วนใหญ่ของคุณคือ pipeline ของข้อมูล ไม่ใช่ agent ตัว agent จะมีสองร้อยบรรทัด ส่วน
pipeline จะเป็นที่ที่คุณใช้เวลาทั้งหมด การรู้ข้อนี้ตั้งแต่วันแรกเปลี่ยนวิธีวางแผนทั้ง
โปรเจกต์

## 5. tool ที่มันต้องมีคืออะไร และอันไหนอันตราย

รายการ tool คือขอบเขตความสามารถทั้งหมดของระบบ ไม่มากไปกว่านั้นและไม่น้อยไปกว่านั้น
agent ทำสิ่งที่ไม่มีใน tool ไม่ได้ ไม่ว่า system prompt จะสั่งอะไร และ agent ทำทุกอย่างที่
มีใน tool ได้ ไม่ว่า system prompt จะห้ามอะไร

ให้เขียนตารางนี้ให้เสร็จก่อนเขียนโค้ดบรรทัดแรก

| คอลัมน์ | ทำไมต้องมี |
| --- | --- |
| ชื่อ | เป็นสิ่งที่ model เห็นและใช้เลือก |
| ทำอะไร ในหนึ่งประโยค | ถ้าเขียนหนึ่งประโยคไม่ได้ แปลว่ามันทำสองอย่าง |
| อ่านหรือเขียน | เส้นแบ่งแรกของ permission ตามบทที่ 5 |
| คืนอะไรกลับมา | สิ่งที่คืนคือสิ่งที่เข้า context และถูกจ่ายซ้ำทุกรอบ |
| ถ้าเรียกผิดจะเกิดอะไร | คำตอบข้อ 2 ในระดับ tool |
| `safe` | ผลสรุปของสองคอลัมน์ก่อนหน้า |

คอลัมน์ที่คนลืมคือคอลัมน์ที่สี่ เพราะจากบทที่ 1 สิ่งที่ tool คืนมาไม่ได้ถูกอ่านครั้งเดียว
มันอยู่ในบทสนทนาและถูกส่งใหม่ทุกรอบจนจบงาน tool ที่คืนแถวดิบสองร้อยแถวจึงไม่ได้แพง
หนึ่งครั้ง มันแพงทุกครั้งที่เหลือ การออกแบบให้ tool คืนสรุปแทนที่จะคืนของดิบ เป็นการ
ตัดสินใจที่ต้องทำตอนนี้ ไม่ใช่ตอน optimise ทีหลัง เพราะการเปลี่ยนสิ่งที่ tool คืนหลังจาก
มี prompt ที่ปรับจนดีแล้ว แปลว่าต้องปรับใหม่หมด

มีสามคำตอบที่แปลว่าควรหยุด สองอย่างแรกเป็นเรื่องขนาดและความคมของรายการ

- รายการยาวเกินสิบสองตัว จากบทที่ 3 schema ของ tool ทุกตัวเดินทางไปกับทุกคำขอ ก่อน
  ที่ model จะอ่านงานจริงสักตัวอักษร และผลที่หนักกว่าความเปลืองคือ model เลือกผิด
  บ่อยขึ้นเมื่อมีตัวเลือกเยอะ รายการที่ยาวเกินไปทำให้ agent แย่ลง ไม่ใช่แค่แพงขึ้น
- สอง tool ที่คำอธิบายเขียนแล้วแยกกันไม่ออก ให้รวมเป็นตัวเดียว เพราะถ้าคุณแยกไม่ออก
  model ก็แยกไม่ออก

อย่างที่สามหนักกว่าสองอย่างแรก เพราะมันไม่ใช่เรื่องคุณภาพของรายการ แต่เป็นเรื่องว่า
อะไรไม่ควรอยู่ในรายการตั้งแต่ต้น

- มี tool ที่ตกอยู่ในชั้นกู้คืนไม่ได้ของข้อ 2 ให้ลบมันออกจากรายการ ไม่ใช่ทำให้มันถามก่อน
  ความต่างสำคัญ เพราะ tool ที่มีอยู่แต่ถามก่อน จะถูกอนุญาตสักวันหนึ่งโดยคนที่กดโดย
  ไม่อ่าน ส่วน tool ที่ไม่มีอยู่ จะไม่ถูกเรียก

รายการที่ไม่มี คือสิ่งที่ทำให้คำตอบข้อ 2 เป็นจริงแทนที่จะเป็นความหวัง ระบบที่บอกว่าอ่าน
อย่างเดียว แล้วมี tool ที่เขียนไฟล์ได้ ไม่ใช่ระบบที่อ่านอย่างเดียว ส่วนระบบที่ไม่มี tool
ที่เขียนอะไรได้เลย เป็นระบบที่อ่านอย่างเดียวจริง และข้อความนั้นตรวจสอบได้ด้วยการดู
รายการ ไม่ต้องเชื่อใครครับ

## 6. จะรู้ได้ยังไงว่ามันทำงานถูก

บทที่ 7 พิสูจน์แล้วว่าคุณแยกการเปลี่ยนแปลงที่ดีออกจากที่แย่ด้วยการดูไม่ได้ และการเขียน
เกณฑ์ก่อนเขียนโค้ดทำอีกอย่างที่สำคัญกว่านั้น คือมันบังคับให้คุณนิยามว่าความสำเร็จคือ
อะไร ในขณะที่คุณยังเปลี่ยนใจได้ถูก

ให้เขียน eval (การประเมิน คือชุดงานที่รันซ้ำได้พร้อมเกณฑ์ตัดสินผ่านหรือตก) สามถึงห้าข้อ
ก่อนเขียน agent แต่ละข้อต้องมีสามอย่าง

1. ข้อความที่ผู้ใช้จะพิมพ์จริง ไม่ใช่คำอธิบายงาน
2. ฟังก์ชันที่ดูโลกจริงแล้วคืนจริงหรือเท็จ ไม่ใช่ความประทับใจ
3. เหตุผลว่าทำไมข้อนี้ต้องอยู่ในรายการ ซึ่งมักคือถ้าข้อนี้ตกระบบนี้ไม่มีประโยชน์ หรือ
   ถ้าข้อนี้ตกระบบนี้เป็นอันตราย

**อย่างน้อยหนึ่งข้อต้องเป็นการทดสอบว่ามันปฏิเสธ** ไม่ใช่ทดสอบว่ามันทำได้ เพราะความ
ล้มเหลวที่แพงที่สุดของ agent เกือบทั้งหมดคือการทำสิ่งที่ไม่ควรทำ ไม่ใช่การทำสิ่งที่ควรทำ
ไม่สำเร็จ eval ที่มีแต่ข้อที่ทดสอบความสามารถ จะให้คะแนนเต็มกับระบบที่ทำทุกอย่างที่ใครขอ

ถ้าคิดเกณฑ์ไม่ออก แปลว่ายังไม่เข้าใจปัญหาพอ และการเขียนโค้ดต่อจากจุดนี้จะทำให้คุณสร้าง
ของที่ประเมินไม่ได้ ซึ่งแปลว่าปรับปรุงไม่ได้ด้วย อาการที่พบบ่อยคือคุณเขียนเกณฑ์ออกมา
แล้วมันหน้าตาแบบนี้

```text
คำตอบต้องเป็นประโยชน์และเข้าใจง่าย
```

ประโยคนั้นตรวจไม่ได้ ให้เปลี่ยนเป็นคำถามว่า ถ้าคำตอบดีกับคำตอบแย่วางอยู่ข้างกัน มีอะไร
ในโลกที่ต่างกันบ้าง ถ้าไม่มีอะไรต่าง คุณจะวัดไม่ได้ตลอดไป ถ้ามีบางอย่างต่าง เช่นมีแถวใน
ฐานข้อมูล มีไฟล์ที่เปลี่ยน หรือมีเบอร์โทรอยู่ในข้อความ นั่นคือเกณฑ์ของคุณ

จากบทที่ 7 การตรวจเชิงกลไกดีกว่า judge เมื่อทำได้ และการที่มันทำได้หรือไม่ ขึ้นกับว่า
ระบบทิ้งร่องรอยไว้ในที่ที่ฟังก์ชันไปดูได้หรือเปล่า ระบบที่ผลลัพธ์ทั้งหมดเป็นข้อความที่ส่ง
ออกไปแล้วหายไป ตรวจเชิงกลไกไม่ได้ ระบบที่เขียนแถวลงฐานข้อมูล ตรวจได้ทันที การรู้ข้อนี้
ตั้งแต่ตอนออกแบบ ทำให้คุณเลือกเก็บสิ่งที่ต้องเก็บ

## 7. ถ้ามันพังกลางทาง จะเกิดอะไรขึ้นกับผู้ใช้ และจะกู้ยังไง

บทที่ 6 บอกว่าทุกชั้นล้มเหลวได้และจะล้มเหลวจริง คำถามนี้บังคับให้คุณเขียนคำตอบไว้ล่วง
หน้า แทนที่จะค้นพบมันตอนตีสอง

มีจุดพังสามจุดที่ต่างกัน และแต่ละจุดถามคนละคำถาม

| จุดพัง | ผู้ใช้เห็นอะไร | สิ่งที่ค้างอยู่ |
| --- | --- | --- |
| เรียก model ไม่ได้ | ไม่มีคำตอบ | บทสนทนาที่มีคำถามแต่ไม่มีคำตอบ |
| tool ตัวหนึ่งล้มเหลว | คำตอบที่อาจถูกหรือผิด | ผลลัพธ์บางส่วนที่ทำไปแล้ว |
| process ตายกลางรอบ | เงียบ | tool call ที่ไม่มีผลลัพธ์คู่ ตามบทที่ 4 |

แถวที่สามคือแถวที่ทำลายระบบได้ถาวร เพราะจากบทที่ 4 คำขอครั้งถัดไปที่มี tool call ที่ไม่
มีผลลัพธ์คู่ จะถูกปฏิเสธด้วย HTTP 400 (รหัสสี่ร้อย คือคำตอบที่บอกว่าคำขอผิดรูป) ทันที
และถ้าบทสนทนานั้นถูกเขียนลงดิสก์ไปแล้ว มันจะถูกปฏิเสธทุกครั้งที่พยายามทำงานต่อ ไม่ใช่
แค่ครั้งเดียว บทสนทนานั้นตายถาวร

หลักสูตรนี้แก้ด้วย `finally` ที่เติมผลลัพธ์ให้คำขอที่ค้าง แต่ให้สังเกตว่า `finally` ทำงาน
เมื่อ process ยังอยู่ ถ้าคำตอบข้อ 3 ของคุณคือ worker ที่ถูก orchestrator ฆ่าได้ทุกเมื่อ
`finally` ไม่ได้ทำงานเลย และการซ่อมต้องย้ายไปอยู่ที่ตอนโหลดบทสนทนากลับมาแทน นี่คือ
ตัวอย่างของการที่คำตอบข้อ 3 เปลี่ยนคำตอบข้อ 7

ถ้าคำตอบคือผู้ใช้จะไม่รู้ว่ามันพัง ให้หยุดแล้วออกแบบใหม่ ความล้มเหลวที่เงียบคือความล้ม
เหลวที่ถูกเข้าใจผิดว่าเป็นคำตอบ และในระบบที่คนเอาคำตอบไปตัดสินใจต่อ นั่นอันตรายกว่า
การไม่มีระบบ

คำตอบข้อนี้ตัดสินว่าคุณต้องเขียนอะไรลงดิสก์และเมื่อไหร่ จากบทที่ 4 หลักสูตรนี้เขียน
session ทีละบรรทัดขณะเกิดเหตุ ไม่ใช่ตอนจบ ด้วยเหตุผลข้อเดียว คือ crash แล้วไม่เสียสิ่งที่
ทำเสร็จไปแล้ว ถ้าคำตอบข้อ 7 ของคุณคือให้ทำต่อจากจุดที่ค้าง คุณต้องเก็บทุกอย่างที่จำเป็น
ต่อการทำต่อ ในจังหวะที่มันเกิด ไม่ใช่ในจังหวะที่สะดวก

## 8. ทำไมลำดับเป็นแบบนี้

คำถามเจ็ดข้อไม่ได้เป็นอิสระต่อกัน มันมีทิศทางของการพึ่งพา และการตอบผิดลำดับทำให้คุณ
ต้องตอบใหม่

สองข้อแรกเป็นประตูของกรอบทั้งหมด ข้อหนึ่งตัดสินว่าจะถามต่อไหม อีกข้อตัดสินว่ารายการ
tool จะถูกกรองด้วยอะไร

- ข้อ 1 มาก่อน เพราะถ้าคำตอบคือไม่ต้องใช้ agent อีกหกข้อไม่ต้องถาม
- ข้อ 2 มาก่อนข้อ 5 เพราะรายการ tool ต้องถูกกรองด้วยความเสียหาย ไม่ใช่ถูกเขียนก่อน
  แล้วค่อยหาความเสียหาย และทั้งสองข้อจะถูกตอบสลับไปมาสองสามรอบ ซึ่งเป็นเรื่องปกติ

สองข้อถัดไปมีลำดับที่มองไม่เห็นจากตัวคำถามเอง ต้องรู้ว่ามันไปแตะข้ออื่นตรงไหนถึงจะเห็น

- ข้อ 3 มาก่อนข้อ 2 ในเชิงผล เพราะความเสียหายชั้นกลางจะยอมรับได้หรือไม่ ขึ้นกับว่ามี
  คนดูอยู่หรือเปล่า ความผิดพลาดที่คนเห็นภายในสิบวินาที กับความผิดพลาดที่ไม่มีใครเห็น
  จนถึงวันจันทร์ เป็นความเสี่ยงคนละระดับ
- ข้อ 4 เกือบเป็นอิสระ ตอบตอนไหนก็ได้ แต่ต้องตอบก่อนเริ่มสร้างอะไร เพราะมันคือข้อที่
  ทำให้คนเสียเวลาสามสัปดาห์กับโครงสร้างที่ไม่ต้องมี

และสองข้อสุดท้ายถูกวางไว้ท้ายด้วยเหตุผลคนละแบบกัน

- ข้อ 6 ต้องมาก่อนโค้ด ไม่ใช่หลังโค้ด เหตุผลอยู่ในหัวข้อของมันเอง
- ข้อ 7 มาท้ายสุดเพราะมันต้องรู้คำตอบของข้อ 3 กับข้อ 5 ก่อน จึงจะบอกได้ว่าอะไรค้างอยู่
  ตอนพัง

## 9. หน้ากระดาษเดียวที่ควรมีก่อนเริ่ม

ผลของกรอบนี้ไม่ใช่ความรู้สึกมั่นใจ มันคือเอกสารหนึ่งหน้าที่หน้าตาแบบนี้

```text
โปรเจกต์
รูปร่าง          agent loop หรือ pipeline หรือโปรแกรมธรรมดา
ความเสียหายสูงสุด  ประโยคเดียว และมันอยู่ชั้นไหนในสามชั้น
คนดู             มี หรือ มีแต่ช้า หรือ ไม่มี
ข้อมูล            กองละบรรทัด พร้อมคำตอบว่าเข้าข้อไหนในสี่ข้อ
tool             ตารางหกคอลัมน์
tool ที่จงใจไม่มี  รายการ พร้อมเหตุผลหนึ่งบรรทัดต่อรายการ
eval             สามถึงห้าข้อ อย่างน้อยหนึ่งข้อทดสอบการปฏิเสธ
เมื่อพัง          จุดพังสามจุด ผู้ใช้เห็นอะไร กู้ยังไง
```

มันต้องถูกเขียนออกมา ไม่ใช่คิดในหัว เพราะห้าในเจ็ดข้อจะถูกอ่านโดยคนอื่นที่ต้องแก้ระบบ
นี้ในหกเดือนข้างหน้า และรายการ tool ที่จงใจไม่มีคือรายการเดียวที่ไม่มีทางเดาจากโค้ดได้
ถ้าไม่เขียนไว้ คนถัดไปจะเพิ่ม tool ที่คุณจงใจไม่ใส่ โดยคิดว่าคุณแค่ลืมครับ

## 10. สิ่งที่กรอบนี้ไม่ได้ทำ

กรอบนี้ไม่ได้บอกว่าไอเดียของคุณดีหรือไม่ มันบอกแค่ว่าถ้าจะทำ ต้องทำรูปไหน คำถามว่าคน
จะใช้ไหม เป็นคำถามคนละชุดที่หนังสือเล่มนี้ไม่ได้ตอบ

และกรอบนี้ไม่ได้แทนการวัด คำตอบทั้งเจ็ดข้อคือสมมติฐาน ข้อ 6 มีอยู่เพื่อเปลี่ยนสมมติฐาน
เหล่านั้นให้เป็นตัวเลข และตามบทที่ 7 ทุกข้ออ้างจะเป็นแค่ข้ออ้างจนกว่าคุณจะวัดมัน

สามบทที่เหลือของภาคนี้คือการใช้กรอบนี้จริง บทที่ 9 เดินทั้งเจ็ดข้อกับโจทย์เดียวอย่าง
ละเอียด บทที่ 10 เดินสามโจทย์ที่คำตอบออกมาคนละทางเพื่อให้เห็นว่ากรอบเดียวกันพาไปคนละ
ที่ และบทที่ 11 คือรายการสิ่งที่พังจริงในโปรเจกต์นี้เอง ซึ่งเป็นหลักฐานว่าทำไมคำถามพวก
นี้ถึงถูกถาม
