# บทที่ 8 กรอบคิดเจ็ดคำถามก่อนเขียนโค้ดบรรทัดแรก

เจ็ดบทที่ผ่านมาอธิบายว่ากลไกทำงานยังไง ภาคนี้อธิบายว่าจะตัดสินใจยังไง
และความต่างสำคัญกว่าที่ฟัง เพราะคนที่เข้าใจกลไกครบทุกข้อยังสร้างของผิดได้
ถ้าเขาไม่เคยถามว่าควรสร้างอะไร

ปัญหาที่พบบ่อยที่สุดในโปรเจกต์ agent (เอเจนต์ คือโปรแกรมที่ให้ model
ตัดสินใจว่าจะเรียกเครื่องมืออะไรต่อ) ไม่ใช่โค้ดผิด แต่คือโค้ดที่ถูกต้อง
สำหรับปัญหาที่ไม่มีอยู่ คนใช้เวลาสามสัปดาห์สร้าง vector database
(ฐานข้อมูลเวกเตอร์ คือที่เก็บข้อความในรูปตัวเลขเพื่อค้นด้วยความหมาย)
ให้ข้อมูลที่ใส่ context ได้หมดตั้งแต่แรก คนสร้าง agent loop สำหรับงานที่มี
ห้าขั้นตอนตายตัว คนออกแบบระบบ permission (สิทธิ์ คือกลไกที่ตัดสินว่า
การกระทำไหนทำได้) หลังจากที่ tool ที่ลบข้อมูลถูกเขียนไปแล้ว

บทนี้เสนอคำถามเจ็ดข้อที่ต้องตอบก่อน คำตอบของแต่ละข้อไม่ใช่ความเห็น
มันเป็นข้อจำกัดที่บีบรูปร่างของระบบ และบางคำตอบแปลว่าให้เลิกทำ

## 0. เจ็ดข้อ และสิ่งที่แต่ละข้อตัดสิน

| ข้อ | คำถาม | สิ่งที่คำตอบตัดสิน |
| --- | --- | --- |
| 1 | งานนี้ต้องใช้ agent จริงหรือ | รูปร่างของโปรแกรมทั้งโปรแกรม |
| 2 | ถ้าทำผิดแล้วเสียหายแค่ไหน | อะไรเป็น tool ได้ และอะไรห้ามเป็น |
| 3 | ใครดูอยู่ตอนมันทำงาน | รูปแบบของ permission และการรายงานผล |
| 4 | ข้อมูลอยู่ที่ไหนและอยู่ในรูปแบบไหน | โครงสร้างพื้นฐานที่ต้องสร้าง |
| 5 | tool ที่ต้องมีคืออะไร อันไหนอันตราย | ขอบเขตความสามารถทั้งหมดของระบบ |
| 6 | จะรู้ได้ยังไงว่ามันทำงานถูก | สิ่งที่ทำให้ทุกข้อข้างบนตรวจสอบได้ |
| 7 | ถ้าพังกลางทางจะเกิดอะไรขึ้น | สิ่งที่ต้องเก็บลงดิสก์และเมื่อไหร่ |

ลำดับไม่ใช่เรื่องบังเอิญ และหัวข้อสุดท้ายของบทนี้อธิบายว่าทำไม

## 1. งานนี้ต้องใช้ agent จริงหรือ

**ถามทำไม** เพราะ agent เป็นเครื่องมือที่แพงที่สุดในกล่อง และคนหยิบมันมาใช้
เพราะมันน่าตื่นเต้น ไม่ใช่เพราะปัญหาเรียกร้อง

งานหนึ่งงานมีสามรูปร่างที่เป็นไปได้ และรูปร่างที่คนเลือกผิดบ่อยที่สุดคือรูปที่สาม

| รูปร่าง | เมื่อไหร่ | ราคาต่อการทำงานหนึ่งครั้ง |
| --- | --- | --- |
| โปรแกรมธรรมดา ไม่มี model | ขั้นตอนแน่นอน และตัดสินใจจากข้อมูลที่มีโครงสร้าง | ศูนย์ |
| โปรแกรมธรรมดาที่เรียก model หนึ่งครั้ง | ขั้นตอนแน่นอน แต่มีจุดหนึ่งที่ต้องเข้าใจภาษา | หนึ่งการเรียก |
| agent loop | ไม่รู้ล่วงหน้าว่าต้องทำกี่ขั้นตอนและขั้นไหนบ้าง | หลายการเรียก และโตแบบกำลังสองตามบทที่ 1 |

**วิธีทดสอบที่ใช้ได้จริง** ลองวาด flowchart (ผังงาน คือแผนภาพที่แสดงลำดับ
ขั้นตอนและจุดแตกแขนง) ของงานนั้นบนกระดาษ ถ้าคุณวาดจบและทุกจุดแตกแขนงตัดสิน
ด้วยเงื่อนไขที่เขียนเป็น `if` ได้ คุณเพิ่งเขียนโปรแกรมเสร็จแล้ว ไม่ต้องมี agent

ถ้าคุณวาดไม่จบเพราะขั้นตอนถัดไปขึ้นกับสิ่งที่อ่านเจอในขั้นก่อนหน้า และคุณ
ไม่รู้ล่วงหน้าว่าจะเจออะไร นั่นคือจุดที่ agent มีค่า จากบทที่ 2 การทำซ้ำที่
ไม่รู้จำนวนรอบล่วงหน้าคือนิยามของลูป และนั่นคือสิ่งเดียวที่ agent ให้คุณ

**คำตอบแบบไหนที่แปลว่าควรหยุด** ถ้าคุณเขียนขั้นตอนออกมาเป็นข้อๆ ได้ครบ
และแต่ละข้อทำอย่างเดิมทุกครั้ง ให้หยุดแล้วเขียนโปรแกรมธรรมดา เหตุผลไม่ใช่
เรื่องความบริสุทธิ์ทางวิศวกรรม แต่เป็นสามข้อที่วัดได้

- โปรแกรมธรรมดาให้ผลเดิมทุกครั้งกับ input เดิม agent ไม่ให้ ซึ่งแปลว่าคุณ
  ทดสอบด้วย assertion ตรงๆ ไม่ได้ ต้องใช้ eval ตามบทที่ 7 ซึ่งแพงกว่ามาก
- โปรแกรมธรรมดาไม่มีพื้นผิวให้ prompt injection ตามบทที่ 5 เพราะไม่มี model
  ให้แทรกคำสั่งใส่
- โปรแกรมธรรมดาไม่ต้องมีระบบ permission เพราะรายการสิ่งที่มันทำได้ถูกเขียน
  ไว้ในโค้ดแล้ว ไม่ได้ถูกเลือกตอนรัน

**คำตอบส่งผลต่อสถาปัตยกรรมยังไง** ถ้าคำตอบคือรูปที่สอง คือโปรแกรมธรรมดา
ที่เรียก model หนึ่งครั้ง คุณไม่ต้องมี loop ไม่ต้องมี tool ไม่ต้องมี
context management และไม่ต้องมี permission ทั้งระบบ สิ่งที่คุณต้องมีคือ
prompt หนึ่งอัน การเรียกหนึ่งครั้ง และการตรวจว่าผลลัพธ์อยู่ในรูปที่คาดไว้
จากบทที่ 3 การบังคับรูปร่างคำตอบใช้กลไกเดียวกับ tool calling คุณจึงนิยาม
tool หนึ่งตัวแล้วไม่รันมัน เท่านั้นพอ

ระหว่างรูปที่สองกับรูปที่สาม มีทางกลางที่คนมองข้าม คือ pipeline ที่แต่ละขั้น
เรียก model หนึ่งครั้ง ลำดับขั้นถูกเขียนไว้ในโค้ด ไม่ใช่ให้ model เลือก
วิธีนี้ได้ความสามารถทางภาษาโดยไม่เสียความแน่นอนของลำดับ และมันเหมาะกับงาน
จำนวนมากที่คนเผลอสร้างเป็น agent

## 2. ถ้าทำผิดแล้วเสียหายแค่ไหน

**ถามทำไม** เพราะคำตอบข้อนี้กำหนดว่าอะไรควรถามและอะไรควรห้ามไปเลย และสอง
อย่างนี้เป็นคนละเรื่องกัน คนส่วนใหญ่ออกแบบ permission ด้วยการไล่ดู tool
ที่เขียนไว้แล้วว่าอันไหนน่ากลัว ซึ่งเป็นการถามช้าไปหนึ่งขั้น เพราะถึงตอนนั้น
tool ที่ไม่ควรมีอยู่ก็มีอยู่แล้ว

ให้แบ่งผลของความผิดพลาดเป็นสามชั้น

| ชั้น | นิยาม | สิ่งที่ควรทำ |
| --- | --- | --- |
| กู้คืนได้เอง | โปรแกรมย้อนกลับได้โดยไม่ต้องมีคน | ให้เป็น tool ที่ `safe` ได้ |
| กู้คืนได้แต่ต้องมีคนทำ | ต้องมีคนกดปุ่ม กู้ backup หรือโทรหาใคร | ต้องถามก่อนทำ และต้องบันทึกว่าทำอะไรไป |
| กู้คืนไม่ได้ | เงินออกไปแล้ว ข้อความส่งไปแล้ว ข้อมูลหายถาวร | ห้ามเป็น tool ของ agent |

**เส้นที่สามคือเส้นที่สำคัญที่สุด** และเหตุผลมาจากบทที่ 5 โดยตรง กลไกป้องกัน
ทุกชั้นที่เรามีตั้งอยู่บนช่องว่างระหว่างคำขอกับการรัน ช่องว่างนั้นทำงานได้ดี
กับสิ่งที่ย้อนกลับได้ แต่กับสิ่งที่ย้อนกลับไม่ได้ ความผิดพลาดครั้งเดียว
ในหมื่นครั้งก็ยังเป็นความผิดพลาดที่แก้ไม่ได้ และ agent จะทำงานเกินหมื่นครั้ง
ในเวลาไม่นาน

วิธีที่ถูกกับการกระทำที่ย้อนกลับไม่ได้ คือให้ agent เตรียมของ แล้วให้คนเป็น
คนกด ต่างกันตรงที่ agent ผลิต artifact (ผลผลิต คือไฟล์หรือข้อมูลที่ตรวจดูได้
ก่อนถูกใช้) แทนที่จะผลิตผลลัพธ์ ตัวอย่างคือ agent ที่เขียนอีเมลลง draft
แทนที่จะส่ง และ agent ที่เขียนไฟล์ migration แทนที่จะรันมัน ซึ่งเป็นกรณี
ที่บทที่ 10 จะเดินให้ดูทั้งกรณี

**คำตอบแบบไหนที่แปลว่าควรหยุด** ถ้าคำตอบคือ "ไม่รู้" แปลว่าคุณยังไม่รู้ว่า
tool จะแตะอะไรบ้าง ให้ข้ามไปตอบข้อ 5 ก่อนแล้วกลับมา สองข้อนี้ตอบคู่กันเสมอ

ถ้าคำตอบคือ "เสียหายมากแต่โอกาสเกิดน้อย" ให้ระวัง เพราะประโยคนั้นเป็นสูตร
มาตรฐานของการยอมรับความเสี่ยงโดยไม่ได้คำนวณ สิ่งที่ต้องคำนวณคือความเสียหาย
คูณจำนวนครั้งที่ระบบจะทำงานในหนึ่งปี ไม่ใช่ความเสียหายคูณความรู้สึก

**คำตอบส่งผลต่อสถาปัตยกรรมยังไง** มันเขียนตัวเองลงไปในฟิลด์เดียวจากบทที่ 3

```python
    safe: bool = False
```

ค่าเริ่มต้นเป็น `False` เพราะการลืมต้องนำไปสู่คำถาม ไม่ใช่ความเงียบ
และเหตุผลที่ฟิลด์นี้อยู่บน `Tool` ไม่ใช่ในไฟล์ config กลาง คือคนที่เขียน
tool คือคนเดียวที่รู้ว่ามันทำลายอะไรได้ คำตอบของข้อ 2 จึงไม่ได้ถูกเก็บไว้
ในเอกสาร มันถูกเก็บไว้ข้างๆ โค้ดที่มันควบคุม

## 3. ใครเป็นคนดูอยู่ตอนมันทำงาน

**ถามทำไม** เพราะระบบ permission ทั้งระบบในบทที่ 5 ตั้งอยู่บนสมมติฐานเงียบๆ
ว่ามีคนอยู่หน้าจอที่พิมพ์ตอบได้

```python
    answer = self.ask(tool, call)
```

บรรทัดนี้หยุดรอ ถ้าไม่มีใครอยู่ตรงนั้น มันหยุดรอตลอดไป

มีสามสถานการณ์จริง และแต่ละอันเปลี่ยนของคนละอย่าง

| สถานการณ์ | permission | การรายงานผล |
| --- | --- | --- |
| มีคนจ้องหน้าจอ เช่น CLI | ถามได้ตอนนั้น จำคำตอบได้ | stream ทีละ token ตามบทที่ 1 |
| มีคนแต่ไม่ได้จ้อง เช่น chat หรือ LINE | ถามได้แต่คำตอบมาช้า ต้องพักงานไว้ | ส่งผลเป็นก้อนเดียวเมื่อเสร็จ |
| ไม่มีคนเลย เช่น cron หรือ CI | ถามไม่ได้ ต้องตัดสินใจล่วงหน้าทั้งหมด | เขียน log และแจ้งเตือนเมื่อผิดปกติ |

**แถวที่สองคือแถวที่คนออกแบบพลาดมากที่สุด** เพราะมันดูเหมือนแถวแรก มีคนอยู่
จริง เขาตอบได้จริง แต่เขาตอบในอีกสิบนาที และในสิบนาทีนั้น process ที่รัน
agent อาจถูกฆ่าไปแล้ว การถามในสถานการณ์นี้จึงไม่ใช่การเรียกฟังก์ชันที่บล็อก
มันคือการหยุดงานไว้ เก็บสถานะลงดิสก์ และเริ่มใหม่จากจุดนั้นเมื่อคำตอบมาถึง
ซึ่งเป็นคนละโปรแกรมกันโดยสิ้นเชิง บทที่ 9 เดินเรื่องนี้ทีละขั้น

**คำตอบแบบไหนที่แปลว่าควรหยุด** ถ้าคำตอบข้อนี้คือไม่มีคนดู และคำตอบข้อ 2
คือมีการกระทำที่กู้คืนไม่ได้ ให้หยุด นี่คือการตรวจไขว้ที่สำคัญที่สุดในกรอบ
ทั้งหมด เพราะมันคือสูตรของความเสียหายที่ไม่มีใครเห็นจนกว่าจะสาย

**คำตอบส่งผลต่อสถาปัตยกรรมยังไง** สังเกตว่าบทที่ 2 ออกแบบ loop ให้คายแต่
event และไม่ถามอะไรใคร นั่นคือสิ่งที่ทำให้คำตอบข้อ 3 เปลี่ยนได้โดยไม่แตะแกน
CLI ฉีดฟังก์ชันที่ถามคนจริง eval ฉีดตัวที่อนุญาตทุกอย่าง และ webhook
ฉีดตัวที่คืนคำตอบจากฐานข้อมูล ถ้า loop ถามเองด้วย `input()` คำตอบข้อ 3
จะกลายเป็นการเขียนใหม่ทั้งโปรแกรม

## 4. ข้อมูลที่มันต้องใช้อยู่ที่ไหนและอยู่ในรูปแบบไหน

**ถามทำไม** เพราะนี่คือข้อที่คนสร้างโครงสร้างพื้นฐานเกินความจำเป็นมากที่สุด
คำว่า retrieval (การค้นคืน คือการหาส่วนของข้อความที่น่าจะตอบคำถามได้)
กับคำว่า vector database กลายเป็นคำเดียวกันในความเข้าใจของคนจำนวนมาก
ทั้งที่อย่างแรกคือปัญหา ส่วนอย่างหลังคือหนึ่งในสี่คำตอบ

บทที่ 16 ของหลักสูตรมีขั้นตอนตัดสินใจสี่ข้อ ถามตามลำดับ และหยุดที่ข้อแรก
ที่ตอบว่าใช่

| คำถาม | ถ้าใช่ ให้ทำ |
| --- | --- |
| ข้อมูลเล็กพอที่จะใส่ context window ไหม | ใส่ไปเลย ไม่ต้องสร้างอะไร |
| ข้อมูลมีโครงสร้าง และคุณรู้ว่ากำลังถามอะไร ไหม | เขียน query เป็น SQL หรือเรียก API |
| มันเป็นข้อความที่ agent เดินหาเองได้ไหม | ให้ glob กับ grep ซึ่งคือบทที่ 09 |
| ไม่เข้าสามข้อแรก | ตอนนี้ vector search ถึงจะคุ้ม |

**ทำไมต้องหยุดที่ข้อแรกที่ตอบว่าใช่ ไม่ใช่เก็บความเห็นทั้งสี่ข้อมาชั่ง**
เพราะสี่ข้อนี้เรียงตามต้นทุนของโครงสร้างที่ต้องสร้างและดูแล ข้อแรกไม่ต้อง
สร้างอะไรเลย ข้อสองต้องมี schema กับ tool ที่ยิง query ข้อสามต้องมี tool
สองตัวที่หลักสูตรนี้เขียนไว้แล้ว ส่วนข้อสี่ต้องมี model สำหรับแปลงข้อความ
เป็นเวกเตอร์ ที่เก็บเวกเตอร์ ขั้นตอน build index ใน pipeline การ deploy
การตัดสินใจเรื่องขนาด chunk และแผนว่าจะทำยังไงเมื่อเอกสารเปลี่ยนแล้วเวกเตอร์
เก่าใช้ไม่ได้ การเลือกข้อสี่ทั้งที่ข้อสองตอบได้ คือการรับภาระทั้งหมดนั้นมา
โดยไม่ได้อะไรตอบแทน

**สิ่งที่ต้องระวังคือถามถูกหน่วย** คำถามนี้ถามต่อกองข้อมูลหนึ่งกอง ไม่ใช่
ต่อโปรเจกต์หนึ่งโปรเจกต์ ระบบเดียวมีข้อมูลสามกองที่ตอบคนละข้อได้เป็นเรื่อง
ปกติ และมันคือคำตอบที่ถูก บทที่ 9 มีตัวอย่างที่ชัด คือบันทึกอาการเป็นตาราง
จึงใช้ SQL ส่วนบทความสุขภาพเป็นร้อยแก้วจึงใช้ retrieval สองกองนี้อยู่ในระบบ
เดียวกันและต้องไม่ถูกยัดเข้าเครื่องมือเดียวกัน

**คำตอบแบบไหนที่แปลว่าควรหยุด** ถ้าคำตอบคือ "ทุกอย่างเข้าข้อสี่" แปลว่า
ยังไม่ได้ถามสามข้อแรกจริง ให้กลับไปตอบข้อหนึ่งด้วยตัวเลข คือนับตัวอักษร
ของข้อมูลจริง หารสี่ตามบทที่ 1 แล้วเทียบกับหน้าต่างของ model ที่จะใช้
คนส่วนใหญ่ประหลาดใจว่ามันเล็กกว่าที่คิด

**คำตอบส่งผลต่อสถาปัตยกรรมยังไง** มันตัดสินว่าครึ่งหนึ่งของงานวิศวกรรม
ในโปรเจกต์นี้จะอยู่ที่ไหน ถ้าคำตอบคือข้อสี่ งานส่วนใหญ่ของคุณคือ pipeline
ของข้อมูล ไม่ใช่ agent ตัว agent จะมีสองร้อยบรรทัด ส่วน pipeline จะเป็น
ที่ที่คุณใช้เวลาทั้งหมด การรู้ข้อนี้ตั้งแต่วันแรกเปลี่ยนวิธีวางแผนทั้งโปรเจกต์

## 5. tool ที่มันต้องมีคืออะไร และอันไหนอันตราย

**ถามทำไม** เพราะรายการ tool คือขอบเขตความสามารถทั้งหมดของระบบ ไม่มากไป
กว่านั้นและไม่น้อยไปกว่านั้น agent ทำสิ่งที่ไม่มีใน tool ไม่ได้ ไม่ว่า
system prompt จะสั่งอะไร และ agent ทำทุกอย่างที่มีใน tool ได้ ไม่ว่า
system prompt จะห้ามอะไร

ให้เขียนตารางนี้ให้เสร็จก่อนเขียนโค้ดบรรทัดแรก

| คอลัมน์ | ทำไมต้องมี |
| --- | --- |
| ชื่อ | เป็นสิ่งที่ model เห็นและใช้เลือก |
| ทำอะไร ในหนึ่งประโยค | ถ้าเขียนหนึ่งประโยคไม่ได้ แปลว่ามันทำสองอย่าง |
| อ่านหรือเขียน | เส้นแบ่งแรกของ permission ตามบทที่ 5 |
| คืนอะไรกลับมา | สิ่งที่คืนคือสิ่งที่เข้า context และถูกจ่ายซ้ำทุกรอบ |
| ถ้าเรียกผิดจะเกิดอะไร | คำตอบข้อ 2 ในระดับ tool |
| `safe` | ผลสรุปของสองคอลัมน์ก่อนหน้า |

**คอลัมน์ที่คนลืมคือคอลัมน์ที่สี่** เพราะจากบทที่ 1 สิ่งที่ tool คืนมา
ไม่ได้ถูกอ่านครั้งเดียว มันอยู่ในบทสนทนาและถูกส่งใหม่ทุกรอบจนจบงาน tool ที่
คืนแถวดิบสองร้อยแถวจึงไม่ได้แพงหนึ่งครั้ง มันแพงทุกครั้งที่เหลือ การออกแบบ
ให้ tool คืนสรุปแทนที่จะคืนของดิบ เป็นการตัดสินใจที่ต้องทำตอนนี้ ไม่ใช่
ตอน optimise ทีหลัง เพราะการเปลี่ยนสิ่งที่ tool คืนหลังจากมี prompt ที่
ปรับจนดีแล้ว แปลว่าต้องปรับใหม่หมด

**คำตอบแบบไหนที่แปลว่าควรหยุด** สามอย่าง

- รายการยาวเกินสิบสองตัว จากบทที่ 3 schema ของ tool ทุกตัวเดินทางไปกับ
  ทุกคำขอ ก่อนที่ model จะอ่านงานจริงสักตัวอักษร และผลที่หนักกว่าความเปลือง
  คือ model เลือกผิดบ่อยขึ้นเมื่อมีตัวเลือกเยอะ รายการที่ยาวเกินไปทำให้
  agent แย่ลง ไม่ใช่แค่แพงขึ้น
- สอง tool ที่คำอธิบายเขียนแล้วแยกกันไม่ออก ให้รวมเป็นตัวเดียว เพราะถ้าคุณ
  แยกไม่ออก model ก็แยกไม่ออก
- มี tool ที่ตกอยู่ในชั้นกู้คืนไม่ได้ของข้อ 2 ให้ลบมันออกจากรายการ ไม่ใช่
  ทำให้มันถามก่อน ความต่างสำคัญ เพราะ tool ที่มีอยู่แต่ถามก่อน จะถูกอนุญาต
  สักวันหนึ่งโดยคนที่กดโดยไม่อ่าน ส่วน tool ที่ไม่มีอยู่ จะไม่ถูกเรียก

**คำตอบส่งผลต่อสถาปัตยกรรมยังไง** รายการที่ไม่มี คือสิ่งที่ทำให้คำตอบข้อ 2
เป็นจริงแทนที่จะเป็นความหวัง ระบบที่บอกว่าอ่านอย่างเดียว แล้วมี tool ที่
เขียนไฟล์ได้ ไม่ใช่ระบบที่อ่านอย่างเดียว ส่วนระบบที่ไม่มี tool ที่เขียนอะไร
ได้เลย เป็นระบบที่อ่านอย่างเดียวจริง และข้อความนั้นตรวจสอบได้ด้วยการดู
รายการ ไม่ต้องเชื่อใคร

## 6. จะรู้ได้ยังไงว่ามันทำงานถูก

**ถามทำไม** เพราะบทที่ 7 พิสูจน์แล้วว่าคุณแยกการเปลี่ยนแปลงที่ดีออกจากที่แย่
ด้วยการดูไม่ได้ และเพราะการเขียนเกณฑ์ก่อนเขียนโค้ดทำอีกอย่างที่สำคัญกว่านั้น
คือมันบังคับให้คุณนิยามว่าความสำเร็จคืออะไร ในขณะที่คุณยังเปลี่ยนใจได้ถูก

ให้เขียน eval (การประเมิน คือชุดงานที่รันซ้ำได้พร้อมเกณฑ์ตัดสินผ่านหรือตก)
สามถึงห้าข้อ ก่อนเขียน agent แต่ละข้อต้องมีสามอย่าง

1. ข้อความที่ผู้ใช้จะพิมพ์จริง ไม่ใช่คำอธิบายงาน
2. ฟังก์ชันที่ดูโลกจริงแล้วคืนจริงหรือเท็จ ไม่ใช่ความประทับใจ
3. เหตุผลว่าทำไมข้อนี้ต้องอยู่ในรายการ ซึ่งมักคือ "ถ้าข้อนี้ตก ระบบนี้ไม่มี
   ประโยชน์" หรือ "ถ้าข้อนี้ตก ระบบนี้เป็นอันตราย"

**อย่างน้อยหนึ่งข้อต้องเป็นการทดสอบว่ามันปฏิเสธ** ไม่ใช่ทดสอบว่ามันทำได้
เพราะความล้มเหลวที่แพงที่สุดของ agent เกือบทั้งหมดคือการทำสิ่งที่ไม่ควรทำ
ไม่ใช่การทำสิ่งที่ควรทำไม่สำเร็จ eval ที่มีแต่ข้อที่ทดสอบความสามารถ
จะให้คะแนนเต็มกับระบบที่ทำทุกอย่างที่ใครขอ

**คำตอบแบบไหนที่แปลว่าควรหยุด** ถ้าคิดเกณฑ์ไม่ออก แปลว่ายังไม่เข้าใจปัญหา
พอ และการเขียนโค้ดต่อจากจุดนี้จะทำให้คุณสร้างของที่ประเมินไม่ได้ ซึ่งแปลว่า
ปรับปรุงไม่ได้ด้วย อาการที่พบบ่อยคือคุณเขียนเกณฑ์ออกมาแล้วมันหน้าตาแบบนี้

```text
คำตอบต้องเป็นประโยชน์และเข้าใจง่าย
```

ประโยคนั้นตรวจไม่ได้ ให้เปลี่ยนเป็นคำถามว่า ถ้าคำตอบดีกับคำตอบแย่วางอยู่
ข้างกัน มีอะไรในโลกที่ต่างกันบ้าง ถ้าไม่มีอะไรต่าง คุณจะวัดไม่ได้ตลอดไป
ถ้ามีบางอย่างต่าง เช่นมีแถวในฐานข้อมูล มีไฟล์ที่เปลี่ยน หรือมีเบอร์โทรอยู่
ในข้อความ นั่นคือเกณฑ์ของคุณ

**คำตอบส่งผลต่อสถาปัตยกรรมยังไง** จากบทที่ 7 การตรวจเชิงกลไกดีกว่า judge
เมื่อทำได้ และการที่มันทำได้หรือไม่ ขึ้นกับว่าระบบทิ้งร่องรอยไว้ในที่ที่
ฟังก์ชันไปดูได้หรือเปล่า ระบบที่ผลลัพธ์ทั้งหมดเป็นข้อความที่ส่งออกไปแล้ว
หายไป ตรวจเชิงกลไกไม่ได้ ระบบที่เขียนแถวลงฐานข้อมูล ตรวจได้ทันที
การรู้ข้อนี้ตั้งแต่ตอนออกแบบทำให้คุณเลือกเก็บสิ่งที่ต้องเก็บ

## 7. ถ้ามันพังกลางทาง จะเกิดอะไรขึ้นกับผู้ใช้ และจะกู้ยังไง

**ถามทำไม** เพราะบทที่ 6 บอกว่าทุกชั้นล้มเหลวได้และจะล้มเหลวจริง คำถามนี้
บังคับให้คุณเขียนคำตอบไว้ล่วงหน้าแทนที่จะค้นพบมันตอนตีสอง

มีจุดพังสามจุดที่ต่างกัน และแต่ละจุดถามคนละคำถาม

| จุดพัง | ผู้ใช้เห็นอะไร | สิ่งที่ค้างอยู่ |
| --- | --- | --- |
| เรียก model ไม่ได้ | ไม่มีคำตอบ | บทสนทนาที่มีคำถามแต่ไม่มีคำตอบ |
| tool ตัวหนึ่งล้มเหลว | คำตอบที่อาจถูกหรือผิด | ผลลัพธ์บางส่วนที่ทำไปแล้ว |
| process ตายกลางรอบ | เงียบ | tool call ที่ไม่มีผลลัพธ์คู่ ตามบทที่ 4 |

**แถวที่สามคือแถวที่ทำลายระบบได้ถาวร** เพราะจากบทที่ 4 คำขอครั้งถัดไปที่มี
tool result ที่ไม่มีคู่ จะถูกปฏิเสธด้วย HTTP 400 (รหัสสี่ร้อย คือคำตอบที่
บอกว่าคำขอผิดรูป) ทันที และถ้าบทสนทนานั้นถูกเขียนลงดิสก์ไปแล้ว มันจะถูก
ปฏิเสธทุกครั้งที่พยายามทำงานต่อ ไม่ใช่แค่ครั้งเดียว บทสนทนานั้นตายถาวร

หลักสูตรนี้แก้ด้วย `finally` ที่เติมผลลัพธ์ให้คำขอที่ค้าง แต่ให้สังเกตว่า
`finally` ทำงานเมื่อ process ยังอยู่ ถ้าคำตอบข้อ 3 ของคุณคือ worker ที่
ถูก orchestrator ฆ่าได้ทุกเมื่อ `finally` ไม่ได้ทำงานเลย และการซ่อมต้อง
ย้ายไปอยู่ที่ตอนโหลดบทสนทนากลับมาแทน นี่คือตัวอย่างของการที่คำตอบข้อ 3
เปลี่ยนคำตอบข้อ 7

**คำตอบแบบไหนที่แปลว่าควรหยุด** ถ้าคำตอบคือ "ผู้ใช้จะไม่รู้ว่ามันพัง"
ให้หยุดแล้วออกแบบใหม่ ความล้มเหลวที่เงียบคือความล้มเหลวที่ถูกเข้าใจผิดว่า
เป็นคำตอบ และในระบบที่คนเอาคำตอบไปตัดสินใจต่อ นั่นอันตรายกว่าการไม่มีระบบ

**คำตอบส่งผลต่อสถาปัตยกรรมยังไง** มันตัดสินว่าคุณต้องเขียนอะไรลงดิสก์
และเมื่อไหร่ จากบทที่ 4 หลักสูตรนี้เขียน session ทีละบรรทัดขณะเกิดเหตุ
ไม่ใช่ตอนจบ ด้วยเหตุผลข้อเดียว คือ crash แล้วไม่เสียสิ่งที่ทำเสร็จไปแล้ว
ถ้าคำตอบข้อ 7 ของคุณคือ "ให้ทำต่อจากจุดที่ค้าง" คุณต้องเก็บทุกอย่างที่
จำเป็นต่อการทำต่อ ในจังหวะที่มันเกิด ไม่ใช่ในจังหวะที่สะดวก

## 8. ทำไมลำดับเป็นแบบนี้

คำถามเจ็ดข้อไม่ได้เป็นอิสระต่อกัน มันมีทิศทางของการพึ่งพา และการตอบผิดลำดับ
ทำให้คุณต้องตอบใหม่

- ข้อ 1 มาก่อน เพราะถ้าคำตอบคือไม่ต้องใช้ agent อีกหกข้อไม่ต้องถาม
- ข้อ 2 มาก่อนข้อ 5 เพราะรายการ tool ต้องถูกกรองด้วยความเสียหาย ไม่ใช่
  ถูกเขียนก่อนแล้วค่อยหาความเสียหาย และทั้งสองข้อจะถูกตอบสลับไปมาสองสามรอบ
  ซึ่งเป็นเรื่องปกติ
- ข้อ 3 มาก่อนข้อ 2 ในเชิงผล เพราะความเสียหายชั้นกลางจะยอมรับได้หรือไม่
  ขึ้นกับว่ามีคนดูอยู่หรือเปล่า ความผิดพลาดที่คนเห็นภายในสิบวินาที
  กับความผิดพลาดที่ไม่มีใครเห็นจนถึงวันจันทร์ เป็นความเสี่ยงคนละระดับ
- ข้อ 4 เกือบเป็นอิสระ ตอบตอนไหนก็ได้ แต่ต้องตอบก่อนเริ่มสร้างอะไร
  เพราะมันคือข้อที่ทำให้คนเสียเวลาสามสัปดาห์กับโครงสร้างที่ไม่ต้องมี
- ข้อ 6 ต้องมาก่อนโค้ด ไม่ใช่หลังโค้ด เหตุผลอยู่ในหัวข้อของมันเอง
- ข้อ 7 มาท้ายสุดเพราะมันต้องรู้คำตอบของข้อ 3 กับข้อ 5 ก่อน จึงจะบอกได้ว่า
  อะไรค้างอยู่ตอนพัง

## 9. หน้ากระดาษเดียวที่ควรมีก่อนเริ่ม

ผลของกรอบนี้ไม่ใช่ความรู้สึกมั่นใจ มันคือเอกสารหนึ่งหน้าที่หน้าตาแบบนี้

```text
โปรเจกต์
รูปร่าง          agent loop หรือ pipeline หรือโปรแกรมธรรมดา
ความเสียหายสูงสุด  ประโยคเดียว และมันอยู่ชั้นไหนในสามชั้น
คนดู             มี หรือ มีแต่ช้า หรือ ไม่มี
ข้อมูล            กองละบรรทัด พร้อมคำตอบว่าเข้าข้อไหนในสี่ข้อ
tool             ตารางหกคอลัมน์
tool ที่จงใจไม่มี  รายการ พร้อมเหตุผลหนึ่งบรรทัดต่อรายการ
eval             สามถึงห้าข้อ อย่างน้อยหนึ่งข้อทดสอบการปฏิเสธ
เมื่อพัง          จุดพังสามจุด ผู้ใช้เห็นอะไร กู้ยังไง
```

**ทำไมต้องเขียนออกมา ไม่ใช่คิดในหัว** เพราะห้าในเจ็ดข้อจะถูกอ่านโดยคนอื่น
ที่ต้องแก้ระบบนี้ในหกเดือนข้างหน้า และรายการ tool ที่จงใจไม่มีคือรายการเดียว
ที่ไม่มีทางเดาจากโค้ดได้ ถ้าไม่เขียนไว้ คนถัดไปจะเพิ่ม tool ที่คุณจงใจไม่ใส่
โดยคิดว่าคุณแค่ลืม

## 10. สิ่งที่กรอบนี้ไม่ได้ทำ

กรอบนี้ไม่ได้บอกว่าไอเดียของคุณดีหรือไม่ มันบอกแค่ว่าถ้าจะทำ ต้องทำรูปไหน
คำถามว่าคนจะใช้ไหม เป็นคำถามคนละชุดที่หนังสือเล่มนี้ไม่ได้ตอบ

และกรอบนี้ไม่ได้แทนการวัด คำตอบทั้งเจ็ดข้อคือสมมติฐาน ข้อ 6 มีอยู่เพื่อ
เปลี่ยนสมมติฐานเหล่านั้นให้เป็นตัวเลข และตามบทที่ 7 ทุกข้ออ้างจะเป็นแค่
ข้ออ้างจนกว่าคุณจะวัดมัน

สามบทที่เหลือของภาคนี้คือการใช้กรอบนี้จริง บทที่ 9 เดินทั้งเจ็ดข้อกับโจทย์
เดียวอย่างละเอียด บทที่ 10 เดินสามโจทย์ที่คำตอบออกมาคนละทางเพื่อให้เห็นว่า
กรอบเดียวกันพาไปคนละที่ และบทที่ 11 คือรายการสิ่งที่พังจริงในโปรเจกต์นี้เอง
ซึ่งเป็นหลักฐานว่าทำไมคำถามพวกนี้ถึงถูกถาม
