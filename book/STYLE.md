# คู่มือสำนวนของหนังสือเล่มนี้

เอกสารนี้ไม่ใช่บทหนึ่งของหนังสือ มันคือกฎที่ทุกบทต้องทำตาม เขียนไว้เพราะหนังสือที่มี
หลายบทและเขียนคนละวันจะกลายเป็นคนละเล่มถ้าไม่มีกฎเขียนไว้

กฎเหล่านี้มาจากการสำรวจว่าหนังสือเทคนิคที่คนชมเรื่องการเขียนจริงๆ เขาทำอะไร และ
งานเขียนเทคนิคภาษาไทยที่อ่านง่ายเขาทำอะไร ไม่ได้มาจากความชอบส่วนตัว

## 1. คำศัพท์

**กฎการอธิบายศัพท์ ครั้งเดียวพอ** ครั้งแรกที่พบศัพท์ในบทหนึ่ง ให้เขียนแบบนี้

```text
context window (ข้อความมากสุดที่ model อ่านได้ในหนึ่งครั้ง)
```

หลังจากนั้นในบทเดียวกันใช้ `context window` เฉยๆ ห้ามอธิบายซ้ำ การอธิบายซ้ำทำให้
ผู้อ่านรู้สึกว่าถูกดูถูก และทำให้หน้ากระดาษยาวขึ้นโดยไม่ได้อะไร

**คำอธิบายต้องบอกว่ามันทำอะไร ไม่ใช่แปลชื่อมัน** หน้าต่างบริบท ลิงก์เชิงสัญลักษณ์
แบบจำลองภาษาขนาดใหญ่ คือการแปลชื่อทีละคำ ไม่มีใครพูด และผู้อ่านต้องแปลกลับเป็นอังกฤษ
ในหัวอยู่ดี ให้ข้ามคำแปลไปอธิบายว่ามันทำอะไรเลย

**คำอธิบายยาวหนึ่งวรรคพอ** ถ้าต้องใช้สองวรรคถึงจะชัด แปลว่ากำลังยัดเนื้อหาลงวงเล็บ
ให้ย้ายส่วนเกินไปไว้ในย่อหน้า

**มีตัวย่อให้ใช้ตัวย่อ** ครั้งแรกเขียน `large language model (model ภาษาขนาดใหญ่ หรือ LLM)`
หลังจากนั้นใช้ `LLM` ตลอด ห้ามสลับไปมาระหว่างตัวเต็มกับตัวย่อ

**ลำดับการตัดสินใจว่าจะแปลศัพท์ไหม** สามขั้นตามลำดับ

1. ถ้ามีคำไทยที่คนใช้จริงอยู่แล้ว ใช้คำไทย เช่น `ผู้ใช้` `ข้อมูล` `ตัวแปร` `หน่วยความจำ`
2. ถ้าคำแปลฟืน ให้ทับศัพท์ เช่น `โมเดล` แต่ในเล่มนี้เราเลือกคงภาษาอังกฤษแทนการทับศัพท์
3. ศัพท์เทคนิคเฉพาะทางและชื่อเฉพาะ คงภาษาอังกฤษ เช่น `token` `agent` `API` `context`

**แบบทดสอบที่ใช้ตัดสิน** ถ้าผู้อ่านต้องแปลคำไทยนั้นกลับเป็นอังกฤษในหัวก่อนจะเข้าใจ
แปลว่าคำแปลนั้นแย่กว่าการไม่แปล

**ห้ามสลับไปมา** เลือกอย่างใดอย่างหนึ่งต่อหนึ่งความคิด แล้วใช้อันนั้นทั้งเล่ม การเขียน
`model` สิบเจ็ดครั้งและ `โมเดล` เก้าครั้งในบทความเดียวคือความผิดพลาดที่พบบ่อยที่สุด
ในงานเขียนเทคนิคไทย

**สะกดทับศัพท์ให้ถูก** รายการที่ผิดบ่อย ฟังก์ชัน ไม่ใช่ ฟังก์ชั่น / อัปเดต ไม่ใช่ อัพเดท /
แอปพลิเคชัน / ลิงก์ ไม่ใช่ ลิงค์ / อัลกอริทึม / ซอฟต์แวร์ / คอมเมนต์

## 2. ประโยคและการเว้นวรรค

**หน่วยที่สำคัญคือช่วงระหว่างการเว้นวรรค ไม่ใช่ความยาวประโยค** ภาษาไทยไม่มีเครื่องหมาย
จบประโยค ตัวที่ทำให้อ่านยากคือช่วงยาวๆ ที่ไม่มีที่พักตา ให้แต่ละช่วงอยู่ที่ประมาณสามถึงห้าคำ

**เว้นวรรคใหญ่แทนจุด** จบความคิดหนึ่งแล้วเว้นวรรค ไม่ใส่จุด

**เว้นวรรคเล็กคั่นไทยกับอังกฤษเสมอ** เขียน `web browser เอาไว้สำหรับ debug` ไม่ใช่
`web browserเอาไว้สำหรับ debug` อันหลังทำให้สายตาสะดุดทันที

**ห้ามใช้จุลภาคในภาษาไทย** ใช้การเว้นวรรคแทน

**ย่อหน้าละสามถึงห้าประโยค ไม่เกินเจ็ด** ประโยคแรกของย่อหน้าต้องแบกน้ำหนัก ถ้าผู้อ่าน
อ่านแค่ประโยคแรกของทุกย่อหน้าแล้วยังตามเรื่องได้ แปลว่าเขียนถูก

## 3. สรรพนามและน้ำเสียง

**เรา** สำหรับสิ่งที่ผู้เขียนกับผู้อ่านทำด้วยกัน เช่น เราจะสร้าง loop ตัวนี้

**คุณ** สำหรับสิ่งที่ผู้อ่านทำเอง หรือสิ่งที่ผู้อ่านข้ามได้

**ผม** ใช้เฉพาะตอนสารภาพความผิดพลาดของตัวเอง ซึ่งมีค่ามากและควรใช้เมื่อมีของจริง

**ครับ ใช้ตอนจบหัวข้อเท่านั้น** ไม่ใช้ในเนื้อความ การใส่ทุกย่อหน้าทำให้เนื้อหาเบาลง
การไม่ใส่เลยทำให้เย็นชา ใส่ตอนปิดหัวข้อคือจุดที่พอดี

**ห้ามใช้ภาษาพูดแบบไม่เป็นทางการ** เช่น รึป่าว หรอ คับ หรือการลากสระ อันนี้เหมาะกับ blog
แต่ในหนังสือมันแปลว่ายังไม่ได้ตรวจ

**แต่ก็ห้ามเป็นทางการแบบเอกสารราชการ** กฎข้อบนกันภาษาแชท ข้อนี้กันอีกด้าน คำอย่าง
กล่าวคือ อันเป็น จึงมีความจำเป็น และการเปลี่ยนกริยาเป็นนามด้วย การ ทุกคำ ทำให้ประโยค
ฟังเหมือนรายงาน ให้ใช้กริยาตรงๆ แทน เขียน model อ่านได้กี่ token แทน ปริมาณ token
ที่ model สามารถรับได้

**แบบทดสอบ อ่านออกเสียงในหัว** ถ้าประโยคนั้นไม่ใช่สิ่งที่คุณจะพูดกับเพื่อนร่วมงาน
ให้เขียนใหม่ นี่คือแบบทดสอบเดียวที่จับได้ทั้งภาษาแข็งเกินและอ่อนเกิน

## 4. จังหวะ

กฎในหัวข้อนี้มาทีหลังกฎอื่น เพราะฉบับแรกของหนังสือทำตามกฎอื่นครบแล้วยังอ่านทื่อ
พอนับดูพบว่ามีย่อหน้าที่ขึ้นต้นด้วยป้ายตัวหนา 368 ย่อหน้า ในนั้น 139 ย่อหน้าขึ้นต้นด้วย
คำว่า ทำไม และทั้ง 16 บทเปิดด้วยประโยคเดียวกัน หนังสือที่โครงเหมือนกันทุกย่อหน้า
อ่านเหมือนเอกสารอ้างอิง ต่อให้เนื้อหาข้างในดีแค่ไหน

**ห้ามขึ้นย่อหน้าด้วยป้ายตัวหนา** ป้ายอย่าง ทำไมต้องมี หรือ มันคืออะไร คือนั่งร้านของ
คนเขียน ไม่ใช่ของคนอ่าน เหตุผลต้องอยู่ในประโยค ให้คำว่า เพราะ ทำงานแทนป้าย ตัวหนา
ใช้ได้กับประโยคเดียวที่เป็นข้อสรุปของทั้งหัวข้อ และหัวข้อหนึ่งควรมีไม่เกินหนึ่งประโยคแบบนั้น

**ย่อหน้าเปิดด้วยข้อสรุป ไม่ใช่การปูพื้น** ประโยคแรกบอกว่าอะไรจริง ประโยคถัดไปบอกว่าเพราะอะไร
ผู้อ่านที่เห็นข้อสรุปก่อนจะอ่านเหตุผลเพื่อตรวจสอบ ผู้อ่านที่เห็นการปูพื้นก่อนจะอ่านเพื่อรอว่า
เมื่อไหร่จะถึงประเด็น

**หลังประโยคยาวสามประโยคติดกัน ต้องมีประโยคสั้น** ประโยคสั้นคือที่ให้หยุดหายใจ และมันคือ
ที่ที่ข้อสรุปฟังหนักที่สุด ประโยคสั้นที่สุดในย่อหน้าควรเป็นประโยคที่สำคัญที่สุด

**หนึ่งประโยค หนึ่ง ซึ่ง** สาย ซึ่ง ที่ต่อกันสามชั้นคือสามประโยคที่ถูกยัดเป็นประโยคเดียว
ให้แยกออกมา

**ประโยคที่มีคำว่า ทำให้ เกิน หนึ่งครั้ง ให้เขียนใหม่** มันคือสัญญาณว่ากำลังเล่าสายเหตุและผล
ที่ยาวเกินจะถือไว้ในหัวทีเดียว

## 5. โครงของบท

**เปิดบทด้วยสิ่งที่บทนั้นแก้ ไม่ใช่ด้วยรายการสิ่งที่จะได้** ฉากที่มันพัง คำถามที่ยังไม่มีคำตอบ
หรือประโยคเดียวที่ทั้งบทตั้งอยู่บนนั้น ห้ามเปิดด้วย จบบทนี้คุณจะมี เพราะทุกบทที่เปิดแบบนั้น
อ่านเหมือนกันหมด ถ้าจะบอกว่าผู้อ่านจะได้อะไร บอกได้ในย่อหน้าที่สามหรือสี่ และบอกด้วยคำ
ที่ต่างกันทุกบท

**บอกว่าตรงไหนข้ามได้** ผู้อ่านที่รู้ว่าอนุญาตให้ไม่เข้าใจทุกอย่างจะอ่านต่อ ผู้อ่านที่คิดว่า
ต้องเข้าใจหมดจะปิดหนังสือ

**เตือนว่ายากแล้วยื่นแผนทันที** ห้ามเตือนอย่างเดียว ประโยคที่บอกว่าเรื่องนี้ยาก ต้องตามด้วย
ประโยคที่บอกว่าเราจะแบ่งมันเป็นกี่ขั้น

**ประโยคที่เปิดความคิดยาก ต้องเป็นประโยคที่โครงสร้างง่าย** เก็บประโยคซับซ้อนไว้ใช้หลังจาก
ผู้อ่านเข้าใจแล้ว

**สลับยากกับง่าย** บทที่ยากติดกันหลายหัวข้อทำให้คนเลิกอ่าน

**จบบทด้วยสิ่งที่รันได้** ทุกบทต้องจบด้วยโค้ดที่ทำงานจริง หรือชี้ว่าบทเรียนไหนในหลักสูตร
คือการลงมือทำเรื่องนี้

**รูปหนึ่งรูปเมื่อโครงสร้างเป็นกล่องกับลูกศร** ตำราทุกเล่มที่หนังสือนี้เทียบด้วยมีรูปประกอบ
ในทุกบท และรูปที่คุ้มคือรูปของสิ่งที่ไหลจากกล่องหนึ่งไปอีกกล่อง loop ชั้นของ model ตาราง
ที่บวกกัน ที่ว่างบนการ์ด เขียนเป็น mermaid ในไฟล์เดียวกัน เพื่อให้แก้พร้อมโค้ดและไม่มีรูปไหน
ล้าสมัยโดยไม่มีใครเห็น รูปไม่ใช่ที่ใส่ข้อมูลใหม่ มันคือย่อหน้าที่อยู่ข้างมันในอีกรูปหนึ่ง

**บทที่สอนทฤษฎีจบด้วย อ่านต่อ** ภาค 0 กับภาค 4 อ้างถึงบทความและหนังสือจริง หัวข้อสุดท้าย
ของบทบอกชื่อผู้เขียน ปี และชื่อบทความ พร้อมหนึ่งประโยคว่ามันตรงกับหัวข้อไหนของบท ไม่ต้อง
มี URL เพราะชื่อบทความค้นเจอและ URL ตาย ภาค 1 ถึง 3 อ้างถึงโค้ดของโปรเจกต์นี้เองและไม่
ต้องมีหัวข้อนี้

## 6. การอธิบาย

**อธิบายที่คนละระดับกับสิ่งที่อธิบาย** ถ้าจะอธิบาย tool calling ห้ามพูดว่าคือการเรียก tool
ให้ลงไปต่ำกว่า คืออธิบายกลไก หรือขึ้นไปสูงกว่า คืออธิบายว่าทำไมถึงมีสิ่งนี้

**รูปธรรมก่อน นามธรรมทีหลัง** สถานการณ์จริง แล้วค่อยนิยาม แล้วค่อยเอาไปใช้

**อุปมาหนึ่งอัน หนึ่งประเด็น แล้วทิ้ง** อุปมาที่ลากยาวบังคับให้ผู้อ่านคิดว่าทุกส่วนแมปกับอะไร
ซึ่งเหนื่อยกว่าไม่มีอุปมา

**บอกว่าอันไหนคือวิธีที่ผิด ก่อนที่ผู้อ่านจะซึมซับมัน** การแสดงวิธีที่ผิดโดยไม่ติดป้ายคือ
การสอนวิธีที่ผิด

**เล่าเรื่องแทนการบอกกฎ** ถ้าผู้อ่านรู้ว่าอะไรเคยพังและพังยังไง เขาตัดสินใจเองได้ กฎที่ไม่มี
เหตุผลติดมาคือกฎที่ถูกลืมทันที

**พูดว่าไม่แน่ใจได้** และบอกได้ว่าเลือกไม่ทำอะไรเพราะอะไร มันทำให้ประโยคที่มั่นใจน่าเชื่อขึ้น

## 7. โค้ด

**ทุกบทต้องมีโค้ดจริงจาก repo** ไม่ใช่โค้ดสมมติ ถ้ายกมาต้องตรงกับไฟล์จริง

**ใช้ fenced code block พร้อมระบุภาษาเสมอ**

**อธิบายโค้ดก่อนวาง ไม่ใช่หลังวาง** ผู้อ่านที่เห็นโค้ดก่อนคำอธิบายจะพยายามเดาเอง แล้วต้อง
แก้ความเข้าใจทีหลัง ซึ่งแพงกว่า

**เทคนิค wishful thinking ใช้ได้** คือเขียนโค้ดที่เรียกฟังก์ชันที่ยังไม่มี ตั้งชื่อมัน ใช้มัน
แล้วค่อยสร้างทีหลัง เหมาะมากกับการอธิบาย agent loop
