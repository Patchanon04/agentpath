## 1. ประตูที่ปิดอยู่ กับหน้าต่างที่เปิดทิ้งไว้

**อาการ** `read_file` ปฏิเสธการอ่าน `.env` อย่างถูกต้อง มีข้อความ error
ที่ชัดเจน และมี test ยืนยัน แต่ `grep_files` ที่หา `API_KEY` คืนบรรทัดที่มี
กุญแจอยู่ในนั้นกลับมาให้ พร้อมชื่อไฟล์และเลขบรรทัด

**สาเหตุจริง** ไม่ใช่ความประมาท และไม่ใช่การลืมเขียนเช็ค สาเหตุคือ tool
สองตัวเดินคนละเส้นทาง ไปหาทรัพยากรเดียวกัน `read_file` เรียก `resolve_inside`
ซึ่งเป็นประตูที่ตรวจสองอย่าง คือพาธอยู่นอกโฟลเดอร์งานหรือไม่ และชื่อไฟล์
ดูเหมือนไฟล์ความลับหรือไม่ ส่วน `grep_files` และ `search_notes` เดินไฟล์เอง
ด้วย `rglob` แล้วอ่านโดยไม่ผ่านประตูนั้น

สังเกตว่า tool ที่มีช่องโหว่ ถูกเขียนสองบทหลังจากประตูถูกเขียน
โดยคนคนเดียวกันที่เขียนประตู นี่ไม่ใช่เรื่องบังเอิญ มันคือผลลัพธ์
ตามธรรมชาติของการเพิ่มเส้นทางที่สอง ไปหาทรัพยากรเดิม เพราะตอนที่คุณ
เขียนเส้นทางที่สอง คุณกำลังคิดเรื่องการค้นหา ไม่ได้คิดเรื่องกฎ
ที่คุณเขียนไว้เมื่อสองสัปดาห์ก่อน

**ชั้นที่สองของความผิดพลาดเดียวกัน** การแก้ครั้งแรกคือกรองชื่อไฟล์ในตัว
`_walk` เอง ซึ่งดูสมเหตุสมผล และยังผิดอยู่ เพราะ `rglob` เดินตาม symlink
(ลิงก์สัญลักษณ์ คือไฟล์ที่ชี้ไปยังไฟล์อื่น) และ junction บน Windows
ลิงก์ที่ถูกวางไว้ในโฟลเดอร์งาน โดยมีชื่อธรรมดา แต่ชี้ไปที่ไฟล์นอกโฟลเดอร์
จะผ่านตัวกรองที่ดูแค่ชื่อ เพราะชื่อที่เห็น กับไฟล์ที่ได้เป็นคนละอัน

ความคิดเห็นในโค้ดปัจจุบัน บันทึกทั้งสองชั้นไว้

```python
    Every candidate goes through resolve_inside rather than being filtered
    here. That matters because rglob follows symlinks and Windows junctions,
    so a link planted inside the workspace would otherwise let search read
    files the workspace was drawn to exclude. Filtering on the name of the
    link never sees the name of the target.
```

**หลักการทั่วไป** กฎที่บังคับใช้ที่ประตูเดียว ไม่ได้แปลว่าบังคับใช้ได้ทั้งระบบ
มันแปลว่าบังคับใช้ได้ กับทุกคนที่เดินผ่านประตูนั้น

คำถามที่ต้องถามทุกครั้งที่เพิ่ม tool ที่แตะทรัพยากรที่มีกฎอยู่แล้ว คือ
tool นี้เรียกฟังก์ชันเดิมหรือเปล่า ถ้าคำตอบคือ มันมีตรรกะการกรองของตัวเอง
คุณเพิ่งสร้างช่องโหว่ขึ้นมา แม้ตรรกะนั้นจะถูกต้อง ในวันที่คุณเขียน เพราะ
กฎสองชุดที่ต้องตรงกันตลอดไป จะไม่ตรงกัน ในวันที่มีคนแก้ชุดหนึ่ง

หลักการนี้ไม่ได้จำกัด อยู่ที่ความปลอดภัย มันคือเหตุผลเดียวกับที่การตรวจสอบ
สิทธิ์ต้องอยู่ใน query ไม่ใช่กรองผลลัพธ์ทีหลัง ตามบทที่ 10 และเป็นเหตุผล
เดียวกับที่ `user_ref` ต้องถูกใส่โดยโค้ด ไม่ใช่โดย model ตามบทที่ 9

## 2. ตัวตรวจที่บอกว่างานไม่คืบหน้า แล้วหยุดงานที่กำลังคืบหน้า

**อาการ** agent หยุดกลางงานที่กำลังไปได้ดี แล้วบอกว่ามันวนอยู่กับที่
ทั้งที่มันไม่ได้วน งานที่ควรเสร็จในสิบรอบ ตายที่รอบที่ห้า

**สาเหตุจริง** ตัวตรวจนั้นถูกเพิ่มใน 1.0.1 เพื่อแก้ปัญหาจริง คือ model
ที่ติด loop แล้วเรียก tool เดิมซ้ำๆ ด้วย argument ที่ต่างกันนิดเดียว เกณฑ์
ที่เลือกใช้คือ ถ้า tool คืนข้อความเดิมสามครั้งติด แปลว่าไม่มีความคืบหน้า

เหตุผลเบื้องหลัง ฟังดูสมเหตุสมผล คือถ้าผลลัพธ์เหมือนเดิม แสดงว่าไม่มีอะไร
เปลี่ยน ปัญหาคือมันไม่จริง คำสั่ง shell ที่สำเร็จ โดยไม่พิมพ์อะไรออกมา
คืนข้อความเดียวกันเสมอ สำหรับงานที่ต่างกัน โดยสิ้นเชิง การสร้างโฟลเดอร์
การคัดลอกไฟล์ และการตั้งค่า ล้วนสำเร็จอย่างเงียบๆ และมีหน้าตาของผลลัพธ์
เหมือนกันหมด agent ที่ทำงานสามอย่างสำเร็จติดกัน จึงถูกตัดสินว่าติด loop

`CHANGELOG.md` บันทึกไว้ตรงๆ ว่ามันถูกถอดออก

```text
The no progress check added in 1.0.1 decided a run had stalled when a
tool returned the same text three times, which a command that succeeds
quietly does for every different thing it does, so it stopped real work.
Reading progress from the shape of the output is not something a cheap check
can do correctly and it has been removed.
```

**สิ่งที่มาแทน** คือการวัดจากฝั่งตรงข้าม แทนที่จะดูว่า ผลลัพธ์เหมือนเดิมไหม
ให้ดูว่าคำขอเหมือนเดิมไหม ซึ่งเป็นสิ่งที่เราควบคุมรูปแบบได้เอง

```python
def loose_signature(call: ToolCall) -> str:
    """The same idea, but blind to whitespace and letter case.

    This one is for spotting a model going in circles, not for deciding what
    is allowed. A model that retries with a trailing space added, or with a
    word capitalised, has not changed anything and should not get a fresh
    fingerprint for it.
    """
```

**หลักการทั่วไปข้อแรก** การเดาสถานะภายใน จากรูปร่างของผลลัพธ์ เป็นสิ่งที่
ทำผิดง่ายมาก เพราะรูปร่างของผลลัพธ์ ไม่ได้เป็นของคุณ มันเป็นของ tool
ของโปรแกรมที่ tool เรียก และของระบบปฏิบัติการ สามฝ่ายนั้น ไม่ได้สัญญาอะไร
กับคุณเรื่องว่า ผลลัพธ์ที่ต่างงานจะมีหน้าตาต่างกัน

ส่วนคำขอที่ model ส่งมา คือสิ่งที่ผ่านมือเราก่อนเสมอ เรากำหนดรูปแบบของ
`ToolCall` เอง เราตัดสินใจเองว่า จะละเลยช่องว่างและตัวพิมพ์ การวัดจากตรงนั้น
จึงเป็นการวัดสิ่งที่เรานิยามได้ ไม่ใช่สิ่งที่เราสังเกตได้

**หลักการทั่วไปข้อที่สอง** การหยุดผิด แพงกว่าการหยุดช้า และนี่คือการคำนวณ
ราคาสองด้าน แบบเดียวกับหัวข้อ 2.4 ของบทที่ 9 แค่ผลลัพธ์ออกมาคนละทาง

| ความผิดพลาด | ราคา |
| --- | --- |
| หยุดช้า คือปล่อยให้วนอีกสองสามรอบก่อนจับได้ | ค่าเรียก model สองสามครั้ง |
| หยุดผิด คือหยุดงานที่กำลังคืบหน้า | งานทั้งงานตาย ผู้ใช้ต้องเริ่มใหม่ และไม่รู้ว่าทำไม |

เมื่อราคาสองด้านต่างกันขนาดนี้ เกณฑ์ต้องถูกตั้งให้ระวังการหยุดผิด ไม่ใช่
ระวังการหยุดช้า และนั่นคือเหตุผลที่โค้ดปัจจุบัน เตือนก่อนหนึ่งครั้ง
แล้วค่อยหยุด แทนที่จะหยุดทันที

**หลักการทั่วไปข้อที่สาม และเป็นข้อที่คนพูดถึงน้อยที่สุด** การแก้บั๊ก
คือการเปลี่ยนแปลง และการเปลี่ยนแปลงสร้างบั๊กได้ บั๊กนี้ไม่ได้อยู่ใน 1.0.0
มันถูกใส่เข้ามาโดยการแก้ใน 1.0.1 และถูกจับได้ในรีวิวรอบถัดไป ซึ่งแปลว่า
ถ้าไม่มีรีวิวรอบที่สอง มันจะยังอยู่

## 3. เส้นตายที่ไม่มีใครไปถึง

**อาการ** model เขียน regular expression (นิพจน์ปกติ คือรูปแบบสำหรับค้นหา
ข้อความ) ที่มีตัวคูณซ้อนกัน เช่นรูปแบบที่ห่อการทำซ้ำ ไว้ในการทำซ้ำอีกชั้น
แล้ว process ค้างทั้งตัว ไม่ตอบสนอง กด Ctrl กับ C ก็ไม่หยุด ทั้งที่โค้ดมี
timeout เขียนไว้ชัดเจน

**สาเหตุจริง** และเรื่องนี้มีสองความพยายามที่ล้มเหลวก่อนจะได้คำตอบ

ความพยายามแรกคือ ตรวจเส้นตายระหว่างบรรทัด คือวนอ่านไฟล์ทีละบรรทัด แล้วเช็ค
นาฬิกาก่อนจับคู่บรรทัดถัดไป วิธีนี้ไม่เคยได้ทำงาน เพราะบรรทัดเดียวก็พอที่จะ
ทำให้การจับคู่ใช้เวลา แบบเลขชี้กำลัง การตรวจครั้งถัดไป จะเกิดขึ้นหลังจาก
บรรทัดนั้นจับคู่เสร็จ ซึ่งอาจเป็นอีกหลายชั่วโมงข้างหน้า

ความพยายามที่สองคือ ย้ายตัวจับเวลาไปอยู่ในเธรดต่างหาก ซึ่งเป็นวิธีมาตรฐาน
และที่นี่มันก็ไม่ทำงาน เพราะการจับคู่ regular expression ไม่ปล่อย
GIL (Global Interpreter Lock คือกลไกที่อนุญาตให้เธรดเดียวรัน bytecode ของ
Python ได้ในเวลาหนึ่ง) เธรดที่ถืออยู่ ไม่คืนการควบคุมจนกว่าการจับคู่จะจบ
เธรดที่รอเส้นตาย จึงไม่มีโอกาสได้รัน มันรอในคิวเดียวกับสิ่งที่มันรออยู่

ความคิดเห็นในโค้ดปัจจุบัน บันทึกทั้งสองความพยายามไว้ เพราะทั้งคู่คือสิ่งที่
คนถัดไปจะลองก่อน

```python
        # The search runs in a separate process. Two earlier attempts at
        # this did not work and both are worth knowing about. Checking a
        # deadline between lines never gets a turn, because one line is
        # enough to go exponential and nothing interrupts a regular
        # expression that is already running. Moving it to a thread does
        # not help either, because matching does not release the global
        # interpreter lock, so the thread waiting on the deadline cannot
        # run until the matching it is waiting on has finished.
        #
        # A separate process can simply be killed, which is the only thing
        # that actually works. The cost is about a tenth of a second of
        # start up on every search.
```

**หลักการทั่วไป** การรอในเธรดเดียวกับสิ่งที่รออยู่ ไม่ใช่การรอ

พูดให้ทั่วไปกว่านั้น timeout ที่เป็นจริงต้องมีสองเงื่อนไข และต้องมีครบทั้งคู่
ข้อแรกคือ ผู้รอต้องได้รัน ในขณะที่สิ่งที่ถูกรอกำลังรันอยู่ ข้อที่สองคือ
ผู้รอต้องมีอำนาจ หยุดสิ่งนั้นได้จริง การขาดข้อใดข้อหนึ่ง ทำให้ timeout
กลายเป็นความคิดเห็น

ตารางนี้คือวิธีตรวจ ว่ากลไกหยุดของคุณเป็นจริงหรือไม่

| กลไก | ผู้รอได้รันไหม | หยุดของจริงได้ไหม |
| --- | --- | --- |
| เช็คนาฬิกาใน loop ของตัวเอง | ได้ ถ้า loop หมุนถึง | ได้ แต่ต้องหมุนถึงก่อน |
| เธรดที่จับเวลา | ได้ ถ้าสิ่งที่รอปล่อย GIL | ไม่ ต้องขอให้อีกฝ่ายหยุดเอง |
| process แยก | ได้เสมอ | ได้ ฆ่าได้ตรงๆ |

**และราคาถูกจ่ายอย่างรู้ตัว** การแยก process เพิ่มเวลาเริ่มต้นประมาณหนึ่ง
ในสิบวินาที ในทุกครั้งที่ค้นหา นั่นเป็นราคาที่ถูกจดไว้ในความคิดเห็น ไม่ใช่
ราคาที่ถูกซ่อน ซึ่งเป็นความต่าง ระหว่างการแลกที่ตั้งใจ กับการแลกที่ไม่รู้ตัว

เรื่องนี้อยู่ตระกูลเดียวกับกฎในบทที่ 6 ที่ว่าการฆ่า process ต้องฆ่าทั้งต้น
ไม่ใช่แค่ราก ทั้งสองเรื่องคือความผิดพลาดชนิดเดียวกัน คือหยุดสิ่งที่คุณคิดว่า
คุณเริ่มไว้ แทนที่จะหยุดสิ่งที่กำลังทำงานอยู่จริงครับ

## 4. บั๊กที่หายไปเมื่อลองซ้ำ

**อาการ** สั่งให้ agent ดูรายชื่อไฟล์ ในโฟลเดอร์ที่มีชื่อไฟล์ภาษาไทย
ผลลัพธ์ออกมาเป็นเครื่องหมายคำถาม แทนตัวอักษร แต่เฉพาะคำสั่งแรกของ session
เท่านั้น คำสั่งที่สองเป็นต้นไปถูกต้องหมด

นี่คืออาการที่ทำให้คนเสียเวลาทั้งบ่าย เพราะปฏิกิริยาแรกของทุกคน เมื่อเห็น
ผลลัพธ์แปลกคือลองซ้ำ และการลองซ้ำ ให้คำตอบว่าไม่มีปัญหา

**สาเหตุจริง มีสองชั้นที่ซ้อนกัน และเป็นคนละเรื่อง**

ชั้นแรกคือการถอดรหัส โค้ดถอดรหัสผลลัพธ์ของคำสั่งเป็น utf-8 เสมอ พร้อมกับ
ตั้งค่าให้แทนที่อักขระที่อ่านไม่ออก แทนที่จะล้มเหลว บน Windows มีการเข้ารหัส
สองแบบอยู่บนเครื่องเดียวกัน เพราะเครื่องมือสมัยใหม่เขียน utf-8 ส่วนโปรแกรม
ที่ติดมากับระบบส่วนใหญ่ เขียน codepage เดิมของคอนโซล การถอดรหัสอย่างหลัง
ด้วยอย่างแรก เปลี่ยนทุกอักขระที่ไม่ใช่ละตินให้เป็นเครื่องหมายแทนที่
โดยไม่มีคำเตือนสักคำ

ชั้นที่สอง ไม่ใช่ปัญหาการถอดรหัสเลย มันคือปัญหาการเข้ารหัส shell เขียน
อักขระเหล่านั้นออกมาใน codepage เดิม ไม่ได้ตั้งแต่แรก ตัวอักษรถูกทำลาย
ก่อนที่เราจะเห็น byte ด้วยซ้ำ และการถอดรหัส กู้สิ่งที่ไม่เคยถูกเข้ารหัสไม่ได้

**ทำไมมันเกิดเฉพาะคำสั่งแรก** เพราะการแก้ที่ชัดเจนที่สุด คือเติม `chcp`
ไว้หน้าคำสั่ง เพื่อเปลี่ยน codepage ไม่ทำงานอย่างที่คิด คำสั่งที่เป็น
builtin ของ shell เช่น `dir` อ่านค่า codepage ตอนที่ shell เริ่มทำงาน
ซึ่งเกิดก่อนที่ `chcp` ในบรรทัดคำสั่งเดียวกัน จะได้รัน ผลคือคำสั่งแรกของ
session เสียชื่อไฟล์ไป ส่วนคำสั่งถัดไปที่ shell เริ่มใหม่แล้ว ได้ค่าที่ถูก

การแก้ที่ถูกคือตั้ง codepage ของ process ตัวเองครั้งเดียว ก่อนที่ shell
ตัวไหนจะถูกสร้างขึ้น

```python
def _use_utf8_console():
    """Put this process's console into utf-8, once.

    The chcp inside the command is not enough on its own. A shell builtin
    such as dir reads the codepage when the shell starts, which happens
    before the chcp in the same command line runs, so the first command of a
    session still lost non ASCII names while every later one was fine. That
    is a maddening thing to debug and the fix is to set it here instead,
    before any shell exists.
    """
```

**หลักการทั่วไปข้อแรก** บั๊กที่หายไปเมื่อลองซ้ำ คือบั๊กที่แพงที่สุด
ไม่ใช่เพราะมันยากในเชิงเทคนิค แต่เพราะการลองซ้ำ คือขั้นตอนแรกของการตรวจสอบ
ของทุกคน และมันให้คำตอบว่าไม่มีปัญหา ความผิดพลาดชนิดนี้ จึงไม่ถูกรายงาน
ไม่ถูกบันทึก และเมื่อมีคนรายงาน ก็ไม่มีใครทำซ้ำได้

วิธีจัดการที่ใช้ได้จริงคือ เมื่อเห็นอาการที่หายไปเมื่อลองซ้ำ ให้ถือว่า
สิ่งที่ต่างระหว่างครั้งแรก กับครั้งที่สอง คือสาเหตุ อย่าถือว่ามันคือ
ความบังเอิญ ในกรณีนี้ สิ่งที่ต่างคือ shell ตัวใหม่ กับ shell ที่เริ่มไปแล้ว
ซึ่งชี้ตรงไปที่คำตอบ

**หลักการทั่วไปข้อที่สอง** การแก้ต้องอยู่ก่อน สิ่งที่มันตั้งใจจะแก้
ไม่ใช่อยู่บรรทัดเดียวกัน `chcp` ที่อยู่หน้าคำสั่งในบรรทัดเดียวกัน ดูเหมือน
มาก่อน แต่มันไม่ได้มาก่อน สิ่งที่อ่านค่านั้นจริงๆ ลำดับที่มองเห็นในข้อความ
ไม่ใช่ลำดับของเหตุการณ์

**หลักการทั่วไปข้อที่สาม** ค่าที่ตั้งให้แทนที่อักขระที่อ่านไม่ออก
เปลี่ยนการสูญเสียข้อมูลที่ดัง ให้กลายเป็นการสูญเสียข้อมูลที่เงียบ
นี่คือความผิดพลาดตระกูลเดียวกับที่บทที่ 1 เตือนไว้ เรื่องการเปลี่ยน JSON
ที่ขาดกลางคันให้เป็น dict ว่างอย่างเงียบๆ ทั้งสองกรณีเลือกที่จะทำงานต่อ
ด้วยข้อมูลที่ผิด แทนที่จะหยุดแล้วบอกว่าอ่านไม่ออก

ทางเลือกของโค้ดปัจจุบันจึงกลับด้าน มันลอง utf-8 ก่อน ด้วยเหตุผล
ที่ระบุไว้ตรงๆ ว่ามันล้มเหลวอย่างดัง เมื่อได้ input ที่ผิด
ส่วนการเข้ารหัสแบบไบต์เดียว ไม่เคยล้มเหลวเลย และการเข้ารหัสที่ไม่เคย
ล้มเหลว คือการเข้ารหัส ที่ไม่เคยบอกคุณว่ามันอ่านผิด

## 5. test ที่ทดสอบเครื่องคุณ ไม่ใช่ทดสอบโค้ด

**อาการ** test ผ่านทั้งหมดบนเครื่องของคนเขียน แล้วพฤติกรรมจริงต่างออกไป
บนเครื่องอื่น

**สาเหตุจริง** สองข้อที่แยกกัน

ข้อแรกคือความผิดพลาดในหัวข้อที่ 4 ทั้งหมด เป็นความผิดพลาดที่ผูกกับแพลตฟอร์ม
และผูกกับ locale ของเครื่อง มันไม่มีทางปรากฏบนเครื่อง Linux เลยแม้แต่น้อย
เพราะไม่มี codepage ของคอนโซลให้ผิดพลาด ผลคือ test ชุดเดียวกันที่รันบน
เครื่องเดียว ให้ความมั่นใจที่ไม่ตรงกับความจริงของผู้ใช้ที่ใช้อีกระบบหนึ่ง

CI ของโปรเจกต์นี้จึงรัน test บนสี่เป้าหมาย ไม่ใช่หนึ่ง

```yaml
  tests:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        python-version: ["3.10", "3.12"]
```

สองระบบปฏิบัติการคูณสองรุ่นของ Python เท่ากับสี่ และ `fail-fast` ถูกตั้ง
เป็นเท็จโดยตั้งใจ เพราะเมื่อเป้าหมายหนึ่งล้มเหลว สิ่งที่คุณต้องรู้คือ
อีกสามเป้าหมายเป็นยังไง การหยุดทั้งชุดทันที ทำให้คุณเห็นความล้มเหลวหนึ่งอัน
แทนที่จะเห็นรูปแบบของมัน และรูปแบบคือสิ่งที่บอกว่าเป็นปัญหาของระบบปฏิบัติการ
หรือของรุ่นภาษา

ข้อที่สองคือสำเนา `CHANGELOG.md` บันทึกไว้ว่า การแก้ทั้งสองเรื่องต้องถูกนำ
ไปใส่ในสำเนาของ shell tool ในบทเรียนอีกสิบหกชุด ซึ่งไม่มีการแก้เหล่านั้น
เลย และไม่มีการแก้ timeout ด้วย

```text
Both fixes also reached the sixteen lesson copies of the shell tool, which
had none of this and none of the timeout fix either, so the course was
teaching two bugs.
```

ประโยคสุดท้ายคือประเด็น โค้ดที่ไม่มี test และไม่ได้ถูกรัน ในสภาพแวดล้อมอื่น
ไม่ได้แค่มีบั๊ก มันสอนบั๊ก

**หลักการทั่วไป** test ที่ไม่เคยรันในสภาพแวดล้อมอื่น คือ test ที่ทดสอบ
เครื่องของคุณ ไม่ใช่ทดสอบโค้ด

สิ่งที่แยกสองอย่างนี้ออกจากกัน คือรายการของสิ่งที่ test ของคุณสมมติไว้เงียบๆ
และรายการนั้นยาวกว่าที่ใครคิด

| สิ่งที่ถูกสมมติเงียบๆ | เมื่อไหร่มันไม่จริง |
| --- | --- |
| การเข้ารหัสของคอนโซล | Windows ที่ตั้ง locale ต่างกัน |
| ตัวคั่นพาธและความไวต่อตัวพิมพ์ | ระบบไฟล์คนละแบบ |
| พฤติกรรมของ `dict` และของไลบรารีมาตรฐาน | Python คนละรุ่น |
| ความเร็วของดิสก์และของเครือข่าย | test ที่มี timeout สั้น บนเครื่อง CI ที่ช้ากว่า |
| การมี git หรือเครื่องมืออื่นติดตั้งอยู่ | เครื่องที่สะอาด |

**ผลเชิงปฏิบัติ** ถ้าโปรเจกต์ของคุณ จะถูกใช้บนสองระบบปฏิบัติการ ต้องรัน
บนสองระบบตั้งแต่วันแรก ไม่ใช่ตอนที่มีคนบ่น เพราะการเพิ่มเป้าหมายที่สอง
เข้าไปในโปรเจกต์ที่มี test สามร้อยตัว ซึ่งไม่เคยรันที่นั่นเลย แปลว่า
คุณจะได้ความล้มเหลวสามสิบอันพร้อมกัน ที่ไม่มีอันไหนเกี่ยวกับงานที่คุณ
กำลังทำอยู่

## 6. บั๊กร้ายแรงเกือบทั้งหมดถูกพบโดยการรีวิว ไม่ใช่โดย test

นี่คือหัวข้อที่สำคัญที่สุดของบทนี้ และมันเป็นข้อความเชิงตัวเลข ไม่ใช่
ความเห็น

**ข้อเท็จจริง** เมื่อหลักสูตรครบ 24 บทในรุ่น 1.0.0 test suite เขียวทั้งหมด
รีวิวที่ตามมา พบช่องโหว่ความปลอดภัยในหัวข้อที่ 1 ความผิดพลาดเชิงตรรกะอีก
เก้าข้อ และข้อผิดพลาดในเนื้อหาราวสี่สิบจุด `CHANGELOG.md` เขียนไว้เอง
ว่าอะไรคือส่วนที่ควรสังเกต

```text
Everything found by a full review of the finished course. Nothing here was
caught by the test suite, which is the part worth noticing.
```

**สาเหตุจริง และมันไม่ใช่เรื่องจำนวน test** โปรเจกต์นี้มี test จำนวนมาก
และแต่ละตัวถูกต้อง ปัญหาคือทุกตัว import ชิ้นส่วนหนึ่งเข้ามา แล้วเรียกมัน
โดยที่ชิ้นส่วนรอบข้าง ถูกแทนด้วยของปลอม บั๊กที่หลุดออกไปทั้งหมด ไม่ได้อยู่
ในชิ้นส่วน มันอยู่ในการต่อสาย ระหว่างชิ้นส่วน

เอกสารบนสุดของ test ชุดที่เขียนใหม่ในรุ่น 1.0.2 บันทึกไว้ตรงๆ

```python
"""Run the command line as a real process, the way a person runs it.

Every other test in this suite imports a piece and calls it. That is useful,
and it is also how four bugs shipped. A run started with --yes refused every
command it had just approved. One interrupt disabled the shell for the rest
of a session. Running out of turns printed a traceback. Resuming added a
second system prompt every time. All four lived in the wiring between the
pieces, which is exactly the part a unit test does not touch.
"""
```

ให้อ่านสี่บั๊กนั้นอีกครั้ง ทุกอันเป็นความผิดพลาด ที่ผู้ใช้เจอในนาทีแรก
ของการใช้งาน และไม่มีอันไหนที่ต้องการ ความรู้ลึกซึ้งในการค้นพบ มันต้องการ
แค่คนคนหนึ่งที่รันโปรแกรมจริงแล้วใช้มันจริง ซึ่งเป็นสิ่งที่ไม่มี test ตัวไหน
ทำอยู่

**สิ่งที่ทำในรุ่น 1.0.2** คือ test สิบหกตัวที่เริ่มคำสั่งเป็น process จริง
ชี้ไปที่ server จำลอง แล้วดูว่ามีอะไรอยู่บนดิสก์ และมีอะไรถูกพิมพ์ออกมา
ไม่มีอะไรถูกแทนด้วยของปลอม นอกจากตัว model

**และวิธีการเขียนมันสำคัญพอๆ กับการมีมัน** test แต่ละตัวถูกยืนยันด้วยการ
เอาบั๊กที่มันควรจะกัน ใส่กลับเข้าไป แล้วดูว่ามันล้มเหลวจริง สองตัวในนั้น
ไม่ล้มเหลวในความพยายามครั้งแรก ซึ่งแปลว่า มันจะเป็น test สีเขียวที่ไม่ได้
ทดสอบอะไรเลย และเป็นเหตุผลที่รุ่นเดียวกัน ต้องแก้ server จำลองให้ตอบด้วย
tool call หลายตัวในข้อความเดียวได้ อย่างที่ model จริงทำ เพื่อให้เส้นทาง
ที่ปรากฏเฉพาะตอนที่รอบถูกทิ้งกลางคัน ถูกเดินถึงได้เลย

**หลักการทั่วไปข้อแรก** ไม่มี test ไหนประกอบชิ้นส่วนแล้วใช้จริง แปลว่า
ไม่มีใครรู้ว่าระบบทำงานได้ ที่รู้คือแต่ละชิ้นทำงานได้ ซึ่งเป็นคนละข้อความ
และในระบบที่ประกอบจากชิ้นส่วนหลายชั้น เหมือน agent harness ระยะห่างระหว่าง
สองข้อความนี้กว้างมาก

**หลักการทั่วไปข้อที่สอง** test ที่ไม่เคยเห็นบั๊กจริงล้มเหลว คือ test
ที่คุณไม่รู้ว่ามันทดสอบอะไร วิธีตรวจมีอยู่วิธีเดียว คือใส่บั๊กกลับเข้าไป
แล้วดูว่ามันแดง ถ้ามันยังเขียว test นั้นไม่ได้กันอะไรเลย มันแค่ทำให้ตัวเลข
ความครอบคลุมดูดีขึ้น

**หลักการทั่วไปข้อที่สาม** การรีวิวกับ test ไม่ได้แทนกัน มันจับความผิดพลาด
คนละชนิด

| ชนิดของความผิดพลาด | ใครจับได้ |
| --- | --- |
| ตรรกะภายในฟังก์ชันหนึ่งผิด | unit test |
| การถดถอย คือสิ่งที่เคยทำงานแล้วพัง | test suite ทั้งชุด |
| การต่อสายระหว่างชิ้นส่วนผิด | test ที่รันของจริงทั้งเส้น |
| กฎที่มีสองเส้นทางแล้วเส้นหนึ่งไม่ทำตาม | การรีวิวที่ถามว่ามีเส้นทางไหนอีก |
| การตัดสินใจที่ถูกต้องทางเทคนิคแต่ผิดเป้าหมาย | การรีวิวเท่านั้น |

สองแถวล่างคือแถวที่ test ไม่มีทางจับได้ เพราะ test ตรวจว่าโค้ดทำสิ่งที่คุณ
เขียนไว้ว่ามันควรทำ มันไม่ได้ตรวจว่า สิ่งที่คุณเขียนไว้นั้นถูกต้อง

## 7. สิ่งที่เปลี่ยนไปในวิธีสร้างโปรเจกต์นี้

ห้าเรื่องข้างบน กลายเป็นกฎที่บังคับใช้ กับการเปลี่ยนแปลงทุกครั้ง หลังจากนั้น

1. tool ใหม่ที่แตะทรัพยากรที่มีกฎอยู่แล้ว ต้องเรียกฟังก์ชันประตูเดิม
   ไม่ใช่มีตรรกะการกรองของตัวเอง และการรีวิวต้องถามคำถามนี้ ก่อนคำถามอื่น

2. heuristic ที่มีอำนาจหยุดงานได้ ต้องวัดจากสิ่งที่เรากำหนดรูปแบบเอง
   ไม่ใช่จากรูปร่างของผลลัพธ์ที่เป็นของคนอื่น และต้องเตือนก่อนหยุด

3. timeout ที่จับเวลาสิ่งที่ไม่ยอมคืนการควบคุม ต้องอยู่คนละ process
   ไม่ใช่คนละเธรด และราคาของการแยก ต้องถูกเขียนไว้ในโค้ด

4. การแปลงข้อมูลที่อาจล้มเหลว ต้องล้มเหลวอย่างดัง ไม่ใช่แทนที่อย่างเงียบ

5. test ที่รันทั้งระบบเป็น process จริง มีค่ามากกว่า unit test สิบตัว
   และ test ทุกตัวที่เขียนเพื่อกันบั๊ก ต้องถูกยืนยันด้วยการเอาบั๊กใส่กลับ

## 8. เหตุการณ์แต่ละเรื่องอยู่ในกฎข้อไหนของภาค 1

| เหตุการณ์ | บทที่กฎถูกเขียนไว้ |
| --- | --- |
| search เดินอ้อมการปฏิเสธไฟล์ความลับ | บทที่ 5 หัวข้อ 3 ประตูเดียว |
| ตัวตรวจความคืบหน้าที่หยุดงานถูก | บทที่ 2 หัวข้อ 5 max_turns ไม่ได้แก้ปัญหาการวนไม่รู้จบ |
| เส้นตายที่ไม่มีใครไปถึง | บทที่ 6 หัวข้อ 6 การขัดจังหวะต้องหยุดของจริงทุกชั้น |
| การถอดรหัสที่แทนที่อย่างเงียบ | บทที่ 1 หัวข้อ 5 ความพังที่ถูกซ่อนกลายเป็นความพังที่ซ้ำ |
| tool call ที่ไม่มีผลลัพธ์คู่เมื่อถูกขัดจังหวะ | บทที่ 4 หัวข้อ 4 กฎคู่เดียวกันนี้โผล่อีกครั้งตอนถูกขัดจังหวะ |
| eval ที่รวมงานชื่อซ้ำเข้าด้วยกัน | บทที่ 7 หัวข้อ 5 eval ต้องรอดจากความล้มเหลวของตัวมันเอง |
| การต่อสายที่ไม่มี test ตัวไหนแตะ | บทที่ 7 หัวข้อ 3 การตรวจเชิงกลไกที่แข็งแรงที่สุดคือการรันของจริง |

ตารางนี้คือคำตอบของคำถามว่า ทำไมหนังสือเล่มนี้ ถึงเน้นเรื่องที่ดูจุกจิก
เช่นการที่ผลลัพธ์ของ tool ต้องเป็นข้อความ ไม่ใช่ exception หรือการที่
`safe` ต้องมีค่าเริ่มต้นเป็นเท็จ ทุกข้อในนั้น เป็นราคาที่มีคนจ่ายไปแล้ว

## 9. สิ่งที่ควรเอาไปใช้กับโปรเจกต์ของคุณ

ถ้าจะเอาอะไรไปจากบทนี้ข้อเดียว ให้เอาข้อนี้

**ก่อนปล่อยของ ให้มีคนหนึ่งคนนั่งลงแล้วใช้ระบบจริง เป็นเวลาสามสิบนาที
โดยไม่มองโค้ด** สี่บั๊กในหัวข้อที่ 6 ทั้งหมดถูกพบด้วยวิธีนี้ ไม่ใช่ด้วย
การอ่านโค้ด และไม่ใช่ด้วยการรัน test เพราะทั้งสี่ปรากฏตัวในนาทีแรก
ของการใช้งานจริง และไม่ปรากฏเลยในสภาพแวดล้อมอื่น

สามสิบนาทีนั้น ถูกกว่าทุกอย่างที่เขียนไว้ในบทนี้ และมันคือสิ่งที่ทุกคนข้าม
เพราะ test เขียวอยู่ครับ
