## 1. ประตูที่ปิดอยู่ กับหน้าต่างที่เปิดทิ้งไว้

อาการคือ `read_file` ปฏิเสธการอ่าน `.env` อย่างถูกต้อง มีข้อความ error ที่ชัดเจน และมี
test ยืนยัน แต่ `grep_files` ที่หา `API_KEY` คืนบรรทัดที่มีกุญแจอยู่ในนั้นกลับมาให้ พร้อม
ชื่อไฟล์และเลขบรรทัด

สาเหตุจริงไม่ใช่ความประมาท และไม่ใช่การลืมเขียนเช็ค สาเหตุคือ tool สองตัวเดินคนละเส้น
ทางไปหาทรัพยากรเดียวกัน `read_file` เรียก `resolve_inside` ซึ่งเป็นประตูที่ตรวจสองอย่าง
คือพาธอยู่นอกโฟลเดอร์งานหรือไม่ และชื่อไฟล์ดูเหมือนไฟล์ความลับหรือไม่ ส่วน `grep_files`
และ `search_notes` เดินไฟล์เองด้วย `rglob` แล้วอ่านโดยไม่ผ่านประตูนั้น

สังเกตว่า tool ที่มีช่องโหว่ ถูกเขียนสองบทหลังจากประตูถูกเขียน โดยคนคนเดียวกันที่เขียน
ประตู นี่เป็นผลตามธรรมชาติของการเพิ่มเส้นทางที่สองไปหา
ทรัพยากรเดิม เพราะตอนที่คุณเขียนเส้นทางที่สอง คุณกำลังคิดเรื่องการค้นหา ไม่ได้คิดเรื่อง
กฎที่คุณเขียนไว้เมื่อสองสัปดาห์ก่อน

ความผิดพลาดเดียวกันมีชั้นที่สอง การแก้ครั้งแรกคือกรองชื่อไฟล์ในตัว `_walk` เอง ซึ่งดู
สมเหตุสมผล และยังผิดอยู่ เพราะ `rglob` เดินตาม symlink (ไฟล์ที่ชี้ไป
ยังไฟล์อื่น) และ junction บน Windows ลิงก์ที่ถูกวางไว้ในโฟลเดอร์งาน โดยมีชื่อธรรมดา แต่ชี้
ไปที่ไฟล์นอกโฟลเดอร์ จะผ่านตัวกรองที่ดูแค่ชื่อ เพราะชื่อที่เห็นกับไฟล์ที่ได้เป็นคนละอัน

ความคิดเห็นในโค้ดปัจจุบันบันทึกทั้งสองชั้นไว้

```python
    Every candidate goes through resolve_inside rather than being filtered
    here. That matters because rglob follows symlinks and Windows junctions,
    so a link planted inside the workspace would otherwise let search read
    files the workspace was drawn to exclude. Filtering on the name of the
    link never sees the name of the target.
```

หลักการทั่วไปคือกฎที่บังคับใช้ที่ประตูเดียว ไม่ได้แปลว่าบังคับใช้ได้ทั้งระบบ มันแปลว่า
บังคับใช้ได้กับทุกคนที่เดินผ่านประตูนั้น

คำถามที่ต้องถามทุกครั้งที่เพิ่ม tool ที่แตะทรัพยากรที่มีกฎอยู่แล้ว คือ tool นี้เรียกฟังก์ชัน
เดิมหรือเปล่า ถ้าคำตอบคือมันมีตรรกะการกรองของตัวเอง คุณเพิ่งสร้างช่องโหว่ขึ้นมา แม้
ตรรกะนั้นจะถูกต้องในวันที่คุณเขียน เพราะกฎสองชุดที่ต้องตรงกันตลอดไป จะไม่ตรงกันในวันที่
มีคนแก้ชุดหนึ่ง

หลักการนี้ไม่ได้จำกัดอยู่ที่ความปลอดภัย มันคือเหตุผลเดียวกับที่การตรวจสอบสิทธิ์ต้องอยู่ใน
query ไม่ใช่กรองผลลัพธ์ทีหลัง ตามบทที่ 10 และเป็นเหตุผลเดียวกับที่ `user_ref` ต้องถูกใส่

## 2. ตัวตรวจที่บอกว่างานไม่คืบหน้า แล้วหยุดงานที่กำลังคืบหน้า

อาการคือ agent หยุดกลางงานที่กำลังไปได้ดี แล้วบอกว่ามันวนอยู่กับที่ ทั้งที่มันไม่ได้วน งาน
ที่ควรเสร็จในสิบรอบ ตายที่รอบที่ห้า

สาเหตุจริงคือตัวตรวจนั้นถูกเพิ่มใน 1.0.1 เพื่อแก้ปัญหาจริง คือ model ที่ติด loop แล้วเรียก
tool เดิมซ้ำๆ ด้วย argument ที่ต่างกันนิดเดียว เกณฑ์ที่เลือกใช้คือถ้า tool คืนข้อความเดิม
สามครั้งติด แปลว่าไม่มีความคืบหน้า

เหตุผลเบื้องหลังฟังดูสมเหตุสมผล คือถ้าผลลัพธ์เหมือนเดิม แสดงว่าไม่มีอะไรเปลี่ยน ปัญหาคือ
มันไม่จริง คำสั่ง shell ที่สำเร็จโดยไม่พิมพ์อะไรออกมา คืนข้อความเดียวกันเสมอสำหรับงาน
ที่ต่างกันโดยสิ้นเชิง การสร้างโฟลเดอร์ การคัดลอกไฟล์ และการตั้งค่า ล้วนสำเร็จอย่างเงียบๆ
และมีหน้าตาของผลลัพธ์เหมือนกันหมด agent ที่ทำงานสามอย่างสำเร็จติดกัน จึงถูกตัดสินว่า
ติด loop

`CHANGELOG.md` บันทึกไว้ตรงๆ ว่ามันถูกถอดออก

```text
The no progress check added in 1.0.1 decided a run had stalled when a
tool returned the same text three times, which a command that succeeds
quietly does for every different thing it does, so it stopped real work.
Reading progress from the shape of the output is not something a cheap check
can do correctly and it has been removed.
```

สิ่งที่มาแทนคือการวัดจากฝั่งตรงข้าม แทนที่จะดูว่าผลลัพธ์เหมือนเดิมไหม ให้ดูว่าคำขอเหมือน
เดิมไหม ซึ่งเป็นสิ่งที่เราควบคุมรูปแบบได้เอง

```python
def loose_signature(call: ToolCall) -> str:
    """The same idea, but forgiving about the edges of a value.

    This one is for spotting a model going in circles, not for deciding
    what is allowed. A model that retries with a trailing space added has
    changed nothing and should not get a fresh fingerprint for it. A model
    that changes a letter's case has, because a case sensitive search for
    Error and a search for error are different searches. Permission
    decisions keep using the exact signature, because there the difference
    between two nearly identical commands can be the whole point.
    """
```

ประโยคสุดท้ายคือเส้นแบ่งที่ห้ามลืม fingerprint แบบหลวมใช้จับการวนเท่านั้น การตัดสินใจว่า
อะไรรันได้ต้องใช้ signature แบบเต็มรูปเสมอ และคำว่าหลวมเองก็ต้องหลวมพอดี เวอร์ชันแรกมอง
ข้ามตัวพิมพ์ด้วย แล้วมันตัดสินว่า model ที่ขยายการค้นหาจาก Error เป็น error กำลังวนอยู่
กับที่ ทั้งที่การค้นหาแบบ case sensitive สองครั้งนั้นเป็นคนละการค้นหา งานจริงเลยถูกหยุด
ตอนนี้จึงมองข้ามแค่ช่องว่างหัวท้าย เพราะสองคำสั่งที่ต่างกันแค่ตัวพิมพ์ อาจเป็นคนละคำสั่ง
กันจริงๆ

หลักการทั่วไปมีสามข้อ

ข้อแรก การเดาสถานะภายในจากรูปร่างของผลลัพธ์ เป็นสิ่งที่ทำผิดง่ายมาก เพราะรูปร่าง
ของผลลัพธ์ไม่ได้เป็นของคุณ มันเป็นของ tool ของโปรแกรมที่ tool
เรียก และของระบบปฏิบัติการ สามฝ่ายนั้นไม่ได้สัญญาอะไรกับคุณ เรื่องว่าผลลัพธ์ที่
ต่างงานจะมีหน้าตาต่างกัน ส่วนคำขอที่ model
ส่งมา คือสิ่งที่ผ่านมือเราก่อนเสมอ เรากำหนดรูปแบบของ `ToolCall`
เอง เราตัดสินใจเองว่าจะละเลยช่องว่างและตัวพิมพ์ การวัดจากตรงนั้นจึงเป็นการวัดสิ่
งที่เรานิยามได้ ไม่ใช่สิ่งที่เราสังเกตได้

ข้อที่สอง การหยุดผิดแพงกว่าการหยุดช้า และนี่คือการคำนวณราคาสองด้าน แบบเดียวกับหัวข้อ
2.4 ของบทที่ 9 แค่ผลลัพธ์ออกมาคนละทาง

| ความผิดพลาด | ราคา |
| --- | --- |
| หยุดช้า คือปล่อยให้วนอีกสองสามรอบก่อนจับได้ | ค่าเรียก model สองสามครั้ง |
| หยุดผิด คือหยุดงานที่กำลังคืบหน้า | งานทั้งงานตาย ผู้ใช้ต้องเริ่มใหม่ และไม่รู้ว่าทำไม |

เมื่อราคาสองด้านต่างกันขนาดนี้ เกณฑ์ต้องถูกตั้งให้ระวังการหยุดผิด ไม่ใช่ระวังการหยุดช้า

## 3. เส้นตายที่ไม่มีใครไปถึง

อาการคือ model เขียน regular expression (รูปแบบที่ใช้ค้นข้อความ หรือ regex) ที่มี
ตัวคูณซ้อนกัน เช่น `(a+)+b` ที่ถูกยิงใส่บรรทัดซึ่งมีตัว a สี่สิบตัวและไม่มีตัว b เลย
เครื่องต้องไล่ทุกวิธีที่จะแบ่ง a สี่สิบตัวออกเป็นกลุ่ม ซึ่งเป็นจำนวนที่โตแบบเลขชี้กำลัง
แล้ว process ค้างทั้งตัว ไม่ตอบ
สนอง กด Ctrl กับ C ก็ไม่หยุด ทั้งที่โค้ดมี timeout เขียนไว้ชัดเจน

เรื่องนี้มีสองความพยายามที่ล้มเหลวก่อนจะได้คำตอบ

ความพยายามแรกคือตรวจเส้นตายระหว่างบรรทัด คือวนอ่านไฟล์ทีละบรรทัด แล้วเช็คนาฬิกา
ก่อนจับคู่บรรทัดถัดไป วิธีนี้ไม่เคยได้ทำงาน เพราะบรรทัดเดียวก็พอที่จะทำให้การจับคู่ใช้
เวลาแบบเลขชี้กำลัง การตรวจครั้งถัดไปจะเกิดขึ้นหลังจากบรรทัดนั้นจับคู่เสร็จ ซึ่งอาจเป็นอีก
หลายชั่วโมงข้างหน้า

ความพยายามที่สองคือย้ายตัวจับเวลาไปอยู่ใน thread (เธรด คือสายการทำงานคู่ขนานในโปรแกรมเดีย
ว) ต่างหาก ซึ่งเป็นวิธีมาตรฐาน และที่นี่มันก็ไม่ทำงาน เพราะการจับคู่ regular expression
ไม่ปล่อย GIL (Global Interpreter Lock คือกลไกที่ยอมให้ Python รัน bytecode ได้ทีละ
thread เท่านั้น) thread ที่ถืออยู่ไม่คืนการควบคุมจนกว่าการจับคู่จะจบ thread ที่รอเส้นตาย
จึงไม่มีโอกาสได้รัน มันรอในคิวเดียวกับสิ่งที่มันรออยู่

ความคิดเห็นในโค้ดปัจจุบันบันทึกทั้งสองความพยายามไว้ เพราะทั้งคู่คือสิ่งที่คนถัดไปจะลอง
ก่อน

```python
        # The search runs in a separate process. Two earlier attempts at
        # this did not work and both are worth knowing about. Checking a
        # deadline between lines never gets a turn, because one line is
        # enough to go exponential and nothing interrupts a regular
        # expression that is already running. Moving it to a thread does
        # not help either, because matching does not release the global
        # interpreter lock, so the thread waiting on the deadline cannot
        # run until the matching it is waiting on has finished.
        #
        # A separate process can simply be killed, which is the only thing
        # that actually works. The cost is about a tenth of a second of
        # start up on every search.
```

หลักการทั่วไปคือการรอใน thread เดียวกับสิ่งที่รออยู่ ไม่ใช่การรอ

พูดให้ทั่วไปกว่านั้น timeout
ที่เป็นจริงต้องมีสองเงื่อนไข และต้องมีครบทั้งคู่ ข้อแรกคือผู้รอต้องได้รันในขณะ
ที่สิ่งที่ถูกรอกำลังรันอยู่ ข้อที่สองคือผู้รอต้องมีอำนาจหยุดสิ่งนั้นได้จริง การ
ขาดข้อใดข้อหนึ่งทำให้ timeout กลายเป็นความคิดเห็น

ตารางนี้คือวิธีตรวจว่ากลไกหยุดของคุณเป็นจริงหรือไม่

| กลไก | ผู้รอได้รันไหม | หยุดของจริงได้ไหม |
| --- | --- | --- |
| เช็คนาฬิกาใน loop ของตัวเอง | ได้ ถ้า loop หมุนถึง | ได้ แต่ต้องหมุนถึงก่อน |
| thread ที่จับเวลา | ได้ ถ้าสิ่งที่รอปล่อย GIL | ไม่ ต้องขอให้อีกฝ่ายหยุดเอง |
| process แยก | ได้เสมอ | ได้ ฆ่าได้ตรงๆ |

และราคาถูกจ่ายอย่างรู้ตัว การแยก process เพิ่มเวลาเริ่มต้นประมาณหนึ่งในสิบวินาทีในทุก
ครั้งที่ค้นหา นั่นเป็นราคาที่ถูกจดไว้ในความคิดเห็น ไม่ใช่ราคาที่ถูกซ่อน ซึ่งเป็นความต่าง
ระหว่างการแลกที่ตั้งใจกับการแลกที่ไม่รู้ตัว

เรื่องนี้อยู่ตระกูลเดียวกับกฎในบทที่ 6 ที่ว่าการฆ่า process ต้องฆ่าทั้งต้น ไม่ใช่แค่ราก ทั้ง
สองเรื่องคือความผิดพลาดชนิดเดียวกัน คือหยุดสิ่งที่คุณคิดว่าคุณเริ่มไว้ แทนที่จะหยุดสิ่งที่
กำลังทำงานอยู่จริงครับ

## 4. บั๊กที่หายไปเมื่อลองซ้ำ

อาการคือสั่งให้ agent ดูรายชื่อไฟล์ในโฟลเดอร์ที่มีชื่อไฟล์ภาษาไทย ผลลัพธ์ออกมาเป็น
เครื่องหมายคำถามแทนตัวอักษร แต่เฉพาะคำสั่งแรกของ session เท่านั้น คำสั่งที่สองเป็นต้นไป
ถูกต้องหมด

นี่คืออาการที่ทำให้คนเสียเวลาทั้งบ่าย เพราะปฏิกิริยาแรกของทุกคนเมื่อเห็นผลลัพธ์แปลกคือ
ลองซ้ำ และการลองซ้ำให้คำตอบว่าไม่มีปัญหา

สาเหตุจริงมีสองชั้นที่ซ้อนกัน และเป็นคนละเรื่อง

ชั้นแรกคือการถอดรหัส โค้ดถอดรหัสผลลัพธ์ของคำสั่งเป็น utf-8 เสมอ พร้อมกับตั้งค่าให้แทน
ที่อักขระที่อ่านไม่ออกแทนที่จะล้มเหลว บน Windows มีการเข้ารหัสสองแบบอยู่บนเครื่องเดียว
กัน เพราะเครื่องมือสมัยใหม่เขียน utf-8 ส่วนโปรแกรมที่ติดมากับระบบส่วนใหญ่เขียน codepage
เดิมของคอนโซล การถอดรหัสอย่างหลังด้วยอย่างแรก เปลี่ยนทุกอักขระที่ไม่ใช่ละตินให้เป็น
เครื่องหมายแทนที่ โดยไม่มีคำเตือนสักคำ บทพื้นฐานที่ 1 แสดงว่า byte ของอักขระไทย
หน้าตาเป็นยังไง และทำไมมันถึงอ่านผิดได้ง่ายขนาดนั้น

ชั้นที่สองไม่ใช่ปัญหาการถอดรหัสเลย มันคือปัญหาการเข้ารหัส shell เขียนอักขระเหล่านั้นออก
มาใน codepage เดิมไม่ได้ตั้งแต่แรก ตัวอักษรถูกทำลายก่อนที่เราจะเห็น byte ด้วยซ้ำ และการ
ถอดรหัสกู้สิ่งที่ไม่เคยถูกเข้ารหัสไม่ได้

มันเกิดเฉพาะคำสั่งแรกเพราะการแก้ที่ชัดเจนที่สุด คือเติม `chcp` ไว้หน้าคำสั่งเพื่อเปลี่ยน
codepage ไม่ทำงานอย่างที่คิด คำสั่งที่เป็น builtin ของ shell เช่น `dir` อ่านค่า codepage
ตอนที่ shell เริ่มทำงาน ซึ่งเกิดก่อนที่ `chcp` ในบรรทัดคำสั่งเดียวกันจะได้รัน ผลคือคำสั่ง
แรกของ session เสียชื่อไฟล์ไป ส่วนคำสั่งถัดไปที่ shell เริ่มใหม่แล้วได้ค่าที่ถูก

การแก้ที่ถูกคือตั้ง codepage ของ process ตัวเองครั้งเดียว ก่อนที่ shell ตัวไหนจะถูกสร้างขึ้น

```python
def _use_utf8_console():
    """Put this process's console into utf-8, once.

    The chcp inside the command is not enough on its own. A shell builtin
    such as dir reads the codepage when the shell starts, which happens
    before the chcp in the same command line runs, so the first command of a
    session still lost non ASCII names while every later one was fine. That
    is a maddening thing to debug and the fix is to set it here instead,
    before any shell exists.
    """
```

หลักการทั่วไปมีสามข้อ

ข้อแรก บั๊กที่หายไปเมื่อลองซ้ำคือบั๊กที่แพงที่สุด ไม่ใช่เพราะมันยากในเชิงเทคนิ
ค แต่เพราะการลองซ้ำคือขั้นตอนแรกของการตรวจสอบของทุกคน และมันให้คำตอบว่าไม่มีปัญ
หา ความผิดพลาดชนิดนี้จึงไม่ถูกรายงาน ไม่ถูกบันทึก และเมื่อมีคนรายงาน ก็ไม่มีใคร
ทำซ้ำได้ วิธีจัดการที่ใช้ได้จริงคือเมื่อเห็นอาการที่หายไปเมื่อลองซ้ำ ให้ถือว่า
สิ่งที่ต่างระหว่างครั้งแรกกับครั้งที่สองคือสาเหตุ อย่าถือว่ามันคือความบังเอิญ ใน
กรณีนี้สิ่งที่ต่างคือ shell ตัวใหม่กับ shell ที่เริ่มไปแล้ว ซึ่งชี้ตรงไปที่คำตอบ

ข้อที่สอง การแก้ต้องอยู่ก่อนสิ่งที่มันตั้งใจจะแก้ ไม่ใช่อยู่บรรทัดเดียวกัน
`chcp` ที่อยู่หน้าคำสั่งในบรรทัดเดียวกันดูเหมือนมาก่อน แต่มันไม่ได้มาก่อนสิ่งที่
อ่านค่านั้นจริงๆ ลำดับที่มองเห็นในข้อความไม่ใช่ลำดับของเหตุการณ์

ข้อที่สาม ค่าที่ตั้งให้แทนที่อักขระที่อ่านไม่ออก เปลี่ยนการสูญเสียข้อมูลที่ดังให้กลายเป็น
การสูญเสียข้อมูลที่เงียบ นี่คือความผิดพลาดตระกูลเดียวกับที่บทที่ 1 เตือนไว้ เรื่องการ
เปลี่ยน JSON ที่ขาดกลางคันให้เป็น dict ว่างอย่างเงียบๆ ทั้งสองกรณีเลือกที่จะทำงานต่อด้วย
ข้อมูลที่ผิด แทนที่จะหยุดแล้วบอกว่าอ่านไม่ออก ทางเลือกของโค้ดปัจจุบันจึงกลับด้าน มันลอง
utf-8 ก่อน ด้วยเหตุผลที่ระบุไว้ตรงๆ ว่ามันล้มเหลวอย่างดังเมื่อได้ input ที่ผิด ส่วนการเข้า
รหัสแบบไบต์เดียวไม่เคยล้มเหลวเลย และการเข้ารหัสที่ไม่เคยล้มเหลว คือการเข้ารหัสที่ไม่
เคยบอกคุณว่ามันอ่านผิด

## 5. test ที่ทดสอบเครื่องคุณ ไม่ใช่ทดสอบโค้ด

อาการคือ test ผ่านทั้งหมดบนเครื่องของคนเขียน แล้วพฤติกรรมจริงต่างออกไปบนเครื่องอื่น

สาเหตุจริงมีสองข้อที่แยกกัน

ข้อแรกคือความผิดพลาดในหัวข้อที่ 4 ทั้งหมด เป็นความผิดพลาดที่ผูกกับแพลตฟอร์มและผูกกับ
locale ของเครื่อง มันไม่มีทางปรากฏบนเครื่อง Linux เลยแม้แต่น้อย เพราะไม่มี codepage ของ
คอนโซลให้ผิดพลาด ผลคือ test ชุดเดียวกันที่รันบนเครื่องเดียว ให้ความมั่นใจที่ไม่ตรงกับ
ความจริงของผู้ใช้ที่ใช้อีกระบบหนึ่ง

CI ของโปรเจกต์นี้จึงรัน test บนสี่เป้าหมาย ไม่ใช่หนึ่ง

```yaml
  tests:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        python-version: ["3.10", "3.12"]
```

สองระบบปฏิบัติการคูณสองรุ่นของ Python เท่ากับสี่ และ `fail-fast` ถูกตั้งเป็นเท็จโดยตั้งใจ
เพราะเมื่อเป้าหมายหนึ่งล้มเหลว สิ่งที่คุณต้องรู้คืออีกสามเป้าหมายเป็นยังไง การหยุดทั้งชุด
ทันที ทำให้คุณเห็นความล้มเหลวหนึ่งอันแทนที่จะเห็นรูปแบบของมัน และรูปแบบคือสิ่งที่บอกว่า
เป็นปัญหาของระบบปฏิบัติการหรือของรุ่นภาษา

ข้อที่สองคือสำเนา `CHANGELOG.md` บันทึกไว้ว่าการแก้ทั้งสองเรื่องต้องถูกนำไปใส่ในสำเนา
ของ shell tool ในบทเรียนอีกสิบหกชุด ซึ่งไม่มีการแก้เหล่านั้นเลย และไม่มีการแก้ timeout
ด้วย

```text
Both fixes also reached the sixteen lesson copies of the shell tool, which
had none of this and none of the timeout fix either, so the course was
teaching two bugs.
```

ประโยคสุดท้ายคือประเด็น โค้ดที่ไม่มี test และไม่ได้ถูกรันในสภาพแวดล้อมอื่น ไม่ได้แค่มี
บั๊ก มันสอนบั๊ก

หลักการทั่วไปคือ test ที่ไม่เคยรันในสภาพแวดล้อมอื่น คือ test ที่ทดสอบเครื่องของคุณ ไม่ใช่
ทดสอบโค้ด สิ่งที่แยกสองอย่างนี้ออกจากกัน คือรายการของสิ่งที่ test ของคุณสมมติไว้เงียบๆ
และรายการนั้นยาวกว่าที่ใครคิด

| สิ่งที่ถูกสมมติเงียบๆ | เมื่อไหร่มันไม่จริง |
| --- | --- |
| การเข้ารหัสของคอนโซล | Windows ที่ตั้ง locale ต่างกัน |
| ตัวคั่นพาธและความไวต่อตัวพิมพ์ | ระบบไฟล์คนละแบบ |
| พฤติกรรมของ `dict` และของไลบรารีมาตรฐาน | Python คนละรุ่น |
| ความเร็วของดิสก์และของเครือข่าย | test ที่มี timeout สั้น บนเครื่อง CI ที่ช้ากว่า |
| การมี git หรือเครื่องมืออื่นติดตั้งอยู่ | เครื่องที่สะอาด |

ผลเชิงปฏิบัติคือถ้าโปรเจกต์ของคุณจะถูกใช้บนสองระบบปฏิบัติการ ต้องรันบนสองระบบตั้งแต่
วันแรก ไม่ใช่ตอนที่มีคนบ่น เพราะการเพิ่มเป้าหมายที่สองเข้าไปในโปรเจกต์ที่มี test สามร้อย
ตัวซึ่งไม่เคยรันที่นั่นเลย แปลว่าคุณจะได้ความล้มเหลวสามสิบอันพร้อมกัน ที่ไม่มีอันไหน
เกี่ยวกับงานที่คุณกำลังทำอยู่

## 6. บั๊กร้ายแรงเกือบทั้งหมดถูกพบโดยการรีวิว ไม่ใช่โดย test

นี่คือหัวข้อที่สำคัญที่สุดของบทนี้ และมันเป็นข้อความเชิงตัวเลข ไม่ใช่ความเห็น

ข้อเท็จจริงคือประโยคที่เปิดบทนี้ และ `CHANGELOG.md` เขียนไว้เองว่าอะไรคือส่วนที่ควร
สังเกต

```text
Everything found by a full review of the finished course. Nothing here was
caught by the test suite, which is the part worth noticing.
```

สาเหตุจริงไม่ใช่เรื่องจำนวน test โปรเจกต์นี้มี test จำนวนมาก และแต่ละตัวถูกต้อง ปัญหาคือ
ทุกตัว import ชิ้นส่วนหนึ่งเข้ามาแล้วเรียกมัน โดยที่ชิ้นส่วนรอบข้างถูกแทนด้วยของปลอม บั๊ก
ที่หลุดออกไปทั้งหมดไม่ได้อยู่ในชิ้นส่วน มันอยู่ในการต่อสายระหว่างชิ้นส่วน

เอกสารบนสุดของ test ชุดที่เขียนใหม่ในรุ่น 1.0.2 บันทึกไว้ตรงๆ

```python
"""Run the command line as a real process, the way a person runs it.

Every other test in this suite imports a piece and calls it. That is useful,
and it is also how four bugs shipped. A run started with --yes refused every
command it had just approved. One interrupt disabled the shell for the rest
of a session. Running out of turns printed a traceback. Resuming added a
second system prompt every time. All four lived in the wiring between the
pieces, which is exactly the part a unit test does not touch.
"""
```

ยกสองอันมาดูให้ชัด อันแรกคือคนที่รัน CLI ด้วย `--yes` เพราะไม่อยากถูกถาม แล้วทุกคำสั่ง
ถูกปฏิเสธ ทั้งที่ flag นั้นแปลว่าอนุญาตทุกอย่างพอดี อันที่สี่คือ resume ที่เติม system
prompt อีกชุดเข้าไปทุกครั้ง บทสนทนาที่ resume สามรอบจึงเริ่มด้วย system prompt สี่ชุด
ซ้อนกัน

ให้อ่านสี่บั๊กนั้นอีกครั้ง ทุกอันเป็นความผิดพลาดที่ผู้ใช้เจอในนาทีแรกของการใช้งาน และไม่มี
อันไหนที่ต้องการความรู้ลึกซึ้งในการค้นพบ มันต้องการแค่คนคนหนึ่งที่รันโปรแกรมจริงแล้วใช้
มันจริง ซึ่งเป็นสิ่งที่ไม่มี test ตัวไหนทำอยู่

สิ่งที่ทำในรุ่น 1.0.2 คือ test สิบหกตัวที่เริ่มคำสั่งเป็น process จริง ชี้ไปที่ server จำลอง
แล้วดูว่ามีอะไรอยู่บนดิสก์และมีอะไรถูกพิมพ์ออกมา ไม่มีอะไรถูกแทนด้วยของปลอม นอกจากตัว
model

และวิธีการเขียนมันสำคัญพอๆ กับการมีมัน test แต่ละตัวถูกยืนยันด้วยการเอาบั๊กที่มันควรจะ
กันใส่กลับเข้าไป แล้วดูว่ามันล้มเหลวจริง สองตัวในนั้นไม่ล้มเหลวในความพยายามครั้งแรก ซึ่ง
แปลว่ามันจะเป็น test สีเขียวที่ไม่ได้ทดสอบอะไรเลย และเป็นเหตุผลที่รุ่นเดียวกันต้องแก้
server จำลองให้ตอบด้วย tool call หลายตัวในข้อความเดียวได้ อย่างที่ model จริงทำ เพื่อให้
เส้นทางที่ปรากฏเฉพาะตอนที่รอบถูกทิ้งกลางคัน ถูกเดินถึงได้เลย

หลักการทั่วไปมีสามข้อ

ข้อแรก ไม่มี test ไหนประกอบชิ้นส่วนแล้วใช้จริง แปลว่าไม่มีใครรู้ว่าระบบทำงานได้ ที่รู้คือ
แต่ละชิ้นทำงานได้ ซึ่งเป็นคนละข้อความ และในระบบที่ประกอบจากชิ้นส่วนหลายชั้น เหมือน
agent harness ระยะห่างระหว่างสองข้อความนี้กว้างมาก

ข้อที่สอง test ที่ไม่เคยเห็นบั๊กจริงล้มเหลว คือ test ที่คุณไม่รู้ว่ามันทดสอบอะไร วิธีตรวจมี
อยู่วิธีเดียว คือใส่บั๊กกลับเข้าไปแล้วดูว่ามันแดง ถ้ามันยังเขียว test นั้นไม่ได้กันอะไรเลย
มันแค่ทำให้ตัวเลขความครอบคลุมดูดีขึ้น

ข้อที่สาม การรีวิวกับ test ไม่ได้แทนกัน มันจับความผิดพลาดคนละชนิด

| ชนิดของความผิดพลาด | ใครจับได้ |
| --- | --- |
| ตรรกะภายในฟังก์ชันหนึ่งผิด | unit test |
| การถดถอย คือสิ่งที่เคยทำงานแล้วพัง | test suite ทั้งชุด |
| การต่อสายระหว่างชิ้นส่วนผิด | test ที่รันของจริงทั้งเส้น |
| กฎที่มีสองเส้นทางแล้วเส้นหนึ่งไม่ทำตาม | การรีวิวที่ถามว่ามีเส้นทางไหนอีก |
| การตัดสินใจที่ถูกต้องทางเทคนิคแต่ผิดเป้าหมาย | การรีวิวเท่านั้น |

สองแถวล่างคือแถวที่ test ไม่มีทางจับได้ เพราะ test ตรวจว่าโค้ดทำสิ่งที่คุณเขียนไว้ว่ามัน
ควรทำ มันไม่ได้ตรวจว่าสิ่งที่คุณเขียนไว้นั้นถูกต้อง

## 7. สิ่งที่เปลี่ยนไปในวิธีสร้างโปรเจกต์นี้

หกเรื่องข้างบนยุบลงเหลือกฎห้าข้อ ที่บังคับใช้กับการเปลี่ยนแปลงทุกครั้งหลังจากนั้น

1. tool ใหม่ที่แตะทรัพยากรที่มีกฎอยู่แล้ว ต้องเรียกฟังก์ชันประตูเดิม ไม่ใช่มีตรรกะการกรอง
   ของตัวเอง และการรีวิวต้องถามคำถามนี้ก่อนคำถามอื่น

2. heuristic ที่มีอำนาจหยุดงานได้ ต้องวัดจากสิ่งที่เรากำหนดรูปแบบเอง ไม่ใช่จากรูปร่างของ
   ผลลัพธ์ที่เป็นของคนอื่น และต้องเตือนก่อนหยุด

3. timeout ที่จับเวลาสิ่งที่ไม่ยอมคืนการควบคุม ต้องอยู่คนละ process ไม่ใช่คนละ thread
   และราคาของการแยกต้องถูกเขียนไว้ในโค้ด

4. การแปลงข้อมูลที่อาจล้มเหลว ต้องลองทางที่ล้มเหลวอย่างดังก่อน และแทนที่อย่างเงียบได้
   ก็ต่อเมื่อทุกทางล้มเหลวแล้ว

5. test ที่รันทั้งระบบเป็น process จริง มีค่ามากกว่า unit test สิบตัว และ test ทุกตัวที่
   เขียนเพื่อกันบั๊ก ต้องถูกยืนยันด้วยการเอาบั๊กใส่กลับ

## 9. สิ่งที่ควรเอาไปใช้กับโปรเจกต์ของคุณ

ถ้าจะเอาอะไรไปจากบทนี้ข้อเดียว ให้เอาข้อนี้

**ก่อนปล่อยของ ให้มีคนหนึ่งคนนั่งลงแล้วใช้ระบบจริง เป็นเวลาสามสิบนาที โดยไม่มองโค้ด**

สี่บั๊กในหัวข้อที่ 6 ถูกพบตอนรีวิว ไม่ใช่ด้วยการรัน test แต่ทั้งสี่จะปรากฏตัวในนาทีแรก
ของการใช้งานจริง และการนั่งใช้จริงสามสิบนาทีจะจับมันได้ก่อนรีวิวเสียอีก

สามสิบนาทีนั้นถูกกว่าทุกอย่างที่เขียนไว้ในบทนี้ และมันคือสิ่งที่ทุกคนข้าม เพราะ test
เขียวอยู่ครับ
