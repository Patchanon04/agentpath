## 1. pyproject.toml ทีละส่วน

ไฟล์เดียวนี้ตอบคำถามสี่ข้อที่คนละคนถาม คนที่ติดตั้งถามว่าต้องมีอะไรก่อน เครื่องมือที่
build ถามว่าเอาไฟล์ไหนไปใส่ เทอร์มินัลถามว่าคำสั่งชื่ออะไรและไปเรียกอะไร ส่วน linter กับ
test runner ถามว่าตั้งค่าไว้ยังไง

นี่คือทั้งไฟล์ของโปรเจกต์นี้ ราวห้าสิบบรรทัด รวมคอมเมนต์ที่อธิบายสี่จุดซึ่งแต่ละจุดเคย
เป็นบั๊กหรือการตัดสินใจที่ต้องแก้ต่าง

```toml
[project]
# The distribution is agentpath-kit and the package it installs is
# agentpath, which is a mismatch on purpose. PyPI refused the bare name as
# too close to agent_path, an abandoned PDM template placeholder. Splitting
# the two is the ordinary Python answer, the same way scikit-learn installs
# sklearn, and it leaves the import, the command and the environment
# variables alone.
name = "agentpath-kit"
version = "1.0.6"
description = "Learn how AI agents actually work by building a real one, from a single LLM call to a full agent harness."
readme = "README.md"
requires-python = ">=3.10"
license = { text = "MIT" }
dependencies = ["httpx>=0.27"]

[project.urls]
Homepage = "https://github.com/Patchanon04/agentpath"
Changelog = "https://github.com/Patchanon04/agentpath/blob/main/CHANGELOG.md"

[project.scripts]
agentpath = "agentpath.cli:main"

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.6"]
# numpy is used by the foundations track and by the numpy demos in the
# training track. The package and the twenty four lessons stay on httpx
# alone, and a person who wants only those never installs it.
foundations = ["numpy>=1.26"]
# Part 4 of the book. The numpy demos in training/ need only the group
# above. The real fine tuning scripts need these, and a GPU, and are not
# run in CI.
training = ["torch>=2.2", "transformers>=4.46", "peft>=0.12", "trl>=0.20", "datasets>=2.20"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

# The sdist is what pip falls back to, so it carries only what building
# the package needs. The course itself lives in the repository, and the
# README says where.
[tool.hatch.build.targets.sdist]
include = ["/src", "/README.md", "/CHANGELOG.md", "/LICENSE"]

[tool.hatch.build.targets.wheel]
packages = ["src/agentpath"]

[tool.ruff]
line-length = 100
exclude = ["lessons"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.pytest.ini_options]
testpaths = ["tests"]
```

`[project]` คือสิ่งที่ผู้ติดตั้งมองเห็น ชื่อ รุ่น คำบรรยาย ไฟล์ที่จะถูกแสดงเป็นหน้าแรก รุ่น
Python ที่ต่ำที่สุดที่รองรับ สัญญาอนุญาต และ dependency (ของที่ต้องพึ่งพา คือ package
อื่นที่ต้องมีก่อนถึงจะทำงานได้) คอมเมนต์ก้อนแรกคือเรื่องของหัวข้อที่ 6 ชื่อบนดัชนีกับชื่อที่
import ไม่ตรงกันโดยตั้งใจ

`dependencies` เขียนเป็นขอบล่าง ไม่ใช่การตรึง และความต่างนี้สำคัญ
ถ้าตรึงไว้ที่รุ่นเดียว คนที่ติดตั้ง package ของคุณคู่กับอย่างอื่นที่ต้องการรุ่นใหม่ก
ว่าจะติดตั้งไม่ได้เลย และ
ทางแก้เดียวคือรอให้คุณออกรุ่นใหม่ library ควรบอกรุ่นเก่าที่สุดที่รู้ว่าใช้ได้ แล้วปล่อยให้
แอปพลิเคชันเป็นคนตัดสินใจที่เหลือ การตรึงรุ่นถูกต้องสำหรับแอปพลิเคชันที่คุณ deploy เอง
และผิดสำหรับ package ที่คนอื่นติดตั้ง

`[project.urls]` คือลิงก์สองอันที่จะโผล่บนหน้า package ในดัชนี คนที่เจอ package จากการ
ค้นหาต้องมีทางกลับมาหา repository และบันทึกรุ่นได้ในคลิกเดียว ไม่อย่างนั้นหน้านั้นคือ
ทางตัน

`[project.optional-dependencies]` คือของที่ผู้ใช้ไม่ต้องได้ `pytest` กับ `ruff` เป็นเครื่อง
มือของคนพัฒนา การเอาไปใส่ใน `dependencies` แปลว่าทุกคนที่ติดตั้ง package นี้จะได้ตัวรัน
test กับ linter ติดมาด้วยโดยไม่มีเหตุผล กลุ่ม `foundations` เป็นเรื่องเดียวกันอีกมุม ภาค
พื้นฐานกับภาค 4 ของหนังสือคือสองที่ที่ใช้ numpy และคนที่ต้องการแค่ตัว package กับบทเรียน
ยี่สิบสี่บทเรียนไม่ควรต้องโหลดมันมาเลย ส่วนกลุ่ม `training` คือ library ฝึก model ที่หนัก
กว่านั้นอีกหลายเท่า และ CI ไม่ติดตั้งมันเลย

`[build-system]` คือคำตอบว่าใครเป็นคนประกอบ โปรเจกต์นี้ใช้ hatchling และ
`[tool.hatch.build.targets.wheel]` คือการชี้ว่าโค้ดจริงอยู่ใต้ `src` ไม่ได้อยู่ที่รากของ
repository ส่วนตาราง sdist ที่อยู่ก่อนหน้ามันคือเรื่องของหัวข้อที่ 3 และมันมีกับดักหนึ่งอันที่
ทำให้ build เสียไปหนึ่งรอบ

สองส่วนสุดท้ายไม่เกี่ยวกับการส่งมอบเลย มันคือการตั้งค่าเครื่องมือ ที่มาอยู่ไฟล์เดียวกัน
เพราะระบบนิเวศของ Python ตกลงกันว่าจะรวมการตั้งค่าไว้ที่นี่ แทนที่จะมีไฟล์ซ่อนคนละไฟล์
ต่อเครื่องมือหนึ่งตัว

## 2. console script คือชื่อคำสั่งที่แมปไปหาฟังก์ชัน

สองบรรทัดนี้คือสิ่งที่ทำให้คนพิมพ์คำว่า `agentpath` ในเทอร์มินัลแล้วมีอะไรเกิดขึ้น

```toml
[project.scripts]
agentpath = "agentpath.cli:main"
```

ฝั่งซ้ายคือชื่อคำสั่งที่จะถูกสร้างขึ้น ฝั่งขวาคือพาธของ module ตามด้วยชื่อฟังก์ชันที่จะถูก
เรียก ตอนติดตั้ง เครื่องมือติดตั้งจะสร้างไฟล์เล็กๆ ไว้ในโฟลเดอร์ที่อยู่ใน PATH ของ
environment นั้น ไฟล์นั้นทำอย่างเดียวคือ import module แล้วเรียกฟังก์ชัน

มันดีกว่าการให้คนพิมพ์ `python -m` เพราะมันซ่อนสองอย่างที่ผู้ใช้ไม่ควรต้องรู้ คือพาธของ
interpreter ที่ถูกตัว และชื่อ module ภายในของคุณ ผู้ใช้รู้แค่ชื่อคำสั่ง และคุณย้าย `main`
ไปอยู่ module อื่นวันหลังได้โดยที่คำสั่งยังเหมือนเดิม

สิ่งที่ต้องเป็นจริงในโค้ดคือฟังก์ชันนั้นต้องเรียกได้โดยไม่รับ argument บังคับ และต้องคืน
exit code หรือปล่อยให้ `SystemExit` ทำงาน ใน `cli.py` ลายเซ็นคือ `def main(argv=None)`
ซึ่ง `argv` มีค่าเริ่มต้น จึงเรียกแบบไม่ส่งอะไรได้ และการรับ `argv` ได้ทำให้ test เรียกมัน
ตรงๆ พร้อม argument ปลอมได้ด้วย โดยไม่ต้องไปยุ่งกับ `sys.argv` จริง

## 3. ทดสอบติดตั้งใน environment สะอาด ก่อน publish ไม่ใช่หลัง

นี่คือขั้นตอนที่คนข้าม และการข้ามมันคือเหตุผลที่รุ่นแรกของหลายโปรเจกต์ตามมาด้วยรุ่นที่
สองภายในหนึ่งชั่วโมง

เหตุผลที่ต้องเป็น environment สะอาดนั้นเจาะจงมาก package ของคุณถูก build จากโฟลเดอร์
งานของคุณ แต่ตอนใช้งานจริงมันถูก import จาก `sys.path` และบนเครื่องของคุณสองอย่างนี้
ซ้อนทับกันอยู่ module ที่คุณลืมใส่ในรายการ ไฟล์ข้อมูลที่ไม่เคยเข้าไปอยู่ใน wheel และ
dependency ที่คุณใช้แต่ไม่เคยประกาศเพราะมันติดตั้งไว้อยู่แล้วจากโปรเจกต์อื่น ทั้งสามอย่าง
นี้ทำงานได้สมบูรณ์แบบบนเครื่องที่ build มัน และพังบนเครื่องแรกที่ไม่ได้ build

เครื่องของคนเขียนคือที่เดียวในโลกที่ตรวจจับบั๊กประเภทนี้ไม่ได้

วิธีตรวจคือสร้าง environment ว่างเปล่า ติดตั้งจากไฟล์ที่ build ออกมา แล้วสั่งมันทำงาน
จริง

```bash
python -m venv fresh
./fresh/bin/pip install dist/agentpath_kit-1.0.6-py3-none-any.whl
./fresh/bin/agentpath --help
```

บน Windows เส้นทางของ environment ต่างออกไป และนี่คือคำสั่งเดียวกัน

```powershell
python -m venv fresh
.\fresh\Scripts\pip install dist\agentpath_kit-1.0.6-py3-none-any.whl
.\fresh\Scripts\agentpath --help
```

ความต่างคือ `Scripts` แทน `bin` และไม่มีขั้น `python` ในเส้นทาง ซึ่งฟังดูจุกจิกจนกระทั่ง
วันที่คุณคัดลอกคำสั่งฝั่ง Unix มาวางแล้วมันหาไฟล์ไม่เจอ บทเรียนของหัวข้อที่ 5 คือเรื่อง
เดียวกันนี้ในรูปแบบที่แพงกว่า

สิ่งที่ควรทำต่อคือดูว่าใน environment นั้นมีอะไรอยู่บ้าง เพราะ dependency หนึ่งบรรทัดไม่ได้
แปลว่า package หนึ่งตัว รายการข้างล่างบันทึกไว้ตอนรุ่น 1.0.4 ก่อนที่ชื่อบนดัชนีจะเปลี่ยน
ในหัวข้อที่ 6

```text
Package           Version
----------------- ---------
agentpath         1.0.4
anyio             4.14.2
certifi           2026.7.22
h11               0.16.0
httpcore          1.0.9
httpx             0.28.1
idna              3.19
pip               22.3.1
setuptools        65.5.0
typing_extensions 4.16.0
```

`httpx` หนึ่งบรรทัดกลายเป็นเจ็ดแพ็กเกจ ซึ่งเป็นเรื่องปกติและไม่ได้ผิด แต่มันคือสิ่งที่คุณ
กำลังยัดลงเครื่องของคนอื่น และคุณควรรู้ว่ามันคืออะไร

อีกอย่างที่ควรเปิดดูคือกล่องที่ build ออกมา โปรเจกต์นี้เปิดดูแล้วพบว่า sdist กวาดทั้ง
repository เข้าไป รวมโฟลเดอร์บทเรียนยี่สิบสี่บทในสองภาษา มีข้อโต้แย้งได้ว่าบทเรียนคือ
ตัวเนื้อหาจริง แต่คนที่ติดตั้ง package ต้องการ package และหลักสูตรอยู่ห่างออกไปแค่คลิก
เดียวใน repository โปรเจกต์นี้จึงตัดมันออก

ทางแก้คือตาราง sdist ในหัวข้อที่ 1 ซึ่งบอกว่าให้ใส่อะไรบ้าง และมันมีกับดักหนึ่งอัน ทุก
pattern ในนั้นขึ้นต้นด้วยเครื่องหมายทับ ส่วนความพยายามครั้งแรกไม่ได้ขึ้นต้นแบบนั้น
hatchling อ่าน pattern พวกนี้แบบเดียวกับที่ git อ่าน `.gitignore` ดังนั้น `README.md`
เปล่าๆ แปลว่าไฟล์ชื่อนั้นที่ความลึกไหนก็ได้ และ repository นี้มีอยู่ยี่สิบหกไฟล์ sdist ออก
มาสามร้อยห้าสิบไฟล์แทนที่จะเป็นสามสิบหก และมันดูน่าเชื่อพอที่จะผ่านไปได้ ถ้าไม่ได้นับ
จำนวนไฟล์ เครื่องหมายทับข้างหน้าคือสิ่งที่ตรึง pattern ไว้กับราก

บทเรียนของเรื่องนี้ใหญ่กว่าทางแก้ **เปิดดูของที่ build ออกมาก่อนที่จะส่งมันออกไป** ค่าเริ่ม
ต้นของสิ่งที่ถูกใส่ลงกล่องนั้นใจกว้างมาก pattern ที่ใช้จำกัดมันไม่ได้แปลว่าอย่างที่หน้าตา
มันบอก และไม่มีใครค้นพบว่ากล่องของตัวเองใหญ่สองร้อยเมกะไบต์ จนกว่าจะมีคนแปลกหน้ามา
บ่นให้ฟัง

ต้องทำก่อน ไม่ใช่หลัง เพราะรุ่นที่ปล่อยไปแล้วแก้ไม่ได้ คุณไม่ได้ซ่อม 1.0.0 คุณออก 1.0.1
มาแทน แล้วตัวที่พังยังอยู่ตรงนั้นให้คนเห็นตลอดไป สิบนาทีใน environment ว่างเปล่าซื้อความ
สามารถที่จะไม่ต้องทำแบบนั้นครับ

## 4. CI สี่งาน และเหตุผลที่ต้องรันบนสองระบบปฏิบัติการ

CI (Continuous Integration คือการให้เครื่องรันการตรวจทุกครั้งที่โค้ดเปลี่ยน) ของ
โปรเจกต์นี้มีสี่งาน ชื่อ `lint` `prose` `tests` และ `lessons` แต่ละงานตอบคำถามคนละข้อ
และการแยกเป็นสี่งานแทนที่จะเป็นงานเดียวที่รันทุกอย่างมีเหตุผลเดียว คือเวลาแดง คุณเห็น
ทันทีว่าอะไรพัง

`lint` ถามว่าโค้ดเขียนตามมาตรฐานเดียวกันไหม มันรัน `ruff` เต็มรูปแบบกับโค้ดของ package
และรันเฉพาะกฎที่เป็น error ร้ายแรงกับโฟลเดอร์บทเรียน เพราะโค้ดบทเรียนจงใจซ้ำและจงใจ
เรียบง่ายกว่ามาตรฐานของ package

```yaml
      - run: pip install ruff
      - run: ruff check .
      - run: ruff check --select E9,F63,F7,F82 lessons
```

`prose` ถามว่างานเขียนตามกฎของเล่มไหม มันรันสคริปต์ที่ปฏิเสธ em dash emoji และ colon
ในร้อยแก้ว กฎพวกนี้เป็นกฎที่คนลืม เครื่องจึงเป็นคนบังคับ

`tests` ถามว่าโค้ดยังทำในสิ่งที่มันสัญญาไว้ไหม และงานนี้เป็นงานเดียวที่มี matrix สองมิติ
คือสองระบบปฏิบัติการคูณสอง Python รวมเป็นสี่ target

```yaml
  tests:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        python-version: ["3.10", "3.12"]
```

`lessons` ถามว่าโค้ดในบทเรียนยังรันได้ไหม ซึ่งเป็นคำถามคนละข้อกับ tests เพราะบทเรียนคือ
ไฟล์คนละชุดที่ผู้อ่านคัดลอกไปใช้ ถ้ามันพัง หนังสือสอนของที่พัง

`fail-fast` ถูกปิดเพราะค่าเริ่มต้นคือเมื่อ target หนึ่งล้ม ตัวที่เหลือจะถูกยกเลิก ซึ่งทำให้
คุณเห็นความล้มเหลวทีละอัน แล้วแก้ทีละอัน แล้วรอรอบใหม่ทีละรอบ การปิดมันคือการยอมจ่าย
เวลาเครื่องเพิ่มเพื่อแลกกับการเห็นภาพรวมของความเสียหายในรอบเดียว

เหตุผลที่ต้องรันสองระบบปฏิบัติการไม่ใช่เพราะอยากละเอียด มันเพราะกลุ่มผู้อ่านของหลักสูตร
นี้ใช้ Windows เยอะ และสิ่งที่ต่างระหว่างสองระบบไม่ใช่เรื่องเล็ก บทที่ 13 ทั้งบทมีสองหัวข้อ
ที่เป็นเรื่อง Windows ล้วนๆ คือการฆ่า process tree กับเรื่อง encoding ถ้า CI รันแต่ Linux
สองหัวข้อนั้นจะไม่มีอะไรตรวจเลย

## 5. เรื่องจริง ผ่านในเครื่อง ล้มทั้งสี่ target

กลับมาที่เรื่องตอนเปิดบท รุ่น 1.0.4 แก้เรื่อง encoding ของ output จากคำสั่ง shell พร้อม
กับเพิ่ม test ที่พิสูจน์ว่ามันทำงาน test นั้นผ่านบนเครื่องที่เขียน แล้วครั้งแรกที่มันขึ้นไปอยู่
บน CI มันล้มทั้งสี่ target ของงาน tests

ข้อความ commit บันทึกไว้แบบนี้

```text
It failed on every continuous integration target while passing here, which
is the useful kind of failure. Two different reasons, neither of them the
code under test.
```

ประโยคที่สองคือหัวใจ ทั้งสองสาเหตุไม่ใช่โค้ดที่กำลังถูกทดสอบ มันคือ test เองที่ผูกอยู่กับ
สภาพแวดล้อมของเครื่องคนเขียน

test ตัวเดิมยืนยันสองอย่างในฟังก์ชันเดียว อย่างแรกคือ output ที่เป็น utf-8 ต้องอ่านได้
อย่างที่สองคือ output ที่เป็น codepage เก่าของ Windows ก็ต้องอ่านได้ด้วย

```python
    legacy = (
        f'"{sys.executable}" -c "import sys; '
        "sys.stdout.buffer.write('cafe resume'.replace('e','\u00e9').encode('cp437'))\""
    )
    assert "caf\u00e9 r\u00e9sum\u00e9" in run(tmp_path, legacy)

    modern = f'"{sys.executable}" -c "print(\'\u0e2a\u0e27\u0e31\u0e2a\u0e14\u0e35\')"'
    assert "\u0e2a\u0e27\u0e31\u0e2a\u0e14\u0e35" in run(tmp_path, modern)
```

สาเหตุที่หนึ่งอยู่บน Linux ข้อยืนยันเรื่อง codepage เก่าของ Windows เป็นจริงไม่ได้ เพราะ
บน Linux ไม่มี codepage นั้นให้ถอยไปหา และ utf-8 ก็ถูกอยู่แล้ว test ข้อนี้เป็น test เรื่อง
Windows มาตั้งแต่แรก แค่ไม่เคยถูกติดป้ายว่าเป็นแบบนั้น

สาเหตุที่สองอยู่บน Windows อีกครึ่งหนึ่งล้มเพราะ process ลูกเขียนภาษาไทยลง stdout ของ
ตัวเองไม่ได้ มันจึงตายก่อนที่จะพิมพ์อะไรออกมา และสิ่งที่ test
วัดจึงกลายเป็นการตายของ process ลูก แทนที่จะเป็นการถอดรหัสของเรา

ทางแก้คือแยก test เป็นสองตัว ครึ่งที่เป็นเรื่อง Windows ถูกติดป้ายว่าเป็นเรื่อง Windows
ตรงๆ ด้วย marker ที่ข้ามมันบนระบบอื่น

```python
@pytest.mark.skipif(sys.platform != "win32", reason="only Windows has an OEM codepage")
def test_output_in_the_old_windows_codepage_is_still_read(tmp_path):
```

ส่วนอีกครึ่งหนึ่งเลิกใช้ `print` แล้วให้ process ลูกเขียนไบต์ที่ต้องการลง stdout ตรงๆ ซึ่ง
เป็นการเอาความเห็นของลูกเรื่อง encoding ออกจากสมการ

```python
    thai = "สวัสดี"
    command = (
        f'"{sys.executable}" -c "import sys; '
        "sys.stdout.buffer.write(bytes([224,184,170,224,184,167,224,184,177,"
        "224,184,170,224,184,148,224,184,181]))\""
    )
    assert thai in run(tmp_path, command)
```

บทเรียนที่เอาไปใช้ต่อได้มีสองข้อ test ที่พึ่งพาสภาพแวดล้อมโดยไม่รู้ตัว คือ test ที่บอก
ความจริงเกี่ยวกับเครื่องของคุณ ไม่ใช่เกี่ยวกับโค้ดของคุณ มันจะเขียวตลอดจนถึงวันที่รันที่อื่น
และ test ที่มี `print` หรือมี process ลูกอยู่ในเส้นทาง กำลังวัดสองอย่างพร้อมกันโดยไม่ได้
ตั้งใจ เมื่อมันล้ม คุณจะไม่รู้ว่าอันไหนล้ม การเขียนไบต์ตรงๆ คือการตัดตัวแปรที่ไม่เกี่ยวออก

คำในข้อความ commit ที่ควรจำคือ useful kind of failure ความล้มเหลวแบบนี้ดีกว่าความล้ม
เหลวที่ไม่เคยเกิด เพราะถ้า CI มีแต่ Linux test ครึ่งหนึ่งจะถูกข้ามไปเงียบๆ และครึ่งที่เหลือ
จะเขียวโดยไม่ได้ตรวจสิ่งที่ตั้งใจจะตรวจครับ

## 6. ชื่อ package ต้องเช็คก่อน และเช็คแต่เนิ่นๆ

เรื่องสุดท้ายใช้เวลาสามสิบวินาที และการไม่ทำมันคือความผิดพลาดที่แพงที่สุดในบทนี้

ชื่อใน `[project]` ต้องไม่ซ้ำกับใครในดัชนีทั้งดัชนี ซึ่งมีชื่อจองไว้แล้วหลายแสนชื่อ การเช็ค
คือคำขอเดียว

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://pypi.org/pypi/agentpath/json
```

```text
404
```

รหัสสี่ศูนย์สี่แปลว่าไม่มีโปรเจกต์ชื่อนี้ ชื่อจึงว่าง ส่วนสองศูนย์ศูนย์แปลว่ามีคนใช้แล้ว และ
ให้รู้ไว้ด้วยว่าชื่อถูกทำให้เป็นรูปมาตรฐานก่อนเทียบ ดังนั้น `agent_path` `agent-path` และ
`Agent.Path` ชนกันเองทั้งหมด

โปรเจกต์นี้เช็คแล้ว และบรรทัดนั้นยังอยู่ในเอกสารออกแบบ ซึ่งถูกเขียนก่อนที่จะมีไฟล์แม้แต่
ไฟล์เดียว

```text
- ชื่อโปรเจกต์ agentpath (ตรวจแล้ว PyPI ว่าง, GitHub แทบไม่มีคู่แข่ง)
```

มันต้องเป็นสิ่งแรกเพราะชื่อนั้นเดินทางไปไกลมากเมื่อจบภาค 3 มันคือพาธที่ใช้ import ในทุก
ไฟล์ มันคือชื่อคำสั่งในเทอร์มินัล มันคือชื่อตัวแปรสภาพแวดล้อมทุกตัวที่บทเรียนอ่าน มัน
คือชื่อ repository ชื่อโฟลเดอร์ในทุกคำสั่งของทุกบท และเป็นคำแรกของประโยคโปรย

ถ้าค้นพบว่าชื่อชนหลังจากภาค 3 งานที่ตามมาคือการเขียนใหม่ยี่สิบสี่บทเรียน พร้อมทุก
code block ในนั้น และผู้อ่านทุกคนที่ตั้งค่าไว้แล้วต้องตั้งใหม่หมด

แล้วการเช็คนั้นก็ยังไม่พอ เรื่องนี้จบลงแบบที่ไม่ได้วางแผนไว้ คำขอข้างบนตอบสี่ศูนย์สี่ให้
`agentpath` และตอนอัปโหลดจริงกลับถูกปฏิเสธ ด้วยประโยคว่าชื่อนี้ใกล้เคียงกับโปรเจกต์ที่มี
อยู่มากเกินไป

ดัชนีไม่ได้ปฏิเสธแค่ชื่อที่ถูกใช้ไปแล้ว มันปฏิเสธชื่อที่ใกล้ของเดิมมากพอจนคนที่พิมพ์จาก
ความจำอาจไปลงเอยที่ package ผิดตัว กฎนี้ป้องกันการโจมตีที่เกิดขึ้นจริง มีโปรเจกต์
ชื่อ `agent_path` อยู่ก่อนแล้ว ในรูปมาตรฐานมันคือ `agent-path` และนั่นไม่เท่ากับ
`agentpath` คำขอจึงบอกว่าว่าง แล้วตัวตรวจความใกล้เคียงบอกว่าไม่

ย่อหน้าเรื่องรูปมาตรฐานข้างบนพูดถูกว่าชื่อไหนชนกัน แต่พูดผิดเรื่องคำถามที่มันตอบ ความ
เท่ากันบอกว่าชื่อถูกใช้ไปหรือยัง มันไม่บอกเลยว่าชื่อนั้นใช้ได้หรือไม่ และไม่มีคำขอสาธารณะที่
ตอบคำถามที่สอง ทางเดียวที่รู้ก่อนคืออัปโหลดขึ้นดัชนีทดสอบตั้งแต่เนิ่นๆ ซึ่งเป็นเหตุผลที่หนัก
กว่าเดิมมากสำหรับสิ่งที่ย่อหน้าท้ายบทแนะนำอยู่แล้ว

สิ่งที่ทำให้เรื่องนี้ไม่กลายเป็นการเขียนใหม่ยี่สิบสี่บทเรียนจริงๆ คือชื่อบนดัชนีกับชื่อที่คุณ
import ไม่จำเป็นต้องตรงกัน โปรเจกต์นี้เผยแพร่ในชื่อ `agentpath-kit` และติดตั้ง package
ชื่อ `agentpath` แบบเดียวกับที่คุณติดตั้ง `scikit-learn` แล้ว import `sklearn` การแก้ทั้ง
หมดคือบรรทัดเดียวใน `pyproject.toml` กับคอมเมนต์ที่อธิบายว่าทำไม และพาธที่ใช้ import
ชื่อคำสั่ง ตัวแปรสภาพแวดล้อมทุกตัว และทุก code block ในยี่สิบสี่บทเรียน ล้วนคงชื่อเดิมไว้

อีกสองอย่างที่ควรจัดการก่อนกดส่ง อย่างแรกคือมีบัญชีบนดัชนีทดสอบด้วย ซึ่งเป็นบริการคนละ
ตัวกันกับของจริงและมีไว้เพื่อให้การอัปโหลดครั้งแรกของคุณผิดพลาดได้ อย่างที่สองคือใช้
token แทนรหัสผ่าน เพราะ token เพิกถอนทีละอันได้โดยไม่ต้องเปลี่ยนรหัสผ่าน และ token ที่
ผูกกับโปรเจกต์เดียวถ้าหลุดออกไปก็แตะอย่างอื่นของคุณไม่ได้ ห้ามเก็บมันไว้ใน repository
เพราะ token ที่ถูก commit หนึ่งครั้งคือ token ที่ต้องเพิกถอน การลบ commit ไม่ได้ลบมันออก
จากสำเนาของคนอื่นครับ
