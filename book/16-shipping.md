# บทที่ 16 ส่งมอบ

จบบทนี้คุณจะมีไฟล์ที่คนอื่นติดตั้งได้ด้วยคำสั่งเดียว มีคำสั่งชื่อสั้นๆ ที่
พิมพ์ในเทอร์มินัลได้ทันทีหลังติดตั้ง และมีการตรวจอัตโนมัติที่ปฏิเสธการเปลี่ยน
แปลงที่ทำให้ของพัง

และคุณจะได้เรื่องจริงหนึ่งเรื่องที่โปรเจกต์นี้เจอ ตอนที่ test ผ่านบนเครื่องคน
เขียนแต่ล้มทั้งสี่ target บนเครื่องของคนอื่น

## 1. pyproject.toml ทีละส่วน

ไฟล์เดียวนี้ตอบคำถามสี่ข้อที่คนละคนถาม คนที่ติดตั้งถามว่าต้องมีอะไรก่อน
เครื่องมือที่ build ถามว่าเอาไฟล์ไหนไปใส่ เทอร์มินัลถามว่าคำสั่งชื่ออะไรและ
ไปเรียกอะไร ส่วน linter กับ test runner ถามว่าตั้งค่าไว้ยังไง

ทั้งไฟล์ของโปรเจกต์นี้ยาวสามสิบเอ็ดบรรทัด

```toml
[project]
name = "agentpath-kit"
version = "1.0.5"
description = "Learn how AI agents actually work by building a real one, from a single LLM call to a full agent harness."
readme = "README.md"
requires-python = ">=3.10"
license = { text = "MIT" }
dependencies = ["httpx>=0.27"]

[project.scripts]
agentpath = "agentpath.cli:main"

[project.optional-dependencies]
dev = ["pytest>=8.0", "ruff>=0.6"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/agentpath"]

[tool.ruff]
line-length = 100
exclude = ["lessons"]

[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]

[tool.pytest.ini_options]
testpaths = ["tests"]
```

**`[project]` คือสิ่งที่ผู้ติดตั้งมองเห็น** ชื่อ รุ่น คำบรรยาย ไฟล์ที่จะถูก
แสดงเป็นหน้าแรก รุ่น Python ที่ต่ำที่สุดที่รองรับ สัญญาอนุญาต และ dependency
(ของที่ต้องพึ่งพา คือ package อื่นที่ต้องมีก่อนถึงจะทำงานได้)

**`dependencies` เขียนเป็นขอบล่าง ไม่ใช่การตรึง** และความต่างนี้สำคัญ ถ้าตรึง
ไว้ที่รุ่นเดียวเป๊ะ คนที่ติดตั้ง package ของคุณคู่กับอย่างอื่นที่ต้องการรุ่น
ใหม่กว่าจะติดตั้งไม่ได้เลย และทางแก้เดียวคือรอให้คุณออกรุ่นใหม่ library ควร
บอกรุ่นเก่าที่สุดที่รู้ว่าใช้ได้ แล้วปล่อยให้แอปพลิเคชันเป็นคนตัดสินใจที่เหลือ
การตรึงเป๊ะถูกต้องสำหรับแอปพลิเคชันที่คุณ deploy เอง และผิดสำหรับ package
ที่คนอื่นติดตั้ง

**`[project.optional-dependencies]` คือของที่ผู้ใช้ไม่ต้องได้** `pytest` กับ
`ruff` เป็นเครื่องมือของคนพัฒนา การเอาไปใส่ใน `dependencies` แปลว่าทุกคนที่
ติดตั้ง package นี้จะได้ตัวรัน test กับ linter ติดมาด้วยโดยไม่มีเหตุผล

**`[build-system]` คือคำตอบว่าใครเป็นคนประกอบ** โปรเจกต์นี้ใช้ hatchling
และ `[tool.hatch.build.targets.wheel]` คือการชี้ว่าโค้ดจริงอยู่ใต้ `src`
ไม่ได้อยู่ที่รากของ repository

**สองส่วนสุดท้ายไม่เกี่ยวกับการส่งมอบเลย** มันคือการตั้งค่าเครื่องมือ ที่มา
อยู่ไฟล์เดียวกันเพราะระบบนิเวศของ Python ตกลงกันว่าจะรวมการตั้งค่าไว้ที่นี่
แทนที่จะมีไฟล์ซ่อนคนละไฟล์ต่อเครื่องมือหนึ่งตัว

## 2. console script คือชื่อคำสั่งที่แมปไปหาฟังก์ชัน

สองบรรทัดนี้คือสิ่งที่ทำให้คนพิมพ์คำว่า `agentpath` ในเทอร์มินัลแล้วมีอะไร
เกิดขึ้น

```toml
[project.scripts]
agentpath = "agentpath.cli:main"
```

ฝั่งซ้ายคือชื่อคำสั่งที่จะถูกสร้างขึ้น ฝั่งขวาคือพาธของ module ตามด้วยชื่อ
ฟังก์ชันที่จะถูกเรียก ตอนติดตั้ง เครื่องมือติดตั้งจะสร้างไฟล์เล็กๆ ไว้ใน
โฟลเดอร์ที่อยู่ใน PATH ของ environment นั้น ไฟล์นั้นทำอย่างเดียวคือ import
module แล้วเรียกฟังก์ชัน

**ทำไมถึงดีกว่าการให้คนพิมพ์ `python -m`** เพราะมันซ่อนสองอย่างที่ผู้ใช้ไม่
ควรต้องรู้ คือพาธของ interpreter ที่ถูกตัว และชื่อ module ภายในของคุณ ผู้ใช้
รู้แค่ชื่อคำสั่ง และคุณย้าย `main` ไปอยู่ module อื่นวันหลังได้โดยที่คำสั่ง
ยังเหมือนเดิม

**สิ่งที่ต้องเป็นจริงในโค้ด** คือฟังก์ชันนั้นต้องเรียกได้โดยไม่รับ argument
บังคับ และต้องคืน exit code หรือปล่อยให้ `SystemExit` ทำงาน ใน `cli.py`
ลายเซ็นคือ `def main(argv=None)` ซึ่ง `argv` มีค่าเริ่มต้น จึงเรียกแบบไม่ส่ง
อะไรได้ และการรับ `argv` ได้ทำให้ test เรียกมันตรงๆ พร้อม argument ปลอมได้ด้วย
โดยไม่ต้องไปยุ่งกับ `sys.argv` จริง

## 3. ทดสอบติดตั้งใน environment สะอาด ก่อน publish ไม่ใช่หลัง

นี่คือขั้นตอนที่คนข้าม และการข้ามมันคือเหตุผลที่รุ่นแรกของหลายโปรเจกต์ตามมา
ด้วยรุ่นที่สองภายในหนึ่งชั่วโมง

**เหตุผลที่ต้องเป็น environment สะอาดนั้นเจาะจงมาก** package ของคุณถูก build
จากโฟลเดอร์งานของคุณ แต่ตอนใช้งานจริงมันถูก import จาก `sys.path` และบน
เครื่องของคุณสองอย่างนี้ซ้อนทับกันอยู่ module ที่คุณลืมใส่ในรายการ ไฟล์ข้อมูล
ที่ไม่เคยเข้าไปอยู่ใน wheel และ dependency ที่คุณใช้แต่ไม่เคยประกาศเพราะมัน
ติดตั้งไว้อยู่แล้วจากโปรเจกต์อื่น ทั้งสามอย่างนี้ทำงานได้สมบูรณ์แบบบนเครื่อง
ที่ build มัน และพังบนเครื่องแรกที่ไม่ได้ build

เครื่องของคนเขียนคือที่เดียวในโลกที่ตรวจจับบั๊กประเภทนี้ไม่ได้

วิธีตรวจคือสร้าง environment ว่างเปล่า ติดตั้งจากไฟล์ที่ build ออกมา แล้วสั่ง
มันทำงานจริง

```bash
python -m venv fresh
./fresh/bin/pip install dist/agentpath_kit-1.0.5-py3-none-any.whl
./fresh/bin/agentpath --help
```

บน Windows เส้นทางของ environment ต่างออกไป และนี่คือคำสั่งเดียวกัน

```powershell
python -m venv fresh
.\fresh\Scripts\pip install dist\agentpath_kit-1.0.5-py3-none-any.whl
.\fresh\Scripts\agentpath --help
```

ความต่างคือ `Scripts` แทน `bin` และไม่มีขั้น `python` ในเส้นทาง ซึ่งฟังดู
จุกจิกจนกระทั่งวันที่คุณคัดลอกคำสั่งฝั่ง Unix มาวางแล้วมันหาไฟล์ไม่เจอ
บทเรียนของหัวข้อที่ 5 คือเรื่องเดียวกันนี้ในรูปแบบที่แพงกว่า

และสิ่งที่ควรทำต่อคือดูว่าใน environment นั้นมีอะไรอยู่บ้าง เพราะ dependency
หนึ่งบรรทัดไม่ได้แปลว่า package หนึ่งตัว

```text
Package           Version
----------------- ---------
agentpath         1.0.4
anyio             4.14.2
certifi           2026.7.22
h11               0.16.0
httpcore          1.0.9
httpx             0.28.1
idna              3.19
pip               22.3.1
setuptools        65.5.0
typing_extensions 4.16.0
```

`httpx` หนึ่งบรรทัดกลายเป็นเจ็ดแพ็กเกจ ซึ่งเป็นเรื่องปกติและไม่ได้ผิด แต่มันคือ
สิ่งที่คุณกำลังยัดลงเครื่องของคนอื่น และคุณควรรู้ว่ามันคืออะไร

**อีกอย่างที่ควรเปิดดูคือกล่องที่ build ออกมา** โปรเจกต์นี้เปิดดูแล้วพบว่า
sdist กวาดทั้ง repository เข้าไป รวมโฟลเดอร์บทเรียนยี่สิบสี่บทในสองภาษา
ซึ่งสำหรับโปรเจกต์นี้พอจะแก้ต่างได้ เพราะบทเรียนคือตัวเนื้อหาจริง แต่มันแทบ
ไม่เคยเป็นสิ่งที่คุณต้องการ และไม่เคยเป็นสิ่งที่คุณคาด

บทเรียนของเรื่องนี้เล็กกว่าและมีประโยชน์กว่าทางแก้ คือ **เปิดดูของที่ build
ออกมาก่อนที่จะส่งมันออกไป** ค่าเริ่มต้นของสิ่งที่ถูกใส่ลงกล่องนั้นใจกว้างมาก
และไม่มีใครค้นพบว่ากล่องของตัวเองใหญ่สองร้อยเมกะไบต์ จนกว่าจะมีคนแปลกหน้ามา
บ่นให้ฟัง

**และเหตุผลที่ต้องทำก่อน ไม่ใช่หลัง** คือรุ่นที่ปล่อยไปแล้วแก้ไม่ได้ คุณไม่ได้
ซ่อม 1.0.0 คุณออก 1.0.1 มาแทน แล้วตัวที่พังยังอยู่ตรงนั้นให้คนเห็นตลอดไป
สิบนาทีใน environment ว่างเปล่าซื้อความสามารถที่จะไม่ต้องทำแบบนั้นครับ

## 4. CI สี่งาน และเหตุผลที่ต้องรันบนสองระบบปฏิบัติการ

CI (Continuous Integration คือการให้เครื่องรันการตรวจทุกครั้งที่โค้ดเปลี่ยน)
ของโปรเจกต์นี้มีสี่งาน ชื่อ `lint` `prose` `tests` และ `lessons` แต่ละงาน
ตอบคำถามคนละข้อ และการแยกเป็นสี่งานแทนที่จะเป็นงานเดียวที่รันทุกอย่าง
มีเหตุผลเดียว คือเวลาแดง คุณเห็นทันทีว่าอะไรพัง

**`lint` ถามว่าโค้ดเขียนตามมาตรฐานเดียวกันไหม** มันรัน `ruff` เต็มรูปแบบกับ
โค้ดของ package และรันเฉพาะกฎที่เป็น error ร้ายแรงกับโฟลเดอร์บทเรียน เพราะ
โค้ดบทเรียนจงใจซ้ำและจงใจเรียบง่ายกว่ามาตรฐานของ package

```yaml
      - run: pip install ruff
      - run: ruff check .
      - run: ruff check --select E9,F63,F7,F82 lessons
```

**`prose` ถามว่างานเขียนตามกฎของเล่มไหม** มันรันสคริปต์ที่ปฏิเสธ em dash
emoji และ colon ในร้อยแก้ว กฎพวกนี้เป็นกฎที่คนลืม เครื่องจึงเป็นคนบังคับ

**`tests` ถามว่าโค้ดยังทำในสิ่งที่มันสัญญาไว้ไหม** และงานนี้เป็นงานเดียวที่มี
matrix สองมิติ คือสองระบบปฏิบัติการคูณสอง Python รวมเป็นสี่ target

```yaml
  tests:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest]
        python-version: ["3.10", "3.12"]
```

**`lessons` ถามว่าโค้ดในบทเรียนยังรันได้ไหม** ซึ่งเป็นคำถามคนละข้อกับ tests
เพราะบทเรียนคือไฟล์คนละชุดที่ผู้อ่านคัดลอกไปใช้ ถ้ามันพัง หนังสือสอนของที่พัง

**ทำไม `fail-fast` ถึงถูกปิด** เพราะค่าเริ่มต้นคือเมื่อ target หนึ่งล้ม ตัวที่
เหลือจะถูกยกเลิก ซึ่งทำให้คุณเห็นความล้มเหลวทีละอัน แล้วแก้ทีละอัน แล้วรอ
รอบใหม่ทีละรอบ การปิดมันคือการยอมจ่ายเวลาเครื่องเพิ่มเพื่อแลกกับการเห็น
ภาพรวมของความเสียหายในรอบเดียว

**และเหตุผลที่ต้องรันสองระบบปฏิบัติการ** ไม่ใช่เพราะอยากละเอียด มันเพราะกลุ่ม
ผู้อ่านของหลักสูตรนี้ใช้ Windows เยอะ และสิ่งที่ต่างระหว่างสองระบบไม่ใช่เรื่อง
เล็ก บทที่ 13 ทั้งบทมีสองหัวข้อที่เป็นเรื่อง Windows ล้วนๆ คือการฆ่า process
tree กับเรื่อง encoding ถ้า CI รันแต่ Linux สองหัวข้อนั้นจะไม่มีอะไรตรวจเลย

## 5. เรื่องจริง ผ่านในเครื่อง ล้มทั้งสี่ target

รุ่น 1.0.4 แก้เรื่อง encoding ของ output จากคำสั่ง shell พร้อมกับเพิ่ม test
ที่พิสูจน์ว่ามันทำงาน test นั้นผ่านบนเครื่องที่เขียน แล้วครั้งแรกที่มันขึ้นไป
อยู่บน CI มันล้มทั้งสี่ target ของงาน tests

ข้อความ commit บันทึกไว้แบบนี้

```text
It failed on every continuous integration target while passing here, which
is the useful kind of failure. Two different reasons, neither of them the
code under test.
```

**ประโยคที่สองคือหัวใจ** ทั้งสองสาเหตุไม่ใช่โค้ดที่กำลังถูกทดสอบ มันคือ test
เองที่ผูกอยู่กับสภาพแวดล้อมของเครื่องคนเขียน

test ตัวเดิมยืนยันสองอย่างในฟังก์ชันเดียว อย่างแรกคือ output ที่เป็น utf-8
ต้องอ่านได้ อย่างที่สองคือ output ที่เป็น codepage เก่าของ Windows ก็ต้องอ่าน
ได้ด้วย

```python
    legacy = (
        f'"{sys.executable}" -c "import sys; '
        "sys.stdout.buffer.write('cafe resume'.replace('e','\u00e9').encode('cp437'))\""
    )
    assert "caf\u00e9 r\u00e9sum\u00e9" in run(tmp_path, legacy)

    modern = f'"{sys.executable}" -c "print(\'\u0e2a\u0e27\u0e31\u0e2a\u0e14\u0e35\')"'
    assert "\u0e2a\u0e27\u0e31\u0e2a\u0e14\u0e35" in run(tmp_path, modern)
```

**สาเหตุที่หนึ่ง บน Linux** ข้อยืนยันเรื่อง codepage เก่าของ Windows เป็นจริง
ไม่ได้ เพราะบน Linux ไม่มี codepage นั้นให้ถอยไปหา และ utf-8 ก็ถูกอยู่แล้ว
test ข้อนี้เป็น test เรื่อง Windows มาตั้งแต่แรก แค่ไม่เคยถูกติดป้ายว่าเป็นแบบนั้น

**สาเหตุที่สอง บน Windows** อีกครึ่งหนึ่งล้มเพราะ process ลูกเขียนภาษาไทยลง
stdout ของตัวเองไม่ได้ มันจึงตายก่อนที่จะพิมพ์อะไรออกมา และสิ่งที่ test วัดจึงไม่ใช่
การถอดรหัสของเรา มันคือการตายของ process ลูก

ทางแก้คือแยก test เป็นสองตัว ครึ่งที่เป็นเรื่อง Windows ถูกติดป้ายว่าเป็นเรื่อง
Windows ตรงๆ ด้วย marker ที่ข้ามมันบนระบบอื่น

```python
@pytest.mark.skipif(sys.platform != "win32", reason="only Windows has an OEM codepage")
def test_output_in_the_old_windows_codepage_is_still_read(tmp_path):
```

ส่วนอีกครึ่งหนึ่งเลิกใช้ `print` แล้วให้ process ลูกเขียนไบต์ที่ต้องการลง
stdout ตรงๆ ซึ่งเป็นการเอาความเห็นของลูกเรื่อง encoding ออกจากสมการ

```python
    thai = "สวัสดี"
    command = (
        f'"{sys.executable}" -c "import sys; '
        "sys.stdout.buffer.write(bytes([224,184,170,224,184,167,224,184,177,"
        "224,184,170,224,184,148,224,184,181]))\""
    )
    assert thai in run(tmp_path, command)
```

**บทเรียนที่เอาไปใช้ต่อได้** มีสองข้อ ข้อแรกคือ test ที่พึ่งพาสภาพแวดล้อมโดยไม่รู้ตัว
คือ test ที่บอกความจริงเกี่ยวกับเครื่องของคุณ ไม่ใช่เกี่ยวกับโค้ดของคุณ มันจะ
เขียวตลอดจนถึงวันที่รันที่อื่น ข้อสองคือ test ที่มี `print` หรือมี process ลูก
อยู่ในเส้นทาง กำลังวัดสองอย่างพร้อมกันโดยไม่ได้ตั้งใจ และเมื่อมันล้ม คุณจะ
ไม่รู้ว่าอันไหนล้ม การเขียนไบต์ตรงๆ คือการตัดตัวแปรที่ไม่เกี่ยวออก

**และคำในข้อความ commit ที่ควรจำคือ useful kind of failure** ความล้มเหลวแบบนี้
ดีกว่าความล้มเหลวที่ไม่เคยเกิด เพราะถ้า CI มีแต่ Linux test ครึ่งหนึ่งจะถูกข้าม
ไปเงียบๆ และครึ่งที่เหลือจะเขียวโดยไม่ได้ตรวจสิ่งที่ตั้งใจจะตรวจ

## 6. ชื่อ package ต้องเช็คก่อน และเช็คแต่เนิ่นๆ

เรื่องสุดท้ายใช้เวลาสามสิบวินาที และการไม่ทำมันคือความผิดพลาดที่แพงที่สุด
ในบทนี้

ชื่อใน `[project]` ต้องไม่ซ้ำกับใครในดัชนีทั้งดัชนี ซึ่งมีชื่อจองไว้แล้ว
หลายแสนชื่อ การเช็คคือคำขอเดียว

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://pypi.org/pypi/agentpath/json
```

```text
404
```

รหัสสี่ศูนย์สี่แปลว่าไม่มีโปรเจกต์ชื่อนี้ ชื่อจึงว่าง ส่วนสองศูนย์ศูนย์แปลว่า
มีคนใช้แล้ว และให้รู้ไว้ด้วยว่าชื่อถูกทำให้เป็นรูปมาตรฐานก่อนเทียบ ดังนั้น
`agent_path` `agent-path` และ `Agent.Path` ชนกันเองทั้งหมด

โปรเจกต์นี้เช็คแล้ว และบรรทัดนั้นยังอยู่ในเอกสารออกแบบ ซึ่งถูกเขียนก่อนที่จะ
มีไฟล์แม้แต่ไฟล์เดียว

```text
- ชื่อโปรเจกต์ agentpath (ตรวจแล้ว PyPI ว่าง, GitHub แทบไม่มีคู่แข่ง)
```

**ทำไมมันถึงต้องเป็นสิ่งแรก** ให้ดูว่าชื่อนั้นเดินทางไปไกลแค่ไหนเมื่อจบภาค 3
มันคือพาธที่ใช้ import ในทุกไฟล์ มันคือชื่อคำสั่งในเทอร์มินัล มันคือชื่อ
ตัวแปรสภาพแวดล้อมสามตัวที่ทุกบทเรียนอ่าน มันคือชื่อ repository ชื่อโฟลเดอร์
ในทุกคำสั่งของทุกบท และเป็นคำแรกของประโยคโปรย

การค้นพบว่าชื่อชนหลังจากภาค 3 ไม่ใช่การเปลี่ยนชื่อ มันคือการเขียนใหม่ยี่สิบสาม
บท พร้อมทุก code block ในนั้น และมันทำให้ผู้อ่านทุกคนที่ตั้งค่าไว้แล้วต้อง
ตั้งใหม่หมด

**และการเช็คนั้นก็ยังไม่พอ** เรื่องนี้จบลงแบบที่ไม่ได้วางแผนไว้ คำขอข้างบนตอบ
สี่ศูนย์สี่ให้ `agentpath` และตอนอัปโหลดจริงกลับถูกปฏิเสธ ด้วยประโยคว่าชื่อนี้
ใกล้เคียงกับโปรเจกต์ที่มีอยู่มากเกินไป

ดัชนีไม่ได้ปฏิเสธแค่ชื่อที่ถูกใช้ไปแล้ว มันปฏิเสธชื่อที่ใกล้ของเดิมมากพอจนคนที่
พิมพ์จากความจำอาจไปลงเอยที่ package ผิดตัว ซึ่งเป็นการป้องกันการโจมตีที่เกิดขึ้น
จริง มีโปรเจกต์ชื่อ `agent_path` อยู่ก่อนแล้ว ทำให้เป็นรูปมาตรฐานแล้วมันคือ
`agent-path` ซึ่งไม่เท่ากับ `agentpath` คำขอจึงบอกว่าว่าง แล้วตัวตรวจความ
ใกล้เคียงบอกว่าไม่

ย่อหน้าเรื่องรูปมาตรฐานข้างบนพูดถูกว่าชื่อไหนชนกัน แต่พูดผิดเรื่องคำถามที่มัน
ตอบ ความเท่ากันบอกว่าชื่อถูกใช้ไปหรือยัง มันไม่บอกเลยว่าชื่อนั้นใช้ได้หรือไม่
และไม่มีคำขอสาธารณะที่ตอบคำถามที่สอง ทางเดียวที่รู้ก่อนคืออัปโหลดขึ้นดัชนี
ทดสอบตั้งแต่เนิ่นๆ ซึ่งเป็นเหตุผลที่หนักกว่าเดิมมากสำหรับสิ่งที่ย่อหน้าถัดไป
แนะนำอยู่แล้ว

สิ่งที่ทำให้เรื่องนี้ไม่กลายเป็นการเขียนใหม่ยี่สิบสามบทจริงๆ คือชื่อบนดัชนีกับ
ชื่อที่คุณ import ไม่จำเป็นต้องตรงกัน โปรเจกต์นี้เผยแพร่ในชื่อ `agentpath-kit`
และติดตั้ง package ชื่อ `agentpath` แบบเดียวกับที่คุณติดตั้ง `scikit-learn`
แล้ว import `sklearn` การแก้ทั้งหมดคือบรรทัดเดียวใน `pyproject.toml` และพาธ
ที่ใช้ import ชื่อคำสั่ง ตัวแปรสภาพแวดล้อมสามตัว และทุก code block ในยี่สิบสาม
บท ล้วนคงชื่อเดิมไว้ทั้งหมด

**อีกสองอย่างที่ควรจัดการก่อนกดส่ง** อย่างแรกคือมีบัญชีบนดัชนีทดสอบด้วย
ซึ่งเป็นบริการคนละตัวกันกับของจริงและมีไว้เพื่อให้การอัปโหลดครั้งแรกของคุณ
ผิดพลาดได้ อย่างที่สองคือใช้ token แทนรหัสผ่าน เพราะ token เพิกถอนทีละอันได้
โดยไม่ต้องเปลี่ยนรหัสผ่าน และ token ที่ผูกกับโปรเจกต์เดียวถ้าหลุดออกไปก็แตะ
อย่างอื่นของคุณไม่ได้ ห้ามเก็บมันไว้ใน repository เพราะ token ที่ถูก commit
หนึ่งครั้งคือ token ที่ต้องเพิกถอน การลบ commit ไม่ได้ลบมันออกจากสำเนาของคนอื่น
