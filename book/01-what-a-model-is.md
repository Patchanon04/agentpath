# บทที่ 1 model คืออะไรจริงๆ และทำไมมันไม่มีความจำ

ทุกอย่างในหนังสือเล่มนี้ตั้งอยู่บนข้อเท็จจริงข้อเดียว ถ้าคุณเข้าใจข้อนี้ผิด
การตัดสินใจทุกข้อที่ตามมาจะผิดตามไปด้วย และคุณจะแก้ปัญหาที่ไม่มีอยู่จริง
ขณะที่ปัญหาที่มีอยู่จริงจะมองไม่เห็น

ข้อเท็จจริงนั้นคือ model (โมเดล คือตัวประมวลผลภาษาที่เราเรียกใช้ผ่านเครือข่าย)
ไม่มีความจำ ไม่มีสักนิดเดียว

จบบทนี้คุณจะมีภาพของ model ที่ตรงกับสิ่งที่เดินทางอยู่บนสายจริง คือ endpoint
ไร้สถานะหนึ่งตัวที่รับ list แล้วคืน message และคุณจะถือข้อเท็จจริงหกข้อที่
หัวข้อสุดท้ายรวบไว้ ตั้งแต่เหตุผลที่ต้นทุนของบทสนทนาโตแบบกำลังสอง ไปจนถึง
เหตุผลที่ streaming ต้องอยู่ในแบบตั้งแต่วันแรก ไม่ใช่ค่อยเติมทีหลัง

หัวข้อที่ 4 เรื่อง token กับตัวนับที่ไม่ตรงกันของแต่ละเจ้า เป็นหัวข้อที่คุณ
ข้ามได้ในรอบแรก แล้วค่อยกลับมาอ่านตอนที่ต้องตัดสินใจว่าจะตัด context ตรงไหน
หัวข้อที่เหลือเรียงต่อกันได้โดยไม่ต้องพึ่งมัน

## 1. เมื่อมองจากข้างนอก model คือ HTTP endpoint หนึ่งตัว

เวลาคนพูดถึง LLM (Large Language Model คือโมเดลภาษาขนาดใหญ่) พวกเขามักนึกถึง
สิ่งที่มีบุคลิก มีความคิด และจำได้ว่าคุยอะไรกันไว้ นั่นคือภาพจากฝั่งผู้ใช้
ซึ่งเป็นภาพที่ถูกในเชิงประสบการณ์ แต่ผิดสนิทในเชิงวิศวกรรม

จากมุมของคนที่เขียนโค้ดเรียกมัน model คือ HTTP endpoint (จุดปลายทาง HTTP
คือ URL หนึ่งตัวที่รับคำขอแล้วตอบกลับ) ที่รับ JSON ก้อนหนึ่งแล้วคืน JSON
อีกก้อนหนึ่ง ในก้อนที่ส่งไปมี list ของ message (ข้อความ คือหน่วยหนึ่งบรรทัด
ของบทสนทนา) และในก้อนที่ได้กลับมามี message อีกหนึ่งอัน จบแค่นั้น

นี่คือหน้าตาจริงของสิ่งที่เดินทางไปบนสาย โค้ดข้างล่างมาจาก
`src/agentpath/providers/openai_compat.py` และเป็นฟังก์ชันที่แปลง Message
ของเราให้เป็นรูปที่ API ต้องการ

```python
def to_wire(message: Message) -> dict:
    """Convert one Message into the shape the API expects."""
    if message.role == "tool":
        return {
            "role": "tool",
            "tool_call_id": message.tool_call_id,
            "content": message.content,
        }
    wire = {"role": message.role, "content": message.content}
    if message.tool_calls:
        wire["tool_calls"] = [
            {
                "id": call.id,
                "type": "function",
                "function": {"name": call.name, "arguments": json.dumps(call.arguments)},
            }
            for call in message.tool_calls
        ]
    return wire
```

สังเกตว่าไม่มีอะไรในนี้ที่อ้างถึงคำขอครั้งก่อนเลย ไม่มี session id
ไม่มี conversation id ไม่มี token ที่ใช้ต่อสาย ทุกคำขอเป็นคำขอแรกเสมอ
ในสายตาของ server

**มันคืออะไร** endpoint ที่รับ list ของ message แล้วคืน message อีกอัน

**ทำไมต้องเป็นแบบนี้** เพราะ model ที่ให้บริการอยู่หลังนั้นถูกรันแบบขนาน
บนเครื่องจำนวนมาก คำขอสองครั้งติดกันของคุณอาจไปลงคนละเครื่อง ถ้า server
ต้องเก็บ state (สถานะ คือข้อมูลที่ค้างอยู่ระหว่างคำขอ) ของทุกบทสนทนา
ผู้ให้บริการต้องแบกภาระเก็บบทสนทนาของคนทั้งโลกไว้ พร้อมกับปัญหาว่าจะเก็บ
นานแค่ไหน ใครลบได้ และเครื่องไหนเป็นเจ้าของ การทำให้ endpoint ไร้สถานะ
ย้ายภาระนั้นมาไว้ที่ผู้เรียกแทน ซึ่งคือคุณ

**ทำไมไม่ใช่แบบอื่น** ผู้ให้บริการบางเจ้ามี API ที่เก็บบทสนทนาให้ และมันสะดวก
จริง แต่มันสะดวกโดยการซ่อนสิ่งที่คุณต้องควบคุม ถ้าคุณไม่เห็นว่าอะไรถูกส่งไปบ้าง
คุณจะตัด context ไม่เป็น คุณจะดู cache ไม่ออก และคุณจะ debug ไม่ได้ตอนที่
model ทำอะไรแปลกๆ หลักสูตรนี้จึงยิง HTTP เองตั้งแต่บรรทัดแรก เพราะสิ่งที่
คุณมองไม่เห็นคือสิ่งที่คุณแก้ไม่ได้

## 2. ความจำที่คุณเห็นคือการส่งซ้ำ

ถ้า model ไม่มีความจำ แล้วทำไมมันตอบได้ว่าแมวของคุณชื่ออะไร ทั้งที่คุณบอก
ไปเมื่อสามข้อความก่อน

คำตอบคือคุณส่งไปใหม่ ทั้งก้อน ทุกครั้ง

```json
[
  {"role": "system",    "content": "You are a terse assistant."},
  {"role": "user",      "content": "My cat is called Miso."},
  {"role": "assistant", "content": "Noted."},
  {"role": "user",      "content": "What is my cat called?"}
]
```

คำขอนี้ไม่ใช่คำขอที่สี่ของบทสนทนา มันคือคำขอแรกของบทสนทนาที่บังเอิญยาวสี่บรรทัด
model อ่านทั้งสี่บรรทัดจากบนลงล่าง แล้วเขียนบรรทัดที่ห้า มันไม่ได้ "จำ" ว่า
เคยตอบว่า Noted มันแค่อ่านเจอว่ามีบรรทัดที่บอกว่ามันเคยตอบแบบนั้น

นี่คือเหตุผลว่าทำไม state ของ agent ในหลักสูตรนี้จึงเป็น list ธรรมดา และ
เหตุผลว่าทำไม session ถูกเก็บเป็น JSONL (JSON Lines คือไฟล์ที่หนึ่งบรรทัด
คือหนึ่ง JSON) ที่เปิดอ่านด้วยตาเปล่าได้ ความจำของ agent ไม่ใช่สิ่งลึกลับ
มันคือไฟล์ข้อความที่คุณเปิดดูได้ ในไฟล์นั้นไม่มีอะไรมากกว่าสิ่งที่คุณเห็น

`src/agentpath/types.py` นิยาม Message ไว้แค่นี้ และความจำทั้งหมดของระบบ
คือ list ของสิ่งนี้

```python
@dataclass
class Message:
    """One entry in the conversation.

    role is one of system, user, assistant, tool. tool_call_id is filled in
    only when role is tool, so the provider can match a result back to the
    call that produced it.
    """

    role: str
    content: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    tool_call_id: str = ""
```

**ทำไมต้องรู้เรื่องนี้** เพราะเมื่อคุณเห็นว่าความจำคือการส่งซ้ำ คุณจะเลิกถาม
คำถามผิดๆ อย่าง "จะสอนให้ model จำเรื่องนี้ได้ยังไง" แล้วเริ่มถามคำถามที่ถูก
ซึ่งคือ "ในคำขอครั้งหน้า อะไรควรอยู่ในนั้นบ้าง" คำถามที่สองตอบได้ด้วยโค้ด
คำถามแรกตอบไม่ได้เลยครับ

## 3. ค่าใช้จ่ายโตแบบกำลังสอง และนี่คือตัวเลขจริง

ค่าใช้จ่ายของบทสนทนาหนึ่งชุดไม่ได้โตแบบเชิงเส้น

เหตุผลอยู่ในข้อเท็จจริงจากหัวข้อที่แล้ว ถ้าทุกคำขอส่งบทสนทนาทั้งก้อน
แล้วบทสนทนาโตขึ้นทุกรอบ ต้นทุนรวมจึงไม่ใช่ผลคูณของจำนวนรอบกับความยาว
ของหนึ่งข้อความ แต่คือผลรวมของอนุกรมที่โตขึ้นเรื่อยๆ

รอบที่หนึ่งส่งหนึ่งข้อความ รอบที่สองส่งสาม รอบที่สิบส่งสิบเก้า ถ้าแต่ละข้อความ
ยาวพอกัน ต้นทุนรวมจะโตประมาณกำลังสองของจำนวนรอบ บทสนทนายี่สิบรอบไม่ได้แพงเป็น
ยี่สิบเท่าของรอบเดียว มันแพงกว่านั้นมาก

บทเรียน 15 ในหลักสูตร วัดเรื่องนี้ด้วยการทดลองที่จงใจทำให้น่าเบื่อที่สุด
คือผู้ใช้พูดว่า Say hello แล้วพูดว่า And again ไปเรื่อยๆ ไม่มีใครอ่านไฟล์
ไม่มีใครเรียก tool แต่ละรอบเพิ่มเนื้อหาใหม่ประมาณสิบแปดตัวอักษร

```text
OK the same conversation cost more every turn, [2, 12, 22, 32]
```

สี่ตัวเลขนั้นคือจำนวน prompt tokens (โทเคนขาเข้า คือส่วนที่ถูกคิดเงินจาก
สิ่งที่เราส่งไป) ที่ถูกรายงานกลับมาในสี่คำขอติดกัน จาก 2 เป็น 32 คือสิบหกเท่า
จากบทสนทนาที่แทบไม่มีเนื้อหาอะไรเลย

**ตัวเลขชุดนี้มาจากไหน ต้องพูดให้ตรง** มันไม่ได้มาจากผู้ให้บริการจริง
บทเรียนรันกับ mock server ของหลักสูตร ซึ่งประมาณจำนวน token ด้วยการหาร
ความยาวข้อความด้วยสี่ แล้วรายงานตัวเลขนั้นในช่อง `usage` โค้ดของ mock
เขียนกำกับไว้เองว่ามันหยาบ

```python
def estimate_tokens(text):
    """A deliberately crude token estimate, about four characters per token.

    This is not accurate and the chapter on token economy says so plainly.
    It exists so the mock can report a number that moves in the right
    direction when the conversation grows.
    """
    return max(1, len(text) // 4)
```

สิ่งที่การทดลองนี้พิสูจน์จึงเป็นรูปร่างของเส้น ไม่ใช่ค่าสัมบูรณ์ ผู้ให้บริการ
จริงจะให้ตัวเลขคนละชุด แต่จะโตในรูปเดียวกัน เพราะรูปนั้นมาจากสิ่งที่เราส่ง
ไม่ได้มาจากวิธีนับ

ผลกระทบมีสองด้าน ด้านแรกคือเงิน ด้านที่สองคือเวลา model ต้องอ่าน input
ทั้งหมดให้จบก่อนจะเขียนคำแรกของ output ดังนั้น input ที่ยาวขึ้นแปลว่า
เวลาก่อนตัวอักษรแรกจะโผล่บนจอก็นานขึ้นด้วย บทสนทนาที่ยาวไม่ได้แค่แพงขึ้น
มันช้าลงในแบบที่ผู้ใช้รู้สึกได้

**ทำไมเรื่องนี้ถึงสำคัญตั้งแต่บทแรก** เพราะสอง subsystem ที่ยากที่สุดใน
หลักสูตร คือ context management กับ token economy มีอยู่เพื่อแก้ผลของ
ข้อเท็จจริงข้อนี้ข้อเดียว ถ้าคุณไม่เข้าใจว่ามันมาจากไหน คุณจะมองว่ามันเป็น
optimization ที่ทำก็ได้ไม่ทำก็ได้ ทั้งที่จริงมันคือสิ่งที่ตัดสินว่า agent
ของคุณทำงานได้เกินสิบรอบหรือไม่

## 4. token คืออะไร และทำไมตัวนับของแต่ละเจ้าไม่เท่ากัน

token (โทเคน คือหน่วยย่อยของข้อความที่ model ใช้นับ) ไม่ใช่ตัวอักษรและไม่ใช่คำ
มันคือชิ้นส่วนของข้อความที่ได้จากการแบ่งด้วย tokenizer (ตัวแบ่งโทเคน
คืออัลกอริทึมที่แปลงข้อความเป็น list ของตัวเลข) คำภาษาอังกฤษที่พบบ่อยมัก
เป็นหนึ่ง token ส่วนคำที่พบน้อย ชื่อเฉพาะ และภาษาไทย มักถูกแบ่งเป็นหลายชิ้น

ข้อเท็จจริงที่คนพลาดบ่อยที่สุดคือ tokenizer ของแต่ละผู้ให้บริการไม่เหมือนกัน
ข้อความเดียวกันนับได้ 100 token ที่เจ้าหนึ่ง และ 130 ที่อีกเจ้าหนึ่ง
ดังนั้นการเอา tokenizer ของเจ้าหนึ่งไปประเมิน token ของอีกเจ้าหนึ่ง
แล้วใช้ตัวเลขนั้นตัดสินใจว่าจะตัด context ตรงไหน คือการตัดสินใจบนตัวเลขที่ผิด

หลักสูตรนี้จึงแยกสองอย่างออกจากกันอย่างชัดเจน `src/agentpath/context.py`
มีตัวประมาณคร่าวๆ ที่จงใจไม่แม่น

```python
def estimate_tokens(messages: list[Message]) -> int:
    """A rough count, deliberately not exact.

    Every provider counts differently and none of them count the way a
    character estimate does. Use this to decide when to start trimming, then
    use the number the provider reports afterwards to know what actually
    happened. Trusting a local estimate to be exact is how people end up
    trimming to ninety percent of a window and still getting rejected.
    """
```

ส่วน `src/agentpath/usage.py` เก็บเฉพาะตัวเลขที่ผู้ให้บริการรายงานกลับมาจริง

```python
    def add(self, reported: dict) -> None:
        """Record what one request actually cost, as the provider reported it."""
        if not reported:
            return
        self.calls += 1
        self.prompt_tokens += reported.get("prompt_tokens", 0)
        self.completion_tokens += reported.get("completion_tokens", 0)
        self.per_call.append(reported)
```

**ทำไมต้องมีสองอย่าง** เพราะสองอย่างนี้ตอบคำถามคนละข้อ ตัวประมาณตอบคำถามว่า
"ถึงเวลาเริ่มตัดหรือยัง" ซึ่งเป็นคำถามที่ต้องตอบก่อนส่ง และตอบผิดนิดหน่อยได้
ตัวเลขจริงตอบคำถามว่า "เมื่อกี้จ่ายไปเท่าไหร่" ซึ่งเป็นคำถามที่ต้องตอบหลังส่ง
และตอบผิดไม่ได้เลยเพราะมันคือเงิน

**ทำไมไม่ใช้ตัวเลขจริงอย่างเดียว** เพราะตัวเลขจริงมาหลังจากส่งไปแล้ว ถ้าคุณ
ส่งเกินหน้าต่าง คุณได้ error ไม่ได้ตัวเลข การตัดสินใจตัดต้องเกิดก่อนหน้านั้น
จึงต้องอาศัยการประมาณ

**ทำไมไม่ใช้ tokenizer ตัวจริงมาประมาณ** ทำได้ถ้าคุณมีของเจ้านั้น แต่มัน
เพิ่ม dependency หนักๆ เข้ามาเพื่อความแม่นที่ไม่ได้เปลี่ยนการตัดสินใจ
ตัวประมาณแบบหารสี่บอกได้ว่าใกล้เต็มหรือยัง ซึ่งเพียงพอกับหน้าที่ของมัน
และไม่มีวันหลอกให้ใครคิดว่ามันแม่นจนตัดถึงเก้าสิบเปอร์เซ็นต์ของหน้าต่าง

## 5. streaming และเหตุผลที่มันเปลี่ยนรูปของโค้ด

model เขียนคำตอบทีละ token ถ้าเรารอจนจบแล้วค่อยคืนทั้งก้อน ผู้ใช้จะเห็น
หน้าจอว่างเปล่านานหลายวินาที ทั้งที่คำตอบเริ่มถูกสร้างตั้งแต่วินาทีแรก
streaming (การส่งเป็นสาย คือการทยอยส่งคำตอบทีละชิ้นแทนที่จะส่งทีเดียวจบ)
คือการเปิดท่อไว้แล้วอ่านชิ้นส่วนที่ทยอยมา

รูปแบบที่ใช้คือ SSE (Server-Sent Events คือรูปแบบส่งข้อมูลทางเดียวจาก
server มา client ทีละบรรทัด) แต่ละบรรทัดขึ้นต้นด้วย `data: ` แล้วตามด้วย
JSON หนึ่งก้อน จบด้วยบรรทัดที่เขียนว่า `[DONE]`

**ทำไมไม่ใช้ websocket** เพราะเราต้องการทางเดียว server พูด client ฟัง
websocket แก้ปัญหาสองทางซึ่งเราไม่มี และแลกมาด้วย protocol ที่ซับซ้อนกว่า
proxy ที่รองรับน้อยกว่า และการ reconnect ที่ต้องเขียนเอง SSE คือ HTTP
response ธรรมดาที่ยังไม่ปิด อ่านด้วยตาก็ได้ debug ด้วย curl ก็ได้

สิ่งที่คนมองข้ามคือ streaming ไม่ได้เปลี่ยนแค่การแสดงผล มันเปลี่ยนรูปร่างของ
โค้ดทั้งเส้น ฟังก์ชันที่เคย `return` ค่าเดียว ต้องกลายเป็นสิ่งที่ทยอยคาย
ค่าออกมา ในหลักสูตรนี้คือ generator (เจเนอเรเตอร์ คือฟังก์ชันที่ yield ค่า
ออกมาทีละตัวแทนที่จะ return ทีเดียว) และผลนั้นไหลขึ้นไปถึงชั้นบนสุด

interface ของ provider ทั้งหมดจึงถูกออกแบบรอบ stream ตั้งแต่แรก ไม่ใช่
เพิ่มทีหลัง

```python
class Provider:
    def stream(self, messages: list[Message], tools: list[dict] | None = None) -> Iterator:
        raise NotImplementedError
```

**ทำไมต้องออกแบบเผื่อ streaming ตั้งแต่แรก** เพราะการเติม streaming เข้าไป
ทีหลังไม่ใช่การเพิ่มฟีเจอร์ มันคือการรื้อ signature ของทุกฟังก์ชันบนเส้นทาง
จาก HTTP ขึ้นมาถึงหน้าจอ หลักสูตรจึงจงใจสอน streaming ในบทที่ 5 ตอนที่โค้ด
ยังเล็ก และสอน provider abstraction ในบทที่ 6 หลังจากนั้น ถ้าสลับลำดับ
คุณจะต้อง retrofit streaming เข้าไปในสอง provider พร้อมกัน เท่ากับรื้อสองรอบ

ผลข้างเคียงที่สำคัญของ streaming คือ tool call มาเป็นเศษ argument ของ
tool call เดินทางมาเป็นชิ้นๆ ของ JSON ที่ต้องสะสมเอง และถ้า model ชนเพดาน
output กลางทาง JSON ก้อนนั้นจะขาดกลางคัน `src/agentpath/providers/base.py`
จัดการเรื่องนี้ด้วยการไม่ซ่อนความพัง

```python
def parse_arguments(raw: str) -> tuple[dict, str]:
    """Turn streamed argument text into a dict, or report why it could not.

    Returns (arguments, error). A model that hits its output limit part way
    through a tool call sends back JSON that stops mid string. Quietly
    turning that into an empty dict is the worst possible answer, because the
    tool then runs with no arguments and the model never learns it made a
    mistake, so it repeats the same broken call every time the conversation
    is replayed.
    """
```

ประโยคสุดท้ายในนั้นคือหัวใจ และมันเชื่อมกลับมาที่หัวข้อแรกของบทนี้ ถ้าคุณ
เปลี่ยน JSON ที่พังให้เป็น dict ว่างอย่างเงียบๆ ความพังนั้นจะถูกเขียนลง
history และเพราะ history ถูกส่งใหม่ทุกรอบ model จะเห็นความพังนั้นซ้ำๆ
โดยไม่มีทางรู้ว่าตัวเองพลาด ความไร้ความจำของ model แปลว่าสิ่งเดียวที่มันรู้
คือสิ่งที่อยู่ใน list และถ้าคุณไม่เขียน error ลงไปใน list มันจะไม่มีวันรู้ครับ

## 6. สรุปสิ่งที่ต้องติดตัวไปบทถัดไป

สามข้อแรกเป็นเรื่องรูปร่างของสิ่งที่เดินทางอยู่บนสาย

- model คือ endpoint ไร้สถานะ ที่รับ list ของ message แล้วคืน message
- ความจำทั้งหมดเป็นของคุณ ไม่ใช่ของมัน และมันคือ list ธรรมดาหนึ่ง list
- ต้นทุนโตแบบกำลังสองเพราะทุกรอบส่งของเก่าไปใหม่ทั้งหมด

สามข้อหลังเป็นผลที่ตามมาจากสามข้อแรก และเป็นข้อที่จะถูกหยิบมาใช้ซ้ำตลอดเล่ม

- token ไม่ใช่คำ และตัวนับของแต่ละเจ้าไม่เท่ากัน ใช้ตัวประมาณเพื่อตัดสินใจ
  ใช้ตัวเลขจากผู้ให้บริการเพื่อรู้ความจริง
- streaming เปลี่ยนรูปของโค้ดทั้งเส้น จึงต้องอยู่ในแบบตั้งแต่วันแรก
- อะไรที่ model ต้องรู้ ต้องอยู่ใน list ไม่มีช่องทางอื่น
