# บทที่ 1 model คืออะไรจริงๆ และทำไมมันไม่มีความจำ

คุณบอกมันว่าแมวของคุณชื่อมิโสะ คุยกันต่ออีกสองสามข้อความ แล้วถามว่าแมวชื่ออะไร
มันตอบว่ามิโสะ ทุกอย่างในประสบการณ์นั้นบอกว่ามันจำได้ และทุกอย่างในประสบการณ์นั้น
ผิด มันไม่ได้จำ คุณส่งชื่อแมวไปให้มันใหม่ทุกครั้งที่พิมพ์ โดยไม่รู้ตัว

หนังสือทั้งเล่มตั้งอยู่บนข้อเท็จจริงข้อเดียวนี้ model (ตัวประมวลผลภาษาที่เราเรียกผ่านเครื
อข่าย) ไม่มีความจำ ไม่มีสักนิดเดียว ถ้าเข้าใจข้อนี้ผิด การตัดสินใจทุกข้อที่ตามมาจะผิดตาม
ไปด้วย และคุณจะแก้ปัญหาที่ไม่มีอยู่จริง ขณะที่ปัญหาที่มีอยู่จริงมองไม่เห็น

บทนี้เดินจากสิ่งที่วิ่งอยู่บนสายจริงๆ คือ endpoint (URL หนึ่งตัวที่รับคำขอแล้วตอบกลับ)
ไร้สถานะที่รับ list แล้วคืน message ไปถึงผลที่ตามมาหกข้อ ตั้งแต่เหตุผลที่ต้นทุนของบทสนทนา
โตแบบกำลังสอง ไปจนถึงเหตุผลที่ streaming (ทยอยส่งคำตอบทีละชิ้น ไม่รอส่งทีเดียวจบ) ต้องอ
ยู่ในแบบตั้งแต่วันแรก ไม่ใช่ค่อยเติมทีหลัง ถ้าคุณอ่านภาคพื้นฐานมาแล้วครึ่งแรกของบทนี้จะ
เป็นการเห็นสิ่งเดิมจากอีกฝั่งของสาย

หัวข้อที่ 4 เรื่อง token กับตัวนับที่ไม่ตรงกันของแต่ละเจ้า ข้ามได้ในรอบแรก แล้วค่อย
กลับมาตอนที่ต้องตัดสินใจว่าจะตัด context ตรงไหน หัวข้อที่เหลือเรียงต่อกันได้โดยไม่
ต้องพึ่งมัน

## 1. เมื่อมองจากข้างนอก model คือ HTTP endpoint หนึ่งตัว

เวลาคนพูดถึง LLM (large language model คือ model ภาษาที่ฝึกบนข้อความกองมหาศาลจนใช้ได้สาร
พัดงาน) พวกเขามักนึกถึงสิ่งที่มีบุคลิก มีความคิด และจำได้ว่าคุยอะไรกันไว้ นั่นคือภาพจาก
ฝั่งผู้ใช้ ซึ่งถูกในเชิงประสบการณ์ และผิดสนิทในเชิงวิศวกรรม

จากมุมของคนที่เขียนโค้ดเรียกมัน model คือ HTTP endpoint ที่รับ JSON ก้อนหนึ่งแล้วคืน
JSON อีกก้อนหนึ่ง ในก้อนที่ส่งไปมี list ของ message (ข้อความ คือหนึ่งรอบพูดในบทสนทนา) และ
ในก้อนที่ได้กลับมามี message อีกหนึ่งอัน จบแค่นั้น

นี่คือหน้าตาจริงของสิ่งที่เดินทางไปบนสาย โค้ดข้างล่างมาจาก
`src/agentpath/providers/openai_compat.py` และเป็นฟังก์ชันที่แปลง Message ของเรา
ให้เป็นรูปที่ API ต้องการ

```python
def to_wire(message: Message) -> dict:
    """Convert one Message into the shape the API expects."""
    if message.role == "tool":
        return {
            "role": "tool",
            "tool_call_id": message.tool_call_id,
            "content": message.content,
        }
    wire = {"role": message.role, "content": message.content}
    if message.tool_calls:
        wire["tool_calls"] = [
            {
                "id": call.id,
                "type": "function",
                "function": {"name": call.name, "arguments": json.dumps(call.arguments)},
            }
            for call in message.tool_calls
        ]
    return wire
```

สังเกตว่าไม่มีอะไรในนี้ที่อ้างถึงคำขอครั้งก่อนเลย ไม่มี session id ไม่มี conversation id
ไม่มี token ที่ใช้ต่อสาย ทุกคำขอเป็นคำขอแรกเสมอในสายตาของ server

มันเป็นแบบนี้เพราะ model ที่ให้บริการอยู่หลังนั้นถูกรันแบบขนานบนเครื่องจำนวนมาก คำขอ
สองครั้งติดกันของคุณอาจไปลงคนละเครื่อง ถ้า server ต้องเก็บ state (สถานะ คือข้อมูลที่
ค้างอยู่ระหว่างคำขอ) ของทุกบทสนทนา ผู้ให้บริการต้องแบกบทสนทนาของคนทั้งโลกไว้ พร้อม
คำถามว่าจะเก็บนานแค่ไหน ใครลบได้ และเครื่องไหนเป็นเจ้าของ endpoint ไร้สถานะย้าย
ภาระนั้นมาไว้ที่ผู้เรียก ซึ่งคือคุณ

ผู้ให้บริการบางเจ้ามี API ที่เก็บบทสนทนาให้ และมันสะดวกจริง แต่มันสะดวกโดยการซ่อนสิ่ง
ที่คุณต้องควบคุม ถ้าคุณไม่เห็นว่าอะไรถูกส่งไปบ้าง คุณจะตัด context ไม่เป็น ดู cache
ไม่ออก และ debug ไม่ได้ตอนที่ model ทำอะไรแปลกๆ หลักสูตรนี้จึงยิง HTTP เองตั้งแต่บรรทัด
แรก สิ่งที่คุณมองไม่เห็นคือสิ่งที่คุณแก้ไม่ได้ครับ

## 2. ความจำที่คุณเห็นคือการส่งซ้ำ

กลับมาที่แมว ถ้า model ไม่มีความจำ ทำไมมันตอบได้ว่าแมวชื่ออะไร ทั้งที่คุณบอกไปเมื่อ
สามข้อความก่อน

เพราะคุณส่งไปใหม่ ทั้งก้อน ทุกครั้ง

```json
[
  {"role": "system",    "content": "You are a terse assistant."},
  {"role": "user",      "content": "My cat is called Miso."},
  {"role": "assistant", "content": "Noted."},
  {"role": "user",      "content": "What is my cat called?"}
]
```

คำขอนี้คือคำขอแรกของบทสนทนาที่บังเอิญยาวสี่บรรทัด ไม่ใช่คำขอที่สี่
model อ่านทั้งสี่บรรทัดจากบนลงล่าง แล้วเขียนบรรทัดที่ห้า มันไม่ได้จำว่าเคยตอบว่า Noted
มันแค่อ่านเจอว่ามีบรรทัดที่บอกว่ามันเคยตอบแบบนั้น บทพื้นฐานที่ 7 ประกอบ string
ก้อนนี้ให้ดูด้วยมือ และบทพื้นฐานที่ 3 สร้าง model ที่ความจำทั้งหมดคือคำที่อยู่ในมือ
ตอนถูกเรียก ตัวจริงต่างกันแค่ขนาด

นี่คือเหตุผลที่ state ของ agent ในหลักสูตรนี้เป็น list ธรรมดา และเหตุผลที่ session ถูก
เก็บเป็น JSONL (JSON Lines คือไฟล์ที่หนึ่งบรรทัดคือหนึ่ง JSON) ที่เปิดอ่านด้วยตาเปล่าได้
ความจำของ agent ไม่ใช่สิ่งลึกลับ มันคือไฟล์ข้อความที่คุณเปิดดูได้ และในไฟล์นั้นไม่มี
อะไรมากกว่าสิ่งที่คุณเห็น

`src/agentpath/types.py` นิยาม Message ไว้แค่นี้ และความจำทั้งหมดของระบบคือ list ของ
สิ่งนี้

```python
@dataclass
class Message:
    """One entry in the conversation.

    role is one of system, user, assistant, tool. tool_call_id is filled in
    only when role is tool, so the provider can match a result back to the
    call that produced it.
    """

    role: str
    content: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    tool_call_id: str = ""
```

พอเห็นว่าความจำคือการส่งซ้ำ คุณจะเลิกถามคำถามผิดๆ อย่าง จะสอนให้ model จำเรื่องนี้
ได้ยังไง แล้วเริ่มถามคำถามที่ถูก คือในคำขอครั้งหน้า อะไรควรอยู่ในนั้นบ้าง คำถามที่สอง
ตอบได้ด้วยโค้ด คำถามแรกตอบไม่ได้เลยครับ

## 3. ค่าใช้จ่ายโตแบบกำลังสอง และนี่คือตัวเลขจริง

ค่าใช้จ่ายของบทสนทนาหนึ่งชุดไม่ได้โตแบบเชิงเส้น เหตุผลอยู่ในหัวข้อที่แล้ว ถ้าทุกคำขอ
ส่งบทสนทนาทั้งก้อน และบทสนทนาโตขึ้นทุกรอบ ต้นทุนรวมจึงไม่ใช่จำนวนรอบคูณความยาว
ของหนึ่งข้อความ แต่คือผลรวมของอนุกรมที่โตขึ้นเรื่อยๆ

รอบที่หนึ่งส่งหนึ่งข้อความ รอบที่สองส่งสาม รอบที่สิบส่งสิบเก้า ถ้าแต่ละข้อความยาวพอกัน
ต้นทุนรวมโตประมาณกำลังสองของจำนวนรอบ บทสนทนายี่สิบรอบไม่ได้แพงเป็นยี่สิบเท่าของรอบ
เดียว มันแพงกว่านั้นมาก

บทเรียนที่ 15 ในหลักสูตรวัดเรื่องนี้ด้วยการทดลองที่จงใจทำให้น่าเบื่อที่สุด ผู้ใช้พูดว่า Say
hello แล้วพูดว่า And again ไปเรื่อยๆ ไม่มีใครอ่านไฟล์ ไม่มีใครเรียก tool แต่ละรอบเพิ่ม
ข้อความสองบรรทัด คำถามกับคำตอบ รวมประมาณสี่สิบห้าตัวอักษร

```text
OK the same conversation cost more every turn, [2, 12, 22, 32]
```

สี่ตัวเลขนั้นคือจำนวน prompt tokens (ส่วนที่โดนคิดเงินจากสิ่งที่เราส่งไป)
ที่ถูกรายงานกลับมาในสี่คำขอติดกัน จาก 2 เป็น 32 คือสิบหกเท่า จากบทสนทนาที่แทบไม่มี
เนื้อหาอะไรเลย

ตัวเลขชุดนี้ต้องพูดให้ตรงว่ามาจากไหน มันไม่ได้มาจากผู้ให้บริการจริง บทเรียนรันกับ
mock server ของหลักสูตร ซึ่งประมาณจำนวน token ด้วยการหารความยาวข้อความด้วยสี่ แล้ว
รายงานตัวเลขนั้นในช่อง `usage` โค้ดของ mock เขียนกำกับไว้เองว่ามันหยาบ

```python
def estimate_tokens(text):
    """A deliberately crude token estimate, about four characters per token.

    This is not accurate and the chapter on token economy says so plainly.
    It exists so the mock can report a number that moves in the right
    direction when the conversation grows.
    """
    return max(1, len(text) // 4)
```

ค่าต่อคำขอโตเป็นเส้นตรง สิ่งที่โตเป็นกำลังสองคือผลรวมของทุกคำขอ ซึ่งคือบิล
สิ่งที่การทดลองนี้พิสูจน์จึงเป็นรูปร่างของเส้น ไม่ใช่ค่าสัมบูรณ์ ผู้ให้บริการจริงจะให้
ตัวเลขคนละชุด แต่จะโตในรูปเดียวกัน เพราะรูปนั้นมาจากสิ่งที่เราส่ง ไม่ได้มาจากวิธีนับ

ผลกระทบมีสองด้าน ด้านแรกคือเงิน ด้านที่สองคือเวลา model ต้องอ่าน input ทั้งหมดให้จบ
ก่อนจะเขียนคำแรกของ output ดังนั้น input ที่ยาวขึ้นแปลว่าเวลาก่อนตัวอักษรแรกจะโผล่
บนจอนานขึ้นด้วย บทสนทนาที่ยาวไม่ได้แค่แพงขึ้น มันช้าลงในแบบที่ผู้ใช้รู้สึกได้
และบทพื้นฐานที่ 6 บอกว่าทำไมการอ่านนั้นถึงแพงเป็นกำลังสองในตัวเองอีกชั้นหนึ่ง

เรื่องนี้สำคัญตั้งแต่บทแรก เพราะสอง subsystem ที่ยากที่สุดในหลักสูตร คือ context
management กับ token economy มีอยู่เพื่อแก้ผลของข้อเท็จจริงข้อนี้ข้อเดียว ถ้าคุณไม่
เข้าใจว่ามันมาจากไหน คุณจะมองว่ามันเป็น optimization ที่ทำก็ได้ไม่ทำก็ได้ ทั้งที่จริง
มันคือสิ่งที่ตัดสินว่า agent ของคุณทำงานได้เกินสิบรอบหรือไม่ครับ

## 4. token คืออะไร และทำไมตัวนับของแต่ละเจ้าไม่เท่ากัน

token (ชิ้นข้อความที่ model หั่นมาเอง แล้วนับทีละชิ้น) คือชิ้นส่วนที่ tokenizer
(ตัวที่แปลงข้อความเป็น list ของตัวเลข) ตัดออกมา
ไม่ใช่ตัวอักษร และไม่ใช่คำ คำภาษาอังกฤษที่พบบ่อยมักเป็นหนึ่ง token คำที่พบน้อย ชื่อ
เฉพาะ และภาษาไทย มักถูกแบ่งเป็นหลายชิ้น บทพื้นฐานที่ 2 สร้าง tokenizer ขึ้นมาจาก
ศูนย์และแสดงว่าทำไมภาษาไทยถึงแพง ถ้าอยากเห็นกลไก ไปที่นั่น

ข้อเท็จจริงที่คนพลาดบ่อยที่สุดคือ tokenizer ของแต่ละผู้ให้บริการไม่เหมือนกัน ข้อความ
เดียวกันนับได้ 100 token ที่เจ้าหนึ่ง และ 130 ที่อีกเจ้าหนึ่ง การเอา tokenizer ของเจ้า
หนึ่งไปประเมิน token ของอีกเจ้าหนึ่ง แล้วใช้ตัวเลขนั้นตัดสินใจว่าจะตัด context ตรงไหน
คือการตัดสินใจบนตัวเลขที่ผิด

หลักสูตรนี้จึงแยกสองอย่างออกจากกันชัดเจน `src/agentpath/context.py` มีตัวประมาณ
คร่าวๆ ที่จงใจไม่แม่น

```python
def estimate_tokens(messages: list[Message]) -> int:
    """A rough count, deliberately not exact.

    Every provider counts differently and none of them count the way a
    character estimate does. Use this to decide when to start trimming, then
    use the number the provider reports afterwards to know what actually
    happened. Trusting a local estimate to be exact is how people end up
    trimming to ninety percent of a window and still getting rejected.
    """
```

ส่วน `src/agentpath/usage.py` เก็บเฉพาะตัวเลขที่ผู้ให้บริการรายงานกลับมาจริง

```python
    def add(self, reported: dict) -> None:
        """Record what one request actually cost, as the provider reported it."""
        if not reported:
            return
        self.calls += 1
        self.prompt_tokens += reported.get("prompt_tokens", 0)
        self.completion_tokens += reported.get("completion_tokens", 0)
        self.per_call.append(reported)
```

สองอย่างนี้ตอบคำถามคนละข้อ ตัวประมาณตอบว่าถึงเวลาเริ่มตัดหรือยัง
คำถามนี้ต้องตอบก่อนส่ง และตอบผิดนิดหน่อยได้ ตัวเลขจริงตอบว่าเมื่อกี้จ่ายไปเท่าไหร่
คำถามนี้ต้องตอบหลังส่ง และตอบผิดไม่ได้เลยเพราะมันคือเงิน

ใช้ตัวเลขจริงอย่างเดียวไม่ได้ เพราะมันมาหลังจากส่งไปแล้ว ถ้าคุณส่งเกินหน้าต่าง คุณได้
error ไม่ได้ตัวเลข การตัดสินใจตัดต้องเกิดก่อนหน้านั้น จึงต้องอาศัยการประมาณ ส่วน
การเอา tokenizer ตัวจริงมาประมาณ ทำได้ถ้าคุณมีของเจ้านั้น แต่มันเพิ่ม dependency หนักๆ
เพื่อความแม่นที่ไม่ได้เปลี่ยนการตัดสินใจ ตัวประมาณแบบหารสี่บอกได้ว่าใกล้เต็มหรือยัง
ซึ่งเพียงพอกับหน้าที่ของมัน และไม่มีวันหลอกให้ใครคิดว่ามันแม่นจนตัดถึงเก้าสิบ
เปอร์เซ็นต์ของหน้าต่าง

## 5. streaming และเหตุผลที่มันเปลี่ยนรูปของโค้ด

model เขียนคำตอบทีละ token ถ้าเรารอจนจบแล้วค่อยคืนทั้งก้อน ผู้ใช้จะเห็นหน้าจอว่างเปล่า
นานหลายวินาที ทั้งที่คำตอบเริ่มถูกสร้างตั้งแต่วินาทีแรก streaming
คือการเปิดท่อไว้แล้วอ่านชิ้นส่วนที่ทยอยมา

รูปแบบที่ใช้คือ SSE (Server-Sent Events คือรูปแบบส่งข้อมูลทางเดียวจาก server มา
client ทีละบรรทัด) แต่ละบรรทัดขึ้นต้นด้วย `data: ` แล้วตามด้วย JSON หนึ่งก้อน และในรูป
แบบของ OpenAI จบด้วยบรรทัดที่เขียนว่า `[DONE]` ส่วน Anthropic จบด้วย event ชื่อ
`message_stop` ไม่ใช้ websocket เพราะเราต้องการทางเดียว server พูด client
ฟัง websocket แก้ปัญหาสองทางซึ่งเราไม่มี และแลกมาด้วย protocol ที่ซับซ้อนกว่า proxy
ที่รองรับน้อยกว่า และการ reconnect ที่ต้องเขียนเอง SSE คือ HTTP response ธรรมดาที่
ยังไม่ปิด อ่านด้วยตาก็ได้ debug ด้วย curl ก็ได้

สิ่งที่คนมองข้ามคือ streaming ไม่ได้เปลี่ยนแค่การแสดงผล มันเปลี่ยนรูปร่างของโค้ดทั้ง
เส้น ฟังก์ชันที่เคย `return` ค่าเดียว ต้องกลายเป็นสิ่งที่ทยอยคายค่าออกมา ในหลักสูตรนี้
คือ generator (ฟังก์ชันที่ yield ค่าออกมาทีละตัว ไม่ return ทีเดียวจบ)
และผลนั้นไหลขึ้นไปถึงชั้นบนสุด

interface ของ provider ทั้งหมดจึงถูกออกแบบรอบ stream ตั้งแต่แรก

```python
class Provider:
    def stream(self, messages: list[Message], tools: list[dict] | None = None) -> Iterator:
        raise NotImplementedError
```

การเติม streaming เข้าไปทีหลังคือการรื้อ signature ของทุก
ฟังก์ชันบนเส้นทางจาก HTTP ขึ้นมาถึงหน้าจอ หลักสูตรจึงจงใจสอน streaming ในบทเรียนที่ 05
ตอนที่โค้ดยังเล็ก และสอน provider abstraction ในบทเรียนที่ 06 หลังจากนั้น ถ้าสลับลำดับ คุณจะ
ต้อง retrofit streaming เข้าไปในสอง provider พร้อมกัน เท่ากับรื้อสองรอบ

ผลข้างเคียงที่สำคัญของ streaming คือ tool call มาเป็นเศษ argument ของ tool call เดินทาง
มาเป็นชิ้นๆ ของ JSON ที่ต้องสะสมเอง และถ้า model ชนเพดาน output กลางทาง JSON ก้อนนั้น
จะขาดกลางคัน `src/agentpath/providers/base.py` จัดการเรื่องนี้ด้วยการไม่ซ่อนความพัง

```python
def parse_arguments(raw: str) -> tuple[dict, str]:
    """Turn streamed argument text into a dict, or report why it could not.

    Returns (arguments, error). A model that hits its output limit part way
    through a tool call sends back JSON that stops mid string. Quietly
    turning that into an empty dict is the worst possible answer, because the
    tool then runs with no arguments and the model never learns it made a
    mistake, so it repeats the same broken call every time the conversation
    is replayed.
    """
```

ประโยคสุดท้ายในนั้นคือหัวใจ และมันเชื่อมกลับมาที่หัวข้อแรกของบทนี้ ถ้าคุณเปลี่ยน JSON
ที่พังให้เป็น dict ว่างอย่างเงียบๆ ความพังนั้นจะถูกเขียนลง history และเพราะ history
ถูกส่งใหม่ทุกรอบ model จะเห็นความพังนั้นซ้ำๆ โดยไม่มีทางรู้ว่าตัวเองพลาด ความไร้ความ
จำของ model แปลว่าสิ่งเดียวที่มันรู้คือสิ่งที่อยู่ใน list และถ้าคุณไม่เขียน error ลงไป
ใน list มันจะไม่มีวันรู้ครับ

## 6. สรุปสิ่งที่ต้องติดตัวไปบทถัดไป

สามข้อแรกเป็นเรื่องรูปร่างของสิ่งที่เดินทางอยู่บนสาย

- model คือ endpoint ไร้สถานะ ที่รับ list ของ message แล้วคืน message
- ความจำเป็นของคุณ ไม่ใช่ของมัน และเป็น list ธรรมดาหนึ่ง list
- ต้นทุนโตแบบกำลังสองเพราะทุกรอบส่งของเก่าไปใหม่ทั้งหมด

สามข้อหลังเป็นผลที่ตามมาจากสามข้อแรก และเป็นข้อที่จะถูกหยิบมาใช้ซ้ำตลอดเล่ม

- token ไม่ใช่คำ และตัวนับของแต่ละเจ้าไม่เท่ากัน ใช้ตัวประมาณเพื่อตัดสินใจ
  ใช้ตัวเลขจากผู้ให้บริการเพื่อรู้ความจริง
- streaming เปลี่ยนรูปของโค้ดทั้งเส้น จึงต้องอยู่ในแบบตั้งแต่วันแรก
- อะไรที่ model ต้องรู้ ต้องอยู่ใน list ไม่มีช่องทางอื่น
