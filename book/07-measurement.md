# บทที่ 7 ถ้าวัดไม่ได้ ก็ไม่รู้ว่าดีขึ้นหรือแย่ลง

หกบทก่อนหน้านี้ตั้งอยู่บนสมมติฐานเงียบๆ ข้อหนึ่ง คือคุณแยกการเปลี่ยนแปลงที่ดี
ออกจากที่แย่ได้ด้วยการดู

คุณแยกไม่ได้ และบทนี้คือเรื่องนั้น

## 1. ทำไมความรู้สึกว่าดีขึ้นเชื่อไม่ได้

คุณแก้คำใน system prompt หนึ่งคำ ลองรันงานที่เคยพัง มันผ่าน คุณสรุปว่าดีขึ้น

สิ่งที่คุณไม่ได้ทำคือรันอีกยี่สิบงานที่เคยผ่าน และในนั้นมีสามงานที่พังไปแล้ว

**ทำไมเรื่องนี้ถึงเกิดขึ้นเป็นปกติ ไม่ใช่ข้อยกเว้น** เพราะ prompt ไม่มี type
system ไม่มี compiler และไม่มีขอบเขต การเปลี่ยนคำหนึ่งคำเปลี่ยนพฤติกรรม
ในงานทั้งหมดพร้อมกัน ต่างจากการแก้ฟังก์ชันหนึ่งตัวซึ่งกระทบเฉพาะคนที่เรียก
ฟังก์ชันนั้น

**ทำไมสมองไม่ช่วย** เพราะการทดสอบด้วยตาเลือกตัวอย่างแบบลำเอียงเสมอ คุณลอง
งานที่คุณเพิ่งแก้ให้มันทำได้ คุณจำงานที่ผ่านได้ดีกว่างานที่พังเงียบๆ
และเมื่อคุณลงแรงกับการแก้ไปแล้ว คุณอยากให้มันได้ผล

**ทำไมความไม่แน่นอนทำให้แย่ลงอีก** เพราะ model ไม่ได้ให้คำตอบเดิมทุกครั้ง
งานที่ผ่านหนึ่งครั้งอาจผ่านสามในสิบครั้ง การรันครั้งเดียวแล้วสรุป จึงวัด
โชคพอๆ กับวัดคุณภาพ

ทางออกเดียวคือมีชุดงานคงที่ที่รันได้ก่อนและหลัง แล้วเทียบตัวเลข

## 2. eval คือชุดงานที่มีเกณฑ์ตรวจ

eval (การประเมิน คือชุดงานที่รันซ้ำได้พร้อมเกณฑ์ตัดสินว่าผ่านหรือไม่)
ไม่ใช่อะไรที่ซับซ้อนกว่านี้ มันคือ test suite ที่ยอมรับว่าผลลัพธ์ไม่แน่นอน

```python
@dataclass
class Task:
    """One thing the agent should be able to do.

    check receives the final answer and the workspace, and returns a pair of
    a boolean and a sentence explaining the verdict. The sentence is not
    decoration. A failing eval you cannot read is a failing eval you will
    ignore.
    """

    name: str
    prompt: str
    check: object
    workspace: object = None
```

**ทำไม check ต้องคืนประโยคด้วย ไม่ใช่แค่ boolean** เพราะ eval ที่บอกว่างานที่
เจ็ดล้มเหลว โดยไม่บอกว่าล้มเหลวยังไง คือ eval ที่คุณจะเลิกอ่านภายในสัปดาห์เดียว
รายงานที่ไม่มีใครอ่านไม่เปลี่ยนอะไร

**ทำไม check ต้องได้ workspace ด้วย ไม่ใช่แค่คำตอบ** เพราะสิ่งที่ agent
ทำสำคัญกว่าสิ่งที่ agent พูด ซึ่งคือหัวข้อถัดไป

## 3. การตรวจเชิงกลไกดีกว่า judge เมื่อทำได้

```python
"""Measuring whether the agent actually works.
...
Two kinds of check exist here and the split matters. A mechanical check is a
function that looks at the world and returns true or false. It is free,
instant, and it has no opinions. A judge asks a model whether an answer is
acceptable, which costs money, takes time, and can be wrong. Use a judge only
for the things a function genuinely cannot decide, such as whether an
explanation is clear.
"""
```

**การตรวจเชิงกลไกคืออะไร** ฟังก์ชัน Python ธรรมดาที่ไปดูโลกจริงแล้วคืน
true หรือ false ไฟล์นี้มีข้อความนี้หรือไม่ เทสของโปรเจกต์ผ่านหรือไม่
ฟังก์ชันที่ agent เขียนคืนค่าถูกหรือไม่

**ทำไมมันดีกว่า** สามเหตุผล มันฟรี มันได้ผลทันที และมันไม่มีความเห็น
ฟังก์ชันที่ตรวจว่าเทสผ่านหรือไม่ ให้คำตอบเดิมทุกครั้งสำหรับสถานะเดิม
ในขณะที่ model ที่ทำหน้าที่กรรมการ อาจให้คำตอบต่างกันสองครั้งกับคำตอบเดียวกัน
และจะให้คำตอบผิดในกรณีที่คลุมเครือ ซึ่งเป็นกรณีที่คุณอยากรู้ผลมากที่สุดพอดี

**ลำดับความแข็งแรงของการตรวจ** เรียงจากดีที่สุดลงมา

```python
# แข็งแรงที่สุด รันเทสของโปรเจกต์เองในโฟลเดอร์ทำงาน
# แข็งแรง import โมดูลที่ถูกแก้แล้วเรียกฟังก์ชันดู
# พอใช้ ไฟล์บนดิสก์มีบรรทัดที่แก้แล้ว และไม่มีบรรทัดที่ผิด
# อ่อน และใช้ได้เฉพาะงานที่ผลลัพธ์ทั้งหมดเป็นร้อยแก้ว ดูคำในคำตอบ
```

**ทำไมลำดับเป็นแบบนี้** เพราะยิ่งลงไปข้างล่าง การตรวจยิ่งห่างจากสิ่งที่คุณ
สนใจจริง คุณไม่ได้สนใจว่าคำว่า median ปรากฏในคำตอบ คุณสนใจว่าฟังก์ชัน median
ทำงานถูก การตรวจคำในคำตอบผ่านได้ด้วย agent ที่พูดว่าทำแล้วโดยไม่ได้ทำอะไรเลย
ซึ่งเป็นความล้มเหลวชนิดที่ eval มีไว้เพื่อจับ

## 4. judge ใช้เมื่อฟังก์ชันตัดสินไม่ได้จริงๆ

มีงานที่เขียนฟังก์ชันตรวจไม่ได้จริง เช่นคำอธิบายนี้ชัดเจนหรือไม่ สรุปนี้
ครอบคลุมประเด็นสำคัญครบหรือไม่ สำหรับงานพวกนั้น LLM-as-judge (การใช้ model
เป็นกรรมการ คือการให้ model อีกตัวตัดสินว่าคำตอบผ่านเกณฑ์หรือไม่) คือทางเลือก
ที่เหลืออยู่

```python
JUDGE_PROMPT = """You are grading one answer against a standard.

The standard
{criteria}

The question
{question}

The answer
{answer}

Reply with the single word PASS or the single word FAIL, then one short
sentence saying why."""
```

```python
def judge(provider, question, answer, criteria):
    """Ask a model whether an answer meets a written standard.

    The verdict is read from the first word rather than parsed out of a
    sentence, because a grader that sometimes cannot be read is worse than
    no grader. Anything that is not clearly a pass counts as a failure, so
    an unreadable verdict never silently becomes a green tick.
    """
```

มีสองการตัดสินใจในโค้ดสั้นๆ นี้ที่สำคัญ

**หนึ่ง เกณฑ์ต้องเขียนไว้เป็นข้อความ** `criteria` เป็น argument ไม่ใช่สิ่งที่
ฝังใน prompt กลาง เพราะกรรมการที่ไม่มีเกณฑ์คือกรรมการที่ตัดสินตามรสนิยม
และรสนิยมของ model เปลี่ยนได้เมื่อคุณเปลี่ยนรุ่น

**สอง อ่านคำตัดสินจากคำแรก และอะไรที่ไม่ใช่ PASS ชัดเจน นับเป็นตก**
กรรมการที่บางครั้งอ่านคำตัดสินไม่ออก แย่กว่าไม่มีกรรมการ เพราะมันสร้าง
ตัวเลขที่ดูน่าเชื่อถือจากผลที่แท้จริงแล้วไม่มีความหมาย การตั้งค่าเริ่มต้น
ให้เป็นตก แปลว่าความคลุมเครือไม่มีทางกลายเป็นเครื่องหมายถูกสีเขียวอย่างเงียบๆ

**ราคาที่ต้องรู้** judge หนึ่งครั้งคือการเรียก model หนึ่งครั้ง ถ้าคุณมี
งานห้าสิบงาน รันสามครั้งต่องาน คุณเพิ่งเพิ่มการเรียก model อีกร้อยห้าสิบครั้ง
ให้ทุกครั้งที่รัน eval นี่คือเหตุผลที่คำแนะนำคือใช้ judge เฉพาะที่จำเป็น
ไม่ใช่ใช้เป็นค่าเริ่มต้น

## 5. eval ต้องรอดจากความล้มเหลวของตัวมันเอง

รายละเอียดที่คนข้ามคือ eval คือโปรแกรมที่รันโปรแกรมที่พังได้ ดังนั้นมันต้อง
ไม่พังไปด้วย

```python
def run_one(task: Task, build_agent) -> Result:
    """Run one task and turn whatever happened into a verdict.

    Building the agent is inside the try because it can fail on its own,
    for a bad workspace or a server that will not start, and one task
    that cannot even begin must not take the whole report with it.
    """
```

```python
    try:
        passed, detail = task.check(answer, task.workspace)
    except Exception as error:
        # A check that throws is a failing task, not a crashed eval run. The
        # whole point is to get a report at the end rather than an exception
        # half way through.
        passed, detail = False, f"the check itself failed, {type(error).__name__}: {error}"
```

**ทำไมสำคัญ** เพราะประโยชน์ทั้งหมดของ eval อยู่ที่ตารางสรุปตอนจบ ถ้างานที่
สิบสองโยน exception แล้วทำให้ทั้งการรันตาย คุณจะไม่ได้ข้อมูลของอีกสามสิบแปด
งานที่เหลือ และคุณจะไม่รู้ว่าการเปลี่ยนแปลงของคุณทำให้อะไรดีขึ้นบ้าง
งานที่พังคือข้อมูล ไม่ใช่อุบัติเหตุ

หลักการเดียวกันนี้ปรากฏในการตั้งชื่องานคู่ขนาน

```python
    # Jobs are labelled by position rather than by name. Two tasks are allowed
    # to share a name, and keying on the name would quietly merge them, turning
    # one task's verdict into the other's and changing the exit code with it.
```

**ทำไมรายละเอียดเล็กๆ แบบนี้ถึงถูกเขียนไว้** เพราะเครื่องมือวัดที่วัดผิด
อันตรายกว่าไม่มีเครื่องมือวัด คนที่ไม่มีตัวเลขรู้ตัวว่าไม่รู้ คนที่มีตัวเลขผิด
เชื่อในสิ่งที่ผิดและตัดสินใจตามนั้น

**ทำไมต้องมี** สามเหตุผล ข้อแรกคือ CI ต้องรันโค้ดของทุกบทได้โดยไม่ต้องมี

## 7. การเลือก model ต้องมาจากการวัด

คำถามที่ทุกคนถามคือ model ตัวไหนดีที่สุด คำถามนั้นไม่มีคำตอบ เพราะไม่มี
บริบทว่าดีสำหรับงานอะไร

**การบอกว่า model ไหนดีกว่าโดยไม่มีชุดทดสอบ คือการเดา** และมันเดาแพงด้วย
เพราะการเลือกตัวที่แพงที่สุดโดยอัตโนมัติทำให้คุณจ่ายเกินสำหรับงานที่ตัวถูก
ทำได้ ส่วนการเลือกตัวถูกที่สุดทำให้คุณเสียรอบไปกับความผิดพลาดที่ตัวแพงไม่ทำ

`Result` เก็บ usage มาด้วยไม่ใช่แค่ผ่านหรือตก

```python
    usage = getattr(agent, "usage", None)
    return Result(
        task=task.name,
        passed=bool(passed),
        detail=str(detail),
        usage={
            "prompt_tokens": getattr(usage, "prompt_tokens", 0),
            "completion_tokens": getattr(usage, "completion_tokens", 0),
            "calls": getattr(usage, "calls", 0),
        },
        answer=answer,
    )
```

**ทำไมต้องเก็บ token ไว้ในผลด้วย** เพราะการเลือก model คือการตัดสินใจสองแกน
ไม่ใช่แกนเดียว model ที่ผ่าน 95 เปอร์เซ็นต์ด้วยราคาสิบเท่า อาจแพ้ model
ที่ผ่าน 90 เปอร์เซ็นต์ในงานที่ความผิดพลาดแก้ง่าย และอาจชนะขาดในงานที่
ความผิดพลาดมีราคาสูง คุณตัดสินใจนั้นไม่ได้ถ้ามีแค่ตัวเลขความถูกต้อง

**แนวทางที่ใช้ได้จริงคือแบ่ง tier ตามงาน** งานถูกอย่างการจัดหมวดหมู่
การสรุปย่อ หรือการตั้งชื่อ ไม่จำเป็นต้องใช้ตัวแพงสุด ส่วนงานที่ต้องวางแผน
หลายขั้นและแก้โค้ด อาจคุ้มที่จะจ่าย และวิธีเดียวที่จะรู้ว่าเส้นแบ่งอยู่ตรงไหน
ในระบบของคุณ คือรัน eval ชุดเดียวกันกับสอง model แล้วเทียบทั้งสองแกน

## 8. รายงานที่อ่านง่ายคือส่วนหนึ่งของเครื่องมือ

```python
def report(results) -> str:
    """A plain table, because a report nobody reads changes nothing."""
    lines = []
    for result in results:
        mark = "pass" if result.passed else "FAIL"
        lines.append(f"{mark}  {result.task}  {result.detail}")
    passed = sum(1 for result in results if result.passed)
    lines.append(f"\n{passed} of {len(results)} tasks passed")
    return "\n".join(lines)
```

**ทำไมเรื่องนี้ถึงถูกนับเป็นการออกแบบ ไม่ใช่ของตกแต่ง** เพราะ eval แข่งกับ
สิ่งเดียว คือความอยากข้ามมันไป ทุกวินาทีที่มันใช้ และทุกบรรทัดที่อ่านไม่รู้เรื่อง
เพิ่มโอกาสที่คนจะเลิกรันมัน เครื่องมือวัดที่ไม่ถูกใช้มีค่าเท่ากับไม่มี
