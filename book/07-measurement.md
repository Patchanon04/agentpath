## 1. ทำไมความรู้สึกว่าดีขึ้นเชื่อไม่ได้

เรื่องตอนเปิดบทเกิดขึ้นเป็นปกติ ไม่ใช่ข้อยกเว้น เพราะ prompt ไม่มี type system ไม่มี
compiler และไม่มีขอบเขต การเปลี่ยนคำหนึ่งคำเปลี่ยนพฤติกรรมในงานทั้งหมดพร้อมกัน ต่าง
จากการแก้ฟังก์ชันหนึ่งตัวซึ่งกระทบเฉพาะคนที่เรียกฟังก์ชันนั้น

สมองไม่ช่วย เพราะการทดสอบด้วยตาเลือกตัวอย่างแบบลำเอียงเสมอ คุณลองงานที่คุณเพิ่งแก้
ให้มันทำได้ คุณจำงานที่ผ่านได้ดีกว่างานที่พังเงียบๆ และเมื่อคุณลงแรงกับการแก้ไปแล้ว
คุณอยากให้มันได้ผล

ความไม่แน่นอนทำให้แย่ลงอีก เพราะ model ไม่ได้ให้คำตอบเดิมทุกครั้ง บทพื้นฐานที่ 3
แสดงว่าความสุ่มอยู่ตรงขั้นเลือกคำ งานที่ผ่านหนึ่งครั้งอาจผ่านสามในสิบครั้ง การรันครั้ง
เดียวแล้วสรุป จึงวัดโชคพอๆ กับวัดคุณภาพ

ทางออกเดียวคือมีชุดงานคงที่ที่รันได้ก่อนและหลัง แล้วเทียบตัวเลข

## 2. eval คือชุดงานที่มีเกณฑ์ตรวจ

eval (การประเมิน คือชุดงานที่รันซ้ำได้พร้อมเกณฑ์ตัดสินว่าผ่านหรือไม่) คือ test suite
ที่ยอมรับว่าผลลัพธ์ไม่แน่นอน ไม่มีอะไรซับซ้อนกว่านั้น

```python
@dataclass
class Task:
    """One thing the agent should be able to do.

    check receives the final answer and the workspace, and returns a pair of
    a boolean and a sentence explaining the verdict. The sentence is not
    decoration. A failing eval you cannot read is a failing eval you will
    ignore.
    """

    name: str
    prompt: str
    check: object
    workspace: object = None
```

`check` คืนประโยคด้วย ไม่ใช่แค่ boolean เพราะ eval ที่บอกว่างานที่เจ็ดล้มเหลวโดยไม่บอก
ว่าล้มเหลวยังไง คือ eval ที่คุณจะเลิกอ่านภายในสัปดาห์เดียว รายงานที่ไม่มีใครอ่านไม่
เปลี่ยนอะไร และมันได้ workspace ด้วย ไม่ใช่แค่คำตอบ เพราะสิ่งที่ agent ทำสำคัญกว่าสิ่ง
ที่ agent พูด ซึ่งคือหัวข้อถัดไป

## 3. การตรวจเชิงกลไกดีกว่า judge เมื่อทำได้

```python
"""Measuring whether the agent actually works.
...
Two kinds of check exist here and the split matters. A mechanical check is a
function that looks at the world and returns true or false. It is free,
instant, and it has no opinions. A judge asks a model whether an answer is
acceptable, which costs money, takes time, and can be wrong. Use a judge only
for the things a function genuinely cannot decide, such as whether an
explanation is clear.
"""
```

การตรวจเชิงกลไกคือฟังก์ชัน Python ธรรมดาที่ไปดูโลกจริงแล้วคืน true หรือ false ไฟล์นี้มี
ข้อความนี้หรือไม่ test ของโปรเจกต์ผ่านหรือไม่ ฟังก์ชันที่ agent เขียนคืนค่าถูกหรือไม่

มันดีกว่าด้วยสามเหตุผล มันฟรี มันได้ผลทันที และมันไม่มีความเห็น ฟังก์ชันที่ตรวจว่า
test ผ่านหรือไม่ ให้คำตอบเดิมทุกครั้งสำหรับสถานะเดิม ในขณะที่ model ที่ทำหน้าที่
กรรมการ อาจให้คำตอบต่างกันสองครั้งกับคำตอบเดียวกัน และจะให้คำตอบผิดในกรณีที่คลุม
เครือ ซึ่งเป็นกรณีที่คุณอยากรู้ผลมากที่สุดพอดี

การตรวจมีลำดับความแข็งแรง เรียงจากดีที่สุดลงมา

1. แข็งแรงที่สุด รัน test ของโปรเจกต์เองในโฟลเดอร์ทำงาน
2. แข็งแรง import โมดูลที่ถูกแก้แล้วเรียกฟังก์ชันดู
3. พอใช้ ไฟล์บนดิสก์มีบรรทัดที่แก้แล้ว และไม่มีบรรทัดที่ผิด
4. อ่อน และใช้ได้เฉพาะงานที่ผลลัพธ์ทั้งหมดเป็นร้อยแก้ว ดูคำในคำตอบ

ยิ่งลงไปข้างล่าง การตรวจยิ่งห่างจากสิ่งที่คุณสนใจจริง คุณไม่ได้สนใจว่าคำว่า median
ปรากฏในคำตอบ คุณสนใจว่าฟังก์ชัน median ทำงานถูก การตรวจคำในคำตอบผ่านได้ด้วย agent
ที่พูดว่าทำแล้วโดยไม่ได้ทำอะไรเลย ซึ่งเป็นความล้มเหลวชนิดที่ eval มีไว้เพื่อจับครับ

## 4. judge ใช้เมื่อฟังก์ชันตัดสินไม่ได้จริงๆ

มีงานที่เขียนฟังก์ชันตรวจไม่ได้จริง เช่นคำอธิบายนี้ชัดเจนหรือไม่ สรุปนี้ครอบคลุม
ประเด็นสำคัญครบหรือไม่ สำหรับงานพวกนั้น LLM-as-judge คือทางเลือกที่เหลืออยู่

```python
JUDGE_PROMPT = """You are grading one answer against a standard.

The standard
{criteria}

The question
{question}

The answer
{answer}

Reply with the single word PASS or the single word FAIL, then one short
sentence saying why."""
```

```python
def judge(provider, question, answer, criteria):
    """Ask a model whether an answer meets a written standard.

    The verdict is read from the first word rather than parsed out of a
    sentence, because a grader that sometimes cannot be read is worse than
    no grader. Anything that is not clearly a pass counts as a failure, so
    an unreadable verdict never silently becomes a green tick.
    """
```

มีสองการตัดสินใจในโค้ดสั้นๆ นี้ที่สำคัญ

เกณฑ์ต้องเขียนไว้เป็นข้อความ `criteria` เป็น argument ไม่ใช่สิ่งที่ฝังใน prompt กลาง
เพราะกรรมการที่ไม่มีเกณฑ์คือกรรมการที่ตัดสินตามรสนิยม และรสนิยมของ model เปลี่ยนได้
เมื่อคุณเปลี่ยนรุ่น

คำตัดสินอ่านจากคำแรก และอะไรที่ไม่ใช่ PASS ชัดเจนนับเป็นตก กรรมการที่บางครั้งอ่านคำ
ตัดสินไม่ออก แย่กว่าไม่มีกรรมการ เพราะมันสร้างตัวเลขที่ดูน่าเชื่อถือจากผลที่แท้จริงแล้ว
ไม่มีความหมาย การตั้งค่าเริ่มต้นให้เป็นตก แปลว่าความคลุมเครือไม่มีทางกลายเป็นเครื่อง
หมายถูกสีเขียวอย่างเงียบๆ

ราคาที่ต้องรู้ judge หนึ่งครั้งคือการเรียก model หนึ่งครั้ง ถ้าคุณมีงานห้าสิบงาน รันสาม
ครั้งต่องาน คุณเพิ่งเพิ่มการเรียก model อีกร้อยห้าสิบครั้งให้ทุกครั้งที่รัน eval นี่คือ
เหตุผลที่คำแนะนำคือใช้ judge เฉพาะที่จำเป็น ไม่ใช่ใช้เป็นค่าเริ่มต้น

## 5. eval ต้องรอดจากความล้มเหลวของตัวมันเอง

eval คือโปรแกรมที่รันโปรแกรมที่พังได้ นี่คือรายละเอียดที่คนข้าม และมันแปลว่าตัว eval
เองต้องไม่พังไปด้วยเมื่อสิ่งที่มันรันพัง

```python
def run_one(task: Task, build_agent) -> Result:
    """Run one task and turn whatever happened into a verdict.

    Building the agent is inside the try because it can fail on its own,
    for a bad workspace or a server that will not start, and one task
    that cannot even begin must not take the whole report with it.
    """
```

```python
    try:
        passed, detail = task.check(answer, task.workspace)
    except Exception as error:
        # A check that throws is a failing task, not a crashed eval run. The
        # whole point is to get a report at the end rather than an exception
        # half way through.
        passed, detail = False, f"the check itself failed, {type(error).__name__}: {error}"
```

ประโยชน์ทั้งหมดของ eval อยู่ที่ตารางสรุปตอนจบ ถ้างานที่สิบสองโยน exception
แล้วพาทั้งการรันตาย คุณจะไม่ได้ข้อมูลของอีกสามสิบแปดงานที่เหลือ และคุณจะไม่รู้ว่าการเปลี่ยน
แปลงของคุณทำให้อะไรดีขึ้นบ้าง งานที่พังคือข้อมูล ไม่ใช่อุบัติเหตุ

หลักการเดียวกันนี้ปรากฏในการตั้งชื่องานคู่ขนาน

```python
    # Jobs are labelled by position rather than by name. Two tasks are allowed
    # to share a name, and keying on the name would quietly merge them, turning
    # one task's verdict into the other's and changing the exit code with it.
```

รายละเอียดเล็กๆ แบบนี้ถูกเขียนไว้ เพราะเครื่องมือวัดที่วัดผิดอันตรายกว่าไม่มีเครื่องมือ
วัด คนที่ไม่มีตัวเลขรู้ตัวว่าไม่รู้ คนที่มีตัวเลขผิดเชื่อในสิ่งที่ผิดและตัดสินใจตามนั้นครับ

## 7. การเลือก model ต้องมาจากการวัด

คำถามที่ทุกคนถามคือ model ตัวไหนดีที่สุด คำถามนั้นไม่มีคำตอบ เพราะไม่มีบริบทว่าดี
สำหรับงานอะไร

**การบอกว่า model ไหนดีกว่าโดยไม่มีชุดทดสอบ คือการเดา**

และมันเดาแพงด้วย เลือกตัวแพงสุด คุณจ่ายเกินสำหรับงานที่ตัวถูกทำได้ เลือกตัวถูกสุด คุณ
เสียรอบไปกับความผิดพลาดที่ตัวแพงไม่ทำ

`Result` เก็บ usage มาด้วยไม่ใช่แค่ผ่านหรือตก

```python
    usage = getattr(agent, "usage", None)
    return Result(
        task=task.name,
        passed=bool(passed),
        detail=str(detail),
        usage={
            "prompt_tokens": getattr(usage, "prompt_tokens", 0),
            "completion_tokens": getattr(usage, "completion_tokens", 0),
            "calls": getattr(usage, "calls", 0),
        },
        answer=answer,
    )
```

token อยู่ในผลด้วย เพราะการเลือก model คือการตัดสินใจสองแกน ไม่ใช่แกนเดียว model ที่
ผ่าน 95 เปอร์เซ็นต์ด้วยราคาสิบเท่า อาจแพ้ model ที่ผ่าน 90 เปอร์เซ็นต์ในงานที่ความผิด
พลาดแก้ง่าย และอาจชนะขาดในงานที่ความผิดพลาดมีราคาสูง คุณตัดสินใจนั้นไม่ได้ถ้ามีแค่
ตัวเลขความถูกต้อง

แนวทางที่ใช้ได้จริงคือแบ่ง tier ตามงาน งานถูกอย่างการจัดหมวดหมู่ การสรุปย่อ หรือการ
ตั้งชื่อ ไม่จำเป็นต้องใช้ตัวแพงสุด ส่วนงานที่ต้องวางแผนหลายขั้นและแก้โค้ด อาจคุ้มที่จะ
จ่าย และวิธีเดียวที่จะรู้ว่าเส้นแบ่งอยู่ตรงไหนในระบบของคุณ คือรัน eval ชุดเดียวกันกับ
สอง model แล้วเทียบทั้งสองแกน

## 8. รายงานที่อ่านง่ายคือส่วนหนึ่งของเครื่องมือ

```python
def report(results) -> str:
    """A plain table, because a report nobody reads changes nothing."""
    lines = []
    for result in results:
        mark = "pass" if result.passed else "FAIL"
        lines.append(f"{mark}  {result.task}  {result.detail}")
    passed = sum(1 for result in results if result.passed)
    lines.append(f"\n{passed} of {len(results)} tasks passed")
    return "\n".join(lines)
```

เรื่องนี้ถูกนับเป็นการออกแบบ ไม่ใช่ของตกแต่ง เพราะ eval แข่งกับสิ่งเดียว คือความอยาก
ข้ามมันไป ทุกวินาทีที่มันใช้ และทุกบรรทัดที่อ่านไม่รู้เรื่อง เพิ่มโอกาสที่คนจะเลิกรันมัน
เครื่องมือวัดที่ไม่ถูกใช้มีค่าเท่ากับไม่มีครับ
